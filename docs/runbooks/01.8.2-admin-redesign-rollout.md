# Runbook: 01.8.2 admin redesign rollout (D-05, D-06, D-07)

**This is an operator-run runbook.** Plan `01.8.2-06` wrote it. **Plan `01.8.2-22` is the plan
that actually executes it** against production — this document is the checklist that plan
follows, not a record of something already run. If you are reading this before plan 01.8.2-22
has landed, nothing here has happened yet.

## Why this exists

This deploy ships two things at once, on purpose (D-07 — **same deploy (D-07)**, not a
staged rollout):

1. The clear-slate migration (`priv/repo/migrations/20260923140000_clear_estantes_and_assignments.exs`,
   D-05) — it **deletes every `shelves` row** and **nilifies every shelf assignment**
   (`games.shelf_id` and every `copies.shelf_id`/`position`), so every copy becomes `Sin
   ubicar`. There is no backfill and no "not yet reviewed" placement state — see the
   migration's own moduledoc.
2. The rebuilt Estantes page (`EstanteLive.Index`, plan 01.8.2-01), Administrar estantes (plan
   01.8.2-18) and the other admin screens this phase redesigned.

**They must ship in the same deploy (D-07).** If the migration ran without the rebuild screen,
production would have a cleared shelf map with no way to recreate it — worse than either state
alone. Confirming this is Task 2's job below, before anything runs.

`down/0` on the migration **raises `Ecto.MigrationError`** rather than pretending a rollback is
possible — D-05's clear has no audit table, because nothing survives the delete that a
rollback could read to reconstruct the room. **The pre-deploy `pg_dump` in Step 1 is therefore
the only recovery path this deploy has**, not a formality.

**Production's shelf state has never been measured** (RESEARCH.md assumption A3). Dev's near-zero
cost — 1 estante, 1 shelved game, measured 2026-09-22 — is not evidence about production; it may
hold real walk-the-shelf work from 01.8.1 that dev never had. Step 2 exists specifically to close
that gap before the migration runs, not after.

## Step 1 — Pre-deploy `pg_dump` (BLOCKING GATE — do not skip either condition)

**This step is a hard gate on the deploy, not a suggestion.** The deploy in Step 4 does **not
proceed** unless BOTH of these are true:

- [ ] **Condition A — the dump was taken.** A fresh `pg_dump` of the production database exists,
      dated the same day as this deploy (the nightly backup from `.github/workflows/backup.yml`
      is not sufficient by itself — it may be hours stale by deploy time; take a fresh one).
- [ ] **Condition B — the dump was verified restorable.** The dump was test-restored (to a scratch
      database, or at minimum `gunzip -t` + `pg_restore --list` against it) and confirmed
      non-empty and structurally intact. A dump that was merely *produced* and never *checked*
      does not satisfy this gate — a corrupt or truncated dump discovered only after the
      migration has already deleted production's shelf data is not a backup.

Do not proceed past this step until both boxes are genuinely checked. If either is false, HOLD
the deploy and fix the dump before continuing — do not run Step 4 "and dump afterward."

**Command** (same shape as the nightly backup in `.github/workflows/backup.yml`, run manually
immediately before this deploy):

```bash
ssh -o StrictHostKeyChecking=accept-new deploy@<DEPLOY_HOST> '
  set -euo pipefail
  ENV_FILE=$(mktemp)
  chmod 600 "$ENV_FILE"
  trap "rm -f \"$ENV_FILE\"" EXIT
  cat > "$ENV_FILE"
  sudo docker exec --env-file "$ENV_FILE" db bash -c \
    "set -o pipefail; pg_dump -U postgres pukllay_club_prod | gzip"
' <<< "PGPASSWORD=<POSTGRES_PASSWORD>" \
  > "01.8.2-pre-deploy-$(date +%F).sql.gz"
```

**Where the dump goes:** download it off the runner/operator machine to durable storage before
proceeding — the same Cloudflare R2 backup bucket the nightly job uses
(`docs/runbooks/production-secrets.md` has the R2 credentials), under a name that marks it as
this deploy's pre-migration dump (e.g. `01.8.2-pre-deploy-<date>.sql.gz`), not overwriting the
nightly rotation.

**Verify restorable:**

```bash
gzip -t "01.8.2-pre-deploy-$(date +%F).sql.gz"          # Condition B, part 1: not corrupt
gunzip -c "01.8.2-pre-deploy-$(date +%F).sql.gz" | pg_restore --list > /dev/null  # part 2: structurally intact
```

Record the dump's path, its size, and the restore-verification result in plan 01.8.2-22's
summary — "a dump exists" is not the recorded fact; "a dump exists and was proven restorable"
is.

## Step 2 — Pre-deploy baseline counts

Before the migration runs, capture the same three counts D-06's migration itself will log —
this is how the migration's own report gets checked against an independent, pre-deploy
measurement, not just trusted on its own say-so:

```sql
SELECT count(*) FROM shelves;
SELECT count(*) FROM games WHERE shelf_id IS NOT NULL;
SELECT count(*) FROM copies WHERE shelf_id IS NOT NULL;
```

Run these against production **before** the deploy (over the same `eval` invocation shape as
Step 5, or directly via `psql` if a read-only connection is available) and record all three
numbers, with the date, in plan 01.8.2-22's summary.

**If production's `shelves` or `games.shelf_id` counts are materially larger than dev's
measured 1 and 1** (2026-09-22), STOP and re-confirm with the developer before proceeding — D-05
was decided knowing dev's cost was near zero; a much larger production count means the
walk-the-shelf re-work staff face afterward is a real cost that decision did not price in.

## Step 3 — Same-deploy gate (D-07)

Before merging/deploying, confirm the deploy image's git SHA carries **both**:

- [ ] The clear-slate migration (`20260923140000_clear_estantes_and_assignments.exs`, plan
      01.8.2-06)
- [ ] The rebuilt Estantes page and Administrar estantes (plans 01.8.2-01, -13, -16, -18)

**This migration must not ship in a deploy that does not also carry the Estantes rebuild
screens.** If the SHA does not carry both, HOLD — do not deploy the migration alone.

## Step 4 — Deploy

Merge and deploy per this repo's standard Kamal path (`config/deploy.yml`,
`.github/workflows/deploy.yml`). Kamal only routes traffic to the new container after
`bin/migrate` and the health check both succeed, so a migration failure here simply keeps the
old container serving traffic rather than corrupting the new one mid-flight.

## Step 5 — Post-deploy checks

Using the production `eval` invocation (see "Production invocation" below — **never `rpc`**),
confirm:

- [ ] `SELECT count(*) FROM shelves` is `0`
- [ ] `SELECT count(*) FROM games WHERE shelf_id IS NOT NULL` is `0`
- [ ] `SELECT count(*) FROM copies WHERE shelf_id IS NOT NULL` is `0` and every copy reads
      `Sin ubicar` in the UI
- [ ] `/admin/estantes` is reachable for a staff session
- [ ] Administrar estantes shows D-09's first-run empty state and **Nuevo estante** successfully
      creates an estante

**Expected noise, not a bug:** the Pendientes badge on `/admin/estantes` will show roughly the
full copy count (measured on dev: 435) as `Sin ubicar` immediately after this migration runs —
this is D-05's intended state, accepted explicitly during planning, and clears only as staff
physically walk the shelves and re-place each copy. Do not treat this badge count as a
regression.

**Compare against the migration's own logged line.** The migration emits one `Logger.info` JSON
line (`estantes_removed`, `assignments_removed`, `copies_unplaced`, `at`) the moment it runs —
pull it from the deploy logs (`kamal app logs`, or Sentry's Logs UI per
`docs/runbooks/production-bgg-reenrichment.md`'s note that `Sentry.LoggerHandler` mirrors every
`Logger.info` call) and confirm `estantes_removed`/`assignments_removed` match Step 2's
independently-captured pre-deploy counts exactly. A mismatch means something changed shelf data
between Step 2's measurement and the migration's run — investigate before treating the deploy
as verified.

## Production invocation: `eval`, never `rpc`

Per `docs/runbooks/production-bgg-reenrichment.md`'s finding (2026-09-22): `rpc` returns
`:noconnection` against this production container for reasons that were investigated and never
resolved. **Every production-side check in this runbook uses `eval`** with the required-processes
preamble, exactly as that runbook establishes:

```bash
ssh deploy@<DEPLOY_HOST>
docker ps   # find the running pukllay_club-web-<suffix> container; don't hardcode the suffix
docker exec pukllay_club-web-<container-suffix> bin/pukllay_club eval '
{:ok, _} = Application.ensure_all_started(:req)
{:ok, _} = Application.ensure_all_started(:ecto_sql)
{:ok, _} = PukllayClub.Repo.start_link()
# ad-hoc query or Release.* call here
'
```

The `:req`/`:ecto_sql`/`Repo.start_link` preamble is not optional — skipping the `:ecto_sql`
line specifically fails with a missing `DBConnection.Watcher` process, per the same runbook's
"easiest thing to get wrong" note. Never substitute `rpc` for this shape in this runbook.

## Rollback

There is **no code-level rollback for the clear-slate migration** — its `down/0` raises
`Ecto.MigrationError` by design (see the migration's moduledoc). The only recovery is restoring
Step 1's verified `pg_dump`. If the post-deploy checks in Step 5 fail in a way that indicates the
migration ran against the wrong data (rather than, say, the Estantes page itself having an
unrelated bug), STOP, do not attempt a partial fix, and restore from that dump.
