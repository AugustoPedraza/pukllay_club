Sketch 018 — Theme Toggle Subtlety vs Social Icons:

Theme Toggle Subtlety

Follow-up to sketch 014 (winner D: bare icons, no card, monochromatic). That sketch solved footprint — the toggle no longer reads as a boxed widget bolted onto the row. It did not solve weight relative to its neighbors: the shipped toggle's rest-state icon color (--color-text-muted) is identical to the social icons' rest color, and its active state jumps to full --color-primary + underline — which can make the "on" icon heavier than any social icon at rest. Raised after the footer-desktop-imbalance debug session shipped: "social links are more relevant, aren't?"

Each variant below reconstructs the real .pk-footer-social + .pk-footer-theme markup from assets/css/app.css so the comparison is against shipped values, not an approximation. All 3 states (system/light/dark) are kept — collapsing to a 2-state toggle was already tested and rejected in sketch 014 (loses live OS-following). The "Tema" label is kept — it exists for discoverability (01.1-08-PLAN.md).

Footer right cluster — social + theme (light)
Tema
social icon: 14px glyph in 28px ring, border always visible toggle icon (rest): 17px glyph, no ring, faded ~55% toward surface toggle icon (active "Sistema"): unchanged — full primary + underline

Only lever: rest-state icon color faded. Active state and icon size untouched — tests whether dimming idle icons alone is enough, or whether the active one still steals attention. Rejected: live-checked in dark theme, rest-state icons became nearly invisible against the dark purple background.

Footer right cluster — social + theme (light)
Tema
social icon: 14px glyph in 28px ring toggle icon (rest): 14px glyph — matched to social's glyph size toggle icon (active): muted-primary tint, shorter underline

Three levers together: faded rest color, glyph size matched to the social icons' own 14px (not today's 17px), and the active indicator toned down so "on" no longer outweighs a hovered social icon.

Footer right cluster — social + theme (light) — hover/focus the theme control to reveal it
Tema
social icon: full opacity always theme control (rest): 50% opacity as a unit — label + all 3 icons theme control (hover/focus): 100% opacity, unchanged colors/sizes

Single lever, common "utility chrome recedes until touched" pattern (GitHub docs, VS Code status bar). Simplest CSS. Risk: discoverability — a control that's 50% transparent at rest may read as disabled rather than de-emphasized, especially for the "Tema" label whose whole point was discoverability.

What to look for

  • Click through system/light/dark in each variant — does the "on" icon ever outweigh a resting social icon?
  • Toggle light/dark page theme (toolbar, bottom-right) — does the faded rest color stay legible in dark mode, or does it disappear entirely?
  • Variant C: tab to the theme control with keyboard — does focus-reveal feel intentional or does the control feel broken/disabled before you touch it?
  • Compare B's 14px glyphs directly against the social icons' 14px glyphs — same size, does the toggle still read as distinct enough to operate?
