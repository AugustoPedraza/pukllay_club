A: Converged Baseline

The real current header structure (logo · nav-or-crumb · search[Catálogo only] · actions[CTA+toggle]), with all three just-finalized winners applied: 013-E (nav links plain text at rest, CTA outline-only until hover — nothing has a filled background at rest), 014-D (bare-icon theme toggle, no card/border), 015-A (active link gets a thick offset underline). Composition rule used here: 013-E decides REST weight (flat), 015-A decides the ACTIVE signal (underline) — the two winners layer rather than compete.

Mobile view reuses sketch 011's validated drawer (hamburger → search + nav + CTA) as-is, since that's the last fully-validated mobile pattern for this shell.

Flag: the real shipped app.css (as of quick task 260822-2v9) does not currently implement a hamburger/drawer at all — at ≤480px it just hides .pk-nav-links outright and shows a separate mobile filter-chip row instead. Sketch 011's drawer was validated in sketch form but was never carried into the real build. This variant renders the drawer as instructed (last validated mobile pattern) — worth deciding explicitly whether to reconcile code with sketch or keep the current simpler mobile behavior.

What to look for

  • Switch pages (Catálogo/Detalle/Acerca de) at Desktop — does the row still feel busy once every element is individually calm?
  • Switch to Mobile — does the drawer pattern feel right, or does today's simpler "hide nav, show chips" behavior make more sense to keep?
  • This is the direct answer to "does it still feel overloaded" — compare against B and C.

B: Expandable Search

Search collapses to a bare icon at rest — no permanent width taken — and expands inline on click, Netflix/Amazon-style (this project's own MANIFEST already names Netflix as a reference point; sketch 008 noted this exact behavior during the original filter-search exploration). While expanded, the rest of the cluster dims and becomes inert so the search doesn't compete with anything else in the row. Closes on the ✕, Escape, or clicking outside.

Mobile call (documented per instruction): on mobile the search icon becomes the sole search entry point — tapping it opens a full-width overlay across the header instead of inline expansion (260px has nowhere to go on a 390px frame). The hamburger drawer no longer duplicates a search field — it holds nav links only. Rationale: two separate search entry points (drawer field + header icon) on the same small viewport would be redundant chrome fighting for the same job; one icon, reachable directly without opening the drawer first, is a shorter path to the action people actually reach for search for.

What to look for

  • Click the search icon at Desktop on Catálogo — does the expand/collapse feel fast and clear, or disorienting?
  • Switch to Mobile, tap the icon — does the full-width overlay feel like the obvious "this is now search mode" state?
  • Does removing the drawer's own search field (mobile) feel like a real simplification, or does it now take an extra tap to reach search from a scrolled-away position?

C: Fully Contextual

Two changes from A, composed together: search stays Catálogo-only (already validated in 003/011 — correctly wired here alongside the new CTA/toggle winners, which round 1 of 013–016 hadn't yet composed together). And a direct answer to "the navigation still looks weird": nav links are no longer floating alone in the middle of the row — they're grouped with the brand into one left-side identity cluster (logo + Inicio + Quiénes Somos, separated by a thin divider from the rest of the row), leaving a clearly separate right-side actions cluster (CTA + toggle). The row now reads as two purposeful groups instead of four loose items in sequence.

What to look for

  • Does grouping nav with the brand make "Inicio / Quiénes Somos" read as site identity/wayfinding rather than a stray floating pair?
  • Does the divider read as a real structural break, or just decoration?
  • On Detalle, the crumb sits inside the same left cluster as the brand — does that still make sense, or does the crumb want its own position?

Round 2

D: Minimal Header

The boldest cut. Header = logo + one plain "Quiénes Somos" link + Catálogo-only expandable search (B's exact mechanism). CTA and toggle are removed from the header entirely.

CTA placement: research is consistent that a persistent header CTA asks someone to convert before they've seen any reason to — "a prominent in-layout button is often enough" once the value case has actually been made. Sumate now lives where that case exists: the Acerca de hero (reusing sketch 004's hero-CTA pattern/copy). Mobile call: a sticky bottom CTA bar appears ONLY on Acerca de, not site-wide — mirroring sketch 005's already-validated detail-page sticky bar, which is also contextual to one page, not global. A site-wide sticky CTA would re-introduce exactly the "asking before context" problem this variant is trying to remove.

Toggle placement: footer is the conventional "affordable area" for utility controls (language/theme switchers) — users already expect to find them there. Relocated to the real footer's right cluster, next to the social icons (see the mini footer preview below the page content above).

Side effect worth naming: with only one link and one icon left in the header, there's nothing left to hide at narrow widths — no hamburger, no drawer needed at all. That's not a separate mobile treatment bolted on, it falls out of the reduction itself.

What to look for

  • Does identity + one link + search feel like "enough" header, or does something feel missing?
  • Switch to Acerca de — does the CTA in the hero feel like it lands better with context around it than it did floating in the header?
  • Mobile, Acerca de: does the sticky bar feel earned (only shows where the case was made), or would you rather it always be reachable?
  • Check the footer's toggle placement — does "Tema" next to social icons feel discoverable, or too easy to miss?

E: Toggle-Out Only

Isolates one variable. Everything is identical to B (expandable search, CTA in the header, same drawer) — the only change is the theme toggle relocating to the footer's right cluster, using the exact same markup/CSS as variant D's footer toggle so the two stay consistent with each other regardless of which composition wins.

Purpose: D removes the CTA and the toggle and simplifies nav all at once — too many variables changing together to know which one was driving "still feels overloaded." E changes exactly one thing from your current favorite (B), so the effect of removing the toggle specifically can be judged on its own.

What to look for

  • Compare directly against B — does the header feel meaningfully calmer with just the toggle gone?
  • Or does it still feel busy, meaning the toggle wasn't the (only) source of the overload feeling?

Round 2

F: Nav Semantics Fix

Isolated from the CTA/toggle question on purpose — everything else here is identical to B. Catálogo and Acerca de already share one .links-plain treatment (that part was never actually inconsistent). The real mismatch is Detalle's crumb: it renders "Ludoteca / Catan" styled close enough to a nav-links row that it reads like a third, slightly-different variant of the same component — but it isn't a peer-navigation control at all, it's a drill-down back-affordance, a fundamentally different job.

The fix: stop trying to make it look like nav-links. Detalle now shows a small, deliberately distinct "‹ Ludoteca" back-caret — muted color, no border-bottom, no active-underline treatment, no second "/ Catan" segment (the page's own title already says which game this is). This is exactly the real app's own narrow-viewport crumb collapse behavior (.pk-nav-crumb a::before { content: "‹ "; } in the shipped app.css) — today it only applies below 480px; this variant asks whether it's simply the right treatment everywhere, not a mobile-only concession.

What to look for

  • Switch to Detalle — does "‹ Ludoteca" read clearly as "go back," distinct from the Inicio/Quiénes Somos pair?
  • Does dropping the "/ Catan" segment lose anything, given the page's own heading already names the game?
  • Does this alone address what felt "weird" about navigation, or was it really the CTA/toggle competing for attention (see D/E) rather than the nav styling itself?
