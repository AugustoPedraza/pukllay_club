## Resolution

root_cause: "The close button (`.pk-lightbox-close`) and both chevron buttons
(`.pk-lightbox-chevron-prev`/`.pk-lightbox-chevron-next`) are markup-identical daisyUI
`btn btn-circle min-h-11 min-w-11` controls sitting on the same opaque `--pk-shadow-color` backdrop,
but only the close button received the dark-theme color-treatment fix from G-01.2-20 (plan 01.2-30):
`[data-theme=\"dark\"] .pk-lightbox-close { --btn-color: var(--color-neutral); --btn-fg:
var(--color-neutral-content); }` (assets/css/app.css lines 3584-3587). No equivalent rule exists for
either chevron (confirmed by grep — zero `--btn-color`/`--btn-fg` overrides scoped to
`.pk-lightbox-chevron*` anywhere in app.css). That fix was deliberately scoped to the close button
only, on the stated rationale that the chevrons 'passed UAT test 21 in both themes on this same
stage' (app.css line 3581-3582) — but test 21 passed one gap-closure round BEFORE G-01.2-19 (plan
01.2-31) changed `.pk-lightbox`'s own full-viewport field from a translucent scrim to the same
full-strength opaque `--pk-shadow-color` fill `.pk-lightbox-img` uses. That backdrop-opacity change
is the exact condition that turned the close button's identical unmodified-daisyUI fill from legible
to a ≈1.1:1 near-invisible chip in dark theme (G-01.2-20's own root cause). The chevrons never got
re-tested after that environmental change and never got the corresponding fill fix, so today they
carry the SAME latent near-invisible dark-theme defect the close button had before 01.2-30 — while
the close button now looks like a distinct, filled, higher-contrast chip. The user's 'must be
consistent' report is a direct, accurate observation of this asymmetric fix: one of three sibling
controls was patched, two were not, against an assumption (test 21's pass) that stopped being valid
one round later."
