## Resolution

root_cause: No code defect. `Catalog.similar_games/1` (`lib/pukllay_club/catalog.ex:178-202`)
intentionally hard-filters same-weight-band candidates with no fallback/widening path when that
pool is small — this is a deliberate, documented design decision (see the function's own
moduledoc) that was explicitly flagged in `01.2-UI-SPEC.md` as a 🧪 backstop scenario requiring
human judgment, and was verified present-and-working exactly as spec'd
(`01.2-VERIFICATION.md` human_verification item 7). The UAT response (G-01.2-7) is a product/UX
policy objection to that accepted backstop — the user does not want a sparse rail to ever be
considered acceptable, and is proposing a broader "Otras sugerencias" fallback shelf instead.
Separately confirmed: with the catalog's real current data (46/179/183 games per weight band,
26 nil-band), a literal 1-2-card rail cannot occur today under any populated `weight_band` — the
UAT item's premise ("very few members") does not match the live catalog's current composition,
so this is a forward-looking guarantee request, not a currently-reproducible broken render.

fix: Not applied — goal was find_root_cause_only. Concrete direction data for plan-phase:
1. The `where: g.weight_band == ^weight_band` clause in `similar_games/1` is the sole
   selectivity constraint; any fix lands there (or in a new sibling function), not in the
   LiveView/template layer (`safe_similar_games/1`/`carousel_row/1` have no independent
   data-fetching capability today).
2. Data available to build a widening fallback pool without any new seed/enrichment work:
   `mechanics`/`themes` (already used for ranking), `tags` (editorial hashtags),
   `min_players`/`max_players`, `min_playtime`/`max_playtime`/`playing_time`, `bgg_weight` (a
   continuous complexity float, independent of the 3-bucket weight_band string — usable for a
   numeric-distance fallback instead of a hard band cliff), `Vocabulary.weight_band_level/1`
   (adjacent-band-by-ordinal-distance fallback). No popularity/BGG-rank field exists in the
   schema — a popularity-based fallback is NOT available without new data/enrichment work; every
   other fallback strategy is.
3. Candidate fallback shapes (for the planner to choose from, not decided here): (a) widen to
   adjacent weight bands by `weight_band_level` distance when the same-band pool is below some
   floor, ranked after true band-mates; (b) drop the band hard-filter for a top-up pool, ranking
   ALL other games by the existing mechanics/themes overlap score alone and appending enough to
   reach a minimum shelf size; (c) rank by `bgg_weight` numeric proximity instead of/alongside
   the band bucket, avoiding the discrete-band cliff entirely. Any of (a)/(b)/(c) may also need a
   conditional shelf title swap ("Juegos similares" -> "Otras sugerencias") per the user's own
   proposed copy, which is a template-layer decision, not just a query-layer one.
