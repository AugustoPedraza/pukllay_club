  over rules in any named layer, regardless of selector specificity or source order. This is
  confirmed directly against the built asset, not inferred: in

- timestamp: 2026-08-26T13:18:00Z

  found: **below 768px**, only the unlayered `position: static` rule applies to `.pk-poster-col` (no
  media-query override matches) — it beats the layered `.relative { position: relative }` utility

  template explicitly adding `relative` to fix exactly this. **At >=768px**, the unlayered
  `@media (min-width: 48rem) { .pk-poster-col { position: sticky; ... } }` rule applies instead —
  also unlayered, so no conflict with the (moot, already-losing) `.relative` utility; `sticky`
  happens to be a non-static position value on its own, so the containing-block requirement is
  accidentally satisfied on desktop only.
  implication: the share-control's absolutely-positioned wrapper has a valid containing block
  (`.pk-poster-col`) on desktop, but **no positioned ancestor at all below 768px** — `.pk-poster-col`

  `grep -n "position:" assets/css/app.css` cross-referenced against every ancestor selector). Per the
  CSS absolute-positioning spec, the wrapper's containing block therefore falls all the way to the

## Resolution

root_cause: "Two independently-confirmed contributing causes (AND-gate: both fire, on different
parts of the reported symptom — the position bug explains 'mobile is even worse' specifically,
while the low-contrast panel fill is a standing, previously-documented condition of this app's
whole design-token ladder that plausibly explains the shared 'isn't correct'/'not a self-contained
panel' read on both breakpoints). (1) CODE — `lib/pukllay_club_web/live/catalog_live/show.ex:292`'s
`relative` Tailwind utility on `.pk-poster-col`, added by plan 01.2-04 Task 2 specifically to give
the new absolutely-positioned share-control wrapper (show.ex:293-295) a containing block, is
silently defeated below the 768px detail breakpoint by `assets/css/app.css`'s unlayered
`.pk-poster-col { position: static; }` base rule (app.css:2279-2281) — because every custom `.pk-*`
rule in `app.css` is written outside any `@layer` block while Tailwind v4's own utility classes
(including `.relative`) live inside `@layer utilities`, and per the CSS Cascading and Layers spec
unlayered rules always beat layered ones regardless of specificity or source order. Verified
directly against the compiled `priv/static/assets/css/app.css`: `@layer utilities {}` spans lines
192-3602 and contains `.relative { position: relative; }` (line 1770); `.pk-poster-col`'s own rules
sit at lines 4693 and 4866, both outside that block. Below 768px, `.pk-poster-col` therefore
computes to `position: static`, and — since no ancestor between it and the document root is
positioned (`<main>` in `layouts.ex:520` carries no position rule) — the share-control wrapper's
absolute positioning resolves against the initial containing block (the top of the whole page), not
the buy-box panel, rendering it detached and near the page's top-right corner instead of anchored
over the cover art. At >=768px this is masked because `.pk-poster-col` separately gets
`position: sticky` from another unlayered rule in the same file, which is non-static and therefore
accidentally satisfies the containing-block requirement — so this specific defect is mobile-only,
matching 'mobile is even worse' precisely. (2) DESIGN TOKEN — the buy-box panel's only boundary
against the page (`bg-base-200` with no border/shadow, deliberately per the plan) reuses a
base-200/base-100 token pair independently measured elsewhere in this exact codebase at 1.415:1
(light) / 1.086:1 (dark) contrast, both well under this app's own documented 3:1 floor — a standing,
previously-diagnosed condition of the whole surface ladder that plausibly weakens the
'self-contained panel distinct from the reading column' read on every viewport width, though with
lower confidence than cause (1) since real whitespace/rounding/padding differentiators (absent in
the prior KB case) are present here."
