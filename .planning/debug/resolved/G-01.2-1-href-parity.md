## Resolution

root_cause: |
  No code-level defect exists in the D-08 `?from=` href-parity feature itself. The two
  `detail_path/2` implementations (`GameCard` and `GamePreview`) are byte-identical, mirrored
  clauses, and — critically — both hrefs for a given card are rendered from the SAME parent
  `game_card/1` invocation consuming the SAME `@from` assign in one pass, so no code path can
  make them diverge for a given render. The grid (the results/filtered surface) correctly wires
  `from={@from_query}` (`index.ex:812`), and `@from_query` is correctly recomputed by
  `apply_filters/1` on every filter-changing event (search, facet/scalar toggle, clear-filters,
  retry, URL deep-link).

  The user's "I can't see that query string" report is best explained by a REPRODUCTION-CONDITIONS
  gap, not an implementation gap: carousel-surface cards (the default/unfiltered browse view)
  deliberately never carry a `from` param by design (documented in `GameCard`'s own moduledoc,
  since carousels only render when `browsing_results?/1` is false — there is no filter state to
  forward). If the tester's reproduction attempt never actually transitioned the app into the
  results-grid surface with an active filter — plausible, and directly evidenced by the
  co-reported G-01.2-2 gap ("search is totally broken. I type and nothing happen," filed in the
  same UAT session immediately after this test) — then every card on screen, of both link types,
  would correctly show no `?from=`, exactly matching the report. This is either (a) a UAT
  instruction gap (Test 1's steps do not explicitly tell the tester to confirm the grid/results
  heading — "Ver X juegos" — is showing before inspecting hrefs), or (b) fully entangled with and
  downstream of G-01.2-2 (if search visibly does nothing, the tester cannot reach the grid surface
  via search at all).
