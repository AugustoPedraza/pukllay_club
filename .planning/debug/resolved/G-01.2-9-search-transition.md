## Resolution

root_cause: >
  The catalog's entire search/filter pipeline (`phx-change="search"` on the nav search input →
  `handle_event("search", ...)` → `apply_filters/1` → `stream(:games, games, reset: true)` in
  `lib/pukllay_club_web/live/catalog_live/index.ex`) has zero loading-state or transition
  affordance wired to it. The `reset: true` stream call produces an instant, un-animated morphdom
  DOM replace of the `#games` container (and, when the carousel-vs-grid surface flips via
  `:rendered_results`, of the whole `#carousel-rows`/results-grid region). Three concrete gaps
  combine to produce this: (1) no client-side loading indicator is set for this request — unlike
  the existing `.GridScroll`/`.CarouselScroll` infinite-scroll hooks, which DO set a
  `data-loading` attribute around their own `pushEvent` calls to reveal trailing skeletons
  (`.pk-grid[data-loading] .pk-trailing-skel`, app.css:446-468) — this mechanism exists in the
  codebase already but was never extended to the search/filter path; (2) the three
  `@custom-variant phx-click-loading`/`phx-submit-loading`/`phx-change-loading` Tailwind variants
  (app.css:210-212) are declared but never applied to any selector anywhere in the app, so
  LiveView's own automatic `.phx-change-loading` class (added to the form while the search event
  is in flight) currently has no visual effect at all; and (3) `.pk-card`/`.pk-grid` carry no CSS
  `transition` on opacity/transform, so even a class-based fade could not animate without first
  adding that channel (this repo's own `mobile-search-expand-jump` knowledge-base entry documents
  the same "no animatable property = no transitionrun" failure mode). This is invisible on local
  dev, where the round trip completes in a handful of milliseconds, but will read as an instant,
  jarring jump on production's real network latency — exactly the user's report and exactly why
  they flagged the environment difference explicitly.
fix: >
  (not applied — diagnose-only mode). Scope for the planner: (a) apply the already-declared but
  unused `phx-change-loading`/`phx-click-loading` variants (or the same `data-loading` attribute
  pattern `.GridScroll` already uses) to the results container(s) (`#games`, `#carousel-rows`, or
  a shared wrapper) so there is a visible dim/opacity-reduce state during the in-flight request;
  (b) add a short opacity/transform `transition` (reusing existing `--duration-fast`/
  `--ease-standard` tokens, per this app's established motion-token discipline) to `.pk-card`/
  `.pk-grid` so the `reset: true` swap fades rather than pops; (c) decide whether to reuse
  `CarouselRow.skeleton_row`/`skeleton_card` for this transient state or keep the fix purely
  visual (dim + fade) without a skeleton — `@loading` today is deliberately set once at mount and
  never toggled again (index.ex moduledoc), so reusing skeletons here is a new design decision,
  not a mechanical wire-up.
