## Eliminated

- hypothesis: "Symptom 2 (scrim not opaque, photo offset over masthead) is caused by a CSS containing-block hazard — an ancestor of #detail-lightbox has transform/filter/perspective/contain/will-change, breaking position:fixed so the scrim only covers a small box near the masthead instead of the full viewport."
  evidence: Walked the full ancestor chain (#detail-lightbox -> #detail-page -> Layouts.app's .mx-auto.space-y-4 -> main.pk-boundary-collapse -> body -> html) via computed-style inspection in a real headless-Chrome render — every ancestor has position:static, transform:none, filter:none, perspective:none, contain:none, will-change:auto. #detail-lightbox itself measured position:fixed, inset 0, rect {x:0,y:0,width:<viewport>,height:<viewport>} at every tested viewport (390/1280/1440/1920px) and after scrolling. This matches an existing documented audit for the sibling #detail-title-echo element (app.css:2869-2876) which walked the identical chain and found it clean.
  timestamp: 2026-08-27 (this session)

- hypothesis: "Symptom 2 is a z-index/stacking-context bug — some page element (buy-box, CTA button, mecanicas chips) paints above the z-index:700 scrim due to a nested stacking context."

  timestamp: 2026-08-27 (this session)

## Evidence

- timestamp: 2026-08-27
  checked: lib/pukllay_club_web/live/catalog_live/show.ex mount/1, handle_event("select-image"/"open-lightbox"), gallery-thumbnails/gallery-dots markup (lines 71-127, 374-405, 696-723), lightbox_neighbor/2 (985-995)
  found: There is exactly one image-selection assign, `@selected_image`, read by (a) the main poster `<img>`, (b) the gallery-thumbnails strip's `border-primary` active state, (c) the gallery-dots' `is-active`/`aria-current` state, and (d) the lightbox's displayed `<img>`. The lightbox's prev/next buttons dispatch the SAME `"select-image"` event (via `lightbox_neighbor/2` computing the next/prev url from the same `gallery_thumbnails/1` whitelist) that the thumbnail/dot buttons use. This is explicitly documented as intentional in the module doc and inline comments ("there is no client-side carouselIndex, so 'gallery and lightbox share one selection' is structural, not something two listeners keep in sync" — from 01.1-04/T-01.1-16).
  implication: Navigating with the lightbox's prev/next chevrons mutates `@selected_image`, which immediately re-renders the underlying (still-mounted, merely hidden-behind-the-scrim) gallery-thumbnails border/gallery-dots active-state — i.e., the "carousel" selection visibly changes while the lightbox is open, and the change persists after closing the lightbox (nothing resets `@selected_image` on close). This is the direct, structural cause of symptom 3.

- timestamp: 2026-08-27
  checked: assets/css/app.css .pk-lightbox-img (2996-3009) vs the shell's width convention (.pk-nav-inner line 647, #detail-masthead-wrap show.ex:321, .pk-footer-row layouts.ex:973) — all three of the latter use `mx-auto w-full max-w-7xl pk-gutter`
  found: `.pk-lightbox-img { max-width: min(90vw, 60rem); ... }` — a hardcoded viewport-relative/rem cap with no reference to `max-w-7xl` or `--pk-gutter`, unlike every other width-capped surface on this page (header nav, footer, masthead). 60rem = 960px is narrower than max-w-7xl's content width (80rem/1280px minus 2x gutter).
  implication: Direct, unambiguous root cause of symptom 1 — the lightbox image's width source of truth was never wired to the shared shell-width token used everywhere else on the page.

- timestamp: 2026-08-27
  checked: Headless-Chrome (Playwright + system google-chrome) automated open-lightbox flow against the live dev server (verified byte-identical to this worktree's source via matching computed background-color `color(srgb 0.0784314 0.0313726 0.133333 / 0.72)` == color-mix(rgb(20 8 34) 72%, transparent)) at viewports 390/1280/1440/1920px, with/without pre-scroll, and at an early (60ms into the 180ms fade) timing sample
  found: `#detail-lightbox` rect is always {x:0, y:0, width:<viewport width>, height:<viewport height>}; `.pk-lightbox-img` is precisely horizontally AND vertically centered (e.g. at 1440x900: img rect x=360.45/w=719.09 → (1440-719.09)/2=360.45 match; y=90/h=719.98 → (900-719.98)/2=90.01 match). No reproduction of "offset/overlapping masthead" at any tested condition.
  implication: The reported symptom-2 positioning complaint does not reproduce as a code-level CSS bug under any tested condition; see Resolution for the reframed explanation.

- timestamp: 2026-08-27
  checked: Full-page screenshot at 390x844 (mobile) with lightbox open (button DOM order in show.ex: data-lightbox-close (z-index:2) -> data-lightbox-prev (no z-index) -> <img class="pk-lightbox-img"> (no z-index) -> data-lightbox-next (no z-index))
  found: Screenshot shows the right chevron (data-lightbox-next) clearly rendered on top of/beside the image, but NO visible left chevron (data-lightbox-prev) anywhere on screen. Per CSS paint-order rules, sibling elements with z-index:auto paint in DOM order (later wins ties) within the same stacking context; since `<img>` comes AFTER the prev button but BEFORE the next button in the markup, the image paints ON TOP of the prev button wherever their boxes overlap, while the next button paints on top of the image. At mobile widths the image's `max-width: min(90vw, 60rem)` leaves only ~5vw (≈19.5px at 390px) of margin on each side, putting the `left-4` (16px)-anchored prev button's box directly under the image's edge — hence it renders invisible/behind. At desktop widths there is enough margin between the viewport-edge-anchored chevron and the (also viewport-width-capped) image that the two boxes don't overlap, so the bug is mobile-only, matching the report.
  implication: Root cause of symptom 4 confirmed — missing/insufficient explicit z-index (or DOM reordering) on `data-lightbox-prev` relative to `.pk-lightbox-img`.

## Resolution

root_cause: |
  Four independent code-level issues bundled under one UAT item, each in `lib/pukllay_club_web/live/catalog_live/show.ex` and/or `assets/css/app.css`:

  (1) Desktop width not capped to shell width — `.pk-lightbox-img`'s `max-width: min(90vw, 60rem)` (app.css:2996-2999) is a standalone, hardcoded cap that never reads the `max-w-7xl`/`--pk-gutter` shell-width convention every other capped surface on the page uses (`.pk-nav-inner`, `#detail-masthead-wrap`, `.pk-footer-row`). CONFIRMED via source read.

  (2) Scrim/centering — INVESTIGATED THOROUGHLY, NOT REPRODUCIBLE as a stacking/positioning/opacity-compositing bug. Automated headless-Chrome testing (5 viewports, scrolled/unscrolled, mid-transition) plus raw pixel sampling of screenshots shows `#detail-lightbox` is always a correctly full-viewport `position:fixed; inset:0` box, `.pk-lightbox-img` is precisely centered both axes, `z-index:700` correctly outranks every other element on the page, and the `--pk-overlay-scrim` (72%-opacity dark tint) composites uniformly and correctly over every layer of underlying content (buttons, headings, body text) with no gaps. Best evidence-supported explanation: the reported "photo offset/overlapping the masthead... background readable through/around" is very likely the SAME root cause as (1) perceived differently — because the photo renders much narrower (960px cap) than the shell's established content width (max-w-7xl ≈ 1280px) at wide desktop viewports, the image sits in a comparatively small central column with a large amount of surrounding scrim, which combined with the scrim's deliberate 28% residual transparency (by design, per WR-04/sketch-033 — the scrim is not meant to be 100% opaque) reads to the eye as "not obscuring enough / off-center relative to the rest of the page." No code fix beyond (1) plus, optionally, a scrim-opacity re-tune is evidenced; a stacking-context/positioning fix is NOT evidenced and should not be applied without a fresh, reproducible screenshot from the actual reporting device/browser.

  (3) Lightbox navigation moves the underlying carousel — `@selected_image` is a single shared LiveView assign, by original design (01.1-04/T-01.1-16), driving the main poster image, the lightbox's displayed image, AND the gallery-thumbnails/gallery-dots "active" state simultaneously. The lightbox's prev/next buttons dispatch the identical `"select-image"` event the thumbnail/dot buttons use (via `lightbox_neighbor/2` walking the same `gallery_thumbnails/1` list). There is no separate lightbox-scoped selection state, so navigating inside the open lightbox necessarily and visibly changes which thumbnail/dot is marked active underneath — and that change persists after the lightbox closes. CONFIRMED via source read (mount/1, handle_event clauses, template bindings).

  (4) Mobile left-chevron behind the image — `data-lightbox-prev`, `<img class="pk-lightbox-img">`, and `data-lightbox-next` are DOM siblings inside `#detail-lightbox`; none carries an explicit `z-index` (only `.pk-lightbox-close` does, at 2). With z-index:auto, sibling paint order follows DOM order, so the `<img>` (which comes after the prev button but before the next button in markup) paints on top of the prev button wherever their boxes visually overlap, while the next button paints on top of the image. At mobile widths the image's `min(90vw, 60rem)` cap leaves the `left-4`(16px)-anchored prev button directly under the image's edge, rendering it invisible; at desktop widths there's enough clearance that the boxes don't overlap, so the defect is mobile-only. CONFIRMED via screenshot (right chevron visible, left chevron absent) matching the DOM-order paint-order mechanism.
