## Resolution

root_cause: |
  01.4-07 did not fail — it closed G-01.4-2's three conditions completely and measurably (caption
  is a 36px single opaque line at all 24 viewport-theme combos; coverage 15.6-32.1%, down from
  40.6-74.9%). The component still reads as awful because the caption was only ONE of four
  necessary conditions. THREE remain, in three different categories, and all three must be closed:

  (A) CSS / WRONG SIZING MODEL FOR THE NEW SHAPE — introduced by 01.4-07 itself.
      `.pk-about-map-label` (app.css:2813-2827) changed from a full-bleed translucent BAND to a
      bordered opaque CHIP but kept the band's `left: 0.5rem; right: 0.5rem` pinning. A chip must
      shrink-wrap its content; only a band may span its container. Result: the chip is sized by
      the container, so at 375px a 283px chip holds 79.3px of left-aligned text — 30.8% fill,
      177.7px of dead space (33.0% / 160.7px at 768px). That is the visual signature of an empty
      disabled input control, which is why it reads as a cheap pasted-on overlay rather than a
      caption. Compounded by non-concentric radii (outer 8px, inset 8px, inner 8px; concentric
      requires inner 0px), which makes it float rather than sit inset.

  (B) DATA / THE SCREENSHOT ASSET IS ITSELF BAD — untouchable by any CSS.
      priv/static/images/about-maps-thumb.jpg is 81.4% featureless, 43.5% of it a single empty
      green park polygon, with all real content crowded into a bottom-left diagonal band. The
      club's own pin label is baked in TRUNCATED ("CLUB DE EMPRENDEDORES…", literal ellipsis).
      Six unrelated third-party POIs share the frame — including "LUGAR DEL HECHO / Temporarily
      closed" — several more legible than the club's own pin, so the subject has no visual
      dominance. Google's attribution wordmark is cropped out, which is a Maps ToS
      non-compliance. And because the map's typography was rasterized at capture scale and is
      then downscaled 2.2-4.0x, every map label renders at 2.7-4.9 CSS px — below any legibility
      floor. The thumbnail communicates "there is a map" and literally nothing else.
      (Note: this is NOT a resolution defect — source-px-per-device-px is 1.12-1.34, i.e. always
      downscaling. It is a zoom-level and composition defect.)

  (C) ENVIRONMENT / NO THEME RESPONSE — untouchable by any caption CSS.
      One light-palette asset serves both themes (the light and dark measurement sweeps are
      identical row-for-row). Card background luminance is 238.5 in light — a 1.03x match to the
      asset's 231, which is why light theme is tolerable — but 22.9 in dark, a 10.1x ratio, with
      86.5% of the asset's pixels in the top-2 luminance bins. In dark theme the component is a
      blazing white rectangle punched into a near-black purple card.

  AND-GATE: YES. (A) alone leaves an illegible, truncated, blazing map. (B) alone leaves the
  empty-input chip and the dark clash. (C) alone leaves the other two. This is precisely why a
  correctly-diagnosed, correctly-implemented fix (01.4-07) did not move the user's verdict — and
  why a fourth CSS-only pass on `.pk-about-map-label` would not either.

  FEASIBILITY OF THE PROPOSED EMBED (second half of the question):
  * BLOCKED TODAY, PROVEN LIVE. `PukllayClubWeb.CSP.policy/0` emits `default-src 'self'` with no
    `frame-src`; a real injected google.com/maps/embed iframe fired a securitypolicyviolation
    (effectiveDirective "frame-src", blockedURI "https://www.google.com") and the browser logged
    the fallback explicitly. Requires adding `frame-src https://www.google.com` — the app's first
    third-party frame origin — plus updating the CSP test at catalog_live_test.exs:1683-1707.
    `frame-ancestors 'none'` is NOT the blocker (it governs who embeds us).
  * NO EXISTING FOUNDATION. Zero Google Maps API keys/config anywhere (the only Google credential
    is `gemini_api_key`); zero iframes anywhere in lib/ or assets/. ClubLinks.maps_url/0 is a bare
    maps.app.goo.gl short link.
  * COST. The official Maps Embed API is free/unlimited but needs an API key AND an enabled Google
    Cloud billing account — real ops surface for a €15/mo solo-dev project. The keyless
    `?pb=` form avoids that but is undocumented/unsupported with an opaque payload.
  * IT DOES NOT SOLVE (C). The Maps Embed API iframe has no dark-mode/custom styling; dark
