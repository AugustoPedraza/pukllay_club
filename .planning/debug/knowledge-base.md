## search-expand-header-overlap — header's expandable search rendered as a stacked, misplaced box overlapping the chip nav, because a premature CSS comment terminator silently deleted its base rule
- **Date:** 2026-08-23
- **Error patterns:** no console errors, purely visual layout bug; expandable search overlaps nav / chip row; element misplaced, wrong width and position; unexpected header height growth; children stack vertically one per line instead of inline; content bleeds outside its container; chips render through / on top of the search box; getComputedStyle disagrees with the declared CSS (position static though `relative` declared, overflow visible though `hidden` declared, height 132px though `44px` declared, `display: flex` and `margin-left: auto` never applied); an entire CSS rule missing from the cascade while its adjacent sibling rules apply normally; rule present verbatim in the built stylesheet yet not honored by the browser; CSS block silently dropped; premature comment close; token wildcard `--duration-*` immediately followed by `/` forming `*/`; stray prose absorbed into a selector; CSS error recovery; "never worked since it was built" (not a regression)
- **Root cause(s):** `assets/css/app.css:582` wrote the motion-token wildcard as `(--duration-*/` inside a prose comment. The trailing `*` of `--duration-*` combined with the following `/` to form `*/`, closing the comment one line early. Line 583 (`--ease-*), not literal timing values. */`) therefore landed in CSS context; per the CSS spec the parser scanned forward to the next `{` and treated `--ease-*), not literal timing values. */ .pk-search-morph` as one invalid selector, so error recovery discarded the entire `.pk-search-morph { ... }` base rule. Each lost declaration maps 1:1 to a reported symptom: `display: flex` → children stacked into a three-row box; `height: 44px` → row grew to 132px and overflowed down into the chip nav; `margin-left: auto` → icon sat beside the nav links instead of the row's right edge ("search icon top-center"); `overflow: hidden` → content bled outside the pill. The `.is-open` rule parsed normally, which is why the box still widened on open while everything else was wrong. Single cause — the AND-gate was answered "no": one dropped rule explains every sub-symptom with no residual.
- **Fix:** Rewrote `(--duration-*/` as `(--duration-* and` so the wildcard no longer forms a `*/` and the comment runs to its intended terminator — this alone re-admits the whole base rule to the cascade. Restoring the rule also re-applied its `flex: 0 0 auto`, which correctly stopped the open pill being squeezed and thereby exposed a latent gap: between 481px and ~790px the row cannot seat brand + nav links + a full 17.5rem pill, so it began overflowing horizontally. Added `min-width: 0; flex-shrink: 1` to `.pk-search-morph.is-open` so the open pill yields in that band instead of raising a horizontal scrollbar; the collapsed icon stays pinned at exactly 44px via the base rule. Commit `325a86e`.
- **Files changed:** assets/css/app.css, test/pukllay_club_web/stylesheet_integrity_test.exs
- **Why not caught:** No gate existed for this class — every layer of the toolchain is silent on a dropped CSS rule, and the branches converge on that. *Code:* CSS comments do not nest and `*/` is greedy, so writing a wildcard token in prose adjacent to a slash silently shifts the comment boundary with no syntax affordance warning the author; the source still *reads* correct to a human, which is why code review passed it. *Config:* the asset pipeline has no CSS lint or validation step — Tailwind v4 / LightningCSS passed the malformed comment through verbatim and exited 0 without a warning, and `mix quality` (hex.audit, deps.audit, format, credo --strict, sobelow, test) covers Elixir sources only and never parses `app.css`. *Environment:* browsers implement spec-mandated CSS error recovery, which discards an invalid rule and reports **nothing** to the console — hence the user's accurate "no console errors" and the bug surviving from the feature's original build rather than arriving as a regression. No person or agent is at fault here: the failure was invisible at every point it could have been seen.
- **Recurrence guard:** `test/pukllay_club_web/stylesheet_integrity_test.exs` (3 tests, verified red on the real defect and green after the fix; runs inside `mix test`, therefore inside `mix quality` and CI). `"no comment is left unterminated"` and `"no comment closes prematurely on a token wildcard"` tokenize `assets/css/app.css` the way a CSS parser does and fail on any comment closed by a `*/` preceded by an identifier character — catching the whole class, not just this line. `"the .pk-search-morph base rule survives into the built stylesheet"` asserts end-to-end on `priv/static/assets/css/app.css` that the selector is preceded only by the previous rule's closing brace (anchoring on `}` rather than line-start — an earlier line-anchored version passed on the broken build, because the orphaned prose also began its own line) and that the four symptom-bearing declarations are present.

## header-height-wordmark-wrap — header silently grew from 65px to 129px across a 327px-wide viewport band because the brand wordmark was free to reflow inside an auto-height flex row
- **Date:** 2026-08-23
- **Error patterns:** no console errors, purely visual layout bug; header height changes / grows when the search opens; header taller at rest than it should be; brand wordmark wraps onto a second line; tagline wraps onto 2 or 3 lines; logo text reflows at narrow widths; sticky header offset wrong, page content below the header shifts down; `--pk-header-h` publishes an inflated height; ResizeObserver faithfully reports a wrong-but-real height; symptom appears only in a middle band of viewport widths (481-808px) and is fine both below and above it; failure boundary does not line up with any declared breakpoint; flex item shrinks below its max-content width; `flex: 0 1 auto` / `flex-initial` on a text item; `white-space: normal` inherited, nothing sets `nowrap`; single-line `flex-wrap: nowrap` row whose *item* wraps internally rather than the row breaking into flex lines; `align-items: center` on a row with no fixed height; nav links wrap ("Quiénes Somos"); mobile-only `@media (max-width: 480px)` override masks the bug on phones; "pre-existing, not a regression"
- **Root cause(s):** AND-gate fired — two conditions had to hold simultaneously, and the fix had to remove both. (1) **Capacity:** `.pk-nav-inner` was over-subscribed by arithmetic, not by a missing breakpoint — seating brand (250px max-content: isologo 36 + gap 8 + wordmark 206) + gap 24 + nav links (166.3px) + gap 24 + pill (44px collapsed / 280px open) + 64px gutters requires 572.3px closed and 808.3px open, and the measured failure boundaries matched those numbers to the pixel; **(2) Reflowability:** the brand lockup was simultaneously shrinkable (`flex-initial` = `flex: 0 1 auto` on header_inner/1's wrapper div) and wrappable (`.pk-brand-wordmark` inherited `white-space: normal`; nothing anywhere set `nowrap`) inside a single-line, `align-items: center`, auto-height flex row, so the row's height was whatever its tallest item needed. Under over-subscription the flex algorithm shrank the brand below 250px and the tagline "JUEGOS DE MESA MODERNOS" — 206px, the widest line in the lockup by 95px — reflowed onto 2 then 3 line boxes; the row grew 48→64→80→112px, the header grew 65→81→97→129px, and the `.CatalogNav` ResizeObserver published the inflated value as `--pk-header-h`, shifting every sticky-offset element on the page. `.pk-nav-links` failed identically as a second-order effect (166.3 → 116.3px min-content). Neither condition alone produces the symptom, which is why the band has both edges: below 480px the row is over-subscribed but the wordmark is hidden so nothing can wrap; above 808px the text is free to reflow but there is room, so nothing does. `@media (max-width: 480px)` hiding the wordmark was the *only* reason phones were immune — the defect was the whole 481-808px band above that rule.
- **Fix:** Removed both preconditions rather than patching the symptom's pixel values. (1) Pinned every text item in the row so nothing in the header can reflow, making the height structurally constant instead of merely usually-correct: brand wrapper `flex-initial` → `shrink-0`, new header-scoped `.pk-nav-inner .pk-brand-wordmark { white-space: nowrap }` (scoped because the footer shares `brand_logo/1` and has no fixed-height contract), `flex-shrink: 0` on `.pk-nav-links` and `white-space: nowrap` on its links — the links were measured collapsing independently, so pinning only the brand would have relocated the bug rather than removed it. (2) Gave the row the capacity it then needs: the wordmark is `display: none` by default and revealed by a new `@media (min-width: 48rem)` block, reusing an existing breakpoint rather than inventing one; the pill's shrink guard (added by the sibling session) covers the 40.3px shortfall, landing it at 239.7px at 768px — above the 220px the search box carried pre-01.1-08. 640px/sm was measured and rejected: it leaves the pill 111.7px, narrower than its own 44px toggle plus 44px close control together. The superseded duplicate in the ≤480px block was deleted so one visual property has exactly one owner. This leaves `.pk-search-morph.is-open`'s shrink guard as the row's single point of give, which is what it was added for. Net effect: hiding the wordmark from 481-767px is a visible design change on tablet widths, explicitly surfaced at the human-verify checkpoint and accepted by the user rather than decided silently. Commit `5438fa0`.
- **Files changed:** assets/css/app.css, lib/pukllay_club_web/components/layouts.ex, test/pukllay_club_web/header_row_height_test.exs
- **Why not caught:** No gate existed for this class — nothing in the toolchain observes rendered geometry, and the branches converge on that. *Code:* the two ingredients are individually unremarkable — `flex-initial` on a logo wrapper and an absent `white-space` rule both read as correct in review; the bug only exists in their interaction with an auto-height row, which is invisible in a diff and has no syntax affordance. *Config:* `mix quality` (hex.audit, deps.audit, format, credo --strict, sobelow, test) parses Elixir sources only; the sibling session's `stylesheet_integrity_test.exs` checks that rules survive the build, not what they lay out to. There is no visual-regression or headless-layout gate in CI, so a header can change height by 64px without failing anything. *Data:* the trigger is a content string — the 206px tagline sets where the band starts — so the defect is latent in the CSS and only surfaces for particular copy. *Process:* the prior debug session's harness rendered the tagline as "Ludoteca" rather than `brand_logo/1`'s real default, understating the brand by ~55px, which is why it recorded a mild "65→97px" residual and never saw the closed-state half of the bug at all — a harness that does not render the shipped content will confidently measure the wrong thing. **Generalizable lesson:** a breakpoint chosen by convention (480px) rather than derived from the row's content arithmetic (572.3/808.3px) will mask a bug on exactly the devices the author tested and expose it on the ones they did not.
- **Recurrence guard:** `test/pukllay_club_web/header_row_height_test.exs` (5 tests, each verified RED against the reverted tree with its own diagnostic — not merely written green — and running inside `mix test`, therefore inside `mix quality` and CI). Oracle type: **derived (contract)** — real proof is rendered geometry, which ExUnit cannot observe, so the assertions pin the structural preconditions the geometry depends on: the brand wrapper carries `shrink-0` and no direct child of `.pk-nav-inner` still carries `flex-initial` (asserted against actual rendered component markup via `render_component` + LazyHTML, not against source text); the header wordmark is `nowrap`; `.pk-nav-links` is `flex-shrink: 0` and its links are `nowrap`; the wordmark is `display: none` by default; and the ≤480px block never re-declares its `display` (one property, one owner). The load-bearing one is the **boundary assertion** — it parses the actual `min-width` value off whichever `@media` block restores `display: flex` and fails if it is below 768px, so narrowing the reveal breakpoint (the single change that would reopen the bug) fails the suite with the capacity arithmetic in the message.

## footer-overflow-tablet-width — footer scrolled horizontally across a 481-652px band because a non-wrapping flex cluster's minimum width is the SUM of its children's min-contents, an incompressible floor no viewport could shrink past
- **Date:** 2026-08-23
- **Error patterns:** no console errors, purely visual layout bug; horizontal scrollbar / horizontal overflow at tablet widths; footer overflows its viewport; `documentElement.scrollWidth` **pinned at a constant** (653px) regardless of how narrow the viewport gets; scrollWidth > clientWidth; overflow decays linearly to zero as the viewport widens to meet a fixed ink edge; element measures **exactly** its own `width: min-content` (602.8 == 602.8) — sitting on a hard floor, so narrowing the viewport moves it zero pixels; flex container will not shrink; flex item default `min-width: auto`; `flex-wrap` absent / single-line flex row over-subscribed by its children; `white-space: nowrap` text run has no break opportunity; child overflows parent by a fixed pixel count; atomic `inline-flex` wrapping a fixed-size `<img>` spills past its squeezed parent instead of reflowing; symptom confined to a middle band of widths and clean both below and above it; band's lower edge is a declared breakpoint (`@media (max-width: 480px)`) while its upper edge is content width, not any breakpoint; mobile-only override masks the bug on phones; "mobile override stops one breakpoint too early"; two sibling elements share one CSS rule but only one of them manifests; deepest node in a depth-first walk blamed instead of the shallowest overflowing container; "pre-existing, not a regression"
- **Root cause(s):** AND-gate fired — two conditions had to hold simultaneously, though (unlike `header-height-wordmark-wrap`) removing just one was sufficient. **(1) Over-subscription:** `.pk-footer-right` carries four independent children — social 136 + "Tema" toggle-tag 31.1 + theme-toggle 136 + meta 227.8 = 530.9px, plus 3 × 1.5rem gaps (72px). **(2) No reflow escape:** `assets/css/app.css:899-904` declared `.pk-footer-left, .pk-footer-right { display: flex; align-items: center; gap: 1.5rem }` with **no `flex-wrap`**, so all four had exactly one line to sit on. The load-bearing mechanism: because a flex item's default `min-width: auto` resolves to its min-content, a *non-wrapping* flex container's minimum width is the **SUM** of its children's min-contents rather than the **MAX** — giving a hard 602.8px floor, confirmed directly by the cluster measuring *equal to* its separately-measured `width: min-content` at every viewport in the band. Two children (`.pk-footer-toggle-tag`, `.pk-footer-meta`) additionally carry `white-space: nowrap`, which is what makes their individual terms in that sum full single-line widths. The real ink edge is 18px worse still at **652.8px**: `.pk-footer-meta` *does* flex-shrink, but only by 18px, and since its child `.pk-bgg-note` is an atomic `inline-flex` around a fixed-size 18px BGG logo, that shrink produces child-overflows-parent spill rather than any reflow. 652.8px is invariant to viewport width, so `scrollWidth` sat pinned at 653px and every narrower viewport scrolled — 172px of overflow at 481px decaying linearly to 1px at 652px. The band's lower edge is 481px purely because `@media (max-width: 480px)` collapses the cluster below it (columns the row, hides three of four children, narrows the gutter 2rem → 0.875rem); **480px was never the width at which the cluster starts fitting — it needs 653px.** Below 481px condition (1) is false; above 660px condition (1) is false; only 481-652px has both.
- **Fix:** Added `flex-wrap: wrap` to the shared `.pk-footer-left, .pk-footer-right` base rule, with a comment recording the measured floor arithmetic and the eliminated alternative. This changes how the minimum is **COMPUTED** — `sum(children)` → `max(children)`, i.e. 602.8px → 227.8px — rather than tuning a value that happens to fit today's content. It is also the footer's own established idiom: `.pk-footer-row` (:895) and `.pk-footer-links` (:912) already wrap; these two clusters were the only flex containers in the component that did not, which reads as an omission rather than a decision. Removing condition (2) alone is sufficient *and* introduces no new failure mode, because the outcome of reflow is a taller footer (benign) rather than overflow (the defect) — the contrast with the sibling header bug, where removing one condition merely *converted* the wrap into overflow and both had to go. Two edits were explicitly **not** made, each recorded in Eliminated: extending the ≤480px `display: none` override up through the band (it is only sound because those controls relocate into the drawer, and `.pk-nav-hamburger`/`.pk-drawer`/`.pk-drawer-backdrop` are themselves `display: none` above 480px — so it would have deleted all four social links and the entire theme control from every tablet width with nowhere to reach them), and stripping `white-space: nowrap` from `.pk-footer-meta` (measured as causing no overflow at any width 260-1536px, so it would be an unevidenced edit). Verified by an 18-width CDP sweep of the running app: `scrollWidth == clientWidth` everywhere 260-1536px, defect returns value-for-value on revert, geometry outside the band byte-identical to pre-fix. The 3-row reflow inside the band was surfaced at the human-verify checkpoint with screenshots and accepted by the user rather than decided silently. Commit `a725c4b`.
- **Files changed:** assets/css/app.css, test/pukllay_club_web/footer_overflow_test.exs
- **Why not caught:** No gate existed for this class, and the branches converge on the same absence: **nothing in this toolchain observes rendered geometry.** *Code:* an omitted `flex-wrap` has no syntax affordance — it is invisible in a diff (you cannot review a declaration that isn't there), and the rule reads as obviously correct because its *sibling* selector `.pk-footer-left` is governed by the identical declaration and never manifests the bug. That near-miss is itself instructive: left's min-content is 169.6px against right's 602.8px — **3.5× larger despite holding less text** — purely because right's children are two `nowrap` runs plus two fixed-size icon rows with no wrap escape, and left is saved only by an 8.9px margin, not by any structural guarantee. *Config:* `mix quality` (hex.audit, deps.audit, format, credo --strict, sobelow, test) parses Elixir sources only; the two prior sessions' guards check that CSS rules survive the build and that structural preconditions hold, but nothing lays out a page and measures it, so a footer can scroll horizontally across a 172px-wide band without failing anything in CI. *Process:* **the carry-over suspect from the sibling session was measurably wrong on both counts, and following it would have produced a fix that did not fix.** That session's side-discovery named the `.pk-footer-right → .pk-footer-meta → .pk-bgg-note` chain and framed it as "same shape as the header bug: a mobile override that stops one breakpoint too early." Per-child measurement refuted both halves: (a) `.pk-footer-meta` is only 227.8px of the 602.8px floor — **38%** — and the shallowest overflowing box is `.pk-footer-right` itself at depth 4, not the meta at depth 5 or the note at depth 6; deleting the meta outright would still leave a ~351px + gutters floor and would delete D-04's required BGG attribution. (b) The proposed remedy — extend the ≤480px override upward — was disqualified outright by the missing drawer. No blame attaches: a depth-first walk naturally terminates at the *deepest* overflowing node, which is exactly the wrong end of the chain when the binding constraint is a container's line-packing. **Generalizable lessons:** (i) when a box overflows, blame the **shallowest** element in a depth-ordered walk, not the deepest — the deepest node is usually a passenger; (ii) a *pinned* dimension (one that does not move when the viewport moves) is the signature of a min-content floor, and the one-line test is to measure the element against its own `width: min-content` — equality proves it; (iii) a breakpoint chosen by convention rather than derived from the row's content arithmetic will mask the bug on the devices the author tested and expose it on the ones they did not — the same lesson `header-height-wordmark-wrap` recorded, now observed twice in the same codebase, which is what promoted it from an anecdote to the audit rule below.
- **Recurrence guard:** `test/pukllay_club_web/footer_overflow_test.exs` (6 tests, each run against the **actual reverted tree** — file reverted, not simulated — and confirmed red with its intended message before being confirmed green; runs inside `mix test`, therefore inside `mix quality` and CI). Oracle type: **derived (contract)** — the true oracle is rendered browser geometry, which ExUnit cannot observe, so the assertions pin the structural preconditions the geometry depends on, following the pattern established by `header_row_height_test.exs`; the geometric oracle itself was exercised directly via the CDP harness against the running app. The **audit-style rule is the transferable part**: *every flex container in a responsive footer/header must declare `flex-wrap` explicitly* — the suite enumerates the footer's flex containers and fails if any omits it, so the guard covers the class rather than this one selector. Two further tests block the *wrong* fix rather than the bug: the footer's social/theme controls may only be `display: none` inside a media block that also opens the drawer, and a breakpoint-creep assertion fails if the ≤480px block widens. A markup-contract test keeps the BGG attribution present. Mutation-verified: `wrap`→`nowrap` at the fix site kills 3 tests, deleting `flex-wrap` from the adjacent `.pk-footer-row` kills 1, and widening the media query to 660px (the eliminated fix path) kills 2 — the suite bites on the fix site, its neighbour, and the wrong path.

## footer-desktop-overloaded — desktop footer read as cluttered with zero overflow and zero breakage, because a single 1.5rem gap served every spacing tier at once and switched off proximity, the only grouping cue the design allows
- **Date:** 2026-08-23
- **Error patterns:** no console errors, purely visual; **density/UX complaint, not a functional bug** — nothing overflows, nothing wraps unexpectedly, every gate is green, yet the layout reads as cramped; "too overloaded for being one line"; footer cluttered / busy / crammed; "how can this be simplified?"; "get a consistent rhythm for desktop and mobile"; too many concerns in one horizontal band; N atoms read as a single flat undifferentiated run; no visible spacing break at any concern boundary; a text label sits exactly as far from the control it labels as from an unrelated element; **one gap value serving every spacing tier**; uniform gap; no group tier distinct from the item tier; measured gaps identical (24.0px) at every viewport from 375-1440px; **proximity signal absent**; **proximity INVERTED** — same-group items spaced further apart than different-group items; flex `row-gap` smaller than the container's own `gap`; two-value shorthand `gap: 0.75rem 1.5rem`; wrapped flex lines sit closer together than the items within each line; symptom reported as "one line" but the layout is actually two wrapped tiers at most widths; single-line layout only begins above ~1070px; `justify-content: space-between` doing nothing because both clusters wrapped to the left gutter; **concern accretion** — a cluster designed for 2 concerns silently grew to 3 across successive sketches, each change individually correct; the same label+control pair already grouped correctly on ANOTHER surface (drawer) but not this one; candidate "just remove something" simplifications blocked by documented decisions / compliance; mobile-first regression risk when fixing a desktop complaint
- **Root cause(s):** Three contributing causes; the AND-gate fired between the first two. **(1) NO SPACING HIERARCHY.** `.pk-footer-left, .pk-footer-right { gap: 1.5rem }` (`app.css:938-944`) was one declaration serving every tier, and 1.5rem was *also* `.pk-footer-row`'s column-gap — so a CDP sweep measured **every** within-cluster gap at exactly 24.0px at 375/430/481/700/1024/1280/1440px. The gap separating unrelated concerns equalled the gap binding the "Tema" label to the toggle it labels: a **1.0x contrast**. Because sketch 011 deliberately gives this footer no divider, proximity is its ONLY grouping cue — and it was switched off, so ~9 atoms read as one flat 620.8px run. **(2) CONCERN ACCRETION.** Sketch 011 sized `.pk-footer-right` for two concerns (social + meta); sketch 017 Round 2 inserted the theme control (label + 3 buttons) *between* them, taking it to three concerns / four children, without the cluster's spacing ever being revisited. **AND-gate: neither alone is sufficient** — five concerns *with* a real hierarchy read as grouped, and two concerns at a flat gap read fine; the overload requires the accreted count AND the absent hierarchy simultaneously. **(3) INVERTED PROXIMITY ACROSS FLEX LINES** (independent third defect with its own distinct symptom, hence root_cause is a set): `.pk-footer-row`'s row-gap was 0.75rem while its clusters' gap was 1.5rem, so on every wrapped line same-group items sat 24px apart and different-group items 12px apart — proximity pointing backwards. **This was not a mobile-only defect**: a fine width sweep found the row wraps to two tiers at *every* width from 481px to 1072px and only becomes one line at 1073px, so most laptop widths inherited the inversion too — and there, `flex-wrap: wrap` (the prior session's fix) left both clusters left-aligned at the gutter with `space-between` doing nothing and the entire right half of the band empty.
- **Fix:** Restored a spacing **hierarchy** where there had been one flat value; **no content was removed or relocated**, because both obvious removals are blocked (see Eliminated below). (1) A four-tier scale declared **once** as tokens scoped to `.pk-footer` and consumed by BOTH the desktop row and the ≤480px column layout — `--pk-footer-gap-item: 0.5rem` (inside one unit), `--pk-footer-gap-list: 1rem` (sibling text links), `--pk-footer-gap-group: 1.5rem` (distinct concerns in a cluster), `--pk-footer-gap-cluster: 2rem` (between clusters, either orientation). The *shared declaration* is the load-bearing part: two orientations consuming one scale cannot drift, and drift is exactly what produced defect (3). (2) A new `.pk-footer-theme` wrapper (`layouts.ex:601-607`) binds the "Tema" label to the theme toggle as one atom at the item tier — an **8px bind against a 24px separation, a 3x contrast where it had been 1.0x**. This mirrors the mobile drawer's existing `.pk-drawer-utility`, which already grouped the identical pair; the footer was the surface that had drifted, so this is a consistency repair against an in-repo pattern, not a newly invented design. (3) `.pk-footer-row`'s `gap: 0.75rem 1.5rem` collapsed to the single cluster token, ending the inversion. (4) The ≤480px block retunes group/cluster to 1rem/1.5rem for vertical rhythm but preserves the tier **order** — mobile grew only 4px (180 → 184px) while its rhythm flipped from inverted (24 within / 12 between) to correct (16 within / 24 between); values were deliberately restrained rather than maximally separated because every added rem grows the wrapped band's height and pushes the single-line threshold rightward. (5) The ≤480px hide rule collapsed from `.pk-footer-right .pk-theme-toggle, .pk-footer-toggle-tag` to just `.pk-footer-theme` — the wrapper is footer-only, so it no longer needs descendant scoping to spare the drawer's reused `.pk-theme-toggle`. Verified by CDP sweep at 9 widths: desktop now 8px item / 24px group, mobile 16px within / 24px between, right cluster 4 children → 3, **zero horizontal overflow at every width** (the prior session's fix intact), one-line threshold 1073px → ~1070px. The user was offered three alternatives at the human-verify checkpoint (A: keep the spacing fix as-is; B/C: additionally shed a concern from the right cluster) and **selected A**, accepting the three-concern cluster as intentional now that it is visibly grouped.
- **Files changed:** assets/css/app.css, lib/pukllay_club_web/components/layouts.ex, test/pukllay_club_web/footer_rhythm_test.exs, test/pukllay_club_web/footer_overflow_test.exs
- **Why not caught:** No gate existed for this class, and this entry sharpens *why* beyond its three predecessors. **Every prior gate on this element was functional.** The sibling `footer_overflow_test.exs` asserts nothing overflows; the CDP harnesses in all three prior footer/header sessions measured **breakage** — scrollWidth, height inflation, dropped rules. A footer can pass "zero horizontal overflow" and "no unexpected wrap" while its proximity signal is fully switched off (one value for every tier) or outright inverted (row-gap < cluster gap), because **no gate anywhere observes a spacing RATIO** — only absolute values and pass/fail geometry. *Code:* the defect is an **equality**, not an error — `gap: 1.5rem` on a cluster is unremarkable in review and correct in isolation; the bug exists only in its relationship to the *other* gaps in the same component, which no diff shows. *Config:* `mix quality` parses Elixir sources only; there is still no visual-regression gate. *Process:* this is the codebase's clearest case of **accretion across correct changes** — sketch 011 (two clusters), sketch 017 R2 (insert theme control), 01.1-09 T2 (move social+theme to drawer below 480px) were each individually right and each reviewed on its own merits; nobody re-measured the cumulative rhythm, and no artifact asked them to. *Notably, the user was the detector* — the complaint arrived as a UX judgement ("too overloaded... how can this be simplified?"), which is the only channel this class had. **Generalizable lessons:** (i) when a design forbids dividers, proximity becomes load-bearing infrastructure and must be tiered *deliberately* — a single gap value is not neutral, it actively destroys grouping; (ii) a **two-value `gap` shorthand is a smell** in a wrapping flex container, because row-gap and column-gap then encode different tiers and silently drift out of order; (iii) reported symptoms can mislocate the state — the user said "one line", but the one-line layout existed only above 1073px, and the 481-1072px band was an *undesigned* `flex-wrap` fallback that had to be treated as a real state; (iv) **check whether another surface already solves the same pair correctly** — the drawer's `.pk-drawer-utility` was the answer sitting in-repo, which turns a design decision into a consistency repair; (v) when "simplify by removing" is the obvious move, search the planning record for provenance **first** — here both removals were blocked (the "Tema" label by a documented discoverability decision, the BGG attribution by D-04 compliance), which *forced* the fix into the correct lane rather than a silent revert of two deliberate decisions.
