## Resolution

root_cause: |
  THREE INDEPENDENT root causes (AND-gate between symptoms: NO — each is
  separately sufficient for its own symptom; fixing one leaves the others).

  S1 BLINK — The header-hiding is applied by client JS, not by the server
  render, and the hide is itself animated. `#app-header` ships from the server
  as `class="pk-header pk-header-sticky"` with no hiding class (verified by
  curl: `pk-header-about-morph` occurs 0 times in the dead render). The class is
  added only in `.AboutHeaderMorph.mounted()` (about_live.ex:72), which cannot
  run until the deferred app.js executes and the LiveSocket WebSocket join
  completes. `#app-header.pk-header-about-morph` (app.css:2871) then declares
  `transition: opacity var(--duration-slow)`, so the header does a visible
  280ms FADE-OUT rather than vanishing. The comment at about_live.ex:71 asserts
  the opposite of what the mechanism does. 01.4-05-SUMMARY.md:202 shows this was
  observed during execution and dismissed as inherent to a "client-hook-only
  mechanism" because "D-10 forbids any server-side per-route class" — but D-10
  (01.4-CONTEXT.md:103-110) only forbids a 4th state on the shared header's
  state machine, and cites AboutLive-rendered markup as its own precedent. The
  constraint that made this "unavoidable" is self-imposed.

  S2 SPACING — `.pk-about-mark-anchor` is a bare 200px-tall box with no padding,
  and `#about-hero`'s `space-y-3` (12px) is the only separator between it and the
  kicker line. Because the isologo is `object-fit: contain` and height-constrained
  in that box, the glyph sits FLUSH to the box's bottom edge, so nothing absorbs
  the 12px. That same flat 12px serves every gap in the hero, so a 200px mark is
  spaced identically to a 12px text line — the proximity signal is switched off.

  S3 NOT FLUID — three contributors, all needed (AND-gate WITHIN S3: YES).
  (a) CURVE/AMPLITUDE: `.pk-about-morph-mark` (app.css:2817-2823) transitions
      top/left/width/height with `--ease-out-soft` (cubic-bezier(0.16,1,0.3,1)),
      which puts 32.7% of any travel into the first 16.7ms frame at 280ms. The
      dock travel is 160.4px (glyph height, both viewports) to 517.2px (glyph
      left, desktop) — 2.2x to 7.1x the KB's ~73px validated ceiling for this
      token. Desktop frame one moves the glyph 169.1px (7.0x the 24px
      perceptibility threshold) and then crawls for 263ms: a pop, not a morph.
      Third occurrence of this exact token-amplitude defect in this codebase.
  (b) CANCELLED UNDOCK: syncPosition()'s `else if (!this.docked)` branch
      (about_live.ex:149-151) calls `place(natural, false)` on the very next
      scroll frame after an undock starts, and `.no-anim` is
      `transition: none !important` (app.css:2865). The eased reversal survives
      one frame (32.7%) and hard-snaps the remaining 67.3%. Docking is unaffected,
      producing a diagnostic dock-animates/undock-teleports asymmetry.
  (c) STALE ENTRANCE: `onScroll` early-returns while `!this.entered`
      (about_live.ex:156), and `entered` is only set by the 500ms
      `setTimeout` that starts at mount (i.e. after the join). All scroll during
      that window is dropped, so the mark fades in at a stale position and is
      then teleported by the next scroll tick — and the intervening window shows
      neither the header nor the isologo.
  Contributing (reasoned, not profiled): tracking writes layout properties
  (top/left/width/height) plus a deliberate forced synchronous reflow every
  scroll frame from a main-thread rAF, so the mark rides a frame behind the page.
