# Phase 01.2 Plan 03: Grid-Becomes-Results-Only Summary

**The flat "El catálogo completo" grid is now exclusively the search/filter results view — gated by a new `browsing_results?/1` predicate that wraps (never restates) `filters_active?/1` — and the filter modal's existing primary CTA is the one path to it via a new socket-only `:browse_all` signal, with a Rule 1 bugfix ensuring the carousel rows actually repopulate every time a member returns to them.**

## Accomplishments
- Added `:browse_all` (mount/3) and the `"apply-filters"` event handler to `CatalogLive.Index`:
  the filter modal's footer CTA now flips this socket-only flag instead of just closing the
  modal, giving D-02's "submit with nothing selected" case a distinct signal from "the member
  just loaded the page."
- Added `browsing_results?/1`, a private predicate defined as `filters_active?(assigns) or
  assigns.browse_all` — it calls `filters_active?/1` rather than duplicating its clauses, per
  the plan's explicit prohibition, and is now the single source of truth for which of the two
  browse surfaces renders.
- Flipped the carousel-rows container, the `:nav_menu` slot, and the `:subnav` slot to
  `not browsing_results?(assigns)`, and added `browsing_results?(assigns)` to each of the five
  grid blocks (heading, empty state, loading skeleton, stream container, load-more control),
  preserving each block's own additional conditions. The load-error banner is left ungated, as
  specified.
- `FilterModal`'s footer CTA now dispatches `apply-filters` instead of `close-filters`; the
  backdrop and corner-close buttons are unchanged. The moduledoc paragraph describing the CTA
  was rewritten to describe it as the modal's one explicit submission signal rather than a pure
  exit affordance, and to explain why dismissal and submission stay two different events.
- **Found and fixed a Rule 1 bug** while wiring the carousel's `:if` gate (see Deviations):
  LiveView's `phx-update="stream"` containers do not automatically repopulate when their DOM
  node is removed and later reappears. This bug already existed in the shipped carousel-rows
  gating (`filters_active?/1` was already used there before this plan) but was invisible
  because the grid was always visible as a fallback; D-01/D-02 makes the carousel the *only*
  unfiltered surface, so the bug would have made every "clear filters" round trip land on an
  empty carousel section. Fixed via a `:carousel_needs_reset` dirty flag and
  `sync_carousel_visibility/1`, invoked from `apply_filters/1`.
- Realigned `catalog_live_test.exs` to the two-surface contract: every `grid_html/1`/`card_count/1`
  call site is now preceded by a filter-applying or results-submitting step in its own test;
  rewrote the G-01-4 unfiltered-landing test; added a new "the two-surface contract" describe
  block with the four core surface-switching tests the plan required.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `phx-update="stream"` containers don't repopulate when removed and
re-added, breaking the carousel's own return-to-browse path**
- **Found during:** Task 2, while manually reproducing the plan's own `<verification>` smoke
  scenario ("Limpiar filtros returns to carousels") via a scratch LiveViewTest before writing
  Task 3's assertions.
- **Issue:** `CatalogLive.Index`'s carousel-rows container was *already* gated by
  `:if={not filters_active?(assigns)}` before this plan (it's pre-existing, shipped behavior —
  not something this plan introduced). The 8 per-row streams are populated exactly once, at
  connected mount, and never re-streamed afterward. LiveView only ever sends *new* stream
  inserts to the client; once a `phx-update="stream"` container's DOM node is removed (because
  an ancestor's `:if` flipped false) and then reappears, the previously-sent inserts are not
  replayed, since the server considers them already delivered. The bug was invisible in
  production because the grid was *always* visible as a fallback — a user going
  filtered-\>unfiltered always still saw *something* populated (the grid), so nobody exercised
  "does the carousel itself come back with cards." D-01/D-02 removes that fallback: the carousel
  is now the *only* unfiltered surface, so this bug would make every filter-clearing action in
  the app land the member on a carousel section with correct headings but zero cards —
  a direct violation of this plan's own must_haves truth ("Limpiar filtros returns the member
  to the carousel browse surface").
- **Fix:** added a `:carousel_needs_reset` boolean assign (`false` at mount). Every
  event that can cause the grid to show sets it `true` (the new `apply_filters/1`-embedded
  `sync_carousel_visibility/1`, and the `apply-filters` handler directly, since that handler
  never calls `apply_filters/1`). Whenever `apply_filters/1` computes a result where the
  carousel is about to (re)appear (`not browsing_results?(assigns)`) and the flag is set,
  `refresh_carousel_rows/1` re-queries `Catalog.list_carousel_rows/0` and re-streams every row
  with `reset: true`, then clears the flag. The flag design (rather than unconditionally
  re-streaming on every `apply_filters/1` call) specifically avoids re-triggering the
  pre-existing "two stream/4 calls before the first render flush" accumulation bug documented in
  `mount/3`'s own comment, which would otherwise fire on the very first connected
  `handle_params` call.
- **Files modified:** `lib/pukllay_club_web/live/catalog_live/index.ex`
- **Verification:** reproduced the failure with a throwaway debug test comparing rendered HTML
  before/after the fix (confirmed 0 cards -\> correct card count after the fix, on both the
  unmodified pre-plan carousel gating and the new `browsing_results?/1` gating); the fix is
  additionally exercised by the "toggling a mechanic pill... toggling it again restores the
  previous set" test and the new two-surface-contract "clear-filters returns the carousel
  surface" test, both of which now assert the actual card content reappears, not just the
  container id.
- **Commit:** `6752722`

**Total deviations:** 1 auto-fixed (1 Rule 1 bug). **Impact:** without this fix, D-01/D-02 would
have shipped a broken "return to browse" path — the single most common interaction the feature
exists to support (open filters, decide not to filter, or clear an applied filter). The fix is
scoped entirely to `CatalogLive.Index`'s carousel population/reset logic; no template markup,
event names, or other modules were touched beyond what Task 2 already required.
