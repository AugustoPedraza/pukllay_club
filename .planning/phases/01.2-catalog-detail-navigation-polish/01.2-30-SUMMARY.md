# Phase 01.2 Plan 30: Lightbox Close-Button Dark-Theme Contrast Summary

**Dark-theme-scoped `--btn-color`/`--btn-fg` fill on `.pk-lightbox-close`, closing UAT test 20 ("On the dark needs a little more constrant") without touching the already-correct light theme.**

## Accomplishments

- Added `[data-theme="dark"] .pk-lightbox-close { --btn-color: var(--color-neutral); --btn-fg: var(--color-neutral-content); }` — the same two custom properties daisyUI's own `.btn-neutral` sets together, applied through a theme-scoped selector instead of a markup class so `.pk-lightbox-close`'s own rule and `show.ex`'s markup stay byte-identical.
- Added three ExUnit tests with reusable WCAG relative-luminance/contrast-ratio helpers that compute the fill-vs-backdrop and icon-on-fill ratios directly from the tokens declared in `app.css`, rather than string-matching values — a future palette retune that walks `--color-neutral` back toward the failing `--color-base-200` pair will fail the suite instead of shipping.
- Recorded the general lesson (a theme-varying control on a theme-invariant surface is a contrast bug in exactly one theme) in `detail-page-mobile-interaction.md`, directly beside the sketch-033 backdrop lesson it mirrors.

## Decisions Made

- **Scoped to dark theme only, not invariant across both.** Dark-theme `--color-neutral` (#B8A6CC) measures ≈8.6:1 against `--pk-shadow-color`, but the same token in light theme measures only ≈3.1:1 — worse than the >10:1 the unscoped default already gives light theme. An invariant rule would have fixed dark theme by degrading light theme's already-signed-off result.
- **Set both `--btn-color` and `--btn-fg`, not `--btn-color` alone.** daisyUI's base `.btn` rule sets `--btn-fg: var(--color-base-content)` independently of `--btn-bg`/`--btn-color`; overriding only the fill would have left a near-white icon (dark theme's `--color-base-content`) on the new light-lavender chip, measuring ≈1.9:1 — trading an invisible chip for an invisible glyph. Confirmed against `deps/daisyui/packages/bundle/daisyui.mjs`: `.btn-neutral` sets exactly the same two properties together.
- **Contrast is computed, not string-matched.** The reported bug was a number (≈1.1:1), not a missing declaration — the failing pair was a perfectly well-formed pair of token reads. Two private ExUnit helpers (`relative_luminance/1`, `contrast_ratio/2`) parse either a `#rrggbb` hex literal or a space-separated `rgb(r g b)` triple (this file's two colour formats) into a WCAG relative luminance, then into a contrast ratio, so the test fails on a real future regression instead of only on a renamed token.

## Deviations from Plan

None — plan executed exactly as written, with one worth noting explicitly rather than silently:

**Test RED-state nuance (not a defect, not a Rule 1-4 deviation).** The plan's action text states "all three [new tests] must fail for the right reason" at RED, citing reasons for test 1 (the rule doesn't exist yet) and test 3 (it "depends on the token the first test is about to introduce"). In practice, running the tests before the CSS change showed only test 1 failing; tests 2 (`.pk-lightbox-close`'s own rule stays exhaustively four properties) and 3 (the neutral-token-pair contrast computation) already passed. This is correct, not a bug in the tests: test 2 guards an invariant that was already true (the rule hadn't been touched yet), and test 3 reads `--color-neutral`/`--color-neutral-content`/`--pk-shadow-color` — pre-existing theme tokens whose values already clear the WCAG floors (per the plan's own key_links: ≈8.6:1 and ≈8.5:1) independent of whether the new rule wires them into the button. Both tests function correctly as regression guards from this point forward; the plan's prose describing all three as failing at RED was imprecise for this specific set of already-conforming token values, not a defect requiring a fix. Verified via a full run (`mix test test/pukllay_club_web/live/catalog_show_test.exs`) showing exactly 1 failure (the new rule missing) before the CSS was added, and 0 failures after.
