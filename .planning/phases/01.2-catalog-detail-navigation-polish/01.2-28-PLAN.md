<objective>
Make the lightbox actually reach the shell's width — by giving its photo a real box instead of a
ceiling it was never tall enough to touch.

Plan 01.2-25 widened `.pk-lightbox-img`'s `max-width` from a standalone literal to the shell's own
content width. Two independent source-only verifier passes confirmed the change. Live UAT then found
the lightbox rendering exactly as before. Neither reading was wrong: `max-width` is an upper bound,
and every photo in this catalog is produced by the seed pipeline at 800px wide and near-square — under
the old cap, under the new cap, under any cap. The rule has no `width`, so the browser renders each
photo at its own 800 intrinsic pixels and both caps sit unused above it. The fix was real; the
constraint it moved was never the binding one.

So this plan stops adjusting a ceiling and gives the element a floor: an explicit width derived from
the same shell formula, an explicit height carrying forward the same vertical envelope, and — the part
that the user's actual complaint turns on — an opaque fill, so the space the photo does not fill is a
solid stage rather than more of the same see-through scrim. The photo is not upscaled and not cropped;
it letterboxes inside a box that finally has the page's own width.

And then it moves the arrows onto that same box. The user has now asked for shell-width arrows twice
in the same UAT report — test 12 and test 17 — and until this round the answer was "recorded 01.2-21
decision, out of scope." A decision that the person it was made for has rejected twice is not a
decision any more, it is an open gap. It is folded in here by explicit user choice, and it belongs
here rather than in a later round for one structural reason: the box the arrows need to anchor to is
the box Task 1 creates. Planned separately, the two rounds would each have to write the shell-width
formula for themselves, and the arrows and the photo would once again be measured against two
independently-authored boundaries — which is precisely the fault sketch 038 diagnosed in the first
place. So the formula is promoted to a single named token in Task 1 and read three times.

Purpose: the reported symptom — "the background is adding noise", "the background is awful", "the
arrows should take same width defined by shell" — is one photo and two buttons all disagreeing with
the page about where its edges are. Growing the opaque field and moving the arrows onto it are the
two halves of a single answer, and the lever that exists without re-seeding every image in the
catalog.
Output: a shell-width opaque stage with the arrows on its own edges, a corrected provenance record,
and a regression guard that names the trap so the next reader cannot fall into it.
</objective>
