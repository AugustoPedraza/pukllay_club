## Catalog Index — Grid vs. Carousels

The user proposed removing the always-present flat grid from the unfiltered browse state, reserving
it exclusively for search/filter results with infinite scroll, and asked whether this was sound and
what industry apps do here.

**User's proposal:** "the carousels is good enough so not needed a grid at the end. Instead of that,
grid must be a layout used as result of a search with infinite scroll."

**Claude's analysis:** Confirmed via code read that today the grid (`index.ex:612-642`) always
renders below the carousels regardless of filter state, while carousels already hide when
`filters_active?/1` is true. The user's proposal extends that same pattern to the grid. Cited
Netflix (no flat "all titles" grid exists anywhere — only rows and category/search-scoped grids),
Spotify, Steam store, and Amazon as precedent for "curated rows to browse, grid only for
search/filter/category results."

| Option | Description | Selected |
|--------|-------------|----------|
| No explicit "see everything" path | Filter modal's empty-submit already produces the full grid — no new UI | ✓ |
| Add a lightweight "Ver todo" entry point | Explicit link/button mirroring the removed per-carousel Ver todo tile | |

**User's choice:** No explicit path — filter modal's empty-state submit covers it (D-02).
**Notes:** User asked directly "what does Netflix pattern do here" for this specific sub-question;
Claude explained Netflix has no flat browse-all grid at all, only row-scoped "See All" or search.

| Option | Description | Selected |
|--------|-------------|----------|
| Auto-load on scroll | IntersectionObserver-triggered load-more, adapting the existing carousel scroll hook | ✓ |
| Keep manual "Cargar más" button | Leave the existing click-to-load-more button, just gate the grid on filters | |

**User's choice:** Auto-load on scroll (D-03).

## Cross-Page Navigation

**Claude's analysis:** All three sub-areas the user flagged (breadcrumb, chip/fact links, losing
scroll/filter state on back) trace to one root cause: `CatalogLive.Index` reads filters entirely
from URL query params (`handle_params/3`), but the detail page's breadcrumb is hardcoded to bare
`~p"/"`. A filtered member who views a game and returns via the breadcrumb loses their filters.

| Option | Description | Selected |
|--------|-------------|----------|
| Filters only | Carry referring filter query params forward; scroll resets to top (simpler, lower risk) | ✓ |
| Filters + scroll position | Also restore exact scroll position (sessionStorage or similar) | |
| Rely on browser back button instead | No custom mechanism, just don't break native back-button behavior | |

**User's choice:** Filters only (D-08). Exact mechanism (query-string forwarding vs. other approach)
left to Claude's discretion during planning.
