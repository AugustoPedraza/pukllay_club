<objective>
Close G-01.2-5 ("The layout for game details on desktop isn't correct (and mobile is even worse)")
and G-01.2-6 ("This need a better balanced layout" — the mobile CTA bar).

**G-01.2-5, primary cause.** `show.ex` gives `.pk-poster-col` a Tailwind `relative` utility
specifically so the absolutely-positioned share-control wrapper has a containing block. That
utility is silently defeated below 768px. Every custom `.pk-*` rule in `app.css` is written
outside any `@layer` block while Tailwind v4's utilities are generated inside `@layer utilities`,
and per the CSS cascading-layers spec an unlayered rule beats a layered one regardless of
specificity or source order. `.pk-poster-col`'s own unlayered `position: static` therefore wins,
the wrapper's containing block falls all the way to the initial containing block, and the share
button renders pinned near the top-right of the whole page. Above 768px the same file separately
gives `.pk-poster-col` `position: sticky` — also unlayered, also non-static — which accidentally
satisfies the containing-block requirement. That is precisely why mobile is worse.

**G-01.2-5, secondary cause.** The panel's only boundary is a `bg-base-200` fill against the
reading column's `bg-base-100` page background, with border and shadow deliberately omitted by
plan 01.2-04. That token pair has already been measured on this codebase at 1.415:1 in light
theme and 1.086:1 in dark, both roughly half this app's own documented 3:1 non-text-contrast
floor. Human UAT has now falsified the fill-only choice; this plan replaces it with the boundary
treatment already shipped elsewhere in this stylesheet.

**G-01.2-6.** Plan 01.2-04 intended to rebalance the bar by adding `btn-sm` to the shared share
control. That was a complete no-op — `min-h-11`/`min-w-11` were already on the same class list and
`min-height`/`min-width` unconditionally clamp a smaller `height`/`width` upward. The real
imbalance is visual weight, not only width: a solid-fill primary pill beside an outline circle
that is mostly the bar's own `bg-base-200` showing through.

## Tradeoff record: targeted position fix versus a full @layer migration

The planner considered wrapping every custom `.pk-*` rule in `app.css` in an explicit `@layer`
block, which would fix this defect *class* rather than this defect instance. It is not taken here,
deliberately, and the reasoning is recorded so it can be revisited rather than rediscovered:

- **What it would buy.** Tailwind utilities would win over custom rules everywhere, which is what
  a reader of the template naturally expects. The `relative`-defeated-by-`static` failure could
  not recur for any property on any element.
- **What it would cost.** 198 top-level `.pk-*` rules across 3116 lines would all flip precedence
  against every Tailwind utility simultaneously, on every page. Some of them almost certainly rely
  on the unlayered win today — that is how they came to be written. No gate in this repo can
  observe a computed style (this is a twice-logged limitation in the debug knowledge base), so the
  blast radius is exactly the class of defect that is invisible to the test suite and only a human
  eyeballing every page could catch.
- **Decision.** Take the targeted fix now, because it is fully reversible and closes the reported
  gap, and buy down the recurrence risk two cheaper ways instead: a written hazard note at the
  point where custom rules begin, and a one-time audit of the specific property that bit us
  (`position`) across all custom rules. The full migration is worth doing on its own, with its own
  visual verification pass, and should be raised to the developer as a follow-up rather than
  smuggled into a gap-closure plan.

Purpose: the detail page is the surface a member lands on from every card in the catalog, and its
one primary action currently renders in the wrong place on the project's primary device class.
Output: a containing block that holds at every width, a panel with a real edge, a share control
with real presence, and a written note so the cascade hazard is not rediscovered a third time.
</objective>
