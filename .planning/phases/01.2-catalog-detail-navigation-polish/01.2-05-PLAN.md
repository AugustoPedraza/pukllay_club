<objective>
D-03: replace the search/filter results grid's manual "load more" button with auto-loading
infinite scroll, driven by an IntersectionObserver sentinel that fires early enough that the
next page is already arriving before the member reaches the bottom.

Purpose: after plan 01.2-03, the grid is exclusively the results view — the surface where a
member is scanning for a match. A manual pagination button in that context is a stall in the
one flow that matters. The carousels already got in-row auto-loading in quick task 260824-u5d;
this brings the vertical axis in line, reusing that hook's proven guard discipline rather
than inventing a second pattern.
Output: one colocated hook, one sentinel, a reply-carrying server handler, a trailing
skeleton state and a compact inline retry state.
</objective>

    unconditional, because a non-stream child of a stream container can be added and updated
    but never removed, so an `:if` would strand them in the DOM permanently. Four covers the
    widest column count; at narrower breakpoints they wrap, which is acceptable.

    After `#games`, still inside the hook element, add the sentinel: a one-pixel-tall,
    full-width, `aria-hidden` div carrying a `data-grid-sentinel` marker. It is a layout
    no-op whose only job is to be observed.

    anywhere in `lib/` — the inline retry from Task 1 is the only remaining control in this
    region, and it renders only on failure.

    Write the `.GridScroll` colocated hook as a `<script :type={Phoenix.LiveView.ColocatedHook}
    name=".GridScroll">` block inside the hook element, following the repo's existing
    colocated-hook style (a default-exported object with `mounted`, `updated` and
    `destroyed`). Its `mounted()`:

    - Resolves the grid and sentinel elements by their marker attributes and initialises
      `pending` to false and `exhausted` from `this.el.dataset.exhausted`, mirroring
      `.CarouselScroll`'s flag pair.
    - Defines a `maybeLoadMore` that returns immediately when `pending` or `exhausted` is
      set, otherwise sets `pending`, sets `data-loading` on the grid element to reveal the
      trailing skeletons, and fires `pushEvent("load-more", {}, reply => ...)`. The reply
      callback clears `pending`, removes `data-loading`, sets `exhausted` when the reply says
      so, and leaves `exhausted` false when the reply reports an error so the member's manual
      retry can proceed. The loading indicator is driven client-side for the same reason
      `.CarouselScroll` documents: the server handler is synchronous, so a server-assigned
      flag would be set and cleared inside one round trip and the placeholders would never be
      visible.

      sentinel, calling `maybeLoadMore` when it intersects. The margin is the "no visible
      pause" requirement from UI-SPEC: the fetch starts roughly a screen before the member
      arrives.
    - Handles the callback's one non-obvious failure mode: an IntersectionObserver fires on a
      CHANGE of intersection state, so if the sentinel is still inside the root margin after
      a page lands, no second callback ever arrives and loading silently stops one page in.
      After each completed round trip, when not exhausted, unobserve and re-observe the
      sentinel to force a fresh evaluation. Do not substitute a scroll listener for this.

    `updated()` re-reads `data-exhausted` from the element's dataset, the same one-line
    resync `.CarouselScroll.updated()` performs. `destroyed()` disconnects the observer.

    Do not create a file under `assets/js/` and do not touch `app.js`: every hook in this

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `load-more` LiveView event | Any connected client can dispatch this event at any rate; after this plan it is also dispatched automatically by a scroll observer, so the normal-use call volume rises. |
| server assigns -> `data-exhausted` attribute -> client hook | The stop condition crosses to the client, where it can be tampered with in devtools. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01.2-17 | Denial of Service | a client ignoring `data-exhausted` and spamming `load-more` to force unbounded paginated reads | high | mitigate | Task 1's pre-query guard is the authoritative stop: when the server's own `:offset` has reached its own `:total`, the handler replies exhausted without touching the database. The client flag is an optimisation, never the control — the same split `carousel-load-more` already enforces per row, and the same clamp-before-query discipline as `fetch_row_page/3`. |
| T-01.2-18 | Tampering | the `load-more` payload influencing what is fetched | low | mitigate | The handler ignores its params entirely and derives offset, limit and every predicate from server-side assigns via `filter_opts/1`. There is no client-supplied value in the query, so there is nothing to inject — unlike `carousel-load-more`, which does take a client row key and guards it explicitly. |
| T-01.2-19 | Denial of Service | overlapping in-flight requests from a scroll fling | medium | mitigate | The hook's `pending` flag is released only from the reply callback, so at most one request per grid is in flight; a LiveView socket also processes events sequentially, so a second event sees the already-advanced offset. Covered by human-check item 5. |
| T-01.2-20 | Tampering | a mid-scroll failure escalating into a full-page error that hides already-rendered results | medium | mitigate | The two error channels are kept separate by design: `:more_error` drives a compact inline line, `:load_error` keeps its full-page banner, and only `apply_filters/1` sets the latter. Enforced by an acceptance-criterion grep. |
| T-01.2-21 | Tampering | a colocated hook leaking an inline script into the response under this app's CSP | high | mitigate | Colocated hooks are extracted at build time, which is why the shipped carousel test asserts no inline script tag renders; Task 3 adds the equivalent assertion for the grid, and `mix assets.build` is part of Task 2's verify. |
| T-01.2-SC | Tampering | package-manager installs | n/a | accept | No npm or hex dependency is added: the hook is colocated in an existing template and `IntersectionObserver` is a platform API. No package-legitimacy gate applies. |
</threat_model>
