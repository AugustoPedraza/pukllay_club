# Phase 01.2: Code Review Report

**Reviewed:** 2026-08-26T00:00:00Z

## Summary

Reviewed the catalog/detail navigation-polish source files (LiveViews, shared
components, the `CatalogFilters` param-sanitisation module, `Catalog`
context, the app-wide stylesheet, and the corresponding test suites) at
standard depth. This is an unusually well-documented codebase — most files
carry inline post-mortems of prior debug sessions, and the test suites are
thorough (hostile-input tables for `catalog_path/1`, XSS/URL-encoding
assertions on the reservation and share flows, CSP header assertions, and
explicit "no atom-from-string" discipline checks). Most of the classic
failure modes (SQL injection via string interpolation, XSS via unescaped
interpolation, open redirects via `?from=`, unbounded queries, atom
exhaustion from client-controlled strings) are already defended against and
covered by tests.

The one genuine correctness gap found is in `CatalogLive.Show.mount/3`'s id
parsing: it guards against non-numeric ids (avoiding an uncaught
`Ecto.Query.CastError`) but does not guard against a *numeric* id outside
Postgres's `int4` range, which — unlike the two cases the moduledoc
explicitly claims to cover — will raise from the Postgrex encoder rather
than `Ecto.NoResultsError`, producing an unhandled 500 instead of the
intended branded 404. The remaining findings are smaller labeling/robustness
gaps that don't affect data integrity.

## Critical Issues

### CR-01: An oversized numeric `/juegos/:id` crashes with a 500 instead of the documented branded 404

**File:** `lib/pukllay_club/catalog.ex:144-151`, consumed by `lib/pukllay_club_web/live/catalog_live/show.ex:68`
**Issue:**

`get_game!/1`'s moduledoc explicitly states the goal: "Parsing the id first
and raising `Ecto.NoResultsError` for anything that doesn't fully parse as
an integer keeps the single 404 contract intact for every kind of bad id,
not just the numeric-but-nonexistent one":

```elixir
def get_game!(id) when is_binary(id) do
  case Integer.parse(id) do
    {int_id, ""} -> Repo.get!(Game, int_id)
    _ -> raise Ecto.NoResultsError, queryable: Game
  end
end
```

`Integer.parse/1` on Elixir has no magnitude limit (arbitrary-precision
integers), so a fully-numeric but out-of-`int4`-range id — e.g.
`/juegos/99999999999999999999999999` — parses cleanly to `{int_id, ""}` and
is handed straight to `Repo.get!(Game, int_id)`. The `id` column is a
default Ecto `:id` (Postgres `int4`, ±2,147,483,647). Postgrex's `int4`
encoder does not silently truncate or wrap an out-of-range Elixir integer;
it raises (`DBConnection.EncodeError`/`Postgrex.Error`, not
`Ecto.NoResultsError` and not something that implements `Plug.Exception`).
That exception is not rescued anywhere in `mount/3`, so it propagates as an
unhandled crash and Phoenix renders the generic 500 page instead of the
branded `404.html.heex` this whole code path was written to guarantee.

This is exactly the same class of defect the surrounding comments already
fixed once (`Ecto.Query.CastError` for a non-numeric id) — the fix only
covers "does it parse as an integer at all," not "is it in range for the
column's actual Postgres type." Test coverage confirms the gap: both 404
tests in `catalog_show_test.exs` (`test/pukllay_club_web/live/catalog_show_test.exs:176-215`)
use `999999999` (9 nines, ~999M, well inside `int4` range) and `"abc"` —
neither exercises a numeric id that overflows `int4`.

**Fix:** Reject an out-of-range parsed integer the same way a non-numeric
id is already rejected:

```elixir
@int4_max 2_147_483_647

def get_game!(id) when is_binary(id) do
  case Integer.parse(id) do
    {int_id, ""} when int_id >= 0 and int_id <= @int4_max -> Repo.get!(Game, int_id)
    _ -> raise Ecto.NoResultsError, queryable: Game
  end
end
```

Add a regression test alongside the existing two 404 tests using an id like
`"99999999999999999999999999"`.

## Warnings

### WR-01: Active-filter chip mislabels the open-ended "6+" players filter as an exact count for any linked value above 6

**File:** `lib/pukllay_club_web/live/catalog_live/index.ex:691-706`
**Issue:**

`Catalog.maybe_filter_players/2` treats any `players` value `>= 6` as the
open-ended "6+" bucket (`max_players >= n`, no upper bound — see
`catalog.ex:465-479`). `players_chip/1` only special-cases the literal value
`6`:

```elixir
defp players_chip(nil), do: []

defp players_chip(6) do
  [scalar_chip_descriptor("players", "6", "Jugadores: 6+", "Quitar filtro: Jugadores — 6+")]
end

defp players_chip(n) do
  [scalar_chip_descriptor("players", to_string(n), "Jugadores: #{n}", ...)]
end
```

`GamePreview.facts_row/1`'s linked players fact (used on the detail page,
`show.ex:371`, `linked={true}`) navigates to `~p"/?players=#{@game.max_players}"`
— i.e. it can produce `players=7`, `players=8`, etc. for any game whose
`max_players` exceeds 6 (common for party games). Landing back on `/` with
`?players=8` applies the correct open-ended filter (`max_players >= 8`), but
the active-filter chip renders "Jugadores: 8", which reads as an exact-fit
filter — the same wording the `2`/`3`/`4`/`5` chips legitimately use for an
exact fit. A visitor removing/re-reading that chip has no way to tell the
filter is actually open-ended.

**Fix:** Route any value `>= @players_open_bucket`-equivalent (6) through
the same "+"-suffixed label:

```elixir
defp players_chip(nil), do: []

defp players_chip(n) when n >= 6 do
  [scalar_chip_descriptor("players", to_string(n), "Jugadores: #{n}+", "Quitar filtro: Jugadores — #{n}+")]
end

defp players_chip(n) do
  [scalar_chip_descriptor("players", to_string(n), "Jugadores: #{n}", ...)]
end
```

(Import or duplicate `Catalog`'s `@players_open_bucket` constant instead of
the bare literal `6` if it's exposed, so the two can't drift.)

### WR-02: `checklist_placeholder/1` breaks this file's own "literal clauses + catch-all" convention

**File:** `lib/pukllay_club_web/components/filter_modal.ex:508-509`
**Issue:**

```elixir
defp checklist_placeholder("mechanics"), do: "Buscar mecánica…"
defp checklist_placeholder("themes"), do: "Buscar temática…"
```

Every other literal-dispatch function in this codebase (`facet_assign_key/1`,
`scalar_assign_key/1`, `row_query/1`, `normalize_sort/1`, `parse_sort/1`,
etc.) explicitly documents and follows a "literal clauses with a final
catch-all, never build an atom/crash on an unrecognized value" convention
(referenced repeatedly as "T-01-37"). `checklist_placeholder/1` has no such
catch-all. It is currently only ever called with the two hardcoded literals
`"mechanics"`/`"themes"` from `checklist/1`'s own call sites
(`filter_modal.ex:366-377`), so it is not reachable today — but that also
means nothing enforces the convention here, and a future third checklist
(e.g. re-adding the cut editorial-hashtag group, which the moduledoc flags
as an open future task) that forgets to add a clause here will crash the
whole modal with `FunctionClauseError` instead of degrading gracefully.

**Fix:** Add the catch-all this file's convention calls for:

```elixir
defp checklist_placeholder("mechanics"), do: "Buscar mecánica…"
defp checklist_placeholder("themes"), do: "Buscar temática…"
defp checklist_placeholder(_unrecognized), do: "Buscar…"
```

### WR-03: `CatalogFilters.parse_int/1` silently truncates trailing garbage instead of rejecting the whole value

**File:** `lib/pukllay_club_web/catalog_filters.ex:44-49`
**Issue:**

```elixir
def parse_int(str) when is_binary(str) do
  case Integer.parse(str) do
    {n, _rest} -> n
    :error -> nil
  end
end
```

`Integer.parse/1`'s second element (the unparsed remainder) is discarded, so
`parse_int("60min")` returns `60`, and `parse_int("5;DROP")` returns `5`
(harmless here since the value is bound as a query parameter, never
interpolated — no injection risk — but still a partial-match acceptance).
This is inconsistent with the stricter, deliberate full-match parsing this
same codebase uses one file over in `Catalog.get_game!/1`
(`case Integer.parse(id) do {int_id, ""} -> ... ; _ -> ... end`), and with
this module's own docstring, which describes the function as rejecting "a
non-parseable binary" — `"60min"` is arguably exactly that, since the value
as a whole doesn't represent an integer.

**Fix:** Require an empty remainder, matching `get_game!/1`'s precedent:

```elixir
def parse_int(str) when is_binary(str) do
  case Integer.parse(str) do
    {n, ""} -> n
    _ -> nil
  end
end
```

Note this would need `CatalogFilters.parse_int_test.exs`/`catalog_filters_test.exs`
coverage added for the "trailing garbage" case, since no current test
exercises it either way.

## Info

### IN-01: Clipboard "copy link" has no feature-detection guard around `navigator.clipboard`

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:744-751` (`.ShareButton` colocated hook)
**Issue:**

```javascript
this.onCopyClick = () => {
  navigator.clipboard.writeText(this.copyBtn.dataset.shareUrl).then(() => { ... })
}
this.copyBtn?.addEventListener("click", this.onCopyClick)
```

If `navigator.clipboard` is `undefined` (a non-secure/`http:` context, or an
older/embedded browser without Clipboard API support), this throws a
synchronous, uncaught `TypeError` on click rather than degrading gracefully
— the surrounding `navigator.share` branch above it is feature-detected
(`if (navigator.share) {...}`), but this fallback path isn't. Low real-world
risk given the production deploy is TLS-only (kamal-proxy), but worth the
same defensive check for consistency and for local/dev HTTP testing.

**Fix:** Guard the call the same way the `navigator.share` branch is
guarded, e.g. `if (navigator.clipboard) { ... } else { /* no-op or show the URL as text */ }`.

### IN-02: `similares_widened?`'s "always true for a nil-band game" guarantee is a catalog-size assumption, not an invariant

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:77-83`, `lib/pukllay_club/catalog.ex:201-251`
**Issue:**

The comment on `similares_widened?` in `show.ex` states: "A no-band game's
every returned game differs from `nil`, so widened? is true — correct."
Tracing `Catalog.similar_games/1`'s SQL: `band_preference_order(nil)`
returns only the three real band values (never includes `nil`), so a
candidate whose own `weight_band` is `nil` gets
`coalesce(array_position(band_order, NULL), 99) = 99` — the same score any
banded game gets when its band isn't in the list, i.e. it's always sorted
*last*. The "always true" claim only holds because the query then trusts
there are at least `@similares_limit` (12) *other, banded* games available
to fill the shelf ahead of any nil-band candidates — true for this club's
~400-game catalog today, but not a structural guarantee the code enforces,
and not covered by a test with a small number of banded games plus several
other nil-band games competing for the same shelf. If the catalog ever
shrinks (or a large batch of unbanded games is seeded) such that fewer than
12 banded games exist, `similares_widened?` could evaluate to `false` for a
nil-band base game, contradicting the doc's stated guarantee and rendering
the wrong subtitle/badge.

**Fix:** Either add a test that pins the boundary case (a nil-band base game
in a catalog with fewer than 12 real-banded games, some of which also carry
`nil`), or soften the comment to state the assumption explicitly rather than
asserting it as unconditionally "correct."
