## Warnings

### WR-01: `.ResultsLoading`'s 5-second failsafe can desync the in-flight indicator from the actual request on a slow round trip

**File:** `lib/pukllay_club_web/live/catalog_live/index.ex:958-964` (colocated `.ResultsLoading` hook, `onStart`)

**Issue:** The colocated hook sets `data-loading="true"` on `#results-region` when
`phx:page-loading-start` fires, and unconditionally clears it via `setTimeout(..., 5000)`
regardless of whether the actual server round trip has completed — explicitly described
in the surrounding comment as a deliberate failsafe against a dropped `stop` event. The
side effect: if a real search/filter round trip legitimately takes longer than 5s (a
plausible scenario given this project's documented deploy target — a *shared*-vCPU
e2-micro with 1GB RAM + swap, per `CLAUDE.md`'s Deploy constraint — under concurrent
load, a cold Ecto pool connection, or a Postgres query that hits a wider `weight_bands`/
`tags` array-overlap scan), the dim is removed at the 5s mark while the request is still
outstanding. The member sees the results region snap back to full opacity/interactivity
with no cards having changed, giving a false "it's done" signal. When the real
`phx:page-loading-stop` eventually arrives, `onStop` is a no-op (the `dataset.loading`
key and the timer are already cleared), so there is no cue at all that the operation
either did or didn't finish — the member has to infer completion purely from whether the
grid contents changed underneath them.

This is a correctness gap in the *signal*, not in the underlying data (the eventual
`stream(:games, ...)` update still lands correctly) — but it directly undermines the
purpose 01.2-16 was built for (G-01.2-9: give the member an in-flight affordance so a
slow search doesn't look broken), specifically in the slow-request case the affordance
matters most for.

**Fix:** Either extend the failsafe well past this project's realistic worst-case
round-trip time (e.g. 15-20s, generous enough that it only ever fires for a genuinely
stuck/dropped event, not a slow-but-live one), or — better — drop the fixed timeout
model entirely and drive the failsafe off missing a `pong`/heartbeat instead. A minimal
low-risk fix that keeps the existing shape:

```js
this.onStart = () => {
  this.el.dataset.loading = "true"
  clearTimeout(this.failsafeTimer)
  // 15s, not 5s: generous enough to only fire for a genuinely dropped
  // event on this project's shared-vCPU deploy target, not a slow-but-
  // live round trip (see CLAUDE.md's e2-micro deploy constraint).
  this.failsafeTimer = setTimeout(() => {
    delete this.el.dataset.loading
  }, 15000)
}
```

## Info

### IN-01: `ficha_tecnica?/1`'s field-count comment undercounts the nullable integers it describes

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:923-925`

**Issue:** The comment above `ficha_tecnica?/1` reads: "Every field read here is present
on every `%Game{}` (two integers, one array column with `default: []`, one nullable
integer) — no nil-dereference path exists." The function actually reads four fields:
`min_age` (nullable int), `year_published` (nullable int), `designers` (array, default
`[]`), and `bgg_id` (nullable int) — three nullable integers and one array, not "two
integers ... one nullable integer." This is a leftover from the five-field version this
plan narrowed (01.2-17 dropped `publishers`, which was itself an array column) and the
comment wasn't fully re-derived for the new four-field shape. No functional impact —
the guard clauses below the comment are correct — but a future reader relying on this
comment to reason about nil-safety would be counting the wrong shape.

**Fix:**

```elixir
# ... Every field read here is present on every %Game{} (three nullable
# integers and one array column with `default: []`) — no nil-dereference
# path exists. ...
```
