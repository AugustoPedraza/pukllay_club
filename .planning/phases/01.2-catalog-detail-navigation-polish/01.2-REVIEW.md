## Summary

This phase's application source (`lib/pukllay_club/catalog.ex`, `lib/pukllay_club_web/catalog_filters.ex`, the catalog/detail LiveViews, and the shared components) is unusually disciplined: every user-supplied value that reaches a query goes through `fragment/2` with pinned `^` parameters (no string-built SQL anywhere), every client-controlled URL/image value is checked against a closed whitelist before being echoed back (`CatalogFilters.catalog_path/1`, `CatalogLive.Show.valid_gallery_image?/2`), no dynamic atom is ever built from client input (`String.to_atom/1` does not appear anywhere in the reviewed `lib/` code; the one occurrence in `catalog.ex` is a comment explaining why it's avoided), and every external URL assembled for sharing/reservation (`reservation_url/3`, `share_control/1`'s WhatsApp/X links) is built server-side with `URI.encode_www_form/1`. No `raw/1`, `Phoenix.HTML.raw`, `innerHTML` assignment, or inline `onerror=`/`onclick=` attribute exists anywhere in the reviewed files — image-load-failure handling is done via a capture-phase `error` listener in `app.js` specifically because inline handler attributes are blocked by this app's CSP. Colocated JS hooks consistently clone `<template>` content via `cloneNode`/`replaceChildren` rather than building markup from strings.

`assets/css/app.css` (4,316 lines) is heavily over-documented relative to typical production CSS, but the content itself is internally consistent: breakpoints are derived from measured arithmetic (and cross-checked by `header_capacity_test.exs`, which recomputes the same sums from the stylesheet's own declared values), the reduced-motion guard is a single `!important` catch-all rather than a hand-maintained per-selector list (closing a documented prior bug class), and no genuine cascade/selector defects were found in the sampled ~60% of the file read directly plus a full selector-inventory `grep` pass over the remainder.

Two WARNING-level correctness/consistency gaps were found, both in edge cases reachable only via direct URL manipulation (not through any in-app control), plus two INFO-level maintainability notes. No BLOCKER-tier issues were found in the reviewed application source.

## Warnings

### WR-01: Active-filter chip mislabels a crafted `?players=` value above the open-ended bucket threshold

**File:** `lib/pukllay_club_web/live/catalog_live/index.ex:691-706`
**Issue:** `players_chip/1` special-cases exactly `6` to render the label `"Jugadores: 6+"`, matching the filter semantics documented in `PukllayClub.Catalog.maybe_filter_players/2` (any `n >= @players_open_bucket` is open-ended: `max_players >= n`, no upper bound). Every other integer, including any value **above** 6, falls through to the catch-all clause and renders as `"Jugadores: N"` (an exact-count label) even though the underlying query for that same value is still open-ended, not exact-fit.

`CatalogFilters.parse_int/1` places no upper bound on `?players=`, and `handle_params/3` assigns whatever it parses directly to `:players` with no re-clamping. The in-app UI can never produce this state (the modal's chips only ever send `"2"`..`"5"` or the fixed `"6"` open-bucket value), but a shared/bookmarked URL like `/?players=10` reaches this code path via `handle_params/3` and will render a chip reading `"Jugadores: 10"` — implying an exact 10-player fit — while the actual result set behind it is every game supporting 10+ players. The chip's label and the filter's real behavior disagree for any player count above the documented open bucket.
**Fix:**
```elixir
defp players_chip(nil), do: []

defp players_chip(n) when n >= 6 do
  [scalar_chip_descriptor("players", to_string(n), "Jugadores: #{n}+", "Quitar filtro: Jugadores — #{n}+")]
end

defp players_chip(n) do
  [
    scalar_chip_descriptor(
      "players",
      to_string(n),
      "Jugadores: #{n}",
      "Quitar filtro: Jugadores — #{n}"
    )
  ]
end
```

### WR-02: `Application.get_env(:pukllay_club, :reservation_whatsapp_number)` misconfiguration is unguarded at concatenation time

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:118, 931-933`
**Issue:** `reservation_number` is read once at `mount/3` from application config and stored in the assign that gates which branch of the reservation modal renders (`:if={is_nil(@reservation_number)}` shows the "no disponible" message; the CTA/link branch is otherwise guarded). `reservation_url/3` is only reachable from the guarded branch today, so this is not exploitable through the current template — but the guard is enforced entirely by template structure, not by the function itself: `reservation_url/3` does `"https://wa.me/" <> number <> "?text=" <> ...` with no nil-check or format validation of `number`. If `reservation_number` were ever passed through a second call site, or the guarding `:if` were refactored without carrying the invariant, a misconfigured/blank env var (`""` or accidentally set to a non-numeric string) would either produce a broken `wa.me` link silently or crash on a `nil` concatenation with no clear error pointing at the config source.
**Fix:** Make the function defend its own contract rather than relying on the call site:
```elixir
defp reservation_url(number, name, game_name) when is_binary(number) and number != "" do
  "https://wa.me/" <> number <> "?text=" <> URI.encode_www_form(reservation_message(name, game_name))
end
```
This turns a future accidental call with `nil`/`""` into an immediate `FunctionClauseError` at the call site during development/tests rather than a silently broken or hard-to-trace link in production.

### IN-02: `FilterModal.checklist_placeholder/1` has no catch-all clause

**File:** `lib/pukllay_club_web/components/filter_modal.ex:508-509`
**Issue:**
```elixir
defp checklist_placeholder("mechanics"), do: "Buscar mecánica…"
defp checklist_placeholder("themes"), do: "Buscar temática…"
```
Only two literal clauses exist, and the only two call sites (`<.checklist key="mechanics" .../>` and `<.checklist key="themes" .../>` inside `filter_modal/1`) always pass one of these two literal strings, so this is not reachable with an unexpected value today. It's flagged only because every other similarly-shaped dispatch function in this same file and in `catalog_live/index.ex` (`facet_assign_key/1`, `scalar_assign_key/1`, `row_query/1`, `parse_sort/1`) deliberately ends with an explicit catch-all clause per the codebase's own stated `T-01-37` convention ("literal clauses with a final catch-all"). This one function breaks that pattern; a future third `<.checklist>` call site with a new `key` would raise `FunctionClauseError` instead of degrading gracefully.
**Fix:**
```elixir
defp checklist_placeholder("mechanics"), do: "Buscar mecánica…"
defp checklist_placeholder("themes"), do: "Buscar temática…"
defp checklist_placeholder(_unrecognized), do: "Buscar…"
```
