# Phase 01.2: Code Review Report

**Reviewed:** 2026-08-27T00:00:00Z
**Depth:** standard
**Files Reviewed:** 18
**Status:** issues_found

## Summary

This phase's catalog/detail-page code is unusually heavily annotated with provenance
comments documenting prior debug sessions, and most of the surface area (filter
whitelisting, XSS/URL-forging guards, atom-safety on client-controlled keys, the
404-not-500 id parsing, CSP-covered image origins) is genuinely well defended and
test-covered — I traced the `catalog_path/1`/`from_params/1` whitelist, the
`select-image`/lightbox membership guard, the `carousel-load-more`/`load-more`
clamp-before-query discipline, and the reservation flow's percent-encoding, and did
not find a way to break any of them from the client.

The one real defect found is a genuine cross-module data/UI inconsistency
(CR-01 below): the game-duration *text* shown in the facts pill is computed from a
different field precedence than the *link target* right next to it and the
catalog's own filter/sort logic, so for a game where BGG's three duration fields
(`playing_time`, `min_playtime`, `max_playtime`) are populated together — the normal
BGG import shape — the displayed "X-Y min" range and the destination of clicking
that same pill do not agree, and neither agrees with what the catalog's own sort
actually ordered by. No test in `game_preview_test.exs` or `catalog_show_test.exs`
constructs a fixture with all three fields set simultaneously, so this has no
regression coverage today.

A handful of smaller robustness/consistency gaps are recorded as warnings, and two
low-severity style notes as info.

## Critical Issues

### CR-01: Duration pill's displayed text and its own filter link disagree with each other and with the catalog's sort/filter field precedence

**File:** `lib/pukllay_club_web/components/game_preview.ex:62-98` (facts_row/1) and `game_preview.ex:394-400` (tiempo_text/1)
**Also:** `lib/pukllay_club/catalog.ex:481-486` (maybe_filter_playtime/2), `catalog.ex:503-511` (apply_sort/2 for `:playtime_asc`/`:playtime_desc`)

**Issue:**
`Catalog.maybe_filter_playtime/2` and both `:playtime_asc`/`:playtime_desc` sort
clauses treat `coalesce(playing_time, max_playtime)` as the single canonical
duration for a game — `playing_time` wins whenever it is present, `max_playtime` is
only the fallback. `facts_row/1`'s own tiempo **link target** matches that
precedence exactly:

```elixir
navigate={~p"/?max_playtime=#{@game.playing_time || @game.max_playtime}"}
```

But the **visible label** shown inside that same link/span comes from
`tiempo_text(assigns.game)` (assigned once, at line 66, and reused by both the
linked and unlinked branches), whose clauses only consult `playing_time` when
**both** `min_playtime` and `max_playtime` are `nil`:

```elixir
defp tiempo_text(%{min_playtime: nil, max_playtime: nil, playing_time: nil}), do: nil
defp tiempo_text(%{min_playtime: nil, max_playtime: nil, playing_time: pt}), do: "#{pt} min"
defp tiempo_text(%{min_playtime: nil, max_playtime: max}), do: "#{max} min"
defp tiempo_text(%{min_playtime: min, max_playtime: nil}), do: "#{min} min"
defp tiempo_text(%{min_playtime: min, max_playtime: max}) when min == max, do: "#{min} min"
defp tiempo_text(%{min_playtime: min, max_playtime: max}), do: "#{min}-#{max} min"
```

For any game that has `playing_time` populated **alongside** a non-nil
`min_playtime`/`max_playtime` — which is the normal shape BGG's API returns
(`playingtime`, `minplaytime`, `maxplaytime` are three independently-populated
fields on almost every BGG game) — `playing_time` is silently ignored by every
clause except the first two, and the label is built purely from the min/max range.

Concretely: a game with `playing_time: 45, min_playtime: 60, max_playtime: 120`
will:
- Sort/filter as a **45-minute** game (catalog.ex's coalesce picks `playing_time`).
- Link its facts pill to `/?max_playtime=45` (facts_row's own `||` also picks
  `playing_time`).
- **Display** the label `"60-120 min"` (tiempo_text ignores `playing_time` here).

A member reading "60-120 min" and clicking that pill lands on a catalog filtered to
games ≤45 minutes — a destination that contradicts the number they just read — and
a member sorting by duration sees this game ranked among 45-minute games while its
own card shows a 60-120 range. This is silent, incorrect, user-visible behavior
with no crash to surface it, and neither `game_preview_test.exs` nor
`catalog_show_test.exs`/`catalog_live_test.exs` constructs a fixture where
`playing_time` and `min_playtime`/`max_playtime` are simultaneously non-nil, so it
is untested.

**Fix:** Make `tiempo_text/1` consult `playing_time` with the same precedence the
filter/sort/link already use, e.g.:

```elixir
defp tiempo_text(%{playing_time: pt}) when not is_nil(pt), do: "#{pt} min"
defp tiempo_text(%{min_playtime: nil, max_playtime: nil}), do: nil
defp tiempo_text(%{min_playtime: nil, max_playtime: max}), do: "#{max} min"
defp tiempo_text(%{min_playtime: min, max_playtime: nil}), do: "#{min} min"
defp tiempo_text(%{min_playtime: min, max_playtime: max}) when min == max, do: "#{min} min"
defp tiempo_text(%{min_playtime: min, max_playtime: max}), do: "#{min}-#{max} min"
```
(or, if the range is intentionally the more informative display value, invert the
fix instead: make `maybe_filter_playtime/2`/`apply_sort/2`/the link target consult
the range first — but pick **one** precedence and apply it in all three places.)
Add a fixture with all three fields populated to whichever test file ends up
owning the corrected contract.

## Warnings

### WR-01: `similares_widened?` can be silently wrong for a nil-band game when other nil-band games exist in its result set

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:85`

**Issue:** `similares_widened? = Enum.any?(similar_games, &(&1.weight_band != game.weight_band))`.
For a nil-`weight_band` viewed game, the module's own doc comment (lines 80-85)
asserts "A no-band game's every returned game differs from `nil`, so widened? is
true — correct." That's only true if every candidate in the shelf has a *non-nil*
band. If one or more of the returned candidates is itself unbanded (plausible in a
partially-classified catalog — this is exactly the D-18/D-20 "missing band" case
this codebase already has a naming convention for elsewhere), `&1.weight_band !=
nil` evaluates `nil != nil` → `false` for those candidates, and if *all* twelve
happened to be unbanded, `similares_widened?` would be `false` — dropping the
"Ampliado" badge and the widened-shelf subtitle for a shelf that, per
`Catalog.similar_games/1`'s own documented contract, is *always* a widened pool for
a nil-band game. No test constructs a catalog where a nil-band game's similar-games
result set itself contains other nil-band games, so this gap is unexercised.

**Fix:** Compute widened-ness the same way `Catalog.band_preference_order/1`
reasons about it — e.g. `Enum.any?(similar_games, &(&1.weight_band == nil or &1.weight_band != game.weight_band))`
when `game.weight_band` is `nil` (equivalently: for a nil-band game, `widened?` is
unconditionally `true`, matching the doc comment's own stated invariant, rather
than being derived by an equality check that can accidentally match on `nil`).

### WR-02: Clipboard write has no rejection handler, unlike the sibling Web Share call two lines above

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:916-922` (`.ShareButton` hook, `onCopyClick`)

**Issue:**
```js
this.onCopyClick = () => {
  navigator.clipboard.writeText(this.copyBtn.dataset.shareUrl).then(() => {
    this.copyConfirm?.classList.remove("hidden")
    ...
  })
}
```
`navigator.clipboard.writeText` can reject (permission denied, an unfocused
document, or a non-secure context), producing an unhandled promise rejection with
no user-visible feedback — "Copiar enlace" would silently do nothing. The
`navigator.share(...).catch(() => {})` call a few lines above (`onClick`) is
explicitly guarded against the equivalent failure mode; this sibling handler isn't.

**Fix:**
```js
navigator.clipboard.writeText(this.copyBtn.dataset.shareUrl)
  .then(() => { ... })
  .catch(() => {})
```
(or surface a brief inline error state, if silent failure isn't acceptable UX
here).

### WR-03: `parse_int/1`'s docstring promises rejection of "a non-parseable binary"; the implementation silently truncates instead

**File:** `lib/pukllay_club_web/catalog_filters.ex:35-51`

**Issue:** The docstring states this returns `nil` for "`nil`, `""`, a
non-parseable binary, or any non-binary value." `Integer.parse/1`, however,
succeeds on any string with a leading integer, discarding the remainder:
`parse_int("4abc")` returns `4`, not `nil`. Every scalar query param this feeds
(`?players=`, `?max_playtime=`, `?min_age=`) will silently accept and use a
garbage-suffixed value rather than degrading to "unset," contradicting the
documented contract. Low practical exposure today (no UI control emits such a
value — this is only reachable via a hand-crafted URL or a forged
`toggle-scalar` payload), but a hand-crafted URL is exactly the threat model the
rest of this module (`@max_from_length`, the `parse_list_param` cap, the whole
`catalog_path/1` rescue) is written to defend against.

**Fix:** Either update the docstring to describe the actual (leading-prefix)
behavior, or validate the full string, e.g.:
```elixir
def parse_int(str) when is_binary(str) do
  case Integer.parse(str) do
    {n, ""} -> n
    _ -> nil
  end
end
```

### WR-04: `Catalog.carousel_page/3` has no fallback clause for an out-of-domain offset

**File:** `lib/pukllay_club/catalog.ex:318-325`

**Issue:** The only defined clause is guarded by `when is_integer(offset) and
offset >= 0`. A call with a negative or non-integer `offset` has no matching
clause and raises `FunctionClauseError` rather than returning `:error` the way
an unrecognized row `key` already does two lines later. Not currently reachable —
`offset` always originates from server-tracked `carousel_rows` metadata, never
directly from client input — but it's a latent gap in a function whose own doc
comment (and this module's broader "never raises on bad input" convention, see
`get_game!/1`, `safe_filter_games/1` at the call sites) argues it should degrade
gracefully instead of crashing if a future caller (or a refactor of the
`handle_event("carousel-load-more", ...)` call site) ever passes an
un-server-validated value through.

**Fix:** Add a catch-all clause:
```elixir
def carousel_page(_key, _offset, _limit), do: :error
```

## Info

### IN-01: Implicit-nil `if` without `else` in a validator

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:191-195`

**Issue:** `reservation_name_error/1`'s length check has no `else` branch, relying
on the implicit `nil` an `if` without `else` returns for the "valid" case. Not
incorrect, but slightly obscures intent versus an explicit `else: nil`, and is the
kind of thing Credo's `--strict` mode sometimes flags.

**Fix:**
```elixir
defp reservation_name_error(name) do
  if String.length(name) > 60 do
    "El nombre es demasiado largo (máximo 60 caracteres)."
  else
    nil
  end
end
```

### IN-02: `console.error` calls in production-shipped colocated hook code

**File:** `lib/pukllay_club_web/components/layouts.ex:245,257,309,326,402,455`

**Issue:** `.CatalogNav`'s six `try/catch` blocks each log to `console.error` on
failure. This is a deliberate, well-reasoned defensive pattern (each block is
independent so one throwing block can't take a sibling down), not an accidental
debug leftover, but it does mean any visitor's browser console will show internal
wiring failure messages verbatim in production if one of these blocks ever throws.

**Fix:** Consider routing these to a lightweight client-side telemetry/reporting
call instead of (or in addition to) `console.error`, if silently degrading without
any operator visibility is a concern — no action needed if console-only visibility
is the intended behavior for a solo-dev project at this stage.
