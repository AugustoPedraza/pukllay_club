See CR-01 below for the full math.

## Critical Issues

### CR-01: `.pk-lightbox-img`'s new real `height: 80vh` (was `max-height: 80vh`) regresses the mobile lightbox to a letterboxed stage, contradicting the shipped comment's "vertical footprint is unchanged" claim

**File:** `assets/css/app.css:3422-3436` (rule), comment at `3392-3411`
**Also:** `test/pukllay_club_web/live/catalog_show_test.exs:2521-2525` (the test that locks the
regressed value in as "correct")

**Issue:**

Before this round, `.pk-lightbox-img` had:
```css
max-width: calc(min(100vw, var(--container-7xl, 80rem)) - (2 * var(--pk-gutter)));
max-height: 80vh;
```
For a **replaced element** (a plain `<img>`) with both `max-width` and `max-height` set and no
explicit `width`/`height`, the browser's standard sizing algorithm shrinks the intrinsic size to
fit *both* caps while preserving the image's own aspect ratio — whichever cap is more restrictive
wins, and the box always matches the photo's real proportions.

Every detail-page photo is produced by `PukllayClub.Catalog.Seed.ImagePipeline` at a fixed,
near-square ~800×800px intrinsic size (this file's own new comment on `.pk-lightbox-img`, lines
3384-3390, states this directly). On a phone (e.g. 390×844):
- `--pk-shell-content-width` = `min(390px, 1280px) - 2×14px` (gutter is 0.875rem below the 480px
  breakpoint) ≈ **362px**.
- Since 362px < 800px, the **width cap was already the binding constraint before this round** —
  the old `max-height: 80vh` (≈675px at 844px viewport height) was never reached; the box rendered
  at roughly 362×362 (aspect-preserved), a tight box around the photo.

This round replaces both caps with **real, independent dimensions**:
```css
width: var(--pk-shell-content-width);   /* ≈362px on the phone above — same as before */
height: 80vh;                            /* ≈675px on the phone above — new: was never binding before */
background: var(--pk-shadow-color);      /* new: opaque fill */
```
`width` alone is an accurate, desktop-motivated fix (a `max-width` can only shrink an already-
smaller intrinsic size, so the previous round's widened cap was a no-op — this part of the
reasoning in the file's own comment is correct and well-evidenced). But making `height` a *real*
80vh — not a cap — is a value that was **never exercised on mobile before**, because mobile's
width constraint always won first. The result: on a phone, the lightbox box is no longer ~362×362
hugging the photo; it becomes ~362×675, with the near-square photo letterboxed by `object-fit:
contain` inside a solid `--pk-shadow-color`-filled rectangle roughly twice as tall as the photo
itself — a large, visually prominent dead-space stage that did not exist before this change and
was never part of the reported defect (which was specifically about *desktop* "photo floats in a
small central column while arrows anchor to the viewport edge").

The rule's own comment states: *"`height` carries the previous round's `max-height: 80vh` forward
as a real size, same number — the lightbox's vertical footprint is unchanged, a human already
signed off on it."* This claim is false for every viewport where the width cap (not the height
cap) was the binding constraint before — which, per the math above, is every mobile viewport and
likely a meaningful band of tablet/laptop widths too (any width where
`--pk-shell-content-width` < ~800px, i.e. below roughly 864px viewport width including gutters).
Only genuinely wide desktop viewports (where the width cap exceeds 800px, which is exactly the
band this fix targets) ever had a chance of the old `max-height: 80vh` being the binding
constraint — and even there, a human sign-off on "80vh, capped" is not the same design decision as
"80vh, forced," since the former only bound when the aspect-preserving box was already taller than
80vh, while the latter always renders at 80vh regardless of the photo's own proportions.

This project's own developer memory explicitly prioritizes mobile ("mobile is primary for all
UI/UX/content/perf work; desktop is secondary") — this change fixes a desktop-only defect in a way
that introduces an unreviewed, undocumented, and inaccurately-described mobile regression, with no
gating breakpoint and no accompanying `<human-check>` covering the mobile case specifically (the
plan's own human-check items, per the doc trail, were scoped to the desktop scrim/width complaint
and to verifying both light/dark themes for the opaque fill — not to mobile vertical footprint).

**Fix:** Scope the forced real `height`/opaque `background` to the range where it is actually
needed (desktop, where the width cap exceeds the photo's intrinsic size), and leave mobile on the
previous aspect-preserving cap behavior:

```css
.pk-lightbox-img {
  width: var(--pk-shell-content-width);
  max-height: 80vh;
  object-fit: contain;
  border-radius: var(--radius-box);
  box-shadow: 0 28px 56px color-mix(in srgb, var(--pk-shadow-color) 38%, transparent), 0 10px 24px color-mix(in srgb, var(--pk-shadow-color) 24%, transparent);
  transform: scale(0.96);
  transition: transform var(--duration-base) var(--ease-out-soft);
}

/* Opaque stage fill + forced full-height box: only where the shell-width
   cap can actually exceed the photo's own ~800px intrinsic size (desktop),
   so mobile keeps its previous aspect-preserving, tightly-hugging box. */
@media (min-width: 48rem) {
  .pk-lightbox-img {
    height: 80vh;
    background: var(--pk-shadow-color);
  }
}
```
(Adjust the exact breakpoint/condition to match wherever product actually wants the stage effect
to start — the point is that the real-height/opaque-fill pair should not apply unconditionally
across every viewport including the ones where it was never exercised or intended.) Update the
now-incorrect "vertical footprint is unchanged" comment to describe the corrected, viewport-scoped
behavior, and update the corresponding test at
`test/pukllay_club_web/live/catalog_show_test.exs:2499-2546` (currently asserts an unconditional
`height: 80vh;` on the bare rule) to match.

## Info

### IN-01: Comment-to-code ratio for this round's CSS change is very high, and one paragraph asserts a viewport-independent claim without the same live-verification rigor used elsewhere in the file

**File:** `assets/css/app.css:263-303` (new `--pk-shell-content-width` token, ~40 lines of comment
for a 1-line declaration), `3379-3421` (~43 lines of comment for a 3-property rule change),
`3469-3505` (~37 lines of comment for two 1-line rules)

**Issue:** This is consistent with the file's existing house style (most rules in this stylesheet
carry proportionally large comments), so it is not a new pattern — but it's worth noting that the
file's own convention elsewhere is to back non-obvious cross-viewport claims with an explicit
"verified live in a real browser (headless Chromium via CDP...)" note (see the containing-block
audits on `.pk-title-echo`/`.pk-lightbox`, and `.pk-app-shell`'s own measured-at-390px note). The
"vertical footprint is unchanged" claim in the comment addressed in CR-01 has no such verification
note attached, and is the one claim in this round's changes that turns out not to hold. Given the
file's own precedent, a live-viewport check (mobile width specifically) before asserting "human
already signed off on it, unchanged" would have caught CR-01 before it shipped.

**Fix:** When a change comment asserts "unchanged" or "same visual result" across viewports,
verify it the same way the rest of this file already does for non-obvious geometry claims (a real
narrow-viewport screenshot/measurement), not just at the one viewport the reported bug was
diagnosed at.
