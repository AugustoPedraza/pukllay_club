## Summary

Scope was narrowed, per the task, to the diff introduced since `054daa2` on `assets/css/app.css` and
`test/pukllay_club_web/live/catalog_show_test.exs` — plan `01.2-30` (dark-theme lightbox close-button
contrast) and plan `01.2-31` (opaque lightbox backdrop). This does not re-review the rest of the
phase's 24 earlier plans, which are covered by the existing `01.2-REVIEW.md` history.

Both changes were independently verified to be functionally correct:

- `.pk-lightbox`'s `background` moved from `var(--pk-overlay-scrim)` (a 72%-alpha mix) to a bare
  `var(--pk-shadow-color)` (opaque). `--pk-overlay-scrim` was confirmed (via grep across the whole
  file) to now have exactly one remaining reader, `.pk-sheet-backdrop`, matching the updated `:root`
  comment's claim.
- `[data-theme="dark"] .pk-lightbox-close { --btn-color: var(--color-neutral); --btn-fg:
  var(--color-neutral-content); }` was checked against daisyUI's actual compiled `.btn`/`.btn-neutral`
  rules (`deps/daisyui/packages/bundle/daisyui.mjs`): `.btn` resolves `--btn-bg` from
  `var(--btn-color, var(--color-base-200))` and its own text/icon color from `--btn-fg`, and
  `.btn-neutral` sets exactly this same pair together — so the new rule is a faithful, minimal
  reimplementation of that variant, scoped correctly to dark theme only.
- The new WCAG contrast test (`relative_luminance/1`, `contrast_ratio/2`) was independently
  recomputed in Python against the actual token hex/rgb values in the file and reproduced the
  documented ≈8.6:1 fill ratio and ≈8.5:1 icon ratio, both comfortably above the asserted 3.0/4.5
  floors — the test is not a false-positive rubber stamp, it measures a real, adequately-margined
  pass.
- All new/modified regexes in the test file were traced against the actual CSS text they target
  (selector anchoring, brace-matching, `.pk-lightbox` vs `.pk-lightbox-close`/`.pk-lightbox-img`/
  `.pk-lightbox.is-open` disambiguation) and match correctly with no false-positive overlap.

Two documentation/traceability defects were found, both real but neither rising to a
functional/security blocker — see below.

## Warnings

### WR-01: Gap identifier `G-01.2-20` is now ambiguous — reused for two unrelated fixes in the same test file

**File:** `test/pukllay_club_web/live/catalog_show_test.exs:2755-2769` (new), colliding with pre-existing
uses at `test/pukllay_club_web/live/catalog_show_test.exs:26`, `:588`, `:1599`, `:2082`
**File:** `assets/css/app.css:3541`, `:3576` (new)

**Issue:** This diff introduces a brand-new gap-closure item labelled `G-01.2-20` for the lightbox
close-button dark-theme contrast fix (new `describe "lightbox close button dark-theme contrast
(Phase 01.2 gap-closure round 8, G-01.2-20, plan 01.2-30)"` block, plus the matching `app.css`
comment at line 3541 and the `[data-theme="dark"] .pk-lightbox-close` rule at line 3576).

That exact literal string, `G-01.2-20`, was already in use in the same test file — before this
diff — for a completely unrelated, already-closed gap: the removal of the weight-band badge/
descriptor sentence and the migration of its link target to the dificultad pill (test names at
lines 26, 588, 1599, and 2082, e.g. `"renders the weight-band label but no badge element and no
descriptor sentence (G-01.2-20)"` and `"Mecánicas/Temáticas chip contrast fix (G-01.2-20 task 2)"`).

Verified against `.planning/phases/01.2-catalog-detail-navigation-polish/01.2-UAT.md`: the current
UAT gap ledger records only one live `gap_id: G-01.2-20` entry, and it is the lightbox close-button
one — so the newer usage is the "correct" canonical one going forward, but the four older test names
carrying the identical literal tag were never renamed or disambiguated when the ID was recycled.
Grepping the test suite for `G-01.2-20` today returns eight matches spanning two semantically
unrelated features, with nothing in the text to tell a reader which occurrences are current.

This is a real traceability defect this diff completes (even though half of the collision predates
it): a future engineer investigating "what is G-01.2-20" from a test failure or `git grep` has no
way to disambiguate without reading full context on every hit, and a future audit tool that expects
gap IDs to be 1:1 with UAT ledger entries will silently misattribute one of these two fixes to the
other's evidence trail.

**Fix:** Since the UAT ledger has already recycled the ID, the cleanest fix is to rename the four
older test names (and any other stray `G-01.2-20` references tied to the badge-removal task) to a
distinct, non-colliding label — e.g. the enclosing plan number, `01.2-20`, or a synthesized
`G-01.2-20-badge` — so a future `grep -rn "G-01.2-20"` reliably returns only the lightbox
close-button work:

```elixir
test "renders the weight-band label but no badge element and no descriptor sentence (01.2-20)",
```

### WR-02: Two directly contradictory statements about `.pk-lightbox`'s translucency now coexist in the same file

**File:** `assets/css/app.css:3486-3512` (pre-existing, not touched by this diff) vs.
`assets/css/app.css:3362-3419` (new, added by this diff)

**Issue:** The new G-01.2-19 comment block above `.pk-lightbox` (added by this diff, lines
3362-3419) correctly states that a prior round's remark no longer holds:

> "One more consequence worth naming: G-01.2-18's remark below, above `.pk-lightbox-img`, about a
> hairline of scrim during the opening scale-in no longer applies — the photo still visibly scales
> in, but the stage's edge simply stops reading, since the field behind it is now the same colour."

However, the sentences it is referring to (the pre-existing G-01.2-18 paragraph, untouched by this
diff, at lines 3486-3512) were never edited or removed. That paragraph still asserts, in the present
tense, both of the following — both now false given this diff's own change of `.pk-lightbox`'s
`background` from `var(--pk-overlay-scrim)` (translucent) to `var(--pk-shadow-color)` (opaque):

- Line 3491-3492: "...rendered as two symmetric bands of `.pk-lightbox`'s **own translucent scrim**,
  one above the stage and one below it..." — `.pk-lightbox`'s background is no longer translucent.
- Lines 3508-3512: "...a hairline of scrim is visible for the length of that animation and then
  gone — existing motion on existing tokens, **unchanged by this round**." — the new comment block
  three paragraphs above this one explicitly says this is now wrong ("no longer applies"), yet the
  original claim of "unchanged" was left standing.

The file now contains two comment blocks that flatly disagree about the same visual mechanism, with
no correction applied to the older one — only a forward note in the newer one saying the older one
is stale. A future editor who reads the G-01.2-18 paragraph in isolation (a very plausible path,
since it sits directly above `.pk-lightbox-img`, the rule it is actually documenting) will be told
something the code no longer does.

**Fix:** Strike or correct the two stale sentences in the pre-existing G-01.2-18 paragraph rather
than only forward-referencing their staleness from the new paragraph — e.g.:

```diff
-  First: `.pk-lightbox` (above) is a CENTRING flex container, not a stretching
-  one, so any shortfall between this rule's own height and the viewport
-  rendered as two symmetric bands of `.pk-lightbox`'s own translucent
-  scrim, one above the stage and one below it — the entire mechanism
-  behind the user's "the background should be full screen" report.
+  First: `.pk-lightbox` (above) is a CENTRING flex container, not a stretching
+  one, so any shortfall between this rule's own height and the viewport
+  rendered as two symmetric bands of `.pk-lightbox`'s own background
+  (translucent at the time this paragraph was written; opaque as of
+  G-01.2-19, see above), one above the stage and one below it — the entire
+  mechanism behind the user's "the background should be full screen" report.
```
and similarly correct "unchanged by this round" in the closing sentence to point at the newer
G-01.2-19 paragraph instead of asserting something the diff itself falsifies.
