## Warnings

### WR-01: `toggle-facet` bypasses `CatalogFilters`' whitelist/cap, contradicting its own "single authority" claim

**File:** `lib/pukllay_club_web/live/catalog_live/index.ex:239-249`

**Issue:** `CatalogFilters`' moduledoc states it is "the single authority for reading, validating and re-encoding catalog filter params ... The two consumers can never drift apart on which facet values are accepted because there is exactly one copy of each parsing rule." That is true for the URL read path (`from_params/1`, capped at 20 items, membership-checked against the closed Vocabulary set) and the `?from=` breadcrumb path (`catalog_path/1`). It is **not** true for the live socket path: `handle_event("toggle-facet", %{"facet" => facet, "choice" => value}, socket)` pushes any client-supplied `value` string directly into `:mechanics` / `:themes` / `:weight_bands` / `:tags` with:
- no cap (unlike `from_params/1`'s `Enum.take(20)`), and
- no Vocabulary membership check (unlike `from_params/1`'s `Enum.filter(&(&1 in allowed))`).

A scripted client pushing WebSocket events directly (bypassing the rendered pill markup, which normally only emits known-good values) can grow one of these lists without bound simply by sending distinct `choice` values on each call — `current = Map.get(socket.assigns, key, [])` / `[value | current]` never de-dupes against a whitelist, only against exact repeats. For `mechanics`/`themes` this degrades harmlessly to an always-empty result set (`Vocabulary.mechanic_terms_for/1` returns `[]` for an unknown label, so the resulting `&&` array-overlap predicate matches nothing) — but for `weight_bands`/`tags`, arbitrary un-validated strings flow straight into `where: g.weight_band in ^bands` / `fragment("? && ?", g.tags, ...)` as a growing bound parameter array. This is self-inflicted (only that visitor's socket state is affected) and not a SQL-injection vector (still fully parameterized), but it is a genuine input-validation gap directly adjacent to the phase's own "single authority" security claim, and an unbounded-list-growth vector that the phase's other new code (carousel/grid infinite scroll) was explicit about closing.

**Fix:** Route `toggle-facet`'s value through the same Vocabulary/cap discipline `CatalogFilters.parse_list_param/2` already implements, e.g. extract that private function to a public `CatalogFilters.valid_facet_value?/2` (or `CatalogFilters.parse_list_param/2` itself, made public) and reuse it in the handler:
```elixir
def handle_event("toggle-facet", %{"facet" => facet, "choice" => value}, socket) do
  case facet_assign_key(facet) do
    nil -> {:noreply, socket}
    key ->
      current = Map.get(socket.assigns, key, [])

      if CatalogFilters.valid_facet_value?(key, value) do
        updated =
          if value in current,
            do: List.delete(current, value),
            else: Enum.take([value | current], 20)

        {:noreply, socket |> assign(key, updated) |> apply_filters()}
      else
        {:noreply, socket}
      end
  end
end
```

### WR-02: `ficha_tecnica?/1`'s "no nil-dereference path exists" claim is not backed by the schema

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:788-794` (guard), `:399,403` (usage: `Enum.join(@game.designers, ", ")` / `Enum.join(@game.publishers, ", ")`)

**Issue:** The comment on `ficha_tecnica?/1` states: "Every field read here is present on every `%Game{}` (two integers, two array columns with `default: []`, one nullable integer) — no nil-dereference path exists." I checked this against the actual schema/migration:
- `lib/pukllay_club/catalog/game.ex`: `field :designers, {:array, :string}, default: []` — this is an **Ecto-level** default only, applied when the key is *absent* from the changeset's `attrs`.
- `priv/repo/migrations/20260806234228_create_games.exs`: `add :designers, {:array, :string}, default: []` — no `null: false`, so the column itself allows `NULL` at the database level.
- `seed_changeset/2` calls `validate_required([:name, :csv_row])` only — `designers`/`publishers` are cast but never required.

If the seed pipeline (or any future admin write path) ever passes an explicit `nil` for `designers`/`publishers` in `attrs` (e.g. a CSV cell that maps to `nil` rather than being omitted), `cast/3` will set the changeset field to `nil`, overriding the Ecto default, and the row will persist with `designers: NULL`. On the detail page, `:if={@game.designers != []}` evaluates `nil != []` → `true` (Elixir has no falsy `nil == []` shortcut), so the branch renders and `Enum.join(@game.designers, ", ")` raises `Protocol.UndefinedError` for `Enumerable.Atom`, crashing the entire detail-page render (500) — for the game's *primary* content, unlike every other degrade-gracefully path this phase and the surrounding code otherwise take pains to guarantee (e.g. `safe_similar_games/1`, `safe_filter_games/1`).

This is a pre-existing schema gap (not introduced by this phase's diff — the vulnerable `Enum.join` lines are unchanged, only the surrounding `ficha_tecnica?/1` guard is new), but the new comment makes an unverified safety claim about it. I did not confirm any *live* row currently has `designers: nil` — this is a latent risk, not a proven crash today.

**Fix:** Either (a) add a DB-level `null: false` migration + Ecto `default: []` for `tags`/`mechanics`/`themes`/`designers`/`publishers`/`gallery_urls` (closes the gap structurally), or (b) defensively coalesce at the read boundary, e.g. `defp designers(game), do: game.designers || []` used everywhere these fields are read, or (c) at minimum soften the comment to note this is an assumption about the seed pipeline rather than a schema-enforced guarantee.

### WR-03: `.GridScroll` mounts and can fire `load-more` even while `@load_error` is true

**File:** `lib/pukllay_club_web/live/catalog_live/index.ex:726-732` (`:if={browsing_results?(assigns) and not @loading}`, no `and not @load_error` guard)

**Issue:** When `safe_filter_games/1` fails (`apply_filters/1`'s `:error` branch, `index.ex:426-432`) with a filter active, `browsing_results?/1` is still `true` (a filter is set) and `@loading` is `false` (this only happens post-connect), so the `#grid-scroll` container — including its `.GridScroll` colocated hook and `IntersectionObserver` — still mounts, even though the load-error banner (`index.ex:679-689`) is showing and the `#games` grid is empty/`hidden` (`@total == 0`). Because the trailing skeleton placeholders inside `#games` are hidden via `data-loading` (not removed), the sentinel can sit near the top of an effectively-empty container and the `IntersectionObserver` may immediately fire `maybeLoadMore()`, triggering one `pushEvent("load-more", ...)`. The server-side clamp (`offset(0) >= total(0)`) catches this and replies `exhausted: true` with **no additional query** — so this is not a security/correctness bug — but it is an untested, unintended extra round trip on every load-error state, and a maintenance trap: a future change to the clamp logic could silently reintroduce a real double-fetch here since this path has no test coverage (the existing "d3: mid-scroll error unreachable" comment in the test file documents a *different* untestable path, not this one).

**Fix:** Add `and not @load_error` to the `#grid-scroll` container's `:if` guard, matching the discipline already used for the "no results" empty-state block (`index.ex:700`, `and not @load_error`).

### WR-04: Broad `rescue` clauses in the new `catalog_path/1` (and its siblings) log nothing

**File:** `lib/pukllay_club_web/catalog_filters.ex:106-117` (also pre-existing `safe_filter_games/1` in `index.ex:476-480`, `safe_similar_games/1` in `show.ex:806-810`)

**Issue:** `catalog_path/1`'s `rescue _error -> "/"` is a bare catch-all with zero logging. This is by design for the documented hostile-input cases (malformed percent-escapes, oversized junk), but it also silently swallows *genuine* bugs — e.g., a future refactor of `from_params/1` that raises for a legitimate, previously-working `from=` value would degrade indistinguishably from a malicious one, with no error surfaced in logs/telemetry/Sentry. Given this function is new in this phase and directly on a user-navigation path (every "back to catalog" breadcrumb click), a real regression here would be invisible in production until someone reports "the breadcrumb always goes to `/`."

**Fix:** At minimum, `Logger.warning/2` inside the rescue clause with the exception and a truncated/redacted value, e.g.:
```elixir
rescue
  error ->
    Logger.warning("CatalogFilters.catalog_path/1 rescued #{inspect(error.__struct__)}")
    "/"
```

## Info

### IN-01: `q` length-capping logic duplicated between `CatalogFilters.q/1` and the `"search"` handler

**File:** `lib/pukllay_club_web/live/catalog_live/index.ex:207-209` vs. `lib/pukllay_club_web/catalog_filters.ex:32-33`

**Issue:** `CatalogFilters.q/1` exists specifically to be "the single copy" of the `q` bounding rule (per its own doc comment), and `mount/3` correctly calls it. However `handle_event("search", %{"q" => q}, socket)` re-implements the identical `String.slice(q, 0, 100)` inline instead of calling `CatalogFilters.q(%{"q" => q})`. Currently in sync, but two independently-maintained copies of a "single source of truth" rule is exactly the drift pattern this phase's own `CatalogFilters` module was introduced to prevent elsewhere.

**Fix:** `assign(:q, CatalogFilters.q(%{"q" => q}))` (or expose a `CatalogFilters.clamp_q/1` taking the raw string) instead of the inline `String.slice`.

### IN-02: Lightbox main image has no cover-fallback treatment

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:509`

**Issue:** The buy-box cover image and gallery thumbnails all carry (or are adjacent to) the `.js-cover-fallback` pattern, but the lightbox's own `<img src={@selected_image} alt={@game.name} class="pk-lightbox-img" />` does not carry the `js-cover-fallback` class. A broken/404 image URL opened in the lightbox falls back to the browser's default broken-image glyph instead of this app's brand placeholder — inconsistent with every other image surface this phase touched. Pre-existing (not part of this phase's diff), flagged only because it sits directly next to the cover-fallback work done here.

**Fix:** Add `js-cover-fallback` to the lightbox `<img>` and a hidden placeholder sibling, matching the pattern in `GameCard`/`GamePreview`/the buy-box image.
