# Phase 01.2: Code Review Report

**Reviewed:** 2026-08-29T15:03:14Z
**Depth:** standard
**Files Reviewed:** 20 (source + test)
**Status:** issues_found

## Summary

This phase (catalog/detail navigation polish, plus a long tail of UAT gap-closure rounds) is
unusually well-documented — nearly every CSS rule and LiveView handler carries an inline record of
the bug it fixes, the UAT round that reported it, and the measurement that proved the fix. Query
construction consistently uses pinned `^` Ecto parameters (no string-built SQL), every client-
supplied value that reaches a query or an `<img src>` goes through a closed Vocabulary whitelist or
an explicit membership check (`valid_gallery_image?/2`, `CatalogFilters.from_params/1`), and no
`raw/1`, `eval`, or inline-script CSP bypass was found. Reduced-motion, focus-trapping, and
containing-block hazards (the classic `position: fixed` + `transform`/`filter` ancestor trap) are
each handled with a single, well-reasoned mechanism reused across every overlay in the app, rather
than one bespoke implementation per surface.

No BLOCKER-severity defects were found in the reviewed files. The findings below are maintainability
and consistency gaps: a display helper that silently diverges from the filter predicate it should
mirror, a business-rule constant duplicated as a bare literal across three files with nothing tying
them together, a missing catch-all clause in a currently-unreachable-but-fragile private function,
and an untested data combination (`cover_url: nil` + non-empty `gallery_urls`) that the code's own
"cover_url first" comment implies should never happen but does not defensively handle.

## Warnings

### WR-01: `tiempo_text/1`'s display text can silently diverge from the playtime filter's own priority

**File:** `lib/pukllay_club_web/components/game_preview.ex:394-400`

**Issue:** `PukllayClub.Catalog.maybe_filter_playtime/2` filters games using
`coalesce(playing_time, max_playtime) <= n` (`lib/pukllay_club/catalog.ex:483-486`) — i.e.
`playing_time` wins whenever it is present, and `max_playtime` is only a fallback. `tiempo_text/1`'s
clause order does the opposite whenever `min_playtime` is `nil` and `max_playtime` is non-nil:

```elixir
defp tiempo_text(%{min_playtime: nil, max_playtime: nil, playing_time: nil}), do: nil
defp tiempo_text(%{min_playtime: nil, max_playtime: nil, playing_time: pt}), do: "#{pt} min"
defp tiempo_text(%{min_playtime: nil, max_playtime: max}), do: "#{max} min"   # <- ignores playing_time entirely
```

The third clause matches on `min_playtime: nil, max_playtime: <anything non-nil>` and does not
mention `playing_time` at all, so for a game where `min_playtime` is `nil`, `max_playtime` is set,
and `playing_time` is also set to a *different* value, the pill shown to the visitor
(`max_playtime` min) can disagree with the value the "Duración máxima" filter actually evaluated
against (`playing_time`). This combination is not exercised by
`test/pukllay_club_web/components/game_preview_test.exs` (its one playtime-focused test,
"a game with min_playtime: nil and a non-nil, non-equal max_playtime renders without crashing
(CR-01 regression)" at line 84, sets `max_playtime: 45` but leaves `playing_time` at its struct
default of `nil`, so it never reaches the branch where the two diverge) nor by any fixture in
`test/pukllay_club/catalog_test.exs`.

**Fix:** Make the display helper read `playing_time` with the same priority the filter uses, e.g.:

```elixir
defp tiempo_text(%{min_playtime: nil, max_playtime: max, playing_time: pt}) when not is_nil(max) do
  "#{pt || max} min"
end
```

placed before the current third/fourth clauses, and add a test with `playing_time` and
`max_playtime` both set to different values to lock the intended priority in.

### WR-02: The "6+" open players bucket threshold is a bare literal duplicated across three files with nothing enforcing agreement

**Files:**
`lib/pukllay_club/catalog.ex:53` (`@players_open_bucket 6`),
`lib/pukllay_club_web/components/filter_modal.ex:257` (`value="6" label="6+"`),
`lib/pukllay_club_web/live/catalog_live/index.ex:693` (`defp players_chip(6) do`)

**Issue:** The catalog query's open-ended-players threshold is a module attribute
(`@players_open_bucket 6`) in `Catalog`, but it is private to that module. Both the filter modal's
chip markup and the active-filters-chip removal logic in `CatalogLive.Index` re-encode the same `6`
as a bare literal, with no shared constant and no test asserting the three stay in sync. If the
threshold is ever changed (e.g. to `5` or `8`) in `catalog.ex`, the filter predicate changes but the
modal still renders a chip labelled "6+" bound to the old value, and `players_chip/1`'s
pattern-matched clause (`players_chip(6)`) stops matching the new threshold — the active-filter
"chip" for the open bucket would silently fall through to the generic `players_chip(n)` clause and
render `"Jugadores: <new-threshold>"` instead of the intended `"Jugadores: N+"` copy, with no error
raised anywhere.

**Fix:** Expose the threshold from `Catalog` (e.g. `def players_open_bucket, do: @players_open_bucket`)
and have both `filter_modal.ex` and `index.ex` read it, or add a shared module (already the pattern
used for `CatalogFilters`) that both the query layer and the two presentation layers import from.
At minimum, add a test in `catalog_live_test.exs` or `filter_modal_test.exs` that fails loudly if the
three literals ever disagree.

### WR-03: `checklist_placeholder/1` has no catch-all clause

**File:** `lib/pukllay_club_web/components/filter_modal.ex:508-509`

**Issue:**

```elixir
defp checklist_placeholder("mechanics"), do: "Buscar mecánica…"
defp checklist_placeholder("themes"), do: "Buscar temática…"
```

Every current call site passes a hardcoded `key="mechanics"` or `key="themes"` (lines 367, 372), so
this is unreachable today, but it is a `FunctionClauseError` waiting for the next author who adds a
third checklist (`weight_bands`, `tags`, etc.) to the disclosure and forgets this helper exists —
the crash would surface as a 500 in the LiveView render path rather than a compile-time warning.

**Fix:** Add a catch-all clause (`defp checklist_placeholder(_key), do: "Buscar…"`) or, since `key`
is always one of two literal strings by construction from `checklist/1`'s own two call sites, narrow
`checklist/1`'s `attr :key` to an enum (`values: ["mechanics", "themes"]`) so Phoenix.Component
itself rejects an unrecognized key at compile/render time instead of at the private helper.

### WR-04: No fallback when a game has gallery images but no `cover_url`

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:104, 1053-1057`

**Issue:** `mount/3` seeds `@selected_image` (the page's main poster image) directly from
`game.cover_url`, with no fallback:

```elixir
|> assign(:selected_image, game.cover_url)
```

`gallery_thumbnails/1`'s own comment states the intent explicitly: "`cover_url` first so it's always
the initial thumbnail/main image when present" — implying the assumption that `cover_url` is always
present whenever a gallery exists. Nothing in the reviewed code enforces that invariant. If a game
row ever has `cover_url: nil` together with a non-empty `gallery_urls` list, `@selected_image` stays
`nil` at mount: the poster panel renders the puzzle-piece placeholder (`show.ex:426-432`) instead of
the first real gallery photo, the lightbox trigger button never renders (`:if={@selected_image}` at
line 410), and the visitor must manually tap a thumbnail before any real image or the lightbox
becomes reachable. `test/support/fixtures/catalog_fixtures.ex` always sets a non-nil `cover_url` by
default, and no test in `catalog_show_test.exs` exercises `cover_url: nil` together with a non-empty
`gallery_urls`, so this combination is untested either way.

**Fix:** If the seed pipeline can genuinely produce this combination, default `@selected_image` to
`List.first(gallery_thumbnails(game))` instead of `game.cover_url` directly, e.g.
`assign(:selected_image, game.cover_url || List.first(game.gallery_urls))`, and add a regression
test. If the pipeline provably cannot produce this combination (worth confirming against
`PukllayClub.Catalog.Seed.ImagePipeline`, outside this review's file scope), leave a comment on
`gallery_thumbnails/1` recording that invariant explicitly rather than only implying it.

### IN-02: `active_filter_chips/1` is invoked twice per render in `index.ex`

**File:** `lib/pukllay_club_web/live/catalog_live/index.ex:1026, 1036`

```heex
<div :if={active_filter_chips(assigns) != []} ...>
  <button :for={chip <- active_filter_chips(assigns)} ...>
```

The same pure function is called once for the `:if` guard and again for the `:for` enumeration on
every render of the results header. This is a minor duplication of work (out of this review's
in-scope performance concerns) rather than a correctness issue, but it is easy to fix cheaply: bind
the result to an assign once (e.g. via a local `let` in the template or an `assign` upstream) and
reuse it for both the guard and the loop.
