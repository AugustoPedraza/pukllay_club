# Phase 01.2 Plan 12: Active-Filters Chip Row + Settle-Once Background Surface Summary

**Inline removable active-filters summary beside "Resultados" (sketch 029 winner C) plus a DESIRED-vs-RENDERED surface split (`:rendered_results`/`settle_surface/1`) that freezes the carousel/grid background while the filter modal is open and repopulates it in one round trip when the modal closes — closing gap G-01.2-4's remaining two sub-defects (no active-filter affordance; the UI "jumping" during live-apply filtering).**

## Performance

- **Duration:** 45 min
- **Completed:** 2026-08-26
- **Tasks:** 3/3 completed
- **Files modified:** 5

## Accomplishments

- Added an inline chip row to `CatalogLive.Index`'s Resultados header: one `.pk-active-filter-chip` per active mechanic/theme/weight-band/tag/scalar plus a chip for the free-text query (deliberately included even though `active_filter_count/1` excludes it), each removable by reusing the already-shipped `toggle-facet`/`toggle-scalar` handlers with the value the handler already treats as a toggle-off, plus a new parameterless `clear-query` handler for the query chip and a `Limpiar filtros` clear-everything action.
- Introduced `:rendered_results` as the single source of truth for what the DOM actually holds, distinct from `browsing_results?/1` (the pure DESIRED-surface predicate, now called from exactly one place: `settle_surface/1`). `settle_surface/1` is a no-op while `@filters_open` is true, so toggling facets inside the open modal no longer restructures the carousels/grid behind the blur — only the modal's own live match count updates, exactly as before.
- Wired `settle_surface/1` into `apply_filters/1` (immediately before `sync_carousel_visibility/1`, which now reads `:rendered_results` instead of re-deriving it) and into `mount/3` (seeding the correct first-paint value). Made `apply-filters`, `close-filters`, and `clear-filters` all close the modal and re-enter `apply_filters/1` — this is what settles the surface AND repopulates the about-to-reappear container's stream in the same round trip, mirroring the carousel-repopulation fix from 01.2-03 in the opposite direction (grid instead of carousels).
- Gave `FilterModal`'s primary CTA `min-w-40 tabular-nums` so its box stops resizing as the live "Ver N juegos" count changes on every keystroke/facet click, while the count itself keeps updating live.
- Added three new CSS rules (`.pk-active-filter-chip`, `.pk-active-filter-chip-x`, `.pk-clear-filters-link`) plus a header comment documenting the deliberate separation from `filter_modal.ex`'s own `chip_class/1` selection-chip contract — every colour resolves through a daisyUI theme variable, no new literal hex.
- Wrote 15 new tests across both test files covering chip labels/removal/clear-all, the negative "not the modal's own chip class" assertion, the settle-once behaviour (frozen while open, committed on close, repopulated with an actual card count not just a container), the explicit-submission and clear-filters repopulation mirrors, and the CTA's fixed-width/still-live-count contract — plus mutation-verified two of the plan's own acceptance criteria (see Deviations/Issues below).

## Decisions Made

- **Chip removal routes through existing literal-clause helpers, never a new dynamic-key path** (T-01.2-12-01's mitigation): mechanics/themes/weight_bands/tags chips dispatch `toggle-facet`, which maps through `facet_assign_key/1` (literal clauses, `nil` catch-all); players/max_playtime chips dispatch `toggle-scalar`, which maps through `scalar_assign_key/1` (same discipline). The query chip has no facet/scalar key at all — it dispatches the new parameterless `clear-query` handler instead, which reads nothing from the client.
- **`Etiqueta` as the editorial-tag chip's facet-name prefix** — a judgment call, since `FilterModal` itself has no rendered section for this facet to match against (cut deliberately in sketch 019 Round 3, per its own moduledoc). Not specified by the plan; flagged here for review if a different term is preferred later.
- **CTA min-width sized by character-count heuristic, not live measurement** — no browser/screenshot tool was available in this executor's environment. `"Ver 9999 juegos"` (16 chars — the plan's own stated 4-digit sizing ceiling, wider than the singular `"Ver 1 juego"`) at an assumed ~8px/character for this button's font, plus its own horizontal padding, comfortably fits inside Tailwind's `min-w-40` (10rem/160px). This should be spot-checked visually in the browser at some point; flagged as `D6` (human_judgment: true) in this SUMMARY's coverage block.
- **`clear-filters` now unconditionally sets `:filters_open` to `false`** before re-entering `apply_filters/1` — it's dispatched both from inside the modal's own footer (where the modal must now close) and from the zero-results empty-state banner (where it's already `false`, making the reassignment a no-op there).

## Deviations from Plan

### Process deviation (not a Rule 1-4 auto-fix)

**Tasks 1 and 2 were committed together, not as two separate commits.** The plan's own design couples them at the line level: Task 1's action explicitly rewrites the Resultados header block (the `:if` that gates it, plus its new interior chip-row markup), and Task 2's action changes that *same* `:if` expression from `browsing_results?(assigns)` to the new `:rendered_results` assign. There is no way to land Task 1's chip markup and Task 2's guard-predicate swap as two independently-revertible commits without hand-splitting a single template line's history — attempting it would have meant either (a) committing Task 1 with the OLD `browsing_results?(assigns)` guard and then re-diffing it away one commit later (extra churn, no real atomicity gained), or (b) fabricating an artificial intermediate test-file state to keep Task 1's own `<verify>` command isolated from Task 3's not-yet-written tests. Neither improves reviewability over one combined commit with a clear message. Recorded here per the "document any CLAUDE.md/process-driven adjustment as a deviation" instruction — no functionality was added or changed as a result; only the commit boundary.
