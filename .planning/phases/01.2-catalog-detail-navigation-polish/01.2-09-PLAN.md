<objective>
Close G-01.2-7. The member's verbatim rejection of the shipped backstop: "1-2 isn't acceptable.
This 'juegos similares' must to be fulled. Maybe this could be 'otras sugerencias' (otras opciones
que te van a encantar) or something like that."

There is no code defect here. `Catalog.similar_games/1` hard-filters to the viewed game's own
weight band with no widening path, which was a deliberate, documented design choice flagged in the
UI-SPEC as a backstop for a human to judge. The human judged it and rejected the premise: a sparse
shelf should never be an acceptable outcome. That is a product decision arriving through UAT, and
this plan implements it.

## The product decision this plan makes

The debug session left three fallback strategies open. This plan takes the first and records why,
so the choice is auditable rather than arbitrary:

- **Chosen — widen to adjacent bands by ordinal distance, ranked after true band-mates.** Weight
  band is this app's primary complexity-teaching facet; it is the axis three home-page carousel
  rows are built on and the reason D-06 made it the hard filter in the first place. Widening by
  *distance along that axis* keeps the teaching intact: a member looking at an expert game gets
  strategist games before beginner games. `Vocabulary.weight_band_level/1` already converts a band
  to its ordinal and is derived from `weight_bands/0`'s own order, so the distance metric cannot
  drift from the vocabulary.
- **Rejected — drop the band filter entirely and rank the whole catalog by overlap.** It throws
  away the complexity signal the entire product is built to teach, and would happily recommend a
  four-hour expert game underneath a gateway filler because they share a theme.
- **Rejected — rank by the continuous `bgg_weight` float instead of the band bucket.** Defensible,
  and it avoids the discrete-band cliff, but it replaces the app's own vocabulary with a raw
  BoardGameGeek number that appears nowhere else in the UI. If the band cliff ever proves to be the
  real problem, this is the change to make — noted here so it is not rediscovered.

**Floor:** fill to the shelf's existing cap of 12. "Must be fulled" has no smaller honest reading,
and with the current catalog of 434 games the cap is always reachable.

**Copy:** the user proposed the wording themselves and it is better than anything invented here. A
shelf that had to reach outside the band is titled "Otras sugerencias" and subtitled with their own
parenthetical. A shelf filled entirely from the band keeps the shipped title and its weight-band
subtitle, because in that case "similar" is still literally true.

**Scope note.** A game with no weight band currently returns an empty list and renders no shelf at
all — 26 games in the live catalog. That is the same "empty shelf" failure the member is objecting
to, reached by a different branch, and it is fixed by the same change: with no band to anchor to,
the shelf fills from overlap alone and is titled as other suggestions.

Purpose: the recommendation shelf is the detail page's only path back into the catalog, and a shelf
with two cards on it — or none — is a dead end.
Output: one widened query, one derived title, and tests that pin D-06's within-band order against
the change.

  <action>
    Replace the hard band filter with a single query whose ORDER BY expresses the whole preference
    ladder, keeping one LIMIT at the existing cap.

    The ladder, outermost key first:

    1. **Same band first.** A boolean expression that is true when the candidate's band equals the
       viewed game's band, sorted so true comes first. This is what preserves D-06: every genuine
       band-mate outranks every top-up, so the band block is unchanged as a set and unchanged in
       position.
    2. **Then band distance, ascending.** The absolute difference between the candidate's ordinal
       band position and the viewed game's, computed from the vocabulary's declared band order —
       reuse the existing `array_position` fragment shape. Candidates with no band sort last within
       this key rather than sorting as distance zero; decide the null handling explicitly in the SQL
       rather than relying on the default, and say which you chose in the SUMMARY.
    3. **Then the existing overlap score, descending.** Keep the shipped fragment exactly as it is —
       mechanics intersection weighted 2, themes weighted 1 — and keep it in `order_by` only. It
       still ranks and never filters.
    4. **Then name ascending, then id ascending**, as shipped, so the shelf is stable across reloads.

    Because keys 1 and 2 are constant across every same-band candidate, the order *within* the band
    block reduces to keys 3 and 4 — byte-identical to what D-06 shipped. Say this in the moduledoc;
    it is the property that makes this change safe and it is what Task 3 asserts.

    Handle the no-band case in the same function rather than in a separate branch that returns an
    empty list. When the viewed game has no band there is no band to match and no ordinal to measure
    distance from, so keys 1 and 2 collapse and the ladder reduces to overlap, name, id — which is a
    perfectly good recommendation and is exactly what the member asked for instead of an empty
    shelf. Keep the existing exclusion of the viewed game itself. Write the clauses so this falls
    out of the same query rather than duplicating it.

    Rewrite the moduledoc to describe what the function now does and, just as importantly, why the
    band is no longer a filter — cite G-01.2-7 and the decision recorded in this plan's objective,
    so the next reader does not "restore" the hard filter believing it was lost by accident.

    Note the cost characteristic in the moduledoc and in the SUMMARY: ordering by a computed
    expression over the whole table means Postgres sorts every row before applying the LIMIT. At the
    catalog's current scale of a few hundred games that is not worth optimising, but it is a real
    ceiling, and the honest place to record it is next to the query.
  </action>
