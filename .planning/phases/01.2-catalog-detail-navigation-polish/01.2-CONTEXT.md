<decisions>
## Implementation Decisions

### Catalog Index — Grid vs. Carousels
- **D-01:** The flat "El catálogo completo" grid (`index.ex:612-642`, currently always rendered
  below the 8 carousel rows regardless of filter state) is **removed from the default/unfiltered
  browse state**. Carousels alone are the browse surface. The grid becomes **exclusively the
  search/filter results view** — i.e. it only renders when `filters_active?/1` is true, matching
  the same condition that already hides carousels (`index.ex:578`). This continues the direction
  already established by quick task 260824-u5d, which removed the per-carousel "Ver todo" tile in
  favor of in-row infinite scroll (30-game ceiling) — this decision extends that same "carousels
  are the primary browse surface" logic to the page level.
  — **Reversibility:** reversible — the grid markup/query logic isn't deleted, just gated on
  `filters_active?/1` instead of always-rendered; trivial to un-gate.
- **D-02:** **No dedicated "browse everything unfiltered" entry point is added.** Modeled on
  Netflix's pattern (no flat "all titles" grid exists anywhere in that product — the closest is a
  row's "See All," scoped to that row's category, or search). A member who wants the full
  catalog opens the existing filter modal (nav search icon) and submits with nothing selected,
  which already produces the grid in its "El catálogo completo" heading state — no new UI required.
- **D-03:** Search/filter results grid switches from the current manual "Cargar más" button
  (`index.ex:646`) to **auto-loading infinite scroll** (IntersectionObserver-triggered `load-more`,
  no click required). Likely adaptable from the existing in-row carousel scroll-load hook shipped in
  quick task 260824-u5d (`.CarouselScroll`), applied to the vertical grid axis instead of horizontal.
  — **Reversibility:** reversible — swapping the trigger mechanism doesn't change `handle_event(
  "load-more", ...)`'s existing stream-append logic (`index.ex:319-331`).

### Detail Page — Reading Column
- **D-04:** Remove the two permanently-`No disponible` spec rows from "Ficha técnica"
  (`show.ex:400-407`: Ilustrador, Puesto en el ranking BGG) — this data doesn't exist anywhere in
  the seed/enrichment pipeline (confirmed: no illustrator or BGG-rank field on the `Game` schema or
  in `BggClient`), so these rows are dead weight on every single game, not a partial/missing-data
  case worth a placeholder.
- **D-05:** De-duplicate players/duration, currently shown twice: once in the compact
  `GamePreview.facts_row/1` near the title (`show.ex:335`, icon + link-to-filter), and again as
  plain `Jugadores`/`Duración` rows in "Ficha técnica" (`show.ex:376-383`). **Claude's discretion**
  on which representation stays — keep whichever reads better once Ilustrador/BGG-rank are removed
  and the spec list is shorter; the two remaining `pk-spec-row--wide` items (Diseñadores, Editorial)
  plus the BGG external link may end up carrying the section alone.

### Detail Page — "Juegos similares"
- **D-06:** `Catalog.similar_games/1` (`catalog.ex:168-178`) is upgraded from "same `weight_band`
  only, alphabetical order" to **weight band + shared mechanics/themes**, ranked so games with more
  tag overlap surface first. Exact scoring approach (e.g. count of shared `mechanic_labels`/
  `theme_labels`, or a simple weighted sum) is Claude's discretion during planning — the requirement
  is that overlap actually influences ranking, not just the weight-band filter.
  — **Reversibility:** reversible — changes one query function's body, no schema change (mechanics/
  themes are already `text[]` columns per PROJECT.md's durable architecture principle).

### Detail Page — Buy-box
- **D-07:** The buy-box (cover + gallery thumbnails + reserve CTA + share, `show.ex:284-332`) needs
  a **fuller redesign pass**, not a single targeted fix — the user flagged all three of visual
  prominence, its positioning/proportions relative to the reading column, and the mobile fixed CTA
  bar interaction as unsatisfying, without a specific fix in mind for any of them.
  **Claude's discretion, flagged for review:** reconsider prominence (is `btn-primary` alone enough
  visual weight for the page's one primary action?), column split/order (image-left-text-right vs.
  alternatives), and how the mobile `.pk-mobile-cta-bar`/title-echo hide-on-scroll/park-at-footer
  behavior (`show.ex:200-267`, `.DetailChrome` hook) reads in practice. Recommend routing this
  specific sub-area through `/gsd-ui-phase` rather than deciding blind in `/gsd-plan-phase` — it's a
  visual/interaction judgment call, not a mechanical fix like D-04/D-05/D-06.

### Cross-Page Navigation
- **D-08:** The detail page's breadcrumb (`show.ex:173-177`, currently hardcoded
  `<.link navigate={~p"/"}>Ludoteca</.link>`) must **carry forward whatever catalog filters were
  active when the member navigated to this game**, so returning via the breadcrumb lands back on
  the same filtered view — not always the bare unfiltered catalog. Root cause: `CatalogLive.Index`
  reads all filter state from URL query params via `handle_params/3`
  (`index.ex:93`), but the breadcrumb link never carries them.
  **Scope: filters only, not scroll position.** Scroll resets to the top of the catalog on return —
  acceptable, since detail→catalog is a full LiveView remount (different LiveViews) and the grid/
  carousel content order may differ from what was on screen before anyway. Do not build scroll-
  position persistence (sessionStorage or similar) for this phase.
  **Mechanism is Claude's discretion during planning** — e.g. a `?from=` param carrying the
  referring query string, or reading `assign(:params, params)` at mount and threading it through to
  the detail route's `patch`/`navigate` call. The existing chip/fact links on the detail page
  (weight band → `/?weight_bands=X`, mechanics/themes → `/?mechanics=X`/`/?themes=X`, players/
  duration → `/?players=X`/`/?max_playtime=X`) are intentionally NOT changed by this decision — they
  are deliberate forward-navigation to a *new* filtered view, a different concern from the
  breadcrumb's back-navigation.

### Claude's Discretion
- Exact players/duration de-duplication choice for the reading column (D-05).
- Exact similarity scoring formula for "Juegos similares" (D-06).
- Full buy-box redesign specifics (D-07) — flagged for `/gsd-ui-phase` rather than blind planning.
- Exact mechanism for carrying filter state through the breadcrumb link (D-08).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `.CarouselScroll` colocated hook (introduced in quick task 260824-u5d, referenced from
  `carousel_row.ex`/`index.ex`) — scroll-triggered in-row loading for carousels; D-03's grid
  infinite-scroll likely adapts this same IntersectionObserver approach to a vertical axis rather
  than inventing a new pattern.
- `GameChips.weight_band_badge/1`, `GameChips.chip_row/1`, `GameChips.editorial_tags/1` — already
  used both on cards and the detail page's reading column; D-06's mechanics/themes overlap scoring
  can read the same `mechanic_labels`/`theme_labels` assigns already computed for chip rendering.

### Established Patterns
- Filters are 100% URL-query-param-driven (`handle_params/3` in `index.ex`), never socket-only
  state — this is why D-08's breadcrumb fix is a query-string-forwarding problem, not a session/
  assign-passing problem.
- `filters_active?/1` is the single source of truth gating both carousel visibility and (per D-01)
  will now also gate grid visibility — one predicate, two consumers, matching the existing
  `index_rows/1` "one derived list feeds two surfaces" convention already used for the mega-menu/
  chip-nav pair.

### Integration Points
- D-01/D-03 changes are scoped to `catalog_live/index.ex`'s template + `load-more`/new scroll-hook
  wiring; no schema or context changes.
- D-04/D-05/D-07/D-08 are scoped to `catalog_live/show.ex`'s template + breadcrumb data threading;
  D-08 may need a new query param read in `show.ex`'s `handle_params/mount` to receive the referring
  filter state.
- D-06 is scoped to `lib/pukllay_club/catalog.ex`'s `similar_games/1` — pure query logic change, no
  LiveView changes needed beyond what already renders the shelf.
