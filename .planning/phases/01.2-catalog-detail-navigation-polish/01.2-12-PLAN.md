<objective>
Close G-01.2-4's three sub-defects. Defect A (the search box fighting itself) is fixed by plan
01.2-11 and is a dependency of this one. This plan fixes the other two, and gives the first one its
missing information surface.

**Defect B — no active-filters affordance.** `index.ex`'s Resultados header (lines 691-697) renders
a heading and a count and nothing else. The only existing proxy for "which filters are applied" is
the numeric `.pk-filter-badge` count on the filter trigger, which lives inside the collapsible
search region — and after 01.2-11 that region no longer force-opens itself when a filter is applied,
which is correct but leaves the member with no signal at all until this plan lands. Sketch 029
resolved what that signal looks like: **Inline with Heading**, with a deliberately lightened chip
treatment picked in Round 2 after Round 1's reuse of the filter modal's own solid-filled chip
outweighed the heading it sat beside.

**Defect C — the UI "jumps all the time".** `apply_filters/1` runs `stream(:games, games,
reset: true)` on every keystroke and every facet click, and `browsing_results?/1` flips the entire
page's structural layout (carousels vs grid, mega-menu and chip row present or absent) on the very
first typed character — all of it visible through the filter modal's own blur overlay. Plus the
modal's footer CTA carries a live match count in its label, so it resizes on every interaction and
drags the footer row with it: the "jumps the UI all the time on the 'Ver {x} games'" half of the
complaint, verbatim.

Purpose: a member filtering the catalog should be able to see what they filtered by, undo any of it,
and not watch the page rebuild itself underneath the modal while they work.
Output: a removable active-filters summary in sketch 029's winning treatment, a background surface
that settles once, and a footer CTA that stops resizing.
</objective>

  <action>
    **Separate the desired surface from the rendered surface.**

    `browsing_results?/1` stays exactly as it is — the pure predicate answering "which surface should
    the member be looking at right now", still wrapping `filters_active?/1` rather than restating it.
    Add a `:rendered_results` boolean assign holding the surface actually rendered, and switch every
    template `:if`, both slot guards, and `sync_carousel_visibility/1` over to reading that assign
    instead of calling the predicate. That single substitution is what stops the page restructuring
    under the modal: `sync_carousel_visibility/1` reasons about what is in the DOM, so it must read
    the same value the DOM was rendered from, or it will mark a container dirty that never left.

    Add one private function `settle_surface/1` that writes the predicate's current answer into that
    assign. Call it from `apply_filters/1`, but only when `@filters_open` is false. While the modal is
    open the assign is frozen, so the background stays exactly as the member left it no matter how
    many facets they click, and the blur overlay covers a static page instead of one rebuilding
    itself.

    **Settle on every path that closes the modal, and repopulate before rendering.**

    The three handlers that close the modal — the explicit-submission CTA (`apply-filters`), the X
    and backdrop close (`close-filters`), and `clear-filters` when dispatched from inside the modal —
    must all end by re-entering `apply_filters/1` *after* `:filters_open` is false. That is what
    settles the assign and, critically, what repopulates the grid stream with a reset in the same
    round trip the grid reappears in. Without it, a grid that was frozen out of the DOM while the
    member filtered comes back empty — the exact mirror of the carousel bug
    `sync_carousel_visibility/1` was written to fix, and the reason that comment must be read before
    this edit. `close-filters` does not call `apply_filters/1` today; it will now, and the extra query
    it costs is the same query every keystroke already ran.

    Verify the ordering explicitly: `settle_surface/1` must run before `sync_carousel_visibility/1`
    within the same call, so that whichever container is about to render has been repopulated.
