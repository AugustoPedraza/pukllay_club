<objective>
Close G-01.2-4's two remaining sub-defects. Its third, the search box refusing to reopen, is
plan 01.2-06's scope and shares its root cause with G-01.2-3.

**Defect B — no active-filters affordance.** The member's verbatim report: "Resultados shows
something but there aren't any affordance about which filters are been applied." The Resultados
header renders a heading and a result count and nothing else. The only element anywhere on the
page that reflects which filters are active is the numeric badge on the filter trigger — and that
trigger is nested inside the collapsible search region, so it is invisible whenever the search
pill is closed. There was never an active-filters summary; this is a missing feature, not a
regression.

**Defect C — the page restructures on every filter interaction.** The member's verbatim report:
"the filtering jumps the UI all the time on the 'Ver {x} games' and also the overladed grip at the
back." Two mechanisms, both confirmed by static trace. First, `apply_filters/1` runs a full
stream reset on every keystroke and every facet click, and `browsing_results?/1` flips the entire
page's structure — carousels out, grid in, mega-menu and chip row gone — on the very first
character typed. All of that churn happens behind the filter modal's blur overlay while the member
is still clicking facets inside it. Second, the modal's own primary CTA carries its live match
count in its label, so the button resizes on every interaction. No bespoke stacking or z-index
defect was found; this is live-render churn.

The fix for C is not to slow filtering down. It is to stop *committing* the structural swap while
the member is still filtering: the background surface settles once, when the modal closes. The
count in the footer keeps updating live, because that is the feedback the modal exists to give.

Purpose: a filtered result set the member cannot read the filters off is not a usable results view,
and a background that rebuilds under every click reads as the page fighting the member.
Output: a removable active-filters summary on the results surface, a background surface that
settles once, and a CTA that stops resizing.
</objective>

  <action>
    **Separate the desired surface from the rendered surface.**

    `browsing_results?/1` stays exactly as it is — the pure predicate answering "which surface
    should the member be looking at right now", still wrapping `filters_active?/1` rather than
    restating it. Add an assign that holds the surface actually rendered, and switch every template
    `:if` and `sync_carousel_visibility/1` over to reading that assign instead of calling the
    predicate. That single substitution is what stops the page restructuring under the modal:
    `sync_carousel_visibility/1` reasons about what is in the DOM, so it must read the same value
    the DOM was rendered from, or it will mark a container dirty that never left.

    Add one private function that writes the predicate's current answer into that assign — settling
    it. Call it from `apply_filters/1`, but only when the modal is closed. While the modal is open
    the assign is frozen, so the background stays exactly as the member left it no matter how many
    facets they click, and the blur overlay covers a static page instead of one rebuilding itself.

    **Settle on every path that closes the modal, and repopulate before rendering.**

    The three handlers that close the modal — the explicit-submission CTA, the X and backdrop
    close, and the clear action when it is dispatched from outside the modal — must all end by
    re-entering `apply_filters/1` after `filters_open` is false. That is what settles the assign and,
    critically, what repopulates the grid stream with a reset in the same round trip the grid
    reappears in. Without it, a grid that was frozen out of the DOM while the member filtered comes
    back empty — the exact mirror of the carousel bug `sync_carousel_visibility/1` was written to
    fix, and the reason that comment must be read before this edit. The close handler does not call
    `apply_filters/1` today; it will now, and the extra query it costs is the same query every
    keystroke already ran.

    Verify the ordering explicitly: the assign must be settled before the streams are synchronised
    within the same call, so that whichever container is about to render has been repopulated.

    **Stop the modal CTA resizing.**

    The footer's primary action carries a live match count in its label, so it resizes on every
    facet click and every keystroke, dragging the whole footer row with it — this is the "jumps the
    UI all the time on the 'Ver {x} games'" half of the complaint. Fix the geometry, not the
    liveness: keep the count updating on every interaction, and give the button a minimum width
    from Tailwind's named scale wide enough to seat the longest label the catalog can produce, plus
    tabular figures so the digits themselves stop shifting. Take the longest label from the
    catalog's real scale — the count ceiling is the full catalog size, and the singular and plural
    forms differ in length, so size for the wider of the two. Keep the explicit class list the
    footer's comment requires; do not switch either action to the variant attribute.
  </action>
