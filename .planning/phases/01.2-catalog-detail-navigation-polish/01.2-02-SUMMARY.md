# Phase 01.2 Plan 02: Rank Juegos Similares by Shared Mechanics/Themes Summary

**`Catalog.similar_games/1` now ranks same-weight-band candidates by a Postgres-computed set-intersection overlap score (mechanics weighted 2x, themes weighted 1x) instead of plain alphabetical order, with overlap ranking but never filtering.**

## Performance

- **Completed:** 2026-08-26T02:27:33Z
- **Tasks:** 2
- **Files modified:** 2

## Accomplishments
- Rewrote `similar_games/1`'s `order_by` to compute a weighted overlap score in a single `fragment/2` call: `(2 * cardinality(mechanics intersect)) + cardinality(themes intersect)`, descending, then `asc: g.name`, then `asc: g.id` for a deterministic tie-break — matching this module's existing "compute in the query, never post-process in Elixir" discipline (T-01-22).
- Confirmed via a genuine RED/GREEN cycle that the new tests actually exercise ranking logic and not incidental alphabetical agreement: candidate names were deliberately chosen so alphabetical order is the *opposite* of overlap-ranked order, and both differentiating tests failed against the old alphabetical-only implementation before the query rewrite, then passed after.
- Rewrote the function's `@doc` to record the D-06 rationale (weighting, overlap-ranks-never-filters, retained guards/cap) and remove the now-false sentence claiming the overlap axis "was rejected as a new query shape with no existing precedent."
- Added 8 new tests to the existing `similar_games/1` describe block covering: A/high-B/mid-C/zero ranking order with a different-band exclusion, name/id tie-break, empty-arrays-on-base safety, cap-cannot-truncate-best-matches, determinism across 3 repeated calls, and empty-arrays-on-a-band-mate safety — while leaving the 5 pre-existing tests byte-identical (only the describe string changed).
- Live-verified the SQL against real dev data (Brass: Birmingham, a 14-mechanic/6-theme game) — the 12 returned band-mates come back with shared-mechanics/shared-themes counts strictly non-increasing (6+2, 6+1, 6+1, 6+0, 5+1, ... down to 3+0), confirming the query behaves correctly outside the synthetic fixture data too.

## Decisions Made
- Mechanics weighted 2x, themes weighted 1x in the overlap score, per the plan's explicit rationale (mechanics describe how a game plays; themes are flavour) — CONTEXT.md D-06 left the exact formula to plan-time discretion, and the plan text specified this weighting directly, so no alternative was evaluated.
- Both weighted cardinalities are computed in a single `fragment/2` call (one multi-line SQL string, four pinned placeholders) rather than two separate `order_by` keys, keeping the whole score as one Postgres-side computation with one `ORDER BY` column — matching `apply_sort/2`'s existing single-expression `order_by` precedent for computed sort keys.
- Test candidate names were deliberately chosen to make alphabetical order the *opposite* of overlap-ranked order (e.g. "Zulu High Overlap" ranks first by overlap but last alphabetically; "Alfa Low 01".."Alfa Low 12" sort before "Zeta High 1".."Zeta High 3" alphabetically) — this is what let the RED phase genuinely fail against the old implementation instead of coincidentally passing because fixture names already matched the intended order.
