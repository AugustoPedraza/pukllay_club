<objective>
Close G-01.2-2 (blocker: "search is totally broken. I type and nothing happen"), G-01.2-3
("after the search, I can't open again the search"), and defect A of G-01.2-4 (same reopen
mechanism), and re-verify G-01.2-1 (href parity, which has no code defect and could not be
tested while search was unusable).

**Root cause, restated precisely.** `.pk-search-morph`'s `is-open` class is client-only state
living on a server-rendered element. `header_inner/1` renders that element with a literal
`class="pk-search-morph"` alongside a *dynamic* `data-search-expanded={to_string(@search_expanded)}`
attribute, so the element sits in a change-tracked part of the template. The moment any of its
dynamic inputs move — `@search_expanded` flipping on the first search character, the
`.pk-filter-badge` count appearing, or the `nav_menu` / `subnav` sibling slots disappearing when
`browsing_results?/1` flips — LiveView re-applies the server's attribute set and **strips
`is-open`**. `syncMorph()` in `updated()` then silently re-adds it, but never restores focus. So
the member types one character, the pill snaps shut and the caret is lost, and every subsequent
keystroke goes nowhere: "I type and nothing happen." The same strip/re-add cycle, plus
`onDocumentClick` treating every FilterModal control as an outside click (the modal renders as a
sibling far outside `.pk-search-morph`, while its only trigger is nested *inside* it), is the
"I can't open again the search" symptom.

The fix is not a patch on either mechanism. It is to stop splitting ownership of one piece of
state across two runtimes: the server renders whether the box is open, the hook only moves focus.
That deletes the whole class of desync — the strip, the one-way `syncMorph` reopen, and the
outside-click race — in one change.

Purpose: search is the catalog's primary action and it is currently unusable, which also blocked
three other UAT tests from being reproducible at all.
Output: server-owned search-morph state, a focus-only header hook, and tests that pin the
regression which caused this gap.
</objective>

  </read_first>

  <action>
    Rewrite the hook's search-morph block. After Task 1 the server owns the class, so the hook's
    only remaining job is focus, and its only remaining outputs are two pushed events.

    - Delete the three functions that mutated the open state and the row-dim modifier, and delete
      the document-level click listener entirely along with its registration and its teardown.
      Removing that listener is the deliberate fix for defect A: the filter modal's controls are
      never descendants of the search morph, so no correct outside-click test can exist without
      the header hook hardcoding knowledge of another page's DOM. The pill already has an
      always-visible 44px close control and an Escape binding, so click-outside was never its only
      dismissal path. Record this tradeoff in the block's comment.
    - Keep an Escape binding, but it now pushes the close event instead of mutating the DOM, and
      only when the box is currently open (read the data attribute, not a class).
    - The toggle and close buttons no longer need JS listeners at all — they carry `phx-click`
      after Task 1. Remove their listeners and their teardown lines.
    - Add focus handling driven by a transition, not by the current value: store the data
      attribute's value on mount, and in `updated()` compare the stored value against the current
      one. On a false-to-true transition, focus the input. On a true-to-false transition, return
      focus to the toggle. On no transition, do nothing — this is what stops the box from stealing
      focus on every unrelated round trip. Update the stored value each time.
    - Do NOT focus on mount. A page loaded with a query in the URL renders the box already open,
      and grabbing focus there would scroll the viewport and hijack the keyboard on arrival.

    Then make the hook's wiring failure-isolated, which closes the other candidate branch the
    G-01.2-2 debug session could not rule out (an uncaught exception in an earlier block silently
    aborting the rest of `mounted()` before the search controls are wired).

    - Move the search block so it wires first, ahead of the scroll listener, the scroll-spy
      observer, the height publisher, the drawer and the category menu.
    - Wrap each of those blocks in its own try/catch that reports the failure to the console and
      continues, so one throwing block can never prevent the others from wiring.
    - In `updated()`, guard the height-publisher call the same way its siblings are already
      guarded. Today it is the one unguarded call in that callback, so if the height block ever
      throws during mount, every subsequent server round trip throws too — which would look
      exactly like "the page stopped responding to anything."
    - Keep `destroyed()` in sync: remove teardown for every listener this task removed, add
      teardown for anything it adds.
  </action>
