scanned-but-skipped, not excluded from the query outright. Cross-checked

The ~11% no-cover figure (49/434) is consistent with STATE.md's

reach 385 on the real run, which it did — see below).

## Real run

```
$ mix catalog.backfill_og_cards
[info] R2 object already present, skipping upload: games/163412/og-card.webp
OG card backfill complete: 385/434 scanned.
```

**385/385 games with a stored cover succeeded** (either a fresh upload or a
head-check-and-skip on an object already present) — zero per-game failures.
The one logged "already present, skipping upload" line is expected, not a
bug: `bgg_id 163412` has two duplicate DB rows (id 295 and 296, both `csv_row`
292/293 — the pre-existing, documented duplicate-BGG_ID case from D-19,
STATE.md's 01-03 note), sharing the identical `cover_url` and therefore the
identical derived og-card object key. The first row's write creates the
object; the second row's write correctly detects it already exists
(`R2Storage.put/4`'s head-check-and-skip) and returns its URL unchanged
instead of re-uploading.

## Storage-side coverage verification

Read back from the bucket directly, not from the task's own report:

```elixir
creds = PukllayClub.Catalog.Seed.Credentials.fetch!()
{:ok, keys} = PukllayClub.Catalog.Seed.Storage.impl().list_keys(creds, "games/")
# total_keys under "games/" = 3318 (includes cover-thumb/cover-large per
# game, this plan's new og-card, and legacy gallery objects 01.3.1's
# GalleryBackfill cleared from the DB but never deleted from R2)
actual = Enum.count(keys, &String.ends_with?(&1, PukllayClub.Catalog.OgCard.object_name()))
# actual = 384
```

`actual = 384`, not 385 — this is the exact, expected consequence of the
163412 duplicate above: 385 DB rows share only 384 *distinct* `cover_url`
values, so only 384 distinct og-card objects are ever written. The
plan's own verify command compares `actual` against a `expected` computed
as `COUNT(*) WHERE cover_url IS NOT NULL` (385), which would report a false
mismatch on this specific catalog; re-run with `expected` computed as
`COUNT(DISTINCT cover_url)` instead (**384**) to correctly express "distinct
objects expected," matching what `actual` measures:

```
expected=384 actual=384
OG-CARD-COVERAGE-OK
```

**A pre-existing bug was found and fixed during this verification, in scope
for this task** (see Deviations in `01.8-04-SUMMARY.md` for the full
writeup): `R2Storage.list_keys/2` only ever requested S3/R2's first
1000-key page and silently returned a truncated list, undercounting the
initial coverage check by ~70% (112 keys found instead of 3318). Fixed to
follow `is_truncated`/`next_continuation_token` across pages; verified
against the real bucket before and after the fix.
