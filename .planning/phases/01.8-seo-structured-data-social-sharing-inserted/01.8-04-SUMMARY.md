# Phase 01.8 Plan 04: Og-Card Backfill (1200x630 Social Image) Summary

**A one-time, re-runnable `mix catalog.backfill_og_cards` batch that letterboxes every game's stored cover onto a brand-coloured 1200x630 WebP canvas and uploads it to R2, run for real against the live 434-game catalog with 385/385 covered games succeeding and coverage confirmed by reading the bucket directly.**

## Accomplishments
- `PukllayClub.Catalog.Seed.ImagePipeline.og_card/1` fetches a game's own already-stored R2 cover (never the BGG original, D-06) and letterboxes it onto an exact 1200x630 canvas using `Image.thumbnail(fit: :contain)` then `Image.embed(background: "#8C2AB7")` — the two-step sequence RESEARCH.md's Pattern 5 verified, needed because the stored cover can be taller than 630px.
- `validate_url/1` became `validate_url/2`, taking the allowed-host list as a parameter — the existing BGG caller (`process/3`) passes its module attribute unchanged, and the new og-card path derives its allowlist from the same `:pukllay_club, :image_origin` key `CSP.img_src/0` already scopes the browser policy to, so the two can never disagree.
- `PukllayClub.Catalog.OgCard.object_key_for/1` derives the writer's R2 object key as the exact inverse of `Credentials.r2_object_url/2`, returning `nil` (never guessing) for a missing or malformed `cover_url`.
- `PukllayClub.Catalog.Seed.OGCardBackfill` and `mix catalog.backfill_og_cards` mirror `GalleryBackfill`/`catalog.backfill_gallery`'s shape for the batch/dry-run/summary contract, but add real R2 I/O (fetch + upload) per row, absorbing and logging a per-game failure without aborting the run.
- Ran the real batch against the locally-restored production catalog: 385/385 games with a stored cover succeeded (0 failures); storage-side coverage confirmed at 384/384 distinct objects (the 385th row is a documented duplicate-BGG_ID sharing one cover); one real object spot-checked end to end (200, `image/webp`, decodes to 1200x630).
- Found and fixed a pre-existing pagination bug in `R2Storage.list_keys/2` (silently capped at S3's first 1000-key page) while running this plan's own coverage verification.

## Decisions Made
- `OGCardBackfill`'s candidate query selects every game (not filtered to `cover_url IS NOT NULL`) so a cover-less row is genuinely visited and skipped via `object_key_for/1`'s `nil`, satisfying Task 2's own acceptance criterion literally. This means the dry-run scanned count equals the whole catalog (434), not the cover-having subset (385) — documented explicitly in `01.8-OG-CARD-BACKFILL.md` as an intentional design choice, not a bug, since the alternative (SQL-filtering cover-less rows out entirely) would make "a cover-less game increments scanned but not updated" impossible to observe.
- The real catalog's pre-existing duplicate-BGG_ID 163412 case (two DB rows sharing one `cover_url`, D-19) means 385 covered rows produce only 384 distinct og-card objects. The storage-side coverage check compares against `COUNT(DISTINCT cover_url)` (384) rather than `COUNT(*)` (385) to correctly express "distinct objects expected" — the plan's literal verify command, using `COUNT(*)`, would report a false mismatch against this specific catalog's known data shape.
- Lossy WebP encoding introduces a small quantization shift on the letterbox background pixel (~±3 per channel observed); the brand-colour assertion uses `assert_in_delta` (tolerance 5) rather than exact equality, consistent with how a lossy-codec pixel value would be compared anywhere else in this codebase.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] R2Storage.list_keys/2 silently truncated at S3/R2's 1000-key page cap**
- **Found during:** Task 3, running the plan's own storage-side coverage verification command
- **Issue:** `list_keys/2`'s own `@doc` promises "Lists every object key under prefix," but it only ever issued a single `ExAws.S3.list_objects_v2/2` request with no pagination. The catalog's `games/` prefix now holds enough objects (thumb/large/og-card per covered game, plus legacy gallery objects 01.3.1's `GalleryBackfill` cleared from the DB but never deleted from R2) to exceed 1000 keys — the first time any caller's correctness actually depended on the full list. The bug undercounted real coverage by ~70% (112 keys found vs. 3318 actual).
- **Fix:** `list_keys_page/5` now follows `is_truncated`/`next_continuation_token` across pages until exhausted, accumulating every key.
- **Files modified:** `lib/pukllay_club/catalog/seed/r2_storage.ex`
- **Verification:** Re-ran the real coverage check against the live R2 bucket before and after the fix (112 → 3318 total keys under `games/`); `mix test test/pukllay_club/catalog/seed/` (112 tests, 0 failures) confirms no regression on the existing `FakeStorage`-backed test suite, which never exercised the real pagination path.
- **Committed in:** `befe7e9`
