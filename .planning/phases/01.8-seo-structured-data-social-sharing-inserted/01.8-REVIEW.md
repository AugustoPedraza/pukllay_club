## Summary

This is an incremental review scoped to the gap-closure window since commit `0e22977`: plan
01.8-06 (rebuilding `PukllayClubWeb.SEOTags.seo_tags/1` as a plain-Elixir, escaping-safe markup
builder to eliminate LiveView's `phx-r` root-tag attribute injection — the confirmed root cause of
G-01.8-3), plan 01.8-07's production verification tooling
(`test/production/og_tags_whatsapp_ua.mjs`), a small `game_text.ex` nil-safety fix carried over
from an earlier plan, and two documentation-only files (`.claude/CLAUDE.md`, `AGENTS.md`).

The core fix is sound: dropping the HEEx `~H` template in favor of building tags directly through
`Phoenix.HTML.attributes_escape/1` correctly takes the tag engine (and its `phx-r` root-tag
stamping) out of the rendering path entirely, and the new/tightened tests (`seo_tags_test.exs`,
the strict-form regression test added to `game_seo_test.exs`, the anchored regexes in
`structured_data_test.exs`) verify the identifying attribute is now always first, with nothing
interposed. Escaping of hostile input (quotes, `&`, `<`, `>`) was verified directly with
`Phoenix.HTML.attributes_escape/1` and behaves correctly.

Two things are worth fixing before calling this gap fully closed: (1) the new markup builder
inherits — and now that it's the single, explicit escaping seam for this head block, should own —
an edge case where a `nil` dynamic value silently drops the whole attribute rather than degrading
to a well-formed (if empty) tag, and this exact failure mode has zero test coverage even though
it's the same *class* of defect (a malformed tag a strict crawler can't parse) this whole phase
exists to prevent; and (2) the new WhatsApp verification script crashes on the first unreachable
URL instead of reporting a clean FAIL and continuing, undermining its stated purpose as "the one
gate in this repo that can catch this class of defect."

## Warnings

### WR-01: `seo_tags/1` silently drops an attribute entirely when its value is `nil`, with no test coverage for that path

**File:** `lib/pukllay_club_web/components/seo_tags.ex:54-70`

**Issue:** Every dynamic tag is built as `meta([{"key", "attr-name"}, {"content", seo.description}])`
(and similarly for `title`, `canonical_url`, `image_url`), piped through
`Phoenix.HTML.attributes_escape/1`. That function's `build_attrs/1` has an explicit clause —
`defp build_attrs([{_, nil} | t]), do: build_attrs(t)` — that drops any attribute pair whose value
is `nil`, regardless of key. Verified directly:

```
iex> Phoenix.HTML.attributes_escape([{"name", "description"}, {"content", nil}])
{:safe, [" name=\"description\""]}
```

If any of `seo.description` / `seo.canonical_url` / `seo.title` / `seo.image_url` is ever `nil`,
the emitted tag degrades to e.g. `<meta name="description">` — a well-formed-looking but
content-less tag, not an omitted tag and not an error. This is exactly the same *category* of
defect this whole phase exists to eliminate (a head-block tag a strict crawler can't correctly
read), just via a different mechanism than the `phx-r` bug that prompted the rewrite.

Today this is latent, not exercised: `SEO.site_default/1`'s four fields are all literals/derived
strings that are never `nil`, and `SEO.for_game/2`'s `description`/`canonical_url`/`image_url` are
all built by functions with non-`nil` fallbacks. But `title: game.name` has no such guarantee —
`Game.name` is only enforced non-`nil` by `Ecto.Changeset.validate_required/2`, which a raw write
outside the seed changeset (e.g. `Repo.insert_all`) bypasses. This codebase's own
`lib/pukllay_club_web/game_text.ex` moduledoc already documents this exact bypass scenario as real
for `publishers` ("a row written outside the seed changeset's `validate_required/2` — e.g. a raw
`Repo.insert_all` backfill — can legally carry a null array"); the same risk applies to `name`.
Neither `seo_tags_test.exs` nor `game_seo_test.exs` has a test that passes a `nil` value for any
individual field (only the whole-payload-`nil` case is tested).

**Fix:** Guard against `nil` in the values handed to `attributes_escape/1` so a missing value
degrades predictably (empty string) rather than silently vanishing the attribute, and add a test
asserting the tag still carries a `content=""`/`href=""` attribute when a field is `nil`:

```elixir
defp meta(attrs), do: tag("meta", normalize(attrs))
defp link(attrs), do: tag("link", normalize(attrs))

defp normalize(attrs), do: Enum.map(attrs, fn {k, v} -> {k, v || ""} end)
```

### WR-02: `og_tags_whatsapp_ua.mjs` crashes on the first unreachable URL instead of reporting FAIL and continuing

**File:** `test/production/og_tags_whatsapp_ua.mjs:121-140` (`checkUrl`), `142-168` (`runUrls`)

**Issue:** `checkUrl` only handles a non-2xx HTTP response (`if (!res.ok)`); it does not wrap the
`await fetch(url, ...)` call itself in a `try/catch`. A DNS failure, connection refused, TLS
error, or malformed URL passed as an argument throws inside `fetch`, and since `runUrls`'s
`for (const url of urls) { const { lines, failures } = await checkUrl(url) ... }` loop has no
error handling either, that exception propagates out of `runUrls` uncaught, crashing the whole
process with a raw stack trace. Given the script's own documented usage
(`node test/production/og_tags_whatsapp_ua.mjs <url> [<url> ...]`), a single bad/unreachable URL
among several aborts the entire run — no PASS/FAIL summary is printed, and the remaining URLs are
never checked at all. AGENTS.md's "Social/Crawler Head-Block Changes" section requires running
this script against the deployed host after every head-block change and treats it as the one gate
that can catch this class of defect; a crash on one bad URL silently defeats that guarantee for
every other URL in the same invocation.

**Fix:** Catch fetch-level failures per URL and report them the same way an HTTP error is
reported:

```javascript
async function checkUrl(url) {
  let res
  try {
    res = await fetch(url, { headers: { "User-Agent": WHATSAPP_USER_AGENT } })
  } catch (err) {
    return {
      url,
      lines: [`\n${url}`, `  FAIL  request error — ${err.message}`],
      failures: [{ key: "(fetch)" }],
    }
  }

  if (!res.ok) {
    return {
      url,
      lines: [`\n${url}`, `  FAIL  HTTP ${res.status} — could not fetch page`],
      failures: [{ key: "(fetch)" }],
    }
  }
  // ...
}
```

## Info

### IN-01: `seo_tags/1`'s `%{} = seo` clause accepts any map and does not validate required keys

**File:** `lib/pukllay_club_web/components/seo_tags.ex:54`

**Issue:** `def seo_tags(%{} = seo)` matches *any* map (per Elixir's own semantics — `%{}` is not an
empty-map guard), not specifically one carrying `:description`/`:canonical_url`/`:title`/
`:image_url`. If a future caller ever assigns `conn.assigns[:seo]` to a map missing one of those
keys, this function raises `KeyError` at render time (a 500) rather than failing in a way that
points at the actual contract violation. Currently unreachable — the only two producers
(`SEO.for_game/2`, `SEO.site_default/1`) always populate all four keys — so this is an
observability/robustness note, not a live bug.

**Fix:** Optional: destructure explicitly in the function head (
`def seo_tags(%{description: _, canonical_url: _, title: _, image_url: _} = seo)`) so a
missing-key caller gets a `FunctionClauseError` naming the mismatch instead of a `KeyError` deep
inside tag-building, or add a `@spec`-level typed struct for `seo` if this payload shape grows
further call sites.
