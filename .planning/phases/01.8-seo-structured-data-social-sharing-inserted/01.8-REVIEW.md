# Phase 01.8: Code Review Report

**Reviewed:** 2026-09-12T00:00:00Z
**Depth:** standard
**Files Reviewed:** 34
**Status:** issues_found

## Summary

This phase adds per-game/site-wide SEO (meta tags, JSON-LD, sitemap, robots.txt), a per-request CSP
nonce, and an offline `og-card.webp` letterboxing/backfill pipeline. The security-sensitive surfaces
— the og-card SSRF host allowlist, the 15 MB download cap, the JSON-LD `</script>`-breakout escaping,
and the CSP nonce plumbing — are all correctly implemented and are backed by explicit adversarial
tests (evil-host rejection, oversized-download rejection, script-injection-in-name round-trip). No
SQL/command injection, hardcoded secrets, or unsafe eval/deserialization were found.

The issues below are all correctness/robustness gaps rather than exploitable vulnerabilities: a
missing pattern-match clause that can crash game-card rendering on a legally-nullable DB column, a
dry-run mode that can never report what it would actually change, an unguarded precondition on the
backfill's credentials argument, a JSON-LD `image` field that reuses a social-card asset it probably
shouldn't, and an unaddressed (undocumented, untested) staleness of `<head>` SEO tags across
client-side LiveView navigation. None are blockers; all are worth fixing or explicitly accepting
before this ships.

## Warnings

### WR-01: `GameText.editorial_text/1` has no clause for `publishers: nil`, but the DB column allows NULL

**File:** `lib/pukllay_club_web/game_text.ex:52-56`
**Issue:** The function only special-cases the schema-default empty list:

```elixir
def editorial_text(%Game{publishers: []}), do: nil

def editorial_text(%Game{publishers: publishers}) do
  "editado por #{Enum.join(publishers, ", ")}"
end
```

The moduledoc argues this is safe because `publishers` is `{:array, :string}, default: []`. That
default only applies when a value is *omitted* from a changeset's `attrs` — it is not a NOT NULL
constraint. `priv/repo/migrations/20260806234228_create_games.exs:34` declares
`add :publishers, {:array, :string}, default: []` with no `null: false`, so the column can legally
hold SQL `NULL`. If any current or future write path (a manual `UPDATE`, an admin edit added in a
later phase, a raw SQL fixup) ever persists `NULL` for a game's `publishers`, this second clause
still matches (it's an unguarded catch-all), and `Enum.join(nil, ", ")` raises
`Protocol.UndefinedError` — crashing `GameCard`/`GamePreview` rendering (and therefore the whole
catalog/detail page) for that game. The two call sites (`game_card.ex`, `game_preview.ex`) have no
fallback for a raised exception.

**Fix:**
```elixir
def editorial_text(%Game{publishers: nil}), do: nil
def editorial_text(%Game{publishers: []}), do: nil

def editorial_text(%Game{publishers: publishers}) do
  "editado por #{Enum.join(publishers, ", ")}"
end
```
(Optionally also add `null: false` to the `publishers`/other array columns in a follow-up migration
so the DB itself rules this out, matching the "never a blind interpolation" intent already stated in
the moduledoc.)

### WR-02: `OGCardBackfill.run(dry_run: true)` always reports `updated: 0`, making the dry run uninformative

**File:** `lib/pukllay_club/catalog/seed/og_card_backfill.ex:80-98`
**Issue:**
```elixir
defp apply_backfill(game, dry_run?, credentials, acc) do
  case OgCard.object_key_for(game) do
    nil -> %{acc | scanned: acc.scanned + 1}
    _key when dry_run? -> %{acc | scanned: acc.scanned + 1}
    key -> ...
  end
end
```
The `_key when dry_run?` branch discards the fact that this game *does* have a derivable key — it
increments only `scanned`, never `updated`. So `mix catalog.backfill_og_cards --dry-run` always
prints `"[DRY RUN] OG card backfill complete: 0/N scanned."` regardless of how many of those N games
would actually receive a new og-card. Both the task's own `@moduledoc` ("`--dry-run` scans and
reports without fetching...") and the module's `@doc` ("Returns a summary map with `:scanned` and
`:updated`") imply the dry run should reveal how much work a real run would do; today it cannot,
because `updated` is definitionally always `0` in that mode. An operator has no way to preview impact
before running the real (network-I/O, non-idempotent-on-content-change) backfill.

**Fix:** Track "would update" separately from "updated", e.g. rename the accumulator key for
dry-run (`would_update`) or count eligible-key games into `updated` during dry-run since no upload
actually happens either way:
```elixir
_key when dry_run? -> %{acc | scanned: acc.scanned + 1, updated: acc.updated + 1}
```
and adjust `og_card_backfill_test.exs`'s `"dry_run: true reports the same scanned count..."` test's
`updated: 0` assertion accordingly (or add a distinct field if `scanned`/`updated` must keep their
current dry-run-is-always-0 meaning for another consumer).

### WR-03: `OGCardBackfill.generate_and_upload/3` crashes with an unhelpful `FunctionClauseError` when called without credentials

**File:** `lib/pukllay_club/catalog/seed/og_card_backfill.ex:69-104`
**Issue:** `run/1`'s `@doc` states `:credentials` is "required unless `:dry_run` is `true`," but
nothing enforces this up front. `credentials = Keyword.get(opts, :credentials)` can be `nil`, and if
`dry_run?` is `false`, `apply_backfill/4` falls through to
`generate_and_upload(game, key, credentials)`, whose head pattern-matches
`%Credentials{} = credentials`. Passing `nil` here raises `FunctionClauseError` — deep inside the
`Enum.reduce/3` loop, on the *first* eligible game, with a stack trace that doesn't communicate the
actual precondition violation. The Mix task (`catalog.backfill_og_cards.ex`) always supplies real
credentials via `Credentials.fetch!()` when not in dry-run mode, so this isn't reachable through the
CLI today — but `OGCardBackfill.run/1` is a public function with no other caller-side guard, so any
future caller (a scheduled job, an IEx invocation, a test) that omits `:credentials` while also
passing `dry_run: false` gets a confusing crash instead of a clear error.

**Fix:** Validate the precondition once, before the loop:
```elixir
def run(opts \\ []) do
  dry_run? = Keyword.get(opts, :dry_run, false)
  credentials = Keyword.get(opts, :credentials)

  if not dry_run? and not match?(%Credentials{}, credentials) do
    raise ArgumentError, "OGCardBackfill.run/1 requires :credentials unless :dry_run is true"
  end

  ...
end
```

### WR-04: `Game` JSON-LD's `image` reuses the letterboxed social-card asset instead of the actual cover art

**File:** `lib/pukllay_club_web/seo.ex:270`
**Issue:**
```elixir
defp image_for(game), do: OgCard.url_for(game) || game.cover_url
```
This same helper feeds the `Game` structured-data payload's `"image"` key (`game_json_ld/1`). The
og-card asset it prefers is a 1200x630 canvas with the game's cover *letterboxed and padded with
solid brand-purple bars* (`ImagePipeline.og_card/1`, D-07/D-08) — purpose-built for the fixed-aspect
Open Graph/Twitter preview surface, not as a general-purpose representation of the game. Search
engines that render `Game.image` in a rich result (or an image-search crawl) will show the padded
canvas — with visible purple bars — instead of the real box art `game.cover_url` already provides at
full resolution with no padding. `og:image`/`twitter:image` legitimately want the padded canvas
(fixed 1200x630 aspect is required there); the JSON-LD `image` field does not have that constraint
and should represent the entity itself.

**Fix:** Prefer the real cover for structured data, keep the padded og-card only for the social meta
tags:
```elixir
defp image_for(%Game{cover_url: cover_url}) when is_binary(cover_url), do: cover_url
defp image_for(game), do: OgCard.url_for(game)
```
(or simply `game.cover_url || OgCard.url_for(game)`), and update the "omits `image`... when their
source values are absent" `@doc` note and `game_seo_test.exs`'s nil-cover assertions accordingly.

### WR-05: Per-page `<head>` SEO tags go stale after client-side LiveView navigation between routes

**File:** `lib/pukllay_club_web/router.ex:37-49`, `lib/pukllay_club_web/components/layouts/root.html.heex:6-17`
**Issue:** None of `CatalogLive.Index`, `AboutLive`, or `CatalogLive.Show` are wrapped in an explicit
`live_session` block. Per `Phoenix.LiveView.Router.__live__/4`, every `live/3` route not inside an
explicit `live_session` implicitly gets the *same* `%{name: :default, extra: %{}}` session. Because
all three routes therefore share one live session, `<.link navigate={...}>` transitions between them
(used throughout `GameCard`/`GamePreview` to go from the catalog grid to a game's detail page) are
handled entirely over the existing WebSocket connection — the root layout (and everything this phase
adds to it: `<meta name="description">`, `<link rel="canonical">`, the OG/Twitter tags, and the
per-game `Game` JSON-LD block) is rendered once on the very first HTTP request and is **not**
re-rendered on subsequent client-side navigations. Only `<.live_title>` (Phoenix's own dedicated
mechanism) updates the visible tab title on navigate; everything this phase built in `SEOTags`/
`SEO.json_ld_tag/2` does not.

Concretely: a visitor who loads `/` (site-default SEO/JSON-LD baked in) and then clicks a game card
via `navigate` ends up on `/juegos/:id` (URL bar and `<title>` correctly update) while
`document.querySelector('meta[property="og:title"]')`, the canonical `<link>`, and the JSON-LD script
still describe the catalog index, not the game. This doesn't break the two documented crawler-facing
requirements (social-platform unfurlers and most SEO crawlers always issue a fresh, disconnected
`GET` per URL, which correctly triggers `GameSEO`/`SiteSEO`), but it is an unaddressed, untested gap:
nothing in this phase's test suite exercises a `navigate`-driven transition and asserts on the
resulting `<head>` content, and the moduledocs only ever discuss the disconnected-crawler case
(Pitfall 1), not this connected-but-navigated case.

**Fix:** At minimum, document this as an accepted limitation (crawlers only, not live in-app
navigation) so a future maintainer doesn't assume `<meta>`/JSON-LD are live-reactive. If tag freshness
during in-app browsing matters (e.g. a future "share this page" button reads `document` meta tags,
or Google's rendering pass ever follows client-side transitions), address it with either: (a) wrapping
`/juegos/:id` in its own `live_session` so `navigate` there triggers a full page load, or (b) pushing
head updates via a JS hook keyed off `handle_params`/assign changes (mirroring how `<.live_title>`
itself updates `document.title`).
