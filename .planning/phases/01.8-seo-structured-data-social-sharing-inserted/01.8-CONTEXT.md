<domain>
## Phase Boundary

A game link dropped into WhatsApp/Facebook/Twitter renders an appealing, on-brand preview card,
and Google can discover, crawl, and understand every game page in the catalog. Covers: per-game
meta descriptions, real `alt` text, `robots.txt` + live `sitemap.xml`, JSON-LD (`Game` per detail
page, `LocalBusiness` site-wide), Open Graph + Twitter Card tags, and the CSP nonce refactor
(SEC-05) needed for the JSON-LD blocks to render at all under this app's existing strict
`script-src 'self'`. Requirements: SEO-01..06, SHARE-01..05, SEC-05.

**Out of scope (unaffected by this discussion):** Natural-language search/auth (Phase 2), rules
Q&A/RAG (Phase 3), admin/rental tracking (Phase 4), Google Business Profile setup (out-of-band,
not a codebase change), ongoing CI secret-scanning, server-side per-game OG-image compositing as a
*runtime* concern (a one-time batch backfill is in scope — see D-08/D-09 below; a live
compositing *pipeline* is not).

<decisions>
## Implementation Decisions

### Club NAP for LocalBusiness (SEO-06)
- **D-01:** LocalBusiness `address` uses the real street address of the Maps-pinned meeting venue
  ("Club de Emprendedores de Jujuy"): **Avenida España 1500, Y4600 San Salvador de Jujuy, Provincia
  de Jujuy, Argentina**. This is the club's actual current meeting location, confirmed by the user
  — not a placeholder.
- **D-02:** Add a new, documented `ClubLinks.public_phone/0` accessor holding the same digits as
  `RESERVATION_WHATSAPP_NUMBER` (the club's WhatsApp business number), as a literal — do NOT have
  LocalBusiness JSON-LD resolve `telephone` through the `RESERVATION_WHATSAPP_NUMBER` env var
  directly. — **Reversibility:** reversible — a documentation/accessor-naming choice, not a data
  migration; the underlying phone number is the same either way.
  - **Rationale:** `lib/pukllay_club_web/club_links.ex`'s moduledoc currently states
    `RESERVATION_WHATSAPP_NUMBER` is "operational config, not public marketing copy" and "must
    never be resolved through this module." The user explicitly chose to preserve that contract
    (rather than weaken/remove it) by adding a second, public-facing accessor with the same digits
    as a plain literal. The plan/executor must update `club_links.ex`'s moduledoc to document
    `public_phone/0` alongside the existing entries, following the same pattern as
    `whatsapp_group_url/0`/`instagram_url/0`/etc.
  - **Resolving the literal value:** the actual phone number is the value currently configured for
    `RESERVATION_WHATSAPP_NUMBER` in this app's runtime env/Kamal secrets — the executor should
    read it from there rather than ask the user to retype it mid-plan.
- **D-03:** `openingHoursSpecification`: **Sábados 5pm (Saturdays, 17:00)** — the only recurring
  schedule to encode for now. Don't invent additional days/hours beyond this.

### Brand fallback OG image (SHARE-04)
- **D-04:** Ship a new combined 1200×630 asset (isologo + "Pukllay Club" wordmark on a brand-color
  background) as the OG fallback for hero-less pages (catalog index, About) — not a bare
  `isologo-light.png`/`isologo-dark.png` used directly. Rationale: social crawlers can't detect
  viewer theme, so the fallback must be one deliberately-composed asset rather than a logo mark
  floating on transparency.
- **D-05:** Route this asset's design through `/gsd-sketch` **before or alongside** Phase 01.8
  execution — matches this project's established brand-visual workflow (isologo scroll-morph,
  About page photography/Maps embed all went through sketch rounds first). Do not have the
  executor improvise a static composite ad hoc. — **Reversibility:** reversible — swapping the
  final static image file later costs nothing structurally.
  - **Planning implication:** this phase's plan should either (a) treat the sketch as a prerequisite
    task sequenced before the OG-fallback plan, or (b) flag it as a dependency on a
    not-yet-completed sketch round if planning happens before the sketch does. Do not block the
    rest of Phase 01.8 on it — it's isolated to the hero-less-page fallback path.

### og:image aspect ratio for game covers (SHARE-03)
- **D-06:** Pad the existing `cover-large.webp` (near-square, letterboxed board-game box art from
  Phase 01.3.1's `ImagePipeline`) onto a 1200×630 canvas with a brand-color background — letterbox,
  not crop. Rejected alternatives: cropping tighter (loses box-art detail/title text — board game
  covers aren't shot in landscape) and shipping the near-square image as-is (platforms would
  crop/letterbox unpredictably, inconsistent across WhatsApp/Facebook/Twitter).
- **D-07:** Letterbox background color reuses the site's existing primary brand color
  (`--color-primary` / `--pk-ramp-600` in `assets/css/app.css`) — not a new color choice. Resolve
  the concrete hex value from that CSS variable at plan/execution time, not from a fresh design
  decision.
- **D-08:** Generate this as a new `og-card.webp` variant via a **one-time batch backfill** (new
  mix task, mirrors Phase 01.3.1's `GalleryBackfill` pattern) — storing per-game to R2 alongside
  `cover-thumb.webp`/`cover-large.webp` — **not** live per-request generation. — **Reversibility:**
  one-way-ish for the batch itself (re-running it is cheap and idempotent, matching the existing
  `GalleryBackfill`/seed conventions) but the architectural choice (batch vs. live) is the thing
  that's costly to reverse later: switching to live generation after ship means adding new
  request-path image-processing code and a caching story from scratch.
  - **Rationale:** REQUIREMENTS.md's "Out of Scope" table already excludes "server-side composited
    OG images (cover art + brand overlay)" as a *runtime/per-request* concern for v1.1 — this
    one-time backfill is compatible with that exclusion since it runs once, offline, like every
    other seed-pipeline backfill in this codebase (BGG re-enrichment, gallery backfill,
    description translation), not on the request hot path.

### Meta description & alt text content (SEO-01, SEO-02)
- **D-09:** Per-game meta description template emphasizes **name + weight/mechanics + a "in
  Jujuy"/local hook** (e.g. "Descubrí [Juego], un juego de [mecanismo] para [peso/complejidad] en
  Pukllay Club, Jujuy."). Reuses the same complexity-teaching vocabulary (weight bands,
  plain-language mechanic chips) already established on the detail page — consistent voice, doubles
  as a local-SEO signal. Rejected: reusing the existing Spanish game description verbatim
  (truncated) — less SEO-optimized, risks cutting off mid-sentence.
- **D-10:** Catalog card / hover-preview image alt text template: **game name + editorial** (e.g.
  "Portada de [Juego], editado por [Editorial]") — matches what a sighted user already gets from the
  card (title + publisher badge). Not name-only.
- **D-11:** New SEO copy (meta descriptions) uses the same **Rioplatense/Argentine voseo** already
  established across Phase 01.3's translated game descriptions and the About page — consistent
  site-wide voice, per this project's standing Spanish-locale preference (Argentina, not generic
  Latin American Spanish).

### Claude's Discretion
- Exact wording/templating logic for the meta-description and alt-text generators (D-09/D-10) — the
  content emphasis and tone are locked; the precise sentence template/interpolation is an
  implementation detail for planning.
- Whether `public_phone/0` (D-02) is formatted with country code, spaces/dashes, etc., in
  `telephone` — follow whatever format the number is already stored in for
  `RESERVATION_WHATSAPP_NUMBER`, don't invent a new format.

### Reviewed Todos (not folded)
- **"Surface 'Pukllay Club' brand name in site content"**
  (`.planning/todos/pending/2026-09-07-surface-pukllay-club-brand-name-in-content.md`) — considered
  as a possible match (this phase's meta/OG/JSON-LD tags do put "Pukllay Club" as text in the page
  `<head>` and structured data) but explicitly **not folded**. The user's original ask wanted the
  brand name surfaced in *visible* page content, sketched first — a different scope from invisible
  metadata. Left in the backlog as-is.
