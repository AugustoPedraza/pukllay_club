## Top 3 Priority Fixes

1. **Color mismatch documentation gap** — Per-game og-card backgrounds use ramp-600 (#8C2AB7, dark theme primary per D-07), while fallback uses ramp-800 (#551670, per Sketch 057's deliberate "deeper step" choice). Design intent is clear in sketch/summaries but code comments claim a factually incorrect light-theme attribution. Fix: Update `lib/pukllay_club/catalog/seed/image_pipeline.ex` comment to correctly document that #8C2AB7 is dark's primary, and explain why fallback uses a different ramp step by reference to Sketch 057's design decision.

2. **Meta description template fragility** — String-replace pattern (`String.replace(", en Pukllay Club", " en Pukllay Club")`) works today but breaks if clause order changes. Fix: Replace with a conditional join or explicit formatting that doesn't rely on substring replacement to fix joining artifacts.

3. **Typography static asset maintenance** — og-fallback.webp is a pixel-perfect static composite (Bebas Neue + isologo-dark.png + Inter tagline) with no runtime font control. Future brand font changes require manual re-export and re-commit of the binary asset. Fix: Document the asset-regeneration process in `.planning/sketches/057-og-fallback-share-card/README.md` (or a dedicated MAINTENANCE.md) so future typography updates know to re-run the export.html and Pillow composite step.

## Detailed Findings

### Pillar 1: Copywriting (3/4)

**Strengths:**
- Meta descriptions use Argentine Spanish (voseo "Descubrí") consistent with Phase 01.3's translated game descriptions and About page copy — site-wide linguistic voice is coherent.
- D-10 alt text formula `"Portada de [Juego], editado por [Editorial]"` is descriptive without being verbose; adds publisher information the visible caption doesn't provide.
- Empty-publishers edge case handled correctly: `editorial_text/1` returns `nil` instead of a bare "editado por", preventing dangling connectors.
- Example D-09 meta description: `"Descubrí Carcassonne, un juego de construcción, pensado para el nivel experto en Pukllay Club, Jujuy."` reads naturally and teaches game vocabulary (mechanic + weight) to non-hobbyists.

**Gaps:**
- **Meta description join pattern is fragile** (file: `lib/pukllay_club_web/seo.ex` line ~223): After building `["Descubrí #{game.name}", mechanic_clause, weight_clause, "en Pukllay Club, Jujuy."]`, a `String.replace(", en Pukllay Club", " en Pukllay Club")` call attempts to fix spacing. This works when the clause-building functions return the expected format, but breaks if mechanic/weight clause wording changes or if either becomes a multi-clause string. No truncation warning when max_description_length is hit (user won't know the description got cut).

**Recommendation:** Replace with a conditional builder or an Enum.intersperse approach that doesn't rely on substring replacement.

### Pillar 2: Visuals (3/4)

**Strengths:**
- **og-fallback.webp layout is clean and intentional:** Centered stacked composition (isologo above, "PUKLLAY CLUB" wordmark centered below, tagline underneath) creates a strong focal point and even spacing. The vertical arrangement gives breathing room on a 1200x630 canvas where side-by-side would have felt cramped.
- **All placeholder image branches carry accessible names:** `<img alt={@cover_alt}>` on working images, `<div role="img" aria-label={@cover_alt}>` on broken-image and nil-cover placeholders (file: `lib/pukllay_club_web/components/game_card.ex` lines ~77-96). Previously, two of the three branches were icon-only with no accessible name.
- **Visual hierarchy is immediate:** Isologo mark dominates (white against purple background, high contrast); wordmark is secondary weight; tagline provides context without competing.

**Gaps:**
- **Color difference between fallback and per-game cards is not code-documented as intentional** (file: `lib/pukllay_club/catalog/seed/image_pipeline.ex` lines ~42-46). Per-game cards use `@og_card_background "#8C2AB7"` (ramp-600, dark theme primary), while fallback uses ramp-800 (#551670). Sketch 057's README documents this as a deliberate choice ("which background ramp step reads best at this larger, text-bearing canvas — ramp-600 or a deeper step?"), but a developer reading only the code sees two hardcoded hex values with no explanation of why they differ. The existing comment incorrectly attributes #8C2AB7 to the light theme's primary when it's actually dark's.

**Recommendation:** Add a comment in image_pipeline.ex explaining: (1) #8C2AB7 is dark theme primary per D-07, (2) fallback uses ramp-800 per Sketch 057's independent decision to use a deeper step for better legibility on the text-bearing canvas.

### Pillar 3: Color (4/4)

**Strengths:**
- **Both social card colors are from the approved OKLCh ramp system** (`assets/css/app.css` defines `--pk-ramp-600` and `--pk-ramp-800`), ensuring brand consistency.
- **Intentional color differentiation by surface:** Fallback (hero-less pages like `/` and `/club`) uses ramp-800 (#551670, deeper purple) for visual separation from per-game detail cards (ramp-600, #8C2AB7). This is a legitimate design decision per Sketch 057's explicit weighing of options.
- **Test assertions account for lossy WebP encoding:** `assert_in_delta r, er, 5` (line ~156, `test/pukllay_club/catalog/seed/og_card_backfill_test.exs`) allows ±5 per RGB channel to account for WebP quantization, matching real-world codec behavior.
- **Color accessibility verified:** Both purple shades were chosen to contrast against white/light text in the og-fallback wordmark and maintain readability in social preview thumbnails.

**No issues found.** Score: 4/4.

### Pillar 4: Typography (3/4)

**Strengths:**
- **og-fallback uses on-brand fonts:** Bebas Neue (wordmark, same font as header) and Inter (tagline, same family as body copy per `assets/css/app.css`). Typography is consistent with the live site's design language.
- **Meta description copy is grammatically correct and tonally consistent:** No typos, proper punctuation, consistent use of lowercase labels ("un juego de X, pensado para el nivel Y") across all generated descriptions.
- **Truncation respects byte boundaries:** `truncate/2` function (line ~240, `seo.ex`) uses `String.length/1` to stay within max_description_length (160 chars for SEO best practice).

**Gaps:**
- **og-fallback typography is static-exported as pixels, not responsive:** The asset is a flat WebP composite (isologo-dark.png rendered at 190px, wordmark at 68px, tagline at 27px, all absolute pixel dimensions). Font updates require re-exporting the asset via the sketch's `export.html` and Pillow composite step — not a runtime change. This is correct for OG social cards (platforms show fixed dimensions anyway), but it's a maintainability concern if fonts ever change.

**Recommendation:** Document the asset-regeneration process (Sketch 057's export.html and Pillow composite) in the sketch's README or a dedicated MAINTENANCE.md so future typography updates know the steps to re-build and re-commit the binary asset.

### Pillar 5: Spacing (3/4)

**Strengths:**
- **og-fallback spacing is precisely documented and verified:** Sketch 057's README states 190px mark width, 68px wordmark, 27px tagline, 20px gaps (line ~48, `057-og-fallback-share-card/README.md`). Dimensions verified at exactly 1200x630 via `Image.width/Image.height` assertions (lines ~77-80, `test/pukllay_club_web/structured_data_test.exs`).
- **Meta tags are rendered in fixed order with clean formatting:** `SEOTags` component (file: `lib/pukllay_club_web/components/seo_tags.ex`) emits tags in a single, uninterrupted sequence — `<meta name="description">`, `<link rel="canonical">`, `og:type`, `og:title`, `og:description`, `og:url`, `og:image`, `og:image:width`, `og:image:height`, `twitter:card`, `twitter:title`, `twitter:description`, `twitter:image` — with no extraneous whitespace. This ensures consistent parsing across crawlers.
- **Spacing is intentional and not arbitrary:** All spacing values are derived from sketch decisions (D-04/D-05 referenced in CONTEXT.md), not ad hoc CSS classes.

**Gaps:**
- **og-fallback spacing is pixel-based, not responsive.** The asset is static and the same at every viewport size — WhatsApp, Twitter, and Facebook show it at their own fixed preview dimensions. This is correct for OG cards but means the asset cannot adapt to future brand spacing updates without re-export.

**Recommendation:** This gap is accepted by design (OG cards are static social artifacts); no action needed.

### Pillar 6: Experience Design (3/4)

**Strengths:**
- **Fallback handling is robust:** `og_image_url/1` (line ~255, `seo.ex`) calls `OgCard.url_for(game) || fallback_image_url()` — if no game-specific og-card exists, the branded fallback is used. No broken image links for hero-less pages.
- **Meta description gracefully handles empty input:** `mechanic_clause/1` and `weight_clause/1` return `nil` for empty mechanics list or nil weight band; `Enum.reject(&is_nil/1)` removes them before join, preventing malformed descriptions like "Descubrí Game, , en Pukllay Club" (missing mechanics).
- **Empty publishers don't produce dangling text:** `editorial_text/1` (line ~35, `game_text.ex`) returns `nil` for `publishers: []`, so `cover_alt/1` produces `"Portada de Game"` (not `"Portada de Game, editado por"`).
- **Truncation prevents runaway description length:** `truncate/2` (line ~240, `seo.ex`) caps descriptions at 160 characters, matching SEO best practice for meta description display length in search results.

**Gaps:**
- **Known Stubs resolved by completion of plan 05:** Plan 01's summary noted that `/` and `/club`'s `og:image` pointed to a non-existent `/images/og-fallback.webp` (a 404). This was flagged as an intentional interim state with the note "Resolved by whichever later 01.8 plan ships the sketch-produced fallback asset." Plan 05 placed the asset and verified serving (lines ~79-92, `01.8-05-SUMMARY.md`, test pass). Gap closed.
- **Nonce-based JSON-LD is a deliberate deviation from RESEARCH.md's Pattern 4:** Plan 05's summary (lines ~25-26) documents that both JSON-LD blocks (site-wide `LocalBusiness` and per-game `Game`) use the per-request nonce rather than a compile-time SHA-256 hash for static content. This was weighed and accepted as simpler (nonce already generated at zero cost) vs. hash-source (required exact byte-stability). No issue, but worth noting as a design choice.

**Recommendation:** No action. Known stubs are resolved; design choices are intentional and documented.
