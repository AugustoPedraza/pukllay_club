- **D-02:** Estantes and Web each become **their own phase**, in that order, after this one. The
  user's words: *"After this phase, I'd like to run a new phase for next page estantes and once that
  implemented another for Web. Maybe after all of that I could retake the UAT."* Inserting those two
  roadmap entries is a `/gsd-phase` operation, **not** this workflow's job — it has not been done.

- **D-03:** `G-01.8.2-7` (Secciones facet) stays an **open gap**, untouched. It is in the public
  `filter_modal.ex`, and the user's only note on it was *"pass but needs some refinement"* — no
  specifics were ever captured, so it is not plannable as-is.

- **D-04:** This phase re-runs **only UAT tests 3 and 4** — the two that recorded its gaps — before
  handing off. The remaining 17 outstanding checkpoints stay paused until after Estantes and Web
  ship. Rationale the user accepted: tests 17–23 are Estantes, tests 8 and 26 are Web, test 24 is the

- **D-05:** ⚠️ **UAT test 25 must be rewritten, not merely re-run.** It currently expects *"the SAME

  This phase deletes the page bar and the back control outright, so two thirds of that expectation
  become vacuous. Rewrite it when the UAT resumes; do not discover this mid-session.

### What leads the page

- **D-06:** `/admin/juegos` renders **no back row and no `<h1>`**. It is a tab-bar destination and
  `layouts.ex:957-973` already labels and highlights **Juegos** persistently via `active_tab={:juegos}`
  (passed at `index.ex:503`). Matches 071/d22 and its "What to Avoid" entry *"A page title row on
  Juegos."*

- **D-07:** **One pinned row leads the page: the 48px search field with the `+` at its right end.**
  071/d7's shape. There is no separate `+` band and no title.
  *User's first proposal was `+` alone on a row at top right, then `Juegos` at left of that row.*
  Both were withdrawn after the counter-argument: the row scrolls away (D-08), so a title would show
  only at rest on the first screen while the tab bar says the same word permanently — and the empty
  band the title was meant to fill disappears entirely once `+` moves beside the field.
  Search is **not** collapsed to an icon — 071/d9 measured that at 16px saved (0 extra rows at
  375×667) for the cost of a tap.

- **D-08:** **Two-tier pinned context.** The search row pins at the top (hiding on scroll-down,
  returning on scroll-up per d9); section captions pin beneath it, opaque. Motivated by real size:
  the fully paged list is ~27,664px (~45 screens) and `Sin datos` alone is 3,307px.

- **D-09:** **`page_bar/1` is deleted, with all its scaffolding** — the component in
  `admin_components.ex:1107`, the `.pk-admin-page-bar` CSS, the `inert`-toggling in
  `admin_list.js:48-57`, and the assertions in `admin_components_test.exs`,
  `admin_composition_test.exs`, `game_live_index_test.exs` and `test/visual/admin_shell.mjs`.
  `game_live/index.ex:611` is its **only** call site in the application, and no planned screen wants
  one (Estantes and Web will drop their titles too; the five sub-screens use `back_row` without a
  page bar). — **Reversibility:** costly — restoring it means re-deriving the D-19n inert
  coordination across the component, the JS hook and four test files.

  Note for the planner: `back_row/1` keeps its other call sites and is **not** deleted — only the
  Juegos one goes.

### The + sheet and the create flow

- **D-10:** The `+` opens **076's sheet verbatim**: header `Agregar juego`, label
  `Número o link de BGG`, field with placeholder `342942`, `Agregar` button. 271px, reached over four
  measured rounds from 435px. **No `Crear a mano`** (d51 — it is unbuilt, not unfinished:
  `Game.draft_changeset` does `validate_required([:bgg_id])`, so there is no by-name insert path).
  **No hint line** (d53 — the first one wrongly promised *"y el nivel"*, which enrichment never
  writes).

  `Agregar` is **disabled while the field is empty** (d52). This is consistent with shipped D-24
  ("disabled means nothing to write") — the save bar already disables `Guardar` when clean. A
  non-empty value that does not parse must still raise *"Pegá un número de BGG o el link del
  juego."*: disabling the empty case must not swallow the invalid one.

- **D-11:** This phase ships **step 0 plus 076/d54's completion toast** — when enrichment lands, a
  10s toast naming the game with a 44px action that opens its editor; a failure gets the same toast
  with a different verb. **077's pending-row sheet (AV1) is cut.**

  ⚠️ **The copy in this decision was superseded — see D-17. Build D-17's strings, not the ones
  quoted in `<specifics>` from sketch 076.**

  Rationale: `index.ex:316`'s `handle_info({:game_enriched, _game_id}, socket)` currently does
  `{:noreply, load_groups(socket)}` — the arrival moment is silent. Per d54, *"V2 covers the interval
  between create and completion, the toast covers the moment of completion… a missed toast has no
  second chance."* The signal already exists (`EnrichGameWorker` broadcasts on both success and
  failure and `index.ex:316` already consumes it), so this is a small change on existing plumbing.

  **Already shipped, do not rebuild:** `land_on_fresh_draft/2` (`index.ex:444`) implements d55's V2
  landing (opens Borradores, marks the row `.fresh`, scrolls it in), and the create snackbar
  `"Juego agregado como borrador."` already matches d54's copy at 4s via `admin_flash/1`.

- **D-12:** The **edition prompt moves inside the `+` sheet**. Today it renders as an inline
  `section_panel` at `index.ex:539-576`, between the add-block and search. The sheet transforms in
  place to ask *"¿Es otra edición?"* with the holder list and Sí/Cancelar; nothing renders on the page
  behind it. Keep `confirm-edition`'s existing server-side guard intact — acknowledged ids come only
  from the `:edition_prompt` assign, never from client params (T-01.8.1-69).

### List and section refinement

- **D-13:** **Port 071's measured anatomy wholesale.** 64px min row; 40px cover, radius 6; 15/400 name
  with `overflow-wrap: anywhere`; 13/400 second line; divider inset to 68px; caption 14/600 uppercase
  tracked `.07em` at full strength (d28 — supersedes d17's 13/600-muted and d20's 15/600 sentence
  case); and **d21's air ratio: 27px above a label, 9px below, 3.0:1 measured text-to-text.**

  d21 is a real measured defect in what shipped, not a taste preference: it was 15 above / 17 below —
  *inverted proximity*, so every label attached to the label above it rather than to its own rows.
  Welding below alone failed at 1.2:1 because a header's bottom padding feeds the next header's gap
  too. **Both ends have to move in opposite directions.** Measure ink, not boxes — the headers are
  transparent, so box gaps lie here.

- **D-14:** **Keep D-25's shipped grouping.** Three sections by `status` — `Borradores` ·
  `Juegos del club` · `Retirados` — with `Sin datos` as a **row attribute** inside Borradores, never
  its own section and never a `status_dot`. 071's exceptions-first list (`Sin datos` / `Borradores` /
  `Juegos del club`) is **superseded** by D-25 and is not reinstated. Port the sketch's *anatomy* onto
  the shipped *grouping*. Coverage 14/D1's passing assertions stay valid.

- **D-15:** **The pinned caption fill becomes 071's `::before` band (d29-31)** — anchored to the
  content box and grown by `--band`, centred by construction in every state; `--cap: 0.6px` nudges it
  onto the cap block; `--bandp` fixes the pinned bar at exactly **44px for every section** regardless
  of its resting padding.

  This replaces the shipped approach at `juegos.css:116`, which puts `background` directly on
  `.pk-admin-juegos-section-header`. 071 warns against that by name: with the header's 26px top
  padding it yields 26px of empty tint above the ink, and it leaves `Sin datos`' bar measuring 32.2px
  against `Juegos del club`'s 44.2px.

  **`G-01.8.2-4` is not a missing rule.** The `[data-pinned="true"]` rule and its IntersectionObserver
  (`admin_list.js:92-110`) both exist. Two contributors for the researcher to confirm:
  (a) the observer fires `pinned` at `entry.boundingClientRect.top < 0` with **no `rootMargin`**
  compensating for the heading's sticky `top: 44px`, leaving a ~44px window where the caption is
  visually pinned but `data-pinned` is false — transparent, list showing through, matching the report;
  and (b) that `44px` was the **page bar's** reserved offset, and D-09 deletes the page bar — so the
  sticky offset must become the pinned search row's height.

- **D-16:** **One page width, on the 16px keel.** The forms are the outliers:
  `.pk-admin-juegos-add-form` and `.pk-admin-juegos-search` carry **no** horizontal inset, while
  captions (`padding: 26px 16px 0`) and rows (`.pk-admin-row`, 16px padding-left) self-inset 16px —
  so the top of the page sits 16px wider than everything under it.

  **Fix at the children, not the container.** All nine admin screens hand-copy
  `<div class="mx-auto w-full max-w-3xl space-y-6">` with no gutter; adding padding there would
  **double** every existing child's inset to 32px, and would reach eight screens outside this phase's
  scope. The new pinned search/`+` row honours the 16 keel like its siblings. 16 is the measured admin
  keel (01.8.2 open item 4, `01.8.2-UI-SPEC.md`), not an assumption — sketch 079's `14` measured the
  public ficha, a different surface, and is superseded.

  Full-bleed elements (the pinned caption band, the pinned search row's own background) still span
  edge to edge with their **ink** at 16 — per 071: *"every ancestor up to the 16px-inset content keel
  carry no horizontal padding of their own, so a 100%-width header already spans edge to edge without
  a negative-margin trick."*

### Copy (resolves a conflict D-11 did not know it had)

- **D-17:** **The create/enrich feedback copy is the developer's, given 2026-09-24. It supersedes
  both sketch 076/d54 (quoted in `<specifics>`) and `01.8.2-OPEN-ITEMS.md` item 5.** Build exactly:

  ```
  creation snackbar  Buscando info desde BGG                          4000ms
  arrival toast      {juego} agregado                    [ Editar ]  10000ms
  failure toast      No pudimos traer los datos BGG de #342942  [ Editar ]  10000ms
  ```

  `{juego}` is the game's name at arrival. Per RESEARCH, `game.name` already carries this with no
  special-casing: it is the BGG placeholder `Juego #<bgg_id>` until enrichment succeeds, at which
  point `Enrichment.build_attrs/4` overwrites it with the real title *before* `enrichment_status`
  flips to `"enriched"`. The failure string uses the **`bgg_id`**, not the name.

  **Why this conflict existed, so it is not rediscovered:** `01.8.2-OPEN-ITEMS.md` item 5 records
  the developer resolving all three strings (`Borrador creado` / `Agregado al club` / `Editar`) in
  plan 01.8.2-03 — but grep proves that resolution **was never implemented**: neither
  `Borrador creado` nor `agregado al club` appears anywhere in `lib/` or `test/`. What actually
  ships is `"Juego agregado como borrador."` (`index.ex:170`, asserted by
  `game_live_index_test.exs:381` and `:483`), which is 076's string — the one item 5 superseded.
  D-11 then read the shipped string as confirmation of the sketch and adopted 076 wholesale.

  **What this changes about meaning:** the creation snackbar now describes the *in-flight fetch*
  rather than the creation, which frees **`agregado` to mean arrival only** — the ambiguity 076
  itself flagged as unresolved, now closed. This is item 5's intent reached with the developer's
  own phrasing.

  **Consequences the planner must carry:**
  - `index.ex:170`'s `put_flash(:info, "Juego agregado como borrador.")` **changes** to
    `Buscando info desde BGG`. This is no longer a "already matches, do not touch" item.
  - `game_live_index_test.exs:381` and `:483` assert the old string and **must be updated**, or
    the suite goes red.
  - The action label `Editar` is inherited from `01.8.2-OPEN-ITEMS.md` item 5 (the most recent
    recorded decision on this specific button); the developer overrode the phrasing in this round
    but not the action. — **Reversibility:** reversible; it is one string.
