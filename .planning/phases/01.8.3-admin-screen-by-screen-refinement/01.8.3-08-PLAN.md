## The binding decision this plan implements

**D-20a / D-20b (developer, 2026-09-27, `01.8.3-UAT.md`'s decision block) are settled input, not
open questions.** This plan implements D-20b only; D-20a (pin behaviour) is plan 11.

D-20b: **one axis at 32px. CONTENT DOES NOT MOVE.** `<main>`'s `px-4` stays; each component keeps
its own 16px; the shipped 32px content inset becomes the declared keel. What changes is everything
that is NOT already at 32: the caption band `::before` (16 → 32) and the row divider's right end
(16 → 32). The third item in D-20b's list — the sheet body — is plan 10, because the sheet is
`position: fixed` and escapes `<main>`'s `px-4` entirely, so matching its body to its own 16px
header is what makes it internally consistent. **One axis per stacking context, not one number
globally.** The rejected alternative was stripping the components' duplicated 16px to land content
on 16; the developer confirmed the preview (content unchanged) after an inconsistent option label
was caught.

## Why the token is 16px while the declared keel is 32px

The declared keel is a VIEWPORT-relative quantity (32). The token is the COMPONENT half of it (16);
the other half is `Layouts.app/1`'s `<main class="px-4 sm:px-6 lg:px-8">` (`layouts.ex:637`), which
every admin page inherits except the one `fullbleed` caller — the editor (`form.ex:1177`), where
`main` measures `paddingLeft: 0px` and the same components land on 16. 16 + 16 = 32.

Naming it `--pk-admin-keel-inset` rather than `--pk-admin-keel` is deliberate: a property named for
the keel while holding half of it is exactly the class of lie this gap is made of.

## Recorded planning choices

  divider's own immediate family, where the conversion is what makes the shared axis structural

- **Package legitimacy gate: not applicable.** No package-manager install runs in any task;
