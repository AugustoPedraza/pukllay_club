## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `data-pinned` attribute value never matched its own CSS selector**
- **Found during:** Task 1, while writing and first running the new probe against the live app
- **Issue:** `admin_list.js`'s `setupPinObserver` used `wrap.toggleAttribute("data-pinned", pinned)`,
  which sets an empty-string value (`data-pinned=""`) when `pinned` is `true` — never the literal
  string `"true"`. `juegos.css`'s pinned-band rules select on the exact-value
  `[data-pinned="true"]` (twice). The fill has never actually painted in the shipped app since
  plan 01.8.3-03 shipped it — a probe checking for "band is opaque while pinned" would fail
  permanently and correctly, exposing a real production defect, not a probe bug.
- **Fix:** Switched to `setAttribute("data-pinned", "true")` / `removeAttribute("data-pinned")`,
  mirroring this same function's own `data-pinned-hidden` sibling convention two lines above.
- **Files modified:** assets/js/hooks/admin_list.js
- **Verification:** Standalone CDP script confirmed `data-pinned` reads `"true"` (not `""`) after
  the fix; the full probe's band-height/adjacency/transparency checks all pass live afterward.
- **Committed in:** da427022 (Task 1 commit)

**2. [Rule 1 - Bug] Pin predicate false-positives for a section still below the fold**
- **Found during:** Task 1, while measuring the "later" section (Juegos del club) after expanding
  the collapsed Borradores section (a required setup step to get rows for the ink-ratio check)
- **Issue:** `!entry.isIntersecting` alone is `true` both when a section has scrolled *past* the
  pinned row (the intended meaning) and when it has never been scrolled *to* yet (still fully
  below the fold) — an `IntersectionObserver` cannot distinguish direction. Expanding Borradores
  pushes Juegos del club's heading far down the page; `setupPinObserver()` re-runs (a fresh
  `IntersectionObserver` fires an immediate entry for the new geometry) and its now-far-below
  sentinel reported `isIntersecting: false`, incorrectly marking it `data-pinned="true"` before the
  page had scrolled at all. This is exactly the class of real-usage defect (expanding a
  commonly-collapsed section) LiveViewTest cannot exercise.
- **Fix:** Re-added `entry.boundingClientRect.top < this.pinnedBandPx + 1` as a second, ANDed
  condition — but keyed to the *same* threshold `rootMargin` already uses, unlike the original
  (pre-01.8.3-03) literal `< 0` that caused the diagnosed ~44px delayed-pin window in the first
  place. Both the below-the-fold false-positive and the original delayed-pin defect are closed by
  the same corrected threshold.
- **Files modified:** assets/js/hooks/admin_list.js
- **Verification:** Standalone CDP script confirmed `data-pinned` reads `null` for a
  not-yet-scrolled-to section (was previously `"true"` before this fix) and correctly flips to
  `"true"` only once genuinely scrolled past threshold (`headerRect.top` confirmed at exactly
  60px, the sticky offset, at that point).
- **Committed in:** da427022 (Task 1 commit)

**3. [Rule 1 - Bug] Pinned band's top offset depended on `--pt`, breaking flush alignment for non-first sections**
- **Found during:** Task 1, measuring the band-to-search-row adjacency for both sections
- **Issue:** The pinned rule's `top: calc(var(--pt) - var(--bandp) - var(--cap))` still varied by
  `--pt` (14px for the first section, 26px for every other), even though every header pins at the
  identical sticky offset (`top: var(--pk-juegos-pinned-h)`, 60px, same for all sections). This
  left the band flush against the search row only for the first section (0.5px gap, a near
  coincidence of its own `--pt` value) while later sections sat 12.5px below it — exactly the
  `--pt` delta leaking straight through, the same class of defect (a value that should be
  height-only leaking into position) the original 32.2px/44.2px height bug was.
- **Fix:** Set `top: 0` (the band's top edge now equals the header's own top edge exactly, for
  every section) and re-derived `bottom: calc(var(--pt) - 2 * var(--bandp))` so the height
  invariant (`--cap-box + 2 * --bandp` = 44px, already correct) still holds algebraically. For the
  first section this correctly yields a *negative* `bottom` (the band extends past its own
  shorter box into the row below) — the same overflow shape the pre-existing code already relied
  on for that section's `bottom` side under the old formula, not a new class of rendering.
- **Files modified:** assets/css/admin/juegos.css
- **Verification:** Live probe re-run: both sections report `bandTop=60`, `search-row gap=0px`,
  `height=44px` — identical numbers for both sections, confirming the flush-alignment fix without
  disturbing the already-correct height invariant.
- **Committed in:** da427022 (Task 1 commit)

**4. [Rule 1 - Bug, minor] The ink-to-ink measurement was being taken in the wrong scroll state**
- **Found during:** Task 1, first attempt at measuring the air ratio for the "later" section
- **Issue:** The plan's own behavior spec measures the air ratio "while a caption is pinned"
  alongside the band checks — but D-13's 27px-above/9px-below anatomy is a resting-layout
  property; measuring it while pinned reads nonsense, because the pinned header visually overlaps
  (its own `z-index:10`) whatever content has scrolled up underneath it. Observed: a negative
  `airBelow` distance (`-173.6px`).
- **Fix:** Moved the ink-to-ink measurement to before the pin-triggering scroll begins (at rest, in
  normal document flow, where `getBoundingClientRect()` correctly reports each element's natural,
  non-overlapping position regardless of current scroll position).
- **Files modified:** test/visual/admin_shell.mjs
- **Verification:** Re-run reports `airAbove=39px`, `airBelow=14.7px`, `ratio=2.65:1` — positive,
  sane numbers exceeding the 2.5:1 floor.
- **Committed in:** da427022 (Task 1 commit)
