# Phase 01.8.3: Code Review Report

**Reviewed:** 2026-09-25T04:55:20Z
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

Reviewed the Juegos screen-by-screen refinement (five plans, four waves): the
rewritten pinned-caption mechanism (`admin_list.js` / `juegos.css`), the
deletion of `AdminComponents.page_bar/1`, the Juegos-scoped row/caption
overrides, and the new PubSub-driven enrichment snackbar on
`Admin.GameLive.Index`.

The pinned-caption mechanism itself — the area flagged as highest-risk,
having already produced three real bugs caught by plan 05's browser probe —
checks out on direct inspection and by re-deriving its CSS arithmetic by
hand: the `data-pinned="true"` attribute/selector contract is consistent
end-to-end, the below-fold vs. scrolled-past pin predicate is correct, and
the pinned-band height invariant (44px) holds identically for the first
section (`--pt: 14px`) and every later section (`--pt: 26px`). `page_bar/1`'s
deletion is clean — no orphaned CSS rules, no dead call sites, no leftover
test blocks — only a handful of stale doc comments still name the removed
function. The Juegos-scoped row/caption overrides are correctly fenced by
the `.pk-admin-juegos-rows`/`.pk-admin-juegos-section-header` ancestor
classes and don't leak onto the other eight admin screens.

The one real defect found is in a part of this phase that the pinned-caption
work didn't touch: **the "Agregar juego" sheet never closes after confirming
an edition** (`confirm-edition`'s success branch is missing the
`add_game_sheet_open: false` assign its sibling `add-game` branch has) —
confirmed by direct code inspection and reproduced with a throwaway
`LiveViewTest` run against the real handler (removed afterward, no test
files were left behind). This silently defeats this phase's own "land on
the fresh draft" UX for the entire D-03 known-BGG-id/edition path, which is
exercised by several existing tests that never assert the sheet's open
state.

## Critical Issues

### CR-01: confirming an edition never closes the "Agregar juego" sheet

**File:** `lib/pukllay_club_web/live/admin/game_live/index.ex:246-257`
**Issue:**

`handle_event("add-game", %{"bgg_id" => bgg_id}, socket)`'s success clause
explicitly closes the pinned "+" sheet on a successful add:

```elixir
{:ok, game} ->
  {:noreply,
   socket
   |> assign(:bgg_id_input, "")
   |> assign(:bgg_id_error, nil)
   |> assign(:edition_prompt, nil)
   |> assign(:add_game_sheet_open, false)   # <-- closes the sheet
   |> put_flash(:info, "Buscando info desde BGG")
   |> land_on_fresh_draft(game)}
```

`handle_event("confirm-edition", _params, socket)` — the sibling handler for
"Sí, agregar edición" inside the same sheet's edition-prompt sub-state — does
the identical `land_on_fresh_draft` landing but never sets
`add_game_sheet_open` to `false`:

```elixir
def handle_event("confirm-edition", _params, socket) do
  %{edition_prompt: prompt} = socket.assigns

  case Catalog.add_game_from_bgg(prompt.input, acknowledged_game_ids: Enum.map(prompt.games, & &1.id)) do
    {:ok, game} ->
      {:noreply,
       socket
       |> assign(:bgg_id_input, "")
       |> assign(:bgg_id_error, nil)
       |> assign(:edition_prompt, nil)
       |> put_flash(:info, "Edición agregada como borrador.")
       |> land_on_fresh_draft(game)}
    ...
```

Since `AdminComponents.sheet/1`'s open/closed state is purely the
`add_game_sheet_open` assign (never removed from the DOM, per its own doc:
"Open/closed state is the `pk-admin-overlay--open` class on the root
element"), the sheet stays open — its scrim and bottom-sheet panel remain on
screen — after a staff member pastes an already-claimed BGG id, confirms
"Sí, agregar edición", and gets a freshly created draft. The screen behind
the sheet *does* land correctly (Borradores opens, the new row is marked
`fresh`), but the user can't see it: the sheet visually blocks the page
until they manually tap the scrim or the ✕.

Reproduced directly against the real handler with a throwaway
`Phoenix.LiveViewTest` run (not committed):

```
render_click(lv, "open-add-game-sheet", %{})
lv |> form("#add-game-sheet-form", bgg_id: "184267") |> render_submit()   # known id -> edition prompt
lv |> element("#confirm-edition") |> render_click()

has_element?(lv, "#add-game-sheet.pk-admin-overlay--open")
# => true   (should be false, matching the plain "add-game" success path)
```

None of the existing edition tests
(`test/pukllay_club_web/live/admin/game_live_index_test.exs:297-308`,
`:441-461`, `:560-573`, `:575-593`) assert the sheet's open/closed state
after `confirm-edition`, which is why this shipped undetected — the
`add-game` path's own equivalent test
(`test/pukllay_club_web/live/admin/game_live_index_test.exs:665-684`) does
assert it and passes, because only that branch sets the flag.

**Fix:** add the same `|> assign(:add_game_sheet_open, false)` to
`confirm-edition`'s `{:ok, game} ->` clause, and add a regression assertion
(`refute has_element?(lv, "#add-game-sheet.pk-admin-overlay--open")`) to the
existing "confirming an edition opens Borradores and marks the new row
fresh" test so this can't silently regress again:

```elixir
{:ok, game} ->
  {:noreply,
   socket
   |> assign(:bgg_id_input, "")
   |> assign(:bgg_id_error, nil)
   |> assign(:edition_prompt, nil)
   |> assign(:add_game_sheet_open, false)
   |> put_flash(:info, "Edición agregada como borrador.")
   |> land_on_fresh_draft(game)}
```

## Warnings

### WR-01: the "fresh" row highlight is never cleared — a permanent tint that contradicts its own documented invariant

**File:** `lib/pukllay_club_web/live/admin/game_live/index.ex:113,443,561-566`, `assets/css/admin/juegos.css:445-451`
**Issue:**

`:fresh_game_id` is set once on add/edition/publish (`land_on_fresh_draft/2`,
`handle_publish_after_save/2`) and is **never reset** anywhere else in the
module — `mount/3`'s `assign(:fresh_game_id, nil)` is the only place that
clears it, so it only resets on a genuine remount (hard navigation away and
back), not on a same-LiveView `push_patch`. `juegos.css`'s own comment on
`.pk-admin-juegos-row--fresh` states the intended contract explicitly:

> "held for one session ... No colour beyond the shared surface-2 press
> token — a persistent tint here would read as a second, permanent status,
> which D-19h forbids."

Reproduced directly: after adding a draft, the newly-fresh row keeps its
`.pk-admin-juegos-row--fresh` tint through an unrelated no-op search change,
and — after collapsing/re-expanding its own section, or clicking
"Reintentar" on a completely different draft row — the SAME row is still
rendered with the fresh class. It only stops once a *different* game becomes
the new `fresh_game_id` (add/edition/publish again). In practice: whichever
game a staff member most recently added or published stays visibly tinted
for the rest of that browsing session, which is exactly the "second,
permanent status" the code's own comment says D-19h forbids.

This predates plan 01.8.3 (the `land_on_fresh_draft`/`fresh_game_id`
mechanism itself is unchanged in this phase's diff — confirmed via `git
diff`), but it is directly adjacent to and exercised by this phase's new
sheet/search/toast flows, and no existing test (in either
`game_live_index_test.exs`'s pre-existing or newly-added describe blocks)
asserts the tint ever clears.

**Fix:** clear `:fresh_game_id` on the next unrelated `handle_event`/
`handle_params` after it's been shown once (e.g. a one-shot boolean, or
clear it inside `load_groups/1` whenever the triggering interaction isn't
itself the add/edition/publish path), or have the client tell the server
once `scrollFreshIntoView()` has run (a `pushEventTo` after the scroll
completes) so the highlight is provably shown-and-cleared rather than
"cleared only by being overwritten."

### WR-02: `handle_info({:game_enriched, id}, socket)` has no catch-all clause, and the single stable toast id can silently drop a failure notification

**File:** `lib/pukllay_club_web/live/admin/game_live/index.ex:394-407`
**Issue:**

The only `handle_info/2` clause on this LiveView pattern-matches literally on
`{:game_enriched, game_id}`. Today this is safe in practice — a repo-wide
grep confirms `EnrichGameWorker` is the only broadcaster on the
`"admin:games"` topic — but there is no defensive catch-all, so any future
broadcast on this topic with a different shape (e.g. a second worker added
later) crashes this LiveView's process with a `FunctionClauseError` rather
than degrading gracefully.

Separately, the toast itself always renders at the single stable id
`"enrichment-toast"` (by design, per the module's own doc, "so concurrent
arrivals do not stack" — confirmed intentional and covered by the "two
arrivals in sequence leave exactly one snackbar, naming the second game"
test). The residual risk this leaves: `handle_info` never touches
`:collapsed_sections`, so if Borradores is collapsed (its default state at
every fresh mount) when two enrichments complete close together, the FIRST
game's toast (which could be the "No pudimos traer los datos BGG de #X"
failure message) is silently replaced by the second game's toast before the
staff member ever sees it — and the only remaining evidence, the inline
error + Reintentar row, sits inside a section that is collapsed by default
and that this handler never opens. The data isn't lost, but a staff member
who doesn't know to expand Borradores could plausibly never learn a specific
BGG fetch failed.

**Fix:** add a catch-all `handle_info(_other, socket)` clause (even a
no-op) for defense-in-depth against future broadcasters on this topic; for
the toast-drop risk, consider either surfacing failed enrichments more
durably (e.g. a small pending-count badge on Borradores itself, independent
of the transient toast) or expanding Borradores when a `"failed"` toast
would otherwise be silently superseded.

### WR-03: stale doc comments still describe `AdminComponents.page_bar/1` and its CSS as if they exist

**File:** `lib/pukllay_club_web/components/admin_components.ex:1063,1065,1100`, `assets/css/admin/components.css:836,857`
**Issue:**

`AdminComponents.page_bar/1` and its `.pk-admin-page-bar*` CSS rules were
deleted outright by plan 01.8.3-02 (confirmed: no `def page_bar` and no
`.pk-admin-page-bar` rule block exists anywhere in `assets/css/` or `lib/`
today — `test/visual/admin_shell.mjs`'s own updated comment at line 1027-1043
documents the same deletion and repurposes its check into a
regression guard). But three `@doc` strings in `admin_components.ex` and two
comments in `components.css` still reference `page_bar/1` — including
`components.css:836`'s `.pk-admin-page-bar__back below` — as if the
function/class still exists and can be looked up:

- `admin_components.ex:1063`: "the same anatomy `page_bar/1`'s own back link uses"
- `admin_components.ex:1065`: "Pass `inert={true}` when `page_bar/1` alongside it..."
- `admin_components.ex:1100`: "at `page_bar/1`'s 17/600 rank"
- `components.css:836`: "shared visual anatomy with `.pk-admin-page-bar__back` below" (there is no rule below it — that class doesn't exist in this file)
- `components.css:857`: "a mode header and a pinned [page bar]"

A future editor grepping the codebase for `page_bar` to understand
`back_row/1`'s or `reorder_header/1`'s own rank contract will find prose
that assumes a component this same phase deleted still exists, with no
signal that it's gone.

**Fix:** update the three `admin_components.ex` doc comments to describe the
rank/anatomy in terms of a still-existing reference point (e.g. `back_row/1`
itself, or a literal "17/600" call-out) instead of the deleted `page_bar/1`,
and fix `components.css:836`'s dangling `below` cross-reference.

### WR-04: `setupPinObserver()` tears down and recreates the `IntersectionObserver` on every LiveView `updated()`, with no guard against a stale `data-pinned` value during the async gap

**File:** `assets/js/hooks/admin_list.js:106-119,127-191`
**Issue:**

`updated()` unconditionally calls `this.setupPinObserver()`, which
disconnects the previous observer and constructs a brand-new
`IntersectionObserver` for every LiveView patch — not just patches that
actually add/remove/reorder sections (e.g. a plain search-narrowing
`render_change`, a toggle-section click, or the new enrichment-toast arrival
all trigger this same rebuild). `IntersectionObserver`'s own initial
notification for newly-`observe()`d targets is asynchronous (queued, not
synchronous within `setupPinObserver()`'s call frame), so for one or more
frames after each patch, any `data-pinned` attribute value left over from
the PREVIOUS observer instance is stale rather than recomputed. Given this
exact mechanism has already shipped three distinct real bugs
(`toggleAttribute` vs. `setAttribute`, the below-fold false-pin, and the
per-section `--pt`-dependent band offset — all documented in this file's own
header comment and `juegos.css`'s Rule-1 fix comments), a timing gap with no
test coverage in the same mechanism is worth a guard, even though it's
likely to only produce a one-frame visual flicker in the common case (e.g.
a section reorder that happens to change which caption is currently near
the pinned band).

**Fix:** either only call `setupPinObserver()` when the set of
`[data-pk-section-sentinel]` elements has actually changed (diff against
the previous `sentinels` array before disconnecting/reconnecting), or
explicitly clear every currently-set `data-pinned` attribute at the start
of `setupPinObserver()` so a stale "true" can never survive into the next
patch's paint.

## Info

### IN-01: the pinned-band CSS offset and the JS's rootMargin inset are two independently-declared numbers, not truly one source of truth

**File:** `assets/css/admin/juegos.css:23-34`, `assets/js/hooks/admin_list.js:64-77`
**Issue:**

`juegos.css`'s header comment states the custom property
`--pk-juegos-pinned-h: 60px` exists "so the section captions' sticky offset
... and the pin-observer's rootMargin ... both derive from the same declared
number instead of two independently copied `44`s." In fact `admin_list.js`
never reads `--pk-juegos-pinned-h` at all — it independently measures
`#juegos-search-wrap`'s real rendered height via `getBoundingClientRect()`
(falling back to a separately-typed literal `60` only if that element is
absent). Today the two values agree (both resolve to 60, since
`4 + 48 + 8 = 60` on both sides), but they are two independently-authored
numbers a future edit could desync: e.g. changing
`.pk-admin-juegos-search-row`'s padding updates the JS's live measurement
automatically but does **nothing** to the CSS custom property that actually
drives `.pk-admin-juegos-section-heading-wrap`'s `position: sticky; top:`
offset, silently reopening the exact class of pin-timing bug this whole
mechanism exists to prevent. Only the developer-invoked, non-CI
`test/visual/admin_shell.mjs` probe would catch that drift, and only if
someone remembers to run it.

**Fix:** either have the JS hook read `--pk-juegos-pinned-h` via
`getComputedStyle` instead of independently measuring the DOM (making the
CSS custom property the actual single source of truth the comment already
claims it is), or update the comment to be honest that the two numbers are
parallel-maintained, not derived.
