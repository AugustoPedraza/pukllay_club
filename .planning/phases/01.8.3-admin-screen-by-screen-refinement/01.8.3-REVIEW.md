## Summary

This is an **incremental** review over the gap-closure work only — plan 01.8.3-06 (the
pinned-caption ink-centring fix + its new browser-free ExUnit gate) and plan 01.8.3-07 (the
overlay-viewport-coverage fix + its new CDP walk). It merges with, and does not replace, the
earlier full-phase review (plans 01-05) recorded below under "Carried Forward from the
Plans 01-05 Pass."

The two shipped fixes themselves are sound. Re-deriving `juegos.css`'s pinned-padding algebra by
hand against every `--pt` this codebase actually declares (26px base, 14px `:first-child`) confirms
the header's total vertical padding — and therefore its border-box height — is genuinely conserved
across the pinned/unpinned transition, and the first section's `padding-bottom` (0.5px) stays
non-negative by the thinnest of margins but does stay non-negative. `components.css`'s `margin: 0`
on `.pk-admin-overlay-root` is architecturally correct given this codebase's own established
cascade-layer convention (an unlayered rule beats a layered Tailwind utility regardless of
specificity, confirmed against `app.css`'s own CASCADE-LAYER HAZARD note) — it closes the
`space-y-*`-inherited `margin-block-end` gap for every `sheet/1`/`dialog/1` call site at once, not
just the one call site (`#add-game-sheet`) the bug was originally caught on.

The one real defect found in this incremental scope is in the new **browser-free** regression gate
itself, `admin_pinned_band_test.exs` — not in the shipped CSS. Its stated purpose (per its own
header comment) is to make "a revert of the fix, a literalised `--bandp`, or a `--pt` dropped below
its floor... go red in `mix quality` with no browser at all." Empirically reproducing a mutated
`--bandp` formula (divisor `/3` instead of `/2`, which resolves to a real 35.4px pinned band instead
of the required 44px — the same class of defect as the shipped 32.2px/44.2px bug this whole
mechanism exists to prevent) shows the test suite does **not** catch it: two of its four tests never
extract or evaluate `--bandp`'s actual declared arithmetic, only whether certain substrings
(`calc(`, `--cap-box`, `44px`) are present in its raw text, or a value the test **itself**
independently recomputes from `--cap-box` alone. Since this class of regression is invisible to
`mix quality`/CI and the one check that WOULD catch it (`admin_shell.mjs`'s real-browser
measurement) is developer-invoked only and never runs in CI (per `test/visual/README.md`), this
class of defect could ship and stay shipped indefinitely.

## Critical Issues

### CR-02: `admin_pinned_band_test.exs`'s `--bandp` checks are substring/tautology-based and cannot detect a real formula regression

**File:** `test/pukllay_club_web/admin_pinned_band_test.exs:92-154`
**Issue:**

The test file's own header comment states its purpose: catch "a revert of the fix, a literalised
`--bandp`, or a `--pt` dropped below its floor" with no browser, in `mix quality`. Two of its four
tests do not actually do this for a formula-level regression in `--bandp`:

- **`"--bandp is declared as a calc() derived from --cap-box and the 44px target, not a literal"`**
  (lines 92-113) only checks that the raw declaration text contains the substrings `"calc("`,
  `"--cap-box"`, and `"44px"`. It never parses or evaluates the actual arithmetic. A declaration
  changed to `calc((44px - var(--cap-box)) / 3)` (wrong divisor) or
  `calc((44px - var(--cap-box)) / 2 + 5px)` (added offset) contains all three substrings and passes.

- **`"the band-height algebra closes: --cap-box + 2 * --bandp equals 44"`** (lines 142-154) is a
  **tautology**. It reads `--cap-box` from the real CSS, then computes
  `bandp = (44.0 - cap_box) / 2` **itself** — it never reads `--bandp`'s actual value or formula
  from the CSS at all. `cap_box + 2 * bandp` therefore reduces to `cap_box + 2 * ((44 - cap_box) / 2)
  = 44` by pure algebra, for *any* `cap_box`, regardless of what `--bandp`'s real declared `calc()`
  in the file says. This assertion can never fail (short of a floating-point rounding error).

- **`"every declared --pt clears --bandp + --cap"`** (lines 115-140) inherits the same blind spot:
  its `floor` is computed from the test's own assumed `bandp = (44.0 - cap_box) / 2`, not from the
  real declared value — so if the real formula regresses, this test checks the real `--pt` values
  against a **wrong** floor and can pass a `--pt` that would actually produce a negative
  `padding-bottom` in the shipped CSS.

Empirically confirmed by mutating a scratch copy of `assets/css/admin/juegos.css`'s `--bandp`
declaration to `calc((44px - var(--cap-box)) / 3)` (real rendered band height: 35.4px, not 44px —
verified by hand, not via the browser probe) and re-running the three tests' underlying regex/arithmetic
logic against it: all three still pass. The `/tmp` scratch file used for this reproduction was not
committed and is not part of this review's deliverable.

Because `test/visual/admin_shell.mjs` (the one check with real browser measurements that *would*
catch this) is "Developer-invoked only — never `mix quality`, never CI" (`test/visual/README.md`),
this exact class of regression — a wrong divisor or added offset in `--bandp`'s formula, silently
reopening the 32.2px/44.2px-class defect plan 01.8.3-05/06 exist to fix — has **zero** automated
coverage in CI or `mix quality` today, despite this file's explicit stated purpose being to provide
exactly that coverage.

**Fix:** make the ExUnit test actually evaluate `--bandp`'s declared arithmetic against the real
`--cap-box`/`--cap` values read from the same file, instead of recomputing an assumed-correct value
independently. Since full `calc()` parsing is out of scope for a regex-based guard, a narrower but
non-tautological fix is to assert the *exact* expected `calc()` string (extracted `--cap-box` value
inlined), e.g.:

```elixir
test "--bandp's calc() resolves to the value the 44px band-height invariant requires" do
  src = juegos_source() |> strip_comments()
  cap_box = numeric_value(src, "--cap-box")
  body = rule_body(src, @base_header_selector)
  bandp_raw = declared_value(body, "--bandp")

  expected = "calc((44px - var(--cap-box)) / 2)"
  assert bandp_raw == expected,
         "Expected --bandp to be exactly `#{expected}` (with --cap-box=#{cap_box}px), " <>
           "got `#{bandp_raw}` — a changed divisor/offset here silently reopens the " <>
           "32.2px/44.2px-class band-height defect with no browser-based check running in CI."
end
```

This still isn't a full CSS `calc()` evaluator, but it closes the specific gap demonstrated above:
an exact-string match on the formula, rather than substring presence, catches a changed divisor,
added offset, or flipped sign — the concrete mutations shown to slip through today.

## Warnings

### WR-05: four of six `OVERLAY_CALL_SITES` rows are data-dependent, and a real regression there degrades to a silent "not-openable" verdict, not a failure

**File:** `test/visual/admin_shell.mjs:400-474,633-698`
**Issue:**

`checkOverlayRealOpenWalk`'s design deliberately does not fail a `dataIndependent: false` row when
its opener selector never appears — it logs `NOT-OPENABLE` and excludes it from both `fails` and
`covered` (lines 644-654), on the stated reasoning that a thin dev catalog (no shelf rows, no
placed copies, no band mismatches) is expected and shouldn't be conflated with the walk itself being
broken. This is a reasonable design for the two `dataIndependent: true` rows, but it also means a
**real regression** in any of the four data-dependent overlays (`shelf-options-sheet`,
`confirm-delete-shelf-dialog`, `cover-options-sheet`, `niveles-sheet`) — e.g. an opener's `phx-click`
handler renamed, a selector typo introduced by an unrelated edit — produces the exact same
`NOT-OPENABLE` log line as "the dev DB happens to be empty right now." Nothing distinguishes "this
row was never exercised" from "this row's opener is broken" in the exit code (`process.exit(exitCode)`
is driven only by `fails.length`), and — per `test/visual/README.md` — this script only ever runs
when a developer remembers to invoke it by hand against a seeded dev database. In practice this means
the majority (4 of 6) of this gap's own new call-site coverage can silently run zero real assertions
run after run, with only a `covered=N` count in the console log as the sole signal, and no test
compares that count against a minimum expected value.

**Fix:** either seed the four data-dependent fixtures deterministically as part of this script's own
setup (so `NOT-OPENABLE` becomes a true rarity rather than the common case), or add a summary-level
assertion (e.g. `covered + notOpenable.length === attempted` is already implied, but nothing asserts
`covered >= N` for a known-good dev DB) so a silent drop in real coverage is itself visible as a
`FAIL` rather than requiring a human to notice a lower `covered=` number in scrollback.

## Info

### IN-02: the pinned padding-bottom's real safety margin (0.5px) is thinner than the guarding test can currently prove

**File:** `assets/css/admin/juegos.css:282-308`
**Issue:**

For the first section (`--pt: 14px`), the pinned rule's `padding-bottom` resolves to
`14 - 12.9 - 0.6 = 0.5px` — correct and non-negative today, but only by 0.5px against the
documented floor of `--bandp + --cap` (13.5px). This is not itself a defect (the arithmetic is
correct as shipped, and `admin_pinned_band_test.exs`'s test 3 does check every declared `--pt`
against this floor) — but see CR-02 above: that floor is itself computed by the test from an
assumed-correct `--bandp`, so the safety net protecting this already-thin margin shares the same
blind spot as the band-height check.

**Fix:** no action required beyond CR-02's fix — once the test extracts/verifies the real declared
`--bandp` rather than assuming it, this thin-margin case becomes properly protected as a side
effect.

### WR-02: `handle_info({:game_enriched, id}, socket)` has no catch-all clause, and the single stable toast id can silently drop a failure notification

**File:** `lib/pukllay_club_web/live/admin/game_live/index.ex:394-407`
**Status:** open, unaffected by this incremental pass.

The only `handle_info/2` clause on this LiveView pattern-matches literally on
`{:game_enriched, game_id}` with no defensive catch-all for a future second broadcaster on
`"admin:games"`. Separately, the single stable toast id `"enrichment-toast"` means a failure toast
for game A can be silently superseded by a success toast for game B if both enrichments complete
close together while Borradores is collapsed (its default state).

**Fix:** add a catch-all `handle_info(_other, socket)` clause for defense-in-depth; consider
surfacing failed enrichments more durably than the transient toast alone.

### WR-03: stale doc comments still describe `AdminComponents.page_bar/1` and its CSS as if they exist

**File:** `lib/pukllay_club_web/components/admin_components.ex:1063,1065,1100`, `assets/css/admin/components.css:836,857`

`page_bar/1` and its CSS were deleted by plan 01.8.3-02, but three `@doc` strings in
`admin_components.ex` and two comments in `components.css` (including `components.css:836`'s

### WR-04: `setupPinObserver()` tears down and recreates the `IntersectionObserver` on every LiveView `updated()`, with no guard against a stale `data-pinned` value during the async gap

**File:** `assets/js/hooks/admin_list.js:106-119,127-191`
**Status:** open, unaffected by this incremental pass.

`updated()` unconditionally rebuilds the observer on every patch (search-narrowing, section toggle,
enrichment toast, etc.), and `IntersectionObserver`'s initial notification for newly-observed
targets is asynchronous — so a stale `data-pinned` value can survive into the next patch's paint for
one or more frames.

**Fix:** only rebuild when the set of `[data-pk-section-sentinel]` elements has actually changed, or
explicitly clear every `data-pinned` attribute at the start of `setupPinObserver()`.

### IN-01: the pinned-band CSS offset and the JS's rootMargin inset are two independently-declared numbers, not truly one source of truth

**File:** `assets/css/admin/juegos.css:23-34`, `assets/js/hooks/admin_list.js:64-77`
**Status:** open, unaffected by this incremental pass.

`admin_list.js` never reads `--pk-juegos-pinned-h`; it independently measures
`#juegos-search-wrap`'s rendered height, falling back to a separately-typed literal `60`. The two
values agree today by coincidence of both resolving to 60, not by construction.

**Fix:** have the JS hook read `--pk-juegos-pinned-h` via `getComputedStyle`, or update the comment
to be honest the two numbers are parallel-maintained.
