## The binding decision this plan implements

**D-20a (developer, 2026-09-27) is settled input.** CHOSEN: the band rises to y=0; D-08
(hide-on-scroll-down) is KEPT. The caption's sticky offset becomes DYNAMIC and tracks the search row:
0 while the row is hidden, its measured height when the row returns. Juegos stays consistent with
Estantes. NOT chosen: dropping hide-on-scroll-down. The design conflict `G-01.8.3-3` recorded as
BLOCKING is therefore closed — it must not be re-litigated here.

## How the re-anchor is jump-free, by construction rather than by animation

The two directions are asymmetric on purpose, and this is the whole of the no-jump requirement:

- **On hide (scroll-down):** set the hide attribute AND shrink the reservation to 0 in the same tick.
  The row is mid-transition, occupying the top of the viewport, and `.pk-admin-juegos-search-wrap`'s
  `z-index: 15` paints above the heading wrap's `z-index: 10` — so the band, already in its final
  position, is revealed progressively from behind the outgoing row. Nothing moves twice.
- **On return (scroll-up):** remove the hide attribute immediately, but grow the reservation back only
  AFTER the row's `transform` transition has finished. Growing it at the start would move the band
  down 60px while the row was still sliding in, opening a transient window showing list content
  exactly where the defect used to be. Waiting means the band descends onto a row that has already
  arrived.

The growth is scheduled on a `transitionend` for `transform` on the wrap, with a timeout fallback
derived from the wrap's own computed `transition-duration` at runtime, and applied immediately when
that duration resolves to zero — a reduced-motion or transition-less environment must not strand the
reservation at 0. The `top` property itself is never animated.

## What this plan does NOT fix, deliberately

**The first-section band overhang is an INDEPENDENT fix and must not be folded in.** `juegos.css:339`
sets the pinned band's `bottom: calc(var(--pt) - 2 * var(--bandp))`; with `--bandp = (44px -
18.2px)/2 = 12.9px` that resolves to `--pt - 25.8px`, NEGATIVE for any `--pt < 25.8px`. The first
section declares `--pt: 14px` (`juegos.css:234`), so `bottom = -11.8px`: the sticky header reserves a
32.2px box while painting a 44px opaque band, and 11.8px of tint lies OUTSIDE its own sticky box,
covering flow content that no scroll-offset fix can compensate. Later sections resolve to +0.2px and
do not overhang. That is plan 12, with its own guard and its own developer decision.

So after this plan, the first section will still occlude ~11.8px more than its own box reserves. That
is expected, is recorded here, and must not be patched from inside this plan.

**Ordinary sticky overlap is not in scope because it is not a defect.** Flow content scrolling behind
a sticky header's own reserved box is how a pinned caption works, and the diagnosis says so
explicitly for the published section ("its occlusion is ordinary sticky overlap from the 60px offset
alone"). The assertions below are about content rendering ABOVE the band, never about content passing
behind it.

## Recorded planning choices

- **The observer is rebuilt, not re-configured.** `rootMargin` is immutable after construction, so
  the only way to keep it agreeing with a changing reservation is to rebuild. Direction flips are
  infrequent (a scroll-direction change, not a scroll tick), and `setupPinObserver()` already exists
  and is already called from `updated()`. Rebuild only when the effective value actually changed.
- **The property is written on the hook's own element.** `#juegos-page` carries both
  `phx-hook="AdminList"` and `.pk-admin-juegos`, the selector that declares
  `--pk-juegos-pinned-h` — so an inline value set on it wins over the declaration without a second
  selector or a `!important`.
- **`admin_shell.mjs`'s constraint set is preserved and re-asserted, not replaced.** The 44px band
  height, the band background, the band-to-search-row adjacency, the 64px row floor, the ink-to-ink
  ratio, the per-section ink symmetry (tolerance 2.0px) and the cross-section ink-gap-above equality
  (tolerance 1.0px) all stay. Note precisely what the shipped run reports: `first=13.5px later=13.5px
  delta=0px` is the CROSS-SECTION gap-ABOVE comparison, not gapAbove-against-gapBelow. The
  per-section symmetry tolerance is 2.0px and today's later-section pair is not exactly equal. Do not
  tighten either tolerance to chase a number that was never shipped.
- **API coverage:** `COVERAGE.md` declares `No external API integration`.
- **Package legitimacy gate: not applicable.** No package-manager install; `mix.exs` unchanged.
  `T-01.8.3-SC` stays closed.
