# Phase 01.8.2 Plan 18: Pendientes and Administrar estantes — the queues behind the badge, and estante CRUD behind the gear Summary

**The two remaining estante pages D-08 promised: Pendientes (Afuera + Sin ubicar behind the header badge, sharing one `?copy=` navigation mechanism into the search-first screen) and Administrar estantes (create/rename/reorder/delete from one page, one name sheet, one Ordenar→Listo mode reused verbatim from plan 15, and D-09's honest first run) — with D-10's estante deletion fully undoable down to every copy's exact former position.**

## Accomplishments

- **Pendientes (Task 1).** `/admin/estantes/pendientes` renders Afuera (Phase 4 checkout data — permanently empty until then, by decision) and Sin ubicar (`Shelves.unplaced_copies/0`, the same source the header badge/dashboard/tab bar already read), each a heading with its count, one hint line, and its rows — both sections always render, including at 0 rows. A row navigates to `/admin/estantes?copy=<id>`, a new param `EstanteLive.Index` reads in its own `mount/3` and feeds straight into `select_copy_struct/2` — the exact function a suggestion-row tap already uses, so a Sin ubicar copy opens «¿Dónde va?» immediately and an Afuera copy will land on its estante's rail lifted, with no second sheet or selection mechanism.
- **Administrar estantes (Task 2).** `/admin/estantes/administrar` lists estante rows (icon · name · "N juegos", batched via new `Shelves.counts_for_shelves/1`) with no chevron and no `/admin/estantes/:id` route (D-19i — the row opens a sheet in place). One name sheet serves both Nuevo estante and Editar, pre-filled and selected, with the hint "Un nombre que se reconozca en el salón." and distinct empty/duplicate errors surfaced inside the sheet (the duplicate error raised from `Shelf`'s existing `unique_constraint(:name)`, never a pre-check query). Ordenar reuses `AdminComponents.reorder_header/1`/`reorder_row/1` verbatim as its second consumer (plan 01.8.2-15 named this screen for exactly that role) — a page-level header swap to "Ordenar estantes" + Listo, tap-reveal ↑/↓ per row, a 10s undoable "Orden guardado" snackbar on Listo. D-09's first run: zero estantes renders one line of purpose and Nuevo estante as the ONLY visible action (Ordenar hidden entirely).
- **Deleting an estante (Task 3).** Eliminar (in the estante's options sheet) opens `AdminComponents.dialog/1` — never an in-sheet confirm — naming the estante and stating the real, currently-displayed copy count. `Shelves.delete_shelf/1` snapshots every copy's `{copy_id, position}` before writing anything, explicitly nilifies both `shelf_id` and `position` (never trusting the FK's `on_delete: :nilify_all` alone — verified directly by a dedicated test that deletes a shelf via bare `Repo.delete/1`), then deletes the estante — all under the per-estante advisory lock, and never deleting a `Copy` row. `Shelves.restore_deleted_shelf/1` is a distinct function (not a loop over `restore_position/3`) that re-inserts the shelf at its former position and writes every snapshotted copy back onto it in one pass — safe by construction, since the freshly-inserted shelf starts with zero copies and can never collide with its own snapshot.
- **The visual harness caught a real defect live.** A first version of Administrar estantes' header (title + actions in one flex row, actions after the title in DOM) broke `test/visual/admin_components.mjs`'s D3 page-rhythm check two ways when run live against a real dev server — fixed by mirroring `estante_live/index.ex`'s own absolute-positioned-actions-before-the-title idiom exactly; both `admin_components.mjs` and `admin_shell.mjs` report **ALL CHECKS PASSED** with both new pages included after the fix (proof the check can both fail and pass, not just pass by construction).
- **CSS reaches the build:** `grep -c "pk-admin-pendientes-queue\|pk-administrar\b\|pk-administrar-header-actions\|pk-administrar-title\|pk-admin-administrar-row__icon" priv/static/assets/css/app.css` → 5, after `mix assets.build`.
