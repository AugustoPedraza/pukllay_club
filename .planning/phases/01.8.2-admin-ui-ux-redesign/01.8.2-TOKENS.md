# 01.8.2 Admin Token Reconciliation (D-34)

> This table is what every later admin UI slice reads from for colour tokens — sketch CSS is
> never transcribed on trust. Values below are either the shipped `assets/css/app.css` token
> verbatim, a measured mapping onto a shipped token, or an explicit, measured new value. Where a
> sketch invented a property this reconciliation discards, the row says so and names why.

## Method

Every `--*` custom property declared inside the 20 in-scope admin sketch `<style>` blocks
(059–065, 069, 070, 071, 072–080 — 066/067/068 excluded, superseded per `01.8.2-CONTEXT.md`
D-08/D-22) plus the shared `.planning/sketches/themes/default.css` it all imports, extracted via:

```
grep -oE -- '--[a-zA-Z0-9-]+\s*:' <sketch>/index.html
```

...then diffed against `assets/css/app.css`'s two `@plugin "daisyui/packages/bundle/daisyui-theme"`
blocks (lines ~356–464) by resolving each side to its concrete hex and comparing. `default.css`'s
own header comment already carries a verified upstream-mapping table (app.css daisyUI variable ->
sketch variable) reused here rather than re-derived from scratch — its own hexes were spot-checked
against the live `app.css` values read directly (not trusted from the comment).

## Fate legend

- **ALREADY REAL** — the sketch property has the *same name* and the *same resolved value* as a
  shipped `app.css` token in both themes. Use the shipped token verbatim; nothing to land.
- **LAND** — genuinely new: no shipped token, under any name, carries this value. Gets a real
  admin-scoped semantic token in Task 2 (`assets/css/admin/tokens.css`).
- **MAP** — the sketch invented its own property *name*, but the resolved *value* already exists
  under a different shipped token name. No new property is landed; admin rules reference the
  shipped token directly (e.g. `var(--color-base-100)`, not a new `--color-bg`).
- **DISCARD** — sketch-local bug or sketch-local convenience alias. Nothing is owed upstream.

## `--val` contrast (D-33)

`--color-primary` resolves to `var(--pk-ramp-600)` (`#7B2DCE`) in dark and `var(--pk-ramp-900)`
(`#3C1269`) in light. `--val` must land on a *different* ramp stop in each theme and must beat
**4.83:1** in dark against the admin page ground (`--color-base-100`).

Measured (WCAG relative-luminance contrast, `--color-base-100` as ground):

| theme | stop chosen | hex | vs. `--color-base-100` | vs. `--color-primary`'s own stop | passes 4.83:1? |
|---|---|---|---|---|---|
| dark | `--pk-ramp-400` | `#B896F3` | `#2E154E` -> **6.52:1** | `--pk-ramp-600` (different stop) | yes — 6.52 ≥ **4.83** |
| light | `--pk-ramp-700` | `#6222A6` | `#FFFFFF` -> 9.14:1 (not the required floor, recorded for completeness) | `--pk-ramp-900` (different stop) | n/a (floor is dark-only per D-33) |

`--pk-ramp-400` in dark also clears 5.86:1 against `--color-surface` (`var(--pk-ramp-900)`) and
5.03:1 against `--color-surface-2` (`var(--pk-ramp-800)`), so the floor holds regardless of which
surface a `--val` row sits on, not only the page ground.

## The "Sin guardar" dot colour

The sketches (`080-admin-guardar-fijo/index.html:913,920`) paint it with `--color-accent-text`,

real `app.css` tokens (lines 388 dark / 452 light).
