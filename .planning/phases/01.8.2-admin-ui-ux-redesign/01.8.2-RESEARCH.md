## Summary

This phase has an unusually complete CONTEXT.md (D-01..D-38, 6 open items, a packaged design-system
skill). There is nothing left to *decide* here — the job of this research is to give the planner an
accurate, current, file:line-cited map of what 01.8.1 actually shipped, so slices can be sized
against real code rather than against the (partially stale) `admin-redesign-scope.md` note CONTEXT
itself says predates sketches 069/071/072-080.

Three findings matter most for planning:

1. **The copies/position model does not exist in any form.** `games.shelf_id` is a nullable
   belongs_to with no position column at all; `shelves.ex` orders games **by name**, not by any
   physical position. This is 100% new schema + new context module work (D-01/D-02/D-05), not a
   migration of an existing partial model.
2. **CONTEXT.md's own code_context section has one stale claim.** It says "`/admin/estantes/:id` is
   the estante detail page" — that route does not exist. The real routes are `/admin/estantes`
   (index, with a `?vista=lista` toggle) and `/admin/estantes/:id/asignar` (the Assign screen, to be
   deleted). There is no per-estante detail page today; D-08's "Estantes / Pendientes / Administrar
   estantes" three-page structure is new routing, not a rename of an existing route.
3. **The `sketch-findings-pukllay_club` skill is NOT stale.** CONTEXT.md's own "Claude's Discretion"
   section (line ~530) says it has "zero mentions of 059–065 today," but that line is itself now
   outdated — the file on disk already carries a full 2026-09-22 packaging of sketches 052–080 (six
   dedicated `references/admin-*.md` files, an admin section in the skill's own table, explicit
   supersession notes). Only `ui-design-system` is genuinely stale (zero mentions of "admin"
   anywhere, and it still mandates filled `btn-primary` / `font-display` headings site-wide,
   contradicting S3 Contorno). The planner's first plan (D-17 + Claude's Discretion) should refresh
   `ui-design-system` only — `sketch-findings-pukllay_club` needs no discovery work, just consumption.

Backend obligations D-35..D-38 were individually verified against current source (see table below):
D-35 already shipped as a separate `/gsd-quick` (confirmed via git log and file diff — `bgg_client.ex`

### The copies/position model — current schema (verified, not the target state)

**There is no copies table, no position column, and no per-copy anything today.** The current model
is exactly what D-01/D-02 are reversing:

`[VERIFIED: lib/pukllay_club/catalog/game.ex:1-9, schema block]` — `Game` schema has
`field :units, :integer` (nullable, no default) and `belongs_to :shelf, PukllayClub.Catalog.Shelf`
(nullable FK). One shelf per game, no position, no copy identity.

`[VERIFIED: lib/pukllay_club/catalog/shelf.ex:1-34]` — `Shelf` schema: `id`, `name` (unique,
max 40 chars), `position` (integer — this is the **shelf's own** walking-order position among
shelves, unrelated to D-01's per-copy left-to-right position within a shelf), `has_many :games`.

`[VERIFIED: lib/pukllay_club/catalog/shelves.ex:169-177]` — `games_on_shelf/1`:
```elixir
def games_on_shelf(shelf_id) do
  from(g in Game,
    where: g.status != :retired and g.shelf_id == ^shelf_id,
    order_by: [asc: g.name, asc: g.id]
  )
  |> Repo.all()
  |> Repo.preload(:shelf)
end
```
Orders by **name**, confirming `admin-redesign-scope.md`'s "load-bearing finding" verbatim.

`[VERIFIED: priv/repo/migrations/20260806234228_create_games.exs:16-40]` — `games.units` has no DB

### Concurrency mechanism — PubSub and locking patterns that already exist

**PubSub:** exactly one topic exists in the whole app today: `"admin:games"`.
`[VERIFIED: lib/pukllay_club/workers/enrich_game_worker.ex:104-105]`:
```elixir
defp broadcast(game_id) do
  Phoenix.PubSub.broadcast(PukllayClub.PubSub, "admin:games", {:game_enriched, game_id})
end
```
`[VERIFIED: lib/pukllay_club_web/live/admin/game_live/index.ex:42]` — the only subscriber:
`Phoenix.PubSub.subscribe(PukllayClub.PubSub, "admin:games")`, called conditionally on
`connected?(socket)` inside `mount/3`. This is the idiomatic pattern D-11 should extend for
Estantes/Pendientes/Administrar-estantes live updates (e.g. a topic per estante, or one
`"admin:estantes"` topic broadcasting `{:estante_updated, id}` / `{:copy_moved, ...}` tuples,
handled via `handle_info/2` the same way `GameLive.Index` already does). No existing code
demonstrates a per-entity topic (only one flat topic name exists) — the planner should decide topic
granularity as part of slicing, informed by D-11's requirement that "every open Estantes page,
Pendientes page and Administrar estantes page updates live."

**Locking:** Postgres advisory locks are already an established pattern, not a new concept for this
codebase. `[VERIFIED: lib/pukllay_club/catalog.ex:254-259, 319]`:
```elixir
# T-01.8.1-73: the first key of the two-int4 pg_advisory_xact_lock(int,
# int) form (distinct from the single-bigint form Postgres also
# supports — the two forms live in separate advisory-lock key spaces,
# objsubid 2 vs 1 in pg_locks, so this namespace can never collide
# with a future single-bigint advisory lock elsewhere in this app).
@bgg_id_lock_namespace 8_811_015
...
repo.query!("SELECT pg_advisory_xact_lock($1, $2)", [@bgg_id_lock_namespace, bgg_id_int])
```
This is inside `Repo.transaction/1`, released automatically at transaction end (`_xact_lock`, not a
session-level lock needing explicit unlock). D-11 references this exact pattern ("as plan 01.8.1-15
did per BGG id"). **The planner must pick a new, non-colliding namespace constant** for the
per-estante lock (e.g. a module attribute in `Shelves`, distinct integer from `8_811_015`) and lock
on the estante id, not the copy id, since D-11 says "position writes are serialized per estante."
No `Ecto.Changeset.optimistic_lock`/`lock_version` pattern exists anywhere in this codebase — the
project's own established idiom for this exact problem shape (per-BGG-id serialization) is the
two-int4 advisory lock, not optimistic locking. Recommend following that precedent for consistency
rather than introducing a second concurrency-control idiom.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Per-estante write serialization | A new locking primitive (row-level `SELECT ... FOR UPDATE`, a mutex table, an Oban unique job) | `pg_advisory_xact_tail_lock(int, int)` inside `Repo.transaction/1`, exactly as `catalog.ex:319`'s existing per-BGG-id lock already does | The codebase has one established, tested idiom for "serialize concurrent writes to one logical entity" — reusing it keeps the mental model (and the `pg_locks` namespace convention) consistent, and avoids introducing optimistic-locking as a second, unprecedented concurrency idiom |
| Live updates across open Estantes/Pendientes/Administrar pages | Polling, a custom WebSocket channel, client-side refresh timers | `Phoenix.PubSub.broadcast/3` + `handle_info/2`, exactly as `enrich_game_worker.ex`/`GameLive.Index` already do for `"admin:games"` | One existing, working pattern in the codebase; a second live-update mechanism would be unjustified complexity |
| Bottom sheets, dialogs, drawers, tab bar | A JS component library, a new hex dependency (e.g. an Alpine/Stimulus sheet library) | Server-rendered `Phoenix.Component`s + the existing colocated-hook pattern (`carousel_row.ex`'s `.pk-rail` hook is the established precedent for "a component that needs a small client-side behavior") | This is a Phoenix/LiveView/daisyUI app by fixed project constraint (CLAUDE.md); no client framework is available, and the existing carousel hook proves the colocated-hook pattern already handles this class of problem |

**Key insight:** Every "don't hand-roll" item here is really "don't invent a second idiom for a
problem this codebase has already solved once" — the phase's own precedents (BGG-id advisory lock,
`admin:games` PubSub topic, `carousel_row.ex`'s colocated hook) are the load-bearing prior art, not
external libraries.
