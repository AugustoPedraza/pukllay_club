### CR-01 / WR-01: `place_copy/3`, `remove_copy_from_shelf/1`, `delete_copy/1` read the mover's position before the lock, and `place_copy/3` discarded the pre-write location it verified

**Files modified:** `lib/pukllay_club/catalog/shelves.ex`,
`test/pukllay_club/catalog/shelves_test.exs`,
`lib/pukllay_club_web/live/admin/estante_live/index.ex`,
`lib/pukllay_club_web/live/admin/game_live/form.ex`

**Commits:**
- `11b849c9` — CR-01/WR-01: re-fetch the copy inside the advisory lock in `place_copy/3`,
  `remove_copy_from_shelf/1`, and `delete_copy/1`'s placed clause (never write against the
  unlocked pre-lock read); `place_copy/3` now returns
  `{:ok, %{moved:, previous_shelf_id:, previous_position:}}` built from that same
  lock-verified read; `restore_position/3` unwraps the new shape so its own
  `{:ok, Copy.t()}` contract is unaffected.
- `9fc314d3` — WR-01 caller wiring: `GameLive.Form.commit_shelf_sheet/3` and
  `EstanteLive.Index.commit_placement/4` now build their Deshacer `undo_snapshot` from
  `place_copy/3`'s own returned `previous_shelf_id`/`previous_position`, not from a copy
  struct captured whenever the placement sheet opened.

**Applied fix:** matches the review's suggested fix closely — re-read under the lock,
never the pre-lock unlocked snapshot; the return-shape change was implemented as a
`{:ok, %{...}}` map (one of the two shapes the review explicitly offered) rather than a
3-tuple, specifically to keep `place_copy/3`'s return arity compatible with every existing
`{:ok, _}`-shaped test call site across the suite (~90 occurrences) — only call sites that
destructured the actual `Copy` struct needed updating (4 in `shelves_test.exs`, both
LiveView callers).

**Verification:** added a new concurrency regression test
(`test/pukllay_club/catalog/shelves_test.exs`, "N-way race on ALREADY-PLACED copies")
that races copies with a REAL, non-nil `shelf_id`/`position` each — the exact branch the
review flagged the existing concurrency test as never reaching (it only raced copies
starting `shelf_id: nil`, hitting `vacate/2`'s no-op clause). Confirmed this new test
reproduces the `unique_violation` crash against the pre-fix code (4/5 runs) and passes
reliably (5/5 runs) against the fix. Also confirmed the two WR-01 caller-side regression
scenarios (a malformed `donde-va-commit` index, and the general Deshacer flow) directly by

### WR-05: `restore_deleted_shelf/1` could silently rip a copy away from a shelf it was placed on after the delete

**Files modified:** `lib/pukllay_club/catalog/shelves.ex`,
`test/pukllay_club/catalog/shelves_test.exs`

**Commit:** `4afdc39b`

**Applied fix:** matches the review's suggested fix — locks the destination shelf plus
every currently-distinct live `shelf_id` among the snapshotted copies (mirroring
`lock_estantes/2`'s convention), re-reads each copy's live `shelf_id` under that lock,
and only restores a copy whose live `shelf_id` is still `nil` (i.e., untouched since the
delete) — skipping (never clobbering) a copy a different staff member independently
placed elsewhere in the interim.

**Verification:** added a regression test that places a copy on a different, real shelf
between `delete_shelf/1` and `restore_deleted_shelf/1`. Confirmed the pre-fix code
clobbers it back (`shelf_id` assertion fails, `794 != 793`-shaped mismatch), and the fix
leaves it exactly where the other staff member put it while still restoring the
untouched copy normally.
