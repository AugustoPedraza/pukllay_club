# Phase 01.7 Plan 02: Session Cookie Secure Flag & HSTS Verification Summary

**Env-gated `secure:` session cookie flag with a `session_options/0` assertable accessor, plus a live-confirmed HSTS header requiring no config change.**

## Performance

- **Duration:** ~15 min
- **Tasks:** 3
- **Files modified:** 3 (1 endpoint edit, 1 new test file, 1 new/extended audit doc)
- **Commits:** 3

## Accomplishments

- Session cookie now carries `secure: Mix.env() == :prod` on `@session_options` in
  `lib/pukllay_club_web/endpoint.ex`, propagating automatically to `Plug.Session` and to both the
  websocket and longpoll LiveView `connect_info` through the single shared attribute — no second
  edit site needed.
- Added `session_options/0` (`@doc false`, `@spec`) so the compiled value is mechanically
  assertable from a test process instead of resting on reading source code.
- Added `test/pukllay_club_web/session_cookie_test.exs` (TDD: written first, watched RED against
  the unmodified endpoint — both `session_options/0`-dependent assertions raised
  `UndefinedFunctionError` before the endpoint change) asserting `secure: false` under test env,
  `store`/`same_site`/`key` unchanged, and that the test-env `Set-Cookie` for `_pukllay_club_key`
  carries no `Secure` attribute.
- Live-verified via `MIX_ENV=prod mix run` that the compiled production `session_options/0`
  returns `secure: true`.
- Live-verified `https://pukllay.club/`'s `Strict-Transport-Security: max-age=31536000` header is
  already correctly emitted by `Plug.SSL`'s `force_ssl` defaults — made **no** change to
  `config/prod.exs`, avoiding a redundant/conflicting hand-rolled header plug.
- Confirmed `force_ssl`'s `/up` health-probe exclusion is still declared exactly once in
  non-comment config and the live probe still returns 200 — future deploys' health checks remain
  safe.
- Recorded a named post-deploy verification item (the live `Secure`-cookie check, plus a local
  plain-HTTP session sanity check, Safari specifically called out) in
  `01.7-TRANSPORT-AUDIT.md`, since this compile-time change is only observable in production after
  a deploy this plan's execution does not trigger.

## Decisions Made

- `secure:` gated on the compile-time `Mix.env() == :prod` comparison (matching the file's existing `Tidewave` block idiom), never a runtime env-var read — `@session_options` is a module attribute evaluated once at compile time, and a bare `true` would break Safari-on-localhost dev/CSRF continuity (Safari does not exempt localhost from the Secure-requires-HTTPS rule).
- `config/prod.exs` left untouched for SEC-02 — the live response already carries the correct year-scale HSTS `max-age` via `Plug.SSL`'s own defaults, and RESEARCH.md's Pitfall 2 explicitly warns against adding a redundant/possibly-weaker custom header plug.
- Recorded (did not "fix") a surprising discovery: the live cookie already showed `secure` before this change, because `Plug.Conn`'s `maybe_secure_cookie/2` defaults `:secure` to `true` whenever `conn.scheme == :https` and no explicit `:secure` key is present. This is documented in `01.7-TRANSPORT-AUDIT.md` rather than treated as evidence the task was unnecessary — the point of `session_options/0` is to make the guarantee explicit and tested instead of resting on an unstated library default.
