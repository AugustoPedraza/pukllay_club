# Phase 01.7: Production Catalog Data & Security Hardening (INSERTED) - Context

**Gathered:** 2026-09-11
**Status:** Ready for planning

<domain>
## Phase Boundary

Two independent capabilities, both backend/infra/ops work with no new UI:

1. **Production catalog data:** get the live, currently-empty production database populated with
   the real ~400+ game catalog (BGG stats, Spanish descriptions, images, artists — matching what
   dev already has), plus a documented, repeatable path to re-seed production later.
2. **Security hardening:** secure session cookie, verified HSTS, a directive-by-directive CSP
   audit (must not break the Google Maps `frame-src` or Tailwind's `style-src 'unsafe-inline'`),
   a confirmed LiveView websocket-connect CSRF flow, and a one-time full-git-history secrets sweep
   with every hit explicitly triaged.

Covers requirements SEED-01, SEED-02, SEC-01, SEC-02, SEC-03, SEC-04, AUDIT-01, AUDIT-02.
CSP nonce infrastructure for JSON-LD (SEC-05) is explicitly **out of scope** here — it's mapped to
Phase 01.8, which depends on this phase leaving the nonce path open (not blocked, not implemented).

</domain>

<decisions>
## Implementation Decisions

### Initial data population (SEED-01)
- **D-01:** Populate production's `games` table via `pg_dump`/restore from the developer's local
  dev database, not by re-running the seed pipeline (BGG fetch + Gemini translation + R2 upload)
  against production from scratch. Zero BGG rate-limit or Gemini quota spend; guarantees production
  ends up byte-identical to what's already validated in dev, instead of re-derived data that could
  drift (a fresh BGG re-fetch or a fresh Gemini translation pass can legitimately produce different
  values than what's already live in dev today).
- **D-02:** Confirmed: dev and production share the same R2 bucket
  (`https://pub-8f053d9e82db4d8eb43b5666a37546c4.r2.dev`) — image URLs stored in dev's `games` rows
  resolve correctly in production with no image re-upload or URL rewrite needed.
- **D-03:** Dump/restore scope is the `games` table only — not a full database dump. Smallest safe
  surface; no migration/schema state or unrelated tables cross environments. The transport is the
  same SSH tunnel to `127.0.0.1:5432` on the production host used for D-04 below (the DB accessory
  port is bound to localhost only, per `config/deploy.yml`'s D-15 decision — never expose it
  publicly).

### Repeatable re-seed path (SEED-02)
- **D-04:** Future re-seeds (e.g., when new games are added to `ludoteca.csv`) run via a manual SSH
  tunnel from a developer's laptop (`ssh -L 5432:localhost:5432 deploy@<host>`), then `mix
  catalog.seed` (and whichever companion tasks are needed) run locally against the tunneled
  `DATABASE_URL`, using the developer's existing `config/dev.secret.exs` BGG/R2 credentials. No new
  CI infrastructure. This is consistent with the project's standing decision that BGG/R2 seed
  credentials never touch the production host or get wired through Kamal (01-01 Key Decision).
  Considered and rejected for now: a `workflow_dispatch` GitHub Actions workflow modeled on
  `backup.yml`'s SSH pattern — more setup (new GH secrets, CI Elixir toolchain) for a capability
  that isn't needed yet at this project's cadence.
- **D-05:** The documented runbook for both the one-time dump/restore (D-01/D-03) and future
  re-seed runs (D-04) lives in `AGENTS.md` — the existing home for agent/dev operational
  conventions per project constraints.

### Secrets sweep (AUDIT-01, AUDIT-02)
- **D-06:** Use Gitleaks alone for the one-time full-git-history sweep, not Gitleaks + TruffleHog.
  Per `research/PITFALLS.md`, Gitleaks alone is sufficient for a careful solo-dev one-off sweep;
  TruffleHog's added live-credential verification isn't needed for this pass.
- **D-07:** If the sweep turns up a real, still-live secret: rotate/revoke it immediately and
  document the finding + rotation in the audit record (AUDIT-02). Do **not** rewrite git history
  (BFG/`git filter-repo`) to scrub it — the repo is already public (D-19), so the exposure horizon
  for anyone who already cloned it doesn't change once the credential is rotated, and a history
  rewrite's disruption (force-push, every fork/clone needs to re-sync) isn't worth it for that
  marginal benefit. — **Reversibility:** costly — if this default is revisited later (i.e., the
  team decides retroactively that a rewrite is needed after all), it means force-pushing a rewritten
  history to a now-longer-lived public repo, which is a bigger blast radius the longer it's
  deferred.

### CSP tightening boundary (SEC-03)
- **D-08:** This phase's CSP pass is audit-and-confirm only — verify the existing policy is sound
  directive-by-directive, and only change something that's actually wrong or missing. No
  speculative tightening of directives like `connect-src 'self' ws: wss:` or `base-uri`/`form-action`
  without a concrete reason. `style-src 'unsafe-inline'` (Tailwind/daisyUI) and the single
  third-party `frame-src` (`ClubLinks.maps_embed_origin/0`, the About page's Maps embed) are
  confirmed off-limits — do not remove or narrow either.

</decisions>
