<objective>
Close the two transport-security gaps: mark the session cookie `Secure` in production without
breaking local HTTP development, and verify against the live site that HSTS is already correctly
emitted rather than adding a redundant header.

Purpose: the repo is public and the site's link is being passed around. A session cookie with no
`Secure` attribute is a cookie a downgrade attack can read; HSTS is what prevents the first-visit
downgrade in the first place. Both are ASVS V3/V9 baseline controls.

Output: an env-gated `secure:` session option with a mechanically assertable accessor, a new ExUnit
gate, and a recorded live observation of the production HSTS header and the `/up` probe.
</objective>

    - Under `MIX_ENV=prod`, `PukllayClubWeb.Endpoint.session_options()` returns a keyword list whose `:secure` value is `true`.
    - Under `MIX_ENV=test`, the same call returns `:secure` as `false`.
    - A plain `get(conn, ~p"/")` in the test environment emits a `set-cookie` header for `_pukllay_club_key` that a browser will accept over plain HTTP.

  </behavior>
  <action>
    Add `secure: Mix.env() == :prod` as a new key on `@session_options` in
    `lib/pukllay_club_web/endpoint.ex`, per RESEARCH.md Pattern 3 and PATTERNS.md's required change.
    It must be the compile-time `Mix.env()` comparison, not a bare `true` and not a runtime env-var
    read: `@session_options` is a module attribute evaluated once at compile time, and an
    unconditional flag would break session and CSRF continuity for a developer testing locally in
    Safari, which does not exempt localhost from the Secure-requires-HTTPS rule. The file already
    uses a `Mix.env()` comparison at its `Tidewave` block, so this is an established idiom here.

    Do not add a second edit site. The same `@session_options` attribute is already passed to both
    the `socket "/live", ...` declaration's websocket and longpoll `connect_info` and to
    `plug Plug.Session`, so the new key reaches the LiveView session automatically.

    Add a read-only accessor `session_options/0` returning `@session_options`, carrying `@doc false`
    and a `@spec`. Without it the compiled production value cannot be asserted from any test process,
    and SEC-01 would rest on reading the source rather than on observing the compiled result. Keep it
    read-only — no setter, no option merging.

    Write `test/pukllay_club_web/session_cookie_test.exs` following the `Phoenix.ConnTest`
    response-header shape PATTERNS.md extracts from the existing CSP describe block in

    Write the test first and watch it go red against the unmodified endpoint, then add the endpoint
    change. Assert the behaviours listed above. For the test-environment cookie assertion, match
    case-insensitively on the attribute list of the `_pukllay_club_key` cookie specifically rather
    than on the whole header blob, so an unrelated cookie cannot satisfy or break the assertion.

<deliberate_exclusions>
- **`includeSubDomains` and `preload` are not being added to HSTS.** `preload` is a browser-vendor
  list submission: once a domain is on it, removal is slow and outside this project's control, which
  makes it a one-way door for a single-site hobby domain. `Plug.SSL`'s default year-scale `max-age`
  without either modifier is the ASVS L1-sufficient control. Recorded as an accepted threat
  (`T-01.7-07`) rather than silently omitted.
</deliberate_exclusions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → kamal-proxy | TLS terminates here; anything the browser was tricked into sending over plain HTTP never reaches the app encrypted |
| kamal-proxy → Phoenix endpoint | Plain HTTP inside the Docker network; `x_forwarded_proto` is what force_ssl reads, and the health probe deliberately does not set it |
| Phoenix endpoint → browser cookie jar | The session cookie's attribute list is set server-side and enforced client-side |
