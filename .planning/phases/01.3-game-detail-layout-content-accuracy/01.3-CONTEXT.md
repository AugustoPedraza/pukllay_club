# Phase 01.3: Game Detail Layout & Content Accuracy - Context

**Gathered:** 2026-08-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Improve the game detail page (`CatalogLive.Show`, `/juegos/:id`) on two fronts: **content
accuracy** (the game data shown is missing, wrong-language, or incomplete relative to what's
actually available) and **visual layout/hierarchy** of the reading column. This phase does **not**
re-litigate the masthead/buy-box/spacing/lightbox mechanics Phase 01.2 already closed across 10+
UAT rounds — it picks up where that phase left off: what's still rough about what the page *says*
and how the reading column beneath the masthead *reads*.

No new requirement IDs are introduced. This phase refines SHELL-03 (detail page buy-box/reading
column/Juegos similares) as already defined in REQUIREMENTS.md, without changing its acceptance
criteria.

</domain>

<decisions>
## Implementation Decisions

### Description Language & Quality
- **D-01:** The `description` field is currently raw English text pulled straight from BGG's XML
  API (`bgg_client.ex:113` → `catalog.seed.ex:267`), with zero translation and zero cleanup, despite
  the product being Spanish-first (per `CLAUDE.md`/`ideas.txt`: "the details of the game must to be
  on spanish"). Produce a Spanish description via a **one-off LLM translation**, kept simple: a Mix
  task calls an LLM once per game and stores the Spanish result. This is a seed-time/enrichment-time
  job, not a runtime call — consistent with PROJECT.md's "never an LLM call on the request hot path"
  principle. It is a small, deliberate pull-forward of Phase 2's LLM integration, scoped to a
  one-shot batch translation, not the NL-search feature itself.
  — **Reversibility:** reversible — re-running the translation task or reverting to the raw English
  column value doesn't touch schema or other code paths.
- **D-02:** BGG's raw description text also carries markup noise (literal `&#10;` line-break
  entities, `[b]`/`[i]` BBCode-style tags). Clean this up **at seed/enrichment time**, not at render
  time — store already-clean text, following the same seed-time normalization convention already
  established by `hashtag_normalizer.ex`.

### Reading-Column Layout & Hierarchy
- **D-03:** The current reading-column section order — Título → Descripción → Mecánicas chips →
  Temáticas chips → Ficha técnica (spec grid) → Juegos similares shelf — **stays the same**. The
  problem is not ordering; it's that the sections lack visual distinction (each currently reads as
  one continuous flat block of text/chips rather than a page with clear hierarchy). This also
  applies to the general density/polish of the page — even after Phase 01.2's spacing fixes, the
  page as a whole still reads as too plain/packed for a casual browsing member.
- **D-04:** The visual redesign to fix D-03 is **routed through `/gsd-ui-phase`**, not decided blind
  during `/gsd-plan-phase` — mirroring how Phase 01.2 handled its own open-ended visual call (D-07,
  the buy-box redesign). This discussion captures the WHAT (section order stays, needs stronger
  visual grouping/hierarchy, plus the new content described below); `/gsd-ui-phase` captures the
  visual HOW.

### Illustrator/Artist Credit
- **D-05:** BGG artist data is **not actually missing** — `BggClient` already extracts it
  (`artists: ~x".//link[@type='boardgameartist']/@value"sl`) and the full parsed item, including
  artists, is stored in the `bgg_payload` map column for every enriched game (`catalog.seed.ex:273`,
  `bgg_payload: item`). It was just never promoted to a real column or rendered — Phase 01.2's D-04
  correctly dropped the old "Ilustrador: No disponible" placeholder row because at the time no such
  field existed on `Game`. **Add a real `artists` field now**, backfilled from the existing
  `bgg_payload` (no BGG re-fetch needed), and render it in Ficha técnica.
  — **Reversibility:** reversible — additive column + backfill from data already on hand.

### BGG Advanced Stats (Weight / Rating / Rank)
- **D-06:** Show three BGG stats as "advanced" info, each linking out to the game's BGG page,
  labeled in the "Peso BGG" style:
  - **Peso BGG (weight):** `bgg_weight` is already a stored `:float` column on `Game` (currently
    only consumed internally to derive `weight_band` — never shown as a raw number). Surface it
    directly (e.g. "3.2/5").
  - **Valoración (rating):** NOT currently extracted from BGG at all — `BggClient`'s XPath map
    (`bgg_client.ex`) only pulls `averageweight`, not the average user rating. Requires a new
    extraction (`.//statistics/ratings/average/@value` or equivalent) added to `BggClient`.
  - **Ranking general (rank):** Also NOT currently extracted — requires a new extraction
    (`.//statistics/ratings/ranks/rank[@type='...']/@value` or equivalent).
  User confirmed: **ship all three together in this phase**, including the BggClient extension and
  a full re-enrichment run against BGG's API for all ~400 games (not deferring rating/rank to a
  follow-up). Placement/grouping/labeling of this "advanced" block is **folded into the same
  `/gsd-ui-phase` pass as D-04** — the UI phase decides exact visual treatment (e.g. an "Avanzado"
  sub-block), this discussion only locks in that all three ship and link out to BGG.
  — **Reversibility:** costly — the rating/rank extraction requires a full re-enrichment pass
  against BGG's live API for ~400 games (rate-limited, not instant); reverting after shipping means
  either leaving the columns populated-but-unused or a second pass to null them out.

### Claude's Discretion
- Exact LLM/provider choice and prompt for the one-off Spanish translation task (D-01) — keep it
  simple, matching the user's explicit "keep it simple" guidance.
- Exact BGG markup cleanup implementation (entity decoding, BBCode stripping) (D-02).
- Exact `artists` schema/migration shape and backfill mechanism from `bgg_payload` (D-05).
- Exact BggClient XPath additions for rating and rank, and how the re-enrichment run is invoked/
  batched against BGG's rate limits (D-06).
- Click-through target for the three advanced BGG stats — default assumption is the same pattern
  as the existing "Ver ficha completa en BoardGameGeek" link (`https://boardgamegeek.com/boardgame/
  {bgg_id}`), not a stat-specific deep link, unless `/gsd-ui-phase` or planning surfaces a reason to
  differ.
- Full visual treatment of the reading-column hierarchy and the "advanced" BGG stats block — both
  explicitly deferred to `/gsd-ui-phase` (D-04, D-06).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `hashtag_normalizer.ex` — seed-time text normalization pattern; D-02's BGG description cleanup
  should follow the same convention rather than inventing a new one.
- `bgg_payload` (map column, already populated for every enriched game) — D-05's artist data is
  already sitting in this column for every game that has gone through enrichment; no BGG re-fetch
  needed for that specific fix.

### Established Patterns
- Ficha técnica renders as a 2-column `<dl>` spec grid (`pk-spec-list`/`pk-spec-row`/`pk-spec-row--
  wide`), each row conditionally rendered on real data being present (`:if={@game.field}` /
  `:if={@game.field != []}`) — "ground every field in the real schema, including its gaps" per
  the sketch-findings design doc. New fields (artists, weight, rating, rank) should follow this same
  conditional-render convention.
- BGG-sourced fields flow: `BggClient` XPath extraction → `catalog.seed.ex`'s enrichment pipeline →
  `Game` schema column, with the full raw parsed item additionally retained in `bgg_payload` — any
  new field (artists, rating, rank) either reads from the existing `bgg_payload` (no re-fetch) or
  needs the extraction map extended and enrichment re-run (rating, rank).

### Integration Points
- D-01/D-02 (description) are scoped to the seed/enrichment pipeline (`catalog.seed.ex`,
  `bgg_client.ex`) plus a one-off Mix task for translation — no LiveView changes beyond what already
  renders `@game.description`.
- D-05 (artists) needs a schema migration (new column) + a backfill task reading `bgg_payload`, plus
  one new conditional row in `show.ex`'s Ficha técnica block.
- D-06 (weight/rating/rank) needs `BggClient` XPath additions for rating/rank, a schema migration for
  the two new columns, a full re-enrichment run against BGG's API, plus new UI (deferred to
  `/gsd-ui-phase` for exact placement).
- D-03/D-04 (reading-column visual hierarchy) is scoped to `show.ex`'s template + `app.css` — no
  schema/context changes, pure presentation.
