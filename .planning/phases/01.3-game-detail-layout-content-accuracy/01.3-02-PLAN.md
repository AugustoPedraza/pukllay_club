<objective>
Populate the three columns 01.3-01 created, against the real catalog.

This plan writes no application code. It runs the two offline jobs and proves, with SQL against the
dev database, that the data landed and that nothing else moved. That distinction matters:
`01.3-CONTEXT.md` rates D-06 **costly** to reverse precisely because populating rating and rank
requires a live pass against BGG's API for every one of the roughly 393 games carrying a BGG id, and
reverting afterwards means either leaving the columns populated-but-unused or running a second pass
to null them out. That is a door worth pausing at, so the live pass sits behind a decision
checkpoint.

The artists backfill runs first and unconditionally: it touches no network, cannot be rate-limited,
and reads data the database already holds in `bgg_payload` — exactly the mechanism D-05 specified.
Running it first means the Ilustradores row shipped by 01.3-05 has correct data even if the BGG pass
is deferred.

Purpose: give 01.3-05's rendered rows something true to display, and give the end-of-phase UAT a
real catalog to look at rather than fixtures.
Output: populated `artists`, `bgg_weight`, `bgg_rating` and `bgg_rank` columns, plus a committed run
record naming every gap.
</objective>

  <context>
    `01.3-CONTEXT.md` rates D-06 **costly** to reverse. Populating `bgg_rating` and `bgg_rank`
    requires a live pass against BoardGameGeek's XML API for every game carrying a BGG id — 393 rows
    as of 2026-08-29, batched 20 at a time with a 1500 ms delay between batches, so roughly 30
    seconds of live traffic and 20 authenticated requests. The pass also refreshes each game's
    `bgg_payload`, which is what plan 01.3-04's Spanish translation later reads as its pristine
    English source.

    Undoing it is not free: reverting after the fact means either leaving the two columns populated
    but unrendered, or running a second pass to null them out. Nothing about the run is destructive
    to club-side data — the job writes a narrow five-field changeset and cannot reach cover images,
    descriptions, names or `csv_row` — but it does spend real third-party API budget and rewrites
    `bgg_payload` for the whole catalog.

    Deferring is a real option: `bgg_weight` is already populated from the original seed, so Peso BGG
    would still render; only Valoración BGG and Ranking BGG would stay hidden until the pass runs.
    The per-field render guards shipped in 01.3-01 and 01.3-05 handle "not fetched yet" and "BGG
    never had this" identically, so a deferred run degrades cleanly rather than breaking anything.
  </context>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01.3-08 | Denial of Service | BGG rate limiting mid-run | medium | mitigate | Batching at 20 ids per request with a 1500 ms inter-batch delay plus `fetch_batch/2`'s existing 429 and 5xx exponential backoff; a rate-limited run degrades to null columns that the render guards already hide, and the run record names every failed batch for a targeted re-run. |
