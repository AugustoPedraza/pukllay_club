# Phase 01.3: Code Review Report

**Reviewed:** 2026-08-30
**Depth:** standard
**Files Reviewed:** 25 (+1 fixture)
**Status:** issues_found

## Summary

This phase adds real BGG stats/artists enrichment (`StatsEnricher`, `BggClient` extensions), a
one-off Gemini-backed Spanish description translation job (`DescriptionTranslator`,
`TranslatedDescription`), an HTML-entity normalizer, two new one-off Mix tasks, a migration adding
`games.artists`/`bgg_rating`/`bgg_rank`, and a `catalog_live/show.ex` template rework that groups
the reading column into `.pk-reading-section` wrappers and adds an "Avanzado" BGG-stats sub-group.

Actual diff scope (via `git diff a04e239^..HEAD`) is much narrower than the full file list: most of
`app.css` and `catalog_show_test.exs` predate this phase — only ~34 CSS lines, ~235 `show.ex`
lines, the migration, `mix.exs`/`mix.lock`, and the six brand-new `Catalog.Seed.*` modules (plus
their tests) are actually new/changed work.

No secrets, injection vectors, or crashes were found in the reachable code paths. XXE is correctly
disabled (`dtd: :none`, tested against a hostile payload), credentials are never logged unredacted,
and every DB write goes through a narrow, explicit `cast/3` allowlist. The issues found are
correctness/robustness gaps around dry-run reporting fidelity in the two new Mix tasks, an
incomplete render guard in `show.ex` that currently happens to be masked by an unenforced data
invariant, and a missing bound check on a public batch-size option.

## Warnings

### WR-01: Dry-run mode in the two new Mix tasks silently reports counts as if real writes happened

**File:** `lib/mix/tasks/catalog.enrich_bgg_stats.ex:49-53`, `lib/mix/tasks/catalog.backfill_artists.ex:29-32`
**Also:** `lib/pukllay_club/catalog/seed/stats_enricher.ex:124-135` (`apply_item/4`), `:151-167` (`apply_artists_backfill/3`)

**Issue:** In `StatsEnricher.apply_item/4` and `apply_artists_backfill/3`, the `:updated` (and
`:scanned`/`:deduplicated`) summary counters are incremented unconditionally, regardless of
`dry_run?`:

```elixir
{:ok, item} ->
  if !dry_run?, do: update_game_stats(game, item)
  acc = %{acc | updated: acc.updated + 1}   # incremented even when nothing was written
  ...
```

Both consuming Mix tasks then print this counter with no qualification at all:

```elixir
Mix.shell().info(
  "BGG stats enrichment complete: #{summary.updated}/#{summary.candidates} updated, " <> ...
)
```

and the persisted Markdown reports (`bgg_stats_enrichment_report.md`,
`priv/repo/seed_data/bgg_stats_enrichment_report.md:65-90`) also render `Updated: #{summary.updated}`
with zero "DRY RUN" marker anywhere in the file. A developer who runs `mix catalog.enrich_bgg_stats
--dry-run` sees "BGG stats enrichment complete: 385/393 updated" and a report file that reads
identically to a real run — nothing distinguishes a preview from an executed run. This directly
contradicts the sibling `mix catalog.seed --dry-run` path, which explicitly prefixes every dry-run
line with `"[dry-run] ..."` (`lib/mix/tasks/catalog.seed.ex:227-231`).

The test suite doesn't catch this either: `stats_enricher_test.exs`'s `dry_run: true` test
(`test/pukllay_club/catalog/seed/stats_enricher_test.exs:111-129`) never asserts on
`summary.updated`, and `backfill_artists_from_payload/1` has no dry-run test at all.

**Fix:** Either don't increment `:updated`/`:deduplicated`/`:scanned` writes-only counters during a
dry run (rename to `:would_update` if the preview count is still wanted), or thread `dry_run?`
through into both the console message and the report template so they visibly read
`"[DRY RUN] ..."`, mirroring `catalog.seed.ex`'s existing convention.

### WR-02: `ficha_tecnica?/1` was not extended to cover the new `artists`/advanced-stats fields

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:1184-1189`

**Issue:** `ficha_tecnica?/1` gates the entire "Ficha técnica" `.pk-reading-section` wrapper — the
`<dl>` containing Edad mínima, Año, Diseñadores, **and now also Ilustradores + the Avanzado
sub-group** — but was left unchanged for this phase:

```elixir
defp ficha_tecnica?(game) do
  not is_nil(game.min_age) or
    not is_nil(game.year_published) or
    game.designers != [] or
    not is_nil(game.bgg_id)
end
```

`advanced_stats?/1` (added right below it, line 1197) explicitly documents relying on an
*unenforced* invariant instead: "any game that can carry a weight, rating or rank necessarily
carries a bgg_id (BGG enrichment is keyed on it)." That invariant holds for every current write path
(`StatsEnricher`, `catalog.seed.ex`) but is not enforced by any changeset validation — nothing stops
a future write path (a manual `Repo.update!`, an admin UI, a data-fix script) from setting
`artists` or `bgg_weight`/`bgg_rating`/`bgg_rank` on a game whose `bgg_id` is `nil`. If that ever
happens, the entire Ficha técnica section — including the already-populated Ilustradores/Avanzado
data — silently never renders, with no test covering that combination (all of
`catalog_show_test.exs`'s new D-05/D-06 tests set `bgg_id` alongside `artists`/`bgg_weight`, never
one without the other).

**Fix:** Widen the guard to match the data it actually gates:

```elixir
defp ficha_tecnica?(game) do
  not is_nil(game.min_age) or
    not is_nil(game.year_published) or
    game.designers != [] or
    game.artists != [] or
    not is_nil(game.bgg_id)
end
```

(`advanced_stats?/1`'s three fields are already covered transitively once `bgg_id` is checked, per
its own comment, but `artists` is not currently in that or-chain at all.)

### WR-03: `StatsEnricher.enrich_from_bgg/2`'s public `:batch_size` option has no upper-bound check against `BggClient`'s hard cap

**File:** `lib/pukllay_club/catalog/seed/stats_enricher.ex:43,56` ; `lib/pukllay_club/catalog/seed/bgg_client.ex:33`

**Issue:** `BggClient.fetch_batch/2` has a hard function-clause guard: `when length(bgg_ids) <=
@max_batch_size` (20). If it fails, the call raises `FunctionClauseError` — no graceful `{:error,
_}`. `StatsEnricher.enrich_from_bgg/2` accepts and documents a public `:batch_size` option
(default 20, matching the cap) with no validation:

```elixir
batch_size = Keyword.get(opts, :batch_size, @default_batch_size)
...
games |> Enum.chunk_every(batch_size) |> ...
```

Calling `StatsEnricher.enrich_from_bgg(credentials, batch_size: 25)` (a legal call per the
function's own `@doc`) crashes the whole enrichment run with an unhandled exception instead of
being caught by the module's own "a single bad batch never aborts the run" contract. Not reachable
today via `mix catalog.enrich_bgg_stats` (no `--batch-size` CLI flag is exposed), but it is a public
module API with a documented option, so this is a latent trap for the next caller (e.g. an IEx
session or a future CLI flag).

**Fix:** Clamp or validate `batch_size` against `BggClient`'s cap, e.g.:

```elixir
batch_size = min(Keyword.get(opts, :batch_size, @default_batch_size), BggClient.max_batch_size())
```

(exposing `@max_batch_size` from `BggClient` as a `max_batch_size/0` accessor, mirroring how
`dedup_artists/1` is already exposed for cross-module reuse).

## Info

### IN-01: BGG's 20-id batch cap is duplicated as an independent magic number in three places

**File:** `lib/pukllay_club/catalog/seed/bgg_client.ex:21` (`@max_batch_size 20`),
`lib/mix/tasks/catalog.seed.ex:38` (`@batch_size 20`),
`lib/pukllay_club/catalog/seed/stats_enricher.ex:33` (`@default_batch_size 20`)

**Issue:** The same externally-imposed constant (BGG's practical batch limit) is hand-copied into
three separate module attributes with no shared source of truth. If BGG's limit ever changes, only
one of the three is guaranteed to be updated (`bgg_client.ex`'s own guard), silently leaving the
other two's *intended* alignment stale (though no crash results from `catalog.seed.ex`/
`stats_enricher.ex` choosing a smaller number than the real cap — only a larger one, per WR-03).

**Fix:** Export `BggClient.max_batch_size/0` and have both `catalog.seed.ex` and `stats_enricher.ex`
reference it instead of re-declaring `20` independently.

### IN-02: `DescriptionTranslator.handle_result/1` has a dead/redundant clause

**File:** `lib/pukllay_club/catalog/seed/description_translator.ex:111-112`

```elixir
defp handle_result({:error, %Ecto.Changeset{}} = error), do: error
defp handle_result({:error, _reason} = error), do: error
```

**Issue:** The first clause is fully subsumed by the second (both bind `error` and return it
unchanged) — the `%Ecto.Changeset{}`-specific clause does nothing the generic one wouldn't already
do. Harmless (first-match-wins means it's never actually dead code at runtime, just redundant), but
misleading to a future reader who might assume the Changeset case gets special handling.

**Fix:** Delete the `{:error, %Ecto.Changeset{}} = error` clause; the generic one below it already
covers it.

### IN-03: The four BGG-attribution links in `show.ex`'s Ficha técnica section are hand-duplicated

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex` (Peso BGG, Valoración BGG, Ranking BGG,
and "Ver ficha completa" rows, ~lines 597-660)

**Issue:** `href={"https://boardgamegeek.com/boardgame/#{@game.bgg_id}"}` (plus the identical
`target`/`rel`/`class` attributes) is written out four separate times in the same section, one per
stat row. A future edit to the URL format, target behavior, or link styling has to be applied
consistently in four places by hand.

**Fix:** Extract a small function component (e.g. `bgg_link/1` taking `bgg_id` and an inner block)
so the four call sites share one implementation.
