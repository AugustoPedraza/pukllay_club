# Phase 01.3: Code Review Report

**Reviewed:** 2026-08-31T00:00:00Z
**Depth:** standard
**Files Reviewed:** 34
**Status:** issues_found

## Summary

This phase adds BGG stats/artists re-enrichment (`StatsEnricher`, two Mix
tasks, a migration), an offline Gemini description-translation job, and
detail-page/catalog-filter work exposing the new `artists`/`bgg_rating`/
`bgg_rank` columns (fact-grid pills, Comunidad BGG block, `?designers=`/
`?artists=` filters). The code is heavily commented, well-tested (the
detail-page LiveView test suite alone is ~4,000 lines), and shows evidence
of at least one prior review pass already applied (comments reference
"WR-01"/"WR-03 (01.3 code review)" fixes already folded in). No security
vulnerabilities, XSS, injection, or crash-on-bad-input paths were found in
the reviewed diff — parameterization, DTD-disabling, and 404-not-500
handling are all in place and tested.

The issues found are two real content-accuracy/reliability gaps and one
maintainability nit, none of which are exploitable or crash the
application:

1. `mix catalog.seed` (the ongoing/repeatable seed path) never writes the
   new `artists`/`bgg_rating`/`bgg_rank` columns this phase introduces —
   only the one-time `mix catalog.enrich_bgg_stats` / `mix
   catalog.backfill_artists` tasks do. Any future catalog growth via the
   normal seed path will silently regress the very content this phase
   exists to make accurate.
2. Both write paths in `StatsEnricher` discard `Repo.update/1`'s return
   value and unconditionally increment their `:updated` counter, so a
   per-row database failure during a *real* (non-dry-run) enrichment pass
   is silently swallowed and misreported as a success in the persisted
   Markdown report — the exact artifact this module's own moduledoc says
   exists to be "a reviewable record."
3. `CatalogFilters.parse_name_list_param/1`'s comma-splitting, inherited
   from the closed-vocabulary facets, is unsafe once applied to open BGG
   creator names: a designer/artist name containing a literal comma
   silently breaks its own filter-pill round-trip (zero results), which
   directly contradicts the one exact-round-trip guarantee this phase's
   own test suite pins for accent/space-bearing names.

## Warnings

### WR-01: `mix catalog.seed` never populates `artists`/`bgg_rating`/`bgg_rank` for (re-)seeded games

**File:** `lib/mix/tasks/catalog.seed.ex:259-278`
**Issue:** `enrich_attrs/2` maps a fetched BGG `item` onto the game's
persisted attrs, but the returned map only carries `year_published`,
`min_players`, `max_players`, `min_playtime`, `max_playtime`,
`playing_time`, `min_age`, `description`, `bgg_weight`, `mechanics`,
`themes`, `designers`, `publishers`, `bgg_payload`. It omits
`artists`, `bgg_rating`, and `bgg_rank` — the three fields this phase's
migration (`20260830215001_add_games_artists_and_bgg_stats.exs`) adds and
`BggClient.parse_items/1` already returns (`item.artists`,
`item.average_rating`, `item.rank`), and which `Game.seed_changeset/2`
already casts. `StatsEnricher.update_game_stats/2` sets all three
correctly for its one-time backfill run, but that code path is
independent of `catalog.seed`'s.

Since `mix catalog.seed` is the only ongoing/repeatable ingestion path
(re-run to add new games, or to re-seed after a CSV export refresh), any
game added or re-seeded after this phase's one-time backfill will have
`artists: []`, `bgg_rating: nil`, `bgg_rank: nil` until a developer
remembers to separately re-run `mix catalog.enrich_bgg_stats` (and, for
`artists` alone, `mix catalog.backfill_artists`) by hand. Nothing in the
codebase enforces or even flags that follow-up step — the Comunidad BGG
block and Ilustradores fact-grid column this phase built will silently go
dark for every newly added game.

**Fix:**
```elixir
defp enrich_attrs(base, item) do
  Map.merge(base, %{
    year_published: item.year_published,
    min_players: item.min_players,
    max_players: item.max_players,
    min_playtime: item.min_playtime,
    max_playtime: item.max_playtime,
    playing_time: item.playing_time,
    min_age: item.min_age,
    description: DescriptionNormalizer.clean(item.description),
    bgg_weight: item.average_weight,
    bgg_rating: item.average_rating,
    bgg_rank: item.rank,
    artists: item.artists,
    mechanics: item.mechanics,
    themes: item.categories,
    designers: item.designers,
    publishers: item.publishers,
    bgg_payload: item
  })
end
```

### WR-02: `StatsEnricher` discards `Repo.update/1`'s result and always counts the row as updated

**File:** `lib/pukllay_club/catalog/seed/stats_enricher.ex:143-155, 157-173`
**Issue:** `update_game_stats/2` runs `Repo.update()` for its side effect
only and returns whatever `Repo.update/1` returns, but its caller,
`apply_item/4` (lines 130-141), never inspects that result:

```elixir
{:ok, item} ->
  if !dry_run?, do: update_game_stats(game, item)
  acc = %{acc | updated: acc.updated + 1}
  ...
```

`apply_artists_backfill/3` (lines 157-173) has the identical pattern. If a
`Repo.update/1` call fails on a real (non-dry-run) invocation — a
constraint violation, a dropped connection, a validation error some
future changeset addition introduces — the failure is silently swallowed
and the row is still counted in `:updated` and written into
`bgg_stats_enrichment_report.md` as a successful update. This directly
undercuts the report's stated purpose ("so a partial or rate-limited run
leaves a reviewable record rather than only scrollback") for exactly the
failure mode (a bad write) it exists to surface — `failed_batches` only
tracks HTTP/fetch failures, not write failures.

**Fix:**
```elixir
defp apply_item(game, items_by_bgg_id, dry_run?, acc) do
  case Map.fetch(items_by_bgg_id, game.bgg_id) do
    :error ->
      %{acc | missing_from_bgg: acc.missing_from_bgg ++ [game.bgg_id]}

    {:ok, item} ->
      case (if dry_run?, do: {:ok, :dry_run}, else: update_game_stats(game, item)) do
        {:ok, _} ->
          acc = %{acc | updated: acc.updated + 1}
          if is_nil(item.rank), do: %{acc | unranked: acc.unranked ++ [game.bgg_id]}, else: acc

        {:error, changeset} ->
          %{acc | failed_writes: acc.failed_writes ++ [{game.bgg_id, changeset}]}
      end
  end
end
```
(mirroring `process_batch/4`'s existing `failed_batches` tracking, and
adding a `:failed_writes` counter to the initial summary map and the
Mix task's report).

### WR-03: `?designers=`/`?artists=` silently mis-filters a creator name containing a literal comma

**File:** `lib/pukllay_club_web/catalog_filters.ex:184-199`
**Issue:** `parse_name_list_param/1`'s binary clause splits on `,`
(`value |> String.split(",", trim: true) |> ...`), inherited verbatim from
`parse_list_param/2`'s pattern for the pre-existing closed-vocabulary
facets (`mechanics`, `themes`, `weight_bands`, `tags`), where a comma can
never legitimately appear inside a single value because every value comes
from a fixed Spanish-label Vocabulary. `designers`/`artists` (01.3-06) are
open, BGG-sourced free-text names with no such guarantee — a real BGG
credit containing a comma (e.g. a "Last, Suffix" style credit) will be
percent-encoded into a single `?designers=` value by
`CatalogLive.Show.creator_pills/1`'s own `~p"/?designers=#{name}"` href,
decoded back to a plain string containing a literal comma by
`Plug.Conn.Query.decode/1`, then split into two-or-more separate filter
tokens here. Because `Catalog.maybe_filter_designers/2` uses Postgres
array-overlap (`? && ?`) against those split tokens, neither piece
matches the game's actual single-element designers/artists array entry,
and the filter silently returns zero results for the exact game the pill
was generated from.

This is a real, if narrow, regression risk: the phase's own test
(`T-01.3-07-01` in `test/pukllay_club_web/live/catalog_show_test.exs`)
proves the round-trip holds for a space- and accent-bearing name ("Loïc
Billiau") but there is no equivalent test for a comma-bearing name, and
the round-trip silently breaks for one.

**Fix:** Do not comma-split the open-text `designers`/`artists` params —
treat a single string value as one name, and only accept multiple names
via the already-supported repeated-key list form (`?designers[]=A&designers[]=B`),
which `creator_chips`/`creator_pills` never produce anyway (each link
carries exactly one name):
```elixir
defp parse_name_list_param(value) when is_binary(value) do
  [value]
  |> Enum.filter(&is_binary/1)
  |> Enum.map(&String.slice(&1, 0, @max_name_length))
  |> Enum.reject(&(&1 == ""))
end
```

## Info

### IN-01: `creator_chips/3` is a byte-for-byte duplicate of `facet_chips/3`

**File:** `lib/pukllay_club_web/live/catalog_live/index.ex:650-661, 710-721`
**Issue:** `creator_chips/3` (added by 01.3-06) has an identical body to
the pre-existing `facet_chips/3` — same map shape, same string
interpolation, same field names. The moduledoc comment above it
acknowledges this ("Same descriptor shape as `facet_chips/3` (this is
deliberately not a distinct shape)") but keeps it as a separate function
anyway, which is pure duplication rather than a documented divergence.
**Fix:** Delete `creator_chips/3` and call `facet_chips(assigns.designers,
"designers", "Diseñador")` / `facet_chips(assigns.artists, "artists",
"Ilustrador")` directly from `active_filter_chips/1`.

### IN-02: `BggClient`'s moduledoc hardcodes the batch-size limit instead of referencing `@max_batch_size`

**File:** `lib/pukllay_club/catalog/seed/bgg_client.ex:5, 21`
**Issue:** The moduledoc's `"Fetches up to #{20} ids per request"` (line 5)
interpolates the literal `20` rather than `@max_batch_size` (defined two
lines later, at line 21, which is why it isn't referenced — module
attributes aren't available to an earlier `@moduledoc`). If
`@max_batch_size` is ever changed, this doc line silently goes stale,
while the function-level `@doc` right below `max_batch_size/0` (line 26)
already does reference `#{@max_batch_size}` correctly, showing the
inconsistency is accidental rather than deliberate.
**Fix:** Move `@max_batch_size = 20` above `@moduledoc`, or drop the
number from the moduledoc line entirely and let the `max_batch_size/0`
function doc be the single source of truth for the value.
