# Phase 01.3: Code Review Report

**Reviewed:** 2026-08-31T00:00:00Z
**Depth:** standard

## Summary

This is a fresh, full-phase review of the accumulated final state of
01.3-game-detail-layout-content-accuracy, including the 10 files newly added
by plans 01.3-06 through 01.3-09 that the earlier partial 01.3-REVIEW.md
(already fixed, see 01.3-REVIEW-FIX.md) never saw. The code overall is
disciplined: query parameters are consistently bound (`^`) rather than
interpolated, the seed/translation pipeline degrades per-item failures
without aborting the whole run, and the catalog filter/URL round-trip has
thorough bounds checking with good test coverage.

One genuine BLOCKER survives from a gap in an *earlier* fix: `CatalogLive.Show.mount/3`
calls `Catalog.get_game!/1` with no `rescue`, and `get_game!/1`'s own
non-numeric-id handling (added specifically to guarantee "a single 404
contract... for every kind of bad id") does not bound the parsed integer
against Postgres' `int8` range, so an oversized-but-well-formed numeric id
in the URL crashes with an unhandled `DBConnection.EncodeError` instead of
rendering the branded 404. Two further WARNINGs (an ignored `Repo.update/1`
result in the stats-enrichment write path, and two `handle_event/3` clauses
in the detail LiveView with no catch-all for a malformed/crafted client
payload) and one INFO (duplicated `dry_run_prefix/1` helper across two Mix
tasks) round out the findings.

## Critical Issues

### CR-01: Oversized numeric game id crashes with a raw Postgrex error instead of rendering the branded 404

**File:** `lib/pukllay_club/catalog.ex:149-156` (`get_game!/1`), consumed unguarded by `lib/pukllay_club_web/live/catalog_live/show.ex:91-92` (`mount/3`)

**Issue:** `get_game!/1`'s own moduledoc states its purpose explicitly:

> Parsing the id first and raising `Ecto.NoResultsError` for anything that
> doesn't fully parse as an integer keeps the single 404 contract intact for
> every kind of bad id, not just the numeric-but-nonexistent one.

The implementation only guards against a value that fails to parse as an
integer at all (`Integer.parse/1` returning `:error` or a non-empty
remainder). It does **not** bound the successfully-parsed integer against
Postgres' `int8` range. The `games` table's primary key is the Ecto-default
`:id` column, which `ecto_sql` creates as `bigserial` (confirmed via
`deps/ecto_sql/lib/ecto/migration.ex` and the absence of any
`@primary_key`/`migration_primary_key` override in this repo), i.e. Postgres
`bigint` (`-9_223_372_036_854_775_808..9_223_372_036_854_775_807`). Postgrex's
own `int8` extension (`deps/postgrex/lib/postgrex/extensions/int8.ex`) raises
`DBConnection.EncodeError` for any integer outside that range — it does not
return an error tuple.

Because `String.to_integer`/`Integer.parse` support arbitrary-precision
integers, a URL like `/juegos/99999999999999999999999999` parses cleanly as
`{int_id, ""}` and is handed straight to `Repo.get!(Game, int_id)`. The
router has no constraint on the `:id` segment
(`lib/pukllay_club_web/router.ex:26`, `live "/juegos/:id", ...`), so this URL
is reachable by any visitor, crawler, or scanner. `DBConnection.EncodeError`
does not implement `Plug.Exception`, so Phoenix cannot map it to the branded
404 — the request crashes with an unhandled exception (a generic 500 in
production) instead of the documented 404 behaviour. This is the exact
residual case the earlier "CR-02" fix (referenced in
`test/pukllay_club_web/live/catalog_show_test.exs` around the non-numeric-id
test) did not cover, and there is no existing test for an oversized numeric
id.

Also note `CatalogLive.Show.mount/3` calls `Catalog.get_game!(id)` directly,
with no `rescue` — unlike `CatalogLive.Index`'s `safe_filter_games/1`
(`lib/pukllay_club_web/live/catalog_live/index.ex:596-600`), which
deliberately wraps every filter read in a `rescue` specifically to catch
"a crafted scalar value Postgres rejects" (T-01-24). `Show`'s only line of
defense against a hostile id is `get_game!/1`'s own parsing, and that line
has this gap.

**Fix:**

```elixir
# lib/pukllay_club/catalog.ex
@int8_range -9_223_372_036_854_775_808..9_223_372_036_854_775_807

def get_game!(id) when is_binary(id) do
  case Integer.parse(id) do
    {int_id, ""} when int_id in @int8_range -> Repo.get!(Game, int_id)
    _ -> raise Ecto.NoResultsError, queryable: Game
  end
end
```

Add a regression test alongside the existing "a non-numeric game id renders
the branded 404" test in `catalog_show_test.exs`, e.g.
`get(conn, ~p"/juegos/99999999999999999999999999")` asserting the same
`assert_error_sent(404, ...)` / `"Juego no encontrado"` outcome.

## Warnings

### WR-01: `StatsEnricher`'s two write paths discard `Repo.update/1`'s result, silently misreporting failed writes as successful

**File:** `lib/pukllay_club/catalog/seed/stats_enricher.ex:143-155` (`update_game_stats/2`) and `:157-173` (`apply_artists_backfill/3`)

**Issue:** Both `update_game_stats/2` (called from `apply_item/4`) and
`apply_artists_backfill/3` call `Repo.update/1` but never inspect its return
value:

```elixir
defp update_game_stats(game, item) do
  attrs = %{...}
  game
  |> Ecto.Changeset.cast(attrs, [...])
  |> Repo.update()
end
```

`apply_item/4` unconditionally increments `acc.updated` right after calling
`update_game_stats/2` regardless of whether the update actually succeeded:

```elixir
{:ok, item} ->
  if !dry_run?, do: update_game_stats(game, item)
  acc = %{acc | updated: acc.updated + 1}
  ...
```

The same pattern repeats in `apply_artists_backfill/3`, which increments
`updated`/`deduplicated` unconditionally right after the (unchecked)
`Repo.update`. Every other error path in this module and its sibling
`mix catalog.*` tasks is careful to surface failures into the run
summary/report (`failed_batches`, `missing_from_bgg`, per-game failure
lists in `catalog.translate_descriptions.ex`) — this is the one write path
in the reviewed files where a real failure (a unique-constraint violation,
a stale/deleted row, a future validation added to the changeset) would be
silently swallowed and still counted as a successful update in both the
console summary and the persisted Markdown report
(`bgg_stats_enrichment_report.md`).

**Fix:** Pattern-match the result and route a failure into the summary,
mirroring how `process_batch/4` already handles a failed `BggClient.fetch_batch/2`:

```elixir
defp update_game_stats(game, item) do
  attrs = %{...}
  game
  |> Ecto.Changeset.cast(attrs, [:bgg_weight, :bgg_rating, :bgg_rank, :artists, :bgg_payload])
  |> Repo.update()
end
```
```elixir
{:ok, item} ->
  case (if !dry_run?, do: update_game_stats(game, item), else: {:ok, game}) do
    {:ok, _game} ->
      acc = %{acc | updated: acc.updated + 1}
      if is_nil(item.rank), do: %{acc | unranked: acc.unranked ++ [game.bgg_id]}, else: acc

    {:error, _changeset} ->
      %{acc | failed_batches: acc.failed_batches ++ [{[game.bgg_id], :update_failed}]}
  end
```
(and equivalently thread a `{:error, _}` branch through `apply_artists_backfill/3` into a new/existing failure bucket rather than counting it in `updated`).

### WR-02: Two `handle_event/3` clauses in the detail LiveView have no fallback for a malformed/crafted client payload

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:230-232` (`"validate-reservation"`) and `:235-237` (`"reserve"`)

**Issue:**

```elixir
def handle_event("validate-reservation", %{"nombre" => name}, socket) do
  ...
end

def handle_event("reserve", %{"nombre" => name}, socket) do
  ...
end
```

Both clauses pattern-match directly on `%{"nombre" => name}` with no
catch-all clause. The normal HEEx form always sends this key, but a
LiveView `handle_event` is reachable by any client-side `pushEvent` call —
including a hand-crafted one from devtools/a malicious page — and this
module already treats "never build an atom from client input" /
"degrade gracefully on unexpected payload shape" as a house rule elsewhere
(`facet_assign_key/1`, `scalar_assign_key/1` in `CatalogLive.Index`, and
`valid_gallery_image?/2`'s whitelist here in `Show`). A `pushEvent("reserve", {})`
with no `"nombre"` key raises `FunctionClauseError`, crashing the LiveView
process for that visitor's session (LiveView will reconnect, but the
in-progress reservation-modal state — including any typed name — is lost,
and the visitor sees a full remount/reload).

The same gap exists on `"select-image"` (`:146-152`) and
`"select-lightbox-image"` (`:162-168`), which likewise pattern-match
`%{"url" => url}` with no fallback clause.

**Fix:** Add a catch-all clause per event name, matching the discipline
already used for `toggle-facet`/`toggle-scalar`:

```elixir
def handle_event("reserve", _params, socket), do: {:noreply, socket}
def handle_event("validate-reservation", _params, socket), do: {:noreply, socket}
```
placed after the well-formed clauses (Elixir tries clauses top-to-bottom),
or fold the guard into the existing clause with a `case`/pattern-matched
`Map.get(params, "nombre")` fallback to `""`.

## Info

### IN-01: `dry_run_prefix/1` is duplicated verbatim across two Mix tasks

**File:** `lib/mix/tasks/catalog.backfill_artists.ex:39-40` and `lib/mix/tasks/catalog.enrich_bgg_stats.ex:64-65`

**Issue:** Both files define an identical private helper (including an
identical explanatory comment referencing "01.3 code review"):

```elixir
defp dry_run_prefix(true), do: "[DRY RUN] "
defp dry_run_prefix(false), do: ""
```

`catalog.translate_descriptions.ex` needs no equivalent because it never
prefixes its summary line with a dry-run marker, but the two duplicates
that do exist will drift if the prefix convention ever changes in one file
and not the other.

**Fix:** Extract to a small shared helper (e.g. a `PukllayClub.Catalog.Seed.RunLabel`
module or a function on an existing shared module such as `Credentials`)
that both Mix tasks call, the same way `BggClient.dedup_artists/1` and
`BggClient.max_batch_size/0` are already shared to prevent exactly this
kind of drift.
