### Known Open Item (not a gap — pre-accepted, documented trade-off)

`01.3-REVIEW.md` (a code review scoped to plan 12's delta) flagged **CR-01**: for a description
that renders as a **single line** (non-clamped, under ~44px tall), the collapsed shell's `min-height:
2.75rem` (44px) floor is taller than the one-line paragraph (~24px), so the absolutely-positioned
toggle — anchored to the *shell's* bottom edge, not the *text's* — opens a ~20px visible gap below
the single line of text instead of trailing it flush.

This is not scored as a gap for G-01.3-6: plan 12's own `<planner_note>` ("Known, accepted
behaviour for short descriptions") explicitly documents and accepts this exact trade-off, reasoning
that conditioning the toggle's presence on actual text overflow requires measurement the server does
not currently have, and is declared out of scope for this gap-closure round. The alternative
(letting the overlay hang upward over content above the description on short text) was explicitly
rejected as a worse tap-hijack failure mode. CR-01 is a real, provable UX rough edge on short
descriptions — it is surfaced here as a follow-up candidate, not silently dropped, but it does not
block this phase's goal or this gap's closure, both of which are scoped to the reported symptom
(chevron detaching from the *clamped, three-line* case G-01.3-6 was reported against).

Two review **warnings** (also advisory, not gaps): WR-01 notes the `.pk-desc*` family-span
extraction regex is now duplicated between the pre-existing tripwire test and the new geometry
test (a maintainability nit); WR-02 notes `padding-right: 2.75rem` reserves the toggle's full width
on every clamped line (not just the last), which the rule's own comment already documents as an
accepted trade-off, but is flagged for a mobile-width visual check during UAT.
