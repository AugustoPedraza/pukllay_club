## Summary

This phase has two independent workstreams that share no code paths: (1) a **content-accuracy**
workstream extending the BGG seed/enrichment pipeline (`bgg_client.ex`, `catalog.seed.ex`,
`game.ex`) plus one new one-off Mix task for LLM translation, and (2) a **pure-CSS/template**
workstream on `show.ex` + `app.css` that is *already fully specified* by the approved
`01.3-UI-SPEC.md` — no new visual decisions remain, only implementation.

The most consequential finding from this research is **not** in the CONTEXT.md-flagged risk (BGG
rate limits) but in two things direct inspection of the live dev database surfaced that neither
CONTEXT.md nor UI-SPEC anticipated:

1. **D-02's markup-cleanup target was mis-described.** A direct SQL query against
   `pukllay_club_dev` found **zero** occurrences of literal `&#10;` or `[b]`/`[i]` BBCode tags
   across all 385 stored descriptions, but **261/385 (68%)** contain un-decoded named HTML entities
   (`&mdash;`, `&rsquo;`, `&eacute;`, `&ntilde;`, etc. — 30 distinct entity names found). The
   cleanup step is real and needed; the specific noise pattern is different from what CONTEXT.md
   assumed. See Common Pitfalls.
2. **The existing `bgg_payload['artists']` data that D-05 plans to backfill from is corrupted with
   massive duplication** — confirmed live: 368 of 377 games with artist data have far more raw
   entries than unique names (Spirit Island: 367 raw entries for 15 unique artists). The backfill
   **must** `Enum.uniq/1` the list, or the shipped Ilustradores row will show the same name repeated
   dozens of times. See Common Pitfalls — this is the single most load-bearing new fact this
   research produced.

The BGG XML schema for rating/rank (D-06) was confirmed directly against the project's own captured
fixture (`test/support/fixtures/bgg_thing_on_mars.xml`), and SweetXml's "soft cast" xpath modifiers
(`I`/`F` + `o`) were confirmed against the library's own source on GitHub — together these fully
resolve the UI-SPEC's flagged "Not Ranked" normalization backstop with a one-line xpath change, no
custom parsing helper needed.

**Primary recommendation:** Treat this as two sequenced plans — (A) content-accuracy backend work
(schema + BggClient + two Mix tasks), (B) UI-SPEC implementation (CSS/template only, zero schema
dependency, can ship independently and first if desired) — with (A)'s artists-dedup and (A)'s
translation-task Gemini-key provisioning as the two items needing a `checkpoint:human-verify` gate.

### Pattern 1: BGG rating/rank XPath extraction (D-06)

**What:** Extend `BggClient`'s `parse_items/1` xpath map with two new fields, using SweetXml's
"soft cast" modifiers to handle BGG's `"Not Ranked"` string value without a custom parsing helper.

**Verified against the project's own fixture** `test/support/fixtures/bgg_thing_on_mars.xml:499-508`:
```xml
<statistics page="1">
    <ratings >
    <usersrated value="15149" />
    <average value="8.15856" />
    <bayesaverage value="7.7411" />
    <ranks>
        <rank type="subtype" id="1" name="boardgame" friendlyname="Board Game Rank" value="58" bayesaverage="7.7411" />
        <rank type="family" id="5497" name="strategygames" friendlyname="Strategy Game Rank" value="43" bayesaverage="7.82227" />
    </ranks>
    ...
    <averageweight value="4.6237" />
```
[VERIFIED: test/support/fixtures/bgg_thing_on_mars.xml:499-518]

The overall BGG rank (what D-06/UI-SPEC call "Ranking general"/"Ranking BGG") is the `<rank>` where
`name="boardgame"` — **not** distinguished by `type` (both the overall rank and subdomain ranks like
`strategygames` share `type="subtype"`/`type="family"` inconsistently across BGG's own data; `name`
is the stable discriminator).

For unranked games, community-sourced examples show the value/bayesaverage attributes hold the
literal string `"Not Ranked"` [CITED: mixedconclusions.com/blog/boardgames_part_one — cross-checked
against a second independent source describing the same literal string for BGG expansions]. Extract
with SweetXml's uppercase "soft cast" modifier (`I` = soft integer) combined with `o` (optional),
confirmed directly from the library's own source on GitHub:

```elixir
# Source: github.com/kbrw/sweet_xml lib/sweet_xml.ex (sigil_x/2, to_cast/3)
# [VERIFIED: raw.githubusercontent.com/kbrw/sweet_xml/master/lib/sweet_xml.ex]
defp to_cast(value, :soft_integer, is_opt?) do
  if String.Chars.impl_for(value) do
    case Integer.parse(to_string(value)) do
      :error -> if is_opt?, do: nil, else: 0
      {int, _} -> int
    end
  else
    if is_opt?, do: nil, else: 0
  end
end
```

Applied to `bgg_client.ex`'s existing xpath map (add alongside the existing `average_weight` line):

```elixir
average_rating: ~x".//statistics/ratings/average/@value"fo,
rank: ~x".//statistics/ratings/ranks/rank[@name='boardgame']/@value"Io,
```

`fo` (optional float, same modifier already used for `year_published`/`min_players` elsewhere in
this file) is safe for `average` since BGG always emits a numeric `average` (defaulting to `"0"` for
an unrated game, never a string) — only the `ranks/rank/@value` needs the soft-cast `Io` treatment.

### Pattern 2: Narrow re-enrichment update, not a full seed re-run (D-06)

**What:** A new Mix task fetches BGG data for all games with a `bgg_id` (393 of 434 rows
[VERIFIED: `SELECT count(*) FILTER (WHERE bgg_id IS NOT NULL) FROM games` against `pukllay_club_dev`
— run 2026-08-29]) and updates only the 3-4 fields this phase adds, reusing the existing
`BggClient.fetch_batch/2` (already batches 20 ids/request with a 1500ms inter-batch delay and
429/5xx retry [VERIFIED: lib/pukllay_club/catalog/seed/bgg_client.ex:1-92]) — do not write new
retry/backoff logic.

```elixir
# lib/mix/tasks/catalog.enrich_bgg_stats.ex (new, one-off, dev-only — mirrors catalog.seed.ex's
# @shortdoc/@moduledoc "one-time" framing and Mix.Task structure)
defp update_stats(game, item) do
  game
  |> Ecto.Changeset.cast(
    %{bgg_weight: item.average_weight, bgg_rating: item.average_rating, bgg_rank: item.rank, bgg_payload: item},
    [:bgg_weight, :bgg_rating, :bgg_rank, :bgg_payload]
  )
  |> PukllayClub.Repo.update()
end
```

At 393 games / 20-per-batch = 20 batches × 1.5s inter-batch delay ≈ 30 seconds total against BGG's
API — well within any plausible rate-limit budget; no special throttling design needed beyond what
`BggClient` already does.

### Pattern 3: Artists backfill — deduplicate, do not copy `bgg_payload` verbatim (D-05)

See Common Pitfall 2 below for the full evidence. The backfill logic, whether implemented as a raw
migration `execute/2` (matching the `add_games_is_expansion` precedent) or an Ecto-based Mix task:

```elixir
# Deduplication is NOT optional — 368/377 games with artist data have raw duplicates,
# some extreme (Spirit Island: 367 raw entries -> 15 unique).
artists =
  game.bgg_payload["artists"]
  |> List.wrap()
  |> Enum.uniq()
```

If done as a pure-SQL migration `execute/2` (matching the `is_expansion` precedent), Postgres has no
trivial order-preserving array-dedup one-liner — prefer an Elixir-side idempotent Mix task/one-off
script over forcing this into a migration `execute/2`, since `Enum.uniq/1` is what actually needs to
run, not a SQL rewrite. This is a deliberate, documented departure from the `is_expansion` migration
precedent (see Assumptions Log — flagged for planner judgment, not locked here).

### Anti-Patterns to Avoid

- **Re-running `mix catalog.seed` for D-06's re-enrichment:** re-triggers the full R2 image
  pipeline for all ~400 games for no reason (see Alternatives Considered).
- **Trusting `bgg_payload['artists']` as pre-cleaned data:** it is not — see Common Pitfall 2.
- **Hand-parsing `"Not Ranked"` with a custom `case`/regex helper:** SweetXml's `Io` modifier already
  does this correctly at the extraction layer (Pattern 1) — a second normalization layer downstream
  would be redundant and a second place for the logic to drift.

either in this codebase (`BggClient`'s retry logic) or in a library the project has already
committed to (`InstructorLite`, `SweetXml`) — this phase is unusually free of genuinely novel
technical problems; the risk is entirely in data-quality assumptions (see Common Pitfalls), not
missing tooling.

## Common Pitfalls

### Pitfall 1: D-02's assumed markup-noise pattern does not match the real stored data

**What goes wrong:** Building the description cleanup step around `&#10;` line-break entities and
`[b]`/`[i]` BBCode tags (as `01.3-CONTEXT.md` describes) would ship a normalizer that does nothing,
because a direct query of the live dev database found **zero** occurrences of either pattern.

**Why it happens:** CONTEXT.md's D-02 description appears to be based on general BGG-data folklore
or a small manual sample, not an exhaustive query of this project's own stored data.

**How to avoid:** Build the D-02 normalizer against what is actually stored. Verified via direct SQL
against `pukllay_club_dev` (2026-08-29):

```
SELECT count(*) AS total,
       count(*) FILTER (WHERE description ~ '&#10;')            AS has_lf_entity,   -- 0
       count(*) FILTER (WHERE description ~ '\[b\]|\[i\]')      AS has_bbcode,      -- 0
       count(*) FILTER (WHERE description ~ '&amp;|&rsquo;|&mdash;|&ndash;|&quot;')
                                                                  AS has_html_entity  -- 245
FROM games WHERE description IS NOT NULL;
-- total=385
```
[VERIFIED: live query against pukllay_club_dev, 2026-08-29]

A follow-up query enumerating every distinct named entity found **30 distinct entities** across
261/385 (68%) descriptions — accented-Latin characters (`&eacute;`, `&ntilde;`, `&uuml;`,
`&aacute;`, `&Aacute;`, `&agrave;`, `&auml;`, `&egrave;`, `&iacute;`, `&iuml;`, `&ocirc;`, `&ouml;`,
`&ucirc;`, `&uuml;`, `&szlig;`, `&iexcl;`, `&iquest;`) and typographic punctuation
(`&mdash;` 201×, `&rsquo;` 48×, `&ndash;` 30×, `&ldquo;`/`&rdquo;` 9×, `&hellip;`, `&bull;`,
`&nbsp;`, `&shy;`, `&thinsp;`, `&times;`, `&pound;`) [VERIFIED: live query against
`pukllay_club_dev`, 2026-08-29 — `SELECT DISTINCT (regexp_matches(description, '&([a-zA-Z]+);',
'g'))[1] ... ORDER BY 1` returned exactly this 30-entity set]. Sample: `"It&rsquo;s the late 19th"`,
`"a loyal friend &mdash; your llama"`, `"Loan - Take a &pound;30 loan"`.

This is exactly one HTML-decode pass away from clean (SweetXml already performed the *XML*-level
decode on ingestion — e.g. `&amp;rsquo;` in BGG's raw XML source became the stored `&rsquo;` — see
`test/support/fixtures/bgg_thing_on_mars.xml` for a captured example of the double-encoded source:
`"company&amp;rsquo;s private agenda"` [VERIFIED: test/support/fixtures/bgg_thing_on_mars.xml,
description field] — a second, HTML-entity-specific decode is what D-02 actually needs, not a
newline/BBCode cleanup).

D-02's decision itself ("clean this up at seed time") remains correct and locked — only the
*mechanism* (a small named-HTML-entity decode table covering the 30 confirmed entities, following
`hashtag_normalizer.ex`'s plain-module convention) needs to target the real pattern, not the assumed
one.

**Warning signs:** If the shipped normalizer's test suite only asserts against a synthetic string
containing `&#10;`/BBCode and never against a real captured description, this mismatch will not be
caught before deploy.

### Pitfall 2: `bgg_payload['artists']` contains massive, near-universal duplication — do not copy it verbatim

**What goes wrong:** D-05's own text says "backfilled from the existing `bgg_payload` (no BGG
re-fetch needed)" — if implemented as a literal copy (`artists = bgg_payload["artists"]`), the
shipped Ilustradores row will show the same artist name repeated dozens of times for the majority of
games.

**Why it happens:** Confirmed via direct query against `pukllay_club_dev` (2026-08-29):

```
SELECT count(*) AS games_with_dup_artists
FROM games
WHERE bgg_payload->'artists' IS NOT NULL
  AND jsonb_array_length(bgg_payload->'artists')
      <> (SELECT count(DISTINCT a) FROM jsonb_array_elements_text(bgg_payload->'artists') a);
-- 368  (out of 377 games that have any artists data at all — 97.6%)
```
[VERIFIED: live query against pukllay_club_dev, 2026-08-29]

Worst observed cases: Spirit Island (367 raw entries → 15 unique), Robinson Crusoe (175 → 13),
Takenoko (122 → 3), Wingspan (88 → 4), Pandemic (85 → 5), Mysterium (84 → 2). The already-shipped
`designers` column — populated at original seed time via the *same* `.//link[@type='...']/@value"sl`
xpath pattern — shows **zero** duplicate-count games [VERIFIED: `SELECT count(*) FILTER (WHERE
array_length(designers,1) <> (SELECT count(DISTINCT d) FROM unnest(designers) d)) FROM games` = 0],
confirming this is specific to the `artists` link type's real BGG data, not a per-item XPath-scoping
bug in `BggClient` itself (the same extraction pattern demonstrably works cleanly for designers on
the identical games, e.g. Brass: Birmingham has 37 nested `<versions>` entries and 0 designer
duplicates but 72 raw artist entries for 7 real artists).

**How to avoid:** `Enum.uniq/1` (or equivalent order-preserving dedup) the artist list at backfill
time — see Architecture Patterns, Pattern 3. Also apply the same treatment inside `BggClient`'s
`artists:` xpath extraction going forward (or immediately after extraction in `catalog.seed.ex`) so
any future full re-seed doesn't reintroduce the duplication.

**Warning signs:** A Ficha técnica Ilustradores row rendering the same name 2+ times, or a row so
long it visibly breaks `pk-spec-row--wide`'s layout.

### Pitfall 3: Testing the "removed dead rows" invariant is now backwards

**What goes wrong:** `test/pukllay_club_web/live/catalog_show_test.exs:447-460` currently asserts:

```elixir
test "the ficha técnica never renders the dead Ilustrador or BGG-ranking rows (D-04)", %{conn: conn} do
  ...
  refute spec_html =~ "Ilustrador"
  refute spec_html =~ "Puesto en el ranking BGG"
  refute spec_html =~ "No disponible"
end
```
[VERIFIED: test/pukllay_club_web/live/catalog_show_test.exs:447-460]

This test was written in Phase 01.2 (D-04 there) specifically to lock in the *removal* of these
rows. This phase's D-05/D-06 now *reinstate* an Ilustradores row and an advanced-stats block — this
test's `refute spec_html =~ "Ilustrador"` assertion is now testing for the wrong behavior and will
fail (correctly) the moment D-05 ships, or (worse) silently stop meaning anything if the fixture
used in that specific test happens to have no artists data.

**Why it happens:** Cross-phase test drift — a prior phase's "this must never come back" assertion
collides with this phase's explicit reintroduction of the same content, now backed by real data.

**How to avoid:** Update this specific test as part of the D-05/D-06 plan — either delete it, or
rewrite it to assert the *conditional* render (present when `artists`/`bgg_rating`/`bgg_rank` are
set, absent when nil), matching the pattern already used by the adjacent tests in the same file
(`"omits designers/age/description rows individually when absent"`,
`"a minimal-data game with none of the five spec fields renders no Ficha técnica heading"`).

**Warning signs:** `mix test` failing on this exact test name once the Ilustradores row ships is the
expected, correct signal — do not "fix" it by keeping the row hidden.

### Pitfall 4: `game_fixture/1` has no `artists`/`bgg_rating`/`bgg_rank` defaults

**What goes wrong:** `test/support/fixtures/catalog_fixtures.ex:16-47`'s `game_fixture/1` default
attrs map has no `artists`, `bgg_rating`, or `bgg_rank` keys [VERIFIED:
test/support/fixtures/catalog_fixtures.ex:16-42]. Any new test asserting the Ilustradores/advanced
stats rows must pass these explicitly via the `attrs` override param, and `Game.seed_changeset/2`'s
`cast/3` allowlist (`lib/pukllay_club/catalog/game.ex:67-93`) must be extended to include the three
new fields or the changeset will silently drop them.

**How to avoid:** Add the three fields to `seed_changeset/2`'s cast list (Game.ex) as part of the
D-05/D-06 schema work; decide during planning whether `game_fixture/1`'s defaults should include a
sample artist/rating/rank (most adjacent tests in the file pass explicit overrides per-test rather
than relying on shared defaults for optional fields — follow that existing convention).
