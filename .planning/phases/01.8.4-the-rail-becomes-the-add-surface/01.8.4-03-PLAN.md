## Accepted budget risk (recorded, not split)

`estimate.tokens: 80000` against a per-plan smart-zone budget of 100000 — **ratio 0.80**, 3 tasks,
3 files. The plan checker flagged this as an advisory `scope_sanity` warning (ADR-2629: advisory,
never a block) and offered either a split or a recorded acceptance. **Accepted, not split.**

`confidence: low` is **derived, not self-rated**: `estimate-calibration` reports
`sample_count: 0` (`min_samples: 3`, `factor: 1`, `applied: false`), so there is no calibration
history for this project yet and `raw_tokens` and `tokens` are necessarily equal.

**Why the split was rejected.** The split the ratio suggests is moving Task 3 — the cap plus the
deletion of the inline add control and its test rewrites — into its own plan. Task 3's deletion
**must** stay in the same plan as the replacement sheet. The inline `Agregar un juego` field is
today the page's only way to add a game, so a commit boundary between "the sheet is complete" and
"the old field is gone" is safe in exactly one order and catastrophic in the other; keeping both in
one plan is precisely the ordering-safety property this plan's `<objective>` states and that the
checker separately verified as correct. Moving it out would reintroduce the risk of a wave boundary
at which the destacada page has no working add control.

**If it runs hot during execution.** Commit per task — Task 1 (search states), Task 2 (the move
path) and Task 3 (cap + deletion) each have an independently runnable `<verify>` and touch the same
three files in sequence, so re-entering at a task boundary needs only `index.ex`, `screens.css` and
`section_live_test.exs` in context plus this plan. Do **not** drop or defer the deletion or any
test rewrite to fit: RAIL-05's absence assertions and the two rewritten shipped tests are the
evidence that the replacement actually replaced something.

### Known limitation carried into this phase (user-accepted, not a defect)

`AdminComponents.snackbar/1` renders `data-timeout` but **no JS consumer dismisses it**
(RESEARCH.md D6, grep-only, never browser-driven). A no-action snack therefore persists until
something replaces it. The user explicitly decided NOT to build a dismiss timer in this phase. In
scope instead (Q7 keeps state management in scope): plan 01's `clear_snackbars/1` clears the three
snackbar assigns **and** the `:info`/`:error` flashes, and gates every snack-setting write — which
is what prevents this plan's three new no-action flash snacks from stacking with the remove,
reorder or place snackbar *in either order*. Clearing only the assigns would not be enough
precisely because the flash snack has no dismiss consumer to retire it.
**Follow-up for a later phase: wire a `data-timeout` consumer.**
