# Phase 01.8.4: Code Review Report

**Reviewed:** 2026-10-09
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

The core arithmetic is correct. I traced `rest_index/2`, `insert_game_at/3` and `move_game_to/3` by hand across these cases:

- The first, middle and last slot.
- A move forward past the mover (`from < slot`).
- A move to slot 0.
- Undo as the inverse call `move_game_to(section, id, from)`.

All of them hold. Bounds checks are correct: `0..n` on insert, `0..length(rest)` on move. The `is_integer(slot) and ...` short-circuit also prevents a raise on a non-integer slot.

The ILIKE path is sound:

- `escape_ilike/1` escapes the backslash first, then `%` and `_`, in the right order.
- Postgres' default ILIKE escape character is the backslash.
- Both the term and the pattern go through bound parameters, so there is no injection.
- `unaccent()` does not touch the backslash escapes.

There are no row-level lock-ordering deadlocks inside the new writers: they take the section row first, then update member rows in ascending order. The unique index is on `(section_id, game_id)` only, so the renumber loop cannot trip a transient position collision.

The CSS source-gate test can fail. It reads the flex basis and the margin out of the stylesheet and does arithmetic on what it read. Its selector anchoring is real, and it flunks loudly on a missing rule rather than passing.

The real defects are these:

- The new row lock protects only the new writers. The pre-existing writers bypass it.
- The LiveView swallows every writer error silently.
- The shared param guard is applied to the new events but not to sibling events in the same module.
- There is a check-then-write gap between the snapshot comparison and the writer.

## Warnings

### WR-01: `add_game/2`, `remove_game/2` and `move_game/3` bypass the section row lock the new writers rely on

**File:** `lib/pukllay_club/catalog/sections.ex:191-205, 399-414, 422-443`
**Issue:** `insert_game_at/3` and `move_game_to/3` take `FOR UPDATE` on the section row. Their docs say this is what stops the cap's count-then-insert and the dense renumber from racing.

The other writers on the same `section_games` rows never take that lock:

- `add_game/2` computes `member_count` and `next_member_position` (`max + 1`) without it.
- `remove_game/2` runs `repack_positions` without it.
- `move_game/3` swaps positions without it.

`add_game` is still used by `undo-remove`, by `set_game_sections/2` (the game form) and by `Admin.SectionLive.Edit`. Two failure modes follow:

1. **Cap overshoot.** `add_game` reads `count = 19` while `insert_game_at` is mid-transaction. Its `INSERT` then blocks on the FK `KEY SHARE` against the locked section row, and proceeds after the commit. The featured section ends up with 21 members, which breaks the D-26 cap.
2. **Duplicate or non-dense positions.** `add_game` reads `max + 1` before the renumber commits. It then inserts a row whose position collides with a renumbered row. Later `insert_game_at` calls heal this, but the stored order is wrong until then.

`add_game` also decides `section.featured` from the caller's struct, which can be stale. `insert_game_at` explicitly avoids that by reading the locked row.

**Fix:** Make every positional writer take the same lock. Extract `locked = lock_section!(section.id)` and use `locked.featured` in `add_game`, `remove_game` and `move_game`. Alternatively, have `add_game` delegate to `insert_game_at(section, game_id, length(members))`.

```elixir
def add_game(%Section{kind: :manual} = section, game_id) do
  Repo.transaction(fn ->
    locked = lock_section!(section.id)
    # ... same checks, using locked.featured
  end)
end
```

### WR-02: Every writer error in the add flow is swallowed; the sheet closes with no feedback

**File:** `lib/pukllay_club_web/live/admin/section_live/index.ex:442-444, 468-470`
**Issue:** `insert_member/3` and `move_member/4` match `{:error, _reason}` and only do `assign(socket, :add_sheet, nil)`. The context returns meaningful reasons:

- `:featured_full`
- `:game_not_found`
- `:already_member`
- `:index_out_of_range`
- `:not_member`

A second admin filling the row or retiring the game makes the user's tap silently do nothing. They see the sheet vanish with no flash and no "Juego agregado" snackbar. That is indistinguishable from a bug. The sibling branch for a changed row does flash.

**Fix:** Map the reason to a flash, and at least handle `:featured_full` and `:game_not_found` distinctly:

```elixir
{:error, reason} ->
  socket |> assign(:add_sheet, nil) |> clear_snackbars() |> put_flash(:info, add_error_message(reason))
```

### WR-03: `remove-game` and `open-member-sheet` still use an unranged `Integer.parse`, reintroducing the crash CTX-04 exists to prevent

**File:** `lib/pukllay_club_web/live/admin/section_live/index.ex:233-242, 253-270`
**Issue:** The new events go through `Params.parse_int/2` with an explicit range. The adjacent `remove-game` handler does `Integer.parse(id)` and passes the result straight to `Sections.remove_game/2`. `remove_game` binds the value into a `delete_all` query. An id above the bigint maximum (`"99999999999999999999"`) raises `DBConnection.EncodeError` and kills the LiveView, which is the exact crash `Params`' moduledoc documents.

`Integer.parse(id)` also raises `FunctionClauseError` for a non-binary `id` (for example a number sent via `pushEvent`).

The module's own header comment promises "every param is parsed through `Params.parse_int/2`", but that only covers the new events. The same module also uses a third parser, `parse_id/1`, for section ids. It accepts any integer and is passed to `Repo.get!`, which also raises on an out-of-range id.

**Fix:** Route all three through the shared guard:

```elixir
case Params.parse_int(id, Params.bigint_range()) do
  {:ok, int_id} -> ...
  :error -> {:noreply, socket}
end
```

Use the same pattern for `parse_id/1`.

### WR-04: The check-then-write gap between the snapshot comparison and the writer lets a concurrent change land the game in the wrong gap

**File:** `lib/pukllay_club_web/live/admin/section_live/index.ex:180-196, 421-471`
**Issue:** `add-sheet-pick` compares `live_member_ids(socket) == sheet.snapshot_ids` using a plain read. It then calls `insert_game_at/3` or `move_game_to/3`, which re-read the rows only inside their own later transaction.

Between the two reads another admin can reorder or add a game. The writer then sees a different list but still accepts the slot, because the slot is only range-checked, not checked against the snapshot. Result: the game is silently placed at a shifted gap, which is what the comment above the branch says the code must never do.

For moves the rest index is computed from `from` in the snapshot. A concurrent change can therefore move the game to the wrong spot while the "Juego movido" snackbar claims success.

**Fix:** Pass the expected member-id list into the writers and compare it under the lock, returning `{:error, :stale}`:

```elixir
# inside the transaction, after ordered_member_rows/1
if expected_ids && ids != expected_ids, do: Repo.rollback(:stale)
```

### WR-05: `Params.parse_int/2` accepts `+5` and zero-padded forms, contradicting its "strict" contract, and no test covers it

**File:** `lib/pukllay_club_web/live/admin/params.ex:37-41`; `test/pukllay_club_web/admin_params_test.exs:33-46`
**Issue:** The moduledoc says "no trailing junk, no exponent, no fraction, no leading whitespace" and calls the parse strict. `Integer.parse("+5")` returns `{5, ""}`, and `"007"` returns `{7, ""}`. Both are accepted. They are harmless to a range check, but they let two different wire strings address the same slot or game id. The hostile-input table, which is the test's stated purpose, has no `"+1"` and no `"01"` entry, so the contract is neither enforced nor pinned.

**Fix:** Either reject a leading `+` and leading zeros explicitly, or narrow the doc to match behaviour and add the cases to `@hostile_values` (or to an "accepted forms" test).

```elixir
{int, ""} when binary_part(raw, 0, 1) != "+" -> check_range(int, range)
```

### WR-06: Row-lock correctness is asserted only sequentially; nothing proves the lock blocks

**File:** `test/pukllay_club/catalog/sections_test.exs:372-444`
**Issue:** The "mixed-writer invariant: any interleaving of add_game, insert_game_at and remove_game" test is one fixed sequence on one process. It cannot detect WR-01. The "cap is read from the locked row" tests do prove the stale-struct fix. Nothing proves that a second caller actually blocks on the `FOR UPDATE`, which is the stated reason for the lock. All the tests run in the SQL sandbox with `async: true`, so true concurrency is not exercised. The test name over-claims.

**Fix:** Add a real two-connection test in a `DataCase` with `async: false` and `shared: true`. Hold the lock in one transaction, start `insert_game_at` in a `Task`, and assert it does not complete until the first commits. Rename the existing test to say "sequential".

### IN-01: Hard-coded "20" in the cap flash duplicates the cap constant

**File:** `lib/pukllay_club_web/live/admin/section_live/index.ex:141`
**Issue:** The text `"Ya hay 20 juegos..."` carries its own literal `20`. `Sections.featured_cap/0` exists precisely so "a caller never carries a second `20` literal".
**Fix:** Interpolate it: `"Ya hay #{Sections.featured_cap()} juegos. ..."`.

### IN-02: `refute screens() =~ "prefers-reduced-motion: reduce"` is a repo-wide ban, not a gate on this feature

**File:** `test/pukllay_club_web/admin_web_rail_css_test.exs:~255`
**Issue:** The assertion goes red the moment any unrelated rule in `screens.css` legitimately adds a `reduce` query. It would also pass if the landing rule were ungated but spelled differently. The sibling containment test is the real gate. This one is brittle without adding protection.
**Fix:** Scope it to the landed selector (assert that no `reduce` block mentions `pk-admin-web-land`), or drop it.

### IN-03: Unused-by-design error branches in `Sections` docs versus callers

**File:** `lib/pukllay_club/catalog/sections.ex:226-232`
**Issue:** The docs list `:index_out_of_range` and `:game_not_found` as reachable results, but the LiveView range-checks the slot before calling and treats every error identically (see WR-02). The documented error surface is untested at the UI layer, which is the same gap.
**Fix:** Resolve together with WR-02.
