**Renumber pattern to generalise** (l.223-230). Position is not unique-indexed, so there are no collision concerns:

`update_member_position/2` is an existing private helper used here. I did not open its body (it is outside the ranges read), so confirm its signature before reuse. New code: load ordered ids, `List.insert_at/3` or delete-then-insert, rewrite `1..n`, and skip rows whose position is unchanged.

**Transaction/lock shape from Shelves** (`shelves.ex` l.717-740, trimmed):
```elixir
def place_copy(copy_id, shelf_id, index) when is_integer(index) do
  Multi.new()
  |> Multi.run(:copy, fn repo, _ -> fetch_copy(repo, copy_id) end)
  |> Multi.run(:lock, fn repo, %{copy: copy} -> lock_estantes(repo, [copy.shelf_id, shelf_id]) end)
  # CR-01: the :copy read happens BEFORE the lock ... re-read it here, inside the lock
  |> Multi.run(:fresh_copy, fn repo, %{copy: copy} -> fetch_copy(repo, copy.id) end)
  ...
  |> Repo.transaction()
  |> case do
    {:ok, %{fresh_copy: original, moved: moved}} ->
      {:ok, %{moved: moved, previous_shelf_id: original.shelf_id, previous_position: original.position}}
    {:error, _step, reason, _changes} -> {:error, reason}
  end
end
```
Clamp idiom at `shelves.ex` l.831-834: `target = index |> max(0) |> min(count)`. This phase must NOT clamp. It returns `{:error, :index_out_of_range}` (CTX-04).

Do not copy Shelves' shift loops (l.835-845). Shelves has a unique `(shelf_id, position)` index and 0-based positions. Sections has neither.

**Stale-client guard** is in the LiveView, not the context (see `index.ex` below). The context's guard is the under-lock bounds check.

**Return shapes (RESEARCH §1):** `{:ok, %{section:, index:}}` for insert, `{:ok, %{section:, from:, index:}}` for move, with `:automatic_section | :already_member | :featured_full | :index_out_of_range | :game_not_found | :not_member` as error atoms. Use `@max_bigint` guarding (see Catalog `catalog.ex` l.143, 179) before `Repo.get(Game, id)`, and reject `:retired`.

**FOR UPDATE:** not present anywhere in the repo that I opened. Shelves uses `pg_advisory_xact_lock` (`shelves.ex` l.787). The RESEARCH recipe uses `from s in Section, where: s.id == ^id, lock: "FOR UPDATE"`. That is a new idiom here, but it is plain Ecto.

### `lib/pukllay_club_web/live/admin/params.ex` (new utility)

**Existing guards for untrusted params (the question asked):**
- `PukllayClubWeb.CatalogFilters.parse_int/1` (`catalog_filters.ex` l.68-78): returns `nil` for nil, `""`, non-binary, and unparseable. It accepts trailing junk (`{n, _rest}`), so `"1abc"` parses as 1, and it has no range. Not suitable as-is.
```elixir
def parse_int(nil), do: nil
def parse_int(""), do: nil
def parse_int(str) when is_binary(str) do
  case Integer.parse(str) do
    {n, _rest} -> n
    :error -> nil
  end
end
def parse_int(_non_binary), do: nil
```
- Private `parse_id/1` in `index.ex` (l.262-276, above), `edit.ex` and `estante_live/index.ex` (l.539-546): strict `{int, ""}`, no range.
- `Catalog` has the range idiom `@max_bigint 9_223_372_036_854_775_807` and `defp fetch_by_id!(int_id) when int_id in 1..@max_bigint` (`catalog.ex` l.143, 179).

So no existing module has a `parse_int(raw, range)` guard. The new module combines the strict `{int, ""}` of `parse_id` with an `in range` check, and returns `{:ok, int} | :error`. Accept integer or binary input, since `JS.push value:` delivers integers (comment at `index.ex` l.~264).

Module namespace: Index is `PukllayClubWeb.Admin.SectionLive.Index` (test module `PukllayClubWeb.Admin.SectionLiveTest`), so `PukllayClubWeb.Admin.Params` at `lib/pukllay_club_web/live/admin/params.ex` fits.

### Untrusted params
**Apply to:** every new `handle_event` in `index.ex`. Parse with `Params.parse_int(raw, range)`; slot range is `0..length(live_ids)` from a fresh read, game id is `1..9_223_372_036_854_775_807`.
