# Phase 01.3.1: Game Image Quality & Multi-Image Gallery - Research

**Researched:** 2026-09-01
**Domain:** Fix-and-rerun on an already-shipped Elixir/Phoenix BGG image-enrichment pipeline
(`ImagePipeline`) and an already-shipped LiveView multi-image gallery/lightbox. No new UI
capability, no new external service — this is a data-correctness + CSS-treatment fix plus a
backfill across ~434 existing rows.
**Confidence:** MEDIUM overall. The codebase-internal findings (all `[VERIFIED: path:lines]`) are
HIGH confidence — this phase's two riskiest technical questions (D-02 gallery-source feasibility,
and whether existing image variants are square-cropped) are both resolved by reading source, not
by inference. The one genuinely external question — whether BGG exposes *any* usable
gameplay/component-photo API — is answered as **"no viable path found in this session,"** which is
itself an actionable, MEDIUM/LOW-confidence-bounded finding (see D-02 section below); it is not
left open.

## Summary

This phase has three independent work-streams, and research materially changes the shape of one
of them:

1. **Gallery source (D-01/D-02/D-03).** The bug is confirmed at the code level:
   `ImagePipeline.process_gallery/3` builds the gallery from *other BGG edition/version box-art
   images*, filtered only by "not the chosen cover," with no language gate — so a game with
   several international editions shows non-Spanish box covers as "extra photos." **No viable way
   to fetch BGG's real gameplay/component-photo gallery was found in this research session** (see
   below) — this was already flagged as an open, unresolved BGG API question in Phase 1's own
   `01-COVERAGE.md`, and this session's direct probes reconfirm it. Combined with D-03's explicit
   acceptance of an empty gallery as a fine outcome, **the recommended fix is to stop sourcing the
   gallery from other-edition box art and return an empty gallery** rather than substitute a
   different-but-still-wrong data source. This is a smaller feature than D-01's original ask
   ("real gameplay/component photos") — flag this explicitly to the user before/during planning,
   per D-02's own instruction to "surface the constraint... before implementing a workaround."
2. **Aspect ratio / letterbox (D-04/D-05/D-06).** Verified against the pinned `image` hex package
   (v0.72.0, vendored in `deps/`): the pipeline's `Image.thumbnail(vimage, width)` call passes no
   `:crop`/`:fit` option, so its documented default (`crop: :none`, "resize to fit") already
   preserves the source aspect ratio — **existing WebP variants are NOT square-cropped at
   generation time.** This means the D-04 letterbox fix is **CSS-only** (`object-fit: cover` →
   `object-fit: contain` at each call site) — no image-pipeline change, no re-resize, no backfill
   needed for this part. One surface (the lightbox's `<img class="pk-lightbox-img">`) **already
   ships `object-fit: contain`** — do not re-touch it; only the resting card, hover/sheet preview,
   and the detail page's own cover image still use `object-cover`.
3. **Backfill (D-07/D-08).** Because (1)'s recommended fix produces an *empty* gallery for
   essentially every affected game (no new image bytes to upload), the backfill is **not** a
   BGG-refetch-and-reprocess job like `mix catalog.seed` — it can be a pure, no-network-I/O,
   DB-only task modeled on `mix catalog.backfill_artists`, since every game's already-stored
   `bgg_payload["versions"]` jsonb already contains everything needed to recompute the corrected
   (empty, in the common case) gallery list. This sidesteps a real landmine: R2's `Storage.put/4`
   silently **skips re-uploading** an already-present object key, and R2 objects are served with
   `Cache-Control: public, max-age=31536000, immutable` — so any backfill design that tries to
   reuse existing `gallery-N-*.webp` key paths for *different* replacement content would silently
   keep serving the old, wrong image indefinitely, at both the app layer and the CDN layer.

**Primary recommendation:** Fix `ImagePipeline.process_gallery/3` to return `{:ok, []}`
unconditionally (delete the other-edition-box-art traversal); ship the D-06 letterbox change as a
shared CSS treatment applied at the ~3 remaining `object-cover` call sites; run the D-07 backfill
as a zero-network, zero-R2-write DB migration task over `bgg_payload`. Surface the D-01 scope
reduction (no real gameplay photos) to the user as an explicit checkpoint before/during planning.

## D-02 Research: BGG Gameplay/Component-Photo Gallery Feasibility

This is the phase's single most consequential research question. Findings, in order of how the
investigation actually unfolded:

**1. Prior Phase 1 research already answered this and was not consulted before D-02 was raised.**
`[VERIFIED: .planning/phases/01-catalog-v1/01-COVERAGE.md:56-69]` — quoting the existing
"Constraint flagged for the developer" note verbatim:

> "BGG XML API 2 exposes **no documented gallery/component-photo endpoint**. The `thing` response
> carries exactly one `image` + one `thumbnail`; the website's own photo gallery is served by an
> undocumented, unauthenticated-in-flux AJAX JSON route that is not part of the registered-
> application XML API surface... 'Table setup / component photos' specifically are **not
> obtainable** from the documented API — this is a missing-information constraint on BGG's side."

This is a **present, affirmative statement** from the project's own prior research (not merely an
absence-of-mention) — it earns `[CITED]`, not `[ASSUMED]`.

**2. The codebase's own parsed BGG response shape confirms there is no gallery data to extract even if the phase wanted to reprocess it.**
`[VERIFIED: lib/pukllay_club/catalog/seed/bgg_client.ex:135-141]` — the `versions=1` XPath extracts
exactly one `image` and one `thumbnail` per `<versions><item>` (edition), plus `name`/`languages`:

```elixir
versions: [
  ~x".//versions/item[@type='boardgameversion']"l,
  name: ~x"./name[@type='primary']/@value"so,
  image: ~x"./image/text()"so,
  thumbnail: ~x"./thumbnail/text()"so,
  languages: ~x"./link[@type='language']/@value"sl
]
```

There is no per-image caption/category field anywhere in this schema (BGG's XML doesn't emit one),
so the "any signal usable to filter gameplay vs. box art" sub-question in the phase brief is moot
for the documented API — there is nothing to filter on beyond the single box-art image per
edition already being consumed.

**3. Direct probes of BGG's website from this session were blocked, which is itself informative.**
Both `curl` (with a standard browser User-Agent) and `WebFetch` against
`boardgamegeek.com/boardgame/305096/.../images` (the actual gallery page) and several BGG/RPGGeek
forum threads returned **HTTP 403 Forbidden** — including against page-fetch attempts with no
authentication at all. The documented XML API itself also returned "Unauthorized" against an
unauthenticated request (expected — a Bearer token is required since 2025-07-02, per the existing
`BggClient` moduledoc; no token was configured in this research session).

- I attempted this positively (ran the actual requests, not just reasoned about them) — see the
  raw output above. This is a **falsification attempt that came back inconclusive** (a network/
  bot-detection block, not a confirmed "the endpoint doesn't exist" or "the endpoint works"), so
  per the absent-evidence provenance rule this is reported as **no observation**, not a declared
  absence — it does not by itself prove infeasibility.
- Combined with finding 1 (Phase 1's own prior research already established there's no documented
  surface) and finding 4 (no third party has published one either), the practical conclusion holds
  regardless: **there is no known, reachable way to get gameplay/component photos from this
  environment or from published community knowledge.**

**4. WebSearch across official docs, third-party BGG API wrapper projects, and community
discussion found no documented or reverse-engineered gallery endpoint.** Checked: the BGG XML
API 2 wiki page (also 403'd), multiple open-source BGG API wrapper projects (`bgg-api` Python/Ruby/
Go, `geekdo-sdk` npm package), a third-party BGG-JSON wrapper (`bgg-json.azurewebsites.net`), and
several BGG forum threads about image URLs — none document or discuss a callable images-gallery
endpoint separate from the XML API's single per-item/per-version `<image>` element. `[ASSUMED —
WebSearch coverage, LOW confidence individually, but consistent with findings 1-2 which are
higher-confidence]`

**Conclusion and recommendation:** Treat "BGG gameplay/component-photo gallery" as **not available
through any surface this project can reach** for this phase. This satisfies D-02's instruction to
"fall back to D-01's intent as closely as possible" in the most literal available sense: D-01's
underlying intent is "don't show wrong/irrelevant images" — the recommended fix (stop pulling
other-edition box art, return an empty gallery) achieves that without inventing scraping
infrastructure this project doesn't have (no headless browser, no session/cookie handling — adding
one would be a new architectural capability, not a small fix, and BGG's own bot-blocking behavior
observed directly in this session makes any scraping approach unreliable even if attempted).
**Per D-02's explicit instruction, surface this scope reduction to the user before/during planning
— "no real gameplay photos in this phase" is a materially smaller deliverable than D-01's original
framing, even though it is explicitly D-03-accepted as an outcome.**

**Rejected middle-ground alternative (documented so it isn't silently reconsidered later without
reason):** Filtering the *existing* other-edition-box-art gallery source to only Spanish-language
editions (still using `bgg_payload["versions"]`, still box art, just language-matched) was
considered. It's technically cheap (no new BGG call — see the Backfill section) but rejected as the
primary recommendation because it still doesn't satisfy D-01's actual ask ("real gameplay/component
photos," explicitly "not alternate-language box art") — it only makes the wrong content
less-embarrassing, not correct. It is worth naming to the user as a fallback-of-the-fallback if an
empty gallery for most games is judged unacceptable during discuss/plan review — it has no
technical blockers and could be a small addition to the same backfill task if that discussion goes
that way. But it does not require a design decision now: an empty gallery covers D-03's accepted
outcome and needs no such filter added.

## Code Insights (Verified This Session)

### `ImagePipeline.process_gallery/3` — the exact bug, and the exact fix surface
`[VERIFIED: lib/pukllay_club/catalog/seed/image_pipeline.ex:60-91]` — the full current
implementation:

```elixir
def process_gallery(item, key_prefix, %Credentials{} = credentials) do
  cover_source_url =
    case select_cover(item) do
      {:ok, url, _source} -> url
      {:error, :no_image} -> nil
    end

  item
  |> Map.get(:versions, [])
  |> Enum.map(&Map.get(&1, :image))
  |> Enum.filter(&usable_image?/1)
  |> Enum.uniq()
  |> Enum.reject(&(&1 == cover_source_url))
  |> Enum.take(@max_gallery_images)
  |> Enum.with_index(1)
  |> Enum.reduce([], fn {source_url, index}, acc ->
    case upload_gallery_image(source_url, key_prefix, index, credentials) do
      {:ok, gallery_url} -> [gallery_url | acc]
      {:error, _reason} -> acc
    end
  end)
  |> then(&{:ok, Enum.reverse(&1)})
end
```

This confirms the bug exactly as CONTEXT.md describes: `item.versions` images are filtered only by
"not the chosen cover" and "usable" (non-blank) — **no `languages` check at all**, unlike
`select_cover/1`'s own `spanish_version?/1` guard three lines above it in the same file. This is
the single function the recommended fix touches; `select_cover/1` (D-08's concern) is a separate,
untouched code path with its own tests.

`[VERIFIED: deps/image/lib/image.ex:4841-4845]` (the vendored `image` 0.72.0 source, matching

> "`:crop` determines if the strategy is 'resize to fit' (crop is `:none`) or 'resize to fill'

the "Claude's Discretion" question about whether new image variants are needed: they are not. The

### The reusable bulk-reprocessing task pattern (D-07)
`[VERIFIED: lib/pukllay_club/catalog/seed/stats_enricher.ex:99-108, 157-173]` — the
`backfill_artists_from_payload/1` shape is the correct template for the D-07 task, **not**
`enrich_from_bgg/2` (which re-hits the live BGG API). Its defining properties, all reusable
verbatim:

```elixir
def backfill_artists_from_payload(opts \\ []) do
  dry_run? = Keyword.get(opts, :dry_run, false)
  games = Repo.all(from g in Game, where: not is_nil(g.bgg_payload), order_by: g.id)
  Enum.reduce(games, %{scanned: 0, updated: 0, deduplicated: 0}, fn game, acc ->
    apply_artists_backfill(game, dry_run?, acc)
  end)
end
```

- Queries games by an existing stored column (`bgg_payload`), not a fresh network fetch.
- Narrow `Ecto.Changeset.cast/3` + `Repo.update/1` (never the full-row `upsert_game!/1` used by
  `catalog.seed`, which would require reconstructing every other field).
- `--dry-run` support, a summary map return, mirrored `Mix.Tasks.Catalog.BackfillArtists` shell
  (`[VERIFIED: lib/mix/tasks/catalog.backfill_artists.ex]`) with the same `dry_run_prefix/1`
  convention.
- **No batching/rate-limit/backoff logic needed** — because there's no network call, unlike
  `enrich_from_bgg/2`/`catalog.enrich_bgg_stats`, which exists specifically to manage BGG's rate
  limit.

**Why this pattern (not `catalog.seed`'s) is correct for D-07's recommended fix:** the corrected
`process_gallery/3` returns `{:ok, []}` unconditionally — there is no new image to download, resize
or upload. The backfill's entire job is: for every game whose `gallery_urls != []` today, set it to
`[]`. That's a data migration over the `games` table, needing neither `bgg_payload` nor a live BGG
call — even simpler than `backfill_artists_from_payload/1`'s own query. Model the new task as
`Mix.Tasks.Catalog.BackfillGallery` (or fold into a rename of `backfill_artists` if the planner
prefers one generic "backfill from already-stored data" task) with the same `--dry-run` shell.

If the planner later adds the rejected middle-ground (Spanish-language-filtered gallery, see D-02
section) instead of an outright empty gallery, the *query* can still stay network-free
(`bgg_payload["versions"]` already holds `image`+`languages` per edition, string-keyed, confirmed
via `StatsEnricher`'s own `Map.get(game.bgg_payload || %{}, "artists")` pattern) — only the
*upload* step would need to run again (new binary content for newly-selected URLs), which reopens
the pitfall below.

## Common Pitfalls

### Pitfall 1: R2 upload idempotency + CDN immutable-cache will silently defeat any backfill that re-uploads to the same gallery key path
**What goes wrong:** A backfill that tries to replace `games/{bgg_id}/gallery-1-large.webp`'s
*content* (same key, different source image) will appear to succeed but keep serving the old,
wrong bytes forever.
**Why it happens:** Two independent layers both work against a same-key overwrite:
`[VERIFIED: lib/pukllay_club/catalog/seed/r2_storage.ex:21-37]` — `put/4` calls `head_object`
first; on a 200 (key already exists) it logs `"R2 object already present, skipping upload"` and
returns the *existing* object's URL without uploading anything. Even if that were bypassed, every
object is uploaded with `[VERIFIED: lib/pukllay_club/catalog/seed/r2_storage.ex:19,54]`
`@default_cache_control "public, max-age=31536000, immutable"` — browsers and any CDN edge cache
are explicitly told this exact URL's bytes will never change for a year.
**How to avoid:** The recommended fix (empty galleries, no re-upload at all) sidesteps this
entirely — nothing is ever written to an already-existing gallery key. If the planner later adds
any variant that *does* need to upload replacement gallery content, it must NOT reuse the existing
`gallery-N-*.webp` key naming — either add a cache-busting/content-addressed suffix to the key, or
add an explicit delete-then-reupload step (new capability; `ExAws.S3.delete_object/2` exists but is
currently an intentional Phase-1 `OPT-OUT` per `01-COVERAGE.md`).
**Warning signs:** A backfill run reports "updated: N" but a hard-refreshed browser (or R2's own
object listing timestamp) shows the old image bytes/date — this is the idempotent-skip firing
silently, not a code bug in the traversal logic itself.

### Pitfall 2: Conflating the gallery-source fix with cover-selection logic
**What goes wrong:** Editing `select_cover/1` (or its call sites) "while in the area" would touch
the separately-accepted 39-game "no Spanish edition found" gap (D-08 explicitly says don't).
**Why it happens:** `process_gallery/3` calls `select_cover/1` once, internally, just to know which
URL to *exclude* from the gallery (`cover_source_url`) — it's easy to misread this as coupling.
**How to avoid:** `[VERIFIED: lib/pukllay_club/catalog/seed/image_pipeline.ex:69-74]` — the call is
read-only (`case select_cover(item) do {:ok, url, _} -> url; ... end`), never mutated, never
re-implemented. The recommended fix only changes what happens to `item.versions` *after* that one
read; `select_cover/1` itself, its tests, and its 39-game exception report are untouched.
**Warning signs:** Any diff that touches `spanish_version?/1`, `select_primary_cover/1`, or the
`@spanish_language_link` module attribute is out of this phase's scope.

### Pitfall 3: Treating `.pk-preview-poster`'s different aspect ratio as a bug to "fix" toward `.pk-card-poster`'s
**What goes wrong:** Reading D-06 as "make every poster the same shape" and collapsing the
hover-preview/sheet's 16:9 container to match the resting card's near-square one (or vice versa).
**Why it happens:** D-06 quotes the sketch-findings doc's "one shared class... never scope the same
visual property to each surface independently" rule, which *sounds* like "one aspect ratio
everywhere."
**How to avoid:** Re-reading the same source document
`[VERIFIED: .claude/skills/sketch-findings-pukllay_club/references/card-interaction.md:45-55]`
clarifies the rule is about **surfaces meant to look the same** drifting apart (the historical bug
was the *hover-portal* and *mobile sheet* — both meant to be the identical preview — using
different ratios). The resting card and the expanded preview are **not** meant to look the same;
they are deliberately different UI moments with deliberately different shapes. D-06's actual ask is
about the *treatment* (object-fit + fill color) being one shared mechanism, not about unifying
unrelated aspect ratios. See the call-site inventory above.
**Warning signs:** A diff that changes `aspect-ratio` values, not just `object-fit`/background, on
`.pk-card-poster` or `.pk-preview-poster` without an explicit user request to do so.

### Pitfall 4: Assuming the D-07 backfill needs `mix catalog.seed`'s BGG-refetch machinery
**What goes wrong:** Building the backfill as a full BGG re-fetch (rate-limited batches, retry/
backoff, `--limit`) when the recommended fix needs none of that.
**Why it happens:** D-07's own wording says "reuse the existing bulk-reprocessing task pattern
(`mix catalog.enrich_bgg_stats`, `mix catalog.backfill_artists`)" — plural, and one of those two
*does* hit the network.
**How to avoid:** Model on `catalog.backfill_artists` specifically (see Code Insights above), not
`catalog.enrich_bgg_stats` — the corrected gallery logic needs no fresh BGG data at all, only a
DB-column reset (or, at most, a read of already-stored `bgg_payload`).
