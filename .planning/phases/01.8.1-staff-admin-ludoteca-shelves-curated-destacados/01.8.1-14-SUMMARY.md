## Deviation: the home-section comparison method

Task 3 prescribed comparing `curl -s https://pukllay.club/ | grep -o 'id="carousel-[^"]*"'`
against a pre-deploy record of the same. **That method cannot work, for two independent
reasons, and was substituted.**

1. **The pre-deploy record never existed.** Task 1 said to record the section titles *in the
   SUMMARY* — and this SUMMARY is being written after the deploy (see "Why this plan closed
   out manually"). There was no comparison floor to compare against.

2. **`curl` cannot see the sections at all.** The home page is LiveView and its dead render is
   entirely skeletons: the static HTML contains **56 skeleton elements and 0 `href="/juegos/"`
   links**. The prescribed grep returns `carousel-skeleton-1 … carousel-skeleton-8`, never a
   section title — before the deploy just as much as after.

   This is worth naming precisely: had the grep simply been run and compared, **both sides
   would have been identical skeleton lists and the check would have "passed" while examining
   nothing.** That is the same silent-false-pass shape as the baseline-overwrite hazard
   documented in CLAUDE.md's "GSD Decimal-Phase Resume Bug" section — a check that reports
   success without testing its subject.

**Substituted method:** loaded the live page in a real browser at 420px (mobile-first) so the
LiveView socket connects, then read the rendered DOM. Result — connected, **0 skeletons, 139
game links, 7 sections**:

| id | Title | Games |
|----|-------|-------|
| `carousel-section-2` | Crea conexiones | 20 |
| `carousel-section-3` | Equipo ganador | 20 |
| `carousel-section-4` | Duelos memorables | 19 |
| `carousel-section-5` | Descubre el hobby | 20 |
| `carousel-section-6` | Ingenio estratega | 20 |
| `carousel-section-7` | Nivel experto | 20 |
| `carousel-section-8` | Recientemente añadidos | 20 |

`carousel-section-1` is **absent** (`hasSection1: false`, lowest id 2). That is the expected
D-22/D-24 behaviour, not a missing row: section 1 is the hand-picked featured hero and an empty
section is hidden. It is empty because nothing has been curated into it yet. Every other
section renders titled and populated.

**Claim boundary:** this verifies the home page is *correct now*. It does **not** verify
*unchanged from before*, because no pre-deploy record was ever captured. Recorded honestly
rather than marked as a passed comparison.

## Why this plan closed out manually

Plan 14 was paused after Task 1 on 2026-09-14 pending the admin UI redesign decision, leaving
production commits (`0baeafc`) with no SUMMARY. `execute-phase`'s `safe_resume_gate` exists to
catch exactly that — but it is blind to this repo's decimal phase numbers: `$((10#01.8.1))`
aborts with `bad floating point constant`, and its anchored regex expects `feat(1-14):` where
the real commit is `feat(01.8.1-14):`, matching 0 commits. A bare `/gsd-execute-phase` would
therefore have re-run Task 1 from the top and overwritten the 435 baseline with a post-deploy
count, silently destroying the migration check.

Writing the SUMMARY first would have been the opposite error — `has_summary` then skips the
plan entirely, so Tasks 2 and 3 would never have run.

The recovery path `safe_resume_gate` itself documents was used instead: *"close out manually —
inspect commits, write SUMMARY.md, then update STATE/ROADMAP."* Full detail in `.claude/CLAUDE.md`
§ "GSD Decimal-Phase Resume Bug".
