# Phase 01.8.1: Staff Admin — Ludoteca, Shelves & Curated Destacados - Context

**Gathered:** 2026-09-13
**Status:** Ready for planning

<domain>
## Phase Boundary

Club staff (owner + up to 3 invited accounts) sign in via passwordless magic link and operate an
admin area to: add games by BGG ID (async enrichment in production) and edit/retire them; record a
shelf-level location for every game via a phone-first tap-to-assign flow; manage the home page's
**sections** (staff-created, many-to-many, per-section sort, first one featured); and audit games
whose CSV `weight_band` disagrees with `bgg_weight`. Production outbound email (provider + Swoosh
adapter + SPF/DKIM) is part of this phase because login depends on it.

**Scope change vs. ROADMAP.md (agreed in discussion):** success criterion 4 ("rename the first
carousel and hand-pick its games; all other rows remain automatic") is superseded by fully
**managed sections** (D-19..D-29). This pulls the "fully managed carousels (Option B)" half of seed
`saturday-sessions-and-managed-carousels` forward into this phase (date windows excluded). ROADMAP.md
criterion 4 must be rewritten during planning to match.

**Reversal of a prior decision:** 01.7 D-04 kept BGG/R2/Gemini credentials off the production host.
This phase deliberately reverses that — production now fetches BGG, uploads to R2, and calls Gemini
(D-02, D-05, D-06). Secrets go through `.kamal/secrets` + `deploy.yml` `secret` env vars.

</domain>

<decisions>
## Implementation Decisions

### Adding, editing, retiring games
- **D-01:** Staff add a game by pasting a BGG ID or BGG URL. The game is created immediately as a
  **draft**, and BGG enrichment runs asynchronously in production (background job, not the request
  path). Staff then complete the club-owned fields (sections, weight band, shelf, units…) before
  publishing.
- **D-02:** The async enrichment job reuses the existing seed pipeline modules
  (`Catalog.Seed.BggClient`, `ImagePipeline`, `R2Storage`, `DescriptionTranslator`, OG card
  generation) — it downloads BGG images and uploads them to the same R2 bucket as every existing
  game, and generates the OG card. — **Reversibility:** costly — puts BGG token, R2 write
  credentials, and Gemini key into production secrets, reversing 01.7 D-04.
- **D-03 (revised 2026-09-14, after verification, gap CR-B-01, user decision):** games may share a
  BGG id because they are editions of one another (example: BGG 163412, "Patchwork" and "Patchwork Andino").
  Adding a BGG id that already belongs to any game (draft, published, or retired) creates
  nothing up front — the admin shows those games ("Ya tenés {nombre} con este BGG ID. ¿Es otra
  edición?", each linked to its editor), and only an explicit "Sí, agregar edición" inserts the new
  draft. Accidental double-submits never create two drafts: a per-BGG-id transaction advisory lock
  with an in-lock re-check, plus `phx-disable-with` on both buttons. `games.bgg_id` stays
  non-unique — a unique or partial-unique index is wrong for this project. Fetch failures retry
  automatically; the draft shows a visible error state ("error al traer datos de BGG") with a
  **Reintentar** button.
- **D-04:** New games stay **draft (not public)** until staff press **Publicar**. Drafts never appear
  in the catalog grid, carousels/sections, filters/counts, sitemap, or `/juegos/:id`.
- **D-05:** R2 image upload happens in production (not BGG hotlinking).
- **D-06:** Spanish description is Gemini-translated asynchronously in production from the BGG
  English text; staff can edit the Spanish result before/after publishing.
- **D-07:** Editable fields are **club-owned only**: name, units, `weight_band`, section membership,
  shelf location, `is_expansion`, Spanish description. BGG-derived facts (players, playtime, age,
  mechanics, themes, designers, artists, publishers, rating, rank, `bgg_weight`, images) are
  read-only in the admin.
- **D-08:** "Remove" = **retire** (soft delete), restorable. Retired games disappear from every
  public surface (same set as D-04). Planner decides what an old `/juegos/:id` link for a retired
  game shows (404 vs a "ya no está en la ludoteca" page). — **Reversibility:** one-way — adds a
  status column every public query must filter on.
- **D-09:** **The database is the source of truth.** The CSV seed path is retired entirely
  (`mix catalog.seed` / `Catalog.Seed.CsvImport` removed or disabled) so nothing can overwrite
  admin edits via the `replace_all_except` upsert. Enrichment/backfill tasks that don't clobber
  club-owned fields may remain. — **Reversibility:** one-way — CSV stops being an editing surface;
  AGENTS.md re-seed runbook (01.7 D-04/D-05) must be updated.

### Shelves & locations
- **D-10:** Shelves are a **staff-managed table** (name + walking order), created/renamed/reordered
  in the admin — not hardcoded. Room layout for initial setup: main run 4 long + 4 short (sorted
  light→heavy), Cooperativos, Pocket, Piso (long + short).
- **D-11:** **One location per game** (shelf only, no in-shelf position). `units > 1` copies are
  assumed stored together; per-copy location stays in Phase 4.
- **D-12:** Initial assignment is **tap-to-assign ("walk the shelf")**: staff pick a shelf, then tap
  each game on it; each tap saves immediately. The owner will cover all ~400 games **across multiple
  sessions**, so progress must persist naturally and be visible ("N/400 ubicados").
- **D-13:** Finding games in that flow: type-ahead name search at top, plus the list of
  not-yet-assigned games below it; tap = assign.
- **D-14:** Tapping a game already assigned to another shelf **moves it instantly** and shows a
  toast "Movido desde L2 · Deshacer".
- **D-15:** Pick/restore list = games **grouped by shelf in walking order**, names inside each
  group, plus a "Sin ubicar" group; filterable by name.
- **D-16:** Shelf location is **staff-only** — never shown on the public site.

### Managed sections (replaces "curated Destacados")
- **D-17:** The club's rows (Crea conexiones, Equipo ganador, Duelos memorables, and future ones like
  "Spiel des Jahres") are the owner's **sections**, not fixed hashtags. Staff can create, rename,
  reorder, and hide sections. A game can belong to **many** sections.
- **D-18:** Section order on the home page is staff-controlled; the **first section is the featured
  one**.
- **D-19:** Each section's game order is either **manual** (hand-ordered) or **automatic by rule**
  (name / BGG weight / BGG rating / recently added).
- **D-20:** The 3 difficulty rows (Descubre el hobby / Ingenio estratega / Nivel experto) remain
  **one `weight_band` per game** — it still drives the Nivel filter, level badge, and band audit.
  On the home page they are **automatic sections** staff can rename/reorder/hide, but membership
  always comes from `weight_band`, never hand-picking.
- **D-21:** "Recientemente añadidos" becomes an automatic section (same reorder/rename/hide
  controls, membership by rule).
- **D-22:** Migration: the 3 existing hashtag tags (`#CreaConexiones`, `#EquipoGanador`,
  `#DuelosMemorables` in `games.tags`) become sections **keeping their current members**
  (auto-sorted by name, as today). A hand-picked featured section is created empty. Home page looks
  the same on day one apart from the empty featured section being hidden. — **Reversibility:**
  one-way — data migration from `games.tags` into section membership.
- **D-23:** Today's automatic "Destacados del club" rule (union of the 3 hashtags) is **dropped**;
  featured is purely hand-picked.
- **D-24:** A section with no visible games (empty, or all members draft/retired) is **hidden** from
  the home page — no fallback.
- **D-25:** Picking/ordering on a phone: type-ahead search to add, ↑/↓ buttons to reorder, remove per
  item. No drag-and-drop.
- **D-26:** The featured section is capped at **~20 games**; other sections are uncapped.
- **D-27:** The catalog filter modal's existing tags facet becomes a **sections facet** listing
  visible (non-hidden) staff-created sections.
- **D-28:** Home layout: the featured section gets a **distinct "hero"-style treatment at the top**;
  the other sections render as horizontal rails below. Exact visual design goes through
  `/gsd-ui-phase` (or a sketch) — not decided here.

### Band audit
- **D-29:** Mismatch = a game's `weight_band` differs from the band implied by `bgg_weight` using the
  **existing reviewed thresholds** (<1.9 Descubre el hobby, 1.9–3.1 inclusive Ingenio estratega,
  >3.1 Nivel experto — `HashtagNormalizer.band_for_peso/1`). Move the thresholds to one shared place
  (e.g. `Catalog.Vocabulary`) so audit and any future use can't disagree.
- **D-30:** For each mismatch staff either **correct** the band or **keep** it. "Keep" stores an
  override (band-reviewed) that hides the game from the audit list; it reappears only if its
  `bgg_weight` later implies a different band than when it was kept.

### Staff auth, invites, admin shell
- **D-31:** `phx.gen.auth` magic link, invite-only, long-lived remember-me, role on a users table
  shareable with Phase 2 members (carried from `.planning/notes/staff-admin-decisions.md`).
- **D-32:** The **owner** account is created once via a release command over SSH
  (`bin/pukllay_club eval ...`). The owner then **invites staff by email in `/admin`** (sends a magic
  link) and can remove staff. No public registration route exists.
- **D-33:** Roles: **owner** manages staff (invite/remove); otherwise owner and staff have equal
  access to games, shelves, sections, and band audit. `/admin` rejects non-staff.
- **D-34:** Entry: login lives at an unlinked `/admin/ingresar` (exact path at planner's discretion).
  When a staff session exists, the public header shows an **Admin** link and `/juegos/:id` shows
  **Editar**; visitors see no change.
- **D-35:** Admin home is a **task dashboard** of cards: Juegos (+ borradores count), Estantes
  (N/400 ubicados), Secciones, Revisar niveles (N discrepancias), Staff (owner only). Mobile-first.

### Claude's Discretion
- Exact route paths, schema/table names, status enum naming (draft/published/retired).
- Retired-game `/juegos/:id` behavior (D-08).
- Background job mechanism — Oban is the project's stated queue but is **not yet in `mix.exs`**;
  adding it here is expected.
- How auto-sort rules are stored per section; how section membership is modeled (join table with
  position is the obvious shape).
- Email provider choice (D-36) — researcher compares, user confirms.

### Folded Todos
- **D-36 — `email-provider-and-dns` (Pick transactional email provider, wire Swoosh in prod, set
  SPF/DKIM):** hard prerequisite for magic-link login. GCP blocks outbound port 25, so use an HTTP
  email API via a Swoosh adapter (`Swoosh.ApiClient.Req` is already configured in `config/prod.exs`).
  Researcher compares Resend / Brevo / Postmark free tiers and Swoosh adapter support; user confirms.
  Adapter configured in `config/runtime.exs`, API key via `.kamal/secrets`. Add SPF + DKIM (+ DMARC)
  for `pukllay.club`. Done = a real magic-link email from production lands in a Gmail inbox.

</decisions>

## Existing Code Insights

### Reusable Assets
- `lib/pukllay_club/catalog/seed/` — `bgg_client.ex`, `image_pipeline.ex`, `r2_storage.ex`,
  `description_translator.ex`, `stats_enricher.ex`, `expansion_classifier.ex`, `og_card_backfill.ex`:
  the building blocks for the async add-game job (D-02).
- `HashtagNormalizer.band_for_peso/1` — reviewed band thresholds for the audit (D-29).
- `Catalog.Vocabulary` — `weight_bands/0`, `weight_band_level/1`, editorial tag list (to be replaced by sections).
- `PukllayClubWeb.Components.CarouselRow` + in-row infinite scroll (`Catalog.carousel_page/3`) — reuse for section rails.
- `FilterModal` tags facet (`attr :tags`) — becomes the sections facet (D-27).
- Swoosh + `Swoosh.ApiClient.Req` already present; `PukllayClub.Mailer` exists.

### Established Patterns
- Carousel rows are hardcoded in `Catalog.carousel_row_specs/0` + `row_query/1` string dispatch
  (T-01-37: never `String.to_atom` client keys). Sections replace this with DB rows; keep the
  "page 1 and page N use the identical query" invariant and the `:id` tiebreaker.
- `Catalog` upsert uses `on_conflict: {:replace_all_except, [:id, :inserted_at, :search_vector]}` —
  the reason the seed must be retired (D-09).
- Seed-derived state lives on `games` columns (`weight_band`, `tags`, `is_expansion`); `tags` is the
  migration source for sections (D-22).
- Strict CSP with nonce (`PukllayClubWeb.CSP`); SEO computed in plugs before LiveView mount
  (`Plugs.GameSEO`, `Plugs.SiteSEO`) — drafts/retired must be excluded there too.
- No auth exists yet; no users table.

### Integration Points
- `router.ex` — new `/admin` scope with staff auth pipeline; public `:browser` pipeline needs
  current-staff fetch for the Admin/Editar affordances (D-34).
- Every public read path must filter out draft/retired: `Catalog.filter_games/1`, `count_games`,
  carousel/section queries, `SitemapController`, `Plugs.GameSEO`, `CatalogLive.Show`.
- `CatalogLive.Index` — home rows switch from `list_carousel_rows/0` to DB-driven sections with a
  featured hero (D-28).
- `config/runtime.exs` + `.kamal/secrets` + `config/deploy.yml` — email, BGG, R2, Gemini secrets.
- `mix.exs` — add Oban (not currently a dependency).
