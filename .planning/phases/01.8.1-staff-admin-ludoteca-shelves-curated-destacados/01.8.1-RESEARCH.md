## Summary

This phase adds the project's **first authentication system**, its **first background job queue**,
and its **first production outbound-email dependency**, on top of an existing single-context
(`Catalog`) Phoenix 1.8 LiveView app that today has no admin surface at all. The good news: Phoenix
1.8.9's `mix phx.gen.auth` generator — read directly from the installed package source in this
session — already generates almost exactly the D-31/D-32 flow (passwordless magic-link login,
long-lived remember-me, a `for_user/1` scope struct) as one of its two built-in login paths; the
work is *subtracting* the parts this project doesn't want (public registration, password login,
password settings) rather than building magic-link auth from scratch. The generator's magic-link
token doubles as the invite mechanism: creating an unconfirmed `User` row and calling
`deliver_login_instructions/2` sends a "confirm and log in" email — exactly D-32's "owner invites
staff by email, sends a magic link."

The second major body of work is `Catalog.Game` gaining new columns (`status`, `shelf_id`,
`band_reviewed_*`) and two new join-table-backed concepts (`shelves`, `sections`/`section_games`)
that must integrate with **every existing public read path** (`filter_games/1`, `count_games/1`,
the 8 hardcoded carousel rows, `sitemap_entries/0`, `GameSEO`/`SiteSEO` plugs) without breaking any
of them — this codebase has zero draft/retired concept today, confirmed by direct read of
`PukllayClub.Catalog.Game` and its migration. The single highest-risk mechanical step is the
`status` column's **default value**: production already holds ~434 live games (per `01.7`'s
restore), so a migration that adds `status` with any default other than `"published"` — or a
`NOT NULL` add with no default — silently unpublishes the entire live catalog on deploy.

Third, this phase needs its first background job runner (Oban — not yet a dependency, confirmed
absent from `mix.exs`/`mix.lock`) to move BGG enrichment + R2 upload + Gemini translation off the
request path per D-01/D-02, and its first real transactional-email provider (Resend recommended —
see Standard Stack) to satisfy GCP's outbound-port-25 block.

**Primary recommendation:** Run `mix phx.gen.auth Accounts User users --live`, then delete the
password-login half and the public registration route/LiveView entirely (leave the generated
`hashed_password`/`confirmed_at` columns in place, just never populate/expose them) rather than
hand-writing magic-link auth; add a `status` column to `games` with an explicit `"published"`
default/backfill (mirroring the `add_games_is_expansion` migration's own precedent for a
backfilling migration that runs automatically via Kamal's pre-boot `bin/migrate`); add Oban 2.24 as
the job runner for the reused `Catalog.Seed.*` pipeline modules; use Resend as the email provider.

### Pattern 1: Passwordless-only `phx.gen.auth` (subtractive customization)

**What:** Run the standard generator, then delete the password-login branch, the public
registration route/LiveView, and the `update-password` route — leave the generated
`hashed_password`/`confirmed_at` columns and `password_changeset` function in place (harmless if
unused) rather than editing the generated migration, since a future feature could reasonably want
password login for a different scope.

**When to use:** Exactly this phase's D-31/D-32 requirement — invite-only, magic-link-only staff
auth, shared `users` table with future member accounts.

**Example (confirmed generator behavior, read from `deps/phoenix/priv/templates/phx.gen.auth/`
this session):**
```elixir
# The generator's context_functions.ex.eex already implements the exact "invite" semantics:
# create an unconfirmed user with no password, then call deliver_login_instructions/2 —
# the first login both confirms the account AND logs the staff member in.
def invite_staff(email, invited_by_scope) do
  %User{}
  |> User.email_changeset(%{email: email})
  |> Ecto.Changeset.put_change(:role, "staff")
  |> Repo.insert()
end

# Elsewhere (admin LiveView), after insert:
Accounts.deliver_login_instructions(user, &url(~p"/admin/ingresar/#{&1}"))
```
Source: `deps/phoenix/priv/templates/phx.gen.auth/context_functions.ex.eex` (read this session) —
`deliver_login_instructions/2`'s docstring: *"Delivers the magic link login instructions to the
given user."* The notifier itself branches on `confirmed_at: nil` to send a "Confirmation
instructions" vs. "Log in instructions" email — both resolve to the same magic-link token flow.

## Common Pitfalls

### Pitfall 1: `games.status` default silently unpublishes the entire live catalog

**What goes wrong:** Adding a `status` (or similar) column to `games` with `null: false` and no
default — or a default of `"draft"` — would, on the next production deploy, cause **every one of
the ~434 existing live games** to fail every public query's new `WHERE status = 'published'`
filter, effectively emptying the public catalog instantly.

**Why it happens:** The obvious "safe-looking" default for a new draft/published/retired enum is
often the first value alphabetically or logically (`draft`), but that default is only correct for
*newly inserted* rows going forward — existing rows need `"published"` specifically, because they
are already live and were never drafts.

**How to avoid:** Mirror the exact `add_games_is_expansion` migration pattern (Pattern 2 above):
`add :status, :string, null: false, default: "published"` in the `alter table` (so the column-level
default handles all existing AND future plain-insert rows correctly for the common case), with the
add-game admin flow explicitly setting `status: "draft"` on insert (D-01) rather than relying on
column default divergence between "the CSV-seeded past" and "the admin-inserted future."

**Warning signs:** A UAT/manual check immediately after this phase's first prod deploy that the
home page and catalog grid still show ~434 games, not zero — this should be an explicit
`checkpoint:human-verify` step in the plan, not just a passing test suite (a test suite using
fresh fixtures would never catch a *migration default* bug against pre-existing production rows).

### Pitfall 2: Every existing carousel-row/filter/SEO query must be updated in lockstep, or a draft/retired game leaks publicly

**What goes wrong:** This codebase currently has **no** visibility/status concept at all — verified
this session by reading `PukllayClub.Catalog.Game`'s full schema and its migration, and by
`Catalog.sitemap_entries/0`'s own moduledoc, which states outright: *"There is no visibility,
draft, or soft-delete column on this schema today ... A future phase adding such a column must add
a filter here at the same time, or a hidden/draft game would still appear in the public sitemap."*
`[VERIFIED: lib/pukllay_club/catalog.ex:188-200]` This is a self-documented trap left specifically
for this phase.

**Why it happens:** The status filter needs to be added independently to at least 6 separate call
sites: `filter_games/1`/`base_filtered_query/2` (catalog grid), `count_games/1` (same pipeline, but
worth naming since a naive dev might filter one and forget the other doesn't automatically inherit
it — in fact it does, since `count_games/1` calls `base_filtered_query/2` too, but a *new* read
path added later might not), the section/carousel row queries (`row_query/1` replacement),
`sitemap_entries/0`, `PukllayClubWeb.Plugs.GameSEO`'s game resolution (`Catalog.get_game!/1`), and
`PukllayClubWeb.Plugs.SiteSEO` if it independently queries games for counts anywhere.

**How to avoid:** Add the status filter as close to the single shared query-building surface as
possible (`base_filtered_query/2` already centralizes most read paths); for `get_game!/1` (used by
both the admin edit screen AND the public `GameSEO`/`CatalogLive.Show` path), the cleanest fix is
two distinct functions — `get_game!/1` (admin, no status filter, needed to edit a draft) and a new
`get_published_game!/1` (public, filters status) — rather than adding a boolean flag param to the
existing function, since silently branching a shared function on a caller-supplied flag is exactly
the kind of easy-to-forget-at-a-new-call-site pattern the sitemap moduledoc is warning about.

**Warning signs:** A draft or retired game becomes reachable at `/juegos/:id`, appears in
`sitemap.xml`, or shows up in a home-page section/carousel — each of these needs its own explicit
test, since they are 4+ independently-reachable surfaces, not one shared code path.

### Pitfall 3: Both `login_form_magic` and `login_form_password` render unless the generator's password branch is explicitly stripped

**What goes wrong:** Running `mix phx.gen.auth` and shipping it as-is gives every visitor to
`/admin/ingresar` a working password-login form and a public `/users/register` route — directly
contradicting D-31/D-32/D-33's "no password, invite-only, no public registration" requirements.

**Why it happens:** `mix phx.gen.auth`'s generated `LoginLive` template (read this session) renders
**both** a magic-link form (`submit_magic`) and a password form (`submit_password`) by default,
separated only by a `<div class="divider">or</div>` — password login isn't a flag to disable, it's
baked into the generated template and would need to be deleted post-generation.

**How to avoid:** Treat the generator output as a starting scaffold, not a finished feature: delete
the password `<.form>` block from `LoginLive`, delete `RegistrationLive`/`RegistrationController`
and their routes, delete the `update-password` route, and remove the `divider`/`Sign up` links.
Leave the underlying `hashed_password`/`password_changeset`/`valid_password?` code present but
dead — simpler than editing the generated migration, and harmless since nothing ever calls it.

**Warning signs:** A visible password field or a reachable `/users/register` (or whatever the
chosen route prefix is) URL in a live environment after this phase ships.

### Pitfall 4: The BGG/R2/Gemini seed-credential path (`Catalog.Seed.Credentials`) has never run in production

**What goes wrong:** `Credentials.fetch!/0` raises a `RuntimeError` naming every missing env var if
any of the 6 required keys are absent — this has never been exercised in `config/runtime.exs`
before (confirmed: `config/runtime.exs` currently has zero references to `BGG_API_TOKEN`/`R2_*`/
`GEMINI_API_KEY`, only to `R2_PUBLIC_BASE_URL` for the CSP `img-src` directive). Wiring the async
enrichment Oban worker without also wiring these 6 (7 with Gemini) new secrets into
`config/deploy.yml`'s `env.secret` list and `.kamal/secrets` will crash every enrichment job in
production on first attempt.

**Why it happens:** 01.7 D-04 deliberately kept these credentials off the production host; this
phase is the first time they're needed there, so there is no existing "add a new prod secret"
precedent specifically for `Catalog.Seed.Credentials`' fields to copy (only `SECRET_KEY_BASE`/
`DATABASE_URL`/`SENTRY_DSN`/`POSTGRES_PASSWORD` exist as precedent today, per `config/deploy.yml`
read this session).

**How to avoid:** Add all 6 required keys (`BGG_API_TOKEN`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`,
`R2_SECRET_ACCESS_KEY`, `R2_CATALOG_BUCKET`) plus `GEMINI_API_KEY` (optional per `Credentials`'
own `@optional_keys`, but required in practice for D-06) and the new email provider's API key to
both `.kamal/secrets` (gitignored, local to the deploy operator) and `config/deploy.yml`'s
`env.secret` list, then wire `config/runtime.exs` to expose them as `System.get_env/1` values
`Credentials.fetch!/0` can resolve at runtime (it already checks env vars first, per its own
`resolve/2` implementation).

**Warning signs:** The first staff-added game via BGG ID stays stuck in a `pending`/error
enrichment state forever in production, with an `RuntimeError: Missing seed credentials: ...` in
the Oban job's error output.

## Open Questions

1. **Is 14 days (the `phx.gen.auth` default remember-me/session validity) actually "long-lived
   enough" given the owner's real usage cadence?**
   - What we know: `staff-admin-decisions.md` and CONTEXT.md D-31 both say "keep the generator's
     long-lived remember-me session" (implying the default is already considered sufficient), and
     the generator's actual default is 14 days (verified this session).
     - What's unclear: The owner does the shelf-walking pass "in several Saturday sessions" — if
     those sessions are spaced more than 14 days apart at times, remember-me would expire and
     force a fresh magic-link request more often than the "long-lived" framing implies was
     intended.
   - Recommendation: Ship the 14-day default as-is (matches what CONTEXT.md explicitly asked to
     keep); if UAT reveals staff getting logged out between sessions, bumping
     `@session_validity_in_days`/`@max_cookie_age_in_days` in the generated `Auth`/`UserToken`
     modules is a small, low-risk follow-up change, not a re-architecture.

2. **Exact schema shape for the band-audit "keep" override (D-30) — see Assumption A4.**
   - What we know: the override must hide the game from the audit list, and must reappear "only if
     `bgg_weight` later implies a different band than when it was kept."
   - What's unclear: whether to store a snapshot of the implied band at review time (my
     recommendation), the raw `bgg_weight` value at review time (equivalent, derivable), or a
     simple timestamp+flag (insufficient per A4's analysis).
   - Recommendation: Plan should explicitly pin this schema shape (e.g.
     `band_reviewed_at :utc_datetime`, `band_reviewed_implied_band :string`) before implementation,
     since it's a one-way migration decision.

3. **How does `sections`' "automatic by rule" (D-19) actually store which rule applies?**
   - What we know: 4 known rule types exist today (weight-band membership ×3, "recently added"),
     plus D-19 says rules can be "name / BGG weight / BGG rating / recently added" generically for
     future sections, and D-25/D-26 imply manual sections need a `position`-ordered join table.
   - What's unclear: whether "automatic by rule" sections need a generic rule-DSL column (e.g.
     `rule: :string` with values like `"weight_band:descubre_el_hobby"`, `"recent"`) or whether the
     3 weight-band sections and "recientemente añadidos" should just stay as special-cased code
     branches (matching today's `row_query/1` pattern) with only the *manual/featured* section type
     being truly DB-driven.
   - Recommendation: Given D-19's phrasing implies future rule types beyond today's 4, a small
     `rule` string/atom column (special-cased in Elixir, not a rule-interpreter DSL) is likely
     sufficient and matches this codebase's existing "literal-string clauses, never
     `String.to_atom`" convention (`row_query/1`'s own established pattern) — but this is a
     plan-time modeling decision, not something this research can lock down further without
     over-specifying ahead of the planner's judgment.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | Yes | `phx.gen.auth` generated session/token handling (bcrypt/pbkdf2 hashing infra present but unused since no password login ships); magic-link token expiry (15 min) and single-use (deleted on verify) are generator defaults, verified this session |
| V3 Session Management | Yes | Generator's session renewal on login (`renew_session/2`, CSRF token deletion+regeneration), remember-me signed cookie (`sign: true`), `live_socket_id`-based force-disconnect on logout — all generator defaults, verified this session |
| V4 Access Control | Yes | New `RequireStaffRole` plug/`on_mount` hook (role check on top of the generator's `require_authenticated`) — this project's own addition, no library exists for this since "owner vs staff" is domain-specific |
| V5 Input Validation | Yes | Ecto changesets for all new schemas (`Shelf`, `Section`, `SectionGame`, `Game`'s new fields) — same `Ecto.Changeset` pattern already used throughout `Catalog.Game.seed_changeset/2`; BGG ID input must be validated as an integer (or parsed out of a pasted BGG URL) before hitting `BggClient.fetch_batch/2`, which already expects `[integer()]` |
| V6 Cryptography | Yes (magic-link tokens) | Generator uses `:crypto.strong_rand_bytes/1`-backed token generation internally (standard Phoenix/Plug crypto primitives) — never hand-roll token randomness |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Session fixation on login | Spoofing/Elevation | Generator's `renew_session/2` clears the session and regenerates the CSRF token on every login — already built in, verified this session |
| Enumeration via login/invite response (does an email exist?) | Information Disclosure | UI-SPEC already locks the exact copy for this: "same neutral confirmation copy whether or not the email is staff" (E11) — matches the generator's own `deliver_login_instructions/2` pattern of never revealing existence via response shape |
| CSV-seed upsert clobbering admin-entered data (this project's own novel risk, not a generic pattern) | Tampering (of a sort — legitimate code overwriting legitimate admin data) | D-09's retirement of `Catalog.Seed.CsvImport` entirely; see Anti-Patterns above |
| Draft/retired game data leaking via an un-filtered read path | Information Disclosure | Centralize the status filter in `base_filtered_query/2` and a dedicated `get_published_game!/1`; see Pitfall 2 |
| Untrusted BGG XML/HTML injected via a pasted "BGG URL" instead of a raw ID | Injection (client input) | `BggClient` already expects `[integer()]` ids — the admin add-game form must parse/validate a pasted URL down to its numeric BGG id (regex extract + `Integer.parse/1`) before it ever reaches `BggClient.fetch_batch/2`, never pass the raw pasted string through |
