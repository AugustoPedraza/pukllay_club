# Phase 01.8.1 Plan 07: Staff Invite & Remove Summary

**Owner-only staff lifecycle (`invite_staff/2`, `list_staff/1`, `remove_staff/2`) built on the existing magic-link flow — no separate invite-token concept — plus `/admin/staff` and an owner-only dashboard Staff card.**

## Accomplishments

- The owner invites a staff member by email at `/admin/staff`: an unconfirmed `:staff` user is inserted and a magic-link email sent via the existing `deliver_login_instructions/2`; opening the link confirms the account and signs the invitee in to `/admin` — proven end to end by a real round-trip test (invite → extract token → confirm → `GET /admin`).
- Authorization is enforced at the context (`invite_staff/2`/`remove_staff/2` return `{:error, :unauthorized}` for a non-owner scope, even called directly) and again at the LiveView `mount/3` (defense in depth, non-owner staff `push_navigate`d to `/admin` with no flash).
- The roster is capped at 3 invited staff plus the owner; a fourth invite shows the exact UI-SPEC cap message. Inviting a duplicate email surfaces the changeset's "has already been taken" error inline.
- A failed invite-email delivery rolls the just-inserted user back (`delete_invited_user/1`) and shows the exact UI-SPEC error copy — proven via a test-only `Accounts.notifier/0` seam, since `Swoosh.Adapters.Test` cannot itself be made to fail.
- The owner removes a staff member through a `¿Quitar a {email} del staff?` confirmation modal (Cancelar aborts with no deletion); confirming deletes the user (tokens cascade) and broadcasts `UserAuth.disconnect_sessions/1`, which a second, already-authenticated conn for that same staff member proves revokes access immediately — `GET /admin` redirects to `/admin/ingresar` right after removal, not on some later expiry.
- The owner can never remove themself or another owner (`remove_staff/2` refuses both).
- The `/admin` dashboard gained a `Staff` card, rendered only for the owner.

## Decisions Made

- `Accounts.notifier/0` is a documented, test-only `Application.get_env` override (default `UserNotifier`) so `StaffLiveTest` can simulate a delivery failure and prove the invite-rollback path — `Swoosh.Adapters.Test` (config/test.exs) always returns `{:ok, %{}}` and cannot itself be made to fail. Never set outside a test.
- `list_staff/1` sorts owner-first "for free" via `order_by: [asc: u.role, asc: u.email]` — `:owner` sorts before `:staff` lexicographically on the enum's underlying string, so no fragment/case-when was needed.
- `remove_staff/2` snapshots the target's tokens (`Repo.all_by/2`) before deleting the user inside one `Repo.transact/1`, since the `users_tokens` FK's `on_delete: :delete_all` means the tokens are gone the instant the user row is — the snapshot is exactly what `UserAuth.disconnect_sessions/1` needs to broadcast against.
- The RED phase for Task 2 was verified manually rather than via `gsd_run check tdd-red-evidence`: that verb's TAP-style classifier targets Node.js test-runner output, not `mix test`'s ExUnit format, and this project's `config.json` has no `workflow.tdd_mode` key (the config-gated enforcement path is inactive here). The underlying discipline — write test, confirm it fails on the target assertion for the right reason, then implement — was followed and is documented in the "TDD Gate Compliance" section below.
