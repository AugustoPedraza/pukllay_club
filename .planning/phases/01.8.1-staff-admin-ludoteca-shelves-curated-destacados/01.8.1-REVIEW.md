### Summary

This partition covers the invite-only staff auth flow (`phx.gen.auth` by subtraction), the owner-only
staff roster, the shelf-location admin surface, the two schema migrations that run against ~434 live
production rows, and the Kamal/GitHub Actions deploy pipeline. The core security properties called
out in the review brief hold up under direct tracing:

- The staff role gate (`require_staff_user` plug + `:require_staff` `on_mount`) is enforced on both
  the HTTP pipeline and every LiveView `on_mount` for every route under `/admin` (router.ex:90-109).
- Owner-only actions (`invite_staff/2`, `list_staff/1`, `remove_staff/2`) all re-check
  `User.owner?/1` **inside** the `Accounts` context, independent of the LiveView `mount` check —
  confirmed by `accounts_test.exs`'s "a staff scope is rejected" tests for all three.
- `remove_staff/2` structurally cannot remove an owner or self-remove (pattern-matches
  `%User{role: :staff} = target when target.id != actor.id`) — verified by
  `accounts_test.exs:173-182`.
- Session revocation on staff removal snapshots tokens before delete and broadcasts `"disconnect"`
  on each token's topic (`accounts.ex:194-205`, `user_auth.ex:171-179`), and the DB-level
  `on_delete: :delete_all` FK is a second, independent backstop.
- Magic-link enumeration-neutral login (`login.ex:70-86`) returns identical copy regardless of
  whether the email exists or belongs to staff.
- `GameSEO`'s canonical redirect is provably not an open redirect (location is built only from
  `~p"/juegos/#{game}"` + the request's own `query_string`, never `request_path`/host) — the
  `open-redirect guard, T-2x6-01` test exercises exactly this.
- The `games.status` migration backfills every pre-existing row to `"published"` via a column
  default, not a data migration — the only choice that can't silently unpublish the live catalog.
- The R2 catalog-vs-backup token mapping in `deploy.yml`/`deploy.yml` workflow is correct and
  covered by `deploy_secrets_contract_test.exs`.

The issues found below are real but narrower than the brief's top-line risks: a TOCTOU race on the
3-staff cap, and an inconsistent-with-the-rest-of-the-codebase unvalidated id read in the staff
roster's remove flow. No BLOCKER-severity defect was found in this partition — every owner-only
authorization boundary is independently re-checked server-side, and every migration is safe against
the existing production data.

### Warnings

### WR-A01: `invite_staff/2` has a TOCTOU race on the 3-staff cap

**File:** `lib/pukllay_club/accounts.ex:123-139`
**Issue:** The 3-staff cap is enforced by reading `count_staff()` and branching in a `cond`, with no
transaction, row lock, or DB constraint tying the count check to the subsequent insert:

```elixir
def invite_staff(%Scope{user: %User{} = user}, email) do
  cond do
    not User.owner?(user) -> {:error, :unauthorized}
    count_staff() >= @max_staff -> {:error, :staff_limit_reached}
    true ->
      %User{} |> User.email_changeset(%{email: email}) |> Ecto.Changeset.put_change(:role, :staff) |> Repo.insert()
  end
end
```

Two concurrent invite requests from the owner (a double-submit, two open tabs, or a retried request
after a slow response) can both observe `count_staff() == 2` before either insert commits, and both
proceed to insert — landing on 4 staff rows, one over the documented cap. There is no unique index,
check constraint, or `SELECT ... FOR UPDATE` anywhere in the migration or this function that would
reject the fourth row at the database layer (contrast with `users_role_must_be_known`, which *is* a
DB-level backstop for a different invariant). `move_shelf/2` in the same phase wraps its two updates
in `Repo.transaction/1` specifically to close an analogous race (T-01.8.1-44) — this function has no
equivalent guard.

**Fix:** Wrap the count check and insert in one transaction with a row lock (e.g.
`Repo.transaction(fn -> if count_staff_locked() >= @max_staff, do: ..., else: ... end)`, using
`lock: "FOR UPDATE"` on a real row, since `COUNT(*)` alone can't be locked), or add a `CHECK`/trigger-
backed invariant, or simplest: unique-index-free but correct — re-check the count *inside* the same
transaction as the insert and roll back on overflow:

```elixir
def invite_staff(%Scope{user: %User{} = user}, email) do
  if not User.owner?(user) do
    {:error, :unauthorized}
  else
    Repo.transaction(fn ->
      if count_staff() >= @max_staff do
        Repo.rollback(:staff_limit_reached)
      else
        %User{}
        |> User.email_changeset(%{email: email})
        |> Ecto.Changeset.put_change(:role, :staff)
        |> Repo.insert!()
      end
    end)
  end
end
```
This still has the same fundamental TOCTOU window unless the transaction also takes a lock (e.g.
`Repo.query!("LOCK TABLE users IN SHARE ROW EXCLUSIVE MODE")` scoped to staff rows, or a Postgres
advisory lock keyed on a constant) — call out that the minimal fix is an advisory lock
(`pg_advisory_xact_lock`) around the check+insert, not just a bare transaction.

### WR-A02: `StaffLive.Index`'s "ask-remove" handler trusts an unvalidated client id, unlike every sibling admin LiveView

**File:** `lib/pukllay_club_web/live/admin/staff_live/index.ex:60-62`
**Issue:**
```elixir
def handle_event("ask-remove", %{"id" => id}, socket) do
  {:noreply, assign(socket, :confirm_remove, Accounts.get_user!(id))}
end
```
`id` comes from `phx-value-id={user.id}` and is fully client-controlled at click time (dev tools,
a replayed/edited LiveView event payload). `Accounts.get_user!/1` calls `Repo.get!(User, id)`
directly with no `Integer.parse/1` guard. This diverges from the pattern this same phase establishes
everywhere else id-like params cross a LiveView event boundary:
`Admin.ShelfLive.Assign.handle_event("assign", ...)` and `Admin.ShelfLive.Index`'s `move/3` both
`Integer.parse` the incoming id and no-op on a non-integer rather than calling a bang function. Here,
a non-integer `id` (e.g. `"abc"`) raises `Ecto.Query.CastError` and a well-formed but nonexistent
integer id raises `Ecto.NoResultsError` — both uncaught, crashing the LiveView process (the client
sees a forced reconnect/remount). The eventual authorization is still safe (`remove_staff/2`
re-validates role/owner/self server-side), but the crash-on-malformed-input is a real robustness gap
this phase's own convention was written to avoid (see `ShelfLive.Index`'s own moduledoc: "parsed with
literal clauses ... never `String.to_atom/1` on the client-supplied param" — the same spirit applies
to unguarded id casts).

**Fix:**
```elixir
def handle_event("ask-remove", %{"id" => id}, socket) do
  case Integer.parse(id) do
    {int_id, ""} -> {:noreply, assign(socket, :confirm_remove, Accounts.get_user(int_id))}
    _not_an_integer -> {:noreply, socket}
  end
end
```
(requires adding a non-bang `Accounts.get_user/1` returning `nil`, or matching on `Repo.get`).

### IN-A01: `handle_event("ask-remove", ...)` is not scoped to the already-loaded staff roster

**File:** `lib/pukllay_club_web/live/admin/staff_live/index.ex:60-62`
**Issue:** The handler looks up *any* user id in the `users` table, not just ids present in the
owner's already-rendered roster (`@streams.staff`). Since final removal is re-authorized server-side
in `remove_staff/2` (role must be `:staff`, must not be the actor), this cannot be used to remove an
owner or an arbitrary account — but it does let the confirm-modal render an arbitrary user's email
(e.g. another owner's) if an id is supplied that isn't in the visible roster, which is a harmless but
avoidable trust boundary crossing given the owner already has full visibility via `list_staff/1`.
**Fix:** Look the target up from the already-fetched roster (e.g. keep the stream's backing list in
an assign, or re-derive via `Accounts.list_staff/1 |> Enum.find(&(&1.id == int_id))`) instead of a
bare `Repo.get!/2` against the whole `users` table.

### IN-A02: `count_staff/0` has no index-backed fast path, and no test exercises the WR-A01 race

**File:** `lib/pukllay_club/accounts.ex:139`; `test/pukllay_club/accounts_test.exs:110-115`
**Issue:** The existing test (`"refuses a fourth invite once 3 staff already exist"`) only proves the

the eventual fix for WR-A01 ships with a regression test using two concurrent tasks/transactions
rather than relying on the existing sequential test to catch a re-introduction of the race.
**Fix:** Add a test that spawns two concurrent `Task`s each calling `invite_staff/2` when
`count_staff() == 2`, asserting exactly one succeeds and the roster never exceeds 3 staff — this will

### Critical Issues

### CR-B-01: `add_game_from_bgg/1`'s duplicate-BGG-id rejection has no database backstop — a TOCTOU race can insert two draft games for the same BGG id

**File:** `lib/pukllay_club/catalog.ex:274-300` (also
`priv/repo/migrations/20260914114344_allow_admin_added_games.exs`,
`priv/repo/migrations/20260806234228_create_games.exs:46`)

**Issue:** `Catalog.add_game_from_bgg/1`'s own moduledoc promises: "An id
already belonging to ANY game — draft, published, or retired — is rejected
up front as `{:error, {:duplicate, existing_game}}`". The implementation is:

```elixir
defp insert_draft_or_reject_duplicate(bgg_id_int) do
  if existing = Repo.get_by(Game, bgg_id: bgg_id_int) do
    {:error, {:duplicate, existing}}
  else
    insert_draft_and_enqueue(bgg_id_int)
  end
end
```

This is a plain read-then-write with no transactional isolation and no
unique constraint backing it: `games.bgg_id` only carries a plain
`index(:games, [:bgg_id])` (`20260806234228_create_games.exs:46`,
deliberately non-unique for historical CSV-import reasons per that
migration's own moduledoc), and `20260914114344_allow_admin_added_games.exs`
— the migration this very plan added for admin-added games — only makes
`csv_row` nullable; it does not add a unique index (even a partial one,
`WHERE bgg_id IS NOT NULL`) to back the new duplicate-rejection guarantee.
`Game.draft_changeset/2` has no `unique_constraint(:bgg_id)` either.

**Failure scenario:** Two staff members (two different LiveView
processes/sessions — this is not prevented by LiveView's single-process
event serialization, which only protects a *single* browser tab) paste the
same BGG id/URL within the same race window. Both `Repo.get_by/2` calls see
no existing row, both proceed to `insert_draft_and_enqueue/1`, and both
succeed: two `:draft` games with the identical `bgg_id`, each with its own
`EnrichGameWorker` job (Oban's own `unique` constraint is keyed on
`game_id`, not `bgg_id`, so it does not catch this). Both can independently
be published, producing two visible catalog entries for the same physical
game with no automated way to detect or merge them.

**Fix:**
```elixir
### migration
create unique_index(:games, [:bgg_id], where: "bgg_id IS NOT NULL", name: :games_bgg_id_unique_index)
```
```elixir
### Game.draft_changeset/2
|> unique_constraint(:bgg_id, name: :games_bgg_id_unique_index)
```
```elixir
### Catalog.insert_draft_and_enqueue/1 — translate the constraint error back
### into the existing {:error, {:duplicate, existing}} contract, or accept a
### generic {:error, changeset} and have the caller re-fetch by bgg_id.
```

### WR-B-01: `BandAudit.correct_band/1`/`keep_band/1` trust the client-sent `game-id` without scoping it to the actual mismatch list — an arbitrary game's `weight_band` can be modified from this screen

**File:** `lib/pukllay_club_web/live/admin/band_audit_live.ex:34-53`,
`lib/pukllay_club/catalog/band_audit.ex:69-101`

**Issue:** `Corregir`/`Mantener` send `phx-value-game-id={game.id}` for rows
`BandAudit.mismatches/0` rendered, but `handle_event("correct"/"keep", ...)`
only parses the id as an integer and calls `BandAudit.correct_band/1` /
`keep_band/1` directly — neither function re-checks that `game_id` is
actually one of the current mismatches. `correct_band/1` unconditionally
sets `weight_band: Vocabulary.implied_weight_band(game.bgg_weight)`. For a
game whose `bgg_weight` is `nil`, `implied_weight_band/1` returns `nil`, and
`Game.band_review_changeset/2`'s `validate_inclusion/3` on `weight_band`
skips a `nil` value (per Ecto's own contract, also relied on elsewhere in
this codebase) — so the changeset succeeds and silently **clears** that
game's `weight_band` to `nil`, even though that game was never rendered on
this page and was never part of the mismatch computation
(`mismatches/0` explicitly excludes `bgg_weight == nil` games).

**Failure scenario:** A crafted `correct`/`keep` event (devtools, a stale
tab that still shows a game already fixed by another staff member and now
reused for a different id, or a buggy future client change) with any
existing game id — not necessarily one currently listed — clears or
snapshot-overrides that game's band metadata with no audit trail tying the
action back to "this game was flagged as mismatched."

**Fix:** Re-derive the mismatch set (or at least re-check
`weight_band != implied and band_reviewed_band != implied`) inside
`correct_band/1`/`keep_band/1` before writing, returning `{:error,
:not_a_mismatch}` otherwise — mirroring `retry_enrichment/1`'s own
`{:error, :not_failed}` guard pattern already used elsewhere in this module.

### WR-B-02: Several admin `handle_event` clauses call a raising `Repo.get!`/`get_section!` on a client-supplied id with no rescue — an uncaught exception crashes the LiveView

**File:** `lib/pukllay_club/catalog/band_audit.ex:71,92` (via
`band_audit_live.ex:34-53`), `lib/pukllay_club_web/live/admin/section_live/index.ex:47-56`,
`lib/pukllay_club_web/live/admin/game_live/index.ex:134-145`,
`lib/pukllay_club_web/live/admin/game_live/form.ex:143-160`

**Issue:** `BandAudit.correct_band/1`/`keep_band/1` call `Repo.get!(Game,
game_id)`; `SectionLive.Index.move/2` calls `Sections.get_section!(int_id)`;
`GameLive.Index`/`GameLive.Form`'s `retry-enrichment` clauses call
`Catalog.get_game!(int_id)`. All four are reachable from a `phx-value-*`
attribute an already-staff-authenticated client fully controls once
devtools is open (or via any future bug that renders a stale/wrong id). None
of these call sites rescue `Ecto.NoResultsError` — an id that parses as an
integer but does not exist raises uncaught, killing the LiveView process
(the tab reconnects to a fresh `mount/3`, losing any unsaved edit-form

`move-member-*` handlers a few files over, which use `Sections.add_game/2`/
`remove_game/2`/`move_game/3` — all of which degrade a not-a-member id to a
no-op `{:ok, section}` rather than raising.

**Fix:** Swap the bang reads for `Repo.get/2` (or add
`Catalog.fetch_game/1`/`Sections.fetch_section/1` non-raising variants) and
no-op on `nil`, matching the existing no-op convention in the sibling
handlers.

### WR-B-03: `Sections.add_game/2`'s featured-cap check is not race-safe, despite the moduledoc's explicit claim that it is

**File:** `lib/pukllay_club/catalog/sections.ex:23-27,177-191`

**Issue:** The module comment states: "Checked inside the same transaction
as the insert (T-01.8.1-56) so two concurrent adds can never push the
featured section past the cap." The implementation is:

```elixir
def add_game(%Section{kind: :manual} = section, game_id) do
  Repo.transaction(fn ->
    cond do
      already_member?(section.id, game_id) -> Repo.rollback(:already_member)
      section.featured and member_count(section.id) >= @featured_cap -> Repo.rollback(:featured_full)
      true -> Repo.insert!(%SectionGame{...})
    end
  end)
end
```

Under Postgres' default `READ COMMITTED` isolation (no `SELECT ... FOR
UPDATE`, no advisory lock, no `SERIALIZABLE`), two concurrent `add_game/2`
calls against the featured section both run `member_count/1` before either
commits its insert; both can observe `19` and both proceed, landing the
featured section at 21 members — one over the documented D-26 cap. Being
*inside a transaction* only guarantees atomicity of each call's own
read+write, not mutual exclusion between two callers' reads.

**Fix:** Lock the section row before counting
(`from(s in Section, where: s.id == ^section.id, lock: "FOR UPDATE")
|> Repo.one()`), or add a `SERIALIZABLE` transaction with retry, or enforce
the cap with a Postgres trigger/constraint rather than an application-level
read.

### WR-B-04: `Sections.add_game/2` performs a raw `Repo.insert!` with no existence/foreign-key guard — a bad `game_id` raises uncaught

**File:** `lib/pukllay_club/catalog/sections.ex:177-191`,
`lib/pukllay_club_web/live/admin/section_live/edit.ex:90-109`

**Issue:** `add_game/2`'s success branch is `Repo.insert!(%SectionGame{
section_id: section.id, game_id: game_id, position: ...})` — a raw struct
insert, not routed through a changeset with `foreign_key_constraint/2`. The
caller, `SectionLive.Edit.handle_event("add-game", %{"game-id" => id},
...)`, parses `id` from `phx-value-game-id` on a dynamically rendered
search-result button, then calls `Sections.add_game/2` and pattern-matches
only `{:ok, _}` / `{:error, reason}`. If `game_id` does not reference an
existing `games` row (a devtools-tampered id, or a games row deleted
out-of-band in some future maintenance path), `Repo.insert!/1` raises
`Ecto.ConstraintError` inside the `Repo.transaction/1` function — Ecto
rolls the DB transaction back correctly, but the exception is re-raised to
the caller, which has no `rescue` for it, crashing the LiveView.

**Fix:** Validate `game_id` (e.g. `Repo.exists?(from g in Game, where:
g.id == ^game_id)`) inside the same `cond`, returning `{:error,
:game_not_found}` in the existing tuple contract instead of letting the
insert raise.

### WR-B-05: `create_sections` migration builds SQL via string interpolation, contrary to the project's own no-string-built-queries convention

**File:** `priv/repo/migrations/20260914150000_create_sections.exs:122-129`

**Issue:**
```elixir
defp section_membership_sql(section_name, tag) do
  """
  INSERT INTO section_games (section_id, game_id, position, inserted_at, updated_at)
  SELECT s.id, g.id, row_number() OVER (ORDER BY g.name, g.id), now(), now()
  FROM games g, sections s
  WHERE s.name = '#{section_name}' AND g.tags @> ARRAY['#{tag}']::varchar[]
  """
end
```
Both `section_name` and `tag` are spliced directly into the SQL text rather
than bound as parameters. Every value passed to `section_membership_sql/2`
in this migration is a hardcoded literal, so there is no live injection
vector today — but this is exactly the pattern `Catalog`'s own moduledoc
calls out as forbidden ("no query text is ever built by string
interpolation", T-01-20), and a future migration author copying this
helper with a computed/user-influenced value (e.g. a section name typed by
a developer running a one-off backfill) would silently reintroduce a real
SQL-injection surface with no code-review signal distinguishing it from the
safe fragment-based queries everywhere else in this codebase.

**Fix:** Use `Ecto.Adapters.SQL.query!(Repo, sql, [section_name, tag])`
with `$1`/`$2` placeholders instead of string interpolation, even though
the inputs are currently constants.

### IN-B-01: `Game.enrichment_changeset/2` doesn't validate `enrichment_status` against the known enum, unlike `seed_changeset/2`

**File:** `lib/pukllay_club/catalog/game.ex:181-211`

**Issue:** `seed_changeset/2` calls `validate_inclusion(:enrichment_status,

(`"enriched"`, `"failed"`, `"pending"`), so this isn't exploitable today,

unrecognized status string that every `case`/pattern match elsewhere in the
codebase treats as "not pending, not failed" (i.e. rendered as if enriched).

**Fix:** Add `validate_inclusion(:enrichment_status, @enrichment_statuses)`
to `enrichment_changeset/2` as well.

### IN-B-02: "Agregar juego" has no `phx-disable-with`/loading guard, encouraging the double-submit that intersects with CR-B-01
