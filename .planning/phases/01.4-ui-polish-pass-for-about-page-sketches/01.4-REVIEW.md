# Phase 01.4: Code Review Report

**Reviewed:** 2026-09-05T00:00:00Z
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

Reviewed the full source diff behind Phase 01.4 (the About page UI polish pass plus its three
gap-closure plans, 01.4-06/07/08/09). The bulk of the implementation — the `.AboutHeaderMorph`
scroll-morph hook, the `.AboutCarousel` photo rail, the Contacto card rebuild, the shared
`.pk-band-inner` width fix, and the Maps-thumbnail chip/theme-variant work — is unusually
well-instrumented: every non-obvious CSS/JS decision carries a comment naming the specific defect
it prevents, and most of the plan chain already self-corrected several real bugs it found live
(carousel last-dot scroll math, two cascade-layer `display` hazards, a `<noscript><style>` no-JS
trap). Tracing through the actual mechanics (dock-rect resolution, transform interpolation,
`body:has()` guard specificity, the shrink-wrap/concentric-radius chip math) did not turn up a
functional defect in that core morph/carousel machinery.

What I did find are four real, previously-unflagged defects that survived the phase's own
verification passes: an actual CI-breaking formatting regression committed in the phase's last
plan, a concrete WCAG 2.5.3 accessibility violation introduced when `social_links/1` gained visible
labels, a shipped dark-theme image defect that duplicates the light asset (already tracked as a
"Known Stub" but still a real, currently-live rendering defect), and stale documentation in two
files that now contradicts the shipped code. None of these are severe enough to block on their own
correctness/security grounds, but the formatting regression in particular will fail this project's
own documented `mix quality`/CI gate (`mix format --check-formatted`) the moment it runs, and none
of the four were caught by the phase's nine rounds of self-verification.

## Warnings

### WR-01: Committed formatting regression fails `mix format --check-formatted` (breaks the project's own CI gate)

**File:** `test/pukllay_club_web/live/about_live_test.exs:528-529, 534-535`
**Issue:** Running `mix format --check-formatted` against the current tree fails on this file
(verified directly: `mix format --check-formatted` exits 1). The offending lines were introduced in
commit `0195b99` (plan 01.4-09, Task 3) and are already committed — this is not working-tree drift,
`git status --short` shows the file clean. CLAUDE.md documents `format --check-formatted` (Styler-
augmented) as a required, ordered step in this project's `mix quality` alias and its GitHub Actions
CI pattern, so this is a real, live CI-breaker, not a style nit. The phase's own
`.planning/phases/01.4-ui-polish-pass-for-about-page-sketches/deferred-items.md` tracks exactly one
pre-existing formatting failure (in `layouts_test.exs`, from an unrelated earlier commit) — it does
not mention this one, and 01.4-09-SUMMARY.md's Self-Check list never runs `mix format` at all
(only `mix compile --warnings-as-errors`), which is how this shipped unnoticed through nine plans
of otherwise-thorough self-verification.
**Fix:**
```
mix format test/pukllay_club_web/live/about_live_test.exs
```
Styler will rewrite `LazyHTML.attribute(light, "src") |> List.first()` to
`light |> LazyHTML.attribute("src") |> List.first()` (and the same for the three sibling lines) —
purely mechanical, no behavior change.

### WR-02: `Layouts.social_links/1`'s WhatsApp link fails WCAG 2.5.3 "Label in Name" once `labels: true` is used

**File:** `lib/pukllay_club_web/components/layouts.ex:1083-1110` (WhatsApp branch), consumed with
`labels` at `lib/pukllay_club_web/live/about_live.ex:664-668`
**Issue:** `social_links/1`'s WhatsApp anchor carries a hard-coded `aria-label="WhatsApp"` on every
call site. That attribute is invisible/harmless while `labels` defaults to `false` (footer, drawer
— no visible text, so the icon's only accessible name is the aria-label). Plan 01.4-02 added the
`labels` attr specifically so the About page's Contacto card could render a *visible* Spanish label
next to each icon — and for WhatsApp that visible text is `"Grupo de WhatsApp"`, not `"WhatsApp"`.
Per WCAG 2.1 SC 2.5.3 (Label in Name), a control's accessible name must contain the full visible
label text so that speech-input users (Dragon, Voice Access, etc.) who say the visible label can
actually activate the control. Here the accessible name is fixed to `"WhatsApp"` — it does not
contain `"Grupo de WhatsApp"` — so a user saying "click Grupo de WhatsApp" fails, and a screen
reader announces a name ("WhatsApp") that doesn't match what's on screen ("Grupo de WhatsApp").
The Instagram/Facebook/Correo branches happen not to trigger this (their aria-label already equals
their visible label verbatim), which is why the phase's own tests — which assert the visible text
renders, but never cross-check it against the aria-label — didn't catch it.
**Fix:** Either drop the static `aria-label` when a visible label is present (let the accessible
name derive from the link's own text content), or make the label match:
```elixir
aria-label={if @labels, do: nil, else: "WhatsApp"}
```
(repeat the same conditional pattern for the other three channels for consistency, even though only
WhatsApp currently mismatches).

### WR-03: Dark-theme Maps thumbnail is a byte-identical copy of the light asset — ships a real light-on-dark contrast defect

**File:** `priv/static/images/about-maps-thumb-dark.jpg`, wired at
`lib/pukllay_club_web/live/about_live.ex:696-702`
**Issue:** Verified directly (`cmp` reports the two files identical, both 57767 bytes). The
light/dark `<img>` swap mechanism (mirroring `brand_logo/1`'s isologo pattern) is wired correctly —
this is not a code bug — but the *content* of the "dark" asset is the light-toned Google Maps
capture, so every dark-theme visitor to `/quienes-somos#contacto` sees a bright white map card
sitting on the dark theme's card background, the exact 10.1x luminance mismatch the phase's own
debug session (`.planning/debug/G-01.4-4-maps-thumbnail-approach.md`) diagnosed as root cause (C).
This is disclosed as a "Known Stub" in `01.4-09-SUMMARY.md`, so it is not a hidden regression — but
it is a real, currently-shipping visual defect on a page that otherwise fully supports dark theme,
and it should not be lost track of once this phase's artifacts are archived.
**Fix:** Capture a genuine dark-mode Google Maps screenshot (the mobile Maps app's own dark theme,
per the SUMMARY's own follow-up note — the three avenues tried on desktop/web all failed to
recolor the canvas map tiles) and replace `about-maps-thumb-dark.jpg` in place; no code change is
needed once a real asset exists.

### WR-04: Stale "four-slide"/"no real photography yet" comments contradict the shipped five-real-photo rail

**File:** `lib/pukllay_club_web/live/about_live.ex:15` (moduledoc) and `assets/css/app.css:2621-2622`
**Issue:** The module doc's structure summary still reads `hero -> four-slide photo rail`, and the
CSS comment directly above `.pk-about-rail` still reads `Four-slide photo rail (D-12: labelled
placeholders, no real photography yet)`. Plan 01.4-04 replaced the four placeholder slides with
five real photographs (`about-juego.jpg`, `about-explicacion.jpg`, `about-ludoteca.jpg`,
`about-comunidad.jpg`, `about-festejo.jpg`) and the surrounding code was updated accordingly (the
inline HEEx comment immediately above the rail markup, line 381, correctly says "Five-slide photo
rail of real club photography"), but these two higher-level doc comments were never updated to
match. A future reader/agent skimming the moduledoc or the CSS block header alone would form an
incorrect mental model of both the slide count and whether the images are real. The moduledoc's
adjacent claim that page content is "the user-supplied real copy from `about-page-design-source.html`
... used verbatim" is also now stale — plans 01.4-01/02/03 rewrote the Historia, Qué hacemos,
Juntadas, FAQ-pricing and closing-CTA copy away from the original design source's verbatim text.
**Fix:** Update both comments, e.g.:
```
Structure (D-07): hero -> five-slide photo rail (`.AboutCarousel`) -> ...
```
and
```
/* Five-slide photo rail of real club photography (D-08/D-09, sketch 046).
   Scroll-snapping, scrollbar hidden — same treatment as .pk-rail. */
```
and soften the moduledoc's "used verbatim" claim to note it as the original source, since revised
per subsequent plans.
