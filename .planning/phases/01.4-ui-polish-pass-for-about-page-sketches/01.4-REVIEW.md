# Phase 01.4: Code Review Report

**Reviewed:** 2026-09-03T00:00:00Z
**Depth:** standard
**Files Reviewed:** 8

## Summary

Reviewed the About-page UI polish phase (plans 01.4-01 through 01.4-05): the `.pk-band-inner` width
fix, the rewritten Qué hacemos/Juntadas copy, the Contacto card's Maps thumbnail and icon links, the
five-photo carousel, and the isologo scroll-morph header/hero interaction. The server-rendered HTML
and CSS-fact contracts are well covered by tests, and the copy/link-sourcing discipline (everything
through `ClubLinks`, no invented facts) holds up under inspection.

The one BLOCKER is in client-side JS that ExUnit cannot see and that the phase's own test suite
explicitly defers to manual headless-Chrome verification (per `about_header_morph_test.exs`'s own
comments): the isologo scroll-morph's `dockRect()` selects the **first** `.pk-brand-mark` element in
DOM order rather than the one actually visible for the current theme. Since the header's light/dark
isologo images are toggled with `display:none` (Tailwind's `dark:hidden`/`hidden dark:block`), in dark
theme the selected element is exactly the hidden one, producing a zero-size rect at `(0, 0)`. This is
a real, demonstrable defect for any dark-theme visitor on `/quienes-somos` — the floating isologo mark
collapses to nothing at the top-left of the header once scrolled past the crossing point, on a page
whose entire visual identity is built around this single floating mark (the header's own copy is kept
permanently invisible via `opacity: 0`, so nothing else stands in for it). Nothing in the manual
verification notes (Task 3, headless-Chrome pass) mentions checking dark theme.

Two Warnings and one Info round out the findings — a carousel autoplay that can never resume once a
touch user interacts with it (no touch-equivalent of the existing mouseleave-based reset), and a
header that is hidden purely via `opacity: 0`/`pointer-events: none` while remaining fully reachable
by Tab and screen readers (no `inert`/`aria-hidden` companion, unlike every other overlay in this same
file).

## Critical Issues

### CR-01: Isologo dock position collapses to a zero-size rect in dark theme

**File:** `lib/pukllay_club_web/live/about_live.ex:92`
**Issue:**

```js
this.dockRect = () => this.header.querySelector(".pk-brand-mark").getBoundingClientRect()
```

`brand_logo/1` (`lib/pukllay_club_web/components/layouts.ex:79-92`) renders **two** `<img>` elements
with the shared `pk-brand-mark` class — the light-theme mark first in DOM order, the dark-theme mark
second — each hidden/shown purely via Tailwind's `dark:` variant (`display: none` under the
`[data-theme=dark]` custom variant, `assets/css/app.css:215`):

```heex
<img ... src={~p"/images/isologo-light.png"} class="dark:hidden pk-brand-mark" />
<img ... src={~p"/images/isologo-dark.png"} class="hidden dark:block pk-brand-mark" />
```

`querySelector(".pk-brand-mark")` always returns the **first matching element in DOM order** —
the light-theme `<img>` — regardless of which theme is active. In light theme this happens to be the
visible one, so the bug is invisible there. In dark theme, that same element carries `dark:hidden`
(`display: none`), so `getBoundingClientRect()` returns an all-zero rect (`top: 0, left: 0, width: 0,
height: 0`).

`dockRect()` feeds directly into `syncPosition()` (line 117) and the first-paint dock decision (line
146): `this.docked = natural0.top <= dock0.top`. Once a dark-theme visitor scrolls past the crossing
point, `shouldDock` becomes true and `this.place(this.dockRect(), true)` (line 122) sizes/positions
the floating mark from that zero rect — the isologo visibly shrinks to nothing at the viewport's
top-left corner. Because the header's own isologo copy is permanently suppressed via
`#app-header.pk-header-about-morph .pk-brand-mark { opacity: 0; }` (`app.css:2884-2886`) with no
`:not(.is-docked)` qualifier, there is no fallback mark to be seen underneath — the brand identity
mark disappears entirely for the rest of the scrolled page in dark theme.

The comment directly above this code (`about_live.ex:87-91`) argues correctness for a different,
narrower case — "An opacity:0 element still reports a real rect" — which is true for the
`.pk-header-about-morph` opacity suppression rule, but does not address the `display:none` toggle from
the theme variant, which is the actual defect here.

**Fix:** Select the currently-*visible* mark, not merely the first DOM match:

```js
this.dockRect = () => {
  const marks = this.header.querySelectorAll(".pk-brand-mark")
  for (const mark of marks) {
    const rect = mark.getBoundingClientRect()
    if (rect.width > 0 && rect.height > 0) return rect
  }
  // Fallback: neither mark has a size yet (e.g. not yet laid out).
  return marks[0]?.getBoundingClientRect()
}
```

Add a headless-Chrome pass with `data-theme="dark"` set (or the theme toggle exercised) to the manual
verification this hook already receives, so this class of defect is caught before merge next time.

## Warnings

### WR-01: Photo carousel autoplay can never resume after a touch interaction

**File:** `lib/pukllay_club_web/live/about_live.ex:312-317`
**Issue:**

```js
this.onPointerDown = () => { this.paused = true }
this.onMouseEnter = () => { this.paused = true }
this.onMouseLeave = () => { this.paused = false }
this.rail.addEventListener("pointerdown", this.onPointerDown)
this.rail.addEventListener("mouseenter", this.onMouseEnter)
this.rail.addEventListener("mouseleave", this.onMouseLeave)
```

`this.paused` is only ever reset to `false` by `mouseleave`. On a mouse-driven desktop this
self-heals: a `pointerdown` (e.g. a dot click) sets `paused = true`, but the cursor eventually leaves
the rail and `mouseleave` resets it, so autoplay resumes. Touch devices, however, fire
`pointerdown`/`touchstart` on every swipe or dot tap but never fire `mouseenter`/`mouseleave` — so on
mobile (the project's stated primary platform, per `priority_mobile_first`), the very first swipe or
dot tap permanently stops the 4.5s autoplay for the rest of the page's lifetime, with no code path
that ever sets `paused` back to `false` again. This is undocumented (no comment addresses the
touch-vs-mouse asymmetry, unlike the carefully-reasoned `pointer:fine` gating elsewhere in this
codebase for `.pk-rail-btn`).

**Fix:** Add a touch-equivalent resume, e.g. resume after a short idle delay following the last
touch interaction instead of relying solely on `mouseleave`:

```js
this.resumeTimer = null
this.onPointerDown = () => {
  this.paused = true
  clearTimeout(this.resumeTimer)
  this.resumeTimer = setTimeout(() => { this.paused = false }, 6000)
}
```
(and clear `this.resumeTimer` in `destroyed()`) — or, if permanently stopping autoplay after any
manual interaction is the intended UX, document that decision explicitly the way this file documents
its other deliberate autoplay-pause choices.

### WR-02: Header is hidden via `opacity: 0`/`pointer-events: none` but stays keyboard/screen-reader reachable

**File:** `lib/pukllay_club_web/components/layouts.ex:221` (header wrapper), `assets/css/app.css:2868-2872` (`#app-header.pk-header-about-morph`)
**Issue:** While `.AboutHeaderMorph` is mounted and the page hasn't yet scrolled past the crossing
point, `#app-header` is hidden with:

```css
#app-header.pk-header-about-morph {
  opacity: 0;
  pointer-events: none;
  transition: opacity var(--duration-slow) var(--ease-out-soft);
}
```

`opacity: 0` and `pointer-events: none` remove the header visually and from mouse interaction, but do
**not** remove it from the tab order or the accessibility tree (unlike `display: none` or
`visibility: hidden`). The header still contains real interactive controls at this point — the
hamburger button (`layouts.ex:694-702`) and, on the About page, the `nav_links` slot's two `<.link>`
elements (`about_live.ex:46-47`, rendered as `#app-header`'s `nav_links` region). A keyboard user who
starts tabbing from the top of `/quienes-somos` (the natural first-paint state before any scroll) will
land focus on an invisible hamburger button and invisible "Inicio"/"Quiénes Somos" links before ever
reaching the hero content — a Tab press with no visible focus indicator, and a screen reader will
still announce these controls as present and operable.

Every other hide/reveal overlay in this same file (`pk-nav-drawer`, `pk-cat-menu`) pairs its
visual-hidden state with `inert` specifically to prevent this class of bug (see
`layouts.ex:773-834`'s own comment: *"`inert` is the closed state's a11y mechanism"*) — this new state
is the one place in the file that hides a real interactive region without that companion.

**Fix:** Toggle `inert` on `#app-header` alongside `.pk-header-about-morph` (removed once `.is-docked`
is added), mirroring the drawer/cat-menu pattern:

```js
// in .AboutHeaderMorph mounted(), alongside header.classList.add("pk-header-about-morph")
this.header.setAttribute("inert", "")
// ...and in syncPosition(), when shouldDock flips true:
this.header.toggleAttribute("inert", !this.docked)
```
