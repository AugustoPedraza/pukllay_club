# Phase 01.4: Code Review Report

**Reviewed:** 2026-09-04T02:03:56Z
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Reviewed the About-page UI polish pass: the `.AboutHeaderMorph`/`.AboutCarousel` colocated
hooks and markup in `about_live.ex`, the `brand_logo/1`/`social_links/1` changes in
`layouts.ex`, the new `ClubLinks.maps_url/0`, and the About-scoped CSS additions in
`app.css`, plus their four test files. The bulk of this phase is well-covered by tests and the
inline commentary shows real engineering care (documented failure-path handling, cascade-layer
hazard notes, reduced-motion guards). The one finding that matters is a real gap: the About
page's floating isologo mark renders unconditionally, without the same compile-time
existence gate `brand_logo/1` uses elsewhere in this codebase, and the JS hook that docks it
onto the header has no timeout for the case where a dock target never appears — a missing/
renamed isologo asset would permanently hide the entire header (including the mobile nav
drawer trigger) on `/club` and `/quienes-somos`, with no visible error and no recovery. A
secondary finding notes a doc/test-name vs. actual-behavior mismatch in the newly-public
`social_links/1` component's `icons` attr.

## Critical Issues

### CR-01: A missing/renamed isologo asset permanently hides the About page's header, with no timeout or fallback

**File:** `lib/pukllay_club_web/live/about_live.ex:744-748` (unconditional mark markup) and
`lib/pukllay_club_web/live/about_live.ex:190-197, 230-264` (`dockRect()`/`frame()` in the
`.AboutHeaderMorph` colocated hook)

**Issue:** Every other consumer of the isologo assets in this codebase goes through
`Layouts.brand_logo/1`'s compile-time gate:

```elixir
# lib/pukllay_club_web/components/layouts.ex:19-23
@isologo_light_path "priv/static/images/isologo-light.png"
@isologo_dark_path "priv/static/images/isologo-dark.png"
@external_resource @isologo_light_path
@external_resource @isologo_dark_path
@isologo? File.exists?(@isologo_light_path) and File.exists?(@isologo_dark_path)
```

`brand_logo/1` only renders the two `<img class="pk-brand-mark">` elements when `@isologo?` is
true; otherwise it gracefully degrades to the wordmark-only lockup (lines 80-92). This gate
exists specifically so a missing asset degrades the UI instead of breaking it.

The About page's own floating mark (`#pk-about-morph-mark`), however, renders its two `<img>`
tags **unconditionally** — there is no `@isologo?`-equivalent check anywhere in
`about_live.ex` (confirmed by grep: no `isologo?`/`File.exists?` reference exists in the
file):

```elixir
# lib/pukllay_club_web/live/about_live.ex:744-748
<div id="pk-about-morph-mark" class="pk-about-morph-mark" aria-hidden="true">
  <div class="pk-about-morph-mark-inner">
    <img src={~p"/images/isologo-light.png"} class="dark:hidden" alt="" />
    <img src={~p"/images/isologo-dark.png"} class="hidden dark:block" alt="" />
  </div>
</div>
```

The `.AboutHeaderMorph` hook's guard clause only checks that the **container div** exists, not
that the header actually rendered real `.pk-brand-mark` images to dock onto:

```javascript
this.mark = document.getElementById("pk-about-morph-mark")
if (!this.header || !this.anchor || !this.mark) {
  this.el.removeAttribute("data-morph-armed")
  return
}
```

Since `#pk-about-morph-mark` always exists (it isn't gated), this guard always passes. The
hook then relies on `dockRect()` to find a `.pk-brand-mark` element in the header with a
non-zero rect:

```javascript
this.dockRect = () => {
  const marks = this.header.querySelectorAll(".pk-brand-mark")
  for (const mark of marks) {
    const rect = mark.getBoundingClientRect()
    if (rect.width > 0 && rect.height > 0) return rect
  }
  return null
}
```

If the isologo files are ever missing (deleted, renamed, a broken deploy, an environment that
doesn't ship `priv/static/images/`), `brand_logo/1`'s `@isologo?` gate correctly stops
rendering `.pk-brand-mark` in the header — so `dockRect()` finds **zero** matches and returns
`null` forever. `frame()`'s only response to a null dock rect is to reschedule and try again
next frame:

```javascript
this.frame = () => {
  this.rafId = null
  const natural = this.naturalRect()
  const dock = this.dockRect()
  if (!dock) {
    this.schedule()   // no timeout, no give-up path
    return
  }
  ...
}
```

There is no timeout, retry cap, or fallback here. Meanwhile the CSS makes the header's own
visibility conditional entirely on the hook ever reaching `docked = true`:

```css
/* app.css:2939-2943 */
body:has(#about-hero[data-morph-armed]) #app-header {
  visibility: hidden;
  opacity: 0;
  transition: none;
}
/* only .is-docked reveals it (app.css:2953-2957) */
```

`docked` never becomes `true` in this scenario, `is-docked` is never added, and
`this.header.setAttribute("inert", "")` (set once, early in `mounted()`) is never removed
either. Net effect: `#app-header` — the brand link, the nav links, and critically the mobile
hamburger/drawer trigger — is permanently `visibility: hidden` and `inert` on both `/club` and
`/quienes-somos`, with zero visual indication of failure and no way for the user to recover
(no navigation at all on that page). This is exactly the failure mode the codebase's own
`@isologo?` gate exists to prevent everywhere else, but it isn't applied here, and the hook's
otherwise-careful "hand the header back on failure" design (documented at
`about_header_morph_test.exs:120-136`, "the hook un-arms the page on both failure paths") does
not cover this specific path — the guard clause and the catch block are the only two
un-arming paths, and neither fires when the container div exists but never finds a dock
target.

**Fix:** Add a bounded retry/timeout to the `dockRect()`-is-null branch in `frame()` so a
prolonged failure to find a dock target falls back to the same "hand the header back" recovery
the guard clause and catch block already use, rather than polling forever:

```javascript
// captured once, right before wiring the scroll/resize listeners
this.dockSearchStartedAt = performance.now()

this.frame = () => {
  this.rafId = null
  const natural = this.naturalRect()
  const dock = this.dockRect()
  if (!dock) {
    if (performance.now() - this.dockSearchStartedAt > 3000) {
      // Never found a header mark to dock onto (e.g. missing isologo
      // assets) — hand the header back instead of leaving it hidden and
      // inert forever, mirroring the guard-clause/catch-block recovery.
      this.header.classList.remove("is-docked")
      this.header.removeAttribute("inert")
      this.el.removeAttribute("data-morph-armed")
      return
    }
    this.schedule()
    return
  }
  ...
}
```

Additionally, consider gating `#pk-about-morph-mark`'s markup itself on the same asset-existence
check `brand_logo/1` already computes at compile time (e.g. expose it as a small public
function on `Layouts` and reuse it in `about_live.ex`), so the About page degrades the same way
the header already does instead of only being caught by a runtime timeout.

## Warnings

### WR-01: `social_links/1`'s `icons` attr filters but does not reorder — the render order is always fixed, contradicting the covering test's own name

**File:** `lib/pukllay_club_web/components/layouts.ex:1080-1173` (rendering order),
exercised by `test/pukllay_club_web/components/layouts_test.exs:1247-1263`

**Issue:** `social_links/1` was promoted to public with new `icons`/`labels` attrs this phase.
The four channels are rendered in a **fixed** DOM order (whatsapp, then facebook, then
instagram, then email), each gated only by list membership:

```elixir
<a :if={:whatsapp in @icons} ...>...</a>
<a :if={:facebook in @icons} ...>...</a>
<a :if={:instagram in @icons} ...>...</a>
<a :if={:email in @icons} ...>...</a>
```

`@icons` therefore only controls *which* channels render, never the order they render in. The
covering test is named and worded as if `icons` also controls order:

```elixir
# test/pukllay_club_web/components/layouts_test.exs:1247-1263
test "icons subset renders only the requested channels, in order" do
  html = render_component(&Layouts.social_links/1, %{
    class: "test-social",
    icons: [:whatsapp, :instagram]
  })
  ...
  assert hrefs == [
    PukllayClubWeb.ClubLinks.whatsapp_group_url(),
    PukllayClubWeb.ClubLinks.instagram_url()
  ]
end
```

This only passes because `[:whatsapp, :instagram]` happens to already match the component's
fixed internal order. If the same test had been written as `icons: [:instagram, :whatsapp]`
(a legitimate way to read "in order" from the test name), it would fail — the hrefs would
still come back `[whatsapp, instagram]`. The About page's own call site
(`icons={[:whatsapp, :instagram]}`) is only correct today by coincidence of matching the
markup's built-in order; a future caller who orders the list differently, expecting the
rendered order to follow, will get silently wrong output with no test to catch it.

**Fix:** Either make the component actually honor list order:

```elixir
<div class={@class}>
  <%= for icon <- @icons do %>
    <.social_link icon={icon} labels={@labels} />
  <% end %>
</div>
```
(refactoring each channel's markup into a small `icon`-keyed case/component), or — if
fixed-order-with-filtering is the intended, simpler contract — rename the test and drop "in
order" from its description, and add a code comment on the `icons` attr documenting that it
filters only and does not reorder.

## Info

### IN-01: Vacuous placeholder test always passes and verifies nothing

**File:** `test/pukllay_club_web/about_header_morph_test.exs:376-383`

**Issue:**
```elixir
describe "pre-existing layouts_test.exs suite is unaffected" do
  test "layouts_test.exs still passes unmodified" do
    # Executed as part of the plan's <verify> command..., not re-run here —
    # this test documents the acceptance criterion.
    assert true
  end
end
```
`assert true` can never fail; this test adds a line to the suite's count without exercising
any behavior. If the intent is purely documentary, a code comment (or the plan file itself)
communicates the same acceptance criterion without a phantom "test" in the suite that a future
reader might mistake for real coverage.

**Fix:** Remove the test and fold its rationale into a comment near the top of the `describe`
block, or replace it with a real (if minimal) assertion against `layouts_test.exs`'s content if
the intent is to guard the file's continued existence.

### IN-02: `--pk-about-mark-h` is declared in a second, separate `:root` block instead of the file's primary design-token `:root`

**File:** `assets/css/app.css:2841-2843`

**Issue:** The stylesheet already has one canonical `:root { ... }` block near the top of the
file (`app.css:260-365`) holding every other shared design token (`--pk-gutter`,
`--duration-*`, `--ease-*`, `--pk-shadow-color`, etc.). This phase adds a second, separate
`:root { --pk-about-mark-h: 200px; }` block roughly 2500 lines later, right before the rules
that consume it. CSS allows multiple `:root` blocks (declarations merge), so this isn't
functionally broken, but it splits the "single shared token source" convention the file's own
top-of-file comments repeatedly establish, and makes the token easy to miss on a future audit
of the primary token block.

**Fix:** Either move `--pk-about-mark-h`'s declaration into the primary `:root` block at the
top of the file alongside the other shared tokens, or leave it local but rename it to a
non-`:root`-scoped custom property (e.g. declared directly on `.pk-about-mark-anchor` and read
via a CSS custom-property fallback) if page-local scoping is actually intended.
