## Decisions Made

**Decision (Task 1 checkpoint, resolved by the orchestrator with the human's answer): "size-step-lg + radius-keep" — both recommended options.**

1. **Size step: `size-step-lg`** (daisyUI's `btn-lg` composed with the project's 44px touch-floor utility, the exact composition already shipped at `catalog_live/show.ex:502`) — **chosen** over:
   - `size-step-design-source` (bespoke 16px type / 28px padding-inline / 48px height utilities matching sketches 050/051 literally) — **rejected**. Stated reason: daisyUI has no size step at these exact values, so it would require bespoke one-off utilities — recreating the very defect class being fixed here (one-off geometry substituting for the coupled size system), just in better proportions; it would also leave this as the only content-width button in the app without a real size step.

2. **Radius: `radius-keep`** (keep the app's global 4px field radius, no new radius class) — **chosen** over:
   - `radius-pill-scoped` (pill radius on this one component only) — **rejected**. Stated reason: would make this button the only pill in an app of right-angled buttons, risking an inconsistency read rather than an intentional accent.
   - `radius-pill-global` (flip the global field radius to a pill app-wide) — **rejected**. Stated reason: affects 180+ elements across catalog, detail, filter modal, footer and drawer — far outside a gap-closure round's blast radius; would need its own task and its own review.
   - Underlying rationale for keeping 4px at all: the diagnosis's winning in-browser mutation kept the 4px radius and the button still read as a proper button, so shape was not required to close the gap — only the size-step/touch-floor composition was.
