## The oscillation, in dates

| date | what the developer saw | what was done |
|---|---|---|
| Phase 01.2 round 4 | footer floating mid-page with plain background below it on short pages | sticky-footer mechanism ADDED (`.pk-app-shell` min-height floor + `flex-grow: 1` on its `main`) |
| 2026-09-02 | "a large, empty, unstyled band between the catalog page's last content row and the footer" (real mobile screenshot) | mechanism REMOVED by explicit choice, offered against "investigate a possible missing-content bug first"; `.pk-app-shell` deleted from app.css, from `<body>` in `root.html.heex`, and its three presence tests plus the CSS-facts describe deleted from `layouts_test.exs`. Tradeoff written into `app.css:392-397`. |
| 2026-09-09 | "the foother still isn't a the very bottom of the page" (desktop /quienes-somos screenshot) | this gap |

**The mechanism does not delete the empty space; it relocates it.** Below the footer becomes above
the footer, inside `<main>`, where the transparent wrapper shows the same page background. That is
one channel with two states, and the developer has now reported both. It is the same structural
shape as this phase's other two oscillations (G-01.5-5 -> G-01.5-8 on gap size; G-01.5-4 -> ... on
button geometry), and it is why this needs a decision rather than a fix.

## What is NOT in dispute

- **Cause A is real.** 298.00px / 478.00px / 309.00px / 32.31px / 392.31px / 963.50px, both themes,
  four routes, pixel-scanned as well as box-measured. A zero-result filter is one click away.
- **Cause A is not what the 2026-09-09 screenshot shows.** /quienes-somos is 3434px at every width
  from 1280 to 3440 and with every image and iframe suppressed; its footer's bottom edge IS the
  document's bottom edge to 0.00px; its own tint paints every visible row to the last one.
- **Cause B is what that screenshot shows**, and plan 01.5-11 fixed it (the same fill change, from
  the same footer-side lever, reached independently from this different symptom).
- **M2 is the correct mechanism if one is wanted.** `flex: 1 0 auto`, never `flex: 1`. And never
  `footer { margin-top: auto }`, which was measured to move nothing at all because it loses the
  cascade to two existing higher-specificity rules.

## Constraints that hold in every branch

- **Do NOT touch `body:has(.pk-about-cta-bar)`'s document-end clearance.** It is correct, it is
  painted by the fixed bar sitting over it, and it is plan 01.5-14's to re-derive against sketch 052
  winner B.
- **Do NOT touch the Cierre-to-footer boundary, `#cierre`'s `padding-block`, or the shared
  `main.pk-bottom-collapse + .pk-footer` rule.** All three are closed decisions from G-01.5-5 /
  G-01.5-6, all three were measured unchanged under M2, and none is on this defect's causal path.
- **Do NOT reach for `footer.pk-footer { margin-top: auto }`.** Measured zero effect; making it win
  means duplicating both collapse selectors.
- **Do NOT assume desktop-only.** Cause A reproduces at 390x844 as readily as at 1280x900 and in
  dark theme with identical numbers.
- **`#flash-group` becoming a flex item after the footer is verified safe** — `flash/1` renders with
  daisyUI's `toast` class, which is `position: fixed`, so the group stays height 0 in flow. If that
  class ever changes, the assumption breaks.

## Why no gate caught this — and why re-running the existing one would not help

`test/visual/about_geometry.mjs` is the repo's only rendered-geometry oracle and it runs against
**/quienes-somos only** — the single route that cannot exhibit the defect. Within it, every
bottom-related check measures a boundary ABOVE the footer or a fixed bar OVER it, never the document
below it. A grep for `scrollHeight` across `test/` finds one use, driving a scroll, never as an
assertion target. The gate gap is two-dimensional — route coverage AND the quantity measured — and
both dimensions have to be closed or a guard will not bite.

## What this plan decides, and what it refuses to decide

**Refused:** whether the mechanism comes back. That is Task 1's checkpoint. An executor applying
G-01.5-9's `missing` list verbatim would re-revert a seven-day-old explicit developer decision on
the strength of a diagnosis that did not know the decision existed, and would do it while the report
that triggered it has already been shown to be about something else. This plan exists to make that
impossible.

**Decided:** that G-01.5-9 gets closed on this pass either way, with the record naming which cause
each plan fixed. Leaving it open would guarantee a fourth round on the same 200px of page.

**Decided:** the mechanism, if chosen, is M2 exactly — `min-height` viewport floor on the body plus
`flex: 1 0 auto` on `<main>` — and it goes in as bare element selectors rather than by resurrecting
the `.pk-app-shell` class. That class and its three presence tests were deleted deliberately and
consistently on 2026-09-02 ("no half-applied branch"); bringing back a class whose whole documented
history is its own withdrawal would make the record harder to read, not easier. Bare `body`/`main`
selectors are also exactly what was measured.

**Decided:** the viewport unit follows this file's own documented dual-declaration idiom — the
static unit first as a fallback, the dynamic unit second — which `app.css:417-429` preserves as the
canonical explanation precisely because two other places cite it by name. The `dvh`-vs-`svh`
question the diagnosis raised (dynamic viewport units shift as mobile browser chrome hides, which
would animate the footer during scroll on short mobile pages) is a real one that headless Chrome
cannot answer, and it is flagged for the walkthrough rather than settled here.

**Decided:** the guard protects the CHOSEN state, not one particular state. If the mechanism is
restored, the guard is a rendered-distance assertion on a short page. If it stays withdrawn, the
guard is a source-level assertion that the shell declares no such mechanism, whose failure message
points at the superseding note and this decision — which is the more valuable guard of the two,
because the thing most likely to silently flip a twice-made decision is a future automated pass
reading the same diagnosis this plan had to correct.
