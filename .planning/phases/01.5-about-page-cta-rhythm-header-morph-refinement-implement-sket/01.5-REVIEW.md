## Warnings

### WR-01: `.pk-nav.is-scrolled`'s `background` declaration is now dead — the scrolled header no longer visually differs in fill color

**File:** `assets/css/app.css:1159-1230` (base `.pk-nav` rule at ~1159, `.pk-nav.is-scrolled` at ~1210)
**Issue:** The base `.pk-nav` rule already declares `background: var(--color-base-200);` unconditionally (this predates the phase and is untouched by it). This phase's G-01.5-7 fix changed `.pk-nav.is-scrolled`'s background from `color-mix(in srgb, var(--color-base-200) 94%, transparent)` to `var(--color-base-200)` — i.e., the exact same value the base rule already declares. The fix itself is correct (it closes the "FAQ band ghost-texting through the header" defect the comment describes), but the side effect is that `.pk-nav.is-scrolled`'s `background` declaration, and the `background` term in `.pk-nav`'s own `transition` list, are now no-ops: the header's fill color is identical at rest and while scrolled, and only `border-bottom-color`/`box-shadow` actually change on scroll. The comment directly above the rule ("The scrolled state stays visually distinct via border-bottom + box-shadow alone") already states this correctly, but the redundant `background: var(--color-base-200);` declaration and the `background` transition term are left in place, which will read as load-bearing to a future maintainer who has not traced both rules and will spend time (or make an incorrect edit) assuming a background change is happening.
**Fix:**
```css
/* .pk-nav (base rule) — drop the now-inert `background` transition term */
.pk-nav {
  background: var(--color-base-200);
  border-bottom: 1px solid transparent;
  transition: border-color var(--duration-base) var(--ease-standard),
    box-shadow var(--duration-base) var(--ease-standard);
}

/* .pk-nav.is-scrolled — drop the redundant background declaration entirely,
   or add an explicit comment noting it is intentionally restated for
   readability rather than functional */
.pk-nav.is-scrolled {
  border-bottom-color: var(--color-base-300);
  box-shadow: 0 1px 0 color-mix(in srgb, var(--color-base-content) 8%, transparent);
}
```

### IN-01: Google Maps iframe `sandbox="allow-scripts allow-same-origin"` — confirmed non-issue, noted for the record

**File:** `lib/pukllay_club_web/live/about_live.ex:746-755`
**Issue:** `sandbox="allow-scripts allow-same-origin"` on the same element is a commonly-flagged anti-pattern because the combination can let sandboxed content strip its own sandbox restrictions *when the framed content shares an origin with the parent document*. In this case the framed content is Google's own `maps.google.com`/`google.com` embed, a different origin from `pukllay.club`, so `allow-same-origin` only grants the iframe its own real origin (needed for Google's own maps tiles/cookies to function) rather than reducing isolation from the parent page — this is not exploitable here. Not part of this phase's diff (the embed block was relocated markup-only, from `#contacto` to `#juntadas`; the `sandbox` value itself is untouched), but since the file was in full-review scope I'm recording it as a confirmed non-issue rather than silently passing over a pattern an automated scanner would flag.
**Fix:** No action needed. If a future reviewer or scanner flags this again, this note documents why it was accepted.

### IN-02: `checkSumateButtonGeometry`'s pill-radius assertion can never fail against the current CSS value

**File:** `test/visual/about_geometry.mjs:849-856`
**Issue:** The check compares `getComputedStyle(...).borderTopLeftRadius` against `rect.height / 2` (the "shape-independent definition of a pill"). `.pk-sumate-btn` declares `border-radius: 9999px` (`assets/css/app.css:2576-2581`), and browsers report the *specified* computed value for `border-radius` rather than the value clamped to the box's actual rendered size — so `borderTopLeftRadius` will read `9999` regardless of the button's real height, and the assertion `9999 < radiusFloor - tolerance` is unsatisfiable for any realistic button size. The check is not wrong (it would still catch someone changing `.pk-sumate-btn` back to a small fixed-px radius like the pre-fix `4px`), but it can never distinguish "correctly a pill" from "declared an absurdly large radius that clamps to a pill visually" — a weaker guarantee than the comment ("shape-independent definition of a pill") implies. This is in a developer-invoked, non-CI-gated probe script, so the impact is low.
**Fix:** Not required to block this phase. If tightened later, compare against the *rendered* corner geometry (e.g., sampling whether the box actually paints as a stadium shape) rather than the specified `border-radius` value, or simply drop the radius check to what it can actually prove (radius is declared as a non-trivial value, not literally 4px).
