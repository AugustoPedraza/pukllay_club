## Critical Issues

### CR-01: WhatsApp chip loses its only accessible name at ≤639px in the Contacto card

**File:** `assets/css/app.css:2934-2936` (interacting with `lib/pukllay_club_web/components/layouts.ex:1084-1110`, `Layouts.social_links/1`, not itself in this diff)

**Issue:** Plan 01.5-02's new mobile icon-only rule hides the label `<span>` inside every
`.pk-about-contact-links a` at `≤639px`:

```css
.pk-about-contact-links a span {
  display: none;
}
```

`display: none` removes the span from the accessibility tree, not just from view. `social_links/1`
gives Facebook and Instagram a hardcoded `aria-label` regardless of the `labels` prop, so those two
chips keep an accessible name once their span is hidden. WhatsApp is different — its `aria-label`
is conditionally `nil` whenever `labels: true` is passed (`aria-label={if @labels, do: nil, else:
"WhatsApp"}`), on the assumption that the visible `<span>Grupo de WhatsApp</span>` already supplies
the accessible name. The Contacto card calls `social_links` with `labels` (true), so at rest the
WhatsApp link's *only* accessible name is that span's text.

Once the span is hidden at ≤639px, the WhatsApp anchor renders with no `aria-label` and no visible
text — verified directly against the rendered `/quienes-somos` markup:

```html
<a href="https://chat.whatsapp.com/L1TLhxGSkgiF1dgkJnp8Pp" target="_blank" rel="noopener noreferrer">
  <svg ...></svg><span>Grupo de WhatsApp</span>
</a>
```

(no `aria-label` attribute at all — compare to the Facebook/Instagram anchors right after it, both
of which do carry one). At any viewport ≤639px, a screen-reader user lands on an unlabeled link for
the club's primary contact channel; on the same page, Facebook and Instagram remain correctly
labeled. This is a defect the phase's own change introduced: before this plan's mobile icon-only
rule existed, the span was always visible, so the missing `aria-label` was harmless.

**Fix:** Either give the CSS-visible span a screen-reader-safe hiding technique instead of
`display: none` (this codebase already has an `sr-only` precedent, e.g. the footer's drawer-utility
label at `app.css:2254-2259`) so the accessible name survives when the visual label collapses:

```css
.pk-about-contact-links a span {
  /* sr-only, not display: none — keeps the accessible name when the
     visible label collapses to icon-only (CR-01) */
  position: absolute;
  width: 1px;
  height: 1px;
  padding: 0;
  margin: -1px;
  overflow: hidden;
  clip: rect(0, 0, 0, 0);
  white-space: nowrap;
  border: 0;
}
```

or, more targeted, fix `social_links/1`'s conditional so WhatsApp always carries a real
`aria-label` (matching Facebook/Instagram's unconditional pattern) regardless of `labels`:

```elixir
aria-label="WhatsApp"
```

Either fix closes the gap; the `sr-only` approach is safer long-term since it does not depend on
every future `labels: true` consumer also happening to keep its label visible at every breakpoint.

measurement pass from `#contacto` to `#juntadas` (line 392, with a comment explicitly warning that
this file is "developer-invoked and outside mix quality/CI, so nothing else catches this drift").

```js
...
log(`Open: ${baseUrl}/quienes-somos#juntadas`)
```

### WR-02: Near-duplicated CSS-block-extraction helpers across three `describe` blocks

**File:** `test/pukllay_club_web/live/about_live_test.exs:799-812` (`media_639_body`/`extract_balanced_block`), `:1095-1104` (`media_640_body`), `:1175-1184` (`media_480_body`)

**Issue:** `media_639_body/1`, `media_640_body/1`, and `media_480_body/1` are byte-for-byte
identical except for the hard-coded breakpoint value (`639px` / `640px` / `480px`) and the
`min-width`/`max-width` keyword, each re-implementing the same "find the media query, then hand off
to the shared `extract_balanced_block/2`" pattern. All three exist purely to parametrize one thing
(the media-query regex). This is straightforward duplication that will keep growing linearly with
every future breakpoint-scoped CSS test in this file.

**Fix:** Collapse to one parametrized helper:

```elixir
defp media_body(src, query) do
  case Regex.run(~r/@media\s*\(#{Regex.escape(query)}\)\s*\{/, src, return: :index) do
    [{start, match_len}] -> extract_balanced_block(src, start + match_len)
    nil -> nil
  end
end
```

and call it as `media_body(src, "max-width: 639px")`, `media_body(src, "min-width: 640px")`, etc.,
moving it (and `extract_balanced_block/2`) to module scope once instead of duplicating per
`describe` block.

## Info

### IN-01: Hover state on Contacto chips now changes only `border-color`, losing the prior text-color hover cue

**File:** `assets/css/app.css:2909-2911`

**Issue:** The pre-existing hover rule swapped both `border-color` and `color` to
`var(--color-primary)`. This diff (D-06, accent-tint chip rework) intentionally drops the `color`
swap because the old target color was tuned against the previous `--color-base-100` resting
background, not the new `--color-accent` one, and the comment explains the reasoning. The result is
a real, if minor, UX reduction: hovering a chip now only changes a 1px border, with no text/icon
color shift, versus the previous, more noticeable dual-property hover cue. Not incorrect, and
explicitly deliberate per the comment, but worth a human-eyes check that hover feedback still reads
clearly against both themes' accent-tint backgrounds before treating this as settled.

**Fix:** No code change required unless a visual QA pass on the accent chip's hover state finds it
too subtle; if so, consider deriving a hover text color from `--color-accent-content` via
`color-mix()` (already an established pattern elsewhere in this file) rather than reusing
`--color-primary`, which is what caused the original contrast mismatch this diff worked around.
