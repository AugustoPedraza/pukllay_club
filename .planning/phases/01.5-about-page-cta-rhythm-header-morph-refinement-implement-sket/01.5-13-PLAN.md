## Two causes, one root, proven orthogonal

The ten single-variable mutations settle which lever moves which quantity, and nothing in the matrix
moves both:

| lever | pad/content ("too much space") | sig/h2 ("balance") |
|---|---|---|
| padding-block 2.5rem | 1.67 -> **0.93** | 1.248 unchanged |
| h2 -> 32px/40px | 1.67 -> 1.53 | 1.248 -> **0.936** |
| BOTH | -> **0.85** | -> **0.936**, ink margins 41.5/41.5 |
| gap 24 -> 16 / 12 | -> 1.85 / **1.95 (backwards)** | unchanged |
| signature 10px -> 12px | -> 1.57 | -> **1.498 (worse)** |
| drop the `<br>` | -> **2.03 (worst)** | -> **1.792 (worst)** |

**Shipping one lever closes half the report**, and on this band's four-round history that is how a
gap reopens rather than closes.

## The five landmines the diagnosis recorded, verbatim in force

1. **THE RENDERED GAP IS 36px, NOT 24px.** Bebas Neue is an all-caps face and "NOS VEMOS EL SÁBADO"
   has no descender ink, so 8.5px of the h2's line box below the baseline is permanently empty.
   8.5 + 24.0 declared + 3.5 caption leading = 36.0px exactly. Raising the heading to 32px/40px
   widens this to 38px. Anyone re-tuning this band by reading `gap: 1.5rem` off the stylesheet is
   reasoning from a number 12px smaller than what the eye receives.
2. **DO NOT TOUCH THE GAP.** D-12 requires one unconditional gap rule at every viewport; the desktop
   block's own comment forbids re-declaring it; and tightening it degrades the very complaint it
   would be aimed at. This is the THIRD session in which this band's flat 24px gap looked guilty on
   paper and measured innocent — G-01.5-8 found the same on desktop one gap earlier.
3. **A mobile `#cierre h2` rule must out-specify the `font-display text-2xl` utility** on the same
   element. The `#cierre h2` selector already does this successfully at >= 640px, so reuse that
   exact selector shape — and note this file's top-of-file cascade hazard, where an unlayered
   `.pk-*`/id rule silently beats a utility. That direction is intended here and is a trap in
   reverse.
4. **VERIFY NO HEADING WRAP AT THE NARROWEST SUPPORTED WIDTH.** At 375px a 32px heading measures
   218.3px in a 347px content box (63% fill); at 320px the box is ~292px, so the margin shrinks. A
   two-line heading would introduce a new defect in the act of fixing this one.
5. **STRUCTURE THE FIX AS THE MOBILE COUNTERPART TO THE 640px BLOCK**, not as two scattered
   overrides — and update the desktop block's own comment, which currently justifies its 5rem by
   naming "its larger heading" as a carrier that does not exist on mobile.

## The oracle landmine this plan adds to that list

`checkCierreMobileInvariance` (`test/visual/about_geometry.mjs:565-601`) contains:

```
const SHARED_BAND_PADDING_PX = 144 // 2 x 4.5rem, .pk-band's own padding
const expectedHeight = measured.cierreInner.height + SHARED_BAND_PADDING_PX
```

It asserts, below 640px, that the band's height equals its content plus that literal — i.e. **it
pins the mobile band to exactly the padding value this gap is about**, and it will fail the moment
that padding changes. That is the same class of mistake `CIERRE_DESKTOP_GAP_TARGET_PX = 128` made
one level up, which plan 01.5-09 had to replace with a derived budget before it could ship a
legitimate retune. It must be re-derived in the SAME change, not nudged to a new literal — nudging
it would restate the new value and re-arm the identical trap for the next retune.

The check's OTHER assertion — that the mobile band keeps an even top/bottom split — is correct and
must survive; it is the only thing standing between this plan and an accidental asymmetric padding.

## Not in scope, already answered

- The 89px of clear space between the signature and the footer is **the same lever, already
  counted**: 73.5px of the band's own bottom padding + 1px hairline + ~14px of footer lead-in. The

- The band/footer surface relationship is G-01.5-8's and plan 01.5-11 shipped it.
- The signature's colour at >= 640px is plan 01.5-11's; its size, case and tracking below 640px are

## The values this plan ships, and why each is defensible rather than merely arithmetic

**`padding-block: 2.5rem` below 640px.** Lands pad/content at 0.93 with the current column and 0.85
once the heading step also ships — inside the 0.90-1.02 range derived from this band's OWN
human-accepted desktop state, not from taste. `3rem` measures 1.12 with the current column and 1.02
with the heading step, and is recorded in the comment as the runner-up to reach for if the
walkthrough says 2.5rem reads cramped, exactly as plan 01.5-09 recorded 6rem as the desktop
runner-up. One value, one place, one named alternative.

**`font-size: 32px` with a `40px` line-height below 640px.** Lands sig/h2 at 0.936 — the heading
finally out-measures its own caption. 30px was measured at 0.999, an exact tie, i.e. no hierarchy at
all; 32px is also precisely what the existing desktop clamp resolves to at 640px, so the band's size
ramp becomes continuous across the breakpoint instead of stepping. The line-height is declared
because the heading's line box is the operand in landmine 1's arithmetic and leaving it to inherit
would make the rendered gap unpredictable.

**Both, in one media block, or neither.** No single-variable mutation in the diagnosis's ten-case
matrix moves both quantities into range. Splitting them across two plans or two blocks would ship
half a fix and re-open the gap, and would also lose the structural point: the root cause is one media
block owning both of this band's distinguishing treatments, so the repair is its mirror image.

**PERCEPTUAL SUFFICIENCY IS EXPLICITLY NOT CLAIMED.** These are mechanism-derived targets from a
band that has already had four UAT rounds, on a codebase that has already had one arithmetically
sound, correctly diagnosed fix on this very page rejected on human review. Both numbers go to the
end-of-phase walkthrough as a `<human-check>` with their runner-ups named, and the SUMMARY says so
rather than asserting closure.

**The mobile invariance oracle is re-derived from the stylesheet, not re-pinned to a new number.**
The check should assert what is actually invariant — that the band's vertical padding is symmetric
and that its height is exactly its content plus its own declared padding, read live — rather than
that the padding equals any particular value. Written that way it keeps catching the thing it was
built to catch (a desktop-only treatment leaking below the gate) while surviving every future
deliberate retune, including this one.
</decisions_made>
