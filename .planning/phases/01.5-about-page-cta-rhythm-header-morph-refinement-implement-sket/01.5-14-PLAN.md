## What the sketch specifies, and what does not port

Sketch 052's four frames all reuse one `.sumate-btn` rule whose comment names it as "the shared real
button geometry — `.pk-sumate-btn` (app.css): min-height 48px, padding-inline 28px, radius 9999px,
font-size 1rem". Variant B changes exactly three things about the shipped state:

| channel | shipped today | variant B |
|---|---|---|
| container surface | `background: base-100` + `border-top: 1px solid neutral` + `padding: 0.75rem gutter` | none at all — transparent wrapper |
| container layout | full-bleed flex row, button stretched `w-full` | full-bleed flex row, `justify-content: center`, `pointer-events: none`, offset up from the viewport edge |
| button fill | `btn-outline btn-primary` (transparent, primary ink and border) | solid primary fill with primary-content ink, elevated by a shadow, sized to its own content |

**Does not port:** the sketch's `position: absolute`, which exists only to pin the bar to a 620px
preview frame. The real element is `position: fixed` and stays so. Its `z-index: 40` stays. Its
`left: 0; right: 0` stay.

**Does not change:** `.pk-sumate-btn`'s four geometry values, the hero and closing-band placements,
`Layouts.sumate_cta/1`'s caller-class merge, D-11's suppression of the closing-band button at the
same threshold, and the component being the single source for all three placements.

## The five things that will break if they are not handled deliberately

1. **`about_live_test.exs`'s "no `.pk-about-cta-bar` rule declares `justify-content`" test.** Its
   premise is that daisyUI's `.btn` already centres its own label — true for a `w-full` button,
   irrelevant for a content-sized one that now has to be centred within a full-bleed wrapper.
   Variant B requires the property this test forbids.
2. **`about_live_test.exs`'s "keeps base-100 fill and uses the neutral border token" test.** This is
   plan 01.5-10's G-01.5-7 recurrence guard, one round old, and its failure message carries the
   measured contrast numbers for both themes. Variant B deletes both declarations it pins.
3. **`margin-block-end: 0` on the base rule.** A Rule-1 bug found by live probe in plan 01.5-08:
   Tailwind v4's `space-y-*` puts `margin-block-end` on every non-last child and this element is not
   the last child, so un-neutralised it lifted the fixed bar's rendered box 16px off the viewport
   edge. A floating pill has its own deliberate offset; a stray 16px on top of it would be invisible
   as a bug and wrong as a layout. KEEP THIS DECLARATION.
4. **`body:has(.pk-about-cta-bar)`'s `calc()` clearance**, currently composed from the bar's two
   padding steps, the button's `min-height` and the border width — three of those four operands stop
   existing. A source test asserts the value is composed rather than literal; that contract stays,
   its operands change.
5. **`checkFixedBarFooterClearance`**, which asserts the footer's bottom edge and the bar's top edge
   coincide within tolerance. That is the correct assertion for a bar flush to the viewport edge and
   the wrong one for a pill deliberately floating above it — the pill's top edge must clear the
   footer's bottom edge by the pill's own offset, and the check has to express that without
   restating the offset as a literal.

## The new risk variant B introduces that the shipped bar did not have

A full-width, fully transparent, `position: fixed` element sits over the bottom of every About page
view at mobile widths. If `pointer-events` is not exactly right, it silently swallows taps on
whatever is underneath it — including, at the page bottom, the footer's own links. The shipped
bar was opaque and reserved its own space, so this could not happen. The sketch handles it with
`pointer-events: none` on the wrapper and `pointer-events: auto` on the button; both halves are
required and the pair must be verified against real hit-testing, not assumed from the declaration.

## The judgment calls this plan resolves, and on what evidence

### The solid fill is a CSS modifier class, not a new component attribute

`Layouts.sumate_cta/1` renders `btn btn-outline btn-primary pk-sumate-btn` and merges a
caller-supplied class. A caller cannot REMOVE `btn-outline` by adding a class, so the fill has to be
overridden rather than swapped. Two routes exist and the modifier class is chosen:

- it mirrors the design source exactly — sketch 052 expresses this as `.sumate-btn.solid`, a
  modifier on the shared geometry class, in the same file that insists the three placements share
  one class;
- it keeps `sumate_cta/1`'s API and its three call sites untouched, so the component's own docstring
  argument (one component, one geometry class, no drift) survives verbatim;
- it uses the caller-class merge that already exists and is already tested — the same seam that
  carries `w-full` today.

The modifier must out-specify daisyUI's `btn-outline`, which is the unlayered-beats-layered cascade
direction this file documents at the top and which `.pk-sumate-btn` itself already relies on. No
`!important`. It must also give the solid state its own hover treatment, because `btn-outline`'s
hover is an inversion to a filled state that means nothing once the rest state is already filled.

### The elevation uses this file's own shadow idiom, not the sketch's token

The sketch reaches for `var(--shadow-lg)` from the sketch theme. This app defines no such token; its
established mid-elevation idiom is a two-value shadow built with `color-mix` against
`--pk-shadow-color`, already used on more than one raised surface in this file. Reuse it by name and
value rather than introducing a token the theme does not have — the same reasoning that kept the
pill radius as a literal in plan 01.5-10 rather than inventing a radius token.

### The bar's contrast guard is superseded, not deleted, and the record says why

Plan 01.5-10 closed G-01.5-7 one round ago by re-tokening this bar's border. Variant B removes the
border and the fill together, which makes that guard unassertable — but the concern behind it is
real and must be re-expressed for the new shape rather than dropped. Its successor asserts what now
carries figure/ground: that the button in the bar resolves a solid fill from the primary token pair
rather than rendering as an outline. That is a stronger contrast position than the border ever was
(the primary/primary-content pair is an audited theme pair, unlike every base-ladder step, none of
which clears 3:1), and it should be stated as such in the failure message alongside the numbers the
superseded guard carried, so nobody reads the change as a quiet retreat from G-01.5-7.

### The clearance is derived from the pill, and it is not a "tight fit" any more

The shipped bar sat flush to the viewport edge, so reserving exactly its height and asserting a tight
fit was correct. A floating pill has an offset below it that is part of the design, so the reservation
is the offset plus the pill's own height plus a deliberate breathing step above it, and the oracle's
assertion changes shape accordingly: the footer's last content must sit fully above the pill's top
edge, and the space below the footer must equal the pill's own footprint — no more (bare background
shows) and no less (the pill covers footer content). Both directions still get distinct failure
messages, and neither threshold may be a literal: they are derived from the pill's measured rect and
the reservation's computed value in the same pass, exactly as plan 01.5-10 established.

### D-11's threshold, the co-location block, and the component all stay put

The pill appears at the same width the bar did, the closing-band button is still suppressed there,
and all three rules still share one media block for the reason already written into the stylesheet:
a threshold mismatch between "CTA appears" and "clearance is reserved" or "duplicate ask disappears"
opens a width range that is worse than either problem alone.
</decisions_made>
