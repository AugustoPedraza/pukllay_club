# Phase 01.1: Code Review Report

**Reviewed:** 2026-08-22
**Depth:** standard
**Files Reviewed:** 27
**Status:** issues_found

## Summary

The reviewed surface is the site-shell/content-pages implementation (About page, catalog shell,
filter modal, game preview, error pages, and their configs/tests). The overall code is disciplined
— consistent whitelisting of client input (`select-image`, `see-all`, facet toggles never build
atoms from user data), parameterized Ecto queries throughout `Catalog`, and thorough test coverage
for the happy paths and several adversarial paths (huge `min_age`, malformed sort/facet params,
XSS-adjacent share-link encoding).

That discipline has two real gaps, both of which are crash bugs, not style nits:

1. `GamePreview.tiempo_text/1` raises `Protocol.UndefinedError` for a specific, plausible nullable
   playtime combination, and it runs on the server for every card in the initial grid/carousel
   render (not just on hover/tap) — a single game record with that shape would break the whole
   catalog page.
2. `CatalogLive.Show`'s `mount/3` promises a branded 404 for "an unknown id" (T-01-30), but that
   guarantee is only true for a numeric-but-nonexistent id; a non-numeric `/juegos/:id` (which any
   crawler or manual prod exploration will eventually hit) raises `Ecto.Query.CastError`, which
   does **not** implement `Plug.Exception`, so it 500s instead of rendering the branded 404 the
   moduledoc/tests claim.

Beyond those two, there's a fragile duplicated magic number between `Catalog.filter_games/1`'s
default limit and `CatalogLive.Index`'s page size (currently coincidentally equal, silently
depended on by `"load-more"`), an input-bounding inconsistency on the live search box vs. the
URL-driven `q`, a hardcoded copyright year, and a documented-but-violated CSS rule (literal
`rgba()` shadows in a block whose own comment bans literal colors).

## Critical Issues

### CR-01: `GamePreview.tiempo_text/1` crashes on `min_playtime: nil` + non-nil `max_playtime`

**File:** `lib/pukllay_club_web/components/game_preview.ex:376-381`
**Issue:**

```elixir
defp tiempo_text(%{min_playtime: nil, max_playtime: nil, playing_time: nil}), do: nil
defp tiempo_text(%{min_playtime: nil, max_playtime: nil, playing_time: pt}), do: "#{pt} min"

defp tiempo_text(%{min_playtime: min, max_playtime: max}) when is_nil(max) or min == max, do: "#{min} min"

defp tiempo_text(%{min_playtime: min, max_playtime: max}), do: "#{min}-#{max} min"
```

For a game with `min_playtime: nil, max_playtime: 45` (any non-nil `max_playtime` that isn't equal
to `min`), none of the first three clauses match:
- clause 1/2 require `max_playtime: nil` — false
- clause 3's guard `is_nil(max) or min == max` — `is_nil(45)` is false, and `nil == 45` is false

So it falls through to the last clause, which builds `"#{min}-#{max} min"` with `min = nil`. Raw
Elixir string interpolation of `nil` (as opposed to HEEx's `{}` interpolation, which is safe and
renders empty) raises `Protocol.UndefinedError: protocol String.Chars not implemented for nil`.

This is not a rendering-time edge case hidden behind a click — `facts_row/1` (which calls
`tiempo_text/1`) is invoked for **every** game in `preview_body/1`, and `preview_body/1` is
embedded server-side inside every card's `<template data-game-preview>` (`GameCard`/`CarouselRow`)
as well as directly on `CatalogLive.Show`'s masthead. The `<template>` tag is inert client-side,
but the HEEx is still fully evaluated on the server at render time. A single seeded game with this
playtime shape crashes the whole catalog page render (LiveView process crash), not just that one
card.

Contrast with the sibling function in the same file, `players_text/1`, which correctly handles
this by checking `min_players: nil` unconditionally as its own first clause (independent of
`max_players`), and with `CatalogLive.Show`'s own `playtime_text/1` (`lib/pukllay_club_web/live/catalog_live/show.ex:773-780`), which correctly uses `is_integer(min) and is_integer(max)` guards
rather than `is_nil`/`==` — that one is safe for this exact case.

**Fix:**
```elixir
defp tiempo_text(%{min_playtime: nil, max_playtime: nil, playing_time: nil}), do: nil
defp tiempo_text(%{min_playtime: nil, max_playtime: nil, playing_time: pt}), do: "#{pt} min"
defp tiempo_text(%{min_playtime: nil, max_playtime: max}), do: "#{max} min"
defp tiempo_text(%{min_playtime: min, max_playtime: nil}), do: "#{min} min"
defp tiempo_text(%{min_playtime: min, max_playtime: max}) when min == max, do: "#{min} min"
defp tiempo_text(%{min_playtime: min, max_playtime: max}), do: "#{min}-#{max} min"
```
(or simply mirror `playtime_text/1`'s `is_integer/1` guard style, which already handles every nil
combination correctly).

### CR-02: A non-numeric `/juegos/:id` 500s instead of rendering the promised branded 404

**File:** `lib/pukllay_club/catalog.ex:109` (root cause), called from `lib/pukllay_club_web/live/catalog_live/show.ex:62-63`
**Issue:**

```elixir
# catalog.ex
def get_game!(id), do: Repo.get!(Game, id)

# catalog_live/show.ex
def mount(%{"id" => id}, _session, socket) do
  game = Catalog.get_game!(id)
  ...
```

The moduledoc explicitly promises: *"`mount/3` loads the game via `Catalog.get_game!/1`, which
raises `Ecto.NoResultsError` for an unknown id — Phoenix renders the branded 404 page ... rather
than crashing (T-01-30)."* That's true only when `id` is a value that *can be cast* to the primary
key's type (a numeric string) but doesn't match a row — `Ecto.NoResultsError` implements
`Plug.Exception` with status 404, which is what the existing test exercises
(`~p"/juegos/999999999"`).

It is not true for a non-numeric id, e.g. `/juegos/abc` or `/juegos/12abc`. `Repo.get!/2` attempts
to cast the id to the primary key's type before querying; a value that fails to cast raises
`Ecto.Query.CastError` (a `dumped to type :id` cast failure), which does **not** implement
`Plug.Exception`. That exception propagates as an unhandled 500, in production showing Phoenix's
generic error page rather than the branded `404.html.heex` the team built specifically to avoid
that (`01.1-07`). Every existing test for this path (`test/pukllay_club_web/live/catalog_show_test.exs:165-189`) only exercises the numeric-but-nonexistent case, so this gap is untested and
undetected. This is exactly the class of input a crawler or a mistyped/copy-pasted URL will
produce.

**Fix:** Validate/normalize the id before the `Repo` call and fail the same way `Ecto.NoResultsError`
does, e.g.:
```elixir
def get_game!(id) when is_binary(id) do
  case Integer.parse(id) do
    {int_id, ""} -> Repo.get!(Game, int_id)
    _ -> raise Ecto.NoResultsError, queryable: Game
  end
end
```
(adjust to the actual primary key type — swap for a UUID-format check if `Game.id` is a
`binary_id`). This keeps the single `Ecto.NoResultsError` → 404 contract intact for every kind of
bad id, not just the numeric one.

## Warnings

### WR-01: `"load-more"` silently depends on two independently-maintained page-size constants matching

**File:** `lib/pukllay_club_web/live/catalog_live/index.ex:237-250`, `lib/pukllay_club/catalog.ex:20,41,85`
**Issue:** `handle_event("load-more", ...)` builds its query opts without a `:limit`:
```elixir
def handle_event("load-more", _params, socket) do
  opts = socket.assigns |> filter_opts() |> Map.put(:offset, socket.assigns.offset)
  case safe_filter_games(opts) do
    {:ok, games} -> ...
```
`filter_opts/1` never sets `:limit`, so `Catalog.filter_games/1` falls back to its own
`@default_limit` (`catalog.ex:20`, `= 24`) rather than `CatalogLive.Index`'s `@page_size`
(`index.ex:37`, also `24`). Every other call site (`apply_filters/1`, `index.ex:318`) sets
`:limit` explicitly. Today the two constants happen to match, so pagination looks correct and the
existing "Cargar más" test passes — but nothing enforces that they stay equal. If either constant
is changed independently (a very plausible future edit — e.g. bumping the page size for a wider
grid), "load more" would silently fetch a different page size than the initial page, producing
gaps or duplicate rows in the stream without any error.
**Fix:** Add the missing key explicitly:
```elixir
opts =
  socket.assigns
  |> filter_opts()
  |> Map.put(:offset, socket.assigns.offset)
  |> Map.put(:limit, @page_size)
```

### WR-02: The live "search" event doesn't bound `q`, unlike every other entry point for the same field

**File:** `lib/pukllay_club_web/live/catalog_live/index.ex:147-149` vs. `:143-144`
**Issue:** `initial_q/1` (the URL/mount path) explicitly truncates: `String.slice(q, 0, 100)`, with
a comment citing T-01.1-28 for "bounding the entry point." But the live handler for the same
field has no such bound:
```elixir
def handle_event("search", %{"q" => q}, socket) do
  {:noreply, socket |> assign(:q, q) |> apply_filters()}
end
```
Any length of string typed into (or `render_change`/scripted into) the nav search box or
`FilterModal`'s search input (`filter_modal.ex:119-127`, no `maxlength`) is assigned to socket
state and passed straight to `websearch_to_tsquery` uncapped — inconsistent with the stated
"bound at the entry point" discipline applied everywhere else in this module (`parse_list_param/2`
truncates to 20 elements, `initial_q/1` truncates to 100 chars). `CatalogLive.Show`'s own search
form (`show.ex:174-181`) does carry `maxlength="100"`, making the omission on Index/FilterModal's
inputs an inconsistency rather than a deliberate choice. A Postgres-level failure from a
pathological value is still caught by `safe_filter_games/1`'s rescue, so this isn't an availability
risk, but it is a real, demonstrable gap in the input-bounding discipline the module documents for
itself.
**Fix:** Truncate in the handler the same way `initial_q/1` does (`String.slice(q, 0, 100)`), and
add `maxlength="100"` to both search `<.input>` call sites for client-side parity with `Show`'s.

### WR-03: Hardcoded copyright year in the shared footer

**File:** `lib/pukllay_club_web/components/layouts.ex:566`
**Issue:** `<span class="pk-footer-meta">© 2026 Pukllay Club · <.bgg_attribution /></span>` — the
year is a literal. This is correct today but guaranteed to go stale the moment the calendar rolls
to 2027, on every page, with no test or mechanism to catch it.
**Fix:** `© #{Date.utc_today().year} Pukllay Club` (assign it once, e.g. in `footer/1`, rather than
recomputing per interpolation site).

### WR-04: Literal `rgba()` shadow colors violate the CSS block's own "never a literal color" rule

**File:** `assets/css/app.css:424-426` (`.pk-portal`), `:466` (`.pk-sheet`), `:987` (`.pk-drawer`),
`:1523` (`.pk-lightbox-img`), `:1549` (`.pk-share-popover`)
**Issue:** The "PK CATALOG SURFACES" block's own header comment (`app.css:139-141`) states: *"Every
class resolves colour through the daisyUI theme CSS variables ... never a literal hex/rgb color —
so both the light and dark theme render every surface correctly."* Every one of these five rules
uses a literal `rgba(20, 8, 34, 0.38)`/`rgba(20, 8, 34, 0.24)`/`rgba(20, 8, 34, 0.25)`/
`rgba(20, 8, 34, 0.28)` shadow color instead of a theme variable. Three of the five
(`.pk-drawer`, `.pk-lightbox-img`, `.pk-share-popover`) are new in this phase and their own
comments say they "reuse `.pk-portal`'s exact shadow values" — i.e. the anti-pattern was
knowingly propagated for cross-surface consistency rather than fixed. Functionally this doesn't
break anything (a fixed dark shadow color reads fine in both themes), but it's a real,
demonstrable violation of a rule this same file states is load-bearing for correct dark-theme
rendering, and it will keep getting copy-pasted into new floating surfaces going forward.
**Fix:** Either introduce a `--pk-shadow`/`--shadow-color` custom property (even a static one,
declared once in `:root` alongside `--pk-gutter`) and reference it from all five rules, or amend
the block's own rule comment to carve out an explicit "shadows are the one exception" clause so
future contributors aren't misled by the stated invariant.

## Info

### IN-01: `Layouts.app/1` renders `header_inner`/`subnav`/`nav_drawer` twice (sticky vs. non-sticky branches)

**File:** `lib/pukllay_club_web/components/layouts.ex:144-368`
**Issue:** The `:if={@sticky}` and `:if={!@sticky}` branches are near-identical blocks that both
call `<.header_inner .../>`, `{render_slot(@subnav)}`, and `<.nav_drawer .../>` — the comment
explains this is required because a colocated hook's leading-dot name is only qualified when
`phx-hook` is a static string literal, so a dynamic `@sticky && ".CatalogNav"` expression can't be
used. The workaround is reasonable, but the duplicated three-line tail (`header_inner`/`subnav`/
`nav_drawer`) could be factored into a shared private function taking `sticky` as a plain argument
and called once, reducing the duplicated surface to just the outer wrapping `<div>`.
**Fix:** Extract the shared body into a helper and call it from both branches, or accept the
duplication with a comment noting it's intentional (already partially done).

### IN-02: `Layouts.brand_logo/1`'s `isologo?` is a test-only, undeclared assign

**File:** `lib/pukllay_club_web/components/layouts.ex:39-46`
**Issue:** `assign_new(assigns, :isologo?, fn -> @isologo? end)` accepts an `isologo?` key that is
deliberately *not* declared via `attr`, solely so a test can force the fallback branch
(`render_component(&brand_logo/1, %{isologo?: false})`). This is a legitimate, documented seam,
but it means the component silently accepts an assign no production caller (or `attr` validator)
knows about — a typo'd caller passing `isologo?: false` by accident would silently disable the
logo with no compile-time or attr-validation warning.
**Fix:** No change required given the documented rationale; flagging only so the tradeoff is
visible in review (an alternative would be a `Mix.env() == :test` guard instead of an assign-based
seam).

### IN-03: "Ver todo" on the recency shelf doesn't reproduce that shelf's own expansion filter

**File:** `lib/pukllay_club_web/live/catalog_live/index.ex:277`, `lib/pukllay_club/catalog.ex:219-224`
**Issue:** `list_carousel_rows/0`'s `recientemente_anadidos` row is built from `recent_query/0`,
which filters `where: g.is_expansion == false`. Clicking that row's "Ver todo" tile maps to
`see_all_selection("recientemente_anadidos")` → `%{sort: :year_desc}` only — no
`is_expansion`/tags/weight_band constraint — so the "Ver todo" grid will include expansions the
shelf itself excluded. This is already called out in the code's own comment as a known,
accepted limitation ("out of this plan's scope... See SUMMARY"), so it's not a hidden defect, but
it is a real, user-visible inconsistency (a game absent from the row appears once "Ver todo" is
clicked) worth keeping on record here since this review's job is to surface it independently of
the developer's own note.
**Fix:** None required for this phase per the documented scope decision; flagged for traceability.

### IN-04: `"open-lightbox"` has no server-side guard mirroring the UI's `:if={@selected_image}` condition

**File:** `lib/pukllay_club_web/live/catalog_live/show.ex:104-106` vs. `:280`
**Issue:** The lightbox trigger button only renders when `@selected_image` is truthy
(`:if={@selected_image}`, `show.ex:280`), but `handle_event("open-lightbox", _params, socket)`
itself does not re-check that invariant server-side:
```elixir
def handle_event("open-lightbox", _params, socket) do
  {:noreply, assign(socket, :lightbox_open, true)}
end
```
A forged `pushEvent("open-lightbox", {})` from the browser console (bypassing the hidden button)
would set `lightbox_open: true` with `@selected_image == nil`, rendering `<img src={nil} ...>` —
HEEx interpolation safely degrades `nil` to an empty attribute, so this is a broken-image/empty
lightbox, not a crash, but it's a defense-in-depth gap relative to how carefully the rest of this
module whitelists client-triggered state (`select-image`'s explicit whitelist check is the pattern
this handler doesn't mirror).
**Fix:** `if socket.assigns.selected_image, do: assign(socket, :lightbox_open, true), else: socket`.
