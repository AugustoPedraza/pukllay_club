<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/juegos/:id` with an unknown id | An attacker-chosen id reaches `Catalog.get_game!/1` and produces an error response rendered by a new template. |
| application failure → user-facing page | A raised exception now renders through a template with access to error assigns rather than a fixed status string. |
| browser → `handle_event("retry", ...)` | A new no-payload event re-runs the catalog query. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01.1-09 | Information Disclosure | `404.html.heex` and the `render_errors` layout change | high | mitigate | The template renders three fixed strings and one link — it never interpolates `@reason`, `@conn`, an exception message, a stack trace or the requested id. No 500 template is added, so an application failure still returns the fixed status string rather than executing more template code. Asserted by a negative-content test in Task 3. |
| T-01.1-26 | Denial of Service | `handle_event("retry", ...)` | low | mitigate | Retry re-enters the existing `apply_filters/1` pipeline, which already applies `LIMIT` unconditionally (T-01-22) and already rescues a failing query into `:load_error`. It takes no params, so there is nothing to craft; the cost per click is one bounded query. |
| T-01.1-27 | Information Disclosure | catalog error-state copy | low | mitigate | The error state states the user-visible situation and the next step without asserting a cause the app cannot observe and without echoing the underlying exception — the copy is the design contract's validated wording, not a generated message. |
| T-01.1-SC | Tampering | dependency supply chain | low | accept | No package-manager install occurs — `mix.exs`/`mix.lock` untouched. |
