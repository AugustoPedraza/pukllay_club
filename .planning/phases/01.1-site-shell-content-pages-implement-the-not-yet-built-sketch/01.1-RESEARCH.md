## Summary

This phase turns nine already-locked sketch design documents plus one user-supplied About-page
HTML export into real Phoenix/LiveView code. Almost nothing here is a design decision — the design
work is done and captured in `.claude/skills/sketch-findings-pukllay_club/`. The real risk in this
phase is **implementation drift between the sketch's assumed CSS vocabulary and the actual shipped
`assets/css/app.css`**, which uses a completely different custom-property naming scheme (daisyUI's
`--color-base-100/200/300`/`--color-base-content`/`--color-neutral` vs. the sketch theme's
`--color-bg`/`--color-surface`/`--color-text`/`--color-text-muted`) and has **no motion-token
system at all** in production (`--duration-*`/`--ease-*` exist only in the sketch's own throwaway
theme file, never merged) — despite `motion-system.md` claiming "already the live system." Existing
`.pk-*` classes in `app.css` already demonstrate the correct translation pattern (hardcoded hex/px
values resolved through daisyUI's own `--color-base-*` tokens, motion values hardcoded inline as
`220ms cubic-bezier(...)` rather than referencing a token) — this phase's new CSS should follow that
same established pattern, not the sketch's token names literally.

The second material risk is that `Layouts.app`/`CatalogLive.Show` today are far less built than the
sketch findings assume: there is **no footer at all** in the current shell, the header supports only
2 of the 3 states `page-shell.md` requires (no breadcrumb/crumb state, no about-page nav-links
state, no Sumate CTA slot), and `CatalogLive.Show` renders every field as a bare unstyled `<dl>`
with zero buy-box, zero sticky/mobile chrome, and zero "Juegos similares" shelf. This is a full
build of three of the five requirements (SHELL-01's footer half, SHELL-02, SHELL-03), not a
restyle — size the plan accordingly.

Three deferred gray areas need an explicit decision recorded in the plan (not silently resolved):
filter UI shape (modal vs. keep the shipped drawer), the reservation flow's real WhatsApp number,
and "Juegos similares" selection logic. This research provides a concrete, schema-grounded
recommendation for each so the plan doesn't stall, but each should still be flagged for the user to
confirm/override, per CONTEXT.md's explicit instruction not to silently resolve them.

**Primary recommendation:** Build in dependency order — (1) shell (header 3-state + footer) first,
since detail/about both render inside it; (2) About page second (self-contained, no dependency on
detail-page work); (3) detail page rebuild third (buy-box + reading column + similares shelf,
reusing `CarouselRow`/`GameCard` as-is); (4) empty/loading/error state restyle across catalog+detail
last (touches existing working logic, lowest risk of new bugs). Land the filter-UI decision (modal
vs. drawer) explicitly before wave-planning SHELL-04, since it changes whether that requirement is
new-component work or CSS-only restyle work.

## CSS Token Translation Layer

The sketch findings' theme file (`sources/themes/default.css`) was never merged into production
`app.css` — production instead uses daisyUI's own theme-variable names directly plus hardcoded
px/rem/ms literals for spacing/motion (no custom `--space-*`/`--duration-*` layer exists at all).
Existing `.pk-*` classes in `app.css` already demonstrate the correct translation; use this table,
not the sketch's own CSS blocks verbatim, for every new selector this phase adds:

## Filter UI: Modal vs. Drawer

**This is a real, undiscussed decision — do not resolve it silently in the plan (per CONTEXT.md's
own `<deferred>` instruction). Present the following recommendation to the user for explicit
confirmation before or during planning.**

**What SHELL-04 literally requires:** "a centered modal with checklist-style facets, reachable from
a nav search box with live narrowing."

**What actually exists today** `[VERIFIED: lib/pukllay_club_web/components/filter_drawer.ex,
full file read this session]`: a fully working, already-shipped, UAT-fixed (per STATE.md's
`260821-dah` quick-task log: "closes the 01-05-PLAN.md drawer/pills tappability thread") daisyUI
`drawer drawer-end` slide-over panel with weight-band/editorial-hashtag/mechanic/theme checklist
pills and a scalar-filter form — this already matches "checklist-style facets" functionally, just
not the "centered modal" chrome, and it is reached from a `Filtros` trigger button next to the sort
dropdown, not from the nav search box (the nav search box today only drives free-text `q` search,
per `catalog_live/index.ex`'s `<:nav_search>` slot).

**Recommendation:** Build a **real centered modal** (daisyUI `dialog`/`modal modal-open` pattern,
per `ux-patterns` SKILL.md B10's confirmation that this is available-but-unwired) as a *new*
component, reusing the drawer's existing event contract verbatim (`toggle-facet`,
`set-scalar`, `clear-filters` — no new LiveView handler logic needed, only new trigger markup),
rather than attempting to reskin the drawer's own DOM into a modal shape. Two reasons:
1. **This satisfies the literal requirement text** ("centered modal") rather than reinterpreting it
   to mean "keep the drawer" — SHELL-04 was written into REQUIREMENTS.md deliberately with modal
   language, and no CONTEXT.md decision overrides that literal wording (it's explicitly listed as
   *undiscussed*, not *resolved-in-favor-of-drawer*).
2. **"Reachable from a nav search box with live narrowing"** describes a materially different
   entry point than today's separate `Filtros` button — the modal should likely open when the user
   interacts with (clicks/focuses) the nav search box, with the free-text query and the
   checklist facets living together in one surface, rather than two separate affordances
   (search box + filter button) as today. This is a bigger interaction change than a pure visual
   reskin and should be scoped as such in the plan.

**What NOT to do:** Don't delete/replace `FilterDrawer` and its passing tests speculatively if the
user, when asked, prefers to keep the shipped drawer (a legitimate answer — "SHELL-04's wording
predates knowing a drawer would already ship and get UAT-verified" is a reasonable case for
amending the requirement instead of rebuilding). Either path is viable; what's not viable is the
plan silently picking one without recording that a real requirement-vs.-shipped-reality conflict
existed and was resolved.

## Common Pitfalls

### Pitfall 1: Sketch CSS tokens silently resolving to nothing
**What goes wrong:** Pasting a sketch-findings CSS block (e.g. `page-shell.md`'s `.footer-d
.footer-row { ... }`) directly into `app.css` compiles without error but renders with missing
colors/spacing/radii, because `--color-bg`/`--space-6`/etc. are undefined custom properties in
production.
**Why it happens:** The sketch's own theme file (`sources/themes/default.css`) was authored to
"mirror the real brand tokens" in spirit (same hex values) but was never actually merged — it
defines its own parallel custom-property names that happen to describe the same visual system as
daisyUI's, without being the same tokens.
**How to avoid:** Use the `## CSS Token Translation Layer` table above for every new selector.
**Warning signs:** A new element rendering with browser-default black text, transparent
backgrounds, or square corners despite CSS "clearly" setting a color/radius — check dev tools'
computed styles for `initial`/`unset` custom property values.

### Pitfall 2: Assuming the fixed 64px header-height offset from the sketch
**What goes wrong:** `detail-page-layout.md`'s `.poster-col { top: calc(64px + var(--space-4)); }`
hardcodes 64px as "clears the sticky header" — if the real shipped `.pk-nav` renders at a different
height (likely, since it now needs to fit a Sumate CTA + theme toggle + brand + potentially a
breadcrumb, more elements than the sketch's own header had), the sticky poster column will overlap
or gap incorrectly.
**Why it happens:** Sketch mockups are standalone HTML with their own, simpler header — the real
header has more content packed into it after D-05's Sumate CTA addition.
**How to avoid:** Measure the real rendered header height in the actual app (dev tools, or a
`getBoundingClientRect()` read) before hardcoding any `top:` value that depends on it; consider
deriving it via CSS instead of a magic number where possible (e.g. `top: calc(var(--header-h,
64px) + 1.5rem)` with `--header-h` set by a small JS hook reading the real header's rendered
height, if a fixed value proves unreliable across breakpoints).
**Warning signs:** The sticky poster/buy-box visibly overlapping the header on scroll, or a visible
gap between the header and the poster's sticky resting position.

### Pitfall 3: `IntersectionObserver` for anything that must survive a backgrounded tab
**What goes wrong:** Using `IntersectionObserver` for the About page's fade-in-on-scroll,
detail page's sticky title-bar/mobile CTA bar trigger, or any similar visibility toggle silently
breaks in a backgrounded browser tab (Chrome throttles/suspends the callback).
**Why it happens:** Documented twice already in this project's own sketch history — `page-shell.md`
and `detail-page-mobile-interaction.md` both record this as a real, previously-shipped-then-fixed
bug (sketch 011 corrected sketch 005's original `IntersectionObserver` approach).
**How to avoid:** Use a plain `scroll` listener + `getBoundingClientRect()` for the sticky title-bar
and mobile CTA-bar triggers, per the corrected pattern already documented in `detail-page-mobile-
interaction.md`. The existing `.CatalogNav` hook's chip-scroll-spy use of `IntersectionObserver`
(`layouts.ex:120-136`) is a different, lower-stakes use case (a nav highlight, not a
show/hide toggle) and doesn't need to change — but don't extend that same `IntersectionObserver`
approach to any new visibility-toggling behavior in this phase.
**Warning signs:** A sticky bar or CTA that "sometimes doesn't show up" in manual testing,
especially after switching tabs/apps during testing.

### Pitfall 4: Container-query/transform ancestors breaking `position: fixed` descendants
**What goes wrong:** Adding `container-type`, `transform`, `filter`, `perspective`, `contain`, or
`will-change` to any ancestor of the mobile CTA bar (or any `position: fixed` element) silently
makes that ancestor a new containing block, breaking the fixed element's viewport-relative
positioning.
**Why it happens:** Documented in `detail-page-mobile-interaction.md` as a real bug hit during
sketching.
**How to avoid:** Audit any ancestor of a new `position: fixed` element for these properties before
adding them elsewhere for unrelated reasons; if a fixed element goes missing/mispositioned, check
ancestors for these properties first.
**Warning signs:** A fixed-position element rendering far off-screen or in the wrong position only
in certain contexts.

### Pitfall 5: Equal-specificity CSS cascade order for responsive display toggles
**What goes wrong:** A base `display: none` rule and a later `@media` override with equal
specificity resolve by source order, not by which media query matches — silently hiding an element
at every viewport width if the base rule happens to sit after the media query in file order.
**Why it happens:** Documented as a real, multi-round bug in both `page-shell.md` and
`detail-page-mobile-interaction.md`.
**How to avoid:** When adding any new responsive show/hide rule, place the "narrow-viewport
density and navigation switch" additions in the existing single consolidated `@media (max-width:
480px)` block at the bottom of `app.css` (the file's own convention, explicitly documented at
`app.css:587-602` as "placed last so it wins the cascade") rather than scattering a new base
`display: none` rule elsewhere in the file.
**Warning signs:** An element that should only be hidden/shown at one breakpoint behaving
identically at every width.

### Pitfall 6: `-webkit-line-clamp` bleeding into a flex sibling
**What goes wrong:** A clamped title sharing a flex row with a fixed-width sibling (e.g. a pill or
badge) may not actually shrink for flex-shrink purposes, overlapping the sibling instead of
truncating.
**Why it happens:** Documented in `card-interaction.md` as a real cross-browser quirk with
`-webkit-line-clamp`'s intrinsic-width calculation.
**How to avoid:** Give clamped/truncated content its own row when it must share space with other
fixed-width elements (e.g. the detail page's facts-pill-row above `<h1>` is already correctly
designed as its own row per `detail-page-layout.md` — preserve that separation, don't compress it
into one row with the title to save vertical space), or use plain `white-space: nowrap; text-

## Open Questions

1. **Filter UI: modal vs. drawer — user confirmation needed.**
   - What we know: SHELL-04's literal wording says modal; a working, UAT-verified drawer already
     ships; no sketch designed a modal variant.
   - What's unclear: whether the user wants the literal requirement honored (rebuild as modal) or
     wants to amend SHELL-04 to match what already shipped (keep drawer).
   - Recommendation: surface this explicitly before/during planning (see `## Filter UI` section
     above for the full reasoning); default to building the modal if no answer arrives, since that
     honors the written requirement, but flag it loudly as reversible/questionable.

2. **Reservation WhatsApp number — user must supply the real value.**
   - What we know: it needs to be `config/runtime.exs` env-var-driven, following the
     `image_origin`/R2 precedent exactly.
   - What's unclear: the actual phone number, and whether it's the same as the About page's
     `chat.whatsapp.com` group invite link (probably not — a group invite link and a
     `wa.me/<number>` direct-message deep link are different WhatsApp features entirely).
   - Recommendation: block shipping the reservation flow's real number on user input; the plan
     should include a placeholder/dev-only value (e.g. required in `runtime.exs` similar to
     `SECRET_KEY_BASE`'s "raise if missing" pattern) so it fails loudly in `:prod` rather than
     silently shipping a fake number.

3. **BGG attribution exact wording — user must supply.**
   - What we know: D-04 says the user knows the required wording/format and will provide it; the
     sketch's placeholder ("© 2026 Pukllay Club · datos de BoardGameGeek") must not ship as final.
   - What's unclear: the actual required text — this research did not find it (out of scope; it's
     explicitly a user-supplied input, not something to derive from BGG's public terms via
     WebSearch, since D-04 is explicit that the user "already knows" it).
   - Recommendation: the plan should either wait on this input or ship the placeholder behind an
     explicit `checkpoint:human-verify` / TODO marker that blocks the phase from being marked fully
     done, not silently ship it as final compliance text.

4. **Logo/isologo asset — user must supply.**
   - What we know: D-03, `brand_logo/1` already gates on file presence at compile time with no code
     change needed once supplied.
   - What's unclear: timing — whether the file lands before or during this phase's execution.
   - Recommendation: no blocking action needed; the existing gate degrades gracefully either way.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Reflected content in the reservation modal's name-capture field, echoed into a client-constructed `wa.me` URL | Tampering / Information Disclosure | Follow the existing `select-image` event handler's whitelist-check precedent (`show.ex`'s `gallery_thumbnails/1` check, T-01-26) — but note the reservation name field is inherently free-text (a person's name), so the mitigation here is proper URL-encoding of the name into the `wa.me?text=` query param (client-side `encodeURIComponent`), not a whitelist; this is standard web hygiene, not a novel threat this codebase hasn't handled before (T-01-31's `GamePreview` hook already demonstrates the "clone template content, never assemble markup from strings/dataset values" pattern that should extend to any new client-side markup construction in this phase) |
| A crafted `url` param on any new client-echoed field (mirroring the existing `select-image` mitigation) | Tampering | If any new LiveView event handler echoes client-supplied data back into rendered HTML/attributes, apply the same whitelist-against-known-values check `CatalogLive.Show`'s existing `handle_event("select-image", ...)` already demonstrates — this phase's `AboutLive` and modal work don't obviously need this (no new user-controlled echo surfaces identified in the sketch findings), but flag it as a review point if any new event handler is added that takes free-form client input and reflects it into markup |
| Inline `onerror`/inline event-handler attributes, blocked by this app's CSP (`script-src 'self'`) | Tampering (script injection surface) | Already correctly handled once (`js-cover-fallback` pattern, delegated capture-phase listener in `app.js` rather than inline `onerror`) — any new image-loading fallback in the About page's photo carousel (once real photos exist, still placeholders now) should follow the same delegated-listener pattern, not an inline attribute, which this app's CSP (`[VERIFIED: lib/pukllay_club_web/csp.ex:1-46]`, `script-src 'self'`) would silently refuse |
