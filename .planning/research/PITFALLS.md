# Pitfalls Research

**Domain:** Elixir/Phoenix 1.8 LiveView + Postgres/pgvector deployed via Docker+Kamal to a single
Hetzner CAX31 ARM node, local CPU embeddings, Oban async jobs, free-tier LLM calls, solo dev,
~€15/mo budget
**Researched:** 2026-07-24
**Confidence:** MEDIUM (web-sourced, cross-checked across multiple independent sources per topic;
no official case study exists for this exact stack combination, so treat scale numbers as
directional, not guaranteed)

## Critical Pitfalls

### Pitfall 1: Cross-building the arm64 image via QEMU emulation instead of building natively

**What goes wrong:**
Building the production Docker image `--platform=linux/arm64` from an amd64 GitHub Actions runner
(the default) goes through QEMU emulation. This is 5-20x slower than a native build and, on
Erlang/OTP 25+ (JIT-enabled), has a documented QEMU/Erlang-JIT interaction that can crash the build
or the running container outright, because QEMU doesn't detect the JIT's code-replacement pattern
and disables a memory-mapping trick the JIT relies on.

**Why it happens:**
`docker buildx build --platform linux/arm64` "just works" syntactically on any host, so it's the
first thing tutorials show — but they're usually demoed on amd64 with a JIT-less runtime or a
trivial app, not a full `mix release` compile under QEMU.

**How to avoid:**
Prefer a native arm64 build path: either a native arm64 GitHub Actions runner, or build directly on
the target CAX31 host (fine at this project's scale/budget — one server, infrequent deploys). If
QEMU cross-build is unavoidable, set `ERL_FLAGS="+JPperf true"` as a workaround and budget CI time
accordingly. Multi-stage Dockerfile regardless of build path (compile stage discarded, slim runtime
stage shipped).

**Warning signs:**
CI build times balloon to 10x+ of a local build; container crashes on boot with obscure JIT/memory
errors that don't reproduce when built natively; build works on `linux/amd64` but fails only under
`--platform=linux/arm64`.

**Phase to address:**
Phase 0 (walking skeleton) — this is one of the three decisions explicitly flagged for Phase 0
discuss/plan ("Phoenix release Dockerfile strategy for aarch64").

### Pitfall 2: No safe migration path wired into the Kamal deploy

**What goes wrong:**
Kamal has no built-in Phoenix/Ecto migration hook. Teams either (a) skip migrations on deploy and
run them manually/ad hoc (drifts, forgotten steps, downtime windows), or (b) run migrations from
inside `handle_event`/on every boot without ordering guarantees, causing multiple containers to race
migrations during a rolling deploy, or schema-mismatched code to serve requests against a
half-migrated DB.

**Why it happens:**
Rails' Kamal defaults (and most Kamal tutorials) are Rails-first; the Phoenix equivalent isn't
built-in and has to be assembled from Phoenix's generated `lib/my_app/release.ex` module plus a
custom Docker `ENTRYPOINT`/`cmd` hook, which isn't obvious coming from `mix phx.server` local dev.

**How to avoid:**
Use the release-script pattern: a custom entrypoint script (or Kamal's pre-deploy hook) that runs
`bin/my_app eval "MyApp.Release.migrate"` (generated by `mix phx.gen.release`) to completion *before*
the app process starts listening, so the health check only passes once migrations succeeded —
Kamal's zero-downtime cutover then naturally gates traffic on migration success. Keep migrations
backward-compatible with the *previous* release during rolling restart windows (safe-migration
practices: additive column changes before removing old columns in a later deploy, avoid long table
locks in a single migration).

**Warning signs:**
Deploys that "work" but intermittently 500 on first requests after deploy; schema errors that
disappear on retry; migrations run more than once in the same deploy (check `schema_migrations`
timestamps against deploy logs).

**Phase to address:**
Phase 0 — explicitly flagged as an open decision for Phase 0 planning. Verify by deploying a schema
change through the full Kamal pipeline before Phase 0 is considered done, not just deploying static
code.

### Pitfall 3: Plaintext or under-scoped secrets in `.kamal/secrets`

**What goes wrong:**
Kamal 2 reads secrets from `.kamal/secrets`, not `.env` (Kamal does not auto-load `.env` anymore).
The two failure modes: (1) committing real secret values directly into `.kamal/secrets` — plaintext
credentials sitting in git history, on the dev's laptop, and in CI logs; (2) assuming a secret listed
once is automatically available to every role/accessory — Kamal requires each role and accessory to
explicitly declare which secrets it needs, so a missing declaration silently produces a nil/blank
env var in that specific container rather than an error.

**Why it happens:**
`.kamal/secrets` looks like a normal dotfile and it's tempting to just paste values in during a
solo, move-fast setup — the multi-secret-manager options (1Password, Bitwarden, Doppler, GCP/AWS
Secrets Manager) look like overkill for a single-developer €15/mo project.

**How to avoid:**
For this project's budget/scale, the pragmatic middle ground (not full 1Password/Doppler) is:
`.kamal/secrets` sourced via `$(cat ...)`/environment-variable substitution pointing at values
injected by GitHub Actions repo secrets at deploy time — never literal values in the file — and the
file itself gitignored. Explicitly list required secrets per role/accessory (`SECRETS` config per
service) rather than assuming global availability. Rotate `SECRET_KEY_BASE`/`DATABASE_URL`/API keys
if any were ever committed, even briefly.

**Warning signs:**
`git log -p .kamal/secrets` shows real values at any point in history; a role's container is missing
an env var that's present in `.kamal/secrets` (check with `kamal app exec env` against expectation);
CI logs print secret values because of unmasked echo/debug output.

**Phase to address:**
Phase 0 — the third explicitly flagged open decision ("minimal secrets management approach").

### Pitfall 4: Kamal health check misconfigured for LiveView/Phoenix, silently losing zero-downtime

**What goes wrong:**
Kamal's default health check hits `GET /up` on the app's exposed port and gates traffic cutover +
old-container teardown on it passing. Phoenix's `/up` path either isn't wired up by default in older
`phx.gen.release` output, or gets protected by auth/CSRF/plug pipelines meant for browser routes,
or takes too long to become healthy because of app startup work (embedding model load, Ecto pool
warmup) exceeding Kamal's readiness window. When the health check fails, the deploy either hangs, or
(if someone "fixes" it by disabling health checks to unblock a deploy) it silently ships without
zero-downtime protection or migration-gating — requests can hit a container mid-boot.

**Why it happens:**
Health checks are invisible until the first deploy that's slow to boot (e.g., once Bumblebee/Ortex
model loading is added in Phase 2) — Phase 0's trivial app boots fast and never exercises this edge.

**How to avoid:**
Add an explicit `/up` LiveView-free plain-text health endpoint outside the auth pipeline from Phase
0 onward. Set `readiness_delay` deliberately once Phase 2 adds embedding-model warmup at boot (or,
better, defer model loading to first-use/async so boot stays fast — consistent with this project's
"never on request hot path" principle). Never disable Kamal health checks as a deploy-unblocking
hack; fix the underlying readiness issue instead.

**Warning signs:**
`kamal deploy` hangs at "Waiting for app to become healthy"; deploys succeed but users briefly see
502/503s right after a deploy; health check passes in seconds locally but the container needs 10s+
in production.

**Phase to address:**
Phase 0 (health endpoint + gating baseline); revisit in Phase 2 when embedding-model load is added
to app startup — verify readiness timing didn't regress.

### Pitfall 5: Assuming amd64-tuned embedding runtime performance carries over to ARM CPU

**What goes wrong:**
Both realistic local-embedding paths — Bumblebee/EXLA (Nx's XLA backend) and Ortex (ONNX Runtime
binding) — are primarily tuned and benchmarked on x86/AVX. On aarch64: (a) EXLA/XLA precompiled
binaries may not exist for the exact aarch64-linux-gnu + OTP + Nx version combo, silently falling
back to `XLA_BUILD=true`, a very slow local from-source compile that can make CI or first deploy
take an unexpectedly long time; (b) ONNX Runtime on ARM64 has no AVX/AVX2 kernels and instead uses
Neon/KleidiAI-optimized MLAS kernels — models exported/quantized assuming x86 (especially FP16) can
be *slower* on ARM than a plain FP32 model, because of runtime precision-cast overhead, not faster.

**Why it happens:**
Almost every embedding-model tutorial, benchmark, and blog post available today runs on x86 laptops
or amd64 cloud VMs; ARM-specific behavior is an afterthought even in official docs.

**How to avoid:**
This is exactly why the roadmap already calls for spiking the ARM embedding runtime first in Phase
2 rather than assuming it. During that spike: benchmark the actual embedding model (batch and
single-item latency) on the real CAX31 hardware (or an equivalent Ampere/Neoverse arm64 box), not a
dev laptop; prefer FP32 or INT8-quantized ONNX models over FP16 on ARM; confirm Bumblebee/EXLA has a
working precompiled `xla` binary for the exact target before committing to it, or fall back to Ortex
if not; keep the embedding call fully async via Oban so a slower-than-expected CPU inference time
degrades throughput, not user-facing latency.

**Warning signs:**
`mix deps.compile` for `xla`/`exla` takes many minutes on first CI/deploy run (sign it's compiling
from source, not fetching a precompiled binary); embedding latency on the CAX31 is a large multiple
of what was measured on a dev laptop; CPU pegged at 100% for simple single-item embedding calls.

**Phase to address:**
Phase 2, at the very start (the roadmap already sequences "spike the ARM embedding runtime first" —
this pitfall is the reason why; don't skip the spike).

### Pitfall 6: pgvector index built/tuned wrong for this project's small, static-ish dataset

**What goes wrong:**
Two distinct failure modes at ~400 games (with room to grow moderately, not exponentially): (1)
using IVFFlat and creating the index before the catalog is fully loaded — IVFFlat's centroids are
computed once at index-build time from whatever data exists then, so building it early (e.g., right
after `mix ecto.migrate` on an empty table, before the CSV seed runs) permanently bakes in bad
centroids and poor recall until the index is dropped and rebuilt; (2) leaving IVFFlat's `probes`
at its default of 1, which searches only the single nearest cluster and silently returns poor-quality
matches with no error — a correctness bug that looks like "the recommender just isn't very good."

**Why it happens:**
IVFFlat is the older, more commonly-documented pgvector index type, so tutorials default to it; its
failure mode (bad recall) doesn't error, it just quietly returns mediocre results, which is easy to
mistake for "the embedding model isn't great" rather than an index tuning bug.

**How to avoid:**
At this project's scale (~400-a few thousand rows, well under HNSW's advantage threshold of ~1M
rows), use HNSW instead of IVFFlat — it has no training/centroid step, builds correctly on an
initially-empty or partially-seeded table, and gives strong recall with minimal tuning (`m=16,
ef_construction=200` is a reasonable starting point). This also removes the "index built too early"
failure mode as a class of bug entirely. If IVFFlat is ever used instead, always build the index
*after* the full seed load, and set `probes` explicitly (10-50, tuned against `lists`) rather than
trusting the default.

**Warning signs:**
Natural-language search returns obviously wrong/unrelated games for clear queries; recall looks
fine in a quick manual dev test (small subset) but degrades after the full 400-game seed loads;
`EXPLAIN ANALYZE` on a vector query shows a sequential scan instead of using the index at all
(missing `probes`/`ef_search` config, or index built on wrong column type).

**Phase to address:**
Phase 2 — when pgvector + hybrid ranking is introduced. Verify by testing search quality against
the full seeded catalog, not a handful of rows, before considering the feature done.

### Pitfall 7: pgvector index build memory defaults causing slow, low-quality builds

**What goes wrong:**
Postgres's default `maintenance_work_mem` (64MB) is far too small for building a vector index; when
the index build doesn't fit in that memory, Postgres spills to disk, which is reported to be 10-50x
slower and — for HNSW specifically — produces a measurably lower-quality graph (Postgres emits a
`NOTICE` about this in the build logs, easy to miss if logs aren't watched). At ~400 games this is
unlikely to be catastrophic, but it's a footgun that compounds silently as the catalog and embedding
dimensionality grow (e.g., moving to a larger embedding model later).

**Why it happens:**
Default Postgres memory settings are conservative for a generic shared-hosting-friendly config, not
tuned for vector workloads; nobody notices until an index build that "should" take seconds takes
minutes, or recall quietly degrades.

**How to avoid:**
Set a session-scoped `SET maintenance_work_mem = '256MB'` (or similar, sized to the actual catalog
— 400 rows won't need gigabytes) before running `CREATE INDEX` in the migration, and watch build
logs for the disk-spill `NOTICE`. Also budget `work_mem` per concurrent connection separately —
relevant given Oban workers and web requests share the same small CAX31 Postgres instance.

**Warning signs:**
Index-build migration takes noticeably long relative to row count; a `NOTICE` about the graph not
fitting in `maintenance_work_mem` appears in migration/build logs; vector query recall is worse than
expected even with the right index type and `probes`/`ef_search`.

**Phase to address:**
Phase 2, same migration that creates the pgvector index.

### Pitfall 8: Oban queue concurrency starving the app's own Ecto connection pool

**What goes wrong:**
Oban's job-processing connections and the web app's request-handling connections draw from the same
small Postgres instance (single CAX31, no separate DB tier). If Oban queue concurrency is set
without regard to the app's `pool_size` and Postgres's `max_connections`, bursts of async work
(embedding generation, LLM query-parsing jobs) can starve the pool that LiveView requests need,
turning an async-job backlog into a user-facing outage — the opposite of the project's stated
principle that heavy work should stay off the request path without breaking the request path.

**Why it happens:**
Oban's queue concurrency defaults look independent of the web app, so it's easy to size each in
isolation ("10 web pool + 10 Oban concurrency = 20, seems fine") without checking Postgres's actual
`max_connections` on a modest CAX31-hosted Postgres instance, or without accounting for other
connections (migrations, `psql` debugging sessions, future accessories).

**How to avoid:**
Size Oban queue concurrency and Ecto `pool_size` together against Postgres `max_connections` with
headroom, on a single small instance keep total concurrent connections comfortably below the limit,
and prefer a few well-sized queues over many high-concurrency ones. Since no LLM/embedding work is
ever synchronous with a request per this project's principles, Oban concurrency can be tuned
conservatively without hurting UX — there's no reason to over-provision it.

**Warning signs:**
Web requests intermittently fail/time out only during periods of high Oban job volume (e.g., after
a bulk re-embedding run); `DBConnection.ConnectionError`/pool checkout timeout errors in logs
correlate with Oban queue activity; Postgres `pg_stat_activity` shows connection count near
`max_connections` during normal operation.

**Phase to address:**
Phase 2 — when Oban is introduced. Set explicit, deliberate concurrency limits rather than accepting
defaults, and load-test with a batch job (e.g., re-embedding the full catalog) before shipping.

### Pitfall 9: Treating the free-tier LLM API as a dependable production dependency

**What goes wrong:**
Free-tier LLM APIs (the project's chosen approach is Gemini free tier via InstructorLite) come with
low requests-per-minute limits (roughly 5-15 RPM depending on model), daily request caps, and
quotas that providers have cut with little notice historically (a documented free-tier quota
reduction happened as recently as December 2025). A feature built assuming the free tier "just
works" the way a paid API would will intermittently fail — or fail entirely if the provider tightens
limits again — exactly when a real user is mid-search.

**Why it happens:**
Free tiers are attractive for a €15/mo budget and work fine in dev/testing where request volume is
low, so the failure mode only shows up under real (even light) production traffic or after a
provider-side policy change outside the project's control.

**How to avoid:**
This project's architecture already helps: no LLM call is ever on the request hot path (async via
Oban), which gives natural room for retry/backoff instead of a hard user-facing failure. Make that
explicit: Oban job retries with backoff for rate-limited/failed LLM calls, a sensible max-retry
policy with a graceful degraded result (e.g., fall back to keyword/embedding-only search if
LLM query parsing fails or times out, rather than blocking the whole search), and monitoring/alerting
on LLM call failure rate so a quota change is noticed quickly rather than discovered via user
complaints. Don't build a hard dependency where LLM failure means the feature is unusable — always
have a non-LLM fallback path for the core search flow.

**Warning signs:**
Sporadic search-quality degradation with no code change; Oban job failure/retry counts for the LLM
queue climbing; 429/rate-limit responses appearing in logs, especially correlated with time-of-day
or usage spikes (club events).

**Phase to address:**
Phase 2 — when LLM query parsing is introduced. Build the fallback and retry/backoff behavior as
part of the feature, not as a later hardening pass.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|-----------------|------------------|
| Skip a `/up` health endpoint or leave Kamal defaults untouched | Faster Phase 0 setup | Silent loss of zero-downtime deploys once boot time grows (Phase 2 model loading) | Never past Phase 0 — fix before Phase 2 adds startup work |
| Run migrations manually via SSH instead of wiring an entrypoint hook | Avoids Dockerfile/entrypoint complexity early | Deploys and migrations drift out of sync; someone eventually forgets a step | Only for the very first throwaway deploy, never once real data exists |
| Use IVFFlat because it's the more commonly tutorial'd pgvector index | Slightly simpler mental model, marginally smaller index | Silent recall bugs if index built before full seed, and low value at this row count anyway | Never at this dataset size — HNSW is strictly the better default here |
| Accept default `maintenance_work_mem`/Oban concurrency instead of tuning for the CAX31's actual RAM | Zero config effort | Slow index builds and/or connection-pool starvation under real load | Only acceptable during the Phase 2 spike/prototype, never past first production seed load |
| Treat the free-tier LLM as always-available with no fallback | Simpler code, faster to ship Phase 2 | Feature becomes unusable during rate-limit windows or provider quota changes | Never — the async architecture already makes retry/fallback nearly free to add |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|-----------------|-------------------|
| Kamal + Phoenix release migrations | Assuming Kamal has a Rails-style built-in migration hook | Wire a custom entrypoint calling the generated `MyApp.Release.migrate`, gated by the health check |
| Kamal + Postgres accessory (if self-hosted, not managed) | Exposing the Postgres accessory port to `0.0.0.0`, or assuming UFW protects it (Docker's iptables rules bypass UFW) | Bind accessory ports to `127.0.0.1` only; don't rely on UFW alone to firewall Docker-published ports |
| Kamal accessory startup ordering | Assuming Postgres/other accessories are ready before the app container starts | Add retry/backoff in the app boot path or an explicit accessory health/readiness check before app start |
| Bumblebee/EXLA on aarch64 | Assuming the precompiled XLA binary exists for the exact OTP+Nx+target triplet without checking | Verify precompiled binary availability during the Phase 2 spike; have Ortex as a documented fallback |
| InstructorLite + Gemini | Following outdated examples that hand-roll JSON-schema workarounds | Pin to InstructorLite v1.2.0+ which uses Gemini's native `responseJsonSchema` support directly |
| Cloudflare R2 backups | Treating "upload succeeded" as "backup is good" | Periodically restore-test the dump into a scratch DB, not just verify the upload completed |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|-----------------|
| QEMU cross-build for arm64 image | CI build time far exceeds a native build; occasional inexplicable build/runtime crashes | Build natively on arm64 (runner or the CAX31 host itself) | First cross-platform CI build attempt (Phase 0) |
| IVFFlat index built before full catalog seed | Search results look poor/random despite a correct embedding pipeline | Use HNSW, or always rebuild IVFFlat after full seed | As soon as real search queries run against the seeded catalog (Phase 2) |
| Oban concurrency vs Postgres `max_connections` | Web requests fail during job bursts; pool checkout timeouts | Size Oban concurrency + Ecto pool together against `max_connections` with headroom | First bulk async job (e.g., full-catalog re-embedding) on the single CAX31 Postgres |
| FP16 embedding model on ARM CPU | Embedding latency higher than expected despite "faster" quantization | Prefer FP32/INT8 over FP16 for ONNX models on ARM | Immediately, once real latency is measured on the CAX31 during the Phase 2 spike |
| Default `maintenance_work_mem` for vector index build | Index build takes much longer than row count would suggest; disk-spill NOTICE in logs | Raise `maintenance_work_mem` for the migration session before `CREATE INDEX` | First pgvector index-creation migration (Phase 2) |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Plaintext secrets committed to `.kamal/secrets` | Credential leak via git history, laptop compromise, or CI log exposure | Gitignore the file; source values via env-var/command substitution from CI secrets, never literals |
| Postgres accessory port bound to `0.0.0.0` | Database directly reachable from the internet, bypassing UFW (Docker's iptables NAT rules bypass UFW's filter table) | Bind accessory ports to `127.0.0.1` explicitly in `deploy.yml` |
| Over-broad secret exposure to roles/accessories | A role/accessory gets access to secrets it doesn't need (e.g., LLM API key visible to a Postgres accessory) | Explicitly scope which secrets each role/accessory receives in Kamal config, least-privilege by default |
| No restore testing for nightly backups | Backups exist but are unusable in an actual incident (permission gaps, version mismatch) | Periodic (e.g., monthly) restore drill into a scratch database, not just "dump succeeded" |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-------------------|
| LLM query-parsing failure blocks search entirely | User gets an error or blank result for a valid query during a rate-limit window | Fall back to embedding-only/keyword search when LLM parsing fails or times out, never a hard failure |
| Slow first-ever embedding-model warmup surfaced to the user | First user after a deploy experiences a slow/failed request while the model loads | Warm the model asynchronously at boot (before health check passes) or lazily on first background job, never inline with a user request |
| Deploy-time downtime during migrations users can feel | A LiveView user mid-session gets disconnected/errors during a deploy | Verify true zero-downtime behavior end-to-end (health check + migration gating) before Phase 0 is considered "done," not just "the deploy command succeeded" |

## "Looks Done But Isn't" Checklist

- [ ] **arm64 Docker build:** Often only tested via QEMU cross-build locally on an amd64 dev
      machine — verify it also builds and *runs* correctly on native arm64 (the actual CAX31 or an
      equivalent native arm64 CI runner), not just that `docker buildx build --platform linux/arm64`
      exits 0.
- [ ] **Migration-on-deploy:** Often demoed with a no-op or additive migration — verify with a
      migration that would actually break the *previous* release's queries if run naively (to prove
      ordering/backward-compat safety), and confirm it re-runs correctly and safely on a second
      deploy with no pending migrations.
- [ ] **Zero-downtime deploy:** Often "works" in the sense that `kamal deploy` exits 0 — verify by
      hitting the live site in a loop during an actual deploy and confirming zero failed requests,
      not just checking the command's exit code.
- [ ] **Secrets handling:** Often "looks secure" because `.kamal/secrets` is gitignored locally —
      verify by checking `git log -p` across the whole repo history (not just current state) for any
      commit that ever included real values, and confirm CI doesn't echo secret values into logs.
- [ ] **pgvector search quality:** Often tested against a small hand-picked subset of games during
      development — verify against the full ~400-game seeded catalog with the index built in
      production-representative order (seed first, index after).
- [ ] **Nightly backups:** Often verified only by "the cron job ran and the file appeared in R2" —
      verify by actually restoring a downloaded dump into a scratch Postgres instance and confirming
      row counts/schema match.
- [ ] **LLM fallback behavior:** Often only tested with the API working normally — verify by
      simulating a 429/timeout response and confirming the search flow degrades gracefully instead of
      erroring out for the user.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|----------------|------------------|
| Bad IVFFlat centroids from early index build | LOW | `DROP INDEX`, `CREATE INDEX` again after full data is loaded (or switch to HNSW) |
| Secrets ever committed in plaintext | MEDIUM | Rotate every exposed credential immediately (API keys, `SECRET_KEY_BASE`, DB password); history-scrub is optional/secondary since rotation neutralizes the leak |
| Migration ran out of order / partially applied during a bad deploy | MEDIUM-HIGH | Restore from the most recent tested nightly backup if data corruption occurred; otherwise write a corrective migration rather than manually patching prod schema by hand |
| Oban/Postgres pool exhaustion incident | LOW | Lower Oban queue concurrency immediately (config change, redeploy), then right-size pool/concurrency against measured `max_connections` headroom |
| Untested backup turns out to be broken when needed | HIGH | If discovered before an incident: fix and re-test immediately. If discovered during an incident: this is why restore drills matter — there may be no recovery beyond whatever partial data can be salvaged |
| Free-tier LLM quota cut / rate-limited hard | LOW (if fallback exists) / HIGH (if not) | With graceful fallback already built: no user-facing incident, just degraded feature quality until quota resets or a paid tier is added. Without it: ship the fallback reactively, same as Pitfall 9's prevention |

| Pitfall | Prevention Phase | Verification |
|---------|-------------------|----------------|

| Plaintext/under-scoped secrets | Phase 0 | `.kamal/secrets` gitignored with no real values in git history; each role/accessory has only the secrets it needs |
| Kamal health check misconfigured | Phase 0 (baseline), revisit Phase 2 (model-load startup time) | Deploy-time request-loop test shows zero downtime; readiness timing re-verified after Phase 2 adds startup work |

| pgvector index build memory defaults | Phase 2 | No disk-spill NOTICE in index-build migration logs |
| Oban concurrency starving Ecto pool | Phase 2 | Load test (e.g., full-catalog re-embedding job) shows no web-request pool timeouts |
