## Summary

This phase does two things: (1) `ImagePipeline.process_gallery/3` is gutted to always return
`{:ok, []}` (removing the version-image traversal that surfaced other-edition/other-language box
covers as fake gallery photos) plus a new `GalleryBackfill` offline job/mix task to null out stale
`gallery_urls` on already-seeded rows, and (2) a shared `.pk-poster-img` CSS class (`object-fit:
contain`) replaces per-template `object-cover` on the resting card, hover/sheet preview, and detail
cover, fixing a crop-to-fill letterbox bug.

I traced the actual diff (`git diff f86385cf...^..HEAD`) rather than trusting the full file
contents, since most of `app.css` and `game_preview.ex`/`show.ex` predate this phase. The changed
surface is small and the removal of the gallery-traversal code path is clean — no dangling callers,
no orphaned helper functions, and `mix catalog.seed`'s existing `{:ok, gallery_urls} =
ImagePipeline.process_gallery(...)` call site still pattern-matches correctly against the new
always-`{:ok, []}` return. The CSS/template change is verified by an unusually thorough
comment-stripped-source contract test (`poster_treatment_test.exs`) that guards against exactly the
kind of copy-paste drift this repo has hit before.

The one real correctness gap is in `GalleryBackfill`: it discards the result of `Repo.update/1`
and unconditionally reports the row as `updated`, so a partial failure (constraint violation, DB
hiccup) is silently misreported as a success. This exact pattern already exists in the sibling
`StatsEnricher.apply_artists_backfill/3`, so it's a pre-existing convention being replicated rather
than a novel bug — but it's still worth fixing, especially since this job's whole purpose is a
one-shot data-correction sweep whose summary output is the only feedback an operator gets.

No critical/security issues found in the reviewed diff.

## Warnings

### WR-01: `GalleryBackfill` discards the `Repo.update/1` result and always reports the row as updated

**File:** `lib/pukllay_club/catalog/seed/gallery_backfill.ex:55-63`
**Issue:** `apply_gallery_backfill/3` calls `Repo.update()` inside an `if !dry_run?` block but never
inspects the return value:

```elixir
defp apply_gallery_backfill(game, dry_run?, acc) do
  if !dry_run? do
    game
    |> Ecto.Changeset.cast(%{gallery_urls: []}, [:gallery_urls])
    |> Repo.update()
  end

  %{acc | scanned: acc.scanned + 1, updated: acc.updated + 1}
end
```

`updated` is incremented unconditionally, regardless of whether the write actually succeeded. If
`Repo.update/1` returns `{:error, changeset}` (or raises `Ecto.StaleEntryError` in a future schema
change that adds optimistic locking) for any row, the mix task's final summary
(`"Gallery backfill complete: N/N scanned"`) will still report 100% success even though one or more
rows were never corrected — and because a corrected row is no longer selected as a candidate on the
next run, a silently-failed row would need to be found by manual inspection, not by re-running the
job. This is a one-shot data-correction job (D-07); its printed summary is the only audit trail an
operator has.

Note: this exact discard-the-result pattern already exists in the sibling
`PukllayClub.Catalog.Seed.StatsEnricher.apply_artists_backfill/3` (`lib/pukllay_club/catalog/seed/stats_enricher.ex:157-173`),
which this module's own moduledoc explicitly models itself on — so this is a repo-wide convention
being replicated, not a one-off oversight. Worth fixing in both places, or at minimum in this new
file.

**Fix:**
```elixir
defp apply_gallery_backfill(game, dry_run?, acc) do
  acc = %{acc | scanned: acc.scanned + 1}

  if dry_run? do
    %{acc | updated: acc.updated + 1}
  else
    case game |> Ecto.Changeset.cast(%{gallery_urls: []}, [:gallery_urls]) |> Repo.update() do
      {:ok, _game} -> %{acc | updated: acc.updated + 1}
      {:error, _changeset} -> acc
    end
  end
end
```

### WR-02: No test covers a failed `Repo.update/1` in the gallery backfill path

**File:** `test/pukllay_club/catalog/seed/gallery_backfill_test.exs`
**Issue:** Every test in this file exercises the happy path (successful cast + update). There is no
test forcing an update failure (e.g. stubbing `Repo` or violating a constraint) to pin the expected
`scanned`/`updated` counts when a write does not succeed. Given WR-01 above, this gap is exactly why
the discarded-result bug wasn't caught by the test suite — the summary counters are only ever
asserted against all-successful runs.
**Fix:** Once WR-01 is fixed, add a test that forces `Repo.update/1` to fail (e.g. a row that
violates a DB-level constraint, or a `Mox`/manual stub) and asserts `updated` does not count the
failed row while `scanned` still does.

## Info

### IN-01: Dry-run `updated` count means "would update", not "did update" — easy to misread from the CLI output alone

**File:** `lib/pukllay_club/catalog/seed/gallery_backfill.ex:41-63`, `lib/mix/tasks/catalog.backfill_gallery.ex:30-32`
**Issue:** In dry-run mode, `updated` is incremented for every scanned candidate even though nothing
is written — this is intentional and tested (`gallery_backfill_test.exs:45-55`), and it mirrors
`StatsEnricher`'s existing convention, so it's not a bug. But the printed line
`"[DRY RUN] Gallery backfill complete: N/N scanned."` reads identically in shape to a real run's
`"Gallery backfill complete: N/N scanned."` — the `[DRY RUN]` prefix is the only signal that no
writes occurred. Combined with WR-01, a real run's summary can no longer be trusted to mean "N rows
were actually written" even without the `[DRY RUN]` prefix. Low severity since the prefix exists and
the behavior is deliberate and tested, but worth a one-line mention in the moduledoc (which already
documents scanned/updated semantics) clarifying that "updated" in dry-run mode means "eligible", not
"written".
**Fix:** Optional — add a short clause to the `@doc` for `run/1` clarifying: "In dry-run mode,
`:updated` counts rows that *would* be written, not rows actually written."

### IN-02: `mix catalog.backfill_gallery` silently swallows invalid CLI flags

**File:** `lib/mix/tasks/catalog.backfill_gallery.ex:23`
**Issue:** `{opts, _rest, _invalid} = OptionParser.parse(args, strict: [dry_run: :boolean])` discards
`_invalid` — e.g. `mix catalog.backfill_gallery --dry-run=maybe` or a typo'd flag like `--dryrun`
will not error, it will just silently run a real (non-dry-run) backfill against production data.
This matches the pre-existing convention in every other mix task in this directory
(`catalog.seed.ex`, `catalog.enrich_bgg_stats.ex`, `catalog.backfill_artists.ex`,
`catalog.translate_descriptions.ex` all discard `_invalid` identically), so it is not a regression
introduced by this phase — flagging for awareness only, since this task's failure mode (a typo'd
`--dry-run` silently becoming a real write) is more consequential than most of the others given it
mutates every matching row in the catalog.
**Fix (optional, repo-wide, out of scope for this phase):**
```elixir
{opts, _rest, invalid} = OptionParser.parse(args, strict: [dry_run: :boolean])

if invalid != [] do
  Mix.raise("Unrecognized option(s): #{inspect(invalid)}")
end
```
