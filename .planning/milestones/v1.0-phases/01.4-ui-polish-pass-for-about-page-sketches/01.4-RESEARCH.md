## Summary

This phase is a **verified revision pass**, not new construction — every one of the 5 sketch
findings maps onto a small, precisely locatable change in `lib/pukllay_club_web/live/about_live.ex`
and `assets/css/app.css`. I read the live source for every file CONTEXT.md named and can confirm
the CSS line numbers, the shipped `.AboutCarousel` hook's existing autoplay/pause logic, and the
`social_links/1`/`sumate_cta/1` reuse targets are all real and exactly as described. I also found
five things CONTEXT.md's `<code_context>` section did not fully resolve, each of which changes how
the plan should be scoped:

1. **The header is not "hidden by default" today — it's the same always-visible sticky header
   every other page uses**, complete with its own `.CatalogNav`-driven `is-scrolled` tint and an
   *always-rendered* isologo `<img>` pair inside it (`header_inner/1` calls `<.brand_logo />`
   unconditionally). 045's "hidden at rest, morphs a floating mark into the header's mark" effect
   therefore requires **suppressing the header's own always-present isologo** at rest and revealing
   it (or crossfading it with the floating mark) only at dock — not just adding a new floating
   `<img>` into an otherwise-empty header slot the way the sketch's simplified `.fake-header` did.
2. **A page-owned hook reaching across the DOM into `#app-header` is an already-established pattern
   in this codebase** (`.CatalogNav`'s own scroll-spy does `document.getElementById("app-subnav")`
   outside its own root) — this de-risks the D-10 "page-owned, don't touch the shared header"
   constraint; the new About-only hook can safely read/toggle classes on `#app-header` from
   outside without violating D-10, as long as it doesn't add new phx-hook wiring to `header_inner/1`
   itself.
3. **049's "missing `justify-content: center`" bug does not reproduce in the shipped code.** The
   sketch's bug lived in its own hand-rolled `.closing-cta` CSS; the real `Layouts.sumate_cta/1`
   button uses daisyUI's `.btn` class, whose compiled CSS already sets `justify-content: center`
   (confirmed by reading `deps/daisyui/packages/bundle/daisyui.js`), and no unlayered `.pk-*` rule
   in `app.css` overrides it. A task that blindly re-applies the sketch's CSS delta to
   `.pk-about-cta-bar` would be a no-op (that div isn't even a flex container).
4. **`social_links/1` is `defp` (private)** in `Layouts` — `AboutLive` cannot call it as written.
   It must be promoted to `def` (and given an optional icon-subset attr, since Contacto only needs
   WhatsApp + Instagram, not the footer's four) before D-04/048's reuse instruction is achievable.
5. **`explicacion.tiff` is a Lightroom-exported Adobe DNG, not a flat TIFF** — its primary IFD is a
   256×171 thumbnail; the real image lives in one of six SubIFDs, several of which need raw-aware
   tooling this sandbox does not have installed (no ImageMagick/`dcraw`/`exiftool`/`rawpy`). I
   extracted and decoded a usable 1024×683 embedded JPEG preview directly from the file with a
   ~15-line Python/Pillow script (verified working, code below) — this is the pragmatic conversion
   path, not a Mix task or CLI tool that doesn't exist here.

**Primary recommendation:** Treat this as five small, independent, verifiable changes (isologo
morph, photo-rail content+autoplay-confirm, copy fix, band-width+Contacto rebuild, closing-CTA
de-dup) each landing in `about_live.ex`/`app.css`/`club_links.ex` — plan one wave of small tasks per
sketch rather than one large task, since the five areas don't share files except `app.css` (which
every wave touches in a disjoint line range) and `about_live_test.exs` (which every wave extends).

### Pattern 1: Cross-root DOM access from a page-owned colocated hook (precedent, not new risk)
**What:** A colocated hook mounted on one element reaching outside its own root (`this.el`) via
`document.getElementById(...)` to read/toggle another element's classes.
**When to use:** The isologo-morph hook needs to read `#app-header`'s brand-slot rect and toggle its
own isologo `<img>` visibility — `#app-header` isn't inside AboutLive's own hook root.
**Example (already shipped, confirmed by reading the file):**
```javascript
// Source: lib/pukllay_club_web/components/layouts.ex, .CatalogNav hook, ~line 295
// (existing precedent for a hook reaching outside its own `this.el`)
this.spyRoots = [this.el, document.getElementById("app-subnav")].filter(Boolean)
```
The new About-only hook should follow the identical shape: `document.getElementById("app-header")`,
guarded the same way (`if (!header) return` — never throw if the element is ever absent), matching
this codebase's established try/catch-per-block convention inside `.CatalogNav`'s own `mounted()`.

### Pattern 2: Theme-aware asset swap via the existing `dark:` custom variant, not JS
**What:** `brand_logo/1` already renders BOTH `isologo-light.png` (`class="dark:hidden"`) and
`isologo-dark.png` (`class="hidden dark:block"`) unconditionally, letting CSS pick the visible one.
**Verified:** `assets/css/app.css:215` — `@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *));`
— this is an attribute selector on `[data-theme]`, **not** a `prefers-color-scheme` media query.
**When to use:** The floating morph-mark should render the identical light/dark `<img>` pair with
the identical `dark:hidden`/`hidden dark:block` classes, rather than reading `data-theme` in JS and
swapping `src` — reuses the existing CSS-only mechanism, zero new JS theme logic.

### Pattern 3: Reuse `social_links/1` for Contacto (requires a small, real code change first)
**What:** `social_links/1` in `layouts.ex` (~line 1056) is `defp` — private. `AboutLive` genuinely
cannot call it today.
**Fix:** Promote to `def`, add an optional attr (e.g. `icons`, a list of atoms defaulting to

- **Reproducing the sketch's `.closing-cta { display: inline-flex; align-items: center }` bug fix

## Common Pitfalls

### Pitfall 1: The header's own isologo is already always-rendered — plan for suppressing it, not just adding a floating mark into empty space
**What goes wrong:** Implementing 045 by only adding the floating `#morph-mark` (as the sketch's
simplified `.fake-header` did, which has NO image in its own brand-slot) produces two visible
isologos once the floating mark starts fading in — the header's permanent one (rendered by
`brand_logo/1` inside `#app-header`, unconditionally) plus the new floating one.
**Why it happens:** CONTEXT.md's `<code_context>` section describes the isologo assets and the
theme-variant mechanism but doesn't call out that `header_inner/1` already renders `<.brand_logo />`
on every page including About.
**How to avoid:** The page-owned hook must set the header's own isologo `<img>` pair to `opacity: 0`
(or similar) at rest, and reveal it (or crossfade) exactly at the dock moment.
**Warning signs:** A visible header-brand isologo at page load, before the floating mark has entered
— it shouldn't be there yet per 045 ("hidden at rest").

### Pitfall 2: `.pk-*` rules are unlayered — they always beat Tailwind/daisyUI utilities on the same property
**What goes wrong:** A new `.pk-about-*` rule for the isologo-morph or Contacto card that
accidentally sets a property (`display`, `justify-content`, `position`) also set by a Tailwind
utility class on the same element silently wins, with no specificity warning.
**Why it happens:** `assets/css/app.css:12-35` documents this explicitly — every `.pk-*` rule from
that point on is written with no `@layer` wrapper, and CSS cascade-layer rules make unlayered CSS
always beat layered (Tailwind/daisyUI) rules regardless of source order or specificity. This is a
**previously-hit, documented bug in this exact codebase** (`.pk-poster-col`'s `position: static`
silently defeated a `relative` utility — G-01.2-5).
**How to avoid:** When a new `.pk-about-*` rule and a Tailwind utility on the same element both want
to set one property, delete the utility from the markup and keep the property in the `.pk-*` rule
(the codebase's own stated resolution rule) — never assume the utility "wins" because it's applied
later in the class list.
**Warning signs:** A Tailwind utility class present in the rendered HTML that visibly does nothing.

### Pitfall 3: `explicacion.tiff` is an Adobe DNG, not a flat TIFF — naive tools will silently return a 256×171 thumbnail
**What goes wrong:** Opening the file with a naive TIFF loader (`sips`, basic `PIL.Image.open()`,
or any tool that only reads IFD0) returns a 256×171 image — unusable at any real display size.
**Why it happens:** Verified by reading the file's own IFD tags: it's a Lightroom-exported DNG
(`tag 305 = "Adobe Photoshop Lightroom Classic 14.0.1"`, `tag 50706 DNGVersion` present). IFD0 is
a thumbnail; the real image lives in one of 6 SubIFDs referenced by `tag 330`. Manual parsing found:
```
SubIFD@115814: 5344×3516  compression=7 (old-JPEG)   photometric=32803 (raw CFA — needs demosaic)
SubIFD@118624: 5202×3465  compression=52546 (DNG lossy-JPEG) photometric=34892 (LinearRaw)
SubIFD@119828: 1024×683   compression=7 (old-JPEG)   photometric=6 (YCbCr) <- directly decodable
SubIFD@120236: 2048×1365  compression=52546 (DNG lossy-JPEG)
SubIFD@120966: 512×341    compression=52546 (DNG lossy-JPEG)
SubIFD@121520: 256×171    compression=52546 (DNG lossy-JPEG) — same as IFD0, smallest thumbnail
```
Only the `compression=7`/`photometric=6` SubIFD (1024×683) is a **standard, directly-decodable JPEG
strip** — I confirmed this by extracting its raw bytes via `StripOffsets`/`StripByteCounts` and
opening them with `PIL.Image.open(io.BytesIO(...))`, which succeeded (`Decoded: JPEG (1024, 683)
RGB`). The larger SubIFDs use DNG-specific "lossy JPEG" (compression=52546) or raw CFA data — neither
is decodable by Pillow or any tool available in this sandbox.
**How to avoid:** Use the verified 1024×683 extraction path below, or (simpler, if the developer has
Lightroom/any DNG-aware viewer on their own machine) manually re-export the file as a normal
JPEG/PNG — do not attempt to write Mix-task/Elixir code to decode the DNG SubIFDs; no Elixir library
for this exists and it would be substantial unplanned scope.
**Warning signs:** A "converted" `explicacion.tiff` that looks pixelated/blurry when displayed at
rail size — it's the 256×171 thumbnail, not the SubIFD preview.

### Pitfall 4: The floating morph-mark's width/height must not be forced equal
**What goes wrong:** Copying the sketch's `place(rect, animate)` function verbatim (`mark.style.width
= rect.size + 'px'; mark.style.height = rect.size + 'px'`) squishes the real isologo, which is not
square.
**Why it happens:** Verified via Pillow: `isologo-light.png` is 939×1034px, `isologo-dark.png` is
939×1035px (ratio ≈ 0.908:1) — the sketch's mockup used a placeholder/generic mark and never
surfaced this since it never checked the real asset's aspect ratio.
**How to avoid:** Either derive `height` from `width * (1034/939)` (or the reverse) in the crossing-
point math, or size a square bounding box and add `object-fit: contain` to the `<img>` so the CSS
box can be square while the rendered pixels keep their real ratio.
**Warning signs:** The morph-mark looking visibly squished/stretched at any point during the
animation, especially near the header dock size (32px per the sketch, very noticeable at that size).

### Pitfall 5: Two of the five rail photos are portrait — a single fixed crop ratio will lose real subject content
**What goes wrong:** D-08 requires one fixed `object-fit: cover` aspect ratio for every slide,
matching the shipped rail's existing `3/2` ratio (`.pk-about-slide-ph`, `app.css:2638`, verified).
`comunidad.png` (648×864, 3:4) and `juego.jpg` (4284×5712 → target 1200×1600, still 3:4) are both
portrait — cropped into a 3:2 landscape frame, roughly a third of each photo's height is cut, with
`object-position: 50% 50%` (the CSS default) potentially cropping through faces/the board depending
on where the subject sits in each source photo.
**Why it happens:** D-08 correctly fixes the *technique* project-wide but the specific photos
weren't available when that decision was made against the *existing* 3:2 ratio.

### Extracting a usable preview from `explicacion.tiff`'s DNG SubIFD (verified working this session)
```python
# Source: verified directly against /home/apedraza/Downloads/explicacion.tiff this session.
# Manually parses the TIFF IFD chain (no rawpy/exiftool/dcraw available in this sandbox) to find
# the one SubIFD using standard baseline JPEG compression (compression=7, photometric=6/YCbCr),
# which Pillow CAN decode directly — the other 5 SubIFDs use DNG-specific "lossy JPEG"
# (compression=52546) or raw CFA sensor data (photometric=32803), neither of which Pillow supports.
import struct, io
from PIL import Image

path = "explicacion.tiff"
with open(path, "rb") as f:
    data = f.read()
endian = "<" if data[0:2] == b"II" else ">"

def read_ifd(offset):
    n = struct.unpack_from(endian + "H", data, offset)[0]
    entries = {}
    for i in range(n):
        eo = offset + 2 + i * 12
        tag, typ, count = struct.unpack_from(endian + "HHI", data, eo)
        size = {1:1,2:1,3:2,4:4,5:8}.get(typ, 1) * count
        vo = eo + 8
        raw = data[vo:vo+size] if size <= 4 else data[struct.unpack_from(endian+"I", data, vo)[0]:][:size]
        entries[tag] = (typ, count, raw)
    return entries

# 119828 is the verified offset (from tag 330's SubIFD list) of the 1024x683,
# compression=7/photometric=6 entry — this is the ONE directly-decodable preview.
e = read_ifd(119828)
so_typ, so_count, so_raw = e[273]   # StripOffsets
sbc_typ, sbc_count, sbc_raw = e[279]  # StripByteCounts
offset = struct.unpack_from(endian + "I", so_raw)[0]
count = struct.unpack_from(endian + "I", sbc_raw)[0]
jpeg_bytes = data[offset:offset+count]

im = Image.open(io.BytesIO(jpeg_bytes))  # -> JPEG, (1024, 683), RGB — verified this session
im.save("explicacion.jpg", "JPEG", quality=88)
```

### Resizing/recompressing the 5 real photos before committing (verified working this session)
```python
# Source: verified against the actual 5 files in /home/apedraza/Downloads/ this session.
# Results measured: comunidad.png 1.27MB->116KB, Ludoteca.png 3.22MB->343KB,
# juego.jpg 3.38MB(4284x5712)->293KB(1200x1600), festejo cumple.JPG 3.54MB(5712x4284)->296KB(1600x1200).
from PIL import Image

TARGET_LONG_EDGE = 1600  # slide renders at flex: 0 0 min(84vw, 720px) — 1600px covers ~2.2x density

def prepare(src_path, dst_path, quality=82):
    im = Image.open(src_path).convert("RGB")
    w, h = im.size
    long_edge = max(w, h)
    if long_edge > TARGET_LONG_EDGE:
        scale = TARGET_LONG_EDGE / long_edge
        im = im.resize((round(w * scale), round(h * scale)), Image.LANCZOS)
    im.save(dst_path, "JPEG", quality=quality, optimize=True)
```
