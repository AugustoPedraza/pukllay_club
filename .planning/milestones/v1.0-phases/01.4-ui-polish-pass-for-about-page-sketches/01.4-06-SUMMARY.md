# Phase 01.4 Plan 06: Isologo Morph Gap Closure (G-01.4-1) Summary

**Moved the About header's hidden-at-rest state from a client-applied CSS-transitioned class to a server-rendered `body:has()` guard, gave the isologo mark its own spacing tier, and replaced the layout-property CSS transition driving the scroll-morph with a hook-owned per-frame `transform` interpolation — closing all three independently-diagnosed defects (blink, cramped spacing, non-fluid motion) behind G-01.4-1, plus a live-verified no-JS regression found and fixed along the way.**

## Accomplishments

- **S1 (blink) fixed:** `#about-hero` now server-renders a bare `data-morph-armed` marker; `assets/css/app.css` hides `#app-header` via `body:has(#about-hero[data-morph-armed]) #app-header { visibility: hidden; opacity: 0; transition: none; }` — matched before a single line of JS runs, confirmed against the dead (pre-connect) render via both an ExUnit test and a live curl. The old client-applied `pk-header-about-morph` class and its 280ms fade-out transition are fully retired (no selector in the stylesheet references it).
- **S2 (spacing) fixed:** `[data-morph-anchor]` gained `mb-8`, giving the 200px isologo its own spacing tier instead of sharing the hero's flat 12px `space-y-3` gap with every other element.
- **S3 (non-fluid motion) fixed:** the `.AboutHeaderMorph` hook was rewritten to drive the mark's position/size via a single interpolated `transform` written per animation frame — duration from `--duration-slow`, curve from a hand-verified bisected cubic-bezier matching `--ease-standard`'s exact control points — instead of a CSS transition on `top`/`left`/`width`/`height`. Both the anchor rect and the dock rect are re-read inside the frame callback every time, so a scroll mid-move retargets continuously; the undock now reverses cleanly instead of surviving one frame and hard-snapping the rest.
- **A no-JS escape hatch was added, then found broken via live CDP verification and corrected within the same plan** (see Deviations) — the plan's literal `<noscript><style>` instruction turned out to be exempted from JS-conditional behavior by the HTML spec itself, which would have permanently defeated S1 in every browser regardless of scripting.
- Verified end-to-end via a scratchpad-only CDP driver script at 375px and 1280px: header hidden at rest, 1:1 scroll tracking, correct dock-time transform values (scale ≈0.198, matching the header's real 36px brand slot), clean reversal on scroll-up, and — critically — the no-JS path independently confirmed against the exact same served markup with scripting disabled.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's literal `<noscript><style>` no-JS escape hatch does not work — replaced with a `<noscript><div>` marker plus explicit hook-side removal**
- **Found during:** Task 2's own live CDP verification pass (re-checking Task 1's no-JS hatch before trusting the full plan closed)
- **Issue:** Per the HTML parsing spec, `<noscript>` redirects child-element processing to the SAME restricted allowlist used in `<head>` (`base`/`link`/`meta`/`noframes`/`style`), **regardless of whether scripting is enabled**. A `<style>` placed directly inside `<noscript>` is therefore exempted from the "only when scripting is disabled" behavior and becomes an ALWAYS-ACTIVE stylesheet — confirmed live via CDP (`document.styleSheets` grew by one, and `CSS.getMatchedStylesForNode` showed the override rule matched and winning against a real, connected `#app-header`, with app.js definitively running). Left as originally written, this would have permanently defeated the entire S1 fix, in every browser, JS or not — the header would never hide.
- **Fix (two parts):**
  1. Replaced the inline `<style>` with a bare `<div id="pk-no-js-marker" data-no-js>` (an element NOT on the `<noscript>` allowlist). Per spec this IS correctly discarded by the HTML parser while scripting is enabled — confirmed against the exact same markup served as a static file, isolated from LiveView (`getElementById` returns `null` with JS on, non-null with JS off).
  2. That parser-level discard alone was then found to **not survive LiveView's own connect-time DOM reconciliation** — on the real running page (JS enabled, LiveSocket connected), the marker reappeared in the DOM despite the isolated static-file test discarding it correctly. Fixed by adding an explicit `document.getElementById("pk-no-js-marker")?.remove()` as the first action inside `.AboutHeaderMorph`'s `mounted()`, once the guard clause confirms the hook can actually run — this fires strictly after any connect-time reconciliation has settled, and is what actually ties the override to "JS is running" end to end on this specific app.
- **Files modified:** `lib/pukllay_club_web/live/about_live.ex`, `assets/css/app.css`
- **Verification:** Live CDP re-check with a real connected LiveSocket: `#pk-no-js-marker` absent and `#app-header` visibility `"hidden"` with scripting enabled; marker present and header visibility `"visible"` with `Emulation.setScriptExecutionDisabled(true)`.
- **Committed in:** `2fce58f` (part of the Task 2 commit — found during Task 2's own verification, before Task 2 was committed, so folded in rather than issued as a separate correction commit).
