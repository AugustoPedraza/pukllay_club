## Accomplishments

- **(A) CSS — chip sizing fixed.** `.pk-about-map-label` no longer pins both `left`/`right`; it now shrink-wraps to its own text, bounded by a `max-width` derived from a new single-source `--pk-map-label-inset` custom property declared on `.pk-about-map-thumb`. `border-radius` changed from the bare `var(--radius-box)` token to `max(0px, calc(var(--radius-box) - var(--pk-map-label-inset)))`, closing the non-concentric-corner defect (outer 8px / inset 8px / inner 8px → correctly inner 0px).
- **(B) DATA — screenshot recaptured.** `priv/static/images/about-maps-thumb.jpg` was replaced with a tighter-zoom capture, per the human's own confirmation in Task 2: the club's pin is dominant, Google's attribution wordmark is in frame, and the pin label's truncation is accepted as inherent to the business's registered name (confirmed unfixable even at max zoom), with the full venue name already legible in three surrounding text locations.
- **(C) ENVIRONMENT — mechanically wired, not content-resolved.** A light/dark `<img>` theme-variant pair now renders inside `.pk-about-map-thumb`, mirroring `brand_logo/1`'s isologo pattern exactly (`block dark:hidden` first, `hidden dark:block` second, both `loading="lazy" decoding="async"`). `.pk-about-map-thumb img`'s `display: block` was removed to prevent the identical Rule-1 cascade defect plan 01.4-05 had to undo on the isologo's own theme variants. **The dark asset is currently a byte-identical copy of the light asset** — a genuine dark-mode Maps capture was not achievable this session (see Decisions). The mechanism is proven correct and ready to receive a real dark capture without further code changes.
- Extended `test/pukllay_club_web/live/about_live_test.exs` with 5 new tests: the chip's shrink-wrap/max-width/border-radius CSS-facts gate, the no-`display` CSS-facts gate on `.pk-about-map-thumb img`, a rendered-output gate on both theme variants' src/class values and document order, and a `File.exists?/1` presence gate on both asset paths. All 34 tests in the "Contacto card map thumbnail" describe block pass; full suite is 826/826.

## Decisions Made

- **Pin-label truncation accepted, not a defect.** The human confirmed directly in Google Maps that "CLUB DE EMPRENDEDORES…" truncates on the club's pin even at maximum zoom — this is inherent to how Google renders this business's long registered name, not a recapture-fixable defect. Task 3's markup already carries the full venue name in the `alt` text and both caption spans, and the intro paragraph above the Contacto card also names it in full, so the caption — not the pin — is the mechanism that satisfies the "name reads in full" requirement.
- **Real dark-mode Maps capture deferred, light asset shipped in both slots.** Three real avenues were exhausted before falling back to this interim measure: (a) no in-app Google Maps Settings → Appearance → Dark toggle was found in the web UI, (b) Chrome's `chrome://flags/#enable-force-dark` only recolors DOM overlay text — canvas/WebGL map tiles stayed light, confirmed by screenshot, (c) OS-level (GNOME) dark mode plus a hard reload left tiles rendered light. No smartphone was available to test the Maps mobile app's own dark theme. `about-maps-thumb-dark.jpg` therefore ships as a byte-identical copy of `about-maps-thumb.jpg` (both 1656×804 JPEG, quality 85, from the same source) as an interim measure — the img-swap mechanism (CSS + markup) is fully correct and ready for a future real dark asset swap; only the pixel content is a placeholder.
- **Root cause (C) — theme response — is therefore NOT resolved, only mechanically prepared.** The debug session's dark-theme luminance/contrast finding (10.1x ratio against the dark card) is unchanged in practice: both images are currently identical, so dark theme will still show the light-toned capture. This is a deliberate, tracked deviation from the plan's original objective, not a silently-dropped requirement — see Known Stubs.
