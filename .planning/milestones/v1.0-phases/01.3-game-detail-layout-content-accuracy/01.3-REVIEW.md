## Summary

This is a re-review scoped only to the delta introduced by gap-closure plan 01.3-12 (commits
`370d376` fix + `74b6371` test), which closed UAT gap G-01.3-6 (the collapsed description-toggle
chevron rendering on its own row below the clamped paragraph instead of trailing its last line).
The delta touches four CSS rules in the `.pk-desc*` family in `assets/css/app.css`
(`.pk-desc-shell` gains `position: relative`; a new `.pk-desc-shell:not(.is-expanded)` rule adds
`min-height: 2.75rem`; `.pk-desc.is-clamped` gains `padding-right: 2.75rem`; and a new
`.pk-desc-shell:not(.is-expanded) .pk-desc-toggle` rule takes the collapsed toggle out of flow via
`position: absolute`) and adds a new `describe "collapsed toggle geometry (01.3-12)"` block to
`catalog_show_test.exs` with five derived/computed-contract tests.

I traced the geometry math by hand against the actual file contents (not just the diff) and ran
`mix test test/pukllay_club_web/live/catalog_show_test.exs` — all 181 tests pass, and the specific
numbers the new tests assert (44px reserved gutter, 24px last-line band, 4px top/bottom margin
around the 16px icon in that band) check out for the **3-line, fully clamped** case the tests
exercise. The fix is well-reasoned and well-documented for that case.

However, the fix has a real, provable gap for the **short, non-clamped description** case (any
description rendering as a single line — under ~44px tall — in the reading column at a given
viewport width), which the new test suite does not cover at all (every geometry test either
inspects only CSS source text, or uses a `render_click`/DOM-structure assertion against a fixture
description that is never checked for its actual rendered line count). See CR-01 below — this is
not a hypothetical, it follows directly from the declared values in the rule bodies I read.

## Critical Issues

### CR-01: Collapsed toggle detaches from text (visible gap) for single-line descriptions

**File:** `assets/css/app.css:3124-3126` (`.pk-desc-shell:not(.is-expanded)`) and
`assets/css/app.css:3256-3262` (`.pk-desc-shell:not(.is-expanded) .pk-desc-toggle`)

**Issue:** The fix anchors the collapsed toggle to `.pk-desc-shell`'s own box (`bottom: 0; right:
0`), and the shell's height is `min-height: 2.75rem` (44px) or the paragraph's natural height,
whichever is greater — never less. There is no server-side truncation detection (confirmed in
`lib/pukllay_club_web/live/catalog_live/show.ex:546-566`): the toggle button renders unconditionally
whenever `@game.description` is present, regardless of whether the text actually needs 3 lines.

For any description that renders as **one line** (paragraph height ≈ 24px, since `line-height:
1.5` × 16px base = 24px per `.pk-desc`), the shell's `min-height: 2.75rem` (44px) forces the shell
20px taller than the text itself. Because `justify-content` on `.pk-desc-shell` defaults to
`flex-start`, the one-line paragraph sits at the top of that 44px box, and the absolutely
positioned toggle stays anchored to the *shell's* bottom edge (44px down), not the *text's* bottom
edge (24px down). The result: a ~20px empty gap opens up between the single line of visible text
and the chevron below it — the toggle no longer trails the text at all, which is the exact
regression this gap-closure round exists to prevent (it was previously in-flow via `align-self:
flex-end`, immediately below the text with no gap, before this commit introduced the absolute
overlay).

Any description of 2+ lines is unaffected (paragraph height ≥ 48px > 44px min-height, so shell
height tracks the paragraph exactly and the math the new tests assert holds) — this is narrowly
scoped to single-line-rendering descriptions, but nothing in `show.ex` prevents short descriptions
from existing in the catalog, and nothing in the new test suite exercises this width/line-count
dimension (every new geometry test either parses CSS source directly or uses the same short fixture
string `"Una descripción de prueba para el juego."` for DOM-shape assertions only, never checking
rendered line count or visual position).

**Fix:** The `min-height: 2.75rem` on the shell is doing double duty it cannot actually satisfy at
once: it must be tall enough to avoid the toggle overhanging content above the shell (its stated
purpose) *and* short enough to keep the toggle flush against short text (the goal this whole
gap-closure round exists for) — these are in tension for exactly 1-line text, and the current fix
picks the first at the expense of the second. Consider either:
- Detecting whether a description actually needs truncation (e.g., a rough character-count
  threshold, or measuring rendered height client-side) and only applying `is-clamped` / the
  collapsed-toggle affordance when it's actually needed — this also fixes the pre-existing,
  unrelated issue that a toggle renders even for descriptions that never overflow.
- Or, if the toggle must always render, publish the description's actual rendered height as a CSS
  custom property via a `ResizeObserver` (the same pattern this file already uses for
  `--pk-header-h`, see `.pk-shelf`'s `scroll-margin-top` comment) and anchor the toggle to that
  measured value instead of guessing a fixed floor.

```css
/* Option A (sketch): only clamp/show the toggle when the description is actually long enough
   to need it — computed once in the LiveView, not guessed in CSS. */
```

## Warnings

### WR-01: `family_span` extraction logic duplicated between two describe blocks

**File:** `test/pukllay_club_web/live/catalog_show_test.exs:881-895` and `:1126-1141`

**Issue:** The pre-existing "no rule in the .pk-desc* family declares float-based positioning"
test (01.3-10) and the new "no forbidden mechanism in the new rule, and the tripwire test still
covers it" test (01.3-12) each independently define the identical
`Regex.run(~r/^\.pk-desc-shell\s*\{.*?(?=\n\/\* Boundary between the primary reading block)/ms,
css_source())` extraction (same pattern, same flunk message, copy-pasted). This is exactly the
kind of drift risk this file's own commenting style elsewhere warns against — if the family span's
boundary marker comment is ever reworded, both copies need to be updated in lockstep, and nothing
enforces that.

**Fix:** Factor the extraction into a shared private helper (e.g. `defp pk_desc_family_span!(src)`)
and call it from both tests, mirroring how `overlay_toggle_body!/1` was already correctly factored
out in this same commit.

```elixir
defp pk_desc_family_span!(src) do
  case Regex.run(
         ~r/^\.pk-desc-shell\s*\{.*?(?=\n\/\* Boundary between the primary reading block)/ms,
         src
       ) do
    [span] -> span
    nil -> flunk("Could not locate the .pk-desc* family span in assets/css/app.css.")
  end
end
```

### WR-02: `padding-right` reserves the toggle's full width on every clamped line, not just the last

**File:** `assets/css/app.css:3163-3180` (`.pk-desc.is-clamped`)

**Issue:** `padding-right: 2.75rem` is declared on `.pk-desc.is-clamped` itself, which under
`-webkit-line-clamp` applies uniformly to the whole clamped box — narrowing lines 1 and 2 by the
same 44px reserved for the toggle, even though the toggle only ever occupies the last line's
corner. Combined with the unconditional `text-align: justify; text-justify: inter-word;` a few
lines above (also unconditional per UAT), this reduces the usable text width on every line of every
collapsed description, which can visibly widen inter-word gaps from justification — worse on
narrow mobile viewports, where this project's own conventions (mobile-first priority) put the
reading column at its tightest. This is a known, explicitly documented trade-off in the rule's own
comment (not an oversight), but it's a real, permanent readability cost that's worth flagging for a
mobile-width visual check during UAT rather than assuming it's fine because it's documented.

**Fix:** No code change strictly required if UAT confirms it reads fine on real mobile widths; if
it doesn't, consider `shape-outside`/`initial-letter`-style techniques to reserve space only on the
clipped line, or accept the current approach but add a mobile-width screenshot check to this
phase's UAT checklist specifically for a long (3-line-clamped) description on the narrowest
supported viewport.
