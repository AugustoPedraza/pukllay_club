## Accomplishments
- `.pk-title-echo`'s background moved off the page's own token (`base-100` → `base-200`), the same one-step-darker/tinted rule already validated on the mobile CTA bar.

## Decisions Made
- **Checkpoint outcome:** the developer selected **accept-mechanical** in response to Task 3's `checkpoint:decision`. Full detail in "Open design questions" below.
- **Border token swap** (Rule 1 auto-fix, not part of the original plan text): `var(--color-base-300)` does not clear the 3:1 non-text contrast floor against `var(--color-base-100)` in either theme — none of the `base-100/200/300` family does, by design (it's a subtle background-stepping scale, not built for border visibility). Swapped to `var(--color-neutral)`, reusing the exact token this codebase already applies for the lightbox-close button's own dark-theme contrast fix (G-01.2-20), rather than inventing a new value.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Border token `var(--color-base-300)` fails its own acceptance criterion**
- **Found during:** Task 2, while writing the border's own measured-contrast test
- **Issue:** The plan's Task 1 kept the existing `var(--color-base-300)` border token, on the assumption it already cleared the 3:1 non-text contrast floor `page-shell.md`'s principles require. Measured directly, it does not: 1.41:1 in light theme, 1.23:1 in dark theme — both far short of 3.0.
- **Fix:** Swapped `.pk-title-echo`'s `border-bottom` token to `var(--color-neutral)` (6.16:1 light / 8.45:1 dark), matching this plan's own must_haves and reusing a token this codebase already uses for the identical purpose elsewhere (G-01.2-20).
- **Files modified:** `assets/css/app.css` (both the Task 1 declaration's comment and the border-bottom line itself were updated as part of the Task 2 commit)
- **Verification:** New contrast test in Task 2 measures and asserts `>= 3.0` for both themes against the actual token value; passes.
- **Committed in:** `3e3454b` (Task 2 commit)

## Open design questions

Task 3 was a `checkpoint:decision` (`gate="blocking"`) routing two UAT gap G-01.3-1 items that no sketch in the 039-043 round covered. This project's config had both `workflow._auto_chain_active` and `workflow.auto_advance` set to `false` for this run (invoked without `--auto`), so per the checkpoint gate protocol this was a genuine human decision, not auto-selected.

**Decision:** How to resolve UAT items 7 (sticky header brand treatment/balance) and 8 (mobile footer visual weight) — neither was covered by sketches 039-043 or any recorded design decision.

**Options offered:**
1. `sketch-round` (recommended) — run a sketch round for both, matching how the other seven items in this gap were resolved.
2. `accept-mechanical` — accept Task 1's mechanical fix for the header now; defer the footer to its own phase.
3. `defer-both` — defer both to the backlog and close the phase on the seven already-resolved items.

**Developer selected: `accept-mechanical`.**

**Resulting disposition:**

- **Item 7 (sticky header brand treatment/balance) — PARTIALLY CLOSED.** Task 1's mechanical fix is the final answer for this phase: the bar no longer shares the page's own background token, its text and border now carry enforced 4.5:1 / 3:1 contrast floors in both themes (pinned by Task 2's tests, including the corrected border token), and its content shares the same shell-width box as the rest of the page. The **brand-tint question is explicitly NOT resolved** — whether the bar should carry an accent/primary/translucent-primary treatment instead of a neutral `base-200` step, and whether `.pk-scroll-top`'s solid `--color-primary` fill and infinite bounce are the actual source of the "balance is off" complaint, remain open. Neither `.pk-title-echo`'s fill choice nor `.pk-scroll-top` were changed toward a brand treatment in this plan — that was deliberately left alone in Task 1 and stays alone now. If this resurfaces in a future UAT round (it has now been reported twice: G-01.2-14, then G-01.3-1 item 7), it should be treated as its own sketch-worthy design question rather than another mechanical pass.
- **Item 8 (mobile footer visual weight) — DEFERRED, OUT OF SCOPE for this phase.** No footer CSS or template changes were made. This is recorded as a future concern: the footer is a shared shell component touching every page in the app (not just the detail page this phase covers), and three existing test files (`footer_rhythm_test.exs`, `footer_overflow_test.exs`, `footer_attribution_test.exs`) deliberately pin its current rhythm — any future work here should be scoped as its own phase, evaluated against the catalog and about pages too, not just the detail page.

Both dispositions are added to `.planning/STATE.md` by the orchestrator (not by this worktree-isolated executor) so they are not lost between phases.
