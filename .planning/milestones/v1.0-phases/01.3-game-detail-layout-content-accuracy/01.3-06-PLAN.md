<objective>
Wire `?designers=` and `?artists=` as real catalog filter params so the detail page's
Diseñadores/Ilustradores names can become navigable pills (UAT gap G-01.3-1, item 3).

Sketch 039 chose `/?designers=` / `/?artists=` as the href targets, following this page's
existing filter-linked-chip convention (Mecánicas → `?mechanics=`, Temáticas → `?themes=`),
and **explicitly flagged in the sketch itself** that "Neither filter param is wired in
`CatalogLive.Index` today — this is a real implementation follow-up, not just a style change."
This plan is that follow-up. It ships no UI change to the detail page; plan 01.3-07 renders
the pills against the params this plan creates.

Purpose: without this, the detail page's creator pills would be links into an unfiltered
catalog — a broken round-trip, which is exactly the "flagged gap: URL-persistence isn't proven"
failure mode `detail-page-layout.md` already warns about.
Output: two new filter params, end to end — URL read, query, active-filter chip, chip removal,
breadcrumb round-trip, tests.
</objective>

<planner_note>
**Why an open-text param is acceptable here, stated once so the executor does not re-litigate it.**
`CatalogFilters`' moduledoc says every facet value is re-validated "through `from_params/1`'s
closed Vocabulary whitelist". Designers and artists have no closed vocabulary — they are
free-text BGG-sourced strings, hundreds of distinct values. This plan therefore introduces the
module's FIRST open-text list param. The whitelist invariant is replaced, for these two keys
only, by an explicit bound-and-parameterize contract (element count, per-element length, Ecto
parameterized binding) written in Task 1 and Task 2 and tested in Task 3. Update the moduledoc
to say so — do not leave a doc claiming a whitelist that two of its eleven keys no longer honour.

**Not in scope, deliberately:** no `designers`/`artists` section is added to the filter modal.
These are link-only entry points (arrived at from a detail page) with a chip-row exit; adding a
several-hundred-option checklist to the modal is a different feature with its own UX question.
`filter_modal.ex` is untouched by this plan.
</planner_note>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser URL → `CatalogLive.Index.handle_params/3` | An attacker fully controls the `?designers=`/`?artists=` query string, including element count, element length, nesting depth and content. This is the first OPEN-TEXT (non-whitelisted) list param this app has ever accepted. |
| `?from=` value → `CatalogFilters.catalog_path/1` | The detail page's breadcrumb re-decodes a query string carried across pages; it now carries opaque creator strings in addition to whitelisted facet values. |
| chip label → rendered HTML | An attacker-supplied creator string is interpolated into a visible chip label and an `aria-label`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01.3-06-01 | Tampering (injection) | `Catalog.maybe_filter_designers/2`, `maybe_filter_artists/2` | high | mitigate | Values reach the query only as `type(^values, {:array, :string})` — an Ecto parameterized binding inside `fragment("? && ?", ...)`. No string interpolation into SQL anywhere in either clause. Task 1 acceptance criteria grep for the parameterized form. |
| T-01.3-06-02 | Denial of Service | `CatalogFilters.parse_name_list_param/1` | high | mitigate | `Enum.take(20)` applied BEFORE any per-element work bounds a repeated-key flood; `String.slice(&1, 0, 120)` bounds each element; `filter_games/1` still always applies `LIMIT` (existing T-01-22). GIN indexes on both columns (Task 1) keep the overlap predicate index-backed rather than a sequential scan. |
| T-01.3-06-03 | Tampering (open redirect) | `CatalogFilters.catalog_path/1` | high | mitigate | Unchanged mechanism: the value is length-bounded, decoded, re-validated through `from_params/1`, then **re-encoded from scratch** via `to_query/1` + `Plug.Conn.Query.encode/1`. A `javascript:` or `//host` string can only ever appear as an encoded *value* inside a `/?...` path, never as the path itself. Tested explicitly in Task 3. |
| T-01.3-06-04 | Tampering (XSS) | `active_filter_chips/1` label + `aria_label` | medium | accept | HEEx auto-escapes every `{...}` interpolation and this codebase calls `raw/1` nowhere on this path. The 120-character bound also caps the payload size. Accepted rather than adding a redundant sanitiser that would duplicate the template engine's own guarantee. |
| T-01.3-06-05 | Information Disclosure | `?designers=` enumerating catalog contents | low | accept | The catalog is public and unauthenticated by design (CATALOG-08); enumerating designers reveals nothing a visitor cannot already read by browsing every detail page. |
| T-01.3-06-SC | Tampering (supply chain) | npm/hex/cargo installs | n/a | accept | This plan installs no new packages. `mix.exs`/`mix.lock` are not in `files_modified`; a package-legitimacy checkpoint is therefore not applicable. |
