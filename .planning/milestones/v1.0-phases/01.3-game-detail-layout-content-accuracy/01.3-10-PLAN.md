<objective>
Close UAT gap **G-01.3-4** (blocker): the description card's expand/collapse chevron renders
outside the right edge of the text column at 390px.

The fix is not a new design — it is the fallback `01.3-08-PLAN.md` pre-authored for exactly this
failure class in its own `<planner_note>`, and that `description-truncation.md` recorded as the
known-good landing spot ("built and rejected on aesthetics alone", not on correctness). Replace the
`float`-inside-a-justified-clamped-paragraph positioning technique with the native line-clamp
mechanism plus an always-trailing-sibling toggle.

Purpose: the current chevron's horizontal position depends on an engine correctly excluding a float
from a clipped, justified line's width computation. Blink does; the user's engine (WebKit/Mobile
Safari, per `.planning/debug/chevron-outside-text-column.md`) demonstrably does not. Moving the
button out of the paragraph removes the dependency entirely rather than tuning it — this stops
being a rendering question and becomes a DOM-structure question that every engine answers the same
way.

Output: a description card whose collapsed state clips at three lines with a native ellipsis and
whose toggle is a contained, 44px-square control below the text, with the whole contract pinned by
tests that fail loudly if the float technique is ever reintroduced.
</objective>

<planner_note>
**This plan does not re-open a design question.** `01.3-08-PLAN.md`'s `<planner_note>` already chose
this exact fallback, in writing, before the bug happened, and named the trigger condition ("if
Task 3's human check finds [the technique failing] on real content at either real width... do NOT
re-sketch"). The trigger fired. Apply the pre-decided answer. Do not run a sketch round, do not
re-tune the float, do not invent a third technique.

**One deliberate departure from the fallback's literal wording.** The fallback says to drop "the
`::before` offset tuning". Dropping the offset overlay outright would drop the toggle below this
project's 44px touch floor (`ux-responsive`), which the overlay was the only thing supplying. Once
the button is a standalone block-level control rather than ink inside a justified line, it can carry
a REAL 44px box instead — using `min-h-11 min-w-11` in the markup, the exact idiom `.pk-scroll-top`
already uses on this same page. That is strictly better than an invisible overlay, which by
construction hangs 13px over the paragraph above it and the fact grid below it (an accidental
tap-hijack surface). Record this in the SUMMARY as a departure with its reason.

**The icon steps from 12px to 16px, and this is a consequence, not a style opinion.** 12px was
chosen to match the ink height of the adjacent "…" glyph. That glyph is gone (the clamp supplies its
own ellipsis), so the number that was derived from it is now derived from nothing. 16px is what every
other standalone icon-button on this page uses (`.pk-scroll-top`'s `size-4`).
</planner_note>
