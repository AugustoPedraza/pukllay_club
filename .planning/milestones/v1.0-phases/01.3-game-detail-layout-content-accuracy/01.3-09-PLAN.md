<planner_note>
**What is already known, so the executor does not re-diagnose it.**

`.pk-title-echo` currently declares `background: var(--color-base-100)` — the exact same token
the page body uses. A bar with the page's own background, separated only by a 1px border, is the
same defect `detail-page-mobile-interaction.md` already diagnosed and fixed once on the mobile
CTA bar: *"give a bar of stacked controls a background one step darker/tinted than the controls
sitting on it, not the same token — verify with computed backgroundColor, not by eye, since
near-identical tints are easy to miss on a screen."* That principle is recorded, validated and
directly applicable. Applying it is not a design guess.

A separate, earlier round (G-01.2-14 / G-01.2-24) already measured this bar's TEXT contrast in
light theme and found it fine, and already fixed a two-line-wrap crowding problem via
`.pk-title-echo-name`. Do not undo either. What was never measured is dark theme, and what was
never addressed is the bar-versus-page separation. Those are this plan's Task 1.

**What is NOT known, and must not be invented.** "Using official brand colors or similars" and
"the general visual balance for that dynamic sticky header is off" are look judgements with at
least three plausible answers (neutral base step / accent tint / primary-tinted translucent).
The same is true of the footer's mobile weight — `page-shell.md` records the principle *"Don't
let a footer's visual weight go unchecked against sparse pages — check the thinnest page, not
just the richest"* but no sketch ever produced a mobile remedy, and three existing test files
(`footer_rhythm_test.exs`, `footer_overflow_test.exs`, `footer_attribution_test.exs`) pin the
current rhythm deliberately. Task 3 is a decision checkpoint, not an implementation.
</planner_note>
