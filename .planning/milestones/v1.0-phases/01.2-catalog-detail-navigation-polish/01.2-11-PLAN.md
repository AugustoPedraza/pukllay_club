<objective>
Make the catalog search box work again, and stop the search-morph from fighting itself.

`.pk-search-morph` carries a literal `class="pk-search-morph"` alongside a *dynamic*
`data-search-expanded={to_string(@search_expanded)}` attribute, so the element sits in a
change-tracked part of the template. The moment any of its dynamic inputs move — `@search_expanded`
flipping on the first search character, the `.pk-filter-badge` count appearing, or the `nav_menu` /
`subnav` sibling slots disappearing when `browsing_results?/1` flips — LiveView re-applies the
server's attribute set and strips the client-added open-state class. `syncMorph()` in `updated()`
then silently re-adds it, but never restores focus. The member types one character, the pill snaps
shut, the caret is lost, and every subsequent keystroke goes nowhere: "I type and nothing happen"
(G-01.2-2). The same strip/re-add cycle, plus the hook's document-level outside-click test treating
every FilterModal control as an outside click (the modal renders as a sibling far outside
`.pk-search-morph` while its only trigger is nested *inside* it), is the "I can't open again the
search" symptom that made G-01.2-3 unreproducible.

G-01.2-1 has no code defect at all: `GameCard` and `GamePreview` build `detail_path/2` identically
from the same `@from` assign in one pass. The tester simply never reached the filtered results-grid
surface, because search was dead — so no card on screen carried a `from` param to inspect. This plan
closes it by making that surface reachable and by pinning the parity in a test.

The fix is not a patch on either mechanism. It is to stop splitting ownership of one piece of state
across two runtimes: the server renders whether the box is open, the hook only moves focus. That
deletes the whole class of desync — the strip, the one-way reopen, and the outside-click race — in
one change.

Purpose: search is the catalog's primary action and it is currently unusable, which also blocked
three other UAT tests from being reproducible at all.
Output: server-owned search-morph state, a focus-only header hook, and tests that pin the
regression which caused this gap plus the href parity that could not be observed because of it.
</objective>

| URL query params -> handle_params/3 | Pre-existing; this plan adds one derived boolean read from it |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01.2-11-01 | Tampering | `open-search` / `close-search` handlers | low | mitigate | Both handlers ignore their params entirely (`_params`) and write a hardcoded `true`/`false`. No client value reaches an assign, no atom is created from client input. |
| T-01.2-11-02 | Denial of Service | `close-search` dispatched in a loop from a hostile client | low | accept | Each handler is an `assign/3` with no query, no I/O and no allocation growth; a LiveView process handles events sequentially. Cost is strictly below the already-accepted `search` handler, which runs a DB query per keystroke. |
| T-01.2-11-03 | Information Disclosure | `data-search-expanded` rendered into HTML | low | accept | The value is a boolean describing a UI affordance's state, derived from params the visitor themselves supplied. It discloses nothing not already in their own URL. |
