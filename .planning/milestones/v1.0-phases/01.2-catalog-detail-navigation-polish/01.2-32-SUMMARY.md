# Phase 01.2 Plan 32: Lightbox Chevron Dark-Theme Consistency Summary

Both lightbox chevrons now carry the same dark-theme `--btn-color`/`--btn-fg` fill the close button
got in round 8, applied through the shared `.pk-lightbox-chevron` class so all three lightbox
controls read as one family in dark theme — closing G-01.2-21, the last open item on the lightbox.

## What Was Built

- **Task 1** (`test(01.2-32)` + `feat(01.2-32)`, TDD): Added a dark-scoped CSS rule,
  `[data-theme="dark"] .pk-lightbox-chevron { --btn-color: var(--color-neutral); --btn-fg:
  var(--color-neutral-content); }`, immediately after `.pk-lightbox-chevron-next`'s existing rule.
  Byte-identical in its two declarations to `[data-theme="dark"] .pk-lightbox-close`. Backed by three
  new tests in `catalog_show_test.exs`:
  1. The new rule sets both custom properties from the neutral token pair, no literal colour.
  2. **The consistency gate**: the new rule's declaration set (property/value pairs, sorted,
     whitespace-normalised) equals the dark-scoped close-button rule's declaration set — so a future
     round that re-tunes one control without the other fails the suite instead of reaching UAT as a
     fresh gap.
  3. Exhaustive positive pins confirming `.pk-lightbox-chevron` still declares only `z-index`,
     `.pk-lightbox-chevron-prev` only `left`, `.pk-lightbox-chevron-next` only `right` — light theme
     cannot be dragged along by an unscoped colour addition.

  Before writing the new rule, fixed a pre-existing landmine: the chevron z-index guard's regex
  (`~r/\.pk-lightbox-chevron\s*\{([^}]*)\}/`) had no `(?m)^` start-of-line anchor, unlike every other
  rule-body helper in the file — `Regex.run/2` returns the first match, so an unanchored pattern would
  have silently read the body of the new theme-scoped rule instead of the z-index rule once it was
  added above it in file order. Anchored and re-verified passing before any CSS was written.

- **Task 2** (`docs(01.2-32)`): Extended the round-8 design-record section in
  `detail-page-mobile-interaction.md` (widened heading to name both rounds/gaps) with a new paragraph
  recording: a contrast fix on one of a set of markup-identical sibling controls is a new defect, not
  a partial fix (evidenced by two consecutive user reports on the same overlay); a prior UAT pass
  expires when the surface underneath the control changes; and the implementation rule (one rule on
  the shared class, backed by a declaration-set equality assertion). Extended the existing CSS snippet
  to show both dark-scoped rules together.

## Root Cause (from prior diagnosis, `.planning/debug/G-01.2-21-lightbox-control-consistency.md`)

Round 8 (01.2-30) fixed only `.pk-lightbox-close`'s dark-theme contrast, deliberately excluding the
chevrons because they "passed UAT test 21 in both themes on this same stage." That check ran under
round 7 (01.2-29), while `.pk-lightbox`'s own background was still a translucent scrim. Round 9
(01.2-31, G-01.2-19) then made that background fully opaque, string-identical to the photo stage — the
exact environmental change that made the close button's unmodified `.btn` default measure ≈1.1:1 in
dark theme. The chevrons, carrying the same unmodified default, were never re-tested after that change
and inherited the same latent defect. The user's round-10 report ("the close button and the rest of
controls must be consistent") is a direct, accurate observation of this asymmetric fix.
