## Accomplishments

- **One scrim, two readers, never inverting.** `--pk-overlay-scrim` (`color-mix(in srgb, var(--pk-shadow-color) 72%, transparent)`) is declared exactly once in `:root`, immediately after the existing fixed `--pk-shadow-color` token. `.pk-lightbox` and `.pk-sheet-backdrop` both now read it instead of independently writing `color-mix(in srgb, var(--color-base-content) 55%, transparent)` — the buggy declaration that mixed in the app's *text* color, which is near-black in light theme (looked fine) and near-white in dark theme (a pale veil over an already-dark page). `.pk-drawer-backdrop` was read and deliberately left alone: it already uses a background token, not a text token, and was not part of either UAT report.
- **The lightbox is always rendered now, state lives in a class.** Removed the Phoenix `:if={@lightbox_open}` from the container; `class={["pk-lightbox", @lightbox_open && "is-open"]}` plus `aria-hidden={to_string(!@lightbox_open)}` carry open/closed state instead — matching the conditional-attribute idiom `Layouts.header_inner/1` already uses for `aria-expanded`. This is what makes an actual transition possible: a conditionally-rendered element has no closed DOM state to fade from or to, which is why the old instant `display:none`/`flex` toggle snapped.
- **Token-driven fade + scale, no wrapper element.** `.pk-lightbox`'s closed state is `opacity: 0; visibility: hidden; pointer-events: none;` with `transition: opacity var(--duration-base) var(--ease-out-soft), visibility calc(var(--duration-base) * 2) var(--ease-standard);` — `display: flex` moved permanently into the base rule. `.pk-lightbox-img` gained a `scale(0.96)` → `scale(1)` pair on the same tokens, applied directly (no wrapper — this app's close button is positioned against the viewport, not the image's corner, so a wrapper would carry no job).
- **Arrow keys route through the existing guarded path.** The `.Lightbox` hook's keydown handler gained a top-of-function `if (!this.el.classList.contains("is-open")) return` guard, plus `ArrowLeft`/`ArrowRight` handlers that `.click()` the existing chevron buttons (now carrying stable `data-lightbox-prev`/`data-lightbox-next` hooks) rather than pushing a new event — the keyboard route is byte-identical to the pointer route through `select-image` and its membership whitelist. `grep -c pushEvent` is unchanged against HEAD (2: `close-lightbox`, `close-reservation`).
- **Focus lifecycle keyed off a transition, not the current state.** The hook's `mounted()`/`updated()` both call one `syncFocusOnOpenChange()` routine that compares the current `is-open` state against the previously observed one: closed→open moves focus to the close button, open→closed moves it back to the poster button (now carrying a stable `id="detail-lightbox-trigger"`). This deliberately does nothing on mount when the state hasn't changed, so it never steals focus on page load.
- **Arrow-anchoring decision recorded.** Kept viewport-edge anchoring (production's existing `left-4`/`right-4` placement) rather than switching to image-relative anchoring — decision, three reasons, and one honestly-recorded tradeoff live in a comment beside the chevron buttons and above.

## Decisions Made

See `key-decisions` in frontmatter. In addition:

- **Deviated from the sketch/knowledge-base doc's literal CSS snippet** (`visibility 0s linear var(--duration-base)`) because this repo's own `test/pukllay_club_web/motion_rhythm_test.exs` — added since that doc was written — bans any literal `ms`/`s` duration AND the `step-*`/`linear`/`ease-in`/`ease-out`/`ease-in-out` keywords inside any `transition` shorthand. The textbook technique violates both bans (`0s` is a literal, `linear` is a banned keyword; a `step-end` alternative I tried first is also a banned keyword). Landed on `visibility calc(var(--duration-base) * 2) var(--ease-standard)`: `visibility` is a CSS *discrete* property, which per spec flips at the point its own easing curve's output crosses 50% — doubling its duration via `calc()` times that 50%-crossing to land at approximately the same wall-clock moment the paired `opacity` transition (at the un-doubled `--duration-base`) finishes fading to 0. `calc()` combining a token with a plain multiplier is an idiom this file already uses elsewhere (e.g. `calc(100vw - 2 * var(--pk-gutter))`), so this isn't a new mechanism, just a new application of it. Ran `mix test test/pukllay_club_web/motion_rhythm_test.exs` after the change: 7 tests, 0 failures.
- **Confirmed no JS test harness exists in this project** (checked `assets/package.json` — does not exist; no `.test.js`/`.spec.js` files under `test/`) before writing the SUMMARY's coverage rationale for the client-side-only deliverables (D5, D6) — this is why those two are `human_judgment: true` with an explicit rationale rather than silently marked as automated-covered.

## Colour Verification (Task 1 requirement — both themes, old vs. new)

No browser-automation tool was available in this execution context (same constraint 01.2-19/01.2-20 hit for their own live-measurement requirements), so the before/after scrim contrast is derived analytically from the exact declared CSS values, not a live pixel measurement:

`--pk-shadow-color: rgb(20 8 34)`. `color-mix(in srgb, C P%, transparent)` preserves `C`'s own RGB channels and scales alpha to `P%` (mixing with fully-transparent black contributes nothing once un-premultiplied), so:

| Value | Light theme | Dark theme |
|---|---|---|
| **NEW scrim** (`--pk-overlay-scrim`, this plan) | `rgba(20, 8, 34, 0.72)` | `rgba(20, 8, 34, 0.72)` (same — fixed, not theme-derived) |
| Page background (`--color-base-100`) | `#FFFFFF` = `rgb(255, 255, 255)` | `#170A26` = `rgb(23, 10, 38)` |
| **Darker than page?** | Yes (0.72-alpha near-black over white) | **Yes** (0.72-alpha near-black over an already-dark page — still visibly deepens it) |
| **OLD scrim** (HEAD, `color-mix(..., var(--color-base-content) 55%, transparent)`) | `rgba(36, 18, 56, 0.55)` (base-content `#241238`) | `rgba(243, 236, 250, 0.55)` (base-content `#F3ECFA`) |
| **OLD darker than page?** | Yes (dark text color, coincidentally correct) | **No — the bug.** A 0.55-alpha near-white veil (`rgb(243,236,250)`) over an already-dark page (`rgb(23,10,38)`) is *lighter* than the page, the opposite of a dimming scrim. |

The dark-theme inversion the plan describes is visible directly in this table: the OLD dark-theme scrim (`rgb(243,236,250)`, near-white) sits on the *light* end of the palette while the page it's meant to dim (`rgb(23,10,38)`) sits on the dark end — the scrim was never darker than the page in dark theme before this fix. The NEW scrim is the same fixed near-black value in both themes and is darker than the page in both. Live visual confirmation (does it actually read as a dimmed, separated photo on a real render) is routed to Task 1's own `<human-check>`.
