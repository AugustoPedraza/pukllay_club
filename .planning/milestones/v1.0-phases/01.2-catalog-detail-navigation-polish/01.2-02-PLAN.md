<objective>
D-06: upgrade `PukllayClub.Catalog.similar_games/1` from "same weight band, alphabetical"
to "same weight band, ranked by how many mechanics and themes the candidate shares with the
current game."

Purpose: the "Juegos similares" shelf currently answers "what else is this hard?", which for
a 400-game catalog means an essentially arbitrary alphabetical slice of one third of the
library. Ranking by shared mechanics/themes makes it answer "what else plays like this?" —
the question a member on a detail page is actually asking — using columns that already exist
(`text[]` mechanics/themes per PROJECT.md's durable architecture principle), with no schema
change and no new query shape outside this one function.
Output: one rewritten query function plus its documentation, and the tests that pin the
ranking contract.
</objective>

  <behavior>
    - Base game has mechanics `["Deck Building", "Set Collection"]` and themes `["Fantasy"]`,
      weight band `ingenio_estratega`.
    - Candidate A (same band) shares two mechanics and one theme -> ranks first.
    - Candidate B (same band) shares one mechanic and no theme -> ranks after A.
    - Candidate C (same band) shares nothing -> still present, ranks last.
    - Candidate D (different band) is absent regardless of overlap.
    - Two candidates with identical overlap are ordered by `name` ascending, then `id`
      ascending — the same tie-break discipline `tags_query/1` and `weight_band_query/1`
      already apply, and for the same reason (there is no unique index on `name`).
    - A base game with `mechanics: []` and `themes: []` returns its band-mates without
      raising; every candidate scores 0 and the result is name-ordered.
    - The existing five tests in the `similar_games/1` describe block still pass unchanged:
      never includes itself, only same-band games, empty list for a band with no other
      members, empty list for a nil band, and never more than 12 results.
  </behavior>

  <action>
    Rewrite `similar_games/1`'s second clause in `lib/pukllay_club/catalog.ex`. Keep the
    `%Game{weight_band: nil}` clause, the `where` on `g.weight_band == ^weight_band and
    g.id != ^id`, and `limit: ^@similares_limit` exactly as they are — D-06 changes the
    `order_by` and nothing else about the predicate. Destructure `mechanics` and `themes`
    off the `%Game{}` in the function head alongside `id` and `weight_band`.

    Compute the overlap score in SQL as a weighted sum of two set-intersection cardinalities:
    the count of mechanics the candidate shares with the base game, weighted 2, plus the
    count of shared themes, weighted 1. Mechanics carry the heavier weight because they
    describe how a game actually plays, while themes are flavour — two worker-placement
    games are a better "more like this" answer than two unrelated games that both happen to
    be set in space. Express each cardinality with a single `fragment/2` of the form
    `cardinality(array(select unnest(?) intersect select unnest(?)))`, passing `g.mechanics`
    (or `g.themes`) as the first placeholder and the base game's own list as the second,
    pinned through `type(^mechanics, {:array, :string})` — the same pinned-array-parameter
    form `maybe_filter_mechanics/2` (line 369) and `apply_sort/2`'s complexity clauses
    already use. No query text is interpolated (T-01-20). An empty `text[]` on either side
    yields cardinality 0 rather than NULL, which is why the empty-arrays case needs no
    special-casing; confirm this holds by running the new empty-arrays test rather than by
    assuming it.

    Order by that computed score descending, then `asc: g.name`, then `asc: g.id`. Do not
    fetch band-mates into Elixir and sort them with `Enum.sort_by/2`: this module's stated
    discipline is that the ordering expression lives in the query and every read carries a
    `LIMIT` (T-01-22, cited in `filter_games/1`'s doc at line 99).

    Rewrite the function's `@doc` in the same edit. The current text explicitly records that
    the mechanics/themes-overlap axis "was rejected as a new query shape with no existing
    precedent" — that sentence is now false and must be replaced with the D-06 rationale,
    the weighting (mechanics 2, themes 1), the fact that overlap ranks but never filters,
    and the retained nil-band guard and cap. Also update the sentence deferring "anything
    semantic (mechanics/themes overlap, embeddings)" to Phase 2 so it defers embeddings and
    natural-language matching only.

    Extend the existing `similar_games/1` describe block in
    `test/pukllay_club/catalog_test.exs` with the ranking tests from this task's
    `<behavior>` block. Leave its five existing tests byte-identical; only its describe
    string may change to reflect the new ranking rule.
  </action>
