<objective>
Bring the two lightbox chevrons into the same dark-theme treatment the close button already has, so
the overlay's three controls read as one family instead of one fixed control beside two unfixed
siblings.

Round 8 (01.2-30) gave `.pk-lightbox-close` an explicit dark-theme fill because daisyUI's unmodified
`.btn` default measured ≈1.1:1 against the lightbox's fixed dark backdrop. That fix was correct and
it worked. It was also deliberately scoped to the close button alone, on a stated rationale written
into the stylesheet at the time: the chevrons "passed UAT test 21 in both themes on this same
stage."

That rationale expired one round later, and the diagnosis found exactly when. UAT test 21 was run
under plan 01.2-29, when `.pk-lightbox`'s own full-viewport field was still a 72% translucent scrim.
Plan 01.2-31 (G-01.2-19, round 9) then changed that field to a bare, full-strength `--pk-shadow-color`
— string-identical to the opaque photo stage. The chevrons were never re-tested after that change,
and they carry the identical unmodified `.btn` default the close button had before round 8, sitting
now on the identical opaque field. So the same arithmetic that produced ≈1.1:1 for the close button
applies to them unchanged. Round 8's own plan named this risk in its flagged follow-ups and its own
human-check asked the user, in advance, whether the untreated chevrons would end up looking
under-treated beside the fixed close button. UAT test 24 is the answer: "The close button and the
rest of controls for lightbox must to be consistent."

So this plan applies the same two custom properties, reading the same two tokens, through the shared
class both chevron buttons already carry. It changes nothing else. It does not touch light theme,
where all three controls are already identical and already above 10:1 — and where the token that
rescues dark theme would measure ≈3.1:1, worse than the default it would replace. It does not touch
the close button, which is the reference being matched, not a thing to re-tune. It does not touch
markup, so the family cannot be split again by a modifier class landing on one control.

The durable part is the gate, not the rule. A one-line CSS fix does not need a plan; a CONSISTENCY
guarantee does. This round's assertion compares the two dark-scoped rules' declarations against each
other, so the family is enforced as a relationship rather than as two independently-correct rules
that happen to agree today.

Purpose: close G-01.2-21 — the last open item on the lightbox, severity cosmetic, one rule deep.
Output: three consistent controls in dark theme, an assertion that fails when the family drifts
apart, and the finding recorded that a control-set fix must cover the whole set.

This plan carries no separate `type="tracer"` task because the change IS a single end-to-end slice:
one rule, both controls, verified live in the built stylesheet and by eye in both themes. There is
no second layer for a tracer to prove.
</objective>
