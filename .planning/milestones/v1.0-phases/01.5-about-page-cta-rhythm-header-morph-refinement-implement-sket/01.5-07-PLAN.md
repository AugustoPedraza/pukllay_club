<objective>
Fix the closing band's internal geometry: remove the header-height compensation whose premise a later
plan in this same phase invalidated, resolve the full-viewport-height question with the developer
rather than silently, and move the tests that were pinning the defect in place.

Purpose: the UAT reported the Cierre band as having "a huge space top and bottom". The debug session
split this into two exact, independently-isolated halves by differential test. The band's
`min-height: 100vh` floor owns 100% of the whitespace VOLUME (a 157px content group inside a 900px
band, ~17% fill) — that is D-10 working as specified, so it is a design question, not a bug. The
`padding: var(--pk-header-h, 4.5rem) 0 0` on the same rule owns 100% of the ASYMMETRY: measured
`gapTop - gapBottom == exactly --pk-header-h` at every one of five widths and six viewport heights,
and removing it alone lands the gaps at an identical 371.7/371.7. That padding compensated for the
docked header visually eating the band's top edge — true when written, because `#cierre` was white
then. D-14 later painted the band the exact colour `.pk-nav` already is, so the header now blends in
and subtracts nothing while the 64px shift still applies unconditionally.

Output: a decided and applied treatment for the band's height, the asymmetry compensation removed,
D-10's comment rewritten to describe the code that now exists, the two stale CSS-source tests moved
in lockstep, and a gap-evenness oracle added to the geometry probe.
</objective>

## What the diagnosis established (do not re-derive it)

`.planning/debug/cierre-band-whitespace.md` is a completed, evidence-backed root-cause session with
reversible same-page-load differential tests. Its findings are inputs, not hypotheses.

**Three regimes across the width sweep (10 widths x 844px):**

| width | band height | content height | gapTop | gapBottom | delta | Cierre CTA | below-band void |
|-------|-------------|----------------|--------|-----------|-------|------------|------------------|
| 375-430 | 230 | 86 | 72 | 72 | **0** | hidden (D-11) | 200 |
| 481-639 | 302 | 158 | 72 | 72 | **0** | visible | 144 |
| 640-768 | 844 | 156.7 | 375.7 | 311.7 | **64.0** | visible | 144 |
| 1024-1280 | 844 | 168.6 | 370.2 | 305.2 | **65.0** | visible | 144 |

`delta` tracks `--pk-header-h` exactly (64px, 65px once the header grows when the brand wordmark is
revealed).

**Item 3 differential at 768x900 (measure → mutate → restore, same page load):**

| experiment | band | content | gapTop | gapBottom | delta | doc height |
|------------|------|---------|--------|-----------|-------|------------|
| BASELINE | 900 | 156.7 | 403.7 | 339.7 | 64 | 4216 |
| A: height floor neutralised | 220.7 | 156.7 | 64 | 0 | 64 | 3536 |
| B: top padding neutralised | 900 | 156.7 | 371.7 | 371.7 | **0** | 4216 |
| C: both | 156.7 | 156.7 | 0 | 0 | 0 | 3472 |

The two are orthogonal: A does not fix the asymmetry, B does not fix the volume. At 390px, A is a
total no-op — the rule is media-gated to ≥640px and correctly never applies below it.

**Short-viewport behaviour of the padding shorthand's zeroed bottom value:**

| viewport | band | content | gapTop | gapBottom |
|----------|------|---------|--------|-----------|
| 768 x 220 | 220.7 | 156.7 | 64 | **0** |
| 768 x 300 | 300 | 156.7 | 103.7 | 39.7 |
| 900 x 400 | 400 | 162 | 151.5 | 86.5 |
| 1280 x 600 | 600 | 178 | 243.5 | 178.5 |

`gapTop - gapBottom == --pk-header-h` at every row. The `0` bottom is a latent THIRD defect in the
same declaration: once the height floor is exhausted, the signature sits flush against the tinted
band's bottom edge, because D-10 silently dropped `.pk-band`'s shared bottom padding at this width
and relies entirely on leftover space to replace it.

**Already eliminated — do NOT "fix" any of these:**

- The height floor leaking to mobile or miscalculating against mobile browser chrome. The rule is
  media-gated to ≥640px and verified not to apply at 375/390/430/481/600/639px. Injecting an
  override at 390px changes nothing. The classic mobile-viewport-unit bug is NOT what was reported.
- `#cierre .pk-band-inner`'s own `gap` (D-12). It lives INSIDE the content group and is fully
  contained in the measured content height. It is NOT implicated and must not be retuned to
  compensate.
- `align-items: center`. It only distributes leftover space; with the floor neutralised there is no
  leftover and the band collapses to exactly its content height.
- A D-14 regression. Stripping the tint at runtime leaves every measured pixel in place. D-14 is the
  exposure condition, not the cause. **Do NOT revert or retune the tint.**
- Item 5 (CTA balance). Closed by plan 01.5-05 — same root cause as G-01.5-1, at
  `Layouts.sumate_cta/1`, not here.

**Why the existing gate cannot catch it:** `01.5-PATTERNS.md` specifies the D-10/D-12 assertions as
"min-height/gap CSS-source check", and the shipped tests do exactly that — they assert
`min-height: 100vh` IS PRESENT and that the padding reads the header token. They pass on the bug and
would FAIL on any fix. Nothing in the repo asserts anything about the band's height relative to its
content or the evenness of its gaps.
