### Pattern 1: Shared boolean drives multiple CSS consumers via parallel classList.toggle calls

**What:** The `.AboutHeaderMorph` hook already computes `this.docked` once per frame and toggles it
onto exactly one element (`this.header`, i.e. `#app-header`) at exactly two call sites: inside
`frame()` (`about_live.ex` ~line 244-247) and inside the first-paint block (~line 302-307).

**When to use:** D-03 requires the hero eyebrow's hide/reveal and (if a discrete fade rather than
pure continuous shrink is wanted) the companion text's fade to change "at the identical
crossing-point instant, both scroll directions" as the header reveal. The lowest-risk way to
guarantee this without introducing a second boolean or a second timing source is to add one more
`classList.toggle("is-docked", this.docked)` call at the *same two call sites*, targeting `this.el`
(the hook is mounted on `#about-hero` itself, so `this.el` already refers to it — no new DOM lookup
needed).

**Example:**
```javascript
// Source: about_live.ex, existing .AboutHeaderMorph hook, frame() function (~line 243-251)
const shouldDock = natural.top <= dock.top
if (shouldDock !== this.docked) {
  this.docked = shouldDock
  this.header.classList.toggle("is-docked", this.docked)   // existing
  this.el.classList.toggle("is-docked", this.docked)        // NEW — same instant, same boolean
  this.header.toggleAttribute("inert", !this.docked)
  this.from = this.progress
  this.to = this.docked ? 1 : 0
  this.startedAt = performance.now()
}
```
The identical two-line addition belongs in the first-paint block (~line 306) so a deep-linked visitor
who lands already-docked (D-02, unchanged) also gets the eyebrow/companion state right on first
paint, not just on the next scroll frame.

### Pattern 2: Scope new CSS to page-owned selectors, never edit the shared component

**What:** `Layouts.social_links/1` (`layouts.ex:1076-1175`) is shared by the footer, the mobile
drawer, and (as of Phase 01.4) the Contacto card. Its `class={@class}` prop only reaches the
outer wrapping `<div>` — individual `<a>`/`<span>` children get no per-call-site class hook.

**When to use:** D-06/D-07/D-08's chip redesign (background tint, icon-only+circular at
≤639px, centered) must be implemented as new rules under the existing `.pk-about-contact-links`
selector (already scoped to the Contacto card only, `app.css:2739-2767`), never by adding attrs
or classes to `social_links/1` itself — this is the exact same "page-owned CSS override, not a
shared-component edit" precedent `.pk-about-contact-links a svg` already established (resizing the
shared component's SVGs from 16px to 20px without touching `layouts.ex`).

**Example:**
```css
/* Source: assets/css/app.css, existing precedent to follow (lines 2739-2767) */
.pk-about-contact-links a svg {
  width: 20px;
  height: 20px;
  flex-shrink: 0;
}
/* NEW, same scoping discipline — hide labels + go circular only under 639px,
   never touching social_links/1's own markup */
@media (max-width: 639px) {
  .pk-about-contact-links a span {
    display: none;
  }
  .pk-about-contact-links a {
    /* circular, icon-only sizing */
  }
}
```

### Anti-Patterns to Avoid

- **Adding a second boolean/timer for the eyebrow or companion-text fade** — D-03 explicitly forbids
  gating this on a separate scroll-position/viewport-height check; reuse `this.docked` per Pattern 1.
- **Editing `Layouts.social_links/1` to add per-icon classes** — would ripple into the footer and
  drawer call sites, which must stay byte-identical (both currently pass no `icons`/`labels` attrs
  and rely on the defaults). Scope everything through `.pk-about-contact-links` instead (Pattern 2).
- **Hard-coding the Cierre `padding-top` as a pixel literal** — the header's real height is not a
  fixed number (it already varies with viewport per the existing `--pk-header-h` mechanism); reading
  the live custom property is strictly more correct than any measured constant, including a freshly
  re-measured one.
- **Reusing the `.pk-about-eyebrow` class name for the hero's eyebrow line** — that class already
  exists and is applied ONLY to the Cierre band's closing signature (`about_live.ex:744`,
  `app.css:2596-2606`). The hero eyebrow (`about_live.ex:362-364`) currently has no stable class hook
  at all (only Tailwind utilities) — give it a distinct class (e.g. `pk-about-hero-eyebrow`) or target
  it via the sibling selector `[data-morph-anchor] + p`, never `.pk-about-eyebrow` verbatim, or the
  Cierre signature's unrelated styling will leak onto the hero eyebrow.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Soft accent-tinted chip surface | A new `color-mix()` formula or a new custom property | `background: var(--color-accent); color: var(--color-accent-content);` bare | `--color-accent` is already a soft pastel pairing in both themes (`#EDE1F7`/`#3D096D` light, `#3D2A56`/`#E4D3F5` dark) and is already used this exact way (`.pk-pill-accent`, `app.css:766-770`; `.pk-conn-banner`, `app.css:1110-1116`) |
| "Tint" band background | A new `--color-surface` token | `var(--color-base-200)` | Already the app's established "one step off base" surface color, used this way throughout (`.pk-about-contact-card`, footer, drawer social icons) |
| Header height for Cierre `padding-top` | A hand-measured pixel constant | `var(--pk-header-h, 4.5rem)` | Already a live, continuously-republished custom property (set by `.CatalogNav`'s `ResizeObserver`, `layouts.ex` ~line 340-346) that every other header-relative offset in this codebase already reads (`.pk-shelf` scroll-margin, `.pk-title-echo` top offset) |
| Mobile-only icon-only chip variant | A second markup branch / LiveView conditional | A CSS `@media (max-width: 639px)` block scoped to `.pk-about-contact-links` | Matches the codebase's established mobile/desktop split pattern (e.g. the hero's `sm:hidden`/`hidden sm:block` tagline pair) — pure presentation change, no server-side branching needed |

**Key insight:** Every "don't hand-roll" item above resolves to "the token/mechanism already exists
in this codebase — use it as-is," not "reach for an external library." This phase's entire risk
surface is CSS cascade/specificity correctness (per the established `.pk-*`-vs-Tailwind-utility
cascade hazard already documented at the top of `app.css`) and JS state-sharing correctness (Pattern
1 above), not missing tooling.

## Common Pitfalls

### Pitfall 1: Assuming `sumate_cta`'s mobile centering is broken (it is not)

**What goes wrong:** Blind-copying sketch 051's own centering fix (`justify-content: center` added
to a hand-rolled button class) onto the real app's `.pk-about-cta-bar`/`sumate_cta` combination.

**Why it happens:** The sketch's own button CSS genuinely had the bug (`display: inline-flex;
align-items: center` with no `justify-content`) — but the real app's button is daisyUI's `.btn`
class, which `[VERIFIED: priv/static/assets/css/app.css:22300-22326]` already declares
`display: inline-flex; ...; align-items: center; justify-content: center; ...` at its base layer.

**How to avoid:** Do not add any CSS for this. If a plan task exists to "fix" `.pk-about-cta-bar`
centering, it should be replaced with a verification step (screenshot/DOM check) confirming it's
already correct, not a code change.

**Warning signs:** A diff that touches `.pk-about-cta-bar` or `sumate_cta`'s `justify-content`
property with no other functional change is a signal this pitfall was not checked first.

### Pitfall 2: Treating D-13's Cierre meta line as "already correct"

**Why it happens:** Plan 049 (Phase 01.4) removed the retired `linktree_url` link from the Cierre

**How to avoid:** This phase must actively delete that trailing `<a>` (D-13 requires "plain signature

### Pitfall 3: Colliding the hero eyebrow with the Cierre signature's `.pk-about-eyebrow` class

**What goes wrong:** Applying the existing `.pk-about-eyebrow` class (`app.css:2596-2606`, currently
`font-size: 0.75rem; text-transform: uppercase; letter-spacing: 0.1em; color: var(--color-neutral);`
plus an `a` rule for the underlined link) to the hero's eyebrow paragraph, assuming shared naming
implies shared intent.

**Why it happens:** Both lines are visually similar ("small, uppercase, muted, eyebrow-style
copy"), and it's tempting to reuse an existing class rather than add a new one.

**How to avoid:** `[VERIFIED: lib/pukllay_club_web/live/about_live.ex:744]` — a grep for
`pk-about-eyebrow` in `about_live.ex` returns exactly one match, at the Cierre band, not the hero.
The hero eyebrow (`about_live.ex:362-364`) has zero stable class hooks today (pure Tailwind
utilities: `font-sans text-xs uppercase tracking-widest text-neutral`). Give it its own class name
(e.g. `pk-about-hero-eyebrow`) so D-03's hide/reveal rule doesn't also silently apply to (or get
silently overridden by) the Cierre signature's unrelated styling.

**Warning signs:** A single CSS rule under `.pk-about-eyebrow` that mentions both "docked" state and
the Cierre band's underlined-link styling in the same block is a sign of an accidental merge.

### Pitfall 4: Re-litigating whether `.pk-about-mark-anchor` needs restructuring

**What goes wrong:** Spending a plan task "investigating" whether the existing
`[data-morph-anchor]`/`.pk-about-mark-anchor` element satisfies D-04's "in-flow spacer as first
child of `.hero`" requirement, when this is already directly verifiable by reading the file.

**Why it happens:** CONTEXT.md explicitly flagged this as unresolved ("verify during research

**How to avoid:** `[VERIFIED: lib/pukllay_club_web/live/about_live.ex:361]` — the anchor

362), the `<h1>` (365), the tagline `<p>`s (371-376), and the CTA `<div>` (377-379). No restructuring
is needed for D-04's positional requirement. (Framing nuance: `#about-hero` uses Tailwind's

visual effect CONTEXT.md describes as "the column's own gap" is real, but the CSS mechanism is

### Pitfall 5: Forgetting the visual-probe test's hard-coded `#contacto` scroll target after relocating the map

**What goes wrong:** `test/visual/about_map_attribution.mjs` (a developer-invoked, non-CI Node/CDP
probe) calls `document.querySelector('#contacto').scrollIntoView(...)` (line 384) to bring the map
thumbnail into view before measuring it. Once D-09 relocates the map markup from `#contacto` into
the Juntadas column, this call still finds `#contacto` (the element still exists — Contacto keeps
its heading/copy/chips) but no longer necessarily scrolls the map itself into the viewport center,
since the map is now a sibling column's content, not a descendant of `#contacto`.

**Why it happens:** The probe was written when the map lived inside `#contacto`; D-09 changes that
containment relationship without the probe's author anticipating it.

**How to avoid:** Update the `scrollIntoView` target to `#juntadas` (or to `.pk-about-map-thumb`
directly) when this phase lands. This file is not part of `mix quality`/CI, so it will not fail
loudly — it must be updated deliberately, not left to bit-rot.

**Warning signs:** Running the probe post-implementation and finding the map thumbnail sits outside
the captured viewport/screenshot region.

## Open Questions

1. **Discrete fade vs. pure continuous shrink for the companion wordmark at dock (D-01/D-02/D-03)**
   - What we know: the mark's own scale already continuously shrinks from 1 to `dock.height/markHeight`
     (roughly 0.18 given the mark's 180px rest height and the header's ~32-36px dock target) as part
     of the existing `write()` function — this alone makes the companion text nearly illegible at
     full dock without any extra opacity rule.
   - What's unclear: whether the sketch's "companion-text fade" language means an *additional*,
     separate opacity transition on the companion text specifically (a deliberate crossfade,
     independent of the continuous scale), or whether the continuous scale-to-near-zero is itself
     sufficient and "fade" is describing the perceptual *effect* of that shrink, not a second
     mechanism.
   - Recommendation: implement the companion text as a plain absolutely-positioned child of
     `.pk-about-morph-mark-inner` with no extra opacity rule of its own first (it already gets the
     shared `.pk-about-morph-mark-inner`'s existing `opacity`/`transform` transition for the entrance,
     and the per-frame `scale()` for the dock/undock ride) — add a discrete `.is-docked` opacity rule
     only if the human-verify checkpoint finds the pure-scale version reads poorly at the small end.

2. **Exact companion-text vertical offset below the isologo image**
   - What we know: D-01 says "absolutely positioned below the image, not affecting the box's own
     size math" and D-02 gives the rest-state font metrics (~25px, `0.02em` letter-spacing, weight
     400) — but no exact `top`/`margin-top` pixel offset is specified anywhere in CONTEXT.md or the
     sketch-findings skill.
   - What's unclear: the precise gap between the isologo's own bottom edge (which is cropped tight
     to its ink, per the existing `--pk-about-mark-clear` derivation comment at `app.css:2941-2965`)
     and the companion text's baseline.
   - Recommendation: treat this as a small implementation-detail choice for the planner/executor,
     verified visually at the human-verify checkpoint — not a blocking unknown, since it's a single
     CSS `top`/`margin-top` value with no architectural consequence either way.
