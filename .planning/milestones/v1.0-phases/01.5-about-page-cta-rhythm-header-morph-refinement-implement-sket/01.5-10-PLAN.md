### G-01.5-4 — the closing composition's one deviating object

The Cierre group has exactly three objects (heading, button, signature) and exactly one spacing rule.
The diagnosis rendered the approved design source (`.planning/sketches/051-about-full-page-cta-rhythm/
index.html`) in the SAME headless browser at the same widths and diffed every channel:

| channel @1280px | production | sketch 051 | delta |
|-----------------|------------|------------|-------|
| inner gap | 24px flat | 24px flat | IDENTICAL |
| box gaps heading/button/signature | 24.00 / 24.00 | 24.00 / 24.00 | IDENTICAL |
| heading ink | 327.47 x 57 @48px | 327.47 x 57 @48px | IDENTICAL |
| centring | sub-pixel on band centre | same | IDENTICAL |
| button box | 108.09 x 44 | 119.11 x 48 | -11.02 x -4 |
| button padding-inline | 20px | 28px | -8px (-28.6%) |
| button border-radius | 4px | pill | a KIND difference |
| button font-size | 18px | 16px | +2px, in a SMALLER box |
| button padding ratio | 1.74 : 1 | 2.15 : 1 | -19% |
| button label ink fill | 61.1% of box | 51.3% of box | +9.8pp crowded |

**Falsification / AND-gate:** applying ONLY the design-source button spec to the live page landed it
at 116.75 x 48 / 2.00:1, within 2.4px and 0.7pp of the approved sketch, with every other channel
unmoved. One object accounts for the entire measurable delta.

**Both alternative readings are inherited design, not drift, and are OFF LIMITS.** The flat `gap:
24px` is a byte-for-byte port of the sketch's own rule AND is recorded in the sketch's README round 9
as an explicitly human-requested rebuild ("one rule, unmodified at both viewports... verified live") —
changing it would silently overwrite a human-verified decision. The signature line being wider than
the heading exists in the approved sketch too (110.3% there, 117.9% here) and is inherited, not
introduced.

**Why plan 01.5-05 landed here:** it fixed the real mechanism defect (a bare one-axis height override
producing a 1.03:1 square-padded label box) by re-deriving the button from IN-REPO daisyUI precedent
rather than from the design source the composition's balance had been judged against. That was a
correct consistency repair — it is why the user's report opens with "Its better" — and it left the
fidelity delta open, which is why it continues with "not sure that is the best balanced composition".
The prior session's own `blind_spots` had explicitly left this question open for the user; plan
01.5-05 resolved it unilaterally toward in-repo precedent.

**The design source uses ONE class at all three call sites.** Sketch 051's own comment, verbatim:
`.btn-sumate` is the "same class reused at all THREE Sumate call sites below (hero, closing band,
mobile bar), exactly like production reuses one component so the three can never drift to different
labels/styles" — and it ships a `.btn-sumate.w-full { width: 100% }` variant for the bar. So restoring
fidelity at the component's single source is what the design source itself specifies; it is not a
blast-radius decision that needs mitigating with a per-call-site variant.

### G-01.5-7 — the bar has neither a surface nor an edge

**Eliminated by direct measurement, do NOT chase any of these:** the bar is NOT transparent
(`backgroundColor` fully opaque, `opacity: 1`, `backgroundImage`/`backdropFilter`/`filter`/
`mixBlendMode`/`clipPath`/`maskImage`/`boxShadow` all none, every ancestor transparent with opacity
1). It is NOT mis-stacked (`elementsFromPoint` at 15 points across its box returns the bar or its own
anchor as topmost, in both themes at both scroll offsets; the only higher-z element is the morph mark,
pinned near the top of the viewport). Its `position: fixed` is NOT resolving against an ancestor (the
full ancestor chain has no transform/filter/will-change/contain/perspective; its rect is byte-identical
at scrollY 0, 2678, 2780 and 2907). There is NO alpha-suffixed utility anywhere in the chain — the
bar's class attribute is literally just its own class name.

**Three AND-gated causes, all in the bar's own CSS:**

1. **DOMINANT** — `border-top: 1px solid var(--color-base-300)` (`app.css:2578`) is the bar's only
   declared edge and measures **1.415:1 light / 1.227:1 dark** against its own fill (1.406:1 / 1.19:1
   on rendered pixels) — under the 3:1 WCAG 1.4.11 non-text floor and under any perceptual threshold.
2. **CO-CAUSE** — `background: var(--color-base-100)` (`app.css:2577`) is the token `<html>` itself
   paints, so over most of the scroll range the bar's fill is **byte-identical (1.000:1)** to what is
   behind it, and 1.155:1 / 1.086:1 against the base-200 band and footer at page bottom. NOT
   independently fixable: the base-100/200/300 ladder's adjacent-step ceiling is 1.155:1 / 1.086:1.
3. **THIRD, page-bottom only, latent until (1) is fixed** — `body:has(.pk-about-cta-bar) {
   padding-bottom: 4.5rem }` (`app.css:5831`) = 72px against the bar's then-measured 69px height,
   leaving a 3px strip of document background between the footer's bottom edge and the bar's top
   border. `app.css`'s own comment concedes the value "is inherited unchanged from the spacer this
   rule replaces, not freshly measured".

**The 6-arm runtime differential (metric: strongest 1px luminance edge in the bar's top region):**

| arm | change | result |
|-----|--------|--------|
| A | status quo | 1.406:1 light / 1.19:1 dark, both scroll positions |
| B | fill -> base-200 only | **1.406:1 / 1.19:1 — provably inert**, AND the fill becomes 1.000:1 against the footer it overlays: strictly worse at page bottom |
| C | fill -> base-200 + border -> neutral | 5.785:1 / 7.128:1, but a 3px sliver of base-100 becomes newly visible above the crisp line |
| D | C + clearance re-derived | 4.999:1 / 6.647:1, sliver gone |
| **E** | **border -> neutral + clearance re-derived, fill LEFT on base-100** | **5.785:1 / 7.128:1 at BOTH scroll positions, sliver gone, and the bar keeps a 1.157:1 / 1.072:1 step against the footer instead of collapsing to 1.000:1** |

**Arm E is the fix.** The border is the necessary and sufficient channel; the fill swap is inert on
the reported symptom and actively worse at the page bottom. Arm C isolates the third contributor:
correcting the border makes the clearance slack newly visible, so the clearance must be co-fixed in
the same change or this returns as a new gap.

**In-repo precedent, already twice-diagnosed:** `.pk-title-echo` uses `background: base-200` +
`border-bottom: 1px solid var(--color-neutral)`; `.pk-mobile-cta-bar` uses `background: base-200` +
`border-top: base-300`. `.pk-about-cta-bar` is the only overlay bar still on `base-100` + `base-300`,
on BOTH channels. `app.css`'s own comment above `.pk-title-echo` already states the rule in prose,
including the measured `--color-neutral` contrast (6.16:1 / 8.45:1 vs base-100) and why base-300 fails
the 3:1 floor. Arm E deliberately keeps this bar's fill on base-100 rather than copying the siblings'
base-200, because at page bottom this bar overlays a base-200 surface and the siblings do not.

### Why no gate caught either

`about_live_test.exs` asserts only CSS-source presence/absence for this bar; `about_geometry.mjs` is a
geometric oracle (rects and adjacency); the clearance check asserts NON-INTERSECTION, which 72 > 69
satisfies. **No gate in this repo can observe a rendered colour**, and none observes the button's own
box. A source-level assertion on the two token names would have caught the bar; only a rendered-box
assertion can catch the button.

## The judgment calls this plan resolves, and on what evidence

### Restore the design-source button geometry — at the component's single source, all three call sites

The debug session named restoring design-source fidelity as the fix direction and flagged the
mechanism as an open design-system question: change the app-wide field-radius token, or document a
Cierre/hero exception. Both branches are declined in favour of a third that the evidence supports
better:

- **Changing the app-wide radius token is rejected.** It would restyle every button in the app —
  filters, the reserve CTA, the modal actions — to fix one composition nobody complained about
  elsewhere. That is the exact "global change to fix one surface" move the sibling sessions in this
  round rule out for the shared footer rule.
- **A per-call-site exception is also rejected**, because the design source itself explicitly uses ONE
  class at all three Sumate call sites with only a width variant for the bar, and says so in a comment
  about not letting the three drift. Building a two-geometry component to avoid touching the bar would
  create by design the drift both the sketch and the component's own docstring exist to prevent.
- **The pill is not a token violation.** The design-system rule this appeared to conflict with reads
  "resolves colour through the daisyUI theme CSS variables and radius through
  `--radius-box`/`--radius-field` — never a literal hex/rgb color", i.e. the literal prohibition
  attaches to colour. The same stylesheet already ships a full pill radius as a literal on more than a
  dozen surfaces (chips, badges, avatars, pills), and its own comment near the badge rules explicitly
  distinguishes the `--radius-*` scale from "the full 9999px pill the facts pills already ship". A
  pill Sumate button is the established in-repo way to express a pill, not an exception to be
  documented.

So: the four coupled properties are declared ONCE, in a single `pk-*` class inside the stylesheet's
sanctioned custom-CSS block, applied by `sumate_cta/1` itself. That satisfies the design layer's most
load-bearing rule verbatim — "a field that must look identical on two different surfaces is declared
in exactly one CSS class, shared verbatim by both".

**The size step is retired, not stacked.** `btn-lg` and the touch-floor utility both push on the same
axes the new class now owns; leaving them would recreate exactly the competing-height situation plan
01.5-05's own docstring warns about with the utility it removed. The new class becomes the single
owner of the button's size, and the 44px touch floor is satisfied by measurement (48px) and asserted
as a floor rather than as a specific utility class name.

**The catalog reserve CTA is deliberately NOT changed.** Plan 01.5-05 cited it as the in-repo
precedent for `btn-lg` + the touch floor. It stays exactly as it is: it is a different surface, on a
different page, with no counterpart in sketch 051, and no UAT round has reported it. The component
docstring must record why the Sumate CTA now diverges from it — because the Sumate CTA is the object a
human-approved composition was judged against and the reserve CTA is not — so the divergence reads as
a decision rather than as drift.

### The bar: arm E exactly — border only, fill untouched, clearance re-derived

Not a judgment call; the differential settles it. Arm B proves the fill swap inert AND worse at the
page bottom, arm E reaches the same contrast as arm C at both scroll positions while keeping a real
step against the footer. Recorded here only so a future reader does not "finish the job" by also
copying the siblings' base-200 fill.

### The clearance value is DERIVED, not chosen

The inherited literal was 3px loose against a 69px bar. After the button's height change the bar is
73px, so the same literal becomes 1px tight — the direction of the error flips. The lesson the debug
session drew is that a hard literal against a content-derived height is guaranteed to drift, so the
replacement is expressed in terms of the bar's own composition (its two padding steps, its button's
height, its border) and the probe asserts a TIGHT FIT against the measured bar rather than mere
non-intersection.
</decisions_made>
