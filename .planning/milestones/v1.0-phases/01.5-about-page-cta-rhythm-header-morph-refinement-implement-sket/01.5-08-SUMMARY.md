## Decisions Made

### bottom_collapse over boundary_collapse
About's top spacing (the hero, the isologo morph) is a separately-tuned, correct decision this plan must not move — only the bottom boundary double-stacked. `bottom_collapse` is the bottom-only axis built for exactly this shape (quick task 260902-il3); `boundary_collapse` would also collapse the top and silently move the hero. Task 1's rendered-DOM test asserts both halves of this (the collapsed-bottom class present AND the default top-padding utilities still present) so a future "simplification" to the wrong attr fails loudly.

### Presence-based `:has()` clearance over a JS-applied class
The detail page's own `body.pk-has-cta-bar` precedent is JS-applied by a lifecycle hook (`.DetailChrome`) because that bar retracts/parks on scroll. The About page's bar does neither — it's unconditionally pinned once visible — so there's no lifecycle to hang a hook on, and none is needed. `body:has(.pk-about-cta-bar)` reaches the identical result with zero JavaScript, reusing the exact idiom this file already established for the isologo scroll-morph.

### Value inherited unchanged, then corrected via measurement, not re-derivation
The 4.5rem clearance was deliberately kept as a placement fix, not a height retune, per the plan's own framing. The live probe caught that this was *insufficient by 13px* — not because the inherited value was wrong, but because a separate, pre-existing margin defect on the bar itself was silently consuming part of it. Fixing the margin (not inflating the clearance number) was the correct response: it fixes a real visual defect (a stray unpainted strip below the bar) at its actual source, and the original 72px clearance is provably sufficient once that defect is gone (69px bar height < 72px reservation).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `.pk-about-cta-bar` had a stray 16px `margin-block-end` from the shell's `space-y-4` utility, pushing the fixed bar away from the true viewport edge**
- **Found during:** Task 3, running the new fixed-bar/footer clearance oracle live against a booted dev server
- **Issue:** `.pk-about-cta-bar` is not the last child of the shell's `space-y-4` wrapper (`#pk-about-morph-mark` and the `<noscript>` no-JS marker follow it in `about_live.ex`), and Tailwind v4's `space-y-*` utilities apply `margin-block-end` to every non-last child — a different mechanism from Tailwind v3's `margin-top`-on-non-first-child, which this codebase's own STATE.md decision log had not previously encountered for a `position: fixed` element. Left un-neutralised, this gave the bar a real 16px margin that pushed its rendered box 16px above the true viewport bottom (measured: top=815px/bottom=884px in a 900px viewport, not the 831px/900px its own `bottom: 0` promises) — both a visible defect on its own (an unpainted strip below the bar) and the direct cause of the reserved 72px clearance falling 13px short of covering the bar's real on-screen footprint.
- **Fix:** Added `margin-block-end: 0;` to `.pk-about-cta-bar`'s base rule in `app.css`, the same unlayered-`.pk-*`-beats-layered-Tailwind-utility idiom `.pk-band` used for its own `margin-block-end: 0` fix in plan 01.5-06 — no `!important` needed.
- **Files modified:** `assets/css/app.css`, `test/pukllay_club_web/live/about_live_test.exs` (new regression test)
- **Verification:** Re-ran the live probe — bar top now lands exactly at 831px (the mathematically correct value), fixed-bar/footer clearance check passes with ~2.6px of real margin. Full `mix test` (889/889) and `mix quality` (credo --strict clean, sobelow unchanged pre-existing low-confidence findings only) both pass.

## Issues Encountered

While building Task 3's fixed-bar clearance oracle, an early version measured a ~2800px "overlap" that turned out to be a probe bug, not a real defect: `window.scrollTo(0, y)` animates under this app's `html { scroll-behavior: smooth }` rule (gated on `prefers-reduced-motion: no-preference`, which headless Chrome reports by default), so reading `getBoundingClientRect()` synchronously right after saw the pre-scroll page. Fixed by passing `{ behavior: 'instant' }` in the `ScrollToOptions` dictionary, which per the CSSOM View spec overrides the element's own CSS `scroll-behavior`. Documented inline in the probe so a future extender doesn't rediscover this the hard way.
