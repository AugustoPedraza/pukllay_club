# Plan 01-03 — TRACER: one real club game from CSV row to browser

**Phase goal (verbatim from ROADMAP.md):** Members can browse, filter, sort, and search a public
catalog of ~400 games, with UX that teaches complexity instead of assuming hobbyist vocabulary.

> **Tracer slice.** This plan wires ONE game along the entire Phase 1 stack — real CSV parse, real
> authenticated BGG call, real image download, real resize, real R2 upload, real database row, real
> public LiveView render — and proves it end-to-end before any horizontal expansion. It is
> production-quality, not a prototype: every module written here is the module the full 434-game
> seed (01-04) and the full browse UI (01-05) build on. The functionality gaps it leaves (full-file
> CSV normalization, gallery images, filters, search) are all fillable without an architectural
> change.

<objective>
Prove the three highest-risk boundaries of Phase 1 in one pass: BGG's newly-authenticated XML API
(and the true shape of its response), the image resize + R2 upload path that CATALOG-09 depends on,
and a public LiveView rendering a real seeded row.

Purpose: 01-RESEARCH.md flags the BGG XML field names as LOW-confidence training-data recall
(Assumption A1) because BGG's docs returned bot challenges during research. If those XPath selectors
are wrong they fail silently — `nil` and `[]`, not an exception. Discovering that after building
434 rows, four components, and a filter drawer would be expensive. One game, all the way through,
first.

Output: the `games` table, the `Catalog` context, the four seed modules, `mix catalog.seed`, a
public browse LiveView at `/`, and one real club game visible in a browser with a club-hosted cover.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| BGG XML response → `sweet_xml`/`xmerl` parser | Untrusted external XML is parsed on the seed machine. |
| BGG-supplied image URLs → server-side HTTP fetch | URLs extracted from that untrusted document are then fetched by our own process. |
| downloaded image bytes → libvips decoder | Untrusted binary is decoded and resized in a NIF. |
| anonymous browser → LiveView at `/` | Fully public, unauthenticated request path (CATALOG-08). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-08 | Information Disclosure | XML external entity expansion in `BggClient.parse_items/1` | high | mitigate | Parse with SweetXml's `dtd: :none` option so `xmerl_scan` neither resolves external entities nor expands internal ones. Without this, a hostile or MITM-corrupted response could read local files off the seed machine (which holds the R2 write credentials) or drive an outbound request. |
| T-01-09 | Spoofing / Information Disclosure | Server-side fetch of image URLs parsed from the BGG response (SSRF) | high | mitigate | `ImagePipeline.process/3` rejects any URL whose scheme is not `https` or whose host is not in the `["cf.geekdo-images.com", "boardgamegeek.com", "www.boardgamegeek.com"]` allowlist, before any request is issued. The seed machine can reach a developer's local network and cloud metadata endpoints; the allowlist is what keeps a poisoned `<image>` element from reaching them. |
| T-01-10 | Denial of Service | Oversized image download / decompression bomb into libvips | medium | mitigate | `Req` download capped at 15 MB via `max_length`, plus a `content-type: image/*` check before the bytes are handed to `Image.thumbnail/3`. Bounds both network and NIF memory on a seed run that must also fit a modest developer machine. |
| T-01-11 | Information Disclosure | R2 write credentials in logs or crash reports during the seed run | high | mitigate | The mix task logs `Credentials.redacted/1` only, and `R2Storage` passes config as per-call `ExAws` overrides rather than writing them into the global Application environment where a `LiveDashboard` or Sentry payload could surface them. Enforced by 01-01's `@derive {Inspect, only: [...]}`. |
| T-01-12 | Tampering | Stored image URL pointing at a non-club host (CATALOG-09 violation) | medium | mitigate | Every stored URL is minted exclusively by `Credentials.r2_object_url/2`; the acceptance criteria assert zero rows and zero rendered `src` attributes matching `geekdo`/`boardgamegeek`. |
| T-01-13 | Elevation of Privilege | Catalog routes accidentally acquiring an auth requirement | low | accept | The catalog is intentionally, fully public (CATALOG-08). No auth plug is added; the `:browser` pipeline is reused unmodified. Accepted: there is nothing to protect — the data is a public club library listing. |
| T-01-SC | Tampering | package-manager installs | n/a | mitigate | No new package installs occur in this plan; all five dependencies landed and were legitimacy-audited in 01-01 (see that plan's T-01-SC row). |
</threat_model>
