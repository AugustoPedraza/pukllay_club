<objective>
Replace 16 independently-invented per-theme hexes with one shared, algorithmically-generated OKLCh
ramp that both themes reference by `var()`, so a role's colour is a *position on a palette* rather
than a number somebody typed.

Purpose: the developer's own framing example is that light's `btn-primary` fill (`#3D096D`) has no
relationship to any dark-mode token, even though it is dark enough to plausibly BE a dark-mode
surface. Today nothing structurally prevents that drift — the four-task chain
260910-efe → gck → hdc → if9 is a record of exactly this failure mode, ending in a measurement
instrument built to find hexes that had already drifted apart. This task converts "pick the hex
from the ramp" from a comment into an invariant the existing tripwires enforce.

Output: an 11-stop `--pk-ramp-*` ramp declared once in an unlayered `:root` block; daisyUI's
`--color-*` slots rewired as `var()` reads into it for every role the contrast budget allows; a
committed, re-runnable ramp generator/auditor; and the three hex-parsing verification gates taught
a one-hop dereference that hard-fails rather than silently passing.
</objective>

Two facts to carry into Task 2:

1. **Light's `--color-primary` is already at the gamut wall.** `k_eff = 1.00`. Rotating it to
   H313.1 while holding both L and C is not representable in sRGB — the locked hue move
   (D-HueMove) necessarily costs a small chroma reduction as well. This is expected, not a defect.
2. **The shipped palette is not a constant-k family.** `k_eff` runs 0.22 to 1.00. A single ramp at
   `k ≈ 0.85-0.9` is close to the *dark base ladder + dark primary* curve and materially more
   saturated than everything else. That is the mechanism behind the modest reuse count Decision 1
   exists to surface — it is arithmetic, not a shortfall in effort.

- **D-Reuse** — Reuse scope is *everything the contrast budget allows*, decided role by role by a
  real contrast/ΔE audit, not pre-restricted to backgrounds. Both the sharable set and the
  contrast-blocked set get reported.
- **D-Architecture** — Approach (b): daisyUI's `--color-*` slots become `var()` reads into
  `--pk-ramp-*` tokens declared once in a plain, unlayered `:root` block, matching
  `--pk-ink-brand`'s existing shape.
- **D-Ramp** — 11 stops, Tailwind-numeric naming `--pk-ramp-50 … --pk-ramp-950`, generated
  algorithmically at fixed hue H313.1 from an L ladder with `C = k · maxC(L, H)`, `k ≈ 0.85-0.9`.
  Hand-nudging is permitted **only at anchor stops**. Not hand-picked from scratch. Not flat chroma.
- **D-HueMove** — Light's `--color-primary` (`#3D096D`, H300.1) moves ~13° onto H313.1 to land on
  the shared ramp. Confirmed, not a checkpoint. The exact final value is re-derived from the ramp;
  research's `~#470E5E` is a sighting shot, not a locked hex.
- **D-InkBrand** — `--pk-ink-brand` is left standing as a pre-existing anchor. Its nearest stop
  (`--pk-ramp-400`) is not byte-identical to the approved `#C791E5`, so per CONTEXT.md's own
  default rule it does not fold in. Annotate the nearest stop in a comment; do not silently fold it.
- **D-Semantics** — `info` / `success` / `warning` / `error` stay off the brand ramp entirely.
- **D-NoFourthCopy** — Reuse `oklch-audit.mjs`'s existing OKLab math. A fourth independent copy of
  sRGB↔OKLab conversion is forbidden.
