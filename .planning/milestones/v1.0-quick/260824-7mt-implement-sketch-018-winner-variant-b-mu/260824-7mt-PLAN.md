<objective>
Implement sketch 018's winning variant B: make the theme toggle read as clearly subordinate to the
footer's social links by fading its rest-state glyph colour, shrinking its glyph size, and toning
its active state down from full primary to a muted primary tint.

Purpose: Closes the design question raised during the `footer-desktop-imbalance` debug session —
the toggle's three icons currently carry the same visual weight as the four social icons, and its
active state can outweigh them entirely. The developer picked variant B on 2026-08-24.

Output: A revised `.pk-theme-toggle` block in `assets/css/app.css` (CSS-only — no markup, no
behaviour, no test changes), plus an implementation note recorded in the sketch's README.
</objective>

<planner_findings>
Read this before Task 1. Six facts below were measured against the shipped code and each one
contradicts or corrects the task brief. Do not re-derive them; do not "fix" them back toward the
brief.

**F1 — There are TWO call sites, not three.** `<.theme_toggle />` appears at
`lib/pukllay_club_web/components/layouts.ex:503` (mobile drawer, inside `.pk-drawer-utility`) and
at `:648` (footer, inside `.pk-footer-theme`). The desktop header has none — this is pinned by an
existing test at `test/pukllay_club_web/components/layouts_test.exs:189`, which asserts
`.pk-nav-inner` carries no `data-phx-theme` attribute at all. The brief's "desktop header nav
(~layouts.ex:503)" is a misread: line 503 IS the drawer. Verify two call sites, not three.

**F2 — Hero icons are `<span>` elements with a CSS mask, not `<svg>`.**
`CoreComponents.icon/1` (core_components.ex:455) renders `<span class={[@name, @class]} />`, and
`assets/vendor/heroicons.js` attaches `mask`, `background-color: currentColor`, and `width`/
`height` to the `hero-*` class. A `-micro` icon resolves to `theme("spacing.4")` = 16px. There is
no `<svg>` element anywhere in the toggle, so the sketch's `.toggle-bare button svg { }` selector
would match nothing and the size lever would silently no-op. Target `.pk-theme-toggle button > span`.

**F3 — The social glyphs are 16px, not 14px, and the toggle glyphs are already 16px too.** All
four social SVGs in `social_links/1` carry literal `width="16" height="16"` attributes, and the
toggle's icons use `class="size-4"` = 1rem = 16px. They are already the same size. The sketch
believed it was closing a 17px-vs-14px gap to reach parity; in shipped reality 14px instead makes
the toggle glyph *smaller* than the social glyph. That serves the design question better than
parity would ("read as clearly subordinate"), so ship 14px — but understand you are producing
subordination, not the parity the sketch's prose describes.

**F4 — `color-mix()` is safe here.** `assets/css/app.css` already uses it in 15 places (the
`.pk-sheet-backdrop` / shadow-alpha idiom). No compatibility investigation is needed and no
fixed-colour fallback is required.

**F5 — Token mapping confirmed** against the header of `.planning/sketches/themes/default.css`:
sketch `--color-text-muted` maps to app `--color-neutral`; sketch `--color-surface` maps to app
`--color-base-200`; `--color-primary` maps straight across.

**F6 — The sketch's 55% fade fails WCAG 2.1 SC 1.4.11 in light theme. Ship 75% instead.**
These are bare icon buttons with no border, background, or fill — the glyph is the sole visual
identifier of the control, so the 3:1 non-text contrast floor applies to it. The footer surface is
`--color-base-200`; the drawer surface is `--color-base-100`. Contrast computed against the footer
surface (the tighter of the two in light theme):

| rest colour                                   | light (#F3ECFA) | dark (#22103A) |
|-----------------------------------------------|-----------------|----------------|
| shipped `--color-neutral` (today)              | 5.34:1          | —              |
| sketch's literal 55% mix                       | **2.25:1 FAIL** | 3.22:1         |
| 70% mix                                        | 2.91:1 FAIL     | —              |
| 72% mix                                        | 3.04:1          | —              |
| **75% mix (ship this)**                        | **3.22:1 PASS** | **4.94:1 PASS**|

Light theme is the binding constraint; the sketch never measured contrast because its variants were
a static mockup. 75% is the nearest value to the sketch's intent that clears the floor in both
themes, and it still reads as a clear step down from the social icons' `--color-neutral` (roughly a
2:1 luminance ratio between the two in light theme). Note this project fixed accessibility findings
on this exact component three days ago (quick task 260821-dah: aria-labels + 44px hit targets) —
shipping a contrast regression on it now would undo that work.

The active-state tint was measured too and needs no adjustment: light resolves to #4D2672 at
9.91:1, dark to #AE8DCF at 6.24:1. In dark theme the active tint sits only ~1.26:1 apart from the
rest colour, so the underline (6.24:1 against the surface) carries the active signal there — which
matches the shipped design's own logic, where the underline was always the primary indicator.

**Scope note — underline geometry stays as-is.** Variant B narrowed the underline using absolute
insets (11px) measured on a 32px-wide demo button. The shipped button is 44px wide (`min-w-11`,
the touch target from 260821-dah), so those absolute numbers do not transfer and a re-derived
value would be an unverified guess. Change the underline's `background` only; leave `left`,
`right`, `bottom`, `height`, and `border-radius` untouched, and raise it as a follow-up at the
Task 2 human check if it now reads too wide against the smaller glyph.

**Test surface.** No test asserts any colour or icon-size value for this component. The four
existing references (`footer_overflow_test.exs:211`, `footer_rhythm_test.exs:169`,
`layouts_test.exs:184-198`) assert structure and attributes only, so none should need editing. If
any of them fails, stop — it means markup changed, and this task must not change markup.

Five declaration-level edits, applied in place:

1. Rest colour. On `.pk-theme-toggle button`, replace the `color` value `var(--color-neutral)`

2. Glyph size. Add a new rule immediately after the button rule, selector
   `.pk-theme-toggle button > span`, declaring `width: 14px` and `height: 14px`. The child-combinator
   `span` selector is mandatory and non-negotiable — see F2 and F3. Raw px is consistent with this
   file's existing idiom (`.pk-footer-social a` is declared in px right above).

3. Hover affordance. Add a new rule `.pk-theme-toggle button:hover` declaring
   `color: var(--color-base-content)`. This is the fourth declaration in variant B's own rule set
   (the sketch's `--color-text` maps to `--color-base-content` per F5). The shipped component has no
   hover rule at all today; a faded control needs an explicit response to pointer. Do NOT add a
   `:focus-visible` rule — focus rings on this component were deliberately tuned by 01-07's G-01-7
   fix and are out of scope here.

4. Active colour. In the three-selector `[data-theme-source=...]` group that sets `color`, replace
   `var(--color-primary)` with `color-mix(in srgb, var(--color-primary) 65%, var(--color-neutral))`.
   Leave all three selectors byte-identical.

5. Active underline colour. In the matching three-selector `::after` group, replace the `background`
   value `var(--color-primary)` with the same
   `color-mix(in srgb, var(--color-primary) 65%, var(--color-neutral))` expression. Leave `content`,
   `position`, `left`, `right`, `bottom`, `height`, and `border-radius` exactly as they are — see the
   scope note in planner_findings.
