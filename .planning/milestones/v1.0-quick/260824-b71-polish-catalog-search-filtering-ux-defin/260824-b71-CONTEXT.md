# Quick Task 260824-b71: Polish catalog search filtering UX - Context

**Gathered:** 2026-08-24
**Status:** Ready for planning

<domain>
## Task Boundary

Polish catalog search filtering UX: define filter mechanics (open/close/cancel/confirm/CTA
semantics), fix inaccurate/unclear filter content, remove desktop scroll (desktop modal should fit
without scrolling since space isn't constrained), and design a matching mobile adaptation (evaluate
bottom sheet vs modal).

Scope is `lib/pukllay_club_web/components/filter_modal.ex` (stateless `Phoenix.Component`) and its
caller `lib/pukllay_club_web/live/catalog_live/index.ex` (owns all filter assigns/`handle_event`s).
Facet source data (`lib/pukllay_club/catalog/vocabulary.ex`, `lib/pukllay_club/catalog.ex`'s
`facet_options/0`) is out of scope — the glossary content itself is correct and locked
(`01-VOCABULARY.md`); only how it's *presented* in the filter surface is in scope.

</domain>

<decisions>
## Implementation Decisions

### Apply semantics (open/close/cancel/confirm)
- Keep live-apply: every pill click / number input / search keystroke still applies immediately via
  the existing `phx-change`/`phx-click` events (`"search"`, `"toggle-facet"`, `"set-scalar"`) — no
  staged/draft filter state, no new plumbing in `CatalogLive.Index`.
- X button, backdrop click, and Escape all just close — none of them revert anything, because
  there's nothing staged to revert. This is unchanged from today's actual behavior.
- **New:** add a primary "Ver N juegos" CTA button in a footer, using the live `@total` count
  (already computed, currently rendered as a mid-modal text line via
  `CatalogLive.Index.result_count_text/1`). This button's only behavior is to close the modal
  (`phx-click="close-filters"`) — it is a satisfying way to exit, not a submit/apply action, since
  filtering already happened underneath. This resolves the "missing CTA" complaint without changing
  the live-apply architecture.
- "Limpiar filtros" moves into the same footer, as a secondary action next to "Ver N juegos" (not a
  full-width button above/below it as today), disabled when no filters are active.

### Facet content & hierarchy
- Promote Jugadores, Duración máxima, and Nivel (weight band) to primary, always-visible chip-style
  clusters at the top of the modal body — these are the same facts already surfaced as pills on
  every game card/detail page (`pillsRowHTML` equivalent in this app), matching the priority
  established in `.planning/sketches/008-filter-search-ui` (Round 4 onward) and never carried into
  the shipped component.
  - Jugadores and Duración máxima currently render as bare `<.input type="number">` fields under a
    generic "Otros filtros" heading at the very bottom — convert these to a small fixed set of
    chip-toggle options (e.g. common player-count bands, common duration bands) consistent with how
    Nivel already renders, rather than free-number inputs. Exact bucket values are a planning-time
    detail informed by the real catalog's player/duration distribution — not fixed here.
  - **Superseded 2026-08-24:** drop the age/min_age filter entirely — no UI control for it anywhere
    in the filter surface. Explicit user correction, given mid-execution: difficulty (the `Nivel` /
    weight_bands facet) is the intended substitute for whatever an age filter would otherwise
    express. This replaces the "keep it as a lower-priority field" decision below (kept struck
    through for the record, not as active guidance): ~~Edad mínima (min_age) has no equivalent
    "pill" precedent on cards/detail pages and no earlier sketch coverage. Keep it, but as a
    lower-priority field (not promoted to the primary cluster) — exact placement (folded into the
    checklist disclosure vs. its own small secondary row) is Claude's discretion at planning time.~~
- Destacados (editorial hashtags: #CreaConexiones/#EquipoGanador/#DuelosMemorables) stays a
  secondary, always-visible cluster below the primary group — smaller heading, same as it is today,
  just repositioned relative to the newly-promoted primary group.
- Mecánicas (35 options) and Temáticas (32 options) — currently two separate full flat pill walls —
  collapse into one disclosure ("Buscar por mecánica o temática ›" or equivalent copy, exact wording
  is Claude's discretion) containing a searchable checklist per earlier validated pattern
  (`.fm-checklist`: fixed search input on top, scrollable checkbox list below, ~160px max-height).
  Collapsed by default; auto-expands on open if either facet already has an active selection, so
  re-opening the modal never hides an active choice. Selection count shown as a small suffix on the
  section label (e.g. "Mecánicas (2)").
- Whether Mecánicas and Temáticas share one combined checklist or get two side-by-side/stacked
  checklists (mirroring the earlier sketch's Autor/Mecánica 50/50 grid, collapsing to 1 column on
  mobile) is Claude's discretion at planning time — either satisfies the hierarchy decision above.

### What "no scroll" means
- Soft rule: the primary cluster (Jugadores/Duración/Nivel), the secondary cluster (Destacados), and
  the collapsed Mecánica/Temática disclosure trigger (before expansion) must always be reachable
  without scrolling the modal body on desktop.
- A contained internal scroll region specifically for the expanded Mecánica/Temática checklist list
  (the ~160px `overflow-y: auto` list, not the whole modal) is expected and acceptable — this is not
  a violation of "no scroll." The modal's outer body (`.modal-box`/`.filter-modal-body` equivalent)
  should not need its own scrollbar in the common case (checklist collapsed, or even expanded, given
  its bounded internal height).

### Mobile adaptation
- One `filter_modal.ex` component serves both desktop and mobile — no separate mobile component, no
  duplicated event handlers or facet-rendering logic.
- A single breakpoint-scoped CSS rule (mirroring `.planning/sketches/012-filter-modal-in-shell`'s
  validated `@media (max-width: 640px)` block) flips presentation to a bottom sheet: backdrop aligns
  content to the bottom instead of centering, the panel becomes full-width with only the top corners
  rounded, and `max-height` becomes viewport-relative (~88vh) instead of the desktop centered-dialog
  sizing. The primary/secondary/checklist content and all interaction logic are unchanged between
  the two presentations — only the container's position/shape changes.
- This project uses Tailwind + daisyUI, not the sketch's raw CSS custom-property system — the
  breakpoint split must be re-expressed as Tailwind responsive utility classes (e.g. `sm:` prefixed
  overrides on the `modal-box`) or a scoped `<style>` block if utilities can't express it cleanly.
  Exact implementation mechanism is Claude's discretion at planning time, but the visual/behavioral
  target (centered dialog ≥640px, bottom sheet <640px, same markup) is locked.

### Claude's Discretion
- Exact player-count and duration bucket values/labels for the new primary chip clusters.
- Exact copy for the Mecánica/Temática disclosure trigger and any section micro-labels.
- Whether Mecánica/Temática render as one merged checklist or two checklists side by side.
- Placement of Edad mínima (min_age).
- Whether the breakpoint split is implemented via Tailwind utilities or a scoped `<style>` block.
- Whether the search input (`q`) and result-count line stay in their current position above the
  primary cluster, or move — not raised as a gray area, current position is fine unless it conflicts
  with the new layout.

</decisions>
