<objective>
Replace the fixed `LIMIT 20` cap on the 8 home-page carousel rows with real in-row horizontal
infinite scroll: as a user scrolls a rail toward its right edge, the next page of that row's
category loads into that same rail, up to a 30-game ceiling, with flat skeleton cards marking
the in-flight fetch. Remove the Ver todo tile and every trace of it.

Purpose: today four of the eight rows hide 90%+ of their category behind a fixed cap. This makes
each rail browsable to a useful depth using the Netflix pattern the user explicitly asked for,
without adding a second navigation surface.

Output: per-row Ecto offset/limit pagination, per-row LiveView streams, an extended
`.CarouselScroll` hook, trailing skeleton placeholders, and the full removal of the Ver todo path.
</objective>

Extend the existing `.CarouselScroll` colocated hook rather than adding a second hook or observer:
it already owns the rail reference, already runs a `ResizeObserver`, and already cancels its
animation frame on teardown, so a second lifecycle would duplicate all of that for nothing. The
framework's own infinite-scroll binding reads `scrollTop` and compares vertical rects — there is no
horizontal equivalent, so a custom trigger is mandatory.

In `mounted()`, alongside the existing click/sync wiring, add a fetch-more trigger: read the row
key and the exhausted flag off the section's data attributes; compute remaining runway as the
rail's scroll width minus its scroll offset minus its client width; fire when that runway falls to
one client width or less. Guard with a `pending` flag set before the push and released ONLY inside
`pushEvent`'s reply callback, and set exhausted from that same reply. Throttle the listener through
`requestAnimationFrame` with its own frame handle (distinct from the arrow-scroll animation's
handle — do not share one variable between two independent loops): a single touch-momentum fling
fires the scroll event far more often than once per frame, and the runway computation forces layout
each time, which is a real jank source on this project's mobile-first target. Register the listener
passively.

`updated()` must re-read the exhausted flag from the data attribute so a server-driven stop is
picked up. `destroyed()` must remove the scroll listener and cancel the new frame handle, matching
the cleanup discipline already in the hook.

Have the hook drive the loading indicator itself, client-side: set a loading data attribute on the
rail when the push goes out and clear it in the same reply callback. Do not route this through a
server assign — the handler is synchronous, so a server-driven flag would be set and cleared inside
one round trip and the placeholders would never actually be visible.

Render the placeholders as permanent trailing children of the rail using the existing
`skeleton_card/1` verbatim (locked by CONTEXT.md — the flat no-shimmer treatment, because appending
new cards is a "content appearing for the first time" moment, not the filter-triggered
repopulation moment shimmer is reserved for). Give each a stable unique id derived from the section
id. Render them unconditionally: LiveView's own documentation states non-stream items in a stream
container can be added and updated but never removed, so a conditional render would put them in the
DOM once and strand them there permanently. Their placement stays trailing for free — when
appending at the end, LiveView inserts new stream items before the first non-stream child.

Toggle their visibility from `assets/css/app.css` only, in the block that already declares the rail
and card geometry. No inline style attribute, no arbitrary Tailwind value, no raw colour — read
`ui-design-system`'s banned list first. Before writing the show rule, check whether the shared card
class already declares a display value and mirror that value rather than inventing a new one, so a
revealed placeholder occupies exactly the footprint a real card does and the rail does not reflow.
Two placeholders is enough — they exist to signal "more is coming", not to reserve a full page,
and the ceiling means at most 10 real cards ever arrive per append.

Do NOT reach for the stream option that bounds container size: it prunes from the beginning of the
container, and removing nodes from the left of a horizontally scrolled rail shifts everything and
produces a visible scroll jump. The 30-item ceiling from Task 1 is the bound.

Add an integration assertion that a rendered rail carries the placeholder markup and the row-key
and exhausted data attributes. Note explicitly in the SUMMARY that ExUnit cannot exercise the
scroll trigger, the pending guard, or scroll-position preservation — those are browser-only.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → LiveView `handle_event` | The `carousel-load-more` payload is fully attacker-controlled; a client can push any row string, at any rate, from a devtools console. |
| LiveView → Postgres | The row key selects a query; an offset selects a page. Only one of those may originate outside the server. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-u5d-01 | Tampering | `handle_event("carousel-load-more", ...)` row key | medium | mitigate | Literal-string dispatch in `row_query/1` with a final catch-all returning nil (T-01-37 convention); the handler binary-guards the payload and looks it up against the server's own row list. No atom is ever built from client input, so no atom-table exhaustion and no arbitrary query selection. Covered by the unknown-key unit test and the unknown-row integration test in Task 1. |
| T-u5d-02 | Denial of Service | Per-socket carousel query volume | medium | mitigate | Offset is server-held state, never accepted from the client. Client-side rAF throttle plus the `pending` flag suppress the storm before it leaves the browser. |
| T-u5d-03 | Denial of Service | Per-socket memory on a 1 GB e2-micro | medium | mitigate | Streams transmit only new items rather than re-sending the whole row on each append (a comprehension would re-send every entry's dynamics). | T-u5d-04 | Information Disclosure | Carousel game data | low | accept | The catalog is fully public by requirement (CATALOG-08). Pagination exposes no field the first page did not already expose, and no per-user data exists on this route. |
