## Summary

This phase adds documentation (AGENTS.md), a dev-only `DATABASE_URL` override for the
production re-seed runbook (`config/dev.exs`), a compile-time `secure:` cookie gate
(`lib/pukllay_club_web/endpoint.ex`), and four new/expanded test files pinning session-cookie,
CSRF-meta-tag, CSP-directive, and seed-upsert-idempotency behavior.

I traced each change against the code it exercises rather than trusting the tests' own framing:

- `endpoint.ex`'s `secure: Mix.env() == :prod` is a module attribute, so it is genuinely
  resolved at **compile** time and gets baked as a literal into the release — the comment's claim
  ("not a runtime env-var read") checks out, and this correctly avoids the Safari-localhost-Secure-
  cookie footgun the comment describes.
- The new CSP-directive tests in `catalog_live_test.exs` were checked against the actual
  `PukllayClubWeb.CSP.policy/0` implementation (`lib/pukllay_club_web/csp.ex`) — all ten pinned
  directive strings and the directive count match exactly; these are not vacuous/self-fulfilling
  assertions.
- `test/pukllay_club_web/liveview_csrf_test.exs`'s claim that `root.html.heex` emits the
  `<meta name="csrf-token">` tag was verified directly in the layout template — confirmed present.
- `upsert_idempotency_test.exs`'s assumptions about `Catalog.upsert_game!/1` (`conflict_target:
  :csv_row`, `on_conflict: {:replace_all_except, [:id, :inserted_at, :search_vector]}`) were
  checked against `lib/pukllay_club/catalog.ex` — the exclusion list and conflict target match,
  and Postgres/Ecto's `ON CONFLICT ... DO UPDATE ... RETURNING` semantics genuinely return the
  pre-existing row's `id`/`inserted_at`, so the "same primary key, preserved inserted_at"
  assertions are testing real behavior, not asserting something the test setup itself guarantees
  independent of the code under test.

One robustness gap in `config/dev.exs`'s new `DATABASE_URL` override is worth fixing (see
Warnings) — the file's own comment explicitly worries about a developer accidentally leaving
`DATABASE_URL` exported into a shell profile and silently retargeting an unrelated `mix test` or
`mix ecto.migrate` run at production, but the code that implements the override adds no runtime
signal (log line, banner) when it is active, so that exact accident would be invisible until
something goes wrong.

## Warnings

### WR-01: Dev `DATABASE_URL` override is silent — no runtime signal when active

**File:** `config/dev.exs:35-48`
**Issue:** When `DATABASE_URL` is set, `config/dev.exs` silently switches
`config :pukllay_club, PukllayClub.Repo` from the hardcoded local target to the env-var-provided
one. Nothing prints a warning, host, or database name to the console when this happens. The
comment block directly above this code (lines 27-34) explicitly names the exact risk this
enables — "An exported value silently retargets every later `mix` invocation in that shell,
including an unrelated local `mix test` or `mix ecto.migrate` run, to production" — but the
implementation does nothing to make that retargeting *visible* at the moment it happens. A
developer who forgot they `export`ed `DATABASE_URL` earlier in a terminal session (or sourced it
from a stale `.envrc`/profile) gets no signal before `mix test` or `mix ecto.migrate` runs against
whatever `DATABASE_URL` points at — which, per the AGENTS.md runbook this same phase adds, could be
a production database reached through an SSH tunnel.
**Fix:** Emit a clearly-visible, credential-free notice when the override is active, e.g.:
```elixir
database_url = System.get_env("DATABASE_URL")

if database_url do
  uri = URI.parse(database_url)
  IO.puts(:stderr, "\n*** DATABASE_URL override active: connecting to #{uri.host}#{uri.path} — NOT the local dev database ***\n")
end
```
placed right after `database_url` is read, so every `mix` command that loads this config prints
the target host/db (never the embedded credentials) before doing anything else.

## Info

### IN-01: `attrs/2`'s `overrides` parameter is unused across the whole test file

**File:** `test/pukllay_club/catalog/seed/upsert_idempotency_test.exs:21-49`
**Issue:** `defp attrs(csv_row, overrides \\ %{})` merges `overrides` into the fixture map, but no
test in this file ever calls `attrs/2` with a second argument — every call site is `attrs(row)`.
This isn't wrong, but it's speculative generality: a parameter that exists for hypothetical future
tests, carried in a file whose own moduledoc emphasizes precision (proving idempotency on specific
fields). If a future test does need overrides, that's the moment to add the parameter with a
concrete caller.
**Fix:** Either drop the `overrides` parameter until a real caller needs it, or add a short comment
explaining why it's kept ahead of use (e.g., "kept for the next test that fixture-varies a single
field without repeating the whole map").
