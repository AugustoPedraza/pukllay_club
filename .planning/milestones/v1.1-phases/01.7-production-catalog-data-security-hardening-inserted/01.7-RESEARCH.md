## Summary

This phase has two independent halves, both verification-and-fix work against an already
substantially-built app rather than net-new architecture. The **data half** (SEED-01/02) moves the
~400-game catalog that already exists, verified live in this session, in the developer's local
Postgres database (434 rows, `pukllay_club_dev`) into production's currently-empty `games` table via
a single-table `pg_dump --data-only` over an SSH tunnel to the Kamal DB accessory's
localhost-bound port — never by re-running BGG/Gemini/R2 enrichment against production. The
**security half** (SEC-01..04, AUDIT-01/02) is four independently-verifiable checkpoints against
code this session read directly: a session cookie missing `secure: true`
(`lib/pukllay_club_web/endpoint.ex:7-12`), an HSTS header that is almost certainly *already*
correctly emitted by `Plug.SSL`'s defaults (`config/prod.exs`'s `force_ssl` block has no `hsts:`
override, and `Plug.SSL`'s own hexdocs — fetched directly this session — confirm `:hsts` defaults to
`true` with a 1-year `max-age`), a CSP (`lib/pukllay_club_web/csp.ex`) that is already close to ideal
(`script-src 'self'`, no `unsafe-eval`, `frame-ancestors 'none'`) and needs an audit-only pass, and
LiveView CSRF wiring (root layout `<meta name="csrf-token">` + `assets/js/app.js`'s
`params: {_csrf_token: csrfToken}` + `endpoint.ex`'s `connect_info: [session: @session_options]`)
that is already correctly in place and needs a live-reconnect verification, not new code.

The one genuinely new implementation surface is the **sequence resync risk** on the games-table
restore: the `games.id` column is an Ecto-default `bigserial`, and while `pg_dump --data-only
--table=games` does include the owning sequence's `setval()` command by default (confirmed via
research this session, not assumed), the plan must make this an explicit, grep-verified checkpoint
before restoring — a `pg_dump` invocation that silently drops or short-circuits the `setval()` line
(e.g., a hand-edited SQL file) would leave the production sequence behind the highest restored `id`,
causing a primary-key collision on the very next insert (a future `mix catalog.seed` re-run, or any
`INSERT`). `games`' `search_vector` column is `GENERATED ALWAYS ... STORED`; `pg_dump` automatically
excludes generated-column data from `--data-only` output (standard Postgres ≥12 behavior) and
Postgres recomputes it from `name`/`designers`/`publishers` on restore — no special handling needed,
but worth stating explicitly so a future editor doesn't try to dump/restore it by hand.

**Primary recommendation:** Treat SEED-01/02 and SEC-01..04/AUDIT-01/02 as five independently
verified checkpoints (data restore + 4 security items), each with its own runtime/`curl`/live-browser
proof — not one "did the security stuff" checkbox. Gitleaks is not currently installed in this
environment and must be fetched (static binary, no package-manager step required) before AUDIT-01
can run.

### Pattern 1: Single-table data-only restore with explicit sequence verification

**What:** `pg_dump --data-only --table=games <dev_db> | psql <tunneled prod connection>` — restrict
to one table, verify the sequence `setval()` line is present in the dump *before* restoring.

**When to use:** Any time production's `games` table needs to be (re-)populated from a trusted,
already-enriched dev database rather than a fresh BGG/Gemini/R2 pipeline run (D-01).

**Example:**
```bash
# From the developer's laptop, in one terminal — open the tunnel and leave it running:
ssh -L 5432:localhost:5432 deploy@34.41.63.138

# In a second terminal — dump the dev table (data only, not schema; production
# already has the matching schema via its own migration history):
pg_dump --data-only --table=games \
  -h localhost -U postgres pukllay_club_dev \
  > games_data_only.sql

# VERIFY before restoring — the sequence setval must be present:
grep -c "setval" games_data_only.sql   # expect >= 1

# Restore through the same tunnel, against the production database name:
psql -h localhost -p 5432 -U postgres pukllay_club_prod < games_data_only.sql

# Confirm row count and sequence health after restore:
psql -h localhost -p 5432 -U postgres pukllay_club_prod \
  -c "SELECT count(*) FROM games;" \
  -c "SELECT last_value FROM games_id_seq;"
```

### Pattern 3: `secure:` env-gated session cookie, not an unconditional flag

**What:** `Plug.Session`'s `secure: true` option must be `Mix.env() == :prod` (or an equivalent
runtime check), never a bare `true` — this is a **compile-time** decision (`@session_options` is a
module attribute evaluated once), so `Mix.env()` (compile-time) is correct here, not a runtime env
var read.

**Why:** Safari does not exempt `localhost` from the Secure-cookie-requires-HTTPS rule the way
Firefox/Chrome do (per PITFALLS.md, cross-checked against this project's own established dev-machine
testing pattern) — an unconditional `secure: true` would silently break session/CSRF continuity for
any developer testing locally in Safari, and the failure mode (LiveView reconnect loop) is much
harder to diagnose than a clear compile error.

**Current code, read directly this session** (`lib/pukllay_club_web/endpoint.ex:7-12`):
```elixir
@session_options [
  store: :cookie,
  key: "_pukllay_club_key",
  signing_salt: "NLUjW6HL",
  same_site: "Lax"
]
```

## Common Pitfalls

### Pitfall 1: Sequence not resynced after a data-only restore (silent, delayed failure)

**What goes wrong:** If the `games_id_seq` sequence isn't advanced to match the highest restored
`id`, the *next* `INSERT` (e.g., the very first future `mix catalog.seed` re-run adding a new game,
or any manual insert) will attempt to reuse an `id` value already present in the restored data,
raising a primary-key unique-constraint violation. This will not surface at restore time — it
surfaces later, at the next write, making it a delayed and confusing failure.

**Why it happens:** `pg_dump --data-only` *does* include the sequence's `setval()` command by
default (confirmed via research this session against official Postgres documentation) — but a
hand-edited dump file, a `--table` flag scoped to exclude a dependent sequence, or an interrupted
restore could silently drop that line, and nothing in a naive restore workflow would surface the
omission until the next write fails.

**How to avoid:** Treat "the `setval()` line is present and was executed" as an explicit,
grep-verified checkpoint (Pattern 1's `grep -c "setval"` step) — not an assumption. After restore,
explicitly query `SELECT last_value FROM games_id_seq;` and compare against `SELECT max(id) FROM
games;` to confirm `last_value >= max(id)`.

**Warning signs:** A future `mix catalog.seed` run (or any new game insert) fails with
`duplicate key value violates unique constraint "games_pkey"`.

### Pitfall 2: Assuming HSTS "isn't set up yet" and adding a redundant custom header

**What goes wrong:** A hardening pass that doesn't first check `Plug.SSL`'s actual defaults might
add a hand-rolled `strict-transport-security` header via a new plug, potentially conflicting with
or duplicating the one `force_ssl` already emits, or accidentally setting a weaker value (e.g., a
short `max-age`) than the framework default.

**Why it happens:** `config/prod.exs`'s `force_ssl` block (read directly this session) has no
explicit `hsts:` key visible in the config — it's easy to read "not visible" as "not set," when
`Plug.SSL`'s own defaults (`hsts: true`, `expires: 31_536_000`) already apply because they weren't
overridden to `false`.

**How to avoid:** Verify with `curl -I https://pukllay.club/` first — SEC-02's actual work is very
likely confirming a header that's already correct, then documenting that fact, rather than adding
new code. Only add an explicit `hsts: true` to `config/prod.exs` if the live `curl` check shows the
header is *actually* missing (which would indicate something else is wrong — e.g., `force_ssl` not
being applied to the response, worth investigating rather than papering over).

**Warning signs:** `curl -I` shows no `strict-transport-security` header at all despite `force_ssl`
being present in config — investigate *why* before adding a redundant plug.

### Pitfall 3: CSP tightening breaks the Maps `frame-src` or Tailwind `style-src`

Documented at length in `research/PITFALLS.md` Pitfall 6 (read directly this session) — the CSP's
only third-party origin (`frame-src`, derived from `ClubLinks.maps_embed_origin/0`) and its
`style-src 'unsafe-inline'` are both deliberate, previously-debugged decisions (G-01.4-4,
`.planning/debug/resolved/G-01.4-4-maps-thumbnail-approach.md`), not oversights to "clean up." D-08
already locks this as off-limits. **Avoid by:** reading `csp.ex`'s full moduledoc before editing
anything, and re-running (or at minimum manually re-verifying) the About page's Maps embed and
`catalog_live_test.exs`'s existing CSP assertions (read directly this session, lines 1682-1724) after
any CSP-adjacent change.

### Pitfall 4: Missing `secure: true` cookie flag is invisible to Sobelow and to a header-only audit

Documented in `research/PITFALLS.md` Pitfall 5 — `secure:` is a `Plug.Session` **option**, not an
HTTP response header, so a `curl -I` header inspection alone won't catch its absence; it must be
checked via `Set-Cookie`'s attribute list specifically (`curl -I` does show `Set-Cookie`, but the
check must explicitly look for the `Secure` attribute string, not just header *presence*).

**Warning sign:** `curl -I https://pukllay.club/ | grep -i set-cookie` shows a `Set-Cookie` header
without a `Secure` attribute.

### Pitfall 5: git-history secrets sweep run without confirming full-history coverage

Documented in `research/PITFALLS.md` Pitfall 7 — a scan invocation without `--log-opts="--all"` (or
equivalent) may only walk the current branch's reachable history from `HEAD`, which for this
solo-dev, single-branch (`main`) repo is likely *sufficient* on its own (there are no other
branches/forks to miss), but the plan should state explicitly which invocation was used and why it's
believed to cover full history, rather than assert "ran gitleaks" without that detail.

**Common false positive to pre-empt:** `signing_salt: "NLUjW6HL"` in `endpoint.ex:10` (read directly
this session) will very likely be flagged by Gitleaks' entropy heuristics — this is **not** a real
secret; Phoenix's own generator commits this value intentionally (it derives per-purpose keys from
`secret_key_base`, which is the actual secret and which correctly lives only in `.kamal/secrets`/CI,
never in git per `config/runtime.exs:80-85`'s `raise` on a missing env var). Document this
false-positive triage explicitly per AUDIT-02's requirement.

### Pitfall 6: `pg_dump`/`psql` client-vs-server version mismatch direction

**What goes wrong:** Postgres's official compatibility guidance is that `pg_dump`/`psql` clients
support connecting to servers of an *equal or older* major version reliably; connecting an *older*
client to a *newer* server for `pg_dump`'s catalog-aware dump operations is the direction that can
have issues (newer server-side catalog features the older dump tool doesn't understand).

**Why it doesn't bite here:** This session verified the actual versions in play: the dump *source*
is a local Postgres 16.15 server (this session's `pukllay_club_dev`, `SELECT version()` confirmed
directly), dumped with the matching-version 16.15 `pg_dump` client — no version mismatch on the dump
side. The *restore* target is Postgres 17 (`pgvector/pgvector:pg17`, `config/deploy.yml:80`) — but
restoring an **older**-version dump into a **newer** server is the well-supported, standard direction
(this is exactly how major-version upgrades are normally performed). `psql`'s plain-SQL execution
(as opposed to `pg_dump`'s catalog-parsing dump generation) also tolerates cross-version connections
well for basic `INSERT`/`COPY` statements, since the wire protocol itself is stable across versions.

**Verification still needed at execution time:** the developer's actual laptop `pg_dump`/`psql`
client version may differ from this session's sandbox (16.15) — confirm the developer's real client
version is ≤ 17 (the production server's version) before running the dump, since a client *newer*
than 17 attempting `pg_dump` against a v17 server is the well-supported direction, but a client
*older* than the dump source server would not be (not applicable here, since the dump source is 16 in
this session, but the developer's own machine should be independently confirmed at plan/execution
time rather than assumed identical to this sandbox).
