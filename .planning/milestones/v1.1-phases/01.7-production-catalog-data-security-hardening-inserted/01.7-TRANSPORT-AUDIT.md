# 01.7 Transport Security Audit (SEC-01, SEC-02)

Recorded during execution of plan `01.7-02`, 2026-09-11.

## HSTS (SEC-02, T-01.7-05)

Live check against production, before any config change:

```
$ curl -sSI https://pukllay.club/
...
strict-transport-security: max-age=31536000
...
```

`max-age=31536000` is year-scale (10 digits), matching `Plug.SSL`'s own documented default
(`expires: 31_536_000`) — `config/prod.exs`'s `force_ssl` block has no explicit `hsts:` key and was
never overridden to `false`, so the framework default was already correctly active. **No change
made to `config/prod.exs`** — a redundant hand-rolled header plug was deliberately not added
(RESEARCH.md Pitfall 2); doing so risks duplicating or weakening what `force_ssl` already emits.

`includeSubDomains` and `preload` are deliberately absent — see the plan's `<deliberate_exclusions>`
(accepted threat `T-01.7-07`).

## Unexpected finding: the live cookie was already `Secure`, via Plug's own scheme default

`curl -sSI https://pukllay.club/` (same fetch as above) shows:

```
set-cookie: _pukllay_club_key=...; path=/; secure; HttpOnly; SameSite=Lax
```

...even though `main`'s currently-deployed `endpoint.ex` has no `secure:` key at all in
`@session_options` (confirmed via `git show main:lib/pukllay_club_web/endpoint.ex`). This is not a
stale/incorrect observation — it is `Plug.Conn`'s own documented behavior
(`deps/plug/lib/plug/conn.ex`, `maybe_secure_cookie/2`): when a cookie's options do not already
specify `:secure`, Plug defaults it to `true` whenever `conn.scheme == :https`, via
`Map.put_new(cookie, :secure, true)`. Production terminates HTTPS in front of the app and
`force_ssl`'s `rewrite_on: [:x_forwarded_proto]` makes `conn.scheme` read as `:https`, so the
cookie was already implicitly `Secure` in production before this plan's Task 1 change — and
already implicitly *not* `Secure` under `mix test` (test requests run over `:http`, so the same
default resolves to `false`, consistent with this plan's `session_cookie_test.exs` observing no
`Secure` attribute pre- and post-change).

This does not change what Task 1 does or why: relying on an unstated library default is exactly
the kind of implicit behavior SEC-01 asks to make explicit and mechanically assertable
(`session_options/0`) rather than something that only holds "by accident" of Plug's internals and
could silently regress if any future code path explicitly passed `secure: false`. The explicit
`secure: Mix.env() == :prod` key added in Task 1 makes the previously-implicit guarantee a directly
compiled, tested value.

## Post-deploy verification (required — do not run this against a pre-deploy production box)

Task 1's `secure: Mix.env() == :prod` change is a compile-time endpoint change. Its effect on the
**next** production deploy is not observable until this phase's commits land on `main` and CI's
build + Kamal deploy completes — that deploy is outside this plan's execution (this project lands
commits via a branch + PR behind a required CI check; the deploy runs on merge to `main`).

**Do not treat the pre-existing `secure` attribute recorded above as satisfying this check.** That
observation reflects Plug's scheme-based *default*, not this plan's explicit `session_options/0`
contract — the two happen to currently agree, but only the explicit key is asserted by
`session_cookie_test.exs`. Re-run the check below after the deploy that includes this plan's
commits (`21ca839` and `7087e01`, or later) reaches production, to confirm the explicit contract,
not the implicit default.

**Run after the deploy is confirmed healthy:**

1. `curl -sSI https://pukllay.club/` and confirm the `_pukllay_club_key` cookie's attribute list
   includes `secure` (case-insensitive; Plug lowercases it in the raw header, browsers show
   `Secure`).
2. Load the site locally over plain HTTP (`http://localhost:4000`) and confirm a session still
   works normally — navigate between the catalog and a game detail page, use the filters. A broken
   session shows up as a LiveView reconnect loop, not an error message.
3. If testing locally in Safari specifically, check there — it is the browser that does not exempt
   `localhost` from the Secure-cookie-requires-HTTPS rule (T-01.7-20).

**Pass condition:** step 1's cookie carries `secure` AND step 2's local HTTP session still works
normally in every browser tested, Safari included.
