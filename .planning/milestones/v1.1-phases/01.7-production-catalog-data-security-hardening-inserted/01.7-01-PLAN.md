<objective>
Load the real ~400+ game catalog into production's currently-empty `games` table by restoring the
already-validated dev data over an SSH tunnel (D-01/D-03), and prove it end-to-end by fetching a
restored game's own public detail page from the live site.

Purpose: https://pukllay.club currently serves an empty state. Every downstream capability in this
milestone — Phase 01.8's share cards, Rich Results, and sitemap — needs real production data to
demonstrate against. This is also the phase's tracer: it is the one slice that touches every layer
of the data half (local dev Postgres, the SSH transport, the production accessory, the running
Phoenix release, the public HTTPS surface), so if the transport or the restore shape is wrong, that
is discovered in the first task rather than after a runbook has been written on top of it.

Output: production's `games` table populated and sequence-healthy, plus a committed restore record
in the phase directory.
</objective>

<tracer_note>
This plan's Task 1 is the phase's single `type="tracer"` slice. The security half of this phase
(plans 01.7-02, 01.7-03, 01.7-04) introduces no new architecture — it is verification-and-narrow-fix
work against layers Phase 0 and Phase 1 already proved live — so it has no architecture to trace and
runs in parallel in the same wave rather than expanding out of this slice. That is a deliberate,
recorded shape, not an omitted tracer.
</tracer_note>

  <precondition>`ssh -o BatchMode=yes deploy@34.41.63.138 exit` succeeds from this machine (the developer's own key is present in GCP SSH metadata and unexpired — RESEARCH.md Open Question 2 / Assumption A5)</precondition>

  <files>.planning/phases/01.7-production-catalog-data-security-hardening-inserted/01.7-SEED-RESTORE.md</files>
  <action>
    Wire ONE path from the local dev database through to the public site, end to end, in this order.

    Derive the production connection first. Read the gitignored `.kamal/secrets` (already present on
    this machine, listed in `.gitignore` line 42) and parse its `DATABASE_URL` into its four parts:
    role, password, database name, and the in-network host `db`. Do NOT guess the database name and
    do NOT hardcode it — take it from that URL. Hold the password only in a shell variable
    (`PGPASSWORD`); never place it on a command line, never write it into any file, never echo it.

    Open the transport. Start a background local port-forward:
    `ssh -f -N -o ExitOnForwardFailure=yes -L 127.0.0.1:15432:localhost:5432 deploy@34.41.63.138`.
    Bind the local end to `127.0.0.1` explicitly, never `0.0.0.0`. Use local port 15432, NOT 5432:
    this machine already runs a dev Postgres server on 5432 and CONTEXT.md D-04's illustrative
    `-L 5432:localhost:5432` would collide with it. D-04's decision (a manual laptop-side SSH tunnel,
    no CI) is unchanged; only the local port number is chosen here, which RESEARCH.md assigns to plan
    time as an implementation detail. Record the exact tunnel command used.

    Establish the pre-restore fact. Through the tunnel, run a read-only
    `SELECT count(*) FROM games;` against production and record the number. RESEARCH.md Assumption A4
    claims it is 0 but never queried it. If the count is NOT 0, STOP and surface a checkpoint — a
    populated table turns this from an insert-into-empty-table into a merge/replace decision the
    developer has not made.

    Dump the source. From the local dev database run
    `pg_dump --data-only --table=games -h localhost -U postgres pukllay_club_dev` into the session
    scratchpad directory, never into the repository working tree. Then grep-verify the owning
    sequence's `setval` line is present in that file before restoring anything (RESEARCH.md Pitfall
    1) — a dump missing it leaves the production sequence behind the highest restored id and the
    failure surfaces much later, at the next insert. Do not hand-write a sequence reset; verify
    pg_dump's own.

    Restore through the same tunnel with `psql` against the production database name parsed above.

    Prove it live. Pick a restored game whose name contains only ASCII letters, digits and spaces
    (so HTML escaping cannot break a literal match), read its id and name back out of the production
    database, then fetch `https://pukllay.club/juegos/<id>` over plain curl and confirm the name is
    present in the returned HTML. CatalogLive.Show's disconnected mount loads the game via
    `Catalog.get_game!/1`, so the name is in the static server-rendered response — this is the same
    bytes a crawler or a link recipient sees, which is why it is the tracer's end-to-end gate rather
    than a per-layer check.

    Close the tunnel when the gate passes. Do not leave a forward open.

    Create `01.7-SEED-RESTORE.md` in the phase directory recording: the pre-restore count, the dump
    command, the setval verification, the restore command, the post-restore count, and the live URL
    proven. Record commands with the password redacted.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer laptop → production host | SSH into `deploy@34.41.63.138`; everything past this point is production |
| SSH forward → Postgres accessory | The accessory binds `127.0.0.1:5432` only (deploy.yml D-15); the forward is the only reachable path and it is the real access control, since Docker's iptables rules bypass UFW |
| production database → public HTTPS | Restored rows become publicly readable content the moment the restore commits |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01.7-01 | Information Disclosure | SSH local port-forward | high | mitigate | Forward's local end bound explicitly to `127.0.0.1:15432`, never `0.0.0.0`; `ExitOnForwardFailure=yes` so a failed bind never silently falls through to a different port; forward closed as soon as each task's gate passes |
| T-01.7-02 | Information Disclosure | production DB password | high | mitigate | Parsed out of the gitignored `.kamal/secrets` into `PGPASSWORD` in-process only; never on a command line (process table), never echoed, never written to the restore record — the record carries redacted commands |
| T-01.7-03 | Tampering | production `games` table | medium | mitigate | Read-only pre-restore `count(*)` gates the write and halts on a non-zero count; scope restricted to `--data-only --table=games` (D-03) so no schema or migration state crosses environments; sequence resync verified after the restore |
| T-01.7-19 | Information Disclosure | dump artifact | medium | mitigate | Dump written to the session scratchpad only; an automated gate asserts no `.sql`/`.dump` file appears in the repository working tree before commit |
| T-01.7-SC | Tampering | npm/pip/cargo installs | — | accept | This plan installs no package-manager packages. RESEARCH.md's Package Legitimacy Audit records the phase as not-applicable; the only external binary in the phase (Gitleaks) is fetched and checksum-verified in plan 01.7-04, where its own `T-01.7-SC` row lives |
