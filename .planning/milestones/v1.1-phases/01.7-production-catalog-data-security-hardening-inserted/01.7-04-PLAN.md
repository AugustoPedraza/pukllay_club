<objective>
Run a one-time sweep of the repository's full git history for leaked credentials, adjudicate every
hit individually, rotate anything real and still live, and record the whole thing.

Purpose: this repository was flipped from private to public during Phase 0 (D-19). Everything in its
history is readable by anyone who clones it, permanently. The project has been disciplined about
gitignoring real secrets, but "we think we were careful" is not an audit — and the difference matters
now that the site's link is being passed around. A finding adjudicated per hit is the deliverable;
a green summary is not.

Output: a committed audit record carrying the tool version, the exact full-history invocation, one
adjudicated row per hit, and any rotation performed.
</objective>

  <name>Task 1: Install Gitleaks from a checksum-verified release and sweep the full commit history</name>
  <precondition>`gitleaks` is not currently on PATH in this environment (RESEARCH.md Environment Availability verified it absent), so this task installs it before it can run</precondition>

  <action>
    Install the scanner first. Per D-06 this pass uses Gitleaks alone — not Gitleaks plus TruffleHog;
    TruffleHog's live-credential verification is unneeded process for a careful solo one-off sweep.
    Gitleaks ships as a single static Go binary from its own GitHub releases, so there is no package
    manager involved and no `mix.exs`/`mix.lock` change. Resolve the current release tag at execution
    time rather than pinning the version RESEARCH.md happened to see; the durable fact is the install
    mechanism, not the tag.

    Treat the download as a supply-chain surface, because it is. Fetch the Linux x86_64 release asset
    and its published checksums file from the canonical `gitleaks/gitleaks` repository's release
    page, verify the archive against the published checksum, and only then extract and mark it
    executable. Do not pipe a remote script into a shell. Record the resolved tag and the verified
    checksum in the audit record.

    Run the sweep across full history. A scan invocation that walks only what is reachable from the
    current tip can miss objects on other refs; pass the log options that force the walk across all
    refs and full history, and write the machine-readable report to the session scratchpad directory,
    never into the repository working tree. This repo is effectively single-branch, which likely
    makes the difference moot in practice — but AUDIT-01 asks for a full-history sweep, and "likely
    moot" is a claim the record has to state rather than assume. Record the exact invocation string
    verbatim in the audit record so a future reader can reproduce the coverage claim.

    Count the hits and write the skeleton of the audit record: tool version, resolved tag, verified
    checksum, verbatim invocation, hit count, and an empty adjudication table with one row per hit
    keyed by commit, file path, and rule id. Do not put any detected value into the table — the
    columns are commit, path, rule, verdict, reason. The record is going into a public repository.
  </action>

<task type="checkpoint:decision" gate="blocking-human">
  <decision>Which sweep findings are real and still live, and what gets rotated</decision>
  <context>
    The sweep has run and every hit is listed, unadjudicated, in
    `.planning/phases/01.7-production-catalog-data-security-hardening-inserted/01.7-SECRETS-AUDIT.md`.
    Each hit needs one of three verdicts and a reason.

    Rotating a credential is a one-way door: the previous value is permanently invalidated at the
    issuer the moment it happens, and every consumer must be updated in the same pass or production
    breaks. For this project the consumers of a rotated credential are some combination of GitHub
    Actions repository secrets, the gitignored `.kamal/secrets` file plus a redeploy, and the
    developer's gitignored `config/dev.secret.exs`. That coordination is why this is a human
    decision rather than an autonomous step, and it is why this checkpoint does not auto-approve.

    Two things are already decided and are not being re-asked. D-07: a real finding is rotated, and
    git history is NOT rewritten to scrub it — the repository is already public, so the exposure
    horizon for anyone who already cloned it does not change once the credential is rotated, and a
    force-push that invalidates every existing clone is not worth that marginal benefit. D-06:
    Gitleaks alone, no second scanner.

    One hit is expected and is a known false positive: the session signing salt committed in
    `lib/pukllay_club_web/endpoint.ex` is a Phoenix generator value that the framework commits
    intentionally. It derives per-purpose keys from `secret_key_base`, which is the actual secret and
    which lives only in the deploy secrets and CI — `config/runtime.exs` raises at boot rather than
    defaulting it. Dismissing that hit is correct; dismissing it without writing down that reasoning
    is what AUDIT-02 exists to prevent.
  </context>
  <options>
    <option id="rotate-live-only">
      <name>Rotate only the hits triaged as real-and-still-live</name>
      <pros>Smallest coordinated change; matches D-07's stated policy exactly; each rotation has a concrete justification in the record</pros>
      <cons>Leaves anything triaged as inert-historical unrotated on the triage's judgement alone — if that judgement is wrong about a credential still being accepted by its issuer, the exposure stays open</cons>
    </option>
    <option id="rotate-live-and-historical">
      <name>Rotate the real-and-live hits plus anything historical that still resolves to a real issuer</name>

      <cons>More consumers to update in one coordinated pass, more chances to break production or CI, and more one-way doors walked through than the findings strictly justify</cons>
    </option>
    <option id="no-rotation">
      <name>No rotation — every hit triaged as false-positive or inert-historical</name>
      <pros>Nothing to coordinate; correct outcome if the project's gitignore discipline genuinely held throughout its history</pros>
      <cons>Only valid if every hit really is adjudicated as not-live; must not be selected as a shortcut past triage, and the record has to carry the per-hit reasoning that justifies it</cons>
    </option>
  </options>
  <resume-signal>Select: rotate-live-only, rotate-live-and-historical, or no-rotation — and for whichever you pick, confirm the specific hits it applies to</resume-signal>
