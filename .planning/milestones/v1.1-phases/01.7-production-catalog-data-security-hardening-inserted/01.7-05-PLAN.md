<objective>
Make the documented re-seed path real: give the development Repo an explicit, opt-in way to target
the tunnelled production database, prove the seed's write step is genuinely idempotent, and write the
runbook that ties both together — for the one-time restore plan 01.7-01 just performed and for every
future re-seed.

Purpose: SEED-01 got data into production once. SEED-02 is the part that makes it repeatable by
someone who is not the person who did it the first time, without that person ever putting BGG, R2 or
Gemini credentials on the production host. Right now the documented path does not actually work: the
development Repo is hardcoded to the local database, so "point DATABASE_URL at the tunnel" has
nothing to point at.

Output: an env-var-first dev Repo target, an idempotency gate on the upsert, and the AGENTS.md
runbook (D-05).
</objective>

<task type="auto" tdd="true">
  <name>Task 2: Prove the seed's write step is content-idempotent on its conflict target</name>
  <files>test/pukllay_club/catalog/seed/upsert_idempotency_test.exs</files>
  <behavior>
    - Calling `Catalog.upsert_game!/1` twice with the same attributes leaves exactly one row in the games table.
    - The second call returns the same primary key as the first — it updates rather than inserting.
    - Every content field the second call wrote is equal to what the first call wrote.
    - `inserted_at` is preserved across the second call, while `updated_at` is allowed to move.
    - Two different conflict-target values produce two distinct rows, so the idempotency comes from the conflict target rather than from the upsert never inserting.
  </behavior>
  <action>
    Write this test first and watch each assertion fail for the right reason before it passes.

    `Catalog.upsert_game!/1` is the single write primitive every seed and backfill task funnels
    through, and its conflict target is the CSV row identifier rather than the BGG identifier — a
    deliberate Phase 01-03 decision that also preserves the two legitimate duplicate-BGG-identifier
    rows in the club's catalog. That is the exact property SEED-02's "a second run is idempotent"
    rests on, and nothing currently asserts it. Cover the behaviours listed above.

    Build the attribute map from a fixture rather than a real BGG fetch — this test must run in the
    normal suite with no network and no credentials. Include at least one array-typed field and the
    description field among the content comparisons, since those are the columns a re-seed is most
    likely to silently reshape.

    Do not assert on the generated search vector column: it is a stored generated column that Postgres
    recomputes from other columns, and the upsert deliberately excludes it from replacement alongside
    the primary key and `inserted_at`. Asserting on it would couple this test to a derivation rather
    than to the idempotency property.

    Place the file under the existing seed test directory so it sits with the other seed-pipeline
    tests rather than in the top-level catalog test file.
  </action>
