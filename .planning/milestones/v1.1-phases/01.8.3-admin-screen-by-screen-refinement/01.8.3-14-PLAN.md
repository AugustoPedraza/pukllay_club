<objective>
Close `G-01.8.3-4c`: make focus return to the control that opened a sheet, without undoing the
sheet→dialog handoff the current guard exists to protect.

Purpose: this gap was NOT reported by the developer. It was found by widening the investigation past
the reported symptom, as `G-01.8.3-4a`'s own note asked, and it is an independent defect with an
independent cause. `admin_sheet.js:165` guards the restore on the active element being equal to
`document.body`. Measured INSIDE the close-class mutation microtask on the real sheet, the active
element is the ✕ button, NOT `body` — so the condition is false when it runs, `this.lastFocused.focus()`
is never reached, and the active element settles to `body` at the next style recalc with nothing
listening. The other two conditions would both have passed: `lastFocused` is the `+`, and it is still
in the document.

Proven twice. On the real sheet, with a spy MutationObserver registered on the overlay's class so it
runs in the same microtask as the hook's own and immediately after it: at the close mutation the open
class is gone, the active element inside that microtask is the button labelled Cerrar, it settles to
`body` afterwards, and `#juegos-add-action` is still in the document. And in isolation with no app code:
a focused button inside a div that gains `display: none` via a class reads as the button inside the
MutationObserver microtask and as `body` only after two animation frames.

The guard's own comment (`admin_sheet.js:150-163`) justifies itself with "the browser's own
removal-of-focused-element behaviour resets `document.activeElement` to `body` synchronously". That is
TRUE for the DOM-REMOVAL path it was written for — `staff_live`'s `:if={@selected_staff}` pattern, the
case plan 01.8.2-12 Task 3 was fixing — and FALSE for a stay-mounted `open={...}` sheet that closes via
`display: none`. So a fix for the sheet→dialog focus handoff silently disabled focus-return for every
class-toggle call site. Measured: active element after Escape-close `body`, after ✕-click close `body`,
expected `#juegos-add-action`.

And no test asserts the active element after a sheet close. That absence is why it shipped.

Output: one condition expressed as the property it needs rather than as a coincidence of timing, a
rewritten comment that is true of both close paths, and two assertions — one recorded failing, one
recorded passing as the non-regression baseline.

## The shape of the relaxation, and why it needs no deferral

The property the restore actually needs is: **has anything OUTSIDE this overlay claimed focus?**

- Class-toggle close: at `onClose` the active element is the ✕, which IS inside this overlay's own
  root. Nothing else claimed it → restore. Correct.
- DOM-removal close: at `destroyed()` the active element is already `body`. Nothing claimed it →
  restore. Correct, and unchanged from today.
- Sheet→dialog handoff: LiveView mounts the new dialog's hook and runs its own `onOpen` — which focuses
  Cancelar — BEFORE destroying this sheet's hook, confirmed empirically by instrumenting both callbacks.
  At `onClose` the active element is Cancelar, which is inside a DIFFERENT overlay root. Something
  claimed it → decline. Correct, and this is exactly what plan 01.8.2-12 Task 3 protects.
- User clicked some unrelated background control before the close: the active element is outside this
  overlay → decline. Correct, and strictly better than today, which would also decline but only by
  accident of not being `body`.

All four resolve correctly from the state available SYNCHRONOUSLY at `onClose`. No animation-frame
deferral is needed, and none is added: a deferral would introduce a window in which a later `onOpen`
could interleave, which is the class of bug the original guard was written to prevent.

## Recorded planning choices

- **The condition is the whole change.** No new listener, no new timer, no new state. `lastFocused` is
  still captured in `onOpen` and still cleared exactly once.
- **Plan 13's lock release shares `onClose`.** Both run there now. The release is already guarded by a
  per-instance flag and the restore is already guarded by `lastFocused` being cleared, so neither can
  double-fire — but the guard must re-assert plan 13's whole scroll-lock walk in the same run rather
  than reasoning about it.
- **The handoff test must be recorded PASSING before the change as well as after.** A regression guard
  with no before-baseline cannot distinguish "still works" from "never exercised".
- **The focus-trap structural limitation stays recorded, not repaired** (plan 13's Task 3 records it):
  `admin_sheet.js:177-182` only prevents default at the exact first or last focusable inside the panel,
  so if focus ever reached the background Tab would walk 408 unguarded controls. No faithful user path
  to that state was found and manufacturing one with a programmatic focus call is the documented
  fabrication trap.
- **API coverage:** `COVERAGE.md` declares `No external API integration`.
- **Package legitimacy gate: not applicable.** No package-manager install; `mix.exs` unchanged.
  `T-01.8.3-SC` stays closed.
