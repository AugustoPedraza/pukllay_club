# Phase 01.8.3 Plan 09: Search Cluster Grows With The Viewport, + Lands On The Chevron Axis Summary

**Made `#juegos-search-form` — not the input inside it — the real flex item so the field grows with the viewport (257/272/287px at 360/375/390), and moved `.pk-admin-action--a3`'s leading-icon pull to a trailing-side override on `#juegos-add-action` so the `+`'s glyph lands exactly on the rows' chevron axis (32px) at every width.**

## Accomplishments

- Closed `G-01.8.3-2e`: the search field now grows with the viewport instead of standing at a fixed 264px intrinsic (`size=20`) width at every width, and the `+`'s glyph now lands on the exact same right-hand axis as every list row's chevron (32px, matching D-20b's declared keel) at 360/375/390.
- Root-caused and fixed the real defect: `#juegos-search-input { flex: 1; min-width: 0 }` (`juegos.css:64`) had always been INERT, because the input's real parent is `<form id="juegos-search-form">` (`index.ex:641`), a plain `display: block` element which is itself the flex ITEM of `.pk-admin-juegos-search-row`. A `flex` declaration on a child of a `display: block` parent has no effect on that child — the fix puts `flex: 1; min-width: 0; display: flex` on the FORM instead, which both makes the form itself grow AND turns it into a flex container so the input's own pre-existing `flex: 1` finally does something.
- Fixed the aggravating cause: `.pk-admin-action--a3`'s shared `margin-left: -12px` (`components.css:124`) is a LEADING-icon pull, written so a glyph at the START of a row lands on the content edge. `#juegos-add-action` is a TRAILING action (the row's last flex item), so that pull moved it further FROM the keel rather than onto it. Replaced with an ID-scoped `#juegos-add-action { margin-left: 0; margin-right: calc((18px - 44px) / 2) }` — the magnitude derived from the A3 box's own declared 44px and its glyph rule's own declared 18px (both in `components.css`), not copied as a literal. `.pk-admin-action--a3` itself is unchanged — confirmed via `git status --porcelain -- lib/ assets/css/admin/components.css` printing nothing — since the shared anatomy also backs the sheet's own ✕, which the developer explicitly reported as correct.
- Extended `admin_shell.mjs`'s `measureJuegosKeelAt` (plan 08's viewport-relative measurement function) to additionally collect BORDER-BOX rects for `#juegos-search-input`, `#juegos-add-action`, and the `+`'s own glyph span (located via the same `[class^="hero-"], [class*=" hero-"]` attribute shape the A3 glyph rule itself uses, with a reported fallback to the button's first element child if no such node exists — never a silent box-instead-of-glyph substitution). These are the boxes the shipped probe never read; its existing `searchRow` reading already agreed with the rows at 32/32 and is exactly why the regression shipped past a passing guard.
- Added four new assertions to the Juegos keel loop: Test 1 (positive control — the field's left border-box edge equals the row's content left, proving the cluster's left edge was never the defect), Test 2 (the `+`'s glyph right inset equals the row chevron's own MEASURED right inset, never a literal 32), Test 3 (the `+`'s box doesn't spill past the row's content edge beyond the amount that centres its glyph there, derived from the measured A3 box/glyph widths), and Test 4 (cross-width — the field's width delta between 390/375 and 360 must equal 30px/15px, the assertion that names the inert-`flex` root cause directly).
- Recorded a real RED-before-GREEN transcript pair per this directory's rule 8. The RED run showed Test 2 failing at all three widths (glyph right inset 52/37/67 vs chevron's 32) and Test 4 failing (both deltas measured 0px, field pinned at 264px everywhere) — the two assertions that directly named the shipped defect. Test 1 passed as its positive control. Test 3 did **not** fail in the RED run — see Deviations below for why, and why that is not a problem for this plan's success criteria.
- The GREEN run (after the fix) shows `ALL CHECKS PASSED`: field widths 257/272/287 at 360/375/390 (exact 15px/30px deltas), glyph right inset 32 at all three widths (matching chevron), add-action right inset 19 at all three widths (exactly the derived minimum — no spill beyond the centred-glyph allowance), and every pre-existing check (band/divider from plan 08, tab bar, snackbar, save bar, main padding, overlay coverage) still green in the same run.

## Deviations from Plan

### Informational Finding (not a Rule 1-4 auto-fix)

**1. Test 3 (spill allowance) did not reproduce a failure at 360px in the RED run**
- **Found during:** Task 1, after implementing and running the guard against the unfixed CSS
- **What the plan expected:** The `<action>` and `<done>` prose both state the recorded RED run "must show" Tests 2, 3, and 4 failing, based on the diagnosis's claim that "at 360 the button already spills 8px past the row's own content box."
- **What was actually measured:** `#juegos-add-action`'s right inset at 360 is 24px; the row's content right inset is 32px, so the RAW overhang past the content edge is indeed 8px — matching the diagnosis's own number. But Test 3's literal formula (as specified in `<behavior>`) doesn't flag a raw overhang; it flags an overhang LARGER than the amount needed to centre the `+`'s glyph on that edge — i.e. `addAction.right >= row.right - (addActionWidth - glyphWidth) / 2` = `24 >= 32 - 13` = `24 >= 19`, which holds. I confirmed this allowance (13px) directly against the real, measured, centred-glyph geometry in the RED transcript (glyph left=305/box left=292 → 13px margin on the leading side too), so the formula is internally self-consistent with real rendered geometry, not a math error.
- **Why this is not a bug to fix:** The plan's own "Recorded planning choices" section explicitly flagged this exact uncertainty — "the 360px keel transient... do not assume either [whether it reproduces or disappears]." The diagnosis's raw "8px spill" framing and Test 3's later, more precise "allowance-derived" formula measure two different things; the 8px overhang was always comfortably inside the 13px allowance the centred glyph requires, so this specific guard was never actually violated by the shipped defect — the shipped defect was fully and only captured by Test 2 (glyph off the chevron axis) and Test 4 (field not responsive). Loosening Test 3's threshold to force a RED failure here would have meant asserting a stricter bound than the plan's own stated formula, i.e. manufacturing a defect claim the real rendered page never had — precisely the failure mode this directory's rule 8 discipline exists to prevent from the opposite direction (a guard that never fails proves nothing; a guard tightened past its own stated formula to fail on cue proves something false).
- **Impact:** None on the final result. Test 3 passes in both the RED and GREEN runs (with more margin in GREEN, where the derived minimum is met exactly: 19px). The plan's own success criteria ("no spill at 360... beyond the amount that centres its glyph on that edge") was never actually violated at any point in this plan's execution.
- **Files modified:** None beyond the planned guard code (test/visual/admin_shell.mjs) and CSS fix (assets/css/admin/juegos.css) — no additional changes were made in response to this finding.
