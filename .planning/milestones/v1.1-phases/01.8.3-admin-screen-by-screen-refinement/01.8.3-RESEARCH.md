This phase is a **port**, not a design phase. CONTEXT.md's D-01..D-16 already lock the shape;
the open technical work is entirely in how the existing `Admin.GameLive.Index` render block,
`AdminComponents`, `admin_list.js` and their CSS/test scaffolding must change to reach it. This

**Primary recommendation:** Treat `assets/js/hooks/admin_rail.js` (Estantes' pinned-search

## The `G-01.8.2-4` pinned-caption defect — CONTEXT.md's hypothesis (a) is refuted; the real bug is adjacent

CONTEXT.md D-15 asks the researcher to confirm or refute two candidate contributors. **Both files
were read this session.**

**Contributor (b) — CONFIRMED.** `assets/css/admin/juegos.css:116-118`:

```css
.pk-admin-juegos-section-heading-wrap[data-pinned="true"] .pk-admin-juegos-section-header {
  background: var(--color-surface);
}
```

`background` is set directly on `.pk-admin-juegos-section-header` (the padded box), not on a
`::before` band anchored to the content box. This is exactly what 071's own "What to Avoid"
warns against by name (`admin-juegos.md`: *"Giving the caption its own `background`... gets 26px
of empty tint above the text"*). `[VERIFIED: assets/css/admin/juegos.css:110-118]`

**Contributor (a) — REFUTED as stated, but the underlying window IS real.** CONTEXT.md's claim
is *"the observer fires `pinned` at `entry.boundingClientRect.top < 0` with **no `rootMargin`**
compensating for the heading's sticky `top: 44px`."* Reading `assets/js/hooks/admin_list.js:90-110`
directly:

```js
setupPinObserver() {
  this.pinObserver?.disconnect()
  const sentinels = [...this.el.querySelectorAll("[data-pk-section-sentinel]")]
  if (sentinels.length === 0) return

  this.pinObserver = new IntersectionObserver(
    (entries) => {
      for (const entry of entries) {
        const wrap = entry.target.nextElementSibling
        if (!wrap) continue
        const pinned = !entry.isIntersecting && entry.boundingClientRect.top < 0
        wrap.toggleAttribute("data-pinned", pinned)
      }
    },
    { rootMargin: `-${PAGE_BAR_BAND + 1}px 0px 0px 0px`, threshold: [0, 1] },
  )
  sentinels.forEach((s) => this.pinObserver.observe(s))
},
```

`PAGE_BAR_BAND = 44` (`admin_list.js:32`), so `rootMargin` at line 108 is literally
`"-45px 0px 0px 0px"` — a `rootMargin` **does** exist, and it is correctly sized to compensate
for the 44px sticky offset. `[VERIFIED: assets/js/hooks/admin_list.js:32,90-110]`

**But the second AND-clause defeats it.** `entry.boundingClientRect.top` is always relative to
the *real* viewport (rootMargin only affects when `isIntersecting` flips, never what
`boundingClientRect` reports). A negative rootMargin of `-45px` makes `!entry.isIntersecting`
become `true` once the sentinel's real top passes **y=45** — correctly matching the sticky
header's visual pin point. But the second condition, `entry.boundingClientRect.top < 0`, requires
the sentinel's real top to pass **y=0** — a stricter, later trigger. Because the combined
condition is an AND, the whole expression only becomes true when the *stricter* clause is
satisfied (`top < 0` implies `top < 45`, so `!isIntersecting` is already true by then) — the
rootMargin's compensation is computed correctly but is functionally inert, dominated by the
second clause. The result is exactly the ~44/45px window CONTEXT.md describes (visually pinned
once the sentinel's top crosses 44, but `data-pinned` stays false until it crosses 0) — the
window is real, but the mechanism is "a redundant, over-strict second AND-condition", not
"a missing rootMargin". `[VERIFIED: assets/js/hooks/admin_list.js:104-108]`

**Implication for the port:** the fix is **not** "add a rootMargin" (one already exists and is
correctly computed). The fix is either (1) drop the `entry.boundingClientRect.top < 0` clause
entirely and trust `!entry.isIntersecting` alone (now that rootMargin does the compensation), or
(2) change the threshold from `0` to the same offset the rootMargin uses. Combined with 071's
`::before` band (contributor b), both fixes are needed — the JS fix alone would toggle
`data-pinned` at the right moment, but the CSS fix (`::before` band vs. background-on-the-header)
is what makes the fill read as *centred on the ink* rather than uniformly a translated-but-still-
badly-anchored tint. **Both contributors are real; both need fixing.**

## Two shared-component blast-radius traps CONTEXT.md does not flag

**Trap 1 — `.pk-admin-row`'s `min-height` is shared across 8 admin screens.**
`AdminComponents.list_row/1` is called from `band_audit_live.ex`, `estante_live/index.ex`,
`estante_live/pendientes.ex`, `game_live/form.ex`, `game_live/index.ex`, `section_live/edit.ex`,
`section_live/index.ex`, `staff_live/index.ex` — 8 files.
`[VERIFIED: grep -rln "list_row\|list_section_label" lib/pukllay_club_web/live/admin/, 2026-09-24]`
The shared rule is `.pk-admin-row { min-height: 44px; ... }` (`assets/css/admin/components.css:
301-311`). **D-13 requires 64px rows on Juegos.** Editing `.pk-admin-row`'s shared `min-height`
directly would silently change row height on all 7 other screens, violating D-01's "touches
`/admin/juegos` only" boundary. The existing `juegos.css` file already establishes the correct
precedent for this exact problem — its own row-divider rule is scoped
`.pk-admin-juegos-rows > .pk-admin-row + .pk-admin-row::before` (`juegos.css:200-214`), not a
change to the shared `.pk-admin-row` class. **The 64px min-height must follow the same scoping
convention**: `.pk-admin-juegos-rows > .pk-admin-row { min-height: 64px; }` (or equivalent),
never an edit to `components.css:301-311` itself.

**Trap 2 — `.pk-admin-list-section-label`'s font anatomy is also shared, and Juegos does not
currently override it.** `AdminComponents.list_section_label/1` renders
`<span class="pk-admin-list-section-label">`, styled by the shared rule at
`assets/css/admin/components.css:290-295`: `font-size: 15px; font-weight: 600;` (sentence case,
no letter-spacing). **`juegos.css` does not currently override this class at all** — confirmed
by a full read of `juegos.css` (235 lines, no `.pk-admin-list-section-label` selector present).
D-13 requires `14/600 uppercase, tracked .07em` for Juegos captions specifically. This must be a
new Juegos-scoped rule (e.g. `.pk-admin-juegos-section-header .pk-admin-list-section-label {
font-size: 14px; text-transform: uppercase; letter-spacing: .07em; }`), never an edit to the
shared class, for the same reason as Trap 1 — `estante_live`, `staff_live`, `section_live`, and
`band_audit_live` all render section labels through the same shared component and must keep
their current 15/600 sentence-case rank.
