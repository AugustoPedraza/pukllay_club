The core mechanisms this round shipped are sound on direct inspection:

- **`admin_sheet.js`'s module-level refcounted scroll lock** (plan 13) correctly handles the
  documented sheet→dialog handoff ordering (mount-before-destroy for a different overlay, and — by
  the same mechanism — for a same-id remount): each `onOpen`/`onClose` pair increments/decrements
  independently of instance identity, so the shared counter converges to the correct value
  regardless of interleaving order. The saved-offset read is correctly gated to the first (`0→1`)
  acquire only, so a nested acquire during a handoff cannot clobber it.

  path: the lock release in `onClose` is unconditional (gated only on this instance's own
  `overlayLockHeld` flag) and runs *before* any of the focus-restore logic that the containment test

  paths, single-threaded JS) — no leak, no double-fire found.
- **`admin_pinned_band_test.exs`'s `2 * --bandp` floor** (this round's new assertion) is genuinely
  falsifiable: `declared_bandp_px/1` parses the real `calc()` out of the stylesheet (the prior

## Warnings

### WR-01: plan 10's sheet-body keel compensation is direct-child-only, and two live sheets nest their list rows one level deeper — a new 16px misalignment regression, undetected by this round's own new guard

**File:** `assets/css/admin/components.css:797-821`, `assets/css/admin/estantes.css:348-355`, `test/visual/admin_shell.mjs:1069-1121`

**Issue:**

Plan 10's compensation rule is scoped with a direct-child combinator only:

```css
.pk-admin-sheet__rows > .pk-admin-row,
.pk-admin-sheet__rows > .pk-admin-action--a4 {
  width: calc(100% + 2 * var(--pk-admin-keel-inset));
  margin-left: calc(-1 * var(--pk-admin-keel-inset));
  margin-right: calc(-1 * var(--pk-admin-keel-inset));
}
```

Before this round, `.pk-admin-sheet__rows` carried **zero** horizontal padding, so any `.pk-admin-row`
anywhere inside a sheet's body — direct child or not — landed correctly at 16px from the panel edge
purely from its own `padding: 8px 16px` (`components.css:336`). Plan 10 added
`padding-left/right: var(--pk-admin-keel-inset)` (16px) to `.pk-admin-sheet__rows` itself, and
compensates for it only on rows that are **direct children**.

Two live call sites nest their `.pk-admin-row`s one level deeper, inside a plain, unstyled wrapper
`<div>` with no CSS rule of its own:

- `AdminComponents.placement_sheet/1` (`«¿Dónde va?»`, `donde-va-sheet`) — `#donde-va-estante-list`
  and `#donde-va-results`, both direct children of `.pk-admin-sheet__rows`, each wrapping
  `.list_row`/`.pk-admin-row` elements as **grandchildren**.
- The `«¿Qué juego va acá?»` sheet (`GameLive`'s sibling flow, `estante_live/index.ex:808-846`) —
  `#que-va-aca-unplaced` and `#que-va-aca-results`, identical structure.

For every row inside those four wrappers, the rendered inset is now `16px` (the new body padding,
uncompensated at this depth) `+ 16px` (the row's own padding) `= 32px` from the panel edge — a new,
**this-round-introduced** 16px rightward drift away from the header's 16px axis, on two sheets a
staff member uses on every placement flow.

This is not caught by `checkSheetKeel` (`test/visual/admin_shell.mjs`), the exact sweep this round
extended with a `donde-va-sheet` row (`bodyShape: "mixed"`, lines 787-810) whose own comment already
flags "a body this plan's fix does not fully reach." Two independent structural blind spots in that
sweep both let it through silently:

- **Test 3** (`nothing reaches the panel edge`, lines 1069-1086) excludes any descendant matching
  `.pk-admin-row, .pk-admin-action--a4, .pk-editor-opt` by **class alone**
  (`el.matches(FULL_BLEED_SELECTOR)`), regardless of whether it is actually a direct child that
  received the compensation or a grandchild that did not — so these mis-inset rows are silently
  skipped rather than checked.
- **Test 2** (`ink-vs-ink`, lines 1045-1067) only tracks the **leftmost** ink/control edge in the
  body and compares that single minimum against the header's edge. An element sitting further
  **right** than intended (over-inset, this defect's exact shape) can never be the leftmost
  candidate and is invisible to a leftmost-only comparison — the algorithm can only ever catch a
  descendant poking too far *left*.

Both are instances of `test/visual/README.md` rule 8's own named failure modes ("right axis, wrong
property" and "collected but never asserted") — the sweep measures descendants inside this exact
body and logs them, but no assertion path can fail on this specific shape of defect.

**Fix:** either scope the wrapper `<div>`s themselves to opt out of the body's own padding (e.g. a
shared `.pk-admin-sheet__rows-flush` class applied to `#donde-va-estante-list`/`#donde-va-results`/
`#que-va-aca-unplaced`/`#que-va-aca-results` with `margin: 0 calc(-1 * var(--pk-admin-keel-inset))`
and matching width compensation), or generalize the existing compensation selector to reach
non-direct-child full-bleed rows (`.pk-admin-sheet__rows .pk-admin-row` with a guard against
double-compensating an already-padded ancestor). Either fix should come with a `checkSheetKeel`
change that measures a nested full-bleed row's own ink against the header edge directly (not via
the leftmost-only Test 2, and not skipped by Test 3's class-only exclusion) so this exact shape of
regression cannot recur silently again.

### WR-02: `checkSheetFocusReturn`'s probe-staff-account cleanup has no `try`/`finally` — a thrown error during the guarded walk (most likely exactly when the regression it tests for is present) permanently leaks the throwaway account into the dev database

**File:** `test/visual/admin_shell.mjs:1827-2024`

**Issue:**

Case 3 (`test/visual/admin_shell.mjs:1905-2011`) invites a real, throwaway staff account via the
app's own `/admin/staff` form, then runs the guarded sheet→dialog handoff walk, and only *after*
that walk completes does it reach its own cleanup phase (lines 1992-2010) that removes the probe
account. There is no `try`/`finally` around the walk: every step between the invite and the cleanup
— `clickCenterOf` on the probe row (line 1961), the handoff's `runOpenerSteps` (line 1967), and the
final `clickCenterOf` on the dialog's own cancel control (line 1986) — can throw (`clickCenterOf`
explicitly `throw new Error(...)` when its target selector is not found, per its own definition at
line 361). None of those calls are wrapped.

`main()`'s own top-level `try`/`finally` (`test/visual/admin_shell.mjs:3350-3636`) only tears down
Chrome and the dev server on any thrown error; it does not run per-check cleanup. A throw anywhere
in case 3's guarded section therefore propagates to `main().catch(...)` (line 3641), aborts the
entire script, and skips cleanup — leaving the throwaway `probe-focus-return-*@pukllayclub.invalid`
account permanently in the dev database.

The irony this scope note flags: the single most likely trigger for exactly this throw is a real
regression in the dialog/sheet markup this case exists to test (e.g. a missing
`[data-pk-dialog-cancel]` on `confirm-remove-dialog`, or a renamed `ask-remove` selector) — meaning
the failure mode this test is built to catch is also the failure mode most likely to disable its own
cleanup, silently polluting `/admin/staff` for every subsequent run (including the very
`staffCountBefore !== staffCountAfter` invariant check at the end of this same function, which would
then itself report a spurious failure on the *next* run rather than this one).

**Fix:** wrap the guarded walk (invite → open → handoff → assert → cancel) in a `try`/`finally` whose
`finally` block always attempts the cleanup click sequence, regardless of how the `try` block exited
— mirroring the pattern `checkOverlayScrollLock`/`checkOverlayScrollLockHandoff` already use for
`Emulation.setTouchEmulationEnabled` (`test/visual/admin_shell.mjs:1526-1533`, `1598-1662`).

### WR-03: this round's new data-dependent regression cases repeat WR-04's "silent not-openable, no minimum-coverage assertion" pattern

**File:** `test/visual/admin_shell.mjs:1569-1666` (`SCROLL_LOCK_HANDOFF_CASES`/`checkOverlayScrollLockHandoff`), `1905-2024` (`checkSheetFocusReturn` case 3)

**Issue:**

The prior review's WR-05 (renumbered here to avoid an id collision with new findings — see the
carried-forward section) already found that `OVERLAY_CALL_SITES`'s data-dependent rows degrade a
missing opener to a `NOT-OPENABLE` log line, indistinguishable in the exit code from a genuine
regression in that row's own opener. This round's two new data-dependent checks repeat the exact
same shape:

- `checkOverlayScrollLockHandoff`'s two cases (`staff -> confirm-remove-dialog`,
  `shelf -> confirm-delete-shelf-dialog`) both push to `notOpenable` rather than `fails` when their
  opener selector never appears, and nothing asserts a minimum `covered`/attempted ratio.
- `checkSheetFocusReturn`'s case 3 does the same when the probe-staff invite fails to produce a
  clickable row.

As with the original WR-05, this means the majority of this round's own new lock/handoff/focus-return
coverage (2 of 2 handoff cases, 1 of 3 focus-return cases) can silently execute zero real assertions
run after run against a thin dev database, with only a `not-openable=N` count in console scrollback
as the only signal — no `FAIL` is ever produced purely from a coverage drop.

**Fix:** as with WR-05 below — either seed the required fixtures deterministically, or assert a
minimum `covered` count for a known-good dev DB so a silent coverage drop becomes a visible `FAIL`.
