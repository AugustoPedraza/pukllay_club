## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `admin_sheet.js`'s `isOpen()` was a no-op for `position: fixed` elements**
- **Found during:** Task 1/2 (the harness itself), fixed in Task 3 per explicit user direction
- **Issue:** `offsetParent !== null` is unconditionally `false` in Chrome for a `position: fixed` element — `.pk-admin-overlay-root` (the sheet/dialog mount point) IS `position: fixed`, so `isOpen()` always returned `false`, silently disabling Esc, drag-down, the focus trap, and focus-return.
- **Fix:** `isOpen()` now reads `getComputedStyle(this.el).display !== "none"`.
- **Files modified:** `assets/js/hooks/admin_sheet.js`
- **Verification:** RED (pre-fix, reproduced) → GREEN (post-fix) → RED (fix reverted) → GREEN (fix restored) via `test/visual/admin_components.mjs` against a real dev server + real staff session.
- **Committed in:** `58dba5c`

**2. [Rule 1 - Bug] Focus-return never fired for the shipped (`:if`-unmount) call-site pattern**
- **Found during:** Task 3, re-running the harness after fix #1
- **Issue:** `staff_live/index.ex`'s sheet/dialog call sites remove the element from the DOM via `:if` rather than toggling `pk-admin-overlay--open` on a still-mounted element — the `MutationObserver`-driven `onClose()` (which restores focus) never fires for that pattern, since there's no class mutation to observe before the node is gone.
- **Fix:** `destroyed()` now calls `onClose()` when `wasOpen` was `true`, guarded so a stay-mounted class-toggle usage (if one is ever added) never double-fires it.
- **Files modified:** `assets/js/hooks/admin_sheet.js`
- **Verification:** Same RED→GREEN cycle as fix #1 (this and fix #1 were verified together).
- **Committed in:** `58dba5c`

**3. [Rule 1 - Bug] The invoking row was never actually focusable — focus-return had nothing to restore to**
- **Found during:** Task 3, debugging fix #2's remaining failure (`lastFocused` was captured as `document.body`, not the clicked row)
- **Issue:** `list_row/1`'s `<div>` branch (used for the Staff row that opens the sheet) carried no `tabindex`, so a real mousedown/mouseup on it never moved `document.activeElement` to it — `onOpen()`'s `lastFocused = document.activeElement` captured `body` instead of the row.
- **Fix:** Added `tabindex="0"` to that branch.
- **Files modified:** `lib/pukllay_club_web/components/admin_components.ex`
- **Verification:** Confirmed via a standalone CDP debug script (focus correctly landed on the row after the fix), then via the full harness (focus-return check now passes). No other current call site uses this branch (grep-confirmed single call site).
- **Committed in:** `58dba5c`

**4. [Rule 1 - Bug] A cross-overlay focus race: `ask-remove` stole focus back from the dialog's Cancelar**
- **Found during:** Task 3, re-running the harness after fix #3 (all interactive checks passed except D-19f's dialog-focus check)
- **Issue:** `ask-remove` closes the sheet and opens `confirm-remove-dialog` in the SAME server diff. Traced via CDP instrumentation: LiveView mounts the new dialog's hook (which focuses Cancelar in its own `onOpen()`) BEFORE it destroys the sheet's hook — so fix #2's unconditional focus-restore was running AFTER the dialog already claimed focus, stealing it back to the row.
- **Fix:** `onClose()`'s focus-restore is now guarded on `document.activeElement === document.body` — the browser's own removal-of-focused-element behaviour resets `activeElement` to `body` synchronously, so `body` reliably means "no other overlay's `onOpen()` ran first".
- **Files modified:** `assets/js/hooks/admin_sheet.js`
- **Verification:** Full harness run: `ALL CHECKS PASSED`, run twice for stability. Confirmed via CDP tracing (`onOpen isDialog=true` logged before `onClose id=staff-options-sheet`) before the guard; confirmed the guard resolves it after.
- **Committed in:** `58dba5c`

**5. [Rule 1 - Bug] `.pk-admin-overlay-root` shared `z-index: 70` with the tab bar**
- **Found during:** Task 1/2 (the harness itself, via `elementFromPoint`), fixed in Task 3 per explicit user direction
- **Issue:** Both elements are `bottom: 0`-anchored and `position: fixed` with the identical `z-index: 70` — a short sheet's bottom-most row could be entirely covered by the tab bar, reproduced via a real coordinate click at "Quitar del staff"'s own centre landing on the tab bar's Estantes icon instead.
- **Fix:** Raised `.pk-admin-overlay-root`'s `z-index` to `75` (strictly between the tab bar's `70` and the snackbar's `80`).
- **Files modified:** `assets/css/admin/components.css`
- **Verification:** RED (pre-fix, reproduced) → GREEN (post-fix) → RED (fix reverted) → GREEN (fix restored) via `test/visual/admin_components.mjs`'s Z-INDEX REACHABILITY check.
- **Committed in:** `e944a23`

**6. [Rule 1 - Bug] A stale regression test asserted the OLD (broken) `offsetParent` behaviour by name**
- **Found during:** Task 3, running the full `mix test` suite after fixes #1-4
- **Issue:** `admin_components_test.exs`'s "never checks visibility via a `.hidden` class — only `offsetParent`" test literally `assert`ed `js =~ "offsetParent"` — which now fails on the corrected implementation, because the correction IS removing `offsetParent`.
- **Fix:** Updated the test to assert the corrected guard (`refute ... offsetParent`, `assert ... getComputedStyle`) — the underlying "never a class-name string match" rule it enforces is unchanged, only the concrete visibility check it names.
- **Files modified:** `test/pukllay_club_web/components/admin_components_test.exs`
- **Verification:** `mix test` — 1646 tests, 0 failures (full suite, matching the prior-wave baseline).
- **Committed in:** `58dba5c`
