**2. [Rule 1 - Bug] Fixed `AdminComponents.action/1`'s dead `type` pass-through**
- **Found during:** Task 2 (the Staff invite form's submit button)
- **Issue:** `action/1`'s own `:rest` global attr already declared `type` a legitimate pass-through (its `include:` list names it), but the button branch hardcoded `type="button"` ahead of `{@rest}` in the template — a second, later `type` attribute the browser silently discards. No button this component ever rendered could submit its enclosing form, which Task 2's own instruction ("the invite form uses `field/1` and `action/1`") requires.
- **Fix:** `action/1` now reads `rest[:type]` (default `"button"`) and strips the key from `rest` before spreading, so exactly one `type` attribute is ever emitted.
- **Files modified:** `lib/pukllay_club_web/components/admin_components.ex`
- **Verification:** `mix test test/pukllay_club_web/components/admin_components_test.exs` (the existing `type="button"` default-behavior test still passes unchanged) and `test/pukllay_club_web/live/admin/staff_live_test.exs`'s invite-round-trip tracer test (submits via the rebuilt form)
- **Committed in:** `b334d4e` (Task 2 commit)

**3. [Rule 2 - Missing Critical] Extended `field/1`'s `type` values with `"email"`**
- **Found during:** Task 2 (the Staff invite form)
- **Issue:** `field/1`'s `attr :type` declared `values: ~w(text number select textarea checkbox)` — no `"email"` — so passing `type="email"` (the invite field's actual semantic type, matching the shipped `<.input type="email">` it replaces) would have raised at compile time. The catch-all clause already renders `<input type={@type}>` generically; only the attr's allow-list was missing the value.
- **Fix:** Added `"email"` to the `values:` list.
- **Files modified:** `lib/pukllay_club_web/components/admin_components.ex`
- **Verification:** `mix compile --warnings-as-errors` (the literal `type="email"` attr passes validation); `staff_live_test.exs`'s invite tracer test
- **Committed in:** `b334d4e` (Task 2 commit)

**4. [Rule 2 - Missing Critical] Extended `status_dot/1`'s vocabulary with Staff's own states**

- **Issue:** `status_dot/1`'s `@status_words` map only covered game/copy statuses (`draft`/`published`/`retired`/`sin_lugar`/`afuera`); Staff's genuinely different status set (owner/active/pending invitation) had no atom to render through, and the shipped `estado_label/1` returned plain strings that D-19h's dot-plus-word anatomy would have had to be re-derived around, screen-locally.
