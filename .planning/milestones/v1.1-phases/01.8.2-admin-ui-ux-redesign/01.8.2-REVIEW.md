## Summary

This phase is already live in production (SHA `b774eb4e`), so every finding below is a
follow-up fix ranked by real user impact, not a merge gate.

A narrower prior pass (12 files, 5 findings) exists in the session scratchpad. I re-read
every one of its claims against the current source myself rather than trusting it, and
independently confirm **CR-01, WR-01 (broadened), WR-02, and IN-01** below — each is
restated with fresh line references and, for CR-01/WR-01, an additional consequence the
prior pass did not trace. Its WR-03 (`restore_deleted_shelf/1`'s own missing lock) I also
confirmed and keep, renumbered WR-05.

The main mechanism worth understanding first: `Shelves`' three position-mutating writers
(`place_copy/3`, `remove_copy_from_shelf/1`, `delete_copy/1`) all read the copy **before**
taking the per-estante advisory lock, then act on that stale struct once the lock is held.
This single root cause produces two distinct, independently-triggerable failure modes:
DB-level corruption inside `Shelves` itself (CR-01), and a wrong Deshacer target at the UI
layer even once the DB write is correct, because `place_copy/3`'s own API only ever hands
the caller the *post*-write struct, never the *pre*-write one it read under the lock
(WR-01, now shown to affect both `GameLive.Form` **and** `EstanteLive.Index`, not just the
editor as the prior pass reported).

Everything else in this larger 69-file scope — the destructive migrations, the router/auth
pipeline, the CSS/JS hook layer, the reorder-mode bubble-sort helpers repeated across three
LiveViews, the public-facing `catalog_live/show.ex` diff — reads as solid: locked
transactions where locking matters, defensive `Integer.parse`/`with` dispatch on
server-render-only-sourced client params in the vast majority of handlers, no raw SQL
built from interpolation, no secrets or dangerous functions, and the admin/public CSS
scope split (`ui-design-system` SKILL.md) is respected by every reviewed template.

## Critical Issues

### CR-01: `Shelves.place_copy/3`, `remove_copy_from_shelf/1`, and `delete_copy/1` read the mover's own position *before* taking the estante lock, so a concurrent write to the same shelf can silently corrupt its position sequence

**File:** `lib/pukllay_club/catalog/shelves.ex:658-674` (`place_copy/3`), `:684-701`
(`remove_copy_from_shelf/1`), `:593-607` (`delete_copy/1`'s placed clause), and the shared
culprit `vacate/2` at `:730-747`

**Issue:** Every one of these three public writers follows the same shape:

```elixir
Multi.new()
|> Multi.run(:copy, fn repo, _changes -> fetch_copy(repo, copy_id) end)          # UNLOCKED read
|> Multi.run(:lock, fn repo, %{copy: copy} -> lock_estantes(repo, [copy.shelf_id, shelf_id]) end)
|> Multi.run(:vacated, fn repo, %{copy: copy} -> vacate(repo, copy) end)         # uses the STALE `copy`
```

`fetch_copy/2` (`shelves.ex:703-708`) does a plain unlocked `repo.get(Copy, copy_id)`
*before* `pg_advisory_xact_lock` is acquired. The `shelf_id`/`position` captured in that
struct are never re-read once the lock is held. `vacate/2` (`:730-747`) uses that stale
`position` as the threshold for its gap-closing shift:

```elixir
Copy
|> where([c], c.shelf_id == ^shelf_id and c.position > ^position)   # ^position is STALE
```

`delete_copy/1`'s placed clause (`:593-607`) is worse in a different way: it never fetches
`copy` inside the function at all — it trusts whatever struct the caller already held
(e.g. a `copy_context` a `GameLive.Form` session opened seconds or minutes earlier), locks,
and vacates against it unread.

Because the lock is acquired *after* the read, two staff members racing on the same
estante (5 copies A@0..E@4) can interleave so that staff 1 vacates D using a stale
`position: 3` snapshot taken before staff 2 already shifted the shelf underneath it —
producing either a silent gap (nothing shifts to fill the hole) or a duplicate `position`
that raises an unhandled `Postgrex`/`Ecto` error out of the `Multi.run` step, crashing the
LiveView process (the client sees a disconnect/reconnect, not a graceful error).

This is exactly the screen this phase built for simultaneous staff use
(`EstanteLive.Index`'s "Quitar del estante" / "¿Dónde va?" flows call `remove_copy_from_shelf/1`
and `place_copy/3` directly). The existing concurrency test
(`test/pukllay_club/catalog/shelves_test.exs:385-436`) only races N copies that all start
`shelf_id: nil` onto one *empty* destination shelf — every one of those hits `vacate/2`'s
no-op clause (`vacate(_repo, %Copy{shelf_id: nil})`), so it never exercises the buggy
non-nil branch at all. A green suite hides this completely.

**Fix:** Re-read the copy (or at minimum its `shelf_id`/`position`) *after* the advisory
lock is acquired, and use that fresh value for `vacate/2`'s threshold — the lock only
protects data read while holding it:

```elixir
Multi.new()
|> Multi.run(:copy, fn repo, _changes -> fetch_copy(repo, copy_id) end)
|> Multi.run(:lock, fn repo, %{copy: copy} -> lock_estantes(repo, [copy.shelf_id, shelf_id]) end)
|> Multi.run(:fresh_copy, fn repo, %{copy: copy} -> fetch_copy(repo, copy.id) end)  # re-read INSIDE the lock
|> Multi.run(:vacated, fn repo, %{fresh_copy: copy} -> vacate(repo, copy) end)
|> Multi.run(:moved, fn repo, %{fresh_copy: copy} -> insert_at(repo, copy, shelf_id, index) end)
```

Apply the same fix to `remove_copy_from_shelf/1`, and change `delete_copy/1`'s placed
clause to re-fetch by id inside its own `:lock`-then-`:copy` step rather than trusting the
caller's struct. See WR-01 below for a second, related gap this same API shape creates at
the UI layer even after this fix lands.

## Warnings

### WR-01: `place_copy/3` never returns the copy's *pre*-write location, so every caller's Deshacer snapshot is built from a struct that can be stale — in `GameLive.Form` **and** `EstanteLive.Index`, not the editor alone

**File:** `lib/pukllay_club/catalog/shelves.ex:658-674` (`place_copy/3`'s own return shape);
callers at `lib/pukllay_club_web/live/admin/game_live/form.ex:762-786`
(`commit_shelf_sheet/3`) and `lib/pukllay_club_web/live/admin/estante_live/index.ex:435-479`
(`commit_donde_va/3` -> `commit_placement/4`)

**Issue:** `place_copy/3`'s internal `Multi` does capture the copy's real pre-write state
under the lock as `:copy` (`original`), but the public return only ever forwards `moved`:

```elixir
{:ok, %{copy: original, moved: moved}} ->
  broadcast(shelf_id)
  if original.shelf_id not in [nil, shelf_id], do: broadcast(original.shelf_id)
  {:ok, moved}   # `original` — the only correct "where it was before this write" value — is discarded here
```

Both UI callers therefore compute their own "previous location" for the Deshacer snapshot
from whatever `copy` struct they held **before calling `place_copy/3`**, not from anything
`place_copy/3` itself verified:

```elixir
# game_live/form.ex:762-767
defp commit_shelf_sheet(socket, shelf_id, index) do
  copy = socket.assigns.shelf_sheet.copy        # captured when the sheet OPENED
  previous_shelf_id = copy.shelf_id
  previous_position = copy.position
  case Shelves.place_copy(copy.id, shelf_id, index) do
```

```elixir
# estante_live/index.ex:454-455
defp commit_placement(socket, copy, shelf_id, index) do
  previous = %{shelf_id: copy.shelf_id, position: copy.position}   # same shape, same staleness risk
```

The "¿Dónde va?" and "¿Qué juego va acá?" sheets can stay open for as long as staff spend
searching for the right estante — if a *different* staff member moves this exact copy
while the sheet is open, the write itself still succeeds correctly (it only depends on
`copy.id`), but the recorded "previous" location is wrong. A later tap on "Deshacer"
(`restore_position/3`) then silently relocates the copy back to wherever it was when the
sheet was *opened*, not where it actually was immediately before *this* commit — quietly
undoing more than the one action the button claims to undo, on the very screen built for
concurrent staff use.

The prior review pass caught this only in `GameLive.Form` (as a "never subscribes to
`admin:estantes`" framing) and concluded `EstanteLive.Index` was safer because it does
subscribe and reconcile `selected_copy` on broadcast. That reconciliation only refreshes
what's *rendered* — it does not touch `@donde_va`/`@que_va_aca`'s already-captured `copy`,
so `EstanteLive.Index` carries the identical bug through its own commit path.

**Fix:** Have `place_copy/3` return the pre-write location too (e.g.
`{:ok, %{moved: moved, previous_shelf_id: original.shelf_id, previous_position: original.position}}`,
or a `{:ok, moved, previous}` tuple), and have both callers build their `undo_snapshot` from
that returned value instead of a copy struct captured before the sheet opened. This closes
the gap regardless of how long the sheet stays open, and does not require either LiveView to
grow new PubSub reconciliation logic.

### WR-02: `Administrar`'s "Deshacer" for a deleted shelf crashes the LiveView on a name collision

**File:** `lib/pukllay_club_web/live/admin/estante_live/administrar.ex:186-196`;
`lib/pukllay_club/catalog/shelves.ex:211-236` (`restore_deleted_shelf/1`);
`lib/pukllay_club/catalog/shelf.ex:27-32` (`unique_constraint(:name)`)

**Issue:** `restore_deleted_shelf/1` inserts a brand-new `Shelf` row through
`Shelf.changeset/2`, which carries `unique_constraint(:name)`. If any shelf with the
deleted shelf's exact name has been (re)created in the interim — plausible, since staff
commonly re-create a shelf with the same name right after deleting it, or two staff members
are both managing estantes at once — `restore_deleted_shelf/1` returns `{:error,
changeset}`. The caller does not handle that branch:

```elixir
def handle_event("undo-delete", _params, socket) do
  case socket.assigns.deleted_shelf do
    nil -> {:noreply, socket}
    snapshot ->
      {:ok, _shelf} = Shelves.restore_deleted_shelf(snapshot)   # MatchError on {:error, _}
      {:noreply, socket |> assign(:deleted_shelf, nil) |> load_shelves()}
  end
end
```

A `MatchError` here crashes the LiveView process — the user sees a disconnect/reconnect and
loses the deleted-shelf snackbar (and any other unsaved sheet state on the page); the crash
also discards `deleted_shelf`, so the snapshot cannot even be retried after reconnect.

**Fix:**

```elixir
case Shelves.restore_deleted_shelf(snapshot) do
  {:ok, _shelf} ->
    {:noreply, socket |> assign(:deleted_shelf, nil) |> load_shelves()}
  {:error, _reason} ->
    {:noreply,
     socket
     |> assign(:deleted_shelf, nil)
     |> put_flash(:error, "No se pudo deshacer: ya existe un estante con ese nombre.")}
end
```

### WR-03: `donde-va`/`que-va-aca` event handlers parse client-supplied ids with `String.to_integer/1` instead of the codebase's own defensive `Integer.parse/1` convention, so a malformed payload crashes the LiveView instead of degrading

**File:** `lib/pukllay_club_web/live/admin/estante_live/index.ex:168,174,181,207,234`;
`lib/pukllay_club_web/live/admin/game_live/form.ex:314,320,327`

**Issue:** Every other `phx-value-*` id in this phase's admin LiveViews is parsed
defensively — `parse_id/1` in `estante_live/administrar.ex`, `section_live/index.ex`,
`section_live/edit.ex`; `Integer.parse/1` with a `case`/`with` fallback in `game_live/index.ex`,
`band_audit_live.ex`, `staff_live/index.ex`'s siblings, and even elsewhere in these same two
files (`parse_id/1` in `estante_live/index.ex:504-511`, `parse_copy_id/1` in
`game_live/form.ex:747-754`). But the «¿Dónde va?»/«¿Qué juego va acá?» handlers use the
raising `String.to_integer/1` directly:

```elixir
# estante_live/index.ex:167-168
def handle_event("donde-va-pick-estante", %{"shelf-id" => id}, socket) do
  shelf = Shelves.get_shelf!(String.to_integer(id))   # raises ArgumentError on non-numeric id
```

and identically at `:174` (`donde-va-pick-copy`), `:181`/`:207` (`String.to_integer(idx)` in
`donde-va-commit`/`open-que-va-aca`), `:234` (`que-va-aca-pick`), and the mirrored
`game_live/form.ex:314,320,327`. These events are normally fired only by real ids the server
itself rendered, so a genuine user tap can't trigger this — but a forged/tampered client
payload (browser devtools, a stale cached page after the shelf list changed) raises
`ArgumentError` out of the handler, crashing the LiveView process rather than degrading
gracefully the way every sibling handler in this same phase was deliberately written to.

**Fix:** Route these five call sites through the same `parse_id/1`/`Integer.parse/1` +
fallback pattern already established elsewhere in both files, so a malformed id is a no-op
instead of a crash.

### WR-04: `Catalog.retire_game/1`'s foot save-bar path can silently discard an in-flight draft edit's error without surfacing it distinctly from the lifecycle refusal message

**File:** `lib/pukllay_club_web/live/admin/game_live/form.ex:638-653` (`confirm-retire`)

**Issue:** The moduledoc explicitly states `status` commits "outside `@draft`/`@saved`
entirely" so an in-progress field edit survives a status change untouched — but this means
a staff member who has unsaved draft changes AND retires the game from the same session
ends up with a game now `:retired` (status committed) while their unsaved name/description
edit is still sitting in `@draft`, unpersisted, with no indication anywhere in the retire
flow that the two are now out of sync (the franja becomes "Retirado", the save bar still
shows "Sin guardar" for the untouched draft, and `Guardar` on a retired game is technically
still reachable and would then save into a game the staff member likely believes they just
"finished with"). This is a minor UX inconsistency rather than a data-loss bug — nothing is
lost — but it is unflagged surprising behavior worth a note. Low priority; not a regression
this phase introduced, since the write-model separation (`@draft`/`@saved` vs. `status`) is
this phase's own deliberate design (D-27), and no prior phase had this interaction at all
(the editor screen is new in this phase). Included here because it is the one place the
otherwise-careful "no field write leaks into an unrelated action" discipline (D-31's own
repeated commenting convention) has a gap the plan's own commentary doesn't address.

**Fix:** Consider surfacing a distinct flash/consequence line when `Guardar` is tapped
after `Retirar` in the same session (e.g. "Este juego está retirado — los cambios se
guardan igual."), or block/warn before retiring with an unsaved draft, mirroring the
existing "¿Salir sin guardar?" discard-confirm dialog's own precedent for surfacing dirty
state before a destructive navigation.

### WR-05: `restore_deleted_shelf/1` can silently rip a copy away from a shelf it was placed on *after* the delete, without reindexing the shelf it leaves

**File:** `lib/pukllay_club/catalog/shelves.ex:211-236`

**Issue:** Unlike every other write in this module, `restore_deleted_shelf/1` takes no
per-estante advisory lock and does not re-verify the snapshotted copies' current location
before overwriting it:

```elixir
Enum.each(copies, fn {copy_id, copy_position} ->
  repo.update_all(from(c in Copy, where: c.id == ^copy_id),
    set: [shelf_id: shelf.id, position: copy_position]
  )
end)
```

If, in the window between `delete_shelf/1` returning its snapshot and a staff member
tapping "Deshacer", a *different* staff member independently placed one of the snapshotted
copies onto some other (real, still-existing) shelf — via the normal `place_copy/3` path,
which correctly reindexed that other shelf around the copy's departure — this unconditional
`update_all` blindly overwrites that copy's `shelf_id`/`position` back to the restored
shelf. The other shelf is left with a gap at the position the copy used to occupy there
(nothing reindexes it), and the staff member who placed the copy sees it silently vanish
from where they just put it.

**Fix:** At minimum, lock the destination shelf being restored plus every currently-distinct
`shelf_id` among the snapshotted copies' live rows before writing (mirroring
`lock_estantes/2`'s existing convention), and skip/warn on any copy whose live `shelf_id` no
longer matches what it had when the shelf was deleted, rather than unconditionally
clobbering a copy that moved elsewhere in the interim. Narrow window (typically seconds, the
length of the Deshacer snackbar) and lower priority than CR-01/WR-01, but shares the same
root cause: a write path in this module that doesn't hold its lock across both the read that
decides "what to write" and the write itself.

## Info

### IN-01: `Ecto.Changeset.change/2` bypasses schema-level validation for `bgg_id`/`enrichment_status` writes in `Catalog`

**File:** `lib/pukllay_club/catalog.ex:451-467` (`clear_bgg_id/1`, `restore_bgg_id/3`) and
`:417-441` (`update_bgg_id_with_edition_check/3`, called by `link_bgg_id/3`) — all added by
this phase, calling `Ecto.Changeset.change/2` directly rather than a `Game` changeset
function

**Issue:** These three write paths set `bgg_id`/`enrichment_status` via the
changeset-less `Ecto.Changeset.change/2` rather than routing through
`Game.enrichment_changeset/2` (which mirrors the DB-level
`games_enrichment_status_must_be_known` CHECK constraint added by this same phase's
`20260923121000_validate_enrichment_status.exs`). In practice the DB constraint is the real
backstop and will reject an invalid `enrichment_status`, so this is not exploitable, but it
is the only write path in this phase that skips the schema-level validation convention
`Game.enrichment_changeset/2` exists to centralize elsewhere in the module.

**Fix:** Low priority — route through `Game.enrichment_changeset/2` (or a narrow
purpose-built changeset) for consistency with the rest of `Catalog`'s write paths, so a
future `enrichment_status` vocabulary change only needs to touch one place.
