<task type="checkpoint:decision">
  <name>Task 1: confirm the one-way drop of games.units</name>
  <decision>
Plan 01.8.2-01's migration has already created one copy row per unit for every game
(`generate_series(1, COALESCE(units, 1))`), so every value in `games.units` is now
represented as copy rows. This task drops the column.

**This is one-way.** Undoing it means a migration that collapses copy rows back into an
integer count — recoverable in principle, but it discards the per-copy identity (`number`)
and per-copy location that D-01/D-03 introduced, and Phase 4's rentals are specified to
build on the copies table.

Before proceeding, confirm: (a) plan 01.8.2-01's backfill ran and
`SELECT count(*) FROM copies` is at least `SELECT count(*) FROM games`; (b) no row has
`units` greater than its copy count; (c) a `pg_dump` of the current database exists or the
loss is accepted.
  </decision>
  <options>
    - Proceed with the drop now (D-31 as written)
    - Hold the column as a dead, unread field until after the production rollout in plan 01.8.2-22, and drop it there instead
  </options>
  <recommendation>
Proceed. Holding a dead column means every slice between here and 01.8.2-22 has two plausible
Copias sources, which is the exact ambiguity D-31 exists to remove — and the whole phase ships
in one deploy anyway (Claude's Discretion), so there is no window where production runs a
half-migrated schema.
  </recommendation>
  <acceptance_criteria>
    - the copy-count-versus-units comparison is run and its result recorded in the summary before the drop
    - the developer's choice (drop now / hold to 01.8.2-22) is recorded verbatim
  </acceptance_criteria>
  <resume-signal>Type "drop now" or "hold to 01.8.2-22", after the copy-count comparison is reported</resume-signal>
  <done>The one-way drop is confirmed against a measured copy count, or explicitly deferred.</done>
</task>
