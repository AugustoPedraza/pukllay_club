**CR-B-01 (`add_game_from_bgg/1`'s duplicate-BGG-id rejection has no database backstop — TOCTOU
race) is RESOLVED.** The read-then-write `Repo.get_by(Game, bgg_id: ...)` check is replaced by
`insert_draft_with_edition_check/2`, an `Ecto.Multi` that (1) takes a per-BGG-id
`pg_advisory_xact_lock(8_811_015, bgg_id)` first, (2) re-reads every game holding that `bgg_id`
inside the same transaction (a fresh READ COMMITTED statement-level snapshot after the lock,
correctly picking up whatever a prior lock holder just committed), and (3) inserts only when every
current holder's id is in the caller-supplied `acknowledged_game_ids` (`MapSet.subset?/2`). Note
this resolves the race by a different mechanism than the original REVIEW's suggested fix (a unique
index) — that fix was explicitly and correctly rejected, since `games.bgg_id` must stay non-unique
to support real editions (the Patchwork/Patchwork Andino pair). The advisory-lock approach is
verified against **real, unboxed Postgres connections** in `bgg_editions_test.exs` (lock-holder
test polling `pg_locks` for waiters, and a 4-way concurrent race for a brand-new id yielding exactly
one draft and exactly one Oban job) — I re-ran the full targeted suite (`bgg_editions_test.exs`,
`game_live_test.exs`, `enrich_game_worker_test.exs`) and all 58 tests pass, along with
`mix compile --warnings-as-errors`, `mix format --check-formatted`, and `mix credo --strict` on the
two changed lib files (clean, 0 issues).

**IN-B-02 ("Agregar juego" has no `phx-disable-with`) is RESOLVED.** `phx-disable-with="Agregando…"`
is now present on both "Agregar juego" and "Sí, agregar edición" (`grep -c` on the file returns 2).

## Narrative Findings (AI reviewer)

I traced the full advisory-lock/transaction path, the acknowledged-ids contract, the LiveView event
handlers, and the Spanish copy, specifically looking for ways to disprove the "one staff action can
never produce two drafts" claim and for `phx-value-value`-style param clobbering. I could not find a
way to reproduce a double-draft: the lock namespace (`8_811_015`, two-int4 form, `objsubid = 2`) is
consistent between `lib/pukllay_club/catalog.ex` and the test file; the editions re-check runs as its
own statement after the lock is granted, so it always observes a just-committed prior insert; the
subset rule correctly treats "no existing holders" (empty query result) as vacuously satisfied so a
brand-new id still inserts on the first call; and a stale prompt (second tab, double-tap) always
re-warns with the refreshed holder list instead of inserting, which is proven under both simulated
(same-tab double `render_click`) and real two-LiveView-process conditions. `confirm-edition`'s
acknowledged ids come only from `socket.assigns.edition_prompt` (server-side), never from
`_params` — I confirmed no client payload is read in that handler at all. `phx-value-game-id` (not
`phx-value-value`) is used for the one client-supplied value in this file (`retry-enrichment`),
consistent with the project's memory rule. Copy uses correct Argentine voseo ("Ya **tenés**...",
not "tienes"). HEEx `{...}` interpolation is used throughout for game names (auto-escaped, no `raw`).

Two minor, non-blocking observations:

### IN-01: `confirm-edition`'s generic `{:error, _reason}` branch is untested and effectively dead in normal operation

**File:** `lib/pukllay_club_web/live/admin/game_live/index.ex:153-157`
**Issue:** `handle_event("confirm-edition", ...)` re-parses `prompt.input` via
`Catalog.add_game_from_bgg/2`. Since `prompt.input` only reaches the prompt state after a prior
*successful* parse (the initial "add-game" submit already had to hit the `{:existing_editions, _}`
branch to populate `:edition_prompt`), a re-parse of the same string is deterministic and this
`{:error, _reason}` branch can only be reached defensively (e.g. if `Game.draft_changeset/2` itself
rejected the id, which `parse_bgg_input/1`'s own range check already prevents in practice). No test
exercises it. This is intentional defensive coding per the plan, not a functional bug, but it is
currently unverified — a future refactor of `parse_bgg_input/1` or `draft_changeset/2` could
silently break this path without a test catching it.
**Fix:** Optional — add a regression test forcing `Game.draft_changeset/2` to reject during confirm
(e.g. by mocking/stubbing a boundary value), or leave as documented-defensive and accept the gap.

### IN-02: the advisory-lock `Multi.run` step uses `repo.query!` (raises) rather than returning a tagged error, so an infra-level failure crashes the LiveView instead of surfacing the existing generic error copy

**File:** `lib/pukllay_club/catalog.ex:318-321`
**Issue:** `Multi.run(:bgg_id_lock, fn repo, _changes -> repo.query!(...) ; {:ok, :locked} end)` uses
the bang variant. If the advisory-lock query itself fails at the infrastructure level (connection
loss, statement timeout, a Postgres-side lock/deadlock error unrelated to the advisory lock's own
semantics — advisory locks themselves cannot deadlock here since only one lock is ever held per
transaction, per the plan's own threat-model T-01.8.1-71), `Repo.transaction/1` re-raises the
exception rather than returning `{:error, :bgg_id_lock, reason, changes}`, so neither
`handle_event("add-game", ...)` nor `handle_event("confirm-edition", ...)`'s `case` statements ever
see it — the exception propagates and crashes the LiveView process instead of hitting the existing
"Pegá un número de BGG o el link del juego." fallback copy. This is consistent with how the rest of
the codebase treats infrastructure-level DB failures (not a regression specific to this diff), and is
low-probability/low-impact (LiveView reconnects cleanly on crash), so it does not rise to a Warning.
**Fix:** Optional — not required for this gap-closure plan's scope. If ever hardened, catch the
`Postgrex.Error`/`DBConnection.ConnectionError` around the `query!` call and return
`{:error, :lock_failed}` from the `Multi.run` function instead of letting it raise, then add a
generic-error case-branch for it in both handlers.
