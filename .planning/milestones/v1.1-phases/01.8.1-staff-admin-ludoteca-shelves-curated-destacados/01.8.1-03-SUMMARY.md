## Deviations from Plan

### Verification-method deviations (no code change required)

**1. [Verification note] Task 3's `<verification>` literal `dig +short TXT pukllay.club` does not apply as specified**
- **Found during:** Task 3 re-verification
- **Issue:** The plan's Task 3 `<verification>` and the plan-level `<verification>` block both specify checking SPF via `dig +short TXT pukllay.club` on the root domain. Resend's actual domain-verification flow puts SPF (and the bounce-handling MX) on a delegated `send.pukllay.club` subdomain (`CNAME` to `send.forge.rmta.net.`) — this is how Resend structures its MAIL FROM / return-path, and the root domain has no SPF TXT record at all.
- **Resolution:** Verified the real, provider-correct records instead: `dig +short TXT resend._domainkey.pukllay.club` (DKIM), `dig +short TXT send.pukllay.club` and `dig +short MX send.pukllay.club` (SPF/MX on the delegated subdomain), `dig +short TXT _dmarc.pukllay.club` (DMARC `p=none`), and `gh secret list | grep -c MAILER_API_KEY` (returns 1). All pass. Documented in `docs/runbooks/domain-and-dns.md` so this is not re-flagged as a gap in a future review.
- **Files modified:** `docs/runbooks/domain-and-dns.md`
- **Verification:** All five `dig`/`gh` commands re-run in this session, outputs match exactly what the orchestrator reported at hand-off.
- **Committed in:** `93bf5dc`

**2. [Verification note] Task 2's acceptance-criteria secret-leak grep has known false-positive matches**
- **Found during:** Task 3 re-verification (re-running Task 2's acceptance criteria as part of closing out the plan)
- **Issue:** `git grep -n -e 're_[A-Za-z0-9]{10,}' -e 'xkeysib-' -- config lib` (the check for an accidentally-committed literal Resend/Brevo key) does not print nothing as the acceptance criterion states — it prints 12 lines, all substring matches of `re_` inside unrelated identifiers (`core_components`, `require_authenticated`, `require_authenticated_user`, etc.), not an actual `re_`-prefixed API key.
- **Resolution:** Manually reviewed all 12 matches — none is a credential. No code change needed; documenting here so this known false-positive pattern isn't mistaken for a real leak in a future audit.
