<objective>
Prove gap G-01.8-3 closed where it actually failed — against the live deployed
site, viewed exactly as WhatsApp's link-preview crawler views it — and close out
the diagnostic record.

Purpose: plan 01.8-06 fixes the emitted markup and pins it with unit and
served-response gates, but every one of those runs against a local test `conn`.
The gap was reported against production and the stale-cache hypothesis was
refuted by a human test on production, so the closing evidence has to come from
production too. This plan is the only place the required property is measured on
the real deployed response.

Output: a green run of the committed strict-crawler oracle against the live host
across a game detail page and both branded-fallback routes; the real WhatsApp
share re-test handed to end-of-phase UAT; and the debug session plus the shared
debug knowledge base updated with the confirmed mechanism, the applied fix, and
why no existing gate caught it.

Why this is a separate plan with a precondition rather than a task that deploys.
Plan 06's commits have to reach production before anything here can be measured,
and in this repo that path is not a bare push: `origin/main` is branch-protected
and requires a PR with the `quality` check, while `.planning/config.json` still
carries `branching_strategy: "none"`. That mismatch is the documented root cause
of this project's repeated `main` divergence — CLAUDE.md carries a whole "Git
Sync Discipline" section written because of it, and STATE.md still lists it as an
open blocker. Having an autonomous executor open and merge PRs into protected
`main` is the specific behaviour that history argues against, so this plan states
the deployment as a checkable read-only precondition instead. If it is not met,
the executor halts with a blocking-human gate naming exactly what to do; that
halt is the intended behaviour, not a failure.
</objective>
