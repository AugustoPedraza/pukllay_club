### Pattern 1: Pre-mount Plug writes to `conn.assigns`, never a LiveView socket assign

**What:** A plain `Plug` module, piped into the router only for `/juegos/:id`, that resolves the game and its SEO metadata before the LiveView takes over.
**When to use:** Any per-route dynamic value (title, description, image) that a JS-free crawler must see on the very first HTTP response.
**Example (skeleton, following this app's own conventions):**

```elixir
# Source: this app's own conventions (PukllayClubWeb.verified_routes/0,
# lib/pukllay_club_web.ex:99-106 [VERIFIED]; share_control/1's URL-building
# pattern, lib/pukllay_club_web/live/catalog_live/show.ex:1085-1086 [VERIFIED])
defmodule PukllayClubWeb.Plugs.GameSEO do
  import Plug.Conn
  use PukllayClubWeb, :verified_routes

  alias PukllayClub.Catalog

  def init(opts), do: opts

  def call(%Plug.Conn{params: %{"id" => id}} = conn, _opts) do
    game = Catalog.get_game!(id)
    assign(conn, :seo, build_seo(conn, game))
  end
end
```

This plug must be piped in the router **before** `Phoenix.LiveView.Router`'s `live/3` dispatches, on the `/juegos/:id` route specifically (a `scope` with its own small pipeline, or a route-specific `plug` inside the existing `:browser` scope — Phoenix routers support `plug` calls scoped to individual routes via `pipe_through` composition or a nested scope). `Catalog.get_game!/1` already raises `Ecto.NoResultsError` (implements `Plug.Exception`, 404s cleanly) for a bad id — reuse this, don't add a second not-found branch.

### Pattern 3: CSP nonce generated once, in the plug that also emits the header — no reconnect threading needed

**What:** `put_csp/2` (the router's existing private plug, `lib/pukllay_club_web/router.ex:64-66` `[VERIFIED]`) generates a random nonce, assigns it to `conn`, and passes it into `CSP.policy/1`.

```elixir
# Current (VERIFIED, lib/pukllay_club_web/router.ex:64-66):
defp put_csp(conn, _opts) do
  put_resp_header(conn, "content-security-policy", PukllayClubWeb.CSP.policy())
end

# Refactored shape (skeleton — nonce generation via stdlib, no new dep):
defp put_csp(conn, _opts) do
  nonce = 24 |> :crypto.strong_rand_bytes() |> Base.encode64(padding: false)
  conn
  |> assign(:csp_nonce, nonce)
  |> put_resp_header("content-security-policy", PukllayClubWeb.CSP.policy(nonce))
end
```

**Refined finding vs. `research/SUMMARY.md`'s flagged spike:** SUMMARY.md flagged "~30-minute spike... threading a nonce through `connect_info`/`on_mount` so it survives LiveView websocket reconnects" as a real risk. This session's research refines that: **threading is not needed for this phase's JSON-LD use case.**

- This app's own PITFALLS.md (Pitfall 1/2, HIGH confidence, corroborated by `phoenix_live_view` GitHub issue #1194 and a direct José Valim forum statement) already established that `root.html.heex`'s `<head>` is rendered once on the disconnected HTTP response and is **never re-rendered by the LiveView socket** — not on connect, not on reconnect, not on `live_patch`/`live_redirect`. The nonce and the CSP header that names it are generated in the *same* `put_csp/2` call, for the *same* response, so they are consistent by construction. There is no second render of `<head>` where a stale nonce could cause a mismatch.
- The community pattern that *does* need `connect_info`/`on_mount` nonce-threading (Dan Schultzer's post, `[CITED: danschultzer.com/posts/content-security-policy-with-liveview]`) addresses a different problem: `<style>`/inline-style nonces for CSS the LiveView *socket itself* pushes as diffs during a live session (`style-src`) — content that genuinely does get re-rendered after connect. This app's `style-src` already carries `'unsafe-inline'` (pinned by a regression test as intentional, D-08/T-01.7-21 — see below) and is out of scope for this phase; only `script-src` is being touched.
- This app's own colocated hooks (`.GamePreview`, `.CarouselScroll`, etc., e.g. `lib/pukllay_club_web/components/game_preview.ex:204` `[VERIFIED]`) use `<script :type={Phoenix.LiveView.ColocatedHook}>` — per LiveView's own docs `[CITED: phoenix-live-view.hexdocs.pm/Phoenix.LiveView.ColocatedHook.html]`, these are extracted at **compile time** into a separate bundled JS file and are never rendered as literal inline `<script>` elements at runtime, so they do not interact with `script-src` at all. There is no existing runtime dynamic-script-injection pattern in this app that would need nonce-reconnect support.

**Recommendation:** implement the simple, single-request nonce (no `connect_info` threading). Add one verification checkpoint to the plan — after deploying, simulate a network drop/reconnect (DevTools → Offline → Online, the same technique already used for Phase 01.7's CSRF verification) and confirm no new CSP violation appears in the console. If one *does* appear (this session cannot execute the app to confirm), fall back to the `connect_info` pattern — but do not build it preemptively.

### Pattern 4: Static site-wide JSON-LD uses a hash-source, not the nonce

**What:** The `LocalBusiness` block never changes per-request (D-01/D-02/D-03 are all compile-time literals) — compute its SHA-256 hash once (a module attribute) and add `'sha256-<hash>'` to `script-src` permanently, alongside the per-request nonce. Per CSP spec `[CITED: developer.mozilla.org/.../script-src]`, `'self'`, a nonce-source, and a hash-source can all coexist in one `script-src` value — a script is allowed if it matches *any* listed source. Only `'unsafe-inline'` gets ignored in the presence of a nonce/hash (irrelevant here — `'unsafe-inline'` was never present on `script-src`).

```elixir
# Skeleton — @local_business_json module attribute is the exact byte-for-byte
# string rendered in the template; the hash must be computed over the SAME bytes.
@local_business_hash :crypto.hash(:sha256, @local_business_json) |> Base.encode64()
```

### Pattern 5: og-card.webp — resize-then-pad, verified against the vendored `image` package

**What:** `Image.embed/4` only *pads* — it requires the target canvas to be >= the source image on both axes, it does not shrink. `cover-large.webp` is produced at `@large_width 800` (`[VERIFIED: lib/pukllay_club/catalog/seed/image_pipeline.ex:25]`) and is "near-square, letterboxed" per this project's own D-08 rationale — its height can exceed 630px, which is smaller than `@large_width`. The correct sequence is resize-to-fit, then pad-to-exact-canvas:

```elixir
# Source: deps/image/lib/image.ex [VERIFIED, vendored copy read directly]
#   thumbnail/3 "50x50" dimension-string form: image.ex:4921-4924
#   :fit :contain option: image.ex:4865-4867 ("the image keeps its aspect
#     ratio, but is resized to fit within the given dimension... same as
#     setting crop: :none and resize: :both")
#   embed/4 signature + :background/:x/:y options: image.ex:5690-5705,
#     5622-5650 (":x"/":y" default :center; ":background" accepts a hex
#     string "#rrggbb")
with {:ok, fitted} <- Image.thumbnail(cover_vimage, "1200x630", fit: :contain),
     {:ok, og_card} <- Image.embed(fitted, 1200, 630, background: "#8C2AB7") do
  ...
end
```

`"#8C2AB7"` is `--pk-ramp-600`, the light theme's `--color-primary` value, read directly:

```css
/* VERBATIM, assets/css/app.css:276, 293 [VERIFIED] */
--pk-ramp-600: #8C2AB7;
...
--color-primary: var(--pk-ramp-600);
```

(Dark theme's `--color-primary` resolves to `--pk-ramp-900` instead — `assets/css/app.css:345-347` — but D-07 names `--pk-ramp-600` specifically, and a static social-preview image can't be theme-aware anyway, so `#8C2AB7` is the correct, single, literal value — not a discretion call.)

### Pattern 6: Mix task backfill mirrors `GalleryBackfill`/`catalog.backfill_gallery` exactly

**What:** The existing pair — `lib/mix/tasks/catalog.backfill_gallery.ex` (thin `Mix.Task` wrapper, `--dry-run` flag, `Mix.Task.run("app.start")`) and `lib/pukllay_club/catalog/seed/gallery_backfill.ex` (the actual `Repo`-querying logic, returns a `%{scanned:, updated:}` summary map) — is the exact structural template for `catalog.backfill_og_cards`/`OGCardBackfill`, both read verbatim this session. Unlike `GalleryBackfill` (which does no network I/O), the new task needs `Credentials.fetch!/0` and does R2 uploads — for that half, mirror `ImagePipeline.process/3`'s `with`-chain and `Storage.impl().put/4` call instead (`lib/pukllay_club/catalog/seed/image_pipeline.ex:37-47` `[VERIFIED]`), reusing the *existing* `Credentials.r2_object_url/2` (`[VERIFIED: lib/pukllay_club/catalog/seed/credentials.ex:138-141]`) to mint the returned URL, per this app's own "never a second URL-minting site" convention (`csp.ex` moduledoc, `Credentials` moduledoc).

### Anti-Patterns to Avoid

- **Gating any SEO-tag-producing code on `connected?(socket)`:** already the project's own documented Pitfall 1 — the crawler never connects, so this branch is invisible to it.
- **A live JS hook that rewrites `<head>` `<meta>`/`<script>` tags on every `handle_event`/patch:** tried and found fragile in community discussion per this project's own PITFALLS.md; the staleness it would fix (same-session `<head>` drift across client-nav) is explicitly accepted scope, not a bug.
- **Weakening `script-src` to `'unsafe-inline'`:** reopens the exact XSS surface this app's CSP was hardened to close (Sobelow `Config.CSP`, closed in `.sobelow-conf`).
- **Threading the CSP nonce through `connect_info`/`on_mount` before confirming it's actually needed** — see Pattern 3's refined finding; build the simple version first.

## Common Pitfalls

This phase's pitfalls are already comprehensively researched at the project level in `.planning/research/PITFALLS.md` (Pitfalls 1-4 apply directly to this phase; Pitfalls 5-7 belong to the already-complete Phase 01.7). Do not re-derive them — read that file. This section adds pitfalls found **this session**, specific to this phase's exact code, not covered there.

### Pitfall A: SEO-02's alt text has THREE independent render sites per component, not one

**What goes wrong:** A plan that treats "add alt text" as a single template edit will miss most of the actual DOM. Both `GameCard` and `GamePreview` render the SAME game's cover art through three independently-gated branches: (1) the `<img>` itself, (2) a hidden `<div>` sibling that becomes visible when the JS broken-image listener fires, (3) a separate `<div>` branch for the `nil`-cover-URL case. All three currently carry no accessible name at all — the `<img>`'s `alt=""` is empty and the fallback `<div>`s have no `aria-label`/text content.

**Verbatim, current state (both need fixing, plus `GamePreview.preview_body/1`'s equivalent three):**

```heex
<!-- GameCard, lib/pukllay_club_web/components/game_card.ex:63-82 [VERIFIED] -->
<img
  :if={@game.thumbnail_url}
  src={@game.thumbnail_url}
  alt=""
  loading="lazy"
  class="pk-poster-img js-cover-fallback"
/>
<div
  :if={@game.thumbnail_url}
  class="hidden h-full w-full items-center justify-center bg-base-300 text-primary"
>
  <.icon name="hero-puzzle-piece" class="size-12" />
</div>
<div
  :if={!@game.thumbnail_url}
  class="flex h-full w-full items-center justify-center bg-base-300 text-primary"
>
  <.icon name="hero-puzzle-piece" class="size-12" />
</div>
```

**Why it happens:** `GameCard`'s own moduledoc (`lib/pukllay_club_web/components/game_card.ex:27-30`, `[VERIFIED]`) explicitly *documents* the empty `alt=""` as an intentional choice — "The image's `alt` is empty because the adjacent caption heading already names the game inside the same link — repeating it would announce the name twice to a screen reader." This is a real, considered accessibility tradeoff from an earlier phase, not an oversight — SEO-02 is a deliberate reversal of it, not a blind fix, and D-10 (name + editorial, not name-only) is *more* text than the adjacent `<h3>{@game.name}</h3>` caption already provides, so the "would announce twice" objection the moduledoc raises no longer fully applies once editorial info is added — but the plan should still address it explicitly (e.g., keep the `<img>` `alt` empty since the visible `<h3>` heading already names it in the same link, per WCAG guidance that redundant alt text on a linked image next to visible identical text is unnecessary, and instead put the D-10 template on the two `<div>` fallback branches only, where no visible text exists at all) rather than mechanically stuffing the same string into all three sites.
**How to avoid:** Decide explicitly, in the plan, which of the three sites gets which text (they don't need identical treatment — the `<img alt>` and the two `<div>` fallbacks serve different accessibility purposes: one for a working image, two for a broken/missing one) and apply the fix to **both** `GameCard.game_card/1` and `GamePreview.preview_body/1` (`lib/pukllay_club_web/components/game_preview.ex:134-149`, `[VERIFIED]`, same three-branch shape, same current `alt=""`).
**Warning signs:** A screen-reader spot-check (or an axe-core scan) that only tests the happy-path `<img>` will pass while the broken-image and nil-cover fallback `<div>`s remain silent — SEO-02's own acceptance criterion #5 explicitly calls out the broken-image case, so a happy-path-only fix fails verification.

### Pitfall B: `publishers` (the "editorial" in D-10) is an array, and 26%-class sparse coverage exists elsewhere in this catalog

**What goes wrong:** D-10's template, "Portada de [Juego], editado por [Editorial]," assumes a singular editorial/publisher string. The actual schema field is `field :publishers, {:array, :string}, default: []` (`[VERIFIED: lib/pukllay_club/catalog/game.ex:37]`) — zero, one, or multiple publishers per game. A naive `"editado por #{game.publishers}"` interpolation would render Elixir's list-inspect syntax (`["Devir"]`) directly into the DOM. Separately, this catalog has precedent for meaningfully-sparse per-column coverage — STATE.md's Phase 01.3 note records "`HashtagNormalizer` only derives tags from 3 CSV columns, giving 26% catalog coverage" — so a plan should not assume every game has a non-empty `publishers` list.
**How to avoid:** The alt-text/meta-description generator must (1) join a non-empty list (e.g. `Enum.join(publishers, ", ")` or take just the first entry — a discretion call already granted by CONTEXT.md) and (2) have an explicit, tested branch for `publishers == []` that omits the "editado por..." clause entirely rather than rendering "editado por " with nothing after it. Mirror the existing pattern this codebase already uses for optional facts (`GamePreview.players_text/1`'s `nil`-returning clauses, `lib/pukllay_club_web/components/game_preview.ex:388-400`, `[VERIFIED]`) — every optional fact in this codebase is an independent `nil`-or-value function, never a blind interpolation.
**Warning signs:** A DOM inspection or Rich Results Test showing literal `["Devir"]` or `editado por` with a trailing space and nothing after it.

### Pitfall C: `sitemap.xml`'s `<lastmod>` source column has no verified runtime type — use `Date`, not raw datetime interpolation

**What goes wrong:** `games.updated_at` comes from a bare `timestamps()` call with no `type:` override, in both the schema (`lib/pukllay_club/catalog/game.ex:60`, `[VERIFIED]`) and its migration (`priv/repo/migrations/20260806234228_create_games.exs:42`, `[VERIFIED]`) — neither file specifies whether the loaded Elixir value is a `NaiveDateTime` or `DateTime`. `config/config.exs:62` sets `generators: [timestamp_type: :utc_datetime]`, but that key only affects what `mix phx.gen.schema`/`mix ecto.gen.migration` write into *newly generated* files — it does not retroactively change an already-written bare `timestamps()` call, and this migration's `timestamps()` has no `type:` argument, so this session cannot verify from source alone which struct type Postgres/Ecto actually returns.
**How to avoid:** Don't write code that assumes one or the other. The sitemap protocol accepts a date-only `<lastmod>` (`YYYY-MM-DD`) as fully valid, and `to_date/1` is defined on both `NaiveDateTime` and `DateTime` — format as `game.updated_at |> NaiveDateTime.to_date/1` semantics via a helper that pattern-matches both possible struct types, or simply call `Date.to_iso8601(game.updated_at)`-equivalent via whichever accessor is confirmed at implementation time with one `iex -S mix` check (`Repo.one(from g in Game, limit: 1, select: g.updated_at) |> then(&IO.inspect(&1.__struct__))`). This sidesteps the ambiguity entirely rather than guessing a timezone-aware `DateTime.to_iso8601/1` call that would raise a `FunctionClauseError` if the loaded value is actually a bare `NaiveDateTime`.
**Warning signs:** A `mix test` failure or a runtime crash on `/sitemap.xml` reading `NaiveDateTime.to_iso8601/1 is undefined for type DateTime` or the reverse.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Predictable/reused CSP nonce (enables an attacker to guess/replay a valid nonce to smuggle a script) | Tampering | `:crypto.strong_rand_bytes/1`, generated fresh per HTTP request, never cached/reused across requests |
| XML injection via unescaped game names in `sitemap.xml` | Tampering | Use `Phoenix.Template`/EEx's automatic escaping (or an explicit XML-escape helper) for every interpolated value — see Don't Hand-Roll |
| Reflected/stored XSS via a game's own fields flowing unescaped into JSON-LD `<script>` content | Tampering/Elevation | `Jason.encode!/1` (already a transitive dep via `phoenix`/`phoenix_html`) — JSON-encode the JSON-LD payload as a proper Elixir map through `Jason`, never string-interpolate JSON by hand; JSON-encoding also naturally escapes `</script>`-breaking sequences if done correctly (verify the encoder escapes `<`/`>` or manually replace `</` with `<\/` in the final string, a well-known JSON-in-HTML pitfall) |
| CSP directive drift during the `policy/0` → `policy/1` refactor accidentally weakening `frame-src`/other unrelated directives | Tampering | This app's own existing pinned regression tests (10-directive count, exact-string `frame-src`/`frame-ancestors`/`base-uri`/`form-action`/`style-src` assertions, all `[VERIFIED]` above) already catch this — run the full existing CSP describe block after the refactor, don't just spot-check `script-src` |
