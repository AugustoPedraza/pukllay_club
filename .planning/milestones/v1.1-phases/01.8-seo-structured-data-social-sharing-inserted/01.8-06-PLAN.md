<objective>
Close gap G-01.8-3: the Open Graph and Twitter Card tags are served with an
injected attribute sitting between the tag name and `property=`/`name=`, which
WhatsApp's link-preview crawler cannot parse — so a shared game link renders no
cover art, the wrong title, and no description on the club's single most
important distribution channel.

Purpose: WhatsApp is where club members actually pass links around. Facebook's
Sharing Debugger, Twitter's Card Validator and Google's Rich Results Test all
pass on this identical markup (tolerant parsers; Google does not evaluate
`og:image` at all), so no existing gate in this phase could see the failure.
This plan removes the injected attribute at the source and converts the phase's
own Open Graph assertions into a strict-parser contract that would have caught it.

Output: `SEOTags.seo_tags/1` rebuilt as an escaping-safe markup builder that
emits no interposed attribute; the phase's served-response assertions
re-anchored on the strict tag form; and a committed, developer-runnable
production smoke oracle that views a page exactly as a strict link-preview
crawler does.

Confirmed mechanism (verified in this repo, not assumed). `config/config.exs:31`
sets `root_tag_attribute: "phx-r"` for `Phoenix.LiveView.ColocatedCSS`. In
`phoenix_live_view` 1.2.9, `Phoenix.LiveView.TagEngine.Compiler` seeds every
template's compile state with `local_root?: true` and flips it to `false` in
exactly one place — when it descends into an HTML tag's children. An EEx
`if` block does not flip it. `seo_tags/1`'s template has no wrapping element, so
all 13 sibling `<meta>`/`<link>` tags are individually "local roots" and each is
stamped. Direct production evidence of the same rule from the other side:
`root.html.heex`'s own `<meta charset>`, `<meta name="viewport">` and
`<meta name="csrf-token">` are nested inside `<head>` and carry no stamp, while
`<html>` (the layout's own root) and `<title>` (from the `live_title` component)
both do. The config offers no per-template or per-tag opt-out — the attribute
name is read from global application env at compile time — and disabling it
globally would break colocated-CSS scoping for the rest of the app, so neither
is available.

Fix direction and the alternative that was rejected. The tags are built as
escaped safe markup from Elixir instead of from a HEEx template, which takes the
tag engine out of the path entirely. This mirrors an already-established pattern
in this same phase: `SEO.json_ld_tag/2` (plan 01.8-01) is a hand-built safe
string for the analogous reason that HEEx could not express what the tag needed.
The alternative — inlining all 13 tags directly into `root.html.heex`'s `<head>`
so they become nested children and stop being roots — is confirmed to work by
the `<meta charset>` evidence above, but was rejected: it dissolves the
component boundary and its documented crawler-visibility contract into the
layout, and leaves the fix invisible, so a future re-extraction into a component
silently reintroduces the bug with nothing in the code signalling why it must not
be done.

Scope boundary. The two latent `og:image` findings from the debug session are
recorded as explicit deferrals in Task 3, not implemented. Neither is trivially
cheap and both would require a new decision rather than a defect fix: a JPEG
variant contradicts D-08's single `og-card.webp` batch-backfill artifact and
would mean re-running the backfill over ~385 games plus deciding multi-value
`og:image` precedence; moving off the `pub-*.r2.dev` development origin needs
Cloudflare dashboard configuration plus a resolution path for the absolute
`cover_url` values already stored in the database, which `OgCard.url_for/1`
derives its object URL from. Neither contributed to G-01.8-3 — the debug session
independently verified the served image as HTTP 200, `image/webp`, 42 KB, and
exactly 1200x630 decoded (D-06/D-07 letterbox output behaving as specified).
