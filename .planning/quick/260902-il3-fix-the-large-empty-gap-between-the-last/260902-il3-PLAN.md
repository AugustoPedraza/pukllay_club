<decisions>
**D-01 — Do NOT reuse `boundary_collapse` on the catalog page.** It is a single attr governing BOTH
boundaries: it swaps `pt-8 sm:pt-20` for a flat `padding-top: 1.5rem`. That would cut the catalog
page's top spacing from 32px/80px to 24px at every width. Those top values are the documented outcome
of a closed tuning cycle (layouts.ex lines 595-614, debug session `search-right-align-mobile` cycle 5:
`pt-8` at mobile was chosen specifically to cut a photographed 80px gap by 60%, and `sm:pt-20` was
deliberately restored so desktop stayed byte-identical). REQ-2 forbids moving it, and the top-boundary
problem `boundary_collapse` was built for — the hidden `#detail-title-echo` bar's dead layout space —
does not exist on the catalog page at all.

**D-02 — Add a second, independent bottom axis (`bottom_collapse` -> `pk-bottom-collapse`), NOT a
`.pk-*` rule layered on top of `pb-20`.** layouts.ex's own comment (616-624) explicitly forbids the
latter: an unlayered `.pk-*` rule always outbids a layered Tailwind utility, so shipping both classes
and relying on that cascade-layer hazard to pick a winner "would work by accident." The discipline is
"one field, one declaration, per state," and this plan keeps it on both axes by nesting the new branch
INSIDE the existing `else`, so `pk-boundary-collapse` and `pk-bottom-collapse` are structurally
incapable of both rendering.

**D-03 — Target the value the detail page actually ships at each width: 24px above 480px, 16px at or
below 480px. Not a flat 24px.** REQ-1's literal wording asks for 24px at both widths, but the app does
not ship 24px at mobile anywhere: quick task 260902-fdm (sketch 044 winner H) deliberately retuned the
≤480px boundary to 1rem/16px, and app.css:4847-4859 documents that as "the sketch round that
legitimately reopens sketch 035's closed 24px boundary decision, but only AT ≤480px." Live measurement
confirms the detail page renders 16px at 390px. Forcing 24px at mobile would reopen a closed decision
AND leave the catalog page looser than the detail page at exactly the width the complaint came from.
Matching the detail page satisfies REQ-1's actual intent — "the same small, deliberate value already
used elsewhere in the app." Surface this as a human-judgment item in the SUMMARY.

**D-04 — Share ONE declaration with the detail page; do not duplicate the literals.** Add
`main.pk-bottom-collapse + .pk-footer` as a grouped selector on the two rules that already carry
`main.pk-boundary-collapse + .pk-footer` (app.css:4347 for >480px/1.5rem, app.css:4857 inside the
≤480px block/1rem). app.css:4766-4768 states the rule directly: "declaring separate literals per
orientation is what caused the drift in the first place." Two pages, one boundary decision, one place
to retune it.
</decisions>
