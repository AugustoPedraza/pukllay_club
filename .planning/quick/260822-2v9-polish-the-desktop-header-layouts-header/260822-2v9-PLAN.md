Thin end-to-end slice that touches both layers this task owns (the `pk-*` CSS block and
`header_inner/1`) and delivers the developer's first complaint plus the structural half of the
second. Every CSS edit below goes inside `app.css`'s existing `PK CATALOG SURFACES` block — the app's
only sanctioned custom-CSS region — grouped with the sibling rules named, and NOT inside the trailing
narrow-viewport `@media` block, which is out of scope and must stay byte-identical.

(a) Header surface (F-1). In `.pk-nav`, change the resting `background` from the `base-100` theme
variable to the `base-200` one, and in `.pk-nav.is-scrolled` change the `color-mix` first argument
from the `base-100` variable to the `base-200` variable, keeping the 94% ratio and the rest of the
declaration untouched. `base-200` is the token the shared footer surface already uses, so the header
and footer bookend the page on one surface step and nothing new is introduced into the palette. Do
not write any literal colour value, and do not add a resting bottom border — the resting-vs-scrolled
distinction stays carried by the existing border/shadow transition, which is UAT-verified.

(b) Kill the competing horizontal padding (F-4). `header_inner/1`'s `<header>` carries daisyUI's
`navbar` class, whose own inline padding is a second horizontal padding source on an aligned surface.
Below a ~1296px viewport it shrinks the header's capped inner box relative to every other
`max-w-7xl pk-gutter` section on the page, so at a real 1280px laptop width the nav edges sit inside
the shelf rails' edges. Add the `px-0` utility to that `<header>`'s class list, keeping `navbar` (its
vertical metrics and minimum row height are what the header is currently sized by, and the design
system says prefer daisyUI's own component classes). Tailwind utilities layer after daisyUI's
component layer, so `px-0` wins with no `!important`. `.pk-gutter` on `.pk-nav-inner` is then the
sole horizontal padding source, as the surface layer's gutter rule requires.

(c) Stop the brand from swallowing the row (F-2). In `header_inner/1`, the brand lockup's wrapper div
is `flex-1` and `brand_logo/1`'s own anchor is *also* `flex-1` — a nested double grow, so the brand
box expands to eat all remaining row width and shoves every other element into one lump at the far
right. This is exactly the failure `page-shell.md`'s "Header balance" section documents. Change that
wrapper's class from `flex-1` to `flex-initial` so it takes its natural width but may still shrink
under pressure at narrow widths. Do NOT edit `brand_logo/1` itself — it is shared verbatim with the
footer's left cluster, which is out of scope.

(d) Let the real filler element fill (F-2). Rework `.pk-nav-search` to grow into the leftover space
with a cap, per the sketch's validated recipe: `flex: 1 1 auto`, keep the existing `min-width`, add a
`max-width` of `22.5rem` (the sketch's validated 360px cap) and `margin-left: auto`. Leave the
narrow-viewport override of this class alone — it is in the out-of-scope media block and already
wins the cascade there by source order.

(e) Group the right-hand actions (F-2). In `header_inner/1`, replace the theme toggle's wrapper —
currently a `flex-none` div containing a single-item `ul`/`li` with a stray non-existent
`flex-column` class, a no-op `space-x-4`, and an `px-1` inset that pushes the header's right content
edge 4px inside the shared gutter — with one plain `<div class="pk-nav-actions">` holding the Sumate
CTA and the theme toggle as siblings, in that order. Move the `<.sumate_cta />` call inside it.
Declare `.pk-nav-actions` in the CSS block immediately after `.pk-nav-search`, before the crumb
rules: flex row, centred cross-axis, `gap: 0.75rem` (deliberately tighter than `.pk-nav-inner`'s
`1.5rem`, so the CTA and toggle read as one action unit rather than two loose items),
`flex: 0 0 auto`, and `margin-left: auto`. That auto margin is the universal right-edge fallback the
sketch prescribes: load-bearing on Quiénes Somos, which has neither a search box nor a crumb to
consume the leftover space, and a harmless no-op on the catalogue and detail pages where the growing
search or the growing crumb already consumed it.

(f) Tests. Extend `test/pukllay_club_web/components/layouts_test.exs`'s header describe block with
assertions that the rendered `#app-header` contains the `pk-nav-actions` container, that its header
element carries the horizontal-padding-zeroing utility alongside `navbar`, and that the brand wrapper
no longer uses the grow-everything class. Extract `#app-header` with `LazyHTML` the way the existing
capped-recipe test does, so `main`/footer markup cannot produce a false pass. Do not weaken or delete
any existing test.

Builds out from Task 1's proven skeleton to deliver the hierarchy half of the feedback (F-3, F-4).
Same placement rules as Task 1: base rules only, inside the `PK CATALOG SURFACES` block, never the
trailing narrow-viewport media block.

(a) One shared action-row height. The three right-hand elements currently render at three different
heights: the theme toggle's pill is its 44px touch-target buttons plus a 2px border on each side
(48px), the Sumate CTA is pinned to the 44px floor while carrying daisyUI's small-size horizontal
padding, and the search input takes daisyUI's medium input height (40px). 48px is the fixed anchor —
the toggle cannot go lower without regressing the 44px hit-target floor that quick task 260821-dah
deliberately established, so the other two rise to meet it:
  - `sumate_cta/1`: drop the small-size button modifier and pin the height with the Tailwind
    `min-h-12` utility, keeping `btn btn-primary` (filled primary is correct — this is the site's one
    primary conversion action, and the component inventory reserves the filled tier for exactly that).
    Keep `href`, `target`, and the `rel` value byte-identical.
  - Search field: scope a height override to header context only — a `.pk-nav-search .input` rule
    setting `height: 3rem`. Two-class specificity beats daisyUI's own single-class rule, so no
    `!important` is needed, and nothing outside the header is affected.

(b) Put the search on the row's centre line. `CoreComponents.input/1` wraps its text branch in a
`fieldset` div carrying a bottom margin. Inside a vertically-centred flex row that margin is dead
weight below the box, so the search renders visibly above the row's optical centre while the CTA,
links and toggle sit on it — a direct cause of the "unbalanced" reading. Neutralise it with a rule
scoped to `.pk-nav-search` targeting that wrapper class and zeroing its bottom margin; if the wrapper
also contributes vertical padding or a grid gap in this daisyUI version, zero those in the same
scoped rule. Do NOT edit `CoreComponents.input/1` — every form in the app shares it.

(c) Demote the nav links by colour, not by a new type size. `.pk-nav-links a` currently uses the
base-content colour at the same 600 weight as the CTA's label, so secondary wayfinding and the
primary action read as one tier. Change only its `color` to the `neutral` theme variable — this app's
sanctioned muted colour — leaving `font-size` and `font-weight` untouched. This is deliberate: the
design system caps this screen at 3 type tiers and its measured inventory already lists
`.pk-nav-links a` in the 14px/600 combo; changing the weight or size would add a 6th combo and force a
re-measure, whereas colour is the sanctioned emphasis lever. Leave the existing hover/focus-visible
rule as-is.

(d) Make the active page legible. Both header call sites already emit `aria-current="page"` on the
current page's link, but no CSS consumes it, so the active and inactive links are pixel-identical.
Add a `.pk-nav-links a[aria-current="page"]` rule setting `color` to the `primary` theme variable and
`border-bottom-color` to the same variable (the base rule already reserves a 2px transparent bottom
border for exactly this). No markup change is needed at either call site.

(e) Tests. Add assertions to the layouts test that the Sumate CTA anchor carries the filled primary
button classes and the 48px height utility and no longer carries the small-size modifier — extract
just that anchor's HTML with `LazyHTML` before asserting, so a source comment elsewhere can never
satisfy or break the assertion. Confirm the existing `app/1 external anchor safety (T-01.1-03)` test
still passes unchanged after the CTA's class string changes.
  </action>
