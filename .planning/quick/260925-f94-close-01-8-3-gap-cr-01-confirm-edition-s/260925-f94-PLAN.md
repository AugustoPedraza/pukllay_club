<objective>
Close phase 01.8.3's single verification gap (CR-01): `handle_event("confirm-edition", ...)`'s
success clause creates the edition draft and lands it in Borradores but never closes the
`Agregar juego` bottom sheet, so the sheet visually blocks the very landing the action just
produced. Add the one missing `assign/3`, and add a regression test that is provably red first.

Purpose: a staff member who pastes an already-claimed BGG id, sees the edition warning, and
confirms it should end up looking at their new draft — not at a sheet sitting on top of it.
`add_game_sheet_open` was introduced by this phase (plan 01.8.3-01, commit 537efffb), so this is
a regression this phase introduced and must not leave behind.

Output: a one-line handler fix, one new regression test, and a WR-01 disposition note.

**The load-bearing test-design fact — why the obvious regression test would be a fake.**

All FOUR existing `confirm-edition` tests submit `#add-game-sheet-form` **without ever calling
`open-add-game-sheet`**:

| Test | Line | Opens sheet first? |
|------|------|--------------------|
| "confirming an edition opens Borradores and marks the new row fresh" | 298-308 | no |
| "pasting a known BGG id warns, then Sí, agregar edición adds an edition" | 441-461 | no |
| "a double-tap on confirm-edition creates exactly one new game" | 560-573 | no |
| "a stale confirm in a second tab re-warns instead of duplicating" | 575-593 | no |

`add_game_sheet_open` is `false` from mount (index.ex:121) and the `{:existing_editions, games}`
branch never sets it true — so in all four of those tests the sheet is closed for the whole test.
**Dropping `refute has_element?(lv, "#add-game-sheet.pk-admin-overlay--open")` into any of them
would pass on the unfixed source**: a green-from-birth assertion that proves nothing and would let
this exact bug return silently. That is precisely how the suite stayed green while this shipped.

Therefore the regression test MUST be a NEW test that opens the sheet first. Precedent for that
shape already exists in the same describe block: the error-path test at lines 651-663 opens the
sheet then asserts it STAYS open, and the sibling success test at lines 670-681 opens the sheet
then asserts it CLOSED. Task 1 mirrors the latter.

## Explicitly out of scope: WR-01 is dismissed, not deferred

`fresh_game_id` never being reset (REVIEW.md WR-01) was assessed with the user and dismissed as
documented intent. **Do not "fix" it.** Task 2 records the assessment so it is not re-raised. The
reasoning, each claim re-verified live at planning time:

- `juegos.css:445-451`'s comment says the fresh row is "held for one session ... No colour beyond
  the shared surface-2 press token — a persistent tint here would read as a second, permanent
  status, which D-19h forbids." The D-19h constraint it states is on the **colour**, not the duration.
- The rule already satisfies it: `.pk-admin-juegos-row--fresh` sets only
  `background: var(--color-surface-2)` (juegos.css:449-451) — the shared press token, no distinct colour.
- `fresh_game_id` IS reset to `nil` on mount (index.ex:113), so it genuinely is per-session.
- `admin_list.js` guards re-scrolling via `lastFreshId` (lines 195-196), so persistence does not
  re-trigger the scroll.

Clearing the id eagerly would risk breaking the scroll-into-view feature it exists to serve. The
review's "directly contradicts" wording is a misreading of that comment.
