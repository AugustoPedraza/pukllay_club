## MECHANISM CORRECTION — the brief's root cause is right, its mechanism is wrong

The brief says a bare input "sends the value under `\"value\"` instead", so the `%{\"q\" => q}`
clause never matches and the catch-all no-op at `section_live/index.ex:165` "silently swallows
every keystroke". That is not what happens. LiveView 1.2.9's `pushInput` opens with a hard
guard (`deps/phoenix_live_view/priv/static/phoenix_live_view.esm.js:6001-6004`):

```js
pushInput(inputEl, targetCtx, forceCid, phxEvent, opts, callback) {
  if (!inputEl.form) {
    throw new Error("form events require the input to be inside a form");
  }
```

On a bare `<input phx-change>` the client **throws and sends nothing at all**. No event reaches
the server. Three consequences, all load-bearing for this plan:

1. The catch-all at `:165` is NOT the swallower — it is never reached on this path. It stays
   (it still guards forged/stale payloads) but must not be described as the cause anywhere.
2. **The three handlers that have NO catch-all do not crash.** `estante_live/index.ex:156`,
   `estante_live/index.ex:248` and `game_live/form.ex:316` each have exactly one clause,
   matching `%{"q" => q}`, with no fallback — grep-confirmed. Had the client been sending
   `%{"value" => ...}`, all three would raise `FunctionClauseError` and kill the LiveView. They
   don't, because nothing is sent. **Do not add a catch-all to any of them** — there is no
   payload to catch, and adding one would be unjustified scope.
3. The observable symptom is identical on all three surfaces: a dead field plus an uncaught
   `Error: form events require the input to be inside a form` in the browser console. That the
   developer saw silence rather than a crash is consistent with this, not with the brief's
   mechanism.

The diagnosis's CONCLUSION and the FIX are both unaffected and correct. Only the narrative
changes — and it must change, because a comment written from the brief's version would be
wrong in the repo forever.
